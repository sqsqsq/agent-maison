# UX 行为说明取用指引

## 蓝图事实发现与写作前的取用顺序

有界面行为的请求才提取 UX。范围取本次涉及的屏、元素、条件及直接受影响的跨页关系。只改一个元素时，只补该元素及确受影响的引用，保留其他标识和裁决。非 UI 请求沿原流程，显式提交的文件可作为普通需求材料。

1. **找可复用稿**。优先用显式提供的 `*.ux.yaml`，否则从本次原始需求所在目录查找，并按需求、屏幕 ID 和流转引用选用。多屏稿读取流程、所涉屏及其依据与裁决。受管作者也检查本次已签蓝图目录的 `ux/`，有效草稿可接着用。只补缺项或需求变更。上游原稿保持只读，有冲突时保留两方依据与待决问题。
2. **缺稿时先提取并实际落盘**。从本指引所在目录打开[屏幕模板](../templates/screen.ux.yaml)和 [Schema](../schema/ux-behavior.schema.json)，涉及多屏流转时再读[流程模板](../templates/flow.ux.yaml)。按下方规则从原始需求和实际可用设计提取。受管初设在当前作者会话先写出 `<本次已签蓝图目录>/ux/*.ux.yaml`，然后再写蓝图。独立调用使用调用者指定的目录。单屏或弹层可以只交一份。多屏各写一份并用流程文档集中登记跨页动作、携带数据及分支。资料不齐时照样交回有依据的部分和待决项。
3. **回读并消费**。交回前用本地已有的 YAML 工具实际解析落盘稿，有 Schema 校验能力时一并检查。按各稿所在目录打开其所引文件，修正语法和链接。没有现成解析工具时可用[离线看图页](../viewer/index.html)读取 YAML，如实说明 Schema 是否实测。再从复用稿或刚落盘的稿中读取相关 `屏幕ID.元素ID`、行为及待决项，把它们带入现有蓝图用例、运行流程和验收。保留原需求出处，代码入口、设备定位和技术契约沿既有字段。PRD 明示的规则可形成验收，推断注明依据。同一待决项在流程步骤、用例和验收中保持待决，取得有依据的裁定后才写为确定步骤或预期。

## 按本次作者实际收到的材料提取

每条实质规则用 `evidence` 关联 PRD 条款、设计节点、观察区或产品决定。来源路径相对于声明该来源的 YAML，屏幕可以继承流程中的来源。动态列表或选项组复用一条行模板。

逐张核实当前作者确实收到图像并能定位事实，才写 `visual.observation: observed`。在 `visual.source` 注明图源，可用 `bbox_format: normalized_xywh` 和原图左上为原点的 `[x,y,w,h]` 标出可定位元素。截图中的勾选态等以元素 ID 为键写入 `visual.depicted_state`。业务默认值、离开当前界面时如何处理、返回落点与选择保留另按需求和产品裁定核对。单帧截图和技术惯例仅用于观察或提出带依据的推断。仍无产品依据的规则写 `status: open`，列出待决问题。

图像未送达、路由无视觉或读取失败时，在来源清单和 `visual.source` 保留图源，写 `observation: unobserved` 和可选 `reason`。省略元素截图坐标、原图尺寸和截图示例状态。本次提取的 `evidence` 和 `copy_ref` 不得引用未观察的图源 ID，包括 `图源ID:区域`。可从 PRD 与结构化设计节点继续提取；结构化设计的几何和变体写到对应 `design` 节点及设计源。只能由未观察的图确认的内容留作缺口或待决，例如协议全名与逐字文案。

复用上游稿的观察时，保留其原始出处。本次稿引用上游 UX 文件及其相应元素或区域，并记录本轮实际读图情况。输入路径、文件名和适配器声明仅说明材料或能力存在。上游产品与 UX 负责定稿。外部 provider 供料仍走既有 `requirement-source-materialization@1`，M7 校验在材料生成之后执行。
