## 实施结果

1. 独立产物写手与普通作者共同消费当前处置，使用既有 `workInput.evaluation`、真实交回原件及 `completionProgressFromHistory` 判断改善、往复与可续暂停。负责人从产物 domain 和既有执行角色派生，移除 `needsReviewWriter` 的阶段及检查 id 特判。检查自己的报告不构成新工作，真实业务输入变化仍能继续；未知输入不假判无进展。
2. 一轮检查中局部暂停的写手先让其它可执行职责完成；若剩余检查不能执行、repair 又全属已暂停职责，沿原 `no_progress_guard` 等待，不再空转。这里只使用本轮临时集合，没有持久状态、次数或新停机原因。
3. `design_refs` 仅保存作者的交付及责任选择。删除接受、设计修订及修复发布中的依赖补写；依赖闭包按需派生并检查未知项、blocker 和契约准入。显式目标的选型决定仍须作者选入。投影和 `ownersForAddress` 继续消费同一显式选择，依赖后来增加交付内容不会自动扩大范围或归属。作者指引、现行规格同步；存量 CU 不静默删引用，仍经原设计/CU 内容修订。
4. `conclusion_with_verdict` 的生产输出携带真实报告路径，报告缺结论交独立写手；产品负面裁决仍由原 `negative_verdict_closure` 保留，不能靠改报告格式洗掉。

## 顺带建议的边界

非 knowledge 的组装覆盖缺口自动派回设计修复，本批**未交付**。尝试的派发扩展及其测试已完整撤回，保留原生产行为；不能把“可派发、可发布一次”写成 A10 全链闭环已完成。

已核根因：当前组装仅将 knowledge 缺口交回设计事务，其它缺口等待。已有设计事务的进展比较在发布后结束；原组装缺口若仍存在，发布导致指纹变化，直接扩展派发可能反复开事务并重施工。这个跨发布边界同样需要覆盖原 knowledge 分支。另有 CU 已完成但组装要求补施工证据，以及真正需要新增 CU 的形状，不能冒充已有 CU 内容修订已经解决。

后续最小范围：把原组装检查、实际送达作者的反馈与发布后重新检查接入既有共同完成评估；先证明作者确实收到组装缺口，再验证修复、同问题再现的可续暂停及条件变化后的恢复。沿原设计事务、CU 修订、ready set 和 GoalPhaseRuntime 完成，不新增计数、状态或第二完成循环。真实 provider、授权及已有 CU 的证据问题保留各自责任，不能全部改称设计缺口。
