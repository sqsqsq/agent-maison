# 无人值守设计修复子契约

适用：goal run 无人值守运行、设计权威门报了 **B1** 类阻断、且 `framework.local.json` 有预授权 `design_repair.unattended_b1: true` 时，框架派出的那一次"编写修复"调用。有人在场时由会话里的设计 owner 照 `/component-design` 修，不走本契约。

## 你能做什么

- **只做 B1 类修复**：修复简报里列出的检查与原因码，在既有授权内、依据明确的改正。
- **只依据既有事实**：蓝图里已有的原文、已登记的外部输入（discovery 事实、需求与契约引用）、修复简报里的依据。不推测、不补新事实。
- **只写草稿文件**：提示词里给出的草稿蓝图是唯一允许写入的文件。
- **只改简报定位到的位置**：修复简报每条都写明"只许改的位置"（哪个设计目标的哪个字段）。草稿里只有这些位置可以与原蓝图不同；任何别处的差异——包括同一节点的另一个字段、另一处 `contracts.files`、决策或其它节点——框架逐字段比出来就判越权，**本次修复作废、不发布**，失败事件写明越权的位置。

## 禁止

- **不得改任何决定**：`decisions_and_gaps` 里的决策、缺口与处置原样保留；不新增、不删除、不改结论。
- **不得扩范围**：不新增视图节点、关系、契约文件或授权写集；不改 discovery 事实与来源指纹。
- **不得改 `revision` 与修订依据（根 `provenance`）**：新 revision 号与修订依据由框架登记——`revision` 与根 `provenance` 的 `source_kind`、`source_ref`、`source_revision`、`observed_at`、`extraction_method` 五个字段由框架覆盖，你写的值不作数；根 `provenance` 的其余字段（如 `evidence_strength`）保留并照常校验，改坏会导致本次修复不发布。
- **不得写 `review_summary.admission`**：准入由机器从校验结果派生并写回；改了按自报处理，**本次修复作废**。
- **不得写质询结果（`review_summary.questioning`）**：质询由与你隔离的另一次调用重新产出；改了按自报处理，**本次修复作废**。
- **不得写草稿之外的任何文件**：含 canonical 蓝图、Change Unit、需求、契约、产品源码、`framework.local.json`、蓝图 `source_ref` 引用的任何文件（即使在 `context/`、`reports/` 下），以及本 run 与历史 run 的事件、manifest 等运行记录。框架在调用前后核对这些文件，改了即按越界写入违规处置：**本次修复作废、本 run 终止**；被改的运行记录（事件文件）由框架整份写回为"调用前的内容 + 框架本次自己写入的行"，工程文件框架不替你还原。
- 被允许的那个字段内部，内容是否忠于原文框架不做机器比对，由独立质询把关；改动若让蓝图通不过校验或准入，同样不发布。

## B1 原因码的修法

| 原因码 | 现象 | 修法 |
|---|---|---|
| `authority_content_not_machine_structure` | 蓝图里某个设计节点的机器内容（如 `acceptance`、`contracts`、`use_cases`）被写成了一段文字 | 按这段文字的原意改回机器结构，只用原文里已有的内容；原文表达不出的部分不要补，留给修复后的门禁报出来 |

施工映射属于 plan 的 Feature contracts.change_unit；缺失、过期或冲突回 plan，不由 B1 删改蓝图旧映射或复制版本化设计节点。

## 评审说明的定向复核

事实修复可能使可选 `review_summary.reader_guide` 的 source_digest 失效。按本次事实变化与 guide.source_refs 定向阅读说明；只有修复简报明确允许相应 guide 位置修改时，才可在**同一授权草稿**内必要改写。公开摘要命令只读取 canonical，不读取修复草稿；框架随后登记的根 provenance（包括 observed_at）也参与摘要，会使发布前摘要失效。当前公开 B1 流程保留原说明摘要，不为盖章扩大允许位置，也不把 canonical 的摘要填进草稿宣称说明已更新。

发布后的 renderer 会标“评审说明需更新”，展示当前事实与完整参考；这不改变原恢复判定、不停止 run。后续由设计 owner 复核已发布 canonical，再按 [P1 摘要指引](app-component-blueprint-workflow.md#摘要渲染与读成品) 记录摘要与读成品。你不写 canonical 文档，框架发布/接受/调和后的自动物化仍是确定性生成，零新增模型调用、不自动写说明或盖摘要，不加独立阅读循环。

## 之后框架做什么（供理解，不需要你做）

1. 核对你的调用没有改草稿之外的文件、没有改准入与质询结果，草稿只在简报定位的位置与原蓝图不同。
2. 作废草稿里整份旧质询结果，登记新 revision 与修订依据，把既有派生结论标为 stale，按校验结果派生并写回准入（此时未过）。
3. 派一次与你隔离的独立质询，按必答范围重新产出质询结果；再派生准入并做完整校验，通过才发布。
4. 发布只替换蓝图文件一份；发布后在同锁内调和 CU 指针并由框架重建人读文档，然后重跑原来那道门。文档失败不改变 recovered/探针判定，不回滚设计；事件披露最终 review_document、来源缺口、重建命令和实际写入 files，review_projection_stale 按最终结果计算，内部已刷新且外层未重写的路径仍保留。修复 agent 仍只写草稿。发布成功不等于修复成功：门仍不过时按新状态停机并披露。
5. 每个停机签名只尝试一次。
