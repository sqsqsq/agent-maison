agent 如实承认测试未跑成功，没有伪造 PASS。判定：**宿主验收未通过，交付未闭环。**

## 2. 根因

**3.1.0 放开了"只做一件事"的路径，但这条路只有出口（专项入口能跑），没有引路。** 3.0.0 时所有请求都进整条流水线，每一步由框架牵引，缺口一直被盖住。

| 层 | 事实 | 后果 |
|---|---|---|
| 入口判类 | AGENTS 模板 §4.0 以"是否拟改变行为"划分正式/非正式；"补测试"不改行为却有验收责任，两头不靠 | agent 按"非正式维护、直接完成"处理，跳过了"按什么标准算对"的判断 |
| 依据责任 | UT 技能写着"新增断言必须有授权预期，characterization 仅证明现状"，但只是散文；request 分支里 `checkRequestTests` 自身只产出 `request_test_execution` 一项结论（同轮另有输入项检查与 provider 的原生执行项，均不涉及断言依据） | 现状断言被当成正确性通过来呈现，没有任何东西接住"依据是哪条要求" |
| 能力边界 | UT 专项 provider 只认已配置模块的 `src/ohosTest/`，限制只在执行时抛错；技能的独立调用段落未提落点、未提载体 | agent 写测试时无从得知；库模块无测试载体时也不报能力缺口 |
| 工具链 | 全仓没有"单职责/非正式维护的编译与测试走框架执行器、不裸调工具"的指引；toolchain-probe 的建议只在探针运行时出现 | agent 裸调 hvigor，丢掉框架派生的环境，随后归因过早 |
| 流程 | P1–P8 的验证都是"按正确姿势调用时机器行为对不对"；从未验证"给 agent 一句自然语言，它能否走到正确姿势" | 首次宿主实跑才暴露 |

## 3. 需求条目

### R1 入口判类：分开"本轮改动范围"与"验收语义"

- AGENTS 模板 §4.0 的需求路由必须先后回答两个问题：本轮要动什么（范围）；按什么标准算对（验收语义）。"不改实现"只回答前者。
- 判类前先查已有要求与设计（既有 acceptance、蓝图、catalog、约束知识）。已有依据即复用；涉及新增或变更预期才进入设计职责，再决定复用、修订还是新建蓝图。不得因"不改实现"跳过该判断，也不得因"补测试"强制新建蓝图。
- 只有查完仍存在影响断言或交付的语义缺口时才向用户澄清，且只问该缺口。
- 验收：模板 smoke 断言 §4.0 含两步判断与"先查依据再问"的表述；`project-entry.md` 同步；触发事件那句原话在 §5 宿主重跑中触发依据核查而不是直接落笔。

### R2 预期来源：新增断言必须落实依据，现状测试如实标注

- UT 技能的独立调用段落把"新增断言必须有授权预期"写成可执行步骤：写测试前逐类断言登记预期来源（指向具体要求/验收/约束条目），或明确标注为 characterization（仅记录现状）。
- 两类结果不得混称"正确性通过"。依据要求应当失败的断言保留失败及其原因；在"不改实现"的授权下不得为跑绿调整期望。
- UT 专项请求 JSON 已有 `requested_result` / `targets` / `allowed_test_writes`；预期来源的登记位置由 plan 定（优先复用既有字段或 facts，不新增 schema 体系）。request 检查至少如实呈现"本次哪些断言是 characterization"，不把它们计入正确性结论。
- **裁决（2026-09-17）**：明确标注为 characterization 的断言是合法请求（用户可以只要"记录现状"），不得因此判 FAIL；结果里单列"现状记录 N 条"，不与"按要求验证通过 M 条"混报。**只有既无预期来源、又未标注 characterization 的新增断言才按 BLOCKER 处理。** 宿主上次那种"全部是已标注的现状断言"的请求，改后仍可通过，但呈现为"现状记录"而非"正确性通过"。
- 不为专项测试新增 verifier 环节。
- 验收：专项 UT 夹具中，带来源的断言与 characterization 断言在结果里分开呈现；缺来源且未标注 characterization 的新增断言被指出；既有 feature 主体的 UT 行为不变。

### R3 能力边界事前告知，能力缺口如实报告

- review / UT / testing 三个已有专项技能的独立调用段落写清：需要的输入、测试或报告的合法落点、当前 profile 实际能执行什么。hmos UT 写明只执行已配置模块 `src/ohosTest/` 下的 Hypium 用例；testing 写明用例须含可执行步骤与预期结果。
- 目标模块没有测试载体（例如无 ohosTest 的 HAR 库模块）时，如实报"profile 能力缺口"并停在该处，不得仿照其它目录假装接通，也不得用其它模块的测试通过代替。"无载体"的判定依据用既有事实：`<模块>/src/ohosTest/` 目录与其中的 `module.json5` 是否存在（与 `ut-host-impl` / `hdc-runner` 现有判断同源），**不用**工程根 build-profile 的 targets 语义（宿主实测该字段可缺省而编译照常成功）。
- 为了能跑测试而**新建测试载体或修改模块构建配置**（新增 `src/ohosTest/`、改 `build-profile.json5` 的 targets 等），属于超出"补测试"字面范围的工程改动：技能须要求 agent 先向用户说明这项改动及其原因，得到认可后再做；不得静默完成。这不是新确认点机制，沿用既有"范围外改动先说明"的约定即可。
- 专项入口的 `--prepare-request` 阶段就应暴露落点不兼容（当前只在执行阶段抛错），让 agent 在写测试前得到结论。
- 验收：`--prepare-request` 对 `src/test` 目标与无载体模块给出明确 gap；三份技能文本含上述告知；hmos 与 generic 两个 profile 的行为各有用例（generic 能力关闭时如实报未启用，现状保持）。

### R4 单职责与非正式维护的编译/测试走框架执行器

- AGENTS 模板与 coding / business-ut 技能明确：任何需要编译或跑测试的校验，经框架执行器（专项入口或阶段入口）执行，不直接调用 hvigor 或宿主自带脚本；理由写明（执行器从 `framework.local.json` 派生工具链环境）。
- 失败诊断先看执行器实际解析出的 SDK 路径与构建日志，再下结论；确有外部阻塞时准确报告哪些步骤未执行。不得仅凭一行报错归因"本机环境问题"后结束。
- 非正式的代码维护需要编译校验时的具体入口由 plan 指明（复用既有入口，不新增 CLI；若现有入口确实无法承接，plan 说明缺口与最小补法）。
- **裁决（2026-09-17，同日按代码事实更正）**：无 Feature 的入口其实存在——`--correction-init` / `--adhoc-correction` 修正链在 Feature 参数校验之前分流，no-feature 分支会调编译检查；但该链的 adhoc 上下文不带 `contracts.modules`，`checkCodingCompile` 读到空模块清单即返回 BLOCKER FAIL，**走不到真正的编译**（实跑复现）。此外它强制修正三问语境、要求 `--correction-request` 原文、写修正状态、报告落发布件目录内，不适合当普通维护的即时编译校验。因此本轮不把它指定为 R4 入口，也不在本需求内修它（另行立项）。本轮不补：有测试载体的模块走 UT 专项入口（编译是该链的一部分）；只想确认工具链走既有的工具链探测；两者都不适用时如实报告"框架当前不提供即时编译校验"。"只编译不执行"的形态另行裁决，plan 记为放弃的准确性。
- 验收：模板/技能 smoke 含上述指引；plan 指明的入口在无 `DEVECO_SDK_HOME` 环境变量、仅有 `installPath` 的夹具环境下能派生出工具链环境（复用既有 hvigor-runner 单测面即可，不要求真机）。

### R5 spec / plan / coding 的单职责终点（补 P8 欠账）

- 三个技能补独立调用段落：只做本职责、在请求终点停止、不冒充 Feature 整体完成、不自动追加后续阶段。
- 补 P8 需求 §7 欠的三条验收，各一条：spec-only、plan-only、coding-only 请求经 P8 已交付的范围计算得到单阶段链、`completion_target=request`，完成时不生成 Feature completion。
- 不为这三个阶段新增无 Feature 的 request CLI（P8 需求 §7 已明确不做）。
- 验收：三条用例名进入 plan 追溯矩阵并真实存在于仓库；技能文本 smoke。

### R6 验证方式：把"自然语言到正确姿势"纳入验收

- 本需求的每个条款都要回答"agent 读到的文字是否足以走到正确入口"。模板与技能的关键指引用 smoke 断言锁住（存在性与关键措辞），避免后续改文档时悄悄丢失。
- plan 的追溯矩阵同时列出 §5 宿主重跑的观察点，逐条对应 R1–R4。

## 5. 收口标准（宿主重跑）

内部测试与 smoke 全绿后，由用户在宿主用**同一句原话**重跑。**重跑前提**：宿主先回到事故前状态——撤回工作区里未提交的 CommFunc 测试载体、`build-profile.json5` 改动、`doc/requests/` 与 `doc/reports/` 下本次产物（均未提交，由用户在宿主侧执行）。这样同一句话从同一起点出发，"无载体如实报缺口"这个观察点才验得到。观察点：

| 观察点 | 对应条款 |
|---|---|
| agent 先核查已有依据（catalog、SEC-01、既有验收），指出"短输入预期无书面依据"，只就这一缺口澄清或明确按 characterization 处理 | R1、R2 |
| 写测试前确认框架能执行的落点；发现 CommFunc 无测试载体时如实报能力缺口，不写到无法执行的目录 | R3 |
| 需要编译或跑测试时经框架入口，不裸调 hvigor，不建议用户跑宿主旧脚本 | R4 |
| 全程遵守"先不改实现"；结果如实区分"记录现状"与"正确性通过"；未执行的步骤明确列出 | R2、R4 |

仅改入口文字或仅过框架内部测试，不足以宣布问题解决。宿主重跑由用户触发；结果记入 plan 实施记录。
