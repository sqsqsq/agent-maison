# 需求文档：按任务义务自动确定执行范围（动态阶段编排）

> 文档性质：**需求输入**，交主干（main / 3.1.0 蓝图线）AI 做方案设计与 plan。不是施工图，不含实现步骤。
> 起草日期：2026-09-07。起草分支：Br_release_3.0.0。事实核对基于本地 `Br_release_3.0.0` 与 `origin/main`。
> 关联记忆/原则：效率优先、简单优先、减法优先；不做 A/B，靠宿主实跑迭代；用户不承担框架内部仪式。

---

## 1. 一句话目标

用户只说明要完成什么。Maison 根据任务的**义务**（这次改动必须交付什么产物、必须证明什么）和**已有事实**（请求、蓝图、既有契约、代码、既有证据），自动算出本次需要执行的阶段集合与顺序。用户不需要知道 lite/full，不需要选择从哪个 Skill 开始，不会被要求为不适用的阶段补造空壳产物。

---

## 2. 触发事件（宿主工程真实案例）

宿主工程集成 Maison 最新版后，做了一个 RDB（关系数据库）层的改动。以下 1、4 两条来自用户转述的宿主 AI 原话；2、3、5 是本文基于原话与框架代码的**推断**，尚未用宿主的 acceptance / test-plan / 报告核实：

1. 先做 UT，发现问题，AI 重写 RDB UT，在 ohosTest HAP 中执行，67 条用例全部通过。
2. （推断）流程推进到 testing（真机）阶段。AI 手上没有需要真机验证的内容，但阶段要求交付 6 章节测试计划、7 列 TC 表、`device_test.run` 产出 trace。
3. （推断）AI 把 UT 用例改写成 TC 填进测试计划，执行通道标为 `manual:data_injection`。
4. harness 报三条 BLOCKER：缺 `context/facts.md`、缺 Hylyre trace、`device_case_contract` 不通过。
5. （推断）AI 围绕这三条 BLOCKER 补材料，越走越偏，最终向用户求助。

harness 的三态设计（manual 永不算 PASS）生效了，没有洗绿。代价是一整轮无效的真机准备与返修。

## 3. 根因分析

### 3.1 直接原因（testing 这一站内部）

| 层 | 事实 | 后果 |
|---|---|---|
| 阶段强制 | full 轨链写死为 `spec → plan → coding → review → ut → testing`（`workflows/spec-driven.workflow.yaml:12`），无按条件跳过某一段的字段 | 零设备义务的 feature 也必须进 testing 并交付非空产物 |
| 门禁位置与级别 | `plan_references_unit_layer_ac`（`harness/scripts/check-testing.ts:1568`）能识别"测试计划引用了 unit 层 AC"，但 severity=MINOR，且调用点（约 6013 行）在设备跑机门禁（约 5956 行）之后 | AI 先看到"缺 trace"大红字，最有诊断价值的提示排在末尾且不阻塞 |
| 谓词粒度 | 该检查是"引用了任一 unit 层 AC 即命中"，不区分"全部引用都是 unit"与"unit 与 device/both/NFR 混合引用"；`extractTestCaseACRefs` 还会过滤掉 NFR-* 引用（`check-testing.ts:1332`） | 升级严重级别时无法直接用，混合引用的合法端到端用例会被误伤 |
| 标签缺失（已有门禁） | `acceptance_ut_layer_complete`（`check-acceptance.ts:90`）对缺失/非法 ut_layer 判 BLOCKER，spec/plan/ut/testing 都跑 | 不是缺口；本需求与 R8 都不得把"未声明"视同 unit |
| 菜单误用 | `manual:<gap_class>` 是六个固定枚举，解析器只校验枚举合法性，不校验"这条 TC 的 AC 是否本来就不该出现在真机计划里" | AI 挑了字面最像的 `data_injection` |
| 散文规则 | "ut_layer=unit 不再生成用例"只写在 SKILL 散文里，无机器门禁背书 | 散文对抗"必须交付物"的机器门禁，必输 |

### 3.2 上层原因（编排模型本身）

- **"轻量"不是算出来的，是从两条固定轨道里二选一。** lite 轨 = `change → coding → exit`，full 轨 = 六段。schema 只有"哪条轨包含哪些阶段"（`tracks` / `auto_chain_by_track` / `requires_by_track`），没有"这个阶段对这个 feature 是否适用"。
- **轨道选择依据与义务无关。** `change-rules.yaml > track_scoring` 只看规模维度（module_loc / scope_breadth / cross_layer / new_api_surface / dependency_fan_out）；一票否决只看 pixel_1to1、跨模块、goal 模式。完全不看"有没有设备层验收""有没有用户可见行为变化"。
- **goal 模式一律 full。** headless 需要确定性与可回放，当时的解法是禁止 lite，而不是"算一次后冻结"。
- **轨道是用户可见的仪式。** change-lite 作为一个 Skill 跳板呈现给用户，要求用户理解并确认轨道。这与"用户不承担框架内部仪式"的原则相悖。
- **唯一的阶段级开关粒度错误。** `device_test.run` 的 SKIP 是 profile 级（`profiles/generic/profile.yaml:25` SKIP，`profiles/hmos-app/profile.yaml:23` BLOCKER），一刀切整个宿主，不能按 feature。
- **历史决策背景。** plan d4a7c1e8 决策 19 明确"不做隐式推导，非 full 轨必须显式声明链"。这是为确定性有意选的，代价就是今天的问题。本需求不是推翻确定性，而是把"确定"从"预先写死"改为"入口算一次后冻结"。

### 3.3 为什么"在某一行过滤掉 testing"不够

阶段存在的理由是它产出下游门禁要消费的产物：spec 产出 acceptance，ut/testing 的追溯门吃它；plan 产出 contracts，coding 门吃它。`skills/feature/coding/contract.yaml:20` 在 full 轨把 plan/contracts/acceptance 设为 `on_missing: fail`。只从链里删阶段而不重新安排它承担的责任，下一站会因缺文件报错，AI 又被逼回去补材料。所以本需求的核心不是"跳阶段"，而是"按义务决定需要哪些产物，阶段随之而定，且被省掉的阶段其信息义务由已有事实承接"。

## 4. 现状盘点：可复用的既有机制

以下机制已存在，新方案应复用而非另造。

| 机制 | 位置 | 可承接什么 |
|---|---|---|
| 轨道链声明与拓扑解析 | `workflows/spec-driven.workflow.yaml`；`harness/scripts/utils/runtime-policy.ts` `workflowFeaturePhases` / `trackOrderedPhases`；`phase-transition-policy.ts` `resolveAutoChain` | 从"按 track 过滤"推广为"按 feature 计算的义务集过滤"，拓扑排序逻辑不变 |
| feature 级轨道声明 | `harness/scripts/utils/feature-track.ts`（feature.yaml > track）；`runtime-policy.ts` `resolveFeatureTrack` | 已有 feature 级持久化位置，可扩展为"本次计算出的执行范围" |
| capability 适用性 | `skills/feature/*/contract.yaml` 的 `applicability_provider_id` + `on_missing: fail|prune`；`harness/scripts/utils/capability-resolution.ts` `resolveApplicability`（`applicability.always` / `applicability.ui` / `applicability.pixel_fidelity`） | capability 级"不适用即剪枝"已成型，需要把同一思想上提到阶段级，并让 `on_missing` 由义务决定而非由 track 决定 |
| 验收分层 | `acceptance.yaml` 的 `ut_layer ∈ {unit, device, both}` + `device_focus`；`acceptance-layering.ts` `isUnitUtLayer` / `isDeviceUtLayer` | "是否有设备证据义务"的直接输入 |
| 执行通道三态 | `execution-channel.ts`；`openspec/specs/harness-gates/spec.md` "Execution channels resolve to a machine-proven tri-state" | 解决"计划内某几条用例机器测不了"，与本需求互补，不重叠 |
| 轨道评分与一票否决 | `specs/phase-rules/change-rules.yaml > track_scoring`；`skills/feature/change-lite/SKILL.md` | 评分维度可作为义务谓词的输入之一；一票否决是义务判定的雏形 |
| 回修与回退 | goal-phase-runtime 的 backtrack / must_fix / correction 链路 | "新事实出现后补回阶段"应走这条路，不重新规划全流程 |
| origin/main 蓝图 | `harness/scripts/utils/blueprint-*.ts`、`harness/schemas/app-component-blueprint.schema.json`、`docs/concepts/component-assets.md` | 蓝图区分 changed development 与 verified_unchanged，记录 decisions、verification_refs、current_slice、gaps、admission。它是"判断依据从哪里来"的最佳来源，但目前不做编排决策 |
| Code Graph | `docs/concepts/code-graph.md` | 模块功能索引。一次改动碰了哪些节点、是否碰 UI 节点，可作为"是否有设备/视觉义务"的输入 |

## 5. 期望的最终形态

### 5.1 用户视角

- 用户说明要做什么。系统回一句话说明本次执行范围与理由，例如："需求与既有契约已明确，本次直接修复实现，完成 review 与相关 UT；无设备验收义务。"
- 用户不接触 lite/full、不选择入口 Skill、不为不适用阶段补造产物。
- 减少框架内部的流程选择类确认（轨道、入口 Skill）；既有授权边界与确认点（真机执行、架构 DSL 变更、新增依赖边等）原样保留并复用，已有授权不重复确认。本需求不改授权模型。
- 用户只要求讨论或设计时，范围就止于讨论或设计。

### 5.2 系统视角

1. **义务模型。** 每个阶段对应一组"产物义务"。入口对每项义务回答三个问题：这一步负责解决什么问题？本次有没有这个问题？已有材料是否已经解决了？三问的答案决定阶段是否进入本次执行范围。
2. **判断依据。** 有蓝图时以蓝图为正式需求依据（changed / verified_unchanged / decisions / verification_refs / current_slice）。无蓝图的情形仅限主干既有规则允许的合法入口（维护、存量修复、机械改动等），此时以用户请求 + 既有契约 + 代码事实为依据；**本需求不改变蓝图准入规则**，正式需求仍按主干要求走蓝图，如需调整准入须另列需求。语义判断融入 AI 本来就要做的阅读理解，可确定部分（范围、依赖、证据复用）由脚本计算。**不在每一步前额外调用 AI 决定下一步。**
3. **按工作单元决定。** 同一份蓝图下不同工作单元可以有不同执行范围（一个只改数据库，一个涉及页面交互）。
4. **责任承接。** 省掉的阶段，其信息义务必须有明确来源：来自用户请求、蓝图、既有 contracts / acceptance 或代码。下游输入契约的 `on_missing` 按义务判定，而非按 track 写死。
5. **已确定的范围稳定复用。** 入口计算出的执行范围写入 run manifest / feature 级记录。自动执行、交互提示、恢复任务、verifier、最终完成判定使用同一份结果。信息补齐或事实变化时，只更新受影响的部分（见第 6 条），不要求入口预知一切。跳过原因记入已有运行记录，不产生空壳产物。
6. **新事实才修正。** 初始判断可以被新事实推翻（例如原以为只是内部实现，实施中发现必须改接口，则补回设计义务）。修正走既有回修/回退路径，不每轮重新规划全流程。**某项测试失败不得反向改判为"不适用"。**
7. **确定性保留。** goal / headless 模式不再靠"禁止 lite"保证确定性，靠"冻结的执行范围 + 既有回放机制"保证。

## 6. 需求条目

每条含验收标准。编号供主干 plan 引用。

### R1 义务谓词表

定义一张机器可读的义务谓词表，至少覆盖：

| 义务 | 触发条件（示例，主干细化） | 输入来源 | 对应阶段 |
|---|---|---|---|
| 需要新的验收条目 | 请求带来用户可观察的行为变化，且既有 acceptance / 蓝图未覆盖 | 请求、蓝图 changed 视图、既有 acceptance | spec |
| 需要契约/设计决策 | 请求引入新接口面、跨模块影响、模块拆分或实施顺序待定，且既有 contracts / 蓝图 decisions 未覆盖 | 请求、蓝图 decisions、既有 contracts、Code Graph 影响面 | plan |
| 需要实现 | 请求要求改变代码行为或结构（"只跑测试""只做 review""只讨论"不触发） | 请求 | coding |
| 需要代码审查 | 本次产生了代码变更 | diff | review |
| 需要单元证据 | 变更触及业务逻辑，或存在 unit/both 层 P0/P1 验收/边界 | acceptance ut_layer、diff 范围 | ut |
| 需要设备证据 | 存在 device/both 层 AC 或 BD，或存在需真机验证的性能/NFR 项，或蓝图/Code Graph 显示变更影响用户可见行为 | acceptance ut_layer、acceptance.performance、蓝图 UI 维度、Code Graph | testing |
| 需要视觉保真证据 | fidelity SSOT 定档 pixel_1to1（复用 `applicability.pixel_fidelity`） | fidelity SSOT | testing 视觉轴 |

两条原则：

- **线索不是决定。** 文件位置、改动规模、节点类型是判断线索；执行范围由实际请求、行为影响和未满足的义务决定。触及 UI 文件的机械改动（改名、格式化）不因此必须跑机。
- **未知不等于没有。** 义务判为"无"必须基于完整、有效的适用输入（acceptance 存在且分层合法、蓝图/Code Graph 对该范围有效）。输入缺失或不完整时义务为"未知"，先补足判断依据，不得裁掉阶段。

验收：判断规则同源（一处定义，各入口复用）且可单测：harness 单测可对给定输入集断言输出的义务集合与阶段集合，含"输入不完整 → 未知，不裁剪"的用例。具体承载形状（文件、模块）由主干设计。

### R2 统一入口

执行范围在需求进入时计算一次。有蓝图时入口在蓝图工作单元划分之后、按单元计算；无蓝图时在请求理解之后计算。

验收：交互模式与 goal 模式走同一计算函数；计算结果与理由可在 run manifest / feature 记录中读到；用户看到的一句话说明由该结果投影生成。

### R3 下游输入契约按义务判定

下游阶段对上游产物的输入要求按义务判定，而非按 track 写死：义务不存在的产物缺失不阻塞，义务存在的产物缺失才阻塞。省掉产出阶段时，可以复用**等价信息**（既有 contracts / acceptance、蓝图中的决策与验收内容），并在计算结果中显式登记来源；来源必须能解析到消费者所需的实际内容，登记几个引用不等于满足义务。必需信息缺失仍须补齐。具体如何调整 `contract.yaml` 的 `on_missing` / `tracks` 语义由主干设计。

验收：一个"直接 coding"的 feature，coding / review / ut 门禁不因缺 plan / contracts / spec 报 BLOCKER；一个"有设备义务但跳过 spec"的 feature，testing 追溯门能从登记的承接来源读到验收条目。

### R4 已确定范围稳定复用，执行与完成判定同源

计算结果写入 run manifest（goal）与 feature 级记录（交互）。verifier、恢复、backtrack、最终完成判定、`phase.next_step` 话术全部读同一份结果。跳过的阶段不产生任何产物文件，只有一条带原因的记录。已确定的范围在没有新事实时不重算。

验收：跳过 testing 的 run，完成判定不再要求 test-report；恢复中断的 run 不重新计算范围；verifier 提示中不出现被跳过阶段的义务。

### R5 事实变化只更新受影响的范围

信息补齐（如 spec 完成后验收条目确定）或事实变化（接口变化、发现 UI 影响、验收缺口）时，通过既有 backtrack / correction 机制只更新受影响的义务与阶段，其余已确定范围沿用；不重算全流程，也不要求入口预知一切。新契约可能改变后续测试义务，这属于合法更新。测试失败、门禁失败不得触发"改判不适用"。

验收：单测覆盖"coding 阶段发现需改接口 → plan 义务补回并回退到 plan，后续 testing 义务按新契约重判"；单测覆盖"testing 失败后执行范围不变"。

### R6 用户呈现与 change-lite 退役

- 用户不再看到 lite/full 选择；change-lite 作为用户入口 Skill 退役（其 change.md 引擎可作为"轻量需求承载物"内部保留，由入口决定是否使用）。
- 一句话说明范围与理由；确认点只保留既有"花钱"动作。

验收：confirmation-registry 中不再有轨道选择确认点；smoke 交互脚本无 lite/full 字样；用户请求"只讨论"时流程止于讨论。

### R7 首个落地场景：零设备义务不进 testing

作为本机制的第一个具体场景：基于**完整、有效**的适用输入确认设备义务为空时，testing 不进入执行范围。不产空计划、不产空报告、不调用设备。"为空"的判定至少要求：acceptance 存在且 `acceptance_ut_layer_complete` 通过；无 device/both 层 AC 与 BD；`performance` 中无需真机验证的项；蓝图/Code Graph 对该范围有效且未显示用户可见行为变化。任一输入缺失或无效时义务为"未知"，不裁剪 testing，先补足判断依据。

验收：用一个只有 unit 层 AC 且无 performance 项的夹具跑完整链，run 以 ut 为末段正常完成，manifest 记录 testing 跳过原因；`--report-reconcile-only` 对该 feature 不报缺 trace；用一个缺 acceptance 或含 performance 项的夹具，testing 不被裁剪。

### R8 护栏保留（当前分支已规划，主干需保持兼容）

- `plan_references_unit_layer_ac`：TC 的引用非空、全部可解析、且全部明确为 `ut_layer=unit`（AC 与 BD），并且无任何 NFR/性能引用时，升 BLOCKER；unit 与 device/both/NFR 混合引用保持 MINOR；空引用与含未知引用不由本检查裁决。未声明 ut_layer 不视同 unit（由 `acceptance_ut_layer_complete` 负责）。details 直接指明修复对象："该 TC 仅关联 unit 层 AC，应由 UT 覆盖，请从测试计划删除；不要修改 UT，也不能用 manual 通道解决。"
- 该检查前移到设备跑机门禁之前，命中 BLOCKER 即不启动设备，短路文案写真实原因；`--report-reconcile-only` 不受影响。

理由：R7 只在义务判定生效且输入完整时起作用；计划被人为写偏时仍会进 testing，护栏兜底。两者不冲突。

> R8 已在 Br_release_3.0.0 分支实施（commit 7906a7d2）；实施细节以 commit 与代码为准，本文不承载实施记录。

## 7. 非目标与边界

- **不另造"智能路由系统"或独立 AI 分类器。** 语义判断融入既有阅读理解；可确定部分由脚本算。
- **不在每步前调用 AI 决定下一步。** 一次计算，冻结。
- **不用空壳产物满足门禁。** 不适用就是不产出。
- **不做 A/B。** 靠宿主实跑迭代。
- **不放松证据要求。** 义务存在时门禁强度不变；本需求只改"义务是否存在"的判定来源，不改"义务如何被证明"。
- **不把 manual 通道当逃生口。** 三态语义不变。
- **分支归属。** 本需求是 3.1.0 尺度的编排模型改动，落主干。3.0.0 线只做 R8 两条护栏。

## 8. 验收场景（端到端）

| 场景 | 输入事实 | 期望执行范围 | 期望用户可见输出 |
|---|---|---|---|
| A. 行为要求明确，已有测试复现实现错误 | 请求指明失败用例；既有 acceptance 覆盖 | coding → review → ut | "已有验收与测试覆盖，本次直接修复实现并回归相关 UT；无设备义务。" |
| B. 需求明确，需决定模块拆分/接口 | 请求含新接口；既有 contracts 未覆盖 | plan → coding → review → ut（设备义务按 R1 判） | "需求明确，需先定接口契约……" |
| C. 新行为，验收不清 | 请求含新行为；acceptance 不存在或未覆盖 | spec → 再算后续 | "需先澄清需求与验收，再决定后续工作。" |
| D. 蓝图已明确设计与验收，实现直接 | 蓝图 changed 单元含 decisions + verification_refs | coding → review → ut（+ testing 若有设备义务） | "消费蓝图已有设计与验收，直接实施与验证。" |
| E. 本次案例：纯 RDB 层改动 | acceptance 全 unit 层；无 UI 触及 | （spec/plan 按 B/C 判）→ coding → review → ut | "无设备验收义务，不安排真机测试。" |
| F. 同一蓝图两个单元：数据库修复 + 页面交互 | 单元 1 无 UI，单元 2 有 device AC | 单元 1 不含 testing；单元 2 含 testing | 分单元各一句话 |
| G. 实施中发现必须改接口 | coding 期间 diff 触及公共接口 | 回退补 plan 义务；后续 testing 等义务按新契约重判，未受影响部分沿用 | "发现接口变更，补回契约设计后继续。" |
| I. 输入不完整 | acceptance 缺失或 ut_layer 不合规 | 义务为未知，不裁剪任何阶段，先补判断依据 | "验收分层不完整，无法判定设备义务，请先补齐。" |
| H. testing 失败 | trace 有 failed | 范围不变，走既有回修 | 不出现"改判不适用" |
