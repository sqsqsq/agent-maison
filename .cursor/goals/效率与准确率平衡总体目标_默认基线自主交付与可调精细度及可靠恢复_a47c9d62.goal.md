# 效率与准确率平衡总体目标

> 本文承接用户关于速度、效果和自主交付的裁决，作为后续有界 plan 的上位目标。
> 实施待办由 plan frontmatter 承载，运行事实仍来自既有产物；本文不新增配置、状态机或统计系统。

## 0. 一句话目标

**在用户目标、真实授权和硬预算内，Maison 默认自主、快速地交付足够好的结果；用户可选择更多精修，可靠性始终保持同一底线。**

没有用户主动指令时，goal-mode、无人值守和静默执行使用 Maison 自带基线。达到基线就交付，额外精修由用户明确要求，不因轻微差异反复等待确认。

### 0.1 长期目标域

目标 ID 描述贡献，不作为第二份待办状态。

| ID | 目标 | 达成含义 |
|---|---|---|
| `g1-default-delivery-baseline` | 核实并贯通默认交付基线 | 复用已有默认保真度、严格度和差异处置，静默请求可自主完成 |
| `g2-user-adjustable-quality` | 支持用户调整精细度 | 先使用现有目标更正/配置入口；真实缺口才安排有界改造 |
| `g3-recoverable-execution` | 提高当前任务恢复能力 | 可恢复的框架问题优先局部处理，保留有效产物与累计预算 |
| `g4-completion-and-polish-separation` | 交付与可选精修分开 | 达到当前目标即可交付，剩余差异及能力缺口如实披露 |
| `g5-proportionate-verification` | 验证投入与风险相称 | 复用直接目标测试，稳定后集中验收，减少重复执行 |
| `g6-real-host-delivery` | 以干净宿主检验实际交付 | 新需求重跑证明默认体验；自含回归证明恢复分支，分开报告 |
| `g7-lean-governance` | 裁掉已确认的冗余工作 | 首批删除预算专用刷新、合并重复回放、复用指标与规则；后续按具体消费证据裁剪 |

## 1. 用户裁决与当前边界

“95%”表达足够好的交付偏好，不是统计准确率承诺。落地为具体必需行为、允许差异和完成条件，不新增百分比总分门禁。

用户已决定旧宿主现场不保留、不恢复，按已删除处理。后续以干净基线重跑原需求为主要验收；历史诊断用于构造最小回归，不重建 be091c，也不宣称其恢复已经验证。

近期主要成本来自框架可靠性：预算独变触发刷新、格式错误、重复调用和失效处理。现有缺省已有 `semantic_layout + best_effort` 等规则，开发完成与发布就绪也已分离。先核实这些规则的实际消费效果，暂不另建“默认均衡交付”plan；新运行暴露具体差距后再立有界变更。

## 2. 交付基线与用户选择

### 2.1 必须稳定的底线

各质量选择都保留核心功能、关键交互、数据正确性、明确必需目标、真实授权和硬预算。硬预算指用户明确的总上限与当前生效额度；框架默认额度可在“无人值守＋不要询问＋完整交付”明确授权下由主 Agent 显式调整，普通静默不授予提额权；累计消耗与无进展熔断保持。质量判断依据实际影响，使用已有验收、检查和材料，不靠“UX”“P0”标签单独决定。

| 现有信号 | 核对的实际影响 | 处置 |
|---|---|---|
| 必需构建、关键运行或验收失败 | 产品不可运行、核心流程/数据错误或明确必需目标未达成 | 修复或如实报告未完成 |
| P0/P1 等优先级 | 当前范围、真实失败原因及能力缺口 | 优先级作判断信号；unsupported gap 按既有契约披露 |
| 缺失、遮挡、裁切、错误页面 | 必需内容、关键操作、导航或状态理解是否受阻 | 有实际影响则修复；装饰及排除项不因类别名自动阻断 |
| 尺寸、间距、颜色、字号、圆角差异 | 操作、可读性、状态含义及明确精度要求是否受影响 | 非关键差异可披露交付，类别本身不构成整体豁免 |

视觉三级定义纳入现有 provider 提示契约，使用原 `severity` 与 `note`：

| severity | 定义 |
|---|---|
| `blocker` | 有具体证据表明当前范围/状态下的必需目标、关键操作、导航或状态理解无法成立 |
| `major` | 明显视觉或交互偏差，但主要任务仍可完成、信息仍可理解 |
| `minor` | 局部细节偏差，不影响操作、信息含义和可读性 |

provider 说明影响、定位及不确定性，gate 结合有效目标和严格度裁决。截图不可见不直接证明操作不可达；历史材料中“收键盘后提交通过”和“展开时看不到按钮”是不同事实，应结合适用需求判断。

这项提示修正由 `6e2f9a10` t3 承接。格式测试不证明模型分级正确；分级效果在干净运行中用合法载荷、视觉结果和既有调用/诊断记录观察，不新增模型评测或测试矩阵。

### 2.2 用户可理解的取舍

| 选择 | 要求与交付 |
|---|---|
| 快速交付 | 核心行为完整，外观合理，较多非关键差异如实披露 |
| 均衡交付（默认目标） | 主要布局、文案、状态符合目标，少量细节偏差不拖住交付 |
| 精细还原 | 用户明确要求时处理更细差异，仍受已有预算约束 |

这些是用户侧表达。R1 核对现有参数及运行规则如何承接它们，不预先新增机器档位、评分或配置协议。

### 2.3 自主默认与明确要求

优先顺序：**用户明确要求 → 任务/工程显式配置 → Maison 内置基线**。用户不表态时直接执行默认，不先要求选档。

按措辞推断是解释依据，不是额外授权层级。“按图实现、布局参考某图”确定参考目标，不自动等于所有细节零容忍；清楚的自然语言硬要求同样有效，不必经参数表达才算明确。来源标签不能替代原文，局部要求保持局部作用域。

保真目标、验收严格度与投入分开读取。例如历史 `pixel_1to1 + best_effort + approximate` 不等于最严验收。以实际 gate、完成判定和调用成本核实默认效果，不只检查字段名称。

**达到基线就停止默认打磨，额外精修只在用户明确要求时进行。** 以既有完成判定、任务总 turns/活跃时长及重试边界承载；不为“打磨投入”新增计数器或独立预算账本。核心目标未达成时，继续既有有界修复或准确停放，不能把耗尽预算写成完成。

### 2.4 用户调整

先使用现有自然语言目标更正、范围修订与配置入口。提高或降低精细度只影响相关工作，保留有效材料、真实发现和累计预算。

当前不预先新建动态调整 plan。确有未覆盖的需求时，首版有界改造只调整不改变业务行为的容忍度、精细度与投入；必要真源和投影保持一致，是否更新 spec 由其职责决定。真实业务/数据/外部契约变化沿原责任流程。

## 3. 完成与恢复

普通开发完成、可选精修完成、发布就绪沿现有语义分别表达。未验证内容保持未验证，已知能力缺口按实际目标披露；状态字符串不能替代产品验收。

框架自身的格式、报告、缓存和状态故障优先使用现有纠错、重建和责任恢复。同条件无进展不盲目重复；真实外部条件或授权/预算不足时保留当前任务的有效成果并准确停放。

2026-10-19 新裁决：无人值守完整交付中，原需求范围内的蓝图、CU 与必要架构修订由 runner 自动交设计责任方，经正式修订、隔离质询、检查、发布和重绑后接续，不再以“已交接设计须先问人”或个人 B1 预授权开关为前提。架构覆盖既有 dependency_edge、add_module / move_module / retire_module、responsibility_rewrite、dsl_other；plan/coding 不自行改设计或 DSL。此口径取代 10-16 的一律确认限制，有人在场流程不变；真实需求/实质验收变更、明确禁止、秘密/不可逆外部动作及用户总预算上限仍守原边界。技术条件未满足仍可准确等待/停放，不把静默修订理解为无限重试。预算默认扩容仍按 §2.1 的既定三项条件。实施与验收由 R6 的 5bddfc4a 承接，此段不表示代码已经落地。

“放弃历史 demo”不等于取消今后运行的可恢复性。新运行的生产路径与最小回归仍需覆盖实际恢复行为；不为已删除的 be091c 继续新增旧数据兼容。
