## 4. 修法

### 4.1 同一事实形成下一调用的承接

在两运输分岔之前，由已有调用/request/report/events 与当前磁盘材料形成一次只读承接输入：
前次同职责实际调用及其完成/中断事实、可读的最终作者正文、已落盘材料路径、当前机器诊断、
本次必须补齐的本职产物。已有材料先读后续写，未变化的已核事实无需从零全仓探索。
单纯列文件不假定其内容正确，机器检查与真实语义质询继续判断质量。

会话读取已接受 report，后台读取已有最终正文/调用日志；复用已有提取器，不将 1–5MB 工具输出
整体塞入提示。正文按固定小上限截取并附原件路径，缺失时准确说明，不制造上轮结论。
最新同职责事实和当前检查优先，不误用其它用途、旧质询或先前设计 revision 的成功结论。
重入仍从既有持久材料重建同样内容，不引入第二进度真源，也不为提示加签名/身份层。

普通阶段仅允许纯提取“继续已有工作、明确失败证据”，现有用例下普通`buildPhasePrompt`输出
必须逐字不变；做不到就只在初建写必要承接，不为形式强行共用。receipt、回滚与phase harness
话术保持原处。会话和后台收到的业务内容、职责和差额一致，
只允许运输包装和原件位置不同；重复 next 仍复投原签发请求，不因本次修法多花调用/turn。

### 4.2 明确本职交付与自主推进边界

作者必须在真实工程事实和原请求内完成当前切片的 schema 蓝图；发现笔记是可复用中间材料，
不能作为本职完成。把实际产物路径、格式/schema、当前需要完成的字段/契约和准确检查命令送达。
合法内部存储/账号/导航契约可以按既有结构设计，不制造远程 API，不猜字段、不代填业务答案。
准确必答范围与质询结果形状复用现有 schema/计算函数及修订质询投影；候选数组和 scope 命令
沿现有生成链，不在提示另维护格式副本。检查命令的 cwd、参数和本次身份必须来自同一投影。

作者可在授权设计写集中探索、决策并完成原需求内必要设计，不因普通可恢复缺口停等人。
真实原文冲突如实登记并交原独立质询/责任裁决，不能伪造人签或删验收；确需改变原需求、
实质验收或突破明确禁止时保持原授权边界。作者不能写产品、测试、framework、canonical CU、
运行记录或自签已完成独立质询；机器派生 admission、consumer 接受与正式交接保持原责任。
本职完成后 runtime 继续下一职责，不能因“质询尚未发生”的 checker FAIL 冷启动重做设计。

### 4.3 内容未完成与真实中断分开，仍然有界

事故的三次正常调用均属有真实产物缺口的内容尝试；“自报未完成”“增加笔记”本身不豁免
`max_retries_per_phase`。修复重点是首次就交代蓝图交付、后次具体承接差额，而不是加次数。
重复空笔记或同样未交付继续消耗原内容额度，耗尽准确停放，不能一直耗到 30 总 turns 才止。

同职责内容尝试以已有 start/end、accepted report 和共享 invocation completion 配对重建；
真 waiting、未执行的 pending/重复领取不当作新内容失败。真实超时/API 中断只按既有对应语义
续作，不借正常 exit1 重分类为运输失败；不新增故障分类或重试账本。
author、questioning、decompose、scope 保留各自责任窗口，已有合法 published 后的 scope 重算
继续沿原窗口，不因正文、笔记或本轮新提示变化自动清零。所有真实调用/活动时间仍累计到原请求
总预算，重入、角色切换或设计发布都不重置硬上限。无新增证据不引入“进展指纹”或宽泛免配额机制。

同一run的author额度贯穿发现、写蓝图及修复质询否定，`max_retries_per_phase=2`时合计至多3次
正常内容尝试，不按“已有增量”刷新。真实链若暴露该额度不足，记录为新证据后重审最小修法，
本批不先加额度或进展机制。旧960fa0的resume/force-resume仍准确停在耗尽，不新增调用或提示。

耗尽后的正式出口使用现有显式`--supersede <当前原请求run>`，不另建同run恢复窗口。
显式目标为当前原请求时，`goal-mode-entry`准备入口、launcher/runtime及`prepareInitialDesignRun`
跳过同需求提前rejoin，将supersede传到原`decideRunContinuation`的`explicit_flag`分支，
复用初建已存在的资格核验、后继出生与supersede审计。原需求和来源、adapter合同与请求累计预算
保持；新run_id是合法审计后继，不覆写旧manifest/events或把旧run冒称完成。
存活执行者、未报告签发窗口、adapter变化及总预算不足仍按原逻辑拒绝或停放；无supersede时
同需求仍接回原run，不自动出生。后继首次作者提示读取这条原请求血缘中真实旧调用和现有笔记，
不能因本run暂无调用又冷启动。停机指引给出这个既有显式出口；最终交付提供实际验证过的精确命令。
后继再次耗尽仍停，可再明确起后继，但原30总turns及累计活动时长始终有效。
此处只接回本事故的初建续作出口，不处理未开工child纠错或历史Root身份改写。

## 5. 真实核心小样本与通过证据

先取得事故原始需求、四张图片、真实源码/路由/账号/存储上下文、适用规则和960fa0原件的隔离副本，
记录来源、基线及必要差异；保留真实发现笔记和历史3次调用，不携带旧蓝图、CU、产品完成原件或
其它run的成功结果。framework使用本轮冻结前工作源码物化，不在真实宿主安装。
型号通过现有`adapter_model_pin`钉为`gpt-6.1-terra`，优先复用事故Codex CLI 0.161.0；
仓内没有推理强度参数，effort沿CLI实际配置并从真实会话`turn_context`只读取证，非high则记缺口。
不新增effort参数或修改全局配置。CLI/模型不可用时如实报告，不静默换模型后宣称修好。
独立质询必须是实际隔离调用，不能以provider名称代替隔离。

唯一真实核心链从隔离960fa0的原需求、笔记与3次真实调用出发，以现有显式`--supersede`出生
合法审计后继，再经生产session next/report推进。旧run/events保持原字节，后继需求不变，
旧消耗继续累计，新提示真实承接旧调用和笔记。禁止换无血缘run、改需求或清历史绕过；
空目录普通路径只做定向生产回归，不再另跑冗余真实模型长链。
真实样本只用session lane，以正常child首个签发请求返回exit3为自然停止边界，不执行该请求；
不启动会自动推进到UT/testing/设备的后台lane，也不靠杀进程停在交接点。

核心通过必须同时有可核原件：

1. 原始需求/图片与工程输入来源；960fa0未变的3次历史、supersede血缘/审计、前次正文/发现笔记
   及后继首次提示里的真实承接差额；后继与原请求需求、来源和有效合同一致。
2. 模型亲自产出的 `component-blueprint.yaml`，内容覆盖本次真实请求，保留数据、导航、失败恢复等必要设计义务。
3. 实际独立质询调用/结果、当前真实 checker/admission 与人读设计投影；没有代填质询或冒认 pass。
4. 原 consumer 接受的 canonical CU、真实 readiness 以及正常 CU 的正式交接请求/出生身份；
