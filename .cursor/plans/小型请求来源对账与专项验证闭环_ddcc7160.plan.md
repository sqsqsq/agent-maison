# 小型请求来源对账与专项验证闭环

## 1. 范围、输入与交付边界

用户要求在宿主实施“2-1 银行搜索”。框架选中 `small`，消费短蓝图，无 CU。交付单位仍是原 request。实现沿用[小型设计计划 §4](需求设计按规模减负_短蓝图与CU映射收编_c8d6f1a3.plan.md)和[原 request 入口](../../docs/operations/request-harness.md)。本批交付共享来源归属修正、HMOS UT 注册与诊断、短蓝图到设备证据的消费链，以及分别可核的开发和宿主验收结果。

11 月 24 日样本的发布件为 `3.1.0 / 517b63fe`，宿主起点 `c6a28975761644334a9270e77d13a49f5752a6e4`，request ID 为 `4abc90dcc87a1670`。原生会话 `session-97a072c4-c4bb-47e7-b738-0fb39e305b6c`，原 user 锚点 `8646a93d-5148-48ec-8227-8d1b8f7ae94e`。完整 `session.v4.jsonl.zstd` 的 SHA-256 为 `3c2cbb57c0d3157c93c970e16e92b4df0053e845f723fb989d4563355c3dc239`。回放从只读原件提取必要的原生事件及相应蓝图、测试字节；待测前缀按事件顺序截取。优先复用留存的报告、执行键与冻结日志。已被历史重试覆盖的报告标为缺失，模拟时序单列；不从最终 PASS 倒造早期报告。

## 2. A · 在原 request 核对来源，保住已合格的执行

**一次读到什么。** 读取器交出属于选定会话及请求边界的原生关联事实，保留可定位的未配对调用、已观察到的关联冲突和执行失败。DSH 沿用 seq 与两处 callId 的匹配；Claude 和 CodeAgent 共用 `tool_use/tool_result` 配对，CodeAgent 沿用 `.cac` 原件定位；Codex 沿用自己的调用 ID；OpenCode 沿用 part、callId、完成状态与时间。原生结果 ID 错配留具体缺口；等待中的事件不作为成功读、写或执行的证据。共享 intake 决定已知事实能支持哪项结论。保留 Cursor 既有来源限制。[原生读取](../../agents/shared/native-request.cjs) · [DSH](../../agents/shared/dsh-native-session.cjs) · [OpenCode](../../agents/shared/opencode-native-session.cjs) · [归属计算](../../harness/scripts/utils/request-intake.ts)

**初始干净。** 用原 user、起始提交、初始状态、最终 diff、目标字节及实际使用的原生证据核验。若这些已充分，末尾未配对本身不产生完整对账失败。无需识别当前 shell 的调用号、解析任意 shell 的副作用，或在同步检查内部等自身返回。若某次真实来源读取或执行结果就是必需依据，仍须取得并核验。干扰进程是否中断测试由实际执行结果和日志裁决。

**初始已脏。** 按文件区分初始用户改动和本请求新增改动。显式目标与可核实的结构化写入路径是候选范围，尚未配对的写入可以提供候选路径，不能凭参数证明写入成功。对产品范围内的初始脏文件，优先使用既有、可信的写前原件。比较时涵盖内容和存在性，保持原路径边界。与可靠起点一致的文件不因开工前已脏而产生缺口；发生变化的文件须进入影响核验，无法分清来源时留下该文件的具体缺口。即便 shell 已返回，也不能仅因它没有结构化编辑记录而把文件过滤掉。

| 写前事实 | 最小处置 |
|---|---|
| 已有完整前像或可核验的同一起点字节依据 | 在现有 baseline 上比较。显式目标保留；无关且原样的文件继续原工作。对已变的文件，摘要只能证明不同，行级归属仍须相应前像或其他原件。 |
| 新请求在产品写入前进入原有准备入口，但该适配器只有脏路径名单 | 先用一改一不改两例验证已有材料。若现有材料确实不能区分，允许在该次既有准备时仅给适用的初始脏产品文件随原 request 保存存在性和字节摘要；已具充分前像的文件无需重复保存。收益是 shell 改动可被发现、无关旧改动免停机。无需另建基线库、逐轮账本或保存额外源码正文。 |
| 仅留初始脏名单，缺少可信写前字节或等价原件（包括先修改、后进入框架的请求） | 默认继续执行可核工作。报告逐文件列出归属未核的产品路径、所缺依据和已验证范围；局部结论只覆盖已验证部分。显式目标和必需验收继续由原请求负责，受缺口影响的项目保留欠验，不能通过缩小范围签整单 PASS。若请求要求完整 diff 归属，报告明确其尚未核齐。当前字节不能倒填为起点。 |

**终检与续核。** 在原 [request 执行入口](../../harness/scripts/utils/request-phase.ts) 用已重读的当前 intake 出具来源结论，保留 request 身份、目标绑定和实际输入的新旧校验。蓝图来源准备、验收投影及最终报告应对同一批已配对事实取得一致结论。保留原蓝图指纹、来源和用户控制校验。

银行搜索样本及必需 result 在终检前补齐的时序是本批硬验收。业务输入稳定且已有合格 11/11 时，由本次执行消费最新来源完成对账，从首次合格结果起新增测试包构建、安装和设备执行各 0 次。沿用[失败留存](../../harness/scripts/utils/automatic-request.ts)与[报告原件](../../harness/scripts/utils/report-generator.ts)保留历史 FAIL。相关输入实质变化、较新的真实执行失败、证据失效或明确要求 fresh 时，按现有规则重验受影响部分。

**必需来源晚于首次报告的时序先做回放调查。** 对齐首份失败报告所缺的具体必需事件、对应 result 及报告写出时点。若原件证实首报后才补齐且业务输入未变，才按新增机制准入评估同 request、同目录的最小续核；该真实实例以新增构建、安装和设备执行各 0 次验收。若证据不足，记录“未证实”及原因，即可结束该项调查。模拟延迟本身不触发续核开发或新的收口门禁。

## 3. B、C · UT 授权、执行目标与诊断

- **B · 注册也是测试写入。** 在原 prepare 中同时验证显式用例与其所需、获准写入的同模块注册入口。HMOS 复用[模块注册识别](../../profiles/hmos-app/harness/ut-host-impl.ts)；必要时只抽出已有判据共用，不让 core 按文件名放行。自动 writer、[parser](../../harness/scripts/utils/capability-resolution-entry-input.ts)、预期来源检查和[执行 provider](../../profiles/hmos-app/harness/providers/ut-run.ts)共用同一角色区分。注册字节参与输入绑定；只有所选用例参加 `describe/it`、预期来源和实际计数检查。原有只读目标、既有 request 和权限边界继续可用；跨模块或任意源码不能借注册名义取得写权。维持真实注册与执行数量不符的失败。
- **C · 非法组名单独诊断。** 保留当前字符规则。在首次执行校验中直接报告文件、实际组名与允许的 ASCII 字母、数字及 `._-`；缺字面量组名、缺用例分别给出对应原因。补齐 [HMOS UT 指引](../../profiles/hmos-app/skills/business-ut/profile-addendum.md)与[专项 UT 写入说明](../../skills/feature/business-ut/SKILL.md)。`bank search unit` 首次失败即给可操作原因，`bank_search_unit` 在其他条件满足时执行。首份历史报告另有预期来源与覆盖错误，仍须修正。

## 4. D · 从短蓝图验收到正式设备结论

短蓝图继续沿[当前 request 投影](../../harness/scripts/utils/blueprint-skill-projection.ts)提供验收 ID、操作、预期及 `ut_layer`。复用[已有分层判据](../../harness/scripts/utils/acceptance-layering.ts)（含 `isDeviceUtLayer`），在原请求授权终点内消费适用的 `device / both`，沿原 request 的 testing 输入准备接通 cases 和可执行的 `inputs.test_plan`。从现有测试材料复用或由既有测试职责补齐操作与可观察断言，保留源 AC 和 TC 的对应。内容影响派生继续补充真实专项；`next` 展示实际派生结果。严格消费[正式 provider](../../profiles/hmos-app/harness/providers/device-test-request.ts)的步骤、预期和证据。允许用一份合格设备证据覆盖多条 AC，逐条说明覆盖处，避免按 AC 数量重装或启动设备。

银行搜索须能说明 4 个 `device` 和 8 个 `both` 的设备结论。`both` 同时保留 UT 证据；即使 UT 全绿，任一必需 AC 没有合格设备证据，完整交付仍显示具体欠项或失败。纯 unit、明确仅编译/仅 UT、用户明确排除设备的请求遵守各自终点，排除项不得标成设备 PASS。所有步骤走原发布件和 request/profile 执行器，不额外创建 CU、阶段 verifier 或设备调度器。

## 5. 验收办法

| 样本或操作 | 验收结果 |
|---|---|
| DSH 原生前缀在 530、1413、1427、1434 的 call 和对应 result 处各截一次；另测结果确实永不到达 | 有充分独立依据的干净请求自动通过来源核验；等待号本身不签成功。必需来源始终缺失时报告具体事件与受影响结论。全零蓝图来源指纹仍失败。 |
| 两组均有初始脏的 `src/format.js`，显式目标均只有 `src/search.js`。普通 shell 在一组改写 `format.js`，另一组只查询、保持文件原样；分别在 tool/result 前后核验 | 修改组须检出该文件再次变化；仅有差异摘要、归属或新增影响尚未核实时，完整对账不得 PASS。补齐归属并完成受影响验证后才能通过。未碰组不产生缺口，能继续。另在只有脏名单的请求中验证：对已确认与本请求无关的初始脏文件，报告逐项列出，断言不会仅因该文件产生 `request_input_unresolved` 或触发重跑；归属仍不明且影响显式目标、必需验收或要求的完整 diff 对账时，保留对应欠项。 |
| 源码读取后发起结构化编辑，result ID 错配 | 仍保留明确来源缺口；候选路径不替代成功关联。共享归属场景按 Claude、CodeAgent、Codex、OpenCode、DSH 的适配器入口回放，验证相同业务结论。Claude 和 CodeAgent 共用配对样本，CodeAgent 另核 `.cac` 来源定位；夹具回放只证明读取契约。 |
| 银行搜索样本；另构造同 request 的测试已获 11/11、缺的必需 result 在本次终检前补齐 | 保留合格结果，自动完成对账；新增 `genOnDeviceTestHap / hdc install / aa test` 各 0 次，无作者手动轮询、后台脚本或另建目录。修改测试或相关产品输入、损坏原始日志、要求 fresh 时不能错误复用。历史 FAIL 可按原字节核对。 |
| 调查必需 result 是否确实晚于首报 | 交付能定位的原生事件与报告时序，或写明原件不足。单凭首报 FAIL、后报 PASS 或人工延迟，不算已证实实例。 |
| 注册入口无断言；加入不相关文件；非法与合法组名 | 注册可按授权写入，正常用例只计一次；多授写权被拒；非法值准确报错。改变注册输入不能借旧执行结果。 |
| 短蓝图中有 device/both、纯 unit、明确豁免；另使一条设备 AC 无证据 | 原 request 的正式 testing 对适用 AC 交回原生结果，缺项如实披露；unit-only 不新增设备执行，豁免不伪装已测。 |
| 干净 -br 隔离副本复跑同一需求 | 使用与 manifest 对齐的 HyLyre 环境，记录所用发布件摘要、基线及设备条件。作者沿原 request 完成，正式 UT/testing 结果可追溯；分开报告工程编译、测试包构建、安装、Hypium 和 UI 执行次数、人工介入与耗时。自然运行未出现晚到时序的，以前述独立回放验该项。 |

开发复用[原生会话用例](../../harness/tests/unit/dsh-native-session.unit.test.ts)、[request 入口用例](../../harness/tests/unit/request-entry.unit.test.ts)和[HMOS 专项执行用例](../../profiles/hmos-app/harness/tests/unit/request-execution.unit.test.ts)，以实际调用计数验证复用。实现轮按仓规运行 `npm run test:changed`，稳定后一次 `npm run test:daily`。本计划文档用 `node scripts/check-plan-version.mjs` 校验。宿主复跑使用独立干净副本和已安排的设备，不动 11-24 现场、主宿主或正在验收的候选包；未取得正式宿主结果时保持对应待办未完成。
