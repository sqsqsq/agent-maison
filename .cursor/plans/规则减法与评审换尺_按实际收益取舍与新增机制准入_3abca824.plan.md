## 3. 评审换尺（t1）

根 `AGENTS.md`「Review 要求」增加一条。

### 3.1 保有阻断资格的四类

| 类别 | 包含 |
|---|---|
| 产品与框架的确定性正确性 | 放过它，用户会拿到一个坏产品，或者"通过"的结论失去依据。包括数据完整性、事务一致性、发布件完整性、兼容契约 |
| 真实授权 | 越权写入、越权扩大范围、绕过需要人确认的决定、读取或披露秘密、执行不可逆操作 |
| 硬预算 | 预算被绕过、被重置、被无界消耗 |
| 已承诺的任务完成与自动恢复 | 出现确定性失败。例如某个恢复分支永远无法唤醒，某个确定性异常导致任务必停 |

每条阻断意见指明它属于哪一类，以及放过它的具体后果。沿用现有对具体触发、影响、证据的要求。

### 3.2 不阻断的情形

- **过程证据加固**：只提高过程文件的防篡改能力，没有上面四类的实际后果，出了问题可以由丢弃、重建、回责任阶段重跑来吸收。
- 假设性风险、接口更严格、可选加固。现有要求里已有，保留。
- 只让记录更好看、不影响产品与结论的意见。

### 3.3 重叠时按实际后果判断

一条意见既像过程证据加固、又落在四类之内时，看放过它的实际后果。后果落在四类之内，就保有阻断资格，
不因为反例的构造方式像"伪造"而降级。

用两个已发生的例子核对这段文字：

| 例子 | 按新文字的结论 |
|---|---|
| c4e7a9b2 第四轮：正常的 provider 输出就能让被排除的内容进入返修 | 真实授权，保有阻断资格 |
| c4e7a9b2 第五轮：自报来源标签获得授权例外 | 后果是越权返修，属于真实授权，保有阻断资格。修复做的是减法 |
| 假想例：建议给阶段证据文件加签名以防被改，出了问题重跑该阶段即可恢复 | 过程证据加固，不阻断 |

### 3.4 同步

引用评审要求的地方同步：`.cursor/rules/` 下相关规则，以及调度评审时使用的提示语约定。

## 5. 规则减法（t3、t4、t5）

### 5.1 没有生产消费方的代码与文档（t3）

**取证方法**。对每个候选沿下列入口逐一核对，任何一处命中都算有消费方：

1. 直接调用与导入。测试里的不算。
2. 动态入口：profile 加载、注册表、按字符串键访问、动态 require。
3. schema：JSON Schema 的必填项与属性、运行时的形状校验。
4. 兼容读取：旧 run、旧产物、快照是否还会读到它；代码注释里的兼容说明也是消费契约的证据。

"在手头的旧 run 样本里没出现过"不等于"从未发布产出"。拿不准的保留。

**已知候选**，开工时重新核对：

| 候选 | 位置 | 处理 |
|---|---|---|
| defect-review 裁决块的解析函数及其类型 | `repair-candidates.ts:114-180` | 删除函数与类型。测试只删针对它的用例，同一文件里其它用例保留 |
| 只被上述函数引用的文档段落 | 以检索为准 | P2 已清理的不重复处理 |
| summary 的阻断警告清单 | `harness-runner.ts` 写入处、`summary.schema.json` | 若退役：schema 取消必填、保留属性以读取旧产物；停写之后新旧两种 summary 都能通过回执入口的校验 |
| 停机原因注册表里没有生产产出点的条目 | `adjudication.ts` | 有兼容说明的保留。没有兼容说明、且能证明从未发布产出的才删 |

每一条在实施记录里留下四个入口的核对结果。

### 5.2 P4 之后仍在阻断的账本与形状类检查（t4）

沿用 P4 §6 的做法，不另立标准：

- 每条回答三问：它保护什么；放过它的后果；依据哪次事故、哪条清单或哪个已证实的反例。
- 报告形状类的判别问题：这个形状错了之后，下游是否因此丢失作结论所需的事实，而且没有其它有效证据承接。
- 每条要有实际消费者的证据。
- 回答不了、或者拿不准的，不登记，保持现状。

**取材**：P4 的开发期守卫基线里列出的阻断检查。先处理宿主事故里出现过的，再处理调研列出的代表检查，最后是其余。

**分批**：默认按同一条消费链组批。每批由 opus 逐条取证后提出，codex 逐条评审，通过后进去向表。

**每批的验证**：登记为披露并不等于受影响的入口就能继续推进。报告合法性等消费面保留了原生语义，仍可能让阶段失败。
所以每批至少选一个受影响的公开入口，验证它的结论、退出码或推进确实改变了；没有改变的，在实施记录里写明被哪个消费面拦住，
并把该条退回保持现状。

**收口**：不要求清完。结束时列出剩余的阻断检查及各自不处理的原因。

### 5.3 指引里的祈使条目（t5）

只处理两种分句：

| 种类 | 处理 |
|---|---|
| 与行为规约"权威判定"冲突：要求执行者在目标已经能裁决时停下来问 | 改为引用权威判定 |
| 要求执行者为可恢复的小错误停下、手抄哈希、发明凭证、选技术恢复分支 | 删除，或改为说明框架会处理 |

同一个条目里既有这两种分句、又有真实授权要求时，按分句处理，授权的部分不动。

不处理：

- 真实授权类的停等：设备策略、人审闸门、scope 扩展确认、凭据。
- 阶段间的闸门，它们由转换策略裁决。
- 产品真值类的要求。

取材以 P2 调研列出的清单为起点，开工时重新检索。改动遵守各文件实际的行数预算。

## 9. 放弃的准确性与已知代价

1. 准入要求靠 plan 评审执行。机器检查只覆盖字面量构造的阻断检查与停机原因；评审漏看时，其它新机制仍然可能进来。
2. t4 拿不准的检查保持现状，账本与形状类的阻断不会被清完。
3. 取证只覆盖本仓。宿主扩展若读取了被删的字段或函数，会受影响。
4. 指引分句的改写改变的是对执行者的要求，效果要到真实 agent 层才看得出来。
5. "实际后果"的判断仍然依赖评审者。文字给出了四类与三个例子，不能替代判断。
