# 评估读取去重与效率收口

## 1. 定位与边界

本 plan 挂 [a47c9d62](../goals/效率与准确率平衡总体目标_默认基线自主交付与可调精细度及可靠恢复_a47c9d62.goal.md) 的 R6，遵守 [总设计原则](../../docs/overview.md#121-四条总设计原则) 和 [AGENTS.md](../../AGENTS.md)。起草基线 `514140c4`，版本 `3.1.0`。目标是在现有权威和裁决不变的前提下，减少同一次判断里反复读取、解析、校验同一份材料的成本；不以更少检查、旧结论放行或改变所有权换速度。

用户本轮只授权起草计划并同步路标：不实施、不提交、不打包、不动业务宿主和手机，不复制或清理宿主现场。起草时工作区干净；实施前重新核对最新代码与其它会话改动，不回滚或混入无关文件。5bddfc4a 已在 `514140c4` 提交，本批另立效率边界，不重开 5bdd、28e31f53、395ff0ab 及前序已完成范围；所有联合验收继续 pending。

## 3. 实施顺序与责任入口

### 3.1 先固定两个生产动作（t1）

复用 `rule-convergence.unit.test.ts` 的 `withProject`、既有真实记录和重定位方式，在开发临时副本装入 `20261019T033030Z-1b91ba` 的 manifest/events 及对应产物。原证据由宿主 `ce2465d0` 发布件生成，不能直接用其环境指纹核验当前开发仓。沿该套件 1b91ba 用例现有做法（起草基线第 117–126 行），仅在副本中以 `resolvePhaseEvidenceManifest` 取得 spec/plan 的当前 environment，保留原 requirement 哈希，再以 `recomputeManifestAggregate` 重算 aggregate；历史输入/输出哈希和事件不变。原件保留，重定位、环境字段前后值和适配方法另记，准备副本、环境适配及模块加载的成本单列，不混进动作本身。

**两个动作必须经过正常生产路径**：测量前用生产判据确认 spec/plan 上游 fresh，动作 A 的 facts/能力准入通过，动作 B 不因复制环境失配而把下游按 `stale_upstream` 短路。未达这些条件的运行只记为测量准备失败，不能作为修改前基线或修改后成绩；先查清准备缺口，不跳过准入、手填 fresh 或改写历史输入使其通过。正常路径不要求尚未完成的 coding/UT 等阶段假记 PASS，原本的业务缺陷与未完成状态照实保留。

| 动作 | 生产入口与测量边界 | 必须保留的输出 |
|---|---|---|
| A：coding 前提示准备 | 上游 fresh、准入通过后，按 runtime 原顺序执行 `resolvePhaseWriteBoundary`、`resolveCapabilityResolutionEntryInput` 和 `buildPhasePrompt` 所需的实际准备/组装；计时从本动作准备开始至提示构成，不调用模型、设备或完整 run | 提示的需求、有效范围、写入归属和恢复信息，以及实际走到提示构成的证据；准入拒绝的那次不作性能结果 |
| B：一次 assess 判定 | 上游 fresh 的同一副本上执行 `assessFeature`→`observeFeatureState`，包含其实际有效范围与新鲜度调用，不手填预计算结果 | 阶段新鲜度、义务覆盖、整体结论、责任/恢复动作及相关原因；环境失配导致的提前退出或下游短路不作性能结果 |

两版使用相同 manifest、run 身份、业务输入、profile、Node 和测量适配步骤；各自 environment 按对应被测版本生成，差异登记。报告列清 A 实际覆盖的前置函数，不能只测字符串拼接却声称优化了完整调用准备。基线与修改版保持相同进程冷热条件；动作内调用次数的主要对照从没有上次动作残留校验结论的相同起点开始，准备阶段不预热被测复用。同进程连续两次动作也单列：旧跨动作缓存可能使蓝图校验为零，但不能把这种省略必要依赖复验的结果当作新代码必须保持的性能目标。仅耗时波动妨碍判断时有限复测，不建立基准平台。

统计 CU/蓝图的实际文件读取、YAML 解析、完整校验次数，并按文件、动作和调用来源区分；resolver 调用次数不能冒充实际解析次数。通过开发测试适配计数，不增加生产日志、持久指标、注册表或运行时性能门禁。耗时用同一计时方法记录，秒数是辅助，调用次数和输出等价是主要依据。两个动作都使用生产解析/判定函数，不另写一份性能测试版算法。

### 3.2 最小完整修改：收窄复用边界并接通遗漏（t2）

复用范围为 **§3.1 的一次完整同步动作：一次 assess，或一次 coding 提示准备**，包含其中多个 `identityNeutralDigest` 调用及递归读取；不是每份摘要新建一份，也不是整个进程、run、阶段或 attempt。只收窄到单份摘要会让原来只引用蓝图的多个摘要反复全量校验，抵消 touch 去重收益，因此首步就从动作入口透传同一份局部读取对象。动作结束或抛出后释放，下一动作重新取得依赖；没有外层动作的独立摘要调用以自身作为边界，不回落到进程缓存。

责任入口为 `assessFeature`/`observeFeatureState` 及 runtime 原提示准备调用块，经现有有效范围、完成检查、证据摘要调用链把 `IdentityNeutralDigestReaders` 传到 `identityNeutralDigest`，具体结果保存仍归 reader 所在的读取实现。只补既有参数/options 的内存传递，不新增全局上下文或运行时登记。首次修改同时做生命周期收窄和调用贯通，不先把 `deriveModifiableModules` 接到旧进程缓存上再补正确性。**t2 只共享读取、解析与完整校验的材料，不提前合并阶段新鲜度最终结论；后者仍由 t3 按测量决定。**

复用现有 `IdentityNeutralDigestReaders`、canonical loader、`resolveComponentBlueprintRefFromLoaded`、CU 对应 loaded resolver 和校验函数。每个实际访问的 canonical 文档在同一动作、同一校验上下文内加载、解析并按原职责完整校验一次，随后跨摘要、证据条目和 touch 共享；各引用仍逐条检查身份、摘要和目标地址。`deriveModifiableModules` 使用与其它引用相同的 reader，嵌套 CU/蓝图读取不得悄悄退回另一套全量读取。既有外部注入 reader 的语义不变，不把只供展示的 reader 当成施工校验通过；校验上下文不同的结论不串用。

完整校验涉及架构 DSL、组件索引、目录及权威来源，仍按原校验器读取；利用现有校验 context 的局部 `sourceCache`，不额外建立跨评估的依赖哈希缓存。**只对本次已完整校验的文档复用结论**，不能仅用 `FromLoaded` 跳过首轮校验。保留摘要字段、身份比较、目标解析、失败回落和所有权规则。

移除/收编本链上 `resolvedBlueprintRefs` 的进程级结果保存，不能一边增加局部复用，一边留着旧 Map 继续影响默认读取。局部结果不改写源对象或文件；不跨 `await`、writer、设计/CU 发布、架构修改或事件追加延长生命周期。如果准备动作内部实际经过这些边界，丢弃此前局部读取后再继续，并在测量中标明分段，不能把旧对象带过边界。下一动作重新读取，故同一进程只改 DSL、不改蓝图也必须重新校验。不为其它无关缓存做全仓清理。

### 3.3 测量后才决定是否合并新鲜度计算（t3）

t2 目标回归通过后，先重测 A/B，与 t1 相比列出剩余重复调用来自哪里。能消除的热点重复已经去掉、或剩余调用具有不同语义时，记录“不继续合并”即可完成 t3。只有**同一动作内、相同有效上下文、仍重复计算同一事实**且实测仍构成成本时，才在下表既有链路中作有界传递/合并；不因存在多个调用点便一律合并。

| 现有读点 | 当前用途与必须核对的差别 |
|---|---|
| `goal-run-creation.ts:loadEffectiveExecutionScope` → `feature-track.ts:resolveCurrentScopeView` → `collectPhaseCompletionIssues` | run 有效范围，实际已传 `currentRunId` 和推导的 `pendingOwnerPhase`；逐阶段直接检查 |
| `assess.ts:observeFeatureState` → `recomputePhaseEvidenceStaleness` | 整体状态，显式传 runId，阶段链与上游失效传播有自己的含义 |
| `verify-feature-completion.ts:executionScopeEvidenceFindings` | 逐义务/证明核对；其 freshness 参数未显式传 currentRunId，要核实底层最终选取的权威 run，不把省略参数等同于“无 run” |
| `feature-track.ts:featureScopePhaseHealth` | 独立阶段体检，不是 `loadEffectiveExecutionScope` 的主路径；保持其交互/无 run 语义，不强塞当前 run |

以既有 `recomputePhaseEvidenceStaleness` 和有效范围语义为准，不另建新鲜度算法。先对齐实际解析出的工程/Feature、权威 run 与事件视图、需求、framework、pending owner/paths，以及逐阶段或整链传播语义，再决定可共享哪部分事实。相同上下文共享；不同上下文不能互用最终结果。尤其不能用整链已传播的 stale 替代该阶段自身核对，也不能用无 run 的结果覆盖当前 run 的合法资源写入事实。

若触及外层共享，只在一次同步评估中传递已有计算结果；发生写入、发布或事件变化后，下一次判断重读。不能用常驻缓存、TTL、mtime 或全局“当前评估”状态掩盖上下文差异。若发现需要改变权威选择、裁决语义或扩大到其它恢复主干，先报告具体证据与边界，不以性能理由顺手重构。省掉重复计算后，真实失效、回退责任和未满足义务不能被省掉。

### 3.4 收口材料与规格边界（t4）

开发测量脚本/断言放既有测试范围，沿发布排除规则不进发布件；报告放 `harness/reports/371be428/`，记录基线提交、输入来源、实际动作、前后次数/耗时、t3 决定及验证结果。不要在 reports 留会被 typecheck 扫入的临时 `.ts`。长期需要的断言使用正常测试文件，不依赖本机忽略目录。

本批不改变消费者契约，不新增配置、schema 字段、CLI、报告协议或 OpenSpec 行为机制。若既有文档/注释把旧进程缓存写成保证，只按实际改动纠正；不借此重写授权、预算或验收规格。实施完成实际调用 Claude Code CLI 做有界 review，打印调用与结论；提交前汇报，不把“计划待评审”写成已获实施或提交批准。

## 4. 减法与新增机制准入

| 选择 | 场景、收益与边界 |
|---|---|
| 一次同步动作内复用已加载并校验的对象 | 消除跨摘要/证据条目及 touch/引用循环放大的完整解析和校验；复用现有 reader/context，不新增持久状态或通过凭据 |
| 条件性共享同上下文的新鲜度事实 | 仅承接 t2 后实测剩余重复，减少一次评估内重复工作；不改事实真源和传播裁决 |
| 开发调用次数断言 | 固定真实动作防止重复工作回归；不成为宿主运行时阻断或用户配置 |

不做全仓性能改造、全局缓存系统、自动监控/采样服务、依赖失效注册表、并行校验框架或新停机原因。不放宽校验；除 §3.1 明示的开发副本 environment/aggregate 适配外，不以重写冻结产物、删检查、强制 fresh 或换 profile 取得好看的数字。不改成功/失败复用协议、预算口径、无人值守设计政策或既有联合验收状态。

## 5. 开发验收

| 用例 | 通过标准 |
|---|---|
| 单次动作多摘要/证据条目/引用/touch | 在无写入分段且校验上下文相同的动作内，同一蓝图只加载解析并完整校验一次，CU 按实际不同文件计；完整校验次数不随引用同文档的摘要、证据条目或 touch 数量增长，逐引用身份检查仍执行，输出与原判据一致。额外覆盖仅引用蓝图的摘要：按 §3.1 相同动作起点比较，完整校验次数不多于修改前，不用多次摘要各校验一次抵消其它去重收益 |
| 两个真实动作 A/B | 只接纳已完成 §3.1 environment 适配、上游 fresh、准入通过的正常路径测量；提前退出或环境失配引起的下游短路不作前后结果。分别登记前后读取、解析、完整校验次数和耗时、真实输出。目标链的重复次数必须下降，不能只靠热进程或秒数波动宣称达成；未经过该链的动作如实记无收益，不为凑数扩面。t3 合并时额外证明同上下文的新鲜度重算减少 |
| **只改 DSL、不改蓝图** | 同一进程先成功完成一个动作，在开发副本通过原规则把 DSL 改成不再许可相关依赖/模块的状态，蓝图字节保持不变；下一动作必须重新校验，得到与无复用生产校验相同的拒绝/不可证明等价结果，不能沿用旧成功；恢复合法 DSL 后能恢复正确结果。测试不靠手动清理缓存过关 |
| 其它已有校验依赖变化 | 组件索引、权威来源或已有目录等按实际依赖选择最小反例：依赖变坏后下一次评估识别，恢复后重新评估；保持原规则的适用性和严重度，不新增检查 |
