## 2. 分类与准入

| 类别 | 已证实问题 | 实际收益与最小责任边界 |
|---|---|---|
| 小 bug / 直接兼容回归 | 行号归一后新 fp 绕过旧 declined fp | 消费侧从原事件恢复等价身份，保住原拒修/反驳轮；不迁移账本 |
| 语义混用 / 职责并行 | 中间自检 closed 被当 invocation 结束；一个 env flag 兼任收口与正式写者 | runtime 统一收口与正式提交，执行者能继续施工，不用手设特殊 env |
| 机制不足 | Codex 有 terminal parser，其余三类未接；删探针会丢 07-28 的挂住收尾能力 | 四适配器终态接现有 settle/grace/kill，替代通过后撤掉旧消费 |
| 信息丢失 / 恢复不足 | review 块可解析但行级缺项/旧绑定仍 silent `[]`；provider invalid 原文未回产出者；native 候选丢证据 | 扩现有诊断与回喂，先修格式/证据，再判产品；不引入新 repair 状态机 |
| 语义混用 | 判页锚点包含应被验收的按钮；应用树在场被说成必然错页 | 稳定锚点判页，内容证据判缺陷；真正错页保持拒收 |
| 语义过宽 | 候选集合相同被等同于没有尝试 | 同集合＋相关输入可比且未变才判同输入；新结果验证修复效果 |
| 入口遗漏 / 旧事实洗新风险 | same phase 新 run 无 baseline；pending owner 豁免与当前 SHA 替换可能承接入场前漂移 | 分开入场有效性与阶段内合法写入，保留历史来源，不用身份改写伪造有效事实 |
| 冗余失效 / 时间语义混用 | hint 每次生成时间、两入口字段与诊断差异使有效派生 stale | 同源语义幂等，mtime 只反映派生输入变化，不新增源绑定协议 |

新增只允许承接上述信息所需的既有载体字段/函数参数，逐项在下面给出用途；不新增密钥、授权令牌、常驻服务、
场外事实档案、窗口 manifest、第三种 round 指纹或孤立停机原因。本批不设计防同 OS 用户恶意写盘体系。
flag 冲突的实际后果是抢职责和错误留证，不等于已绕过真实装机、trace/HAP 绑定、产品门禁或真人授权。

## 3. 具体设计与独立验收

### 3.1 历史拒修兼容与失败交接（t1，第一代码批）

入口/SSOT：`repair-candidates.ts` 的 `parseIssueRows`、`itemFingerprintOf`、`resolveRepairDeclineState`、
`findUnreadableDiagnosisChecks`；`harness-runner.ts` 的 summary writer 与 `run_verifier_for_repair`，以及
`goal-brief.ts`/`goal-phase-runtime.ts` 的既有四个拒修消费点。不另建拒修存储。

**先修兼容根因。** 文件引用归一采用共享函数：斜杠、排序去重、末尾 `:行号`/`:起-止行` 一致处理。
历史回放仍以事件中原 `item_fingerprint` 匹配原账本 `repair_candidate:<fp>`，从同一条
`phase_backtrack_requested.candidates[]` 的原 `id/files/summary` 计算规范化后的等价 fp。
原 fp 与新 fp 指向同一个回放状态，按实际 `{run_id, backtrack_event.ts}` 去重计轮，不把别名再当一次候选出现。
只有已验真的事件/责任阶段账本与目标引文生成拒修状态；不得通过当前报告描述猜一个旧拒修。
缺原 files 等无法证明等价时保留原状态，要求当前 subject 的逐条验证，不凭历史报告重新确认。

四处消费统一使用上述回放结果：目标简报展示依据、review 是否必须当前 subject、反驳出现的重复豁免、attempted 的首次拒修轮豁免。
删除各处对原/新 fp 单独补丁式匹配；所有旧事件/账本字节不改，不清预算，不扩反驳次数。

**扩既有诊断，不增新出口。** review 正文与 verifier 逐条块共用同一行解析/绑定判据；
`findUnreadableDiagnosisChecks` 增加当前 review 问题行与 subject/拒修上下文，返回具体 CR 与原因：
缺条目、重复冲突、非法 verdict、缺 evidence、与该行 files/summary 不一致、拒修后只剩旧 subject。
“块可解析”不再代表全部行可消费。合法 `refuted`/`unclear` 与格式坏分开：refuted 不产 coding 候选，
unclear 保留真实不确定并按现有诊断处置，不能用格式重投把它改成 confirmed。
summary/NEXT 按实际 request 资格分两条可达路径，UT 仍复用两个必需检查的现有判据：

- 当前 request 已签发：逐行不可读继续走 `run_verifier_for_repair`，把具体行和原报告路径交给该 request 指定的 verifier；
  保留 FAIL/open，有原回复先修报告转录，确无有效回复才再投当前 request。
- carried/disabled 或混合失败导致资格不足：旧 subject 不可重确认拒修项，候选为 0；NEXT 给出具体资格原因、
  原 subject/报告/拒修依据，不伪造当前 request、不承诺已经自动回投。当前 phase 能合法修资格缺口时，先沿现有检查修其原因再签发；
  用户已明确禁用 verifier 时不自动改配置，保持现有 review open/未确认事实，说明若要新的逐条判断须由既有配置入口启用能力。
  确需用户决定能力配置或目标冲突时沿既有授权路径交还；真人裁决不把真实产品 FAIL 或未确认缺陷签成 PASS，不新增人签绕过口。

**native 交接保留证据。** `checkHylyreFailureRouting` 从已通过协议与 artifact 校验的同一 trace 取
case id、step index、failure domain/code、selector request/resolution、当前失败边界 artifacts 与 derived plan 路径。
在既有 `CheckResult.structured` 留这些证据，候选新增可选 `evidence_refs`：每条最小引用包含工程相对 `trace_path`、
原始 `case_id`、`step_index`，可带同源 `derived_plan_path`、已验真的 `artifact_paths`；selector request/resolution 与
expected-versus-observed 仍读原 StepResult，不复制第二份步骤结果。summary→回退事件序列化/恢复→coding prompt
贯通该可选引用，prompt 明确区分“修复目标”和“只读证据”，按引用读原 trace 的精确 case/step。
同批更新 `RepairCandidate`/check 输入类型、`summary.schema.json` 的严格键集、形状校验、summary writer、
回退事件保存/恢复、prompt 消费；旧记录无 `evidence_refs` 仍可读，不因此补造引用或改变旧 fp。
`files`/`affected_files` 只表达真实修复目标，trace、截图、UI dump、带 timestamp 的目录与派生计划不得作为 native 产品缺陷的源码目标。
本批 native 生产者原有修复目标集合保持不变：当前没有机器可证的源码映射就仍为空，并在交接说明里明说，
不拿 contracts 全写集填充候选。责任阶段解析上下文可供查找源码，但不能冒充已经定位到某个文件。
候选归属仍按已执行 nested outcome 与较早 passed action，不从说明文字猜。
native 的 `item_fingerprint` 保留现行 `itemFingerprintOf(id, files, summary)` 与原输入：旧 id/原修复目标集合/原 route 摘要不变。
丰富交接说明由上述引用和 prompt 渲染提供，不改原 summary 来换 fp；补证据本身不得改变 identity，
不另承诺“任意改文案 fp 都不变”。不新增 candidate 身份 schema，不标为视觉 `signal@1`，视觉既有 one-shot 语义不改。

### 3.2 invocation 结束、阶段闭环与正式写者（t2，依赖 t1）

入口：`agent-invoke.ts`、`codex-terminal-events.ts`、`claude-envelope.ts`、四 adapter；
`harness-runner.ts`、`check-receipt.ts`、`phase-closure-finalizer.ts`、`goal-phase-runtime.ts`；
`phase-state.ts`、`intermediate-rounds-journal.ts`、`visual-diff-check.ts`、`check-testing.ts`。
复用 [a7f2e5d1](设备就绪与阶段完成判定_解锁授权与模拟器托管_a7f2e5d1.plan.md) 的有界收尾原语与
[e6b3f8d2](收官真值与强制kit撤销_FAIL收口单源与错误约束删除_e6b3f8d2.plan.md) 的终态/质量分离。

**先有替代，再撤旧消费。** 当前 Codex parser=`codex_turn_jsonl`，Claude/CodeAgent/Cursor=`none`；
本机 Cursor `--help` 支持 `--print --output-format stream-json`，当前生产 argv 未显式使用。
Cursor 官方成功终态为 `type=result/subtype=success/is_error=false`，失败可能只有非零退出而无 result；
这一来源与本机 help 合用，不能把终态 schema 推导为工具审计能力。[Cursor output format](https://docs.cursor.com/en/cli/reference/output-format)

| adapter | 最小接线 | 失败与自然退出 |
|---|---|---|
| Codex | 保留 `turn.completed`/`turn.failed` parser | failure 优先；顶层 error/item error 仍只是诊断；exit 非零不洗成成功 |
| Claude | 复用 `claude-envelope` 的 result 成功语义，stdout chunk 接现有行缓冲收口 | `type=result/is_error=true` 为失败终态，重试中 system api_retry 不是终态；无终态依真实 exit |
| CodeAgent | 同 Claude kernel 与 `claudeArgv`，复用仓内 07-29 实采 result/error 语义 | 不从 fork 名字猜额外状态；本机无 CLI 的事实披露，不冒称完成新实机 smoke |
| Cursor | goal argv 显式 stream-json，成功 result 接相同收口路径 | 无 result 的失败按实际非零 exit；stderr 散文不伪造 terminal；终态不提升 tool provenance |

Claude kernel 的 terminal 输出应由 adapter argv 自身保证，不能依赖 `tool_event_provenance` 开关才有 stream-json。
同步 `planUsesClaudeStreamJson` 为与内置 Claude/CodeAgent argv 同一判据；四 adapter 的 parser 选择、
stdout 正文投影以及实际消费它们的 canary/critic/断流哨兵同步核对。Cursor 改 NDJSON 后，判卷不能仍扫原始 JSON 的文本行锚；

### 3.3 provider 局部纠错与判页/内容分离（t3，依赖 t2）

入口：`visual-provider-review.ts` 的 `runVisualProviderReview`/validator 与 `visual-provider-invoke.ts` 的既有 invoke-dir 留证；

provider/run/attempt/参考图/截图 hash 写入已有 invoke 证据目录及 check `structured`；NEXT 指向这份诊断。
**纠错对象是实际 provider，且发生在同一次 gate。** `runVisualProviderReview` 第一次 payload 校验失败后，
把原 body 与精确错误追加到同一冻结 provider 的 prompt，用同一批仍有效的 targets、参考图/截图及 hash 最多纠正 1 次。
纠正前重核这些文件与 HAP/采集绑定没有变化；变化则不得沿旧 targets 重标 hash，转原采集/责任路径。
只对“调用成功但 payload 非法”局部纠正；能力不可用、脏工作区或 IO 提交错误沿原出口，不把它们伪装成格式纠正。
第二次仍非法就返回已有 `unusable/invalid`，保持清场态和全部原输出；执行者不手改 provider 证据、hash 或 region verdict。
每次调用有独立 invokeId、留证、usage；这两次合属一次 gate 的评估，不新增 phase retry、不重跑 native、不重新采集。

两次共用同一个绝对 `reviewDeadlineMs`：在本次评估开始时取现有 provider timeout 的到期时刻与 gate 剩余 deadline 的较早者。
`runHarnessPhase` 从已经授予的 gate timeout 计算绝对截止，通过现有子进程数据通道传到 CheckContext；
具体使用 `gateInjectedEnv.MAISON_GOAL_GATE_DEADLINE_MS`（epoch ms），harness 读取有限正数并放入 context，
spawn 时清理同名大小写残留再写入，与现有 gate hard timeout 使用同一授予时点；它只是剩余时间数据。
`RunVisualProviderReviewOptions`/`VisualProviderInvokeInput` 携同一 deadline，分别在每次 invoke 前重算
`timeoutMs = reviewDeadlineMs - now`，并传给既有 `AgentInvokeOptions.deadlineMs` 钳制 settle/grace。
该键不赋予收口/写入职责；runtime 的原 hard timeout 仍独立兜底，改大数据键也不能扩大它。
余额非正不再调用，保留原 invalid 与预算原因；不能给纠正调用重新授予完整 5 分钟，不能清 phase/累计预算。
direct 无 goal 评估也以原 provider timeout 为这两次共同上限，不另建计时器/预算账本。

若同 gate 同时已有 native FAIL，provider 格式修正成功也仍保留该 native FAIL；它不触发局部跑机，
之后真正修产品所需的新 testing 仍按原失败复验契约执行。下一整轮可能重跑失败 native/重新截图，
所以不把“下轮恰好同 hash”当局部恢复前提，也不声称每次截图必然不同。

若目标、截图/hash、build、导航或来源图已变，旧输出只作历史诊断，新调用必须经原 capture/装机/trace 路径得到当前绑定；
禁止让模型把旧 hash 改成新值冒充修复。转录/形状错误与 critic receipt 写盘错误分开：后者重试原提交事务，不让 provider 为 IO 重判产品。

判页仍完全使用原 `identity.all_of/any_of/none_of`：Skill 与生成提示选择稳定 screen/root、route、标题等判别锚点；
`sms_next` 这类被验收的内容留在 ui-spec required/native 断言，不为了满足 identity 隐藏键盘或删缺陷。
目标页锚点已通过时，缺 required 按钮归当前 native/视觉内容失败，进入真实 coding 回修。
旧 nav 把按钮写进 all_of 时，保持该 identity 未通过、正式截图不采信；给出 dump 与原配置，让 testing 责任阶段

删除 capture 中“命中任一已声明应用 id ⇒ 应用树在场但必然非目标页”的过强诊断推论；它只证明应用树在场，

### 3.5 facts 入场有效性与同阶段后继（t5，依赖 t2）

入口统一在 `resolveCapabilityResolutionEntryInput` 与 `FactsInvocationContext.baseline`，所有 phase/harness/receipt/投影消费共用。
当前建立阶段不同才走 baseline；same coding 新 run 直接抛 identity mismatch。不能把该条件简单扩大后继续使用
`pendingOwnerPhase` 豁免与 `ownedNow → 当前 SHA`，那会把入场前已变的旧事实洗成新事实。

**入场判断**：runtime 在任何 executor 调用/授权施工前，调用同一入口严格验证旧 facts 基线、来源 dependencies、有效范围与环境。
此时不传 pending owner 豁免，不将旧 source SHA 换当前字节；首次核验与跨阶段/跨 run 承接的来源由原建立阶段证据及已经合法 closed 的 owner 输出解析，
同 run、同 phase 的下一 invoke 在尚未正式 closed 时只可按下述原调用 context＋真实写观察链另行核验，不能直接借用待闭环 owner 输出。
纯 run 身份变化不是实质 stale。same phase 的旧 run 只要这些事实有效，也组装现有 baseline；保留 `established_by`、原 run 来源及 baseline fingerprint，
追加当前 delta，不复制成第二份事实档案。非法 feature/request/范围混入仍拒绝。

**阶段内承接**：用既有 `PhaseExecutionContext` 携此次核验的 `FactsInvocationContext`；在同一 attempt 的
`agent_invoke_start` 保存 baseline/来源绑定与已有 `source_owners`，供 CLI 按 run/phase/attempt 精确回读。
`source_owners` 由 runtime 的有效范围与既有 phase-write-boundary 组装；本阶段可变集合只取其中 owner 等于当前 phase
且在已授予源码写边界内的路径，不信 facts 作者自报的 owner，不拿结束后才生成的 `phase_write_observed` 支撑中途自检。
用途仅是跨进程保持“入场时已核的事实＋当前阶段既有写权”，没有新文件、身份协议或授权服务。

**下一 invoke 的入场承接（2026-10-04 实证窄补）**：真实链 coding 首 invoke 已经实际 `PASS/open`，
且有精确源码 delta；下一 invoke 仅补 verifier，但 `i${totalTurns}` 已换新 id，精确 lookup 找不到本次 start，
旧 spec manifest 又因该 phase 自身合法改源失效，遂要求无必要的 Research 重建并破坏原链。
场景收益是：在来源仍可证明有效时完成正常两轮及多轮工作，不额外重建/回退；不放过来源漂移，不以承接证明产品成功。

新增的本次 start 尚未存在时，统一入口先保持原严格核验；需要解释同 run、同 phase 已完成 invoke 的合法修改时，
只读取既有未撤销有效窗口内、实际 `${phase}-iN` 的 `agent_invoke_start.facts_context` 与对应
`phase_write_observed.owned`。runtime 将 coding 实际 `allowed` 且具有当前 phase 源码角色的写入补进原 owned 观察，
复用已有 `invoke_id/path/pre_sha256/post_sha256`；不伪造事件、不新增 carry 字段、账本或文件。
新增 coding 源码 owned 行保留本次已计算的 `write.roles`（现有 classification 的 `{kind, source}` 形状），
仅供上述同 phase 入场链核验；`readRecordedRelatedHashes` 在 owned 部分按历史记录的角色精确排除
`event.phase=coding` 且合法 roles 含 source、不含 artifact 的新增 source-only 行，再与 observations 合并。
缺 roles 的旧行、coding artifact owned（含 source/artifact 混合角色）、UT source owned 与全部 observations 保持原消费；
不按路径名字猜 source，不读取当前源码/当前边界重构历史角色。因此 fresh continuation 与 t4 旧窗口补基线不被新增记录改变。

承接以窗口内此前严格入场核验过的原 baseline 为根，核原 subject、phase 与有效范围，排除 label、
未完成/未 settle 的调用、已撤销或回退失效的窗口。原 context/owner 不是新调用的身份或写权；
本次入口仍从当前有效范围和 phase-write-boundary 重算 owner/目标授权，仅在原依赖与合法写后绑定核验后生成本次 start context。
逐项 dependencies 按原 hash/exists 比较：未变照原规则；变更只能是同 phase 原入场已授予且本次仍授权的真实源码，
必须有对应完成调用的真实 owned pre→post 观察，其 pre 与原依赖或前一已核 post 相接，末次 post 与当前字节一致。
三次及以上连续合法修改必须按事件顺序保留从原 pre 到当前 post 的完整链，不能只选 latest start 而丢掉前几轮；
不得用当前重算值补缺失环节。读不到/坏 hash、断链、未归因的两 invoke 间源码变化，以及非源码/config/需求/contracts 漂移仍走原 strict stale/责任出口。
全部核验完成后，本次 context 保留原 baseline fingerprint、dependencies SHA、established_by 与原来源身份；
真实写后的绑定仅证明阶段内授权改动，不把旧依赖换当前 SHA 声称旧事实未变。

该分支只承接同 run、同 phase 有原有效 context 的已完成工作，不扩大跨 phase/cross-run failed context 复用。

| 参与比较 | 精确边界 |
|---|---|
| source/feature/schema | canonical 工程相对源路径、feature、schema；两个入口的字段别名归同一键 |
| test_cases | 现有八个源字段：tc_id/name/precondition/steps_natural_language/expected/priority/ac_ref/execution_channel；沿现有 whitespace/大小写归一；同源 navigation_hint 也参与 |
| 可执行派生知识 | allowed_step_roots、forbidden_in_steps、step_shape_catalog、wait_field_timing_ref；reset 的 available/bundle/page_name/position/order；执行通道 domain 与可执行集合 |
| selector 机器语法 | 真实允许的 match_modes、disambiguation_fields；从现有 selector/步骤解析契约组装，而非比较 policy/static_blockers 等提示散文；字面 selector 与当前 ui-spec 的一致性仍由现有门验证 |

不参与：`generated_at`、源文件 mtime、表外标题/说明、coverage_reason/missing/extra、选中派生路径/mtime、placeholder/lint 诊断；
`snapshot_bundle/snapshot_cache_empty/available_pages`、`selector_contract.entries` 是发现候选的辅助信息，不作源语义版本。
跑机后的 page save、无关 ui-spec 节点新增或同一候选列表排列变化不能令原派生 stale。
纯教学散文、显示路径标签、reset 不可用的错误措辞也不充当行为版本，真实约束由上表机器字段表示。
TC 行内名称/预期/AC 等仍按现有行契约比较，不能借“说明变化”放过行为行改写。

selector 选择的消费边界明确为：entries 给派生作者发现候选；正式步骤的 match/消歧语法由现有步骤 lint 校验，
当前 ui-spec 的同屏多映射、聚合节点与 acceptance action 冲突由 `lintDerivedPlanSelectorContract` 验证，
静态资料不足仍是原 WARN，最终 selector 真值来自本次 native StepResult。
因此本批不把整份 entries 另变成第二个 stale 门，也不因为“不参与 hint 比较”跳过任何当前检查。
最小正反例：新增无关节点/新增 snapshot 页，原步骤仍通过现有门且 hint 不写；
已使用的 by_text 在当前 ui-spec 变成确定同屏多映射且未消歧，现有 selector 门报该 TC/step 并拒绝执行，不能被稳定 hint 放行；
真实 match/消歧可执行语法或 reset 身份变更，参与语义比较与当前静态门。只做现有消费边界核对，不新建逐 TC 依赖图。

coverage/lint/选中派生诊断从 canonical hint 移到原 `device_test_run` check 的 details/structured，保留完整
coverage_reason、top/derived/missing/extra TC、selected/rejected 路径、原 mtime 与逐条 lint/suggested_fix。
summary/NEXT 指向原 script-report，Skill 改为读取该 check 的最新诊断；hint 的比较主体只承载稳定派生输入，
最新缓存/selector 辅助信息由本次 CLI stdout 或明确 `--out` 导出消费，不靠磁盘基线冒充每轮更新的诊断。
验收逐字段对照旧自动 payload 与新的 check 输出，不接受“停止更新旧 hint”却丢了当前诊断。

**旧文件与输出契约**：先归一旧 hint 的 source/source_relative、源 TC/知识字段；旧自动面的 hint 缺
selector_contract.entries、缓存列表等辅助字段，视为非比较字段缺席，不要求补写 canonical 或全量重派生。
旧 schema 4 没把 match/消歧固定词表写为独立数组的，用该 schema 已有的同一 selector/步骤契约归一，
不得从当前 TC/当前文件哈希补造遗失的源快照。canonical 在下一次真实语义变化时才随完整 payload 升级。
缺源 TC 或无法解释的真正可执行语义缺口才走原 stale/派生出口，不把“辅助字段不全”当缺口。

默认 CLI 即使 canonical 不写，也把当前完整 payload 发 stdout，包含最新 selector_contract/缓存辅助字段；
Skill 的派生作者读这次输出与 script-report 最新诊断，gate 文件消费者只读取磁盘基线的比较主体。
`--out <另一文件>` 是显式导出：完整写入本次 payload，保持原 stderr 路径提示，不改 canonical 也不赋予该导出文件源基线权威。
`--out` 若解析到 canonical 路径，仍采用同一语义幂等写入规则，不能强制刷新它的 mtime；
此情况下 stdout 同默认输出当前完整 payload，stderr 说明是否实际更新基线。
需要最新辅助信息的文件消费者必须使用明确的另一导出路径；文档给出该现有出口，不让它继续读未更新的 canonical 辅助字段猜当前状态。
测试覆盖默认 stdout、独立 --out 与 --out 指向 canonical 三种语义；旧文件缺辅助字段时前两种都可获得完整上下文，源基线不因此 stale。

保留“刷新 hint 不能洗绿旧步骤”：TC 自然语言步骤实变会写新 hint，旧派生 mtime 在前仍 stale；
实际重新派生并通过静态与后续验证才有效，不能只 touch 派生/改 hash 自证。
