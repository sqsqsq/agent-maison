## 3. 修复内容与责任入口

本批只改四个实际缺口：闭包加一类决定、设计 owner 标记补上 CU 路线、诊断透传缺失地址、范围派生时缺定档则内存推导。以下 t1 同时承载闭包与其拒绝/readiness 信息；不为每个落点另立机制。

### 3.1 原闭包纳入选型决定，拒绝信息给出地址（t1）

落点为 `change-unit-design-gate.ts::deriveClosure/validateChangeUnitDesign`，复用 `blueprint-addressing.ts` 的稳定地址索引。在现有 relations/scenarios 外扩的同一个循环内，遍历 canonical 蓝图中 `kind=component_asset_selection` 的决定：其精确 `target_ref` 已在当前闭包，就把 `decision:<decision_id>` 纳入闭包并继续原求解。不按自然语言或组件名称猜测，不建立第二份依赖清单。

**适用条件与 plan 同源**：和 `componentProjectionErrors` 一样，以 `fs.existsSync(componentIndexPath(projectRoot))` 为这类隐式外扩的启用条件，不能改成“索引非空”“有策展卡”或“全部资产可读”。无索引文件时不增加这一类外扩，原有显式 design_refs 与其它设计检查照常执行；索引存在但不可解析、选型非法等仍归原校验，不静默视为未启用。

同一目标若有多个选型决定，闭包全部纳入，不选一个“最佳/唯一”决定；未闭合、非法或冲突仍交已有的 `dispositionBlocks`、蓝图选型和依赖检查判断。本次不新增唯一性选择器，也不改候选或 canonical 内容。一条合法决定映射多个组件仍合法，设计期不要求未来的 contracts.change_unit、implementation_refs 或测试映射。

闭包缺引用时，原检查已经生成含稳定地址的 `message`。补齐信息出口：`change-unit-provider-boundary.ts::validateChangeUnitCandidate` 的拒绝文字保留 issue id，并带原 message；`change-unit-design-preparation.ts::deriveDesignPreparationReadiness` 的 perUnit 结果保留 issueIds，并透出对应 message/原 issue 详情。复用原 issue 内容，不另维护人工修法或由消息反向解析依赖。

设计 Agent 因此能在当前设计会话里看到例如 `decision:reuse-add-bank-page`，修改尚未接受的候选草稿并走原接受/readiness 循环。已有 CU 使用既有设计 owner 流程和 `reviseChangeUnitContent`，适用条件不变；机器检查/接受阶段不自动插入 design_refs，不从 plan 的 asset_selection 追认选型。

**验收**：有索引的候选漏引用时，在接受前返回准确地址、canonical 零写入；设计 Agent 替身依据真实拒绝结果补候选后，经原 consumer 接受、readiness 与 plan 投影通过。覆盖正确引用、多个决定均入闭包、多个组件共用、目标不在当前闭包、无索引、空索引、显式引用与非法索引沿原门处理。当前切片依赖的 open_decision/blocker 经原检查在设计期阻断，不拖到 plan；原来合法的“plan 声明下沉”场景也要保留，核实它不是靠把未决设计送入 plan 才能成立，不借本批取消合法下沉路线或放宽未决授权。

这条恢复通道已经存在：`goal-phase-runtime.ts::designOwnerBlockers` 识别设计责任，首次出现时按 `execution_scope_unresolved` 停放并挂 `design_authority_projectable`；`condition-wait.ts` 复用 `diagnoseDesignAuthority` 重评原发现，阻断消失才就绪；绑定变旧交既有恢复入口/关联 successor。既有 `design-authority-repair` 的 S15-wake 已覆盖探针就绪但旧绑定失效的接续，不另造“释放→主 Agent 修订→重发→新 continuation”流程。

实际缺线在 issue 转换：`change-unit-feature-projection.ts` 已把设计 gate 的 CU 问题路由为 `repair_change_unit`，但转换为 CheckResult 时仅给 `reconcile_blueprint` 添加设计 owner 标记。将相同的 `repair_owner: external` 和 `structured.kind: design_authority` 适用于 `repair_change_unit`，继续透传原 codes/reason，不把所有 component_asset_projection 都改成 external。

同时修 `blueprint-skill-projection.ts::DESIGN_AUTHORITY_CLASS_ROWS` 的责任文件分类：包含 `change_unit_design_closure_incomplete` / `change_unit_touch_development_owner_missing` 的行归 `change_unit`，说明修改 CU 的 design_refs / touches，不再指向蓝图；真正属于蓝图的未决决定/失效引用分类保持不变。复用原 B2 语义，不扩大 B1 自动修复授权。

| 成因 | 现有责任出口 |

| CU 设计闭包缺决定引用 | t1 产生 closure_incomplete；`repair_change_unit` 经设计 owner 标记进入原停放/探针链，责任文件为 CU |

### 3.3 未定档时由范围派生做一次内存推导（t4）

落点限定为 `feature-track.ts::collectResolvedScopeFacts` 的 fidelity 读取。其 `loadFidelityIntentSsotState` 为 missing 时，复用 `fidelity-shared.ts::resolveFidelityRoutingDecision`，按本调用已经解析的同源需求及适用的已有显式档位输入，在内存求出 selected fidelity，仅用于 `ResolvedScopeFacts` 的范围派生。没有第二套关键词判断，不新增状态文件、schema 字段或准备期身份。

这里的“同源需求”具体限定为：

- 有调用方实际提供的非空需求文本时，沿 `goal-preflight.ts` 的既有 `dereferenceRequirementDocs` 展开需求引用文档，再用合并文本推导档位；工程根、features 目录及当前 Feature 自引用排除口径与既有初始化器一致。不直接拿未展开的原始文本或需求文件路径判档。
- 没有实际需求文本的调用方保持原行为，包括 CU 交接投影、非 run 的设计检查器；定档仍为 missing，不从其它产物或请求摘要编出一份需求。
- `prepareFeatureScopeCandidate` 当前在缺需求时使用 `requested_results` 兜底。保留该兜底在既有视觉相关性判断中的用途，但不能把它当作本次定档推导的需求；调用处须区分这两种用途，不能因都经过同一个 `requirement` 参数就混用。不改变既有请求/需求绑定语义，不新增来源账本。

已有先例是 `goal-preflight.ts::evaluateDownstreamStartFidelity` 的 missing 分支：使用同一个纯函数，在内存判断而不写定档。候选准备、run 出生和范围修订都经过 `collectResolvedScopeFacts`，因此不在多个入口分别插初始化调用。valid 定档仍读原 SSOT；corrupt 不当 missing 重新猜测，沿既有错误/修复语义处理。

根因描述收窄为：范围原先需要已选定的 pixel 目标才能识别 spec 的视觉定义缺口，却只在磁盘定档已有时才能得到该目标；初始化又晚于这次范围判断，形成初始职责的循环前置。缺文件时的内存推导打破这个依赖。当前现场后来已有定档文件，这一事实保留，不把推演写成“本 run 从未定档”。

内存结果只服务范围判断，取 selected，不拿 effective 能力上限取消用户目标或把内存路由当作能力验证。首次链进入 spec 后，既有初始化器照常用 run 身份写 `fidelity-intent.json` 与 `capability-snapshot.json`，原能力预检/hard 目标判定保留。本批不调用准备期 initializer、不调整定档文件 writer 或覆写规则；查询、dry-run、重复准备/读取不因本改动新增落盘。

**验收**：经真实准备/出生入口传入原需求文件，不手动初始化、不预置定档文件；新 pixel UI 且缺视觉定义时，候选/冻结范围先识别 spec，首个内容调用为 spec，再按原流程初始化和进入 plan。testing required 保留，但不要求它出现在最初可执行链。补候选准备、出生、范围修订三处实际消费的直接回归；非 UI、generic/无 Feature 日常工程、单职责请求不被扩成完整交付，有效定档不改写、损坏定档不伪造有效。能力不足不导致内存 selected 降档或 hard 目标假通过。

需求取值反例一并覆盖：像素要求只写在被引用文档中时，内存推导与随后初始化器的 selected 一致；无需求文本的 CU 交接/非 run 检查仍保持 missing；仅 requested_results 含像素措辞时，不因此定档或新增 spec，候选与出生不因把兜底误当原需求而分歧。
