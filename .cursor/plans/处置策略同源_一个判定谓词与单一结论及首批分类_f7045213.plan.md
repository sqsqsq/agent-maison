## 1. 目标与冻结范围

**目标**：一个失败检查挡不挡、交给谁，有唯一出处；读它的地方得到相同的答案；不属于产品真值的失败不再让任务停下；
既有的真实阻断一个都不被误放。

**做**
- 处置函数、判定谓词、开发期静态守卫。
- 按消费矩阵收编，结论计算共享。
- 首批分类。
- 归因与恢复出口。

**不做**
- 不放宽产品真值类检查，不改任何检查本身的判定逻辑。
- 不动完成判定的十五项条件，不动逐义务缺口分类。"可以宣称完成"仍由它们决定。
- 不在运行时按"认不认识这个 id"来决定披露。
- 不逐个改写检查写点里的严重级别字面量。原始的严重级别与状态保留在报告里。
- 不合并质量轴、可修性、责任归属等既有表。
- 不为了统一顺序前移 compat 降级，不放松报告合法性与 request 入口的证据要求。

## 3. 处置函数与判定谓词（t1）

### 3.1 按保护对象四分

| 保护对象 | 判别 | 失败时的去向 |
|---|---|---|
| 产品真值 | 放过它，用户会拿到一个坏产品 | 阻断本阶段通过，回责任方。现状不变 |
| 结果依据 | 放过它，产品未必坏，但"通过"这个结论不再有依据 | 阻断本阶段通过，必须有可执行的责任方恢复出口，见 §7 |
| 账本与形状 | 放过它，产品与结论都不受影响，只是记录不好看 | 能确定性对齐的自动对齐；对不齐的披露，不阻断 |
| 能力缺口 | 这台机器这一轮做不到 | 沿用既有的能力缺口通道 |

判别顺序沿用 e7a2c4f1 §1.2：先判实际影响，再判证据是否足够，再取最小动作，最后才重试。

### 3.2 去向表

新文件 `harness/scripts/utils/check-disposition.ts`。

去向表只登记去向**发生变化**的检查。每条：

| 项 | 内容 |
|---|---|
| 匹配 | 精确 id；或受限的动态族，写明固定前缀与产出它的生产点 |
| 保护对象 | 四类之一 |
| 责任方 | 结果依据类必填，取当前阶段或 spec、plan、coding 之一 |
| 依据 | 事故或清单编号 |
| 放过的后果 | 一句话 |

动态族不接受过宽的前缀。一个族只对应一个生产点；族的前缀不得是另一个已有检查 id 的前缀。

### 3.3 处置函数

输入一个检查结果，输出去向。规则按序：

1. 检查不是失败，或严重级别不是阻断：不阻断。
2. 检查命中去向表：按表。
3. 其余：按检查自己声明的严重级别与状态。

没有第四条。运行时认不出的 id，包括动态拼出来的、经包装的、用常量间接定义的，都走第 3 条，保持原处置。
本 plan 落地时，没有登记的检查行为不变。

判定谓词：输入一个检查结果，输出它是否阻断本阶段通过。它只是处置函数的布尔投影。

### 3.4 开发期静态守卫

"新增的阻断检查必须先声明它保护什么"由开发期保证：

| 项 | 内容 |
|---|---|
| 基线 | 由脚本从当前生产代码生成：每个源文件里，以字面量构造的阻断检查的 id 集合，以及 id 不是字面量的阻断构造的个数。随开发仓版本管理，不手写 |
| 守卫一 | 出现一个不在基线里的字面量 id，且它不在去向表里：红 |
| 守卫二 | 某个文件里 id 非字面量的阻断构造个数超过基线：红。要新增动态族，就在去向表里登记这个族并重新生成基线 |
| 守卫三 | 谓词模块之外出现"状态为失败且严重级别为阻断"的字面判断：红。§4.1 里标明保留原生语义的位置与两处不读检查结果的位置显式豁免 |

严重级别与状态由变量、展开或辅助函数给出的构造不在扫描范围内，这是静态扫描的边界，与既有的修复建议守卫相同。
这类构造运行时走 §3.3 的第 3 条，行为不变。

### 4.2 compat 与谓词的先后

- 检查执行期：聚合状态、ut 覆盖报告、违规钩子在 compat 降级之前运行，它们读到的是降级之前的检查。这是现状，不改。
- 报告消费期：结论、计数、质量轴、阻断清单在 compat 降级之后求值。
- 谓词在两个时期用的是同一个函数，读到什么就判什么。本 plan 不承诺两个时期读到相同的检查。

### 4.3 披露清单与完成缺口

- summary 增加一项：被披露的失败清单，每条含 id、保护对象、原始严重级别、详情摘录。
- 完成缺口数把这份清单的条数计入。有被披露的失败时，完成标签为带缺口的完成。这只是披露，不阻塞完成。
- goal 报告与控制台各渲染一次。

### 4.4 聚合的运行状态检查

| 情形 | 处理 |
|---|---|
| 聚合失败，同一失败已有源 blocker 表达 | 聚合项不进入阻断清单、签名与计数 |
| 聚合失败，没有任何源 blocker，例如只由关键的阻断跳过或文档缺失引起 | 聚合项保留在阻断清单、签名与计数里 |

聚合项照常产出，照常参与结论。运行时的归因与签名因此总有输入。

## 12. 放弃的准确性与已知代价

1. 既有检查里仍有大量账本与形状类的阻断。本 plan 只改首批登记的那些，其余留给 P5。
2. 静态守卫扫不到严重级别由变量或辅助函数给出的构造。这样写出来的新阻断检查不会被要求登记。
3. 被披露的失败只进清单与完成标签。没有人看清单时，它等于没有被处理。
4. 结论共享之后，过去退出码为 0 而 summary 判失败的情形会变成退出码非零。依赖旧退出码的外部脚本会受影响。
5. 报告形状类的分界靠逐条取证来判，判错一条就是一次误放或一次误拦。
6. 两个时期读到的检查可能不同：检查执行期在 compat 降级之前，报告消费期在之后。
