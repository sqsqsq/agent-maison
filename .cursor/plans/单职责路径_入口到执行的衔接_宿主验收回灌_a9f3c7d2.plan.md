| 笔 | 条款 | 一句话 |

用例不存在」的欠账。故第一笔在**既有** `framework-init-entry-contract` 套件里追加并锁 R1/R3/R4 的文字，第二笔在同一套件追加 R2/R5 的文字断言，

## 3. 需求 §8 七个问题的回答

### 问题 1 — R1 两步判断在模板里的文字与位置；与「正式需求进入 component-design」如何衔接而不产生第三类

**位置**：原位重写 `templates/AGENTS.md.template:46-50`（§4.0 整节），不新增小节、不新增表格行。
重写后 7 行（heading + 空行 + 2 行 blockquote + 空行 + 1 行正文 + 空行），模板从 114 行到 **116/120**。

**不产生第三类的机制**：两问是**同一次判类的两个提问**，不是两个分类轴。分类结果仍只有既有两类
（正式需求 / 非正式维护）；第二问只改变**得出分类前必须先做的事**（查依据），以及
**非正式维护也要说明本次按什么算对**。「补测试」不因第二问被强制升格为正式需求——只有
「涉及新增或变更预期」才进入设计职责。

**完整文字草稿**（中文，替换 `:46-50`）：

```markdown
### 4.0 需求路由（正式性与请求终点）

> **两问定路由**：① 本轮要动什么（**范围**）；② 按什么标准算对（**验收语义**）。「不改实现」只回答①，不免除②。
> **正式需求**＝有明确交付或验收责任，且拟改变**部件行为、外部契约、数据/NFR、运行语义或架构责任**的事项；不改变这些语义的**纯文档和机械维护**除外。

判类前**先查已有依据**（既有 acceptance、蓝图、[{{MODULE_CATALOG_PATH}}]({{MODULE_CATALOG_PATH}})、约束知识）：查到即复用并写明引用；只有涉及**新增或变更预期**才进入设计职责，再决定复用、修订还是新建蓝图——不因「不改实现」跳过②，也不因「补测试」强制新建蓝图。查完仍存在影响断言或交付的语义缺口时，**只就该缺口**问用户。正式需求进入 [component-design](framework/skills/project/component-design/SKILL.md)，沿已有需求源、蓝图与 CU 设计继续；上游明确的正式分类不得降级。非正式维护按本次范围直接完成、不创建蓝图；**任何需要编译或跑测试的校验一律经框架执行器**（专项 request CLI 或 `harness-runner --phase`），不裸调 hvigor 或宿主自带脚本——执行器会从 `framework.local.json` 派生工具链环境（`DEVECO_SDK_HOME` / JBR），裸调必然丢掉它。
```

### 问题 2 — R2 预期来源的登记位置、request 检查如何呈现、对既有 feature 主体 UT 零影响的论证

**登记位置 = 测试文件内标注**，不动请求 JSON、不动 facts。三个理由，全部可核实：

1. 请求 JSON **加不了**字段：`capability-resolution-entry-input.ts:82` 的顶层键白名单会直接抛
   `request: unknown field`；加键即改 schema，违反需求 §3 R2「不新增 schema 体系」。
2. facts.md 是 report-dir 内的一次性产物，**不随测试文件走**；下一次请求、下一个人读到这份测试时
   拿不到登记，问题会原样复发。
3. 测试文件的字节**已经**被本次请求绑定：`bindings`/`sourceContents`（`:142-157`）覆盖它，
   运行中被改会被 `request_execution_inputs_changed`（`request-phase.ts:90`，逐字节比较 `bindings`）拦住。
   登记放这里天然防篡改，零新增机制。（注意：`request_sha256` **不**覆盖授权写入的测试文件——
   `capability-resolution-entry-input.ts:163` 显式把它们排除在指纹外，保护来自上面那条执行前后 bindings 比较。）

**标注形态：每条断言自带，无继承（复用既有词表，只补一个能承载路径的载体）**：

| 标注 | 含义 | 复用目标 |
|---|---|---|
| 断言名以 `[CHAR-xxx]` 起始 | characterization：只记录现状 | 既有 it 名标签词表（`check-ut.ts:2164,2184,2196` 已定义 `[CHAR-*]` 语义） |
| 断言名以 `[AC-*]` / `[BD-*]` / `[BRANCH-*]` 起始 | 已登记来源（**仅标签形态**，见下表「来源形态两分」） | 同一套既有追溯标签词表 |
| **紧邻声明行之上的连续注释行**里的 `// characterization` | 同第一行（ets 里不想改断言名时用） | 无新词表 |
| **紧邻声明行之上的连续注释行**里的 `// expectation: <项目内相对路径>[#锚点]` | 已登记来源（**路径已核**） | 承载路径的唯一新增微约定 |
| `describe(` 上的标注、文件头总括注释 | **不算登记**，任何断言都不继承 | 第三轮裁决：取消作用域继承 |

**解析语法与集合边界**（演进经过见 §11 第一轮 M2 / 第二轮 B2 / 第三轮 B1，正文只写现行方案）：

**登记只认每条断言自身，没有作用域继承**（第三轮裁决）。理由是可核实的：`ut-it-blocks.ts:25-35` 的花括号配平
逐字符数 `{` `}`，**不区分字符串、模板字面量与注释**，回调体里出现 `'{'`、模板字面量或 `// {` 就会把闭合范围
算到错误位置——继承规则建立在这个算法上必然误判，而那种文件并非零解析，FAIL 兜底也拦不住。
**不写词法分析器**：改成十几行的**按行扫描**，问题从根上消失。

| 项 | 规则 | 依据 / 边界 |
|---|---|---|
| 声明行识别 | **只认行首（忽略缩进）起的 `it(` / `test(`**——即该行第一个非空白 token 就是它，且名字是同行的字符串字面量。写在注释里（`// it('x')`）或字符串中间的不算声明 | 纯行扫描，不做括号配平；「认不全」的形态由下一行的**数量对账**统一兜住，不逐形态支持 |
| **数量对账（本节的兜底闸，第四轮 B1 裁决）** | 每个**授权文件**：分类器识别出的 `it(` 形态条数**必须等于**既有 `extractUtItBlocks(content).length`（执行器同源提取器，`ut-it-blocks.ts:15` 的全局正则，**保持不动**）。不等 → **BLOCKER FAIL**，details 列出两个数与差值 | 行扫描只防「零解析」，防不住**部分解析**：把 `it('[CHAR-known] a', 0, () => {});` 与 `it('b', 0, () => {});` 写在**同一行**时，行扫描只认第 1 条（characterization 1 / 未登记 0 / 非零解析），而执行器按 `extractUtItBlocks` 数到 2 条并要求 2 条都执行（`ut-run.ts:34,47`）——两条都通过时来源检查与执行检查会**同时 PASS**。第一道对账把「同行多条、`it(` 后换行才写名字、名字用模板字面量或变量」这类**两侧计数会分叉**的形态落到 FAIL 一侧；`it.skip(` / `xit(` / `it.each` 这类**两侧都认不出**的变体由**第二道对账与 provider 既有检查共同处理**（见下一行与 provider 口径表）。都不必逐形态支持 |
| **第二道对账：识别总数 = provider `total`（第五轮裁决，适用于所有授权文件，不只纯 `test(`）** | 已执行（`executed === true`）时，全部目标文件的识别总数**必须等于** provider 返回的 `total`。不等 → 授权面 **BLOCKER FAIL**（details 列两个数与差值），只读面 WARN。`executed === false` 时本条**不适用**，沿用既有「未执行」呈现 | 第一道对账堵不住 **`it` 与 `it.skip` 分行混排**：`it.skip(` 既不被行扫描认（首 token 不是 `it(`），也不被 `ut-it-blocks.ts:15` 的正则认（`it` 后是 `.` 不是 `(`）——两边都数 1，①相等而漏检。执行器那边照样把它算进去，于是 `total` 与识别总数分叉 |
| 只读历史文件数量不等 | **WARN**，不新增阻断 | 与「历史不问责」同一条原则 |

**两个 provider 的 `total` 对 skip 的计数口径（如实写，不笼统说「已覆盖」）**：

| provider | `total` 从哪来 | 含不含 skipped | `it`+`it.skip` 分行混排由谁拦下 |
|---|---|---|---|
| 专项夹具用的 Node provider（`request-entry.unit.test.ts:33-36`） | `node --test --test-reporter=tap` 输出里的 `# tests N` | **含**——本机实跑确认：`test(a)` + `test.skip(b)` → `# tests 2 / # pass 1 / # fail 0 / # skipped 1` | **本 plan 的第二道对账**：识别 1 ≠ `total` 2 → BLOCKER FAIL（`request_test_execution` 那边 `failed === 0` 仍会 PASS，所以必须靠这一条） |
| hmos `ut.run`（`ut-run.ts` → `hdc-runner.ts:1161-1175`） | Hypium `OHOS_REPORT_RESULT` 的 `Tests run: X`，`skipped` 另取 `Ignore: V` | **仓内无证据可判**（取决于设备侧 reporter 的语义，不在本仓代码内） | 当 `Tests run` 含 Ignore 时同样由第二道对账拦下；**即使不含**，也由 **`ut-run.ts:47` 既有的两条判据**兜住——它要求 `result.testResult.total === group.count`（`group.count` 是 `extractUtItBlocks` 的计数，`:34`）**且** `skipped === 0`，任一不成立即 `request_ut_native` FAIL |

| 登记位置 | **每条断言自带**，两种等价形态（`/* */` 块注释**明确不算标注**，只认 `//` 行注释）：① 断言名里的标签——沿用既有追溯标签词表（`[AC-*]` / `[BD-*]` / `[BRANCH-*]`，characterization 用 `[CHAR-*]`，`check-ut.ts:2164-2196`）；② **紧邻声明行之上的连续注释行**里的 `// expectation: <项目内相对路径>[#锚点]` 或 `// characterization` | 「紧邻」= 声明行上方连续的注释行块，中间不得隔空行或代码 |

| **零解析（只读历史文件）** | **WARN**：`<file> 解析不到可识别的断言声明，本次无法分类呈现`——历史文件不是本次授权面，不新增阻断 | 与「呈现面覆盖 targets.tests 全体、历史不问责」同一条原则 |
| **问责范围**（BLOCKER 面） | 只覆盖 `allowed_test_writes` 点名的文件 = 本次授权新增/改写的断言 | `capability-resolution-entry-input.ts:94,97` 保证该数组只在 ut 且只能点名 `targets.tests` |

**检查项（新增一项，只在 UT 专项分支产出）**：

| 字段 | 取值 |
|---|---|
| check id | `request_expectation_source` |
| category / severity | `structure` / `BLOCKER` |
| 作用域 | 仅 `ctx.phase === 'ut'`；问责面与呈现面按上表二分 |
| **PASS（唯一判据）** | 授权集合内**四条同时成立**：① 识别条数 = `extractUtItBlocks` 条数；② **识别总数 = provider `total`**（仅 `executed === true` 时适用）；③ **未登记 0**；④ **非零解析**。`description` = 「预期来源登记」；`details` 三栏分列不混报：`已登记来源 S 条` / `现状记录 N 条（characterization，仅记录现状，不构成正确性结论）` / `历史未登记 H 条（只读目标，不问责）`；`structured.expectation_classes` 逐条列 `{file, it, class, ref?, ref_sha256?, scope:'authorized'\|'readonly'}` |
| **FAIL** | 四种情形（PASS 四条判据的反面）：① `unregistered ≥ 1`；② 授权文件零解析；③ 第一道对账不等；④ **第二道对账不等**（识别总数 ≠ `total`）。`details` 点名到文件/断言名并给出差值；`suggestion` 逐字包含下方「补齐方法」三句，对账不等时再加排版要求那句，**不提供第三条出路** |

| 来源核验边界 | 只核 `ref` 路径存在、在项目内（复用 `isInsideProjectRoot`）、可读并记录 sha256——与 P8 对 `request.impact.basis` 的边界同款；**不判断语义上是否真的支持该断言** |
| **补齐方法（写进 suggestion，逐字）** | ① `文件头或 describe 上的标注不算登记`；② `在每条用例名前加 [CHAR-…]，或在紧邻该行上方加 // characterization`；③ `保留原测试与期望值，不要为过检查改断言`；对账不等时再加：④ `每条断言单独成行、以 it( 或 test( 起行、名字用字符串字面量，并逐条登记；不要用 skip / each 等变体绕开登记` | 宿主重跑时 agent 拿到的就是这几句——它决定了 H1/H4 能不能观察到「正确补齐」而不是「改门禁」 |

**「登记数量」与「验证结论」分开**：provider 只给聚合结果（`request-phase.ts:20` 的 `{executed,total,failed,…}`、
`ut-run.ts:43-53` 按模块聚合并把「跳过/数量不符」折进 `failed`），**没有 it→结果映射**。所以：

- 本检查只报登记（`已登记来源 S 条`、`现状记录 N 条`），**措辞里不得出现「通过 M 条」**；「通过」只由既有
  `request_test_execution` 说；
- 两个执行状态**各自独立**追加一行说明（逐字）：
  失败 → `已登记来源 1 条；现状记录 0 条。本次存在失败用例，登记数不代表通过数（逐用例归属不可得）。`
  未执行 → `已登记来源 1 条；现状记录 0 条。本次用例未执行，登记数不代表通过数（逐用例归属不可得）。`
- 仅当 `executed === true && failed === 0 && total === 解析出的断言总数`（判断放在 `request-phase.ts:22-23`
  的 provider 结果有效性检查之后）才写一句合并结论「本次全部用例实际执行通过」，**不按类拆分**。
- **同一个等式就是上表的第二道对账**（适用于所有授权文件）：`executed === true` 而 `total ≠ 识别总数` 时，
  授权面判 FAIL、只读面 WARN，不再只是「不写那句合并结论」；`executed === false` 时该条不适用。

**裁决（需求 §3 R2，2026-09-17）**：明确标注为 characterization 的断言是**合法请求**——用户有权只要「记录现状」，
框架不得因此判 FAIL。**但宿主那份 `MaskUtil.test.ets` 今天过不了**：它只有一句**文件头**中文注释
（「固化当前实现行为…短输入用例记录的是现状，含明文泄露」），没有 `[CHAR-*]` 标签、也没有紧邻各条断言的
`// characterization`——按「每条断言自带标注、文件头不算」的规则，**每一条都是未登记 → BLOCKER FAIL**。
**这正是预期结果**（不是误伤）：agent 补上逐条标注后即可通过，结果呈现为「现状记录 N 条」而不是「正确性通过」。
宿主重跑时 H1/H4 按这一点观察。

不早退：该检查与 provider 执行并列产出，执行结果仍照常报告（不因未登记就不跑测试）。

**机器只证明「登记有效」，语义核对是写测试的 agent 的四步职责**：

只核路径可读是不够的——给 MaskUtil 测试补上 `// expectation: doc/module-catalog.yaml#CommFunc` 路径全对，
但该条目写的是「长度 `<= 7` 时原样返回」＝**现状记载**；`security-privacy.md:19` 的 SEC-01 只要求脱敏、
**没规定**短输入输出什么。拿它们当授权预期就是把现状洗成要求（事故根因）。故 `business-ut`（B3）写成
**四步可执行动作 + 一句判别句**：

1. **读具体条目**：打开引用的文件与锚点，读它那一条的原文，不凭文件名或标题推断；
2. **区分现状描述与授权要求**：**catalog / 源码注释 / 既有测试 / 实现代码这类「记载当前是什么」的条目，
   不构成 sourced 依据**；只有 acceptance / 验收条目 / 约束知识里**规定「应当是什么」**的条目才算。
   同一份文件里两种条目可以并存，按**被引的那一条**判，不按文件判；
3. **逐类断言核对**：把本次每一类断言的预期与该条目的原文逐条对照，写下对照结论
   （命中 / 不命中 / 该条目没说）；
4. **登记或标注（逐条写在断言自己身上）**：对得上就登记来源；对不上、或该条目只描述现状 → 标 `characterization`。
   **写在每条断言的名字里（`[CHAR-*]` / `[AC-*]` 等标签）或紧邻它上方的 `//` 注释行**——
   写在 `describe(` 上或文件头的总括注释**不算登记**（框架不做作用域继承），`/* */` 块注释也不算。
   另：**每条断言单独成行、以 `it(` 或 `test(` 起行、名字用字符串字面量，不要用 `skip` / `each` 等变体绕开登记**——
   否则两道数量对账会判 FAIL（§3 问题 2）。
   **依据要求应当失败的断言保留失败与原因**，「不改实现」不授权为跑绿改期望。

**核对说明落既有 facts**，不新增载体：第 3 步的对照结论写进请求本就要求的
`report-dir/context/facts.md`（`capability-resolution-entry-input.ts:130-133,171`）的 `## phase_delta: ut` 节。
**但既有 gate 不强制该节非空**——本 plan **不声称**「既有 gate 已验证四步完成」：四步的兑现由
**技能 smoke**（锁判别句与四步动词）+ **宿主 H1**（看行为，含把 catalog 现状记载当授权预期即判不通过的反例判据）判定，
机器面只保证「有登记、登记可核验」。不新增分类器、verifier、字段或门禁。

**对既有 feature 主体 UT 零影响（三面，均可核实）**：① **调用面**——新检查在 `checkRequestTests` 内，
只被 `check-ut.ts:4321` / `check-testing.ts:5936` 在 `ctx.subject === 'request'` 时调用，feature 主体从 `:4322`
往下走、物理上到不了；② **数据面**——判据是 `ctx.request.allowed_test_writes` / `sourceContents`，
feature 上下文没有 `request` 字段（`:4320` 的联合类型分流即证）；③ **词表面**——`it_name_has_ac_or_branch_tag`
（`check-ut.ts:2164-2196`）与 `extractUtItBlocks` 一行不改，由 `feature-body UT behavior is unchanged…` 用例锁。
不新增 verifier（需求 §3 R2 末条）。

### 问题 3 — R3 `--prepare-request` 暴露落点 gap 的实现位置、是否需要 provider 只读探测、无载体判定依据

**实现位置**：`request-phase.ts:58-62`。把 `loadResolvedProfile`（现 `:62`）**前移到** `--prepare-request`
早退之前，早退分支改为把能力缺口并进既有 `gaps` 数组后再打印。改动量 = 一次移动 + 一个 helper 调用。

**gap 来源两条**：

1. **两条都要判，不能只判前者**（第二轮必修 5）：
   ① `profile.phasesDisabled.has(phase)` → `capability:phase_disabled:<phase>`（现在只在执行期出现，`request-phase.ts:76`）；
   ② **capability 被声明为 SKIP** → `capability:<ut.run|device_test.run>:capability_skipped`——复用既有
   `isCapabilitySkipped`（`capability-registry.ts:24-27`，与 `dispatchRequestTests:189-193` 同一判据）。
   `profiles/generic/profile.yaml` 两者都写了（`:13-17` 禁用阶段、`:19-27` `ut.run: SKIP`），
   只判①就只能给出一个来源，矩阵里「两个来源都断言」的那条会落空。
2. provider 只读探测（**需要**，但不是新造判定，且**边界要划准**——codex 必修 3 属实）：
   把 `ut-run.ts:25-30` 的**模块归属**判定提取成同文件导出的纯函数
   `inspectRequestTargets(projectRoot, tests) => { groups, gaps[] }`，`runRequestTests` 原位改调它，
   并把它登记进 provider 的 `exports`（`ut-run.ts:16`）供准备期调用。分发用 `capability-registry.ts` 新增

② 同文件 `:50-51` 用「除本阶段外仍有 required 未满足义务」算 `remaining`，单阶段请求这里恒为空 → 早退；
③ 没有提案时 `feature-track.ts:704` 返回 null，出生时的 `acceptance-context` / `design-context` unknown 永远留着，
`assess.ts:899` 据此判 `execution_scope_unresolved`。
于是宿主上「只写 spec / 只出 plan」即使产出合法 acceptance/contracts、阶段检查全 PASS，run 仍 HALTED。
**我上一版把 HALTED 锁成了预期断言，等于把缺陷锁成规格**；plan 里「桩不产出 acceptance」的说法对 spec 也不准确

**改哪几处**（复用既有修订链：`designScopeRevisionChecks` → script-report `scope_revision_input` → `scope_revised`；
**R5 侧不新增事件类型、运行期持久状态、schema、注册表或 flag**——口径按条款分别写准，见 §9「新增字段口径」）：
