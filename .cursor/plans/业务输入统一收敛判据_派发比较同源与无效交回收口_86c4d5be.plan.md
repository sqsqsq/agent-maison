# 业务输入统一收敛判据

## 目标与基线

承接 [e2a4145e](初始设计质询死循环修复_否定交作者与评审问题呈现_e2a4145e.plan.md) 划出的跨路径工作。起草基线是 `248f22b8` 加 `6a2f8c91` 和 `e2a4145e` 已交接、尚未提交的实现。后者的代码检视与目标回归已通过，合并全量及真实宿主停止现场仍待验收。本 plan 的起草不代表它们已完成发布验收。

按 [架构 I10](../../docs/architecture.md) 与 [四条总设计原则](../../docs/overview.md#121-四条总设计原则)，同一项工作只有出现真实新条件才自动重派；有效反馈已到作者、作者真实交回、独立检查仍无验收改善时可续暂停。结果未知时保留未知及具体解除条件。用户原目标、授权、验收与明确截止仍由现有责任入口控制。

上述文本对照证明了决策入口的确定性差异。作者、verifier 和 supervisor 的对照尚未作为新的宿主无限循环事故复现，不把一次多派等同于已证明整条业务链无界。

`evaluateCompletionProgress` 的对照也确认，同对象、同输入、反馈已送达且作者已交回时，已完成评估可返回 halt；把当前评估改为未完成便不会 halt。这符合“未知不假判无改善”的契约，闭环应由派发端识别缺少新工作条件。

## 统一比较，复用两种既有决定

1. **是否存在可执行的新条件。** `prepareExecutionContext` 和 `hasNewWorkConditions` 继续负责派发前判断。普通完成、失败重派、next/report、resume 和 detached 都从既有原件重建，首次工作及尚未送达的真实反馈正常派发。
2. **已完成评估是否有验收改善。** `evaluateCompletionProgress` 继续负责已完成结果、真实反馈送达及作者交回之间的比较。未知结果不改成 completed；同输入下重复未知或坏交回走已有等待出口，保留具体缺口和恢复路径。

调用编号、轮次、时间戳、格式错误的字符位置、原报告地址、同一结果的重渲文字以及本调用的输出归档，均不能单独构成新条件。真实产品/候选、原请求或已批准范围、相关事实与证据、用户新诊断输入、获准的执行能力或原探针恢复可以构成新条件。新条件只影响所需职责，不自动授予改目标、扩权、改验收或延长截止的权限。

## 最小数据接线

### 作者与设计职责

在既有 `WorkUnitExecutionContext` 增加一个可选 `workInput`。其中 `material` 保存本次调用的分段比较材料。有调用前完成评估的职责将现有 `CompletionEvaluation` 一并保存为 `evaluation`，直接取自工作单元的 `readWork`、初始设计的当前观察或设计修复的 `evaluationOf`。本次明确传入的 repair notes 通过现有输入快照形状纳入业务输入，完整文字仍供作者读取。

`renderWorkUnitAuthorFeedback` 在生成作者提示时读取当时的阶段 summary 和检查报告。下一次调用可能已覆盖同一路径的报告，单凭旧 `CompletionEvaluation` 无法重现当时送达的处置段。`workInput` 由运行时派生，不新增文件、台账、nonce、签名层或注册表。

派发准备时，提示组装方用同一批已读取的输入同时生成实际 instruction 和下表的 `material`。在组装各段时就以处置投影替代渲染段、以规范请求替代 `requestText`，把所得比较材料冻结进 `workInput`。本次派发判断读取当前准备好的冻结值。签发时，`writePhaseExecutionRequestMaterial` 将同一个 `workInput` 随 process/session 请求原件一并保存并绑定到已有请求哈希。后续派发或冷恢复通过 `executionRequestForInvoke` 取原件，历史侧只读其中的 `context.workInput.material`，禁止读取当前报告重渲旧反馈或从整段旧 instruction 反推分段。产品变化仍由既有调用前后快照判断。

| 现有组成 | 比较方式 |
| --- | --- |
| 渲染的处置/作者反馈段 | 准备时取该段实际对应的 disposition，复用现有 `problemIdentity/dispositionFacts`，把投影写入 `material`。它保留 action、affects、责任方、实际对象及证据身份。detail 全文随提示送达。验收键、相关输入快照和检查族仍按冻结的完成评估比较。 |
| verifier 的 `requestText` | 用 `canonicalRequestInput` 替代该请求段；审计字段仍保留在实际请求中，不参与业务差异。 |
| 当前职责 | 将既有请求的 `purpose` 纳入比较，当前值取调用参数；初设作者、拆分、范围补充等具体工作仍保留各自签发的职责与目标对象，不仅按 author/verifier 合并。 |

| 已确认的展示与运输内容 | 仅作线索的前次作者最终正文、同一质询结果的历史问答重渲、调用编号/日志地址/时间、原生会话重建提示及 session 运输后缀不单独产生新条件；完整原文照常保留供读取。它们所指的真实候选、证据及新反馈仍进入对应业务输入比较。 |

仅替换上述有明确来源的投影段并剔除已确认的展示噪声，不做任意自然语言的语义等价判断，也不把所有非处置文字一并丢弃。首次补格式反馈按下节的实际送达事实区分，不能作为普通诊断噪声删除。

反馈送达由原请求中实际冻结的对应输入及真实交回事件证明，不再依赖 `instruction.includes(render...)`。替换以下现有判断，保留其业务作用；定位行号为起草基线，以函数/变量为准：

- `goal-phase-runtime.ts:7826/:7829/:7840/:7884` 的 `newDriverHypothesis`、`authorFeedbackDelivered`、`checkedFeedbackDelivered` 和 verifier 的 `notes` 选择；新诊断能交给作者，已实际送达的诊断继续进入核验材料。
- `goal-phase-runtime.ts:4789/:5029` 的初设 `designFeedbackDelivered` 与 `invokeDesignOwner` 中的设计修复反馈送达；保持否定、作者交回和独立复核的因果顺序。
- `design-repair-unattended.ts:263` 的 `deriveDesignDeclineFeedback`；保留候选身份、拒修发生顺序和作者实际收到反馈的判断，不因删掉文字匹配而重复送达或吞掉拒修反馈。

初设和设计修复使用 `blueprintAuthorContent`、现有候选内容快照及 scope 级发现身份。同一 scope 的细粒度新问题拆分继续沿 e2a4145e 的既定范围；单纯问题或回答换措辞不会重置无改善窗口。真实新增证据、作者改稿和用户补充仍通过各自实际输入进入比较。

### verifier、检查工具与输出归档

verifier 直接复用 `canonicalRequestInput` 及材料视图。`purpose` 参与比较，但不能单独代表首次核验与补格式：现有核验入口可一直使用 `verifier_format_repair`，两条设计质询路径也在补格式时继续使用 `questioning`。首次不可用交回产生一份尚未送达的补格式反馈，按原调用/交回事实派生，给原职责一个明确的补格式机会；该反馈已实际送达且再次坏交回时，若对象和其它真实输入未变则等待。沿用 e2a4145e 的固定补格式提示与原件读取方式，不新增计数、持久字段或台账；原始答复、解析位置和诊断措辞变化不反复生成新反馈。实际审查材料、规则或获准执行能力改变，按原签发链更新输入并仅补受影响验证。

检查工具保留 `readCurrentCheckObservation` 与 `checkWorkConditions`。框架写入的本轮输出和人读投影不作为该 producer 的新业务输入，继续按已有输入/输出角色和调用前后事实判别。先核写界，再做重复比较；其它真实改动及后续职责消费的产物仍有效，不能整段排除 reports 或 goal-runs 来隐藏变化。保留 e2a4145e 已验证的原文归档窄例外及坏交回回归；指令投影不会代替文件快照中的归档判别，本批不将该例外泛化成新归属机制。只删除确已被同源比较替代的旧判断，保留首次补格式提示和有实际阅读价值的上下文。

### 自动恢复与旧原件

supervisor 保持 `reduceRunState`、存活观察和既有 `conditionProbe` 的职责边界，`decideSupervision` 仍是纯决策函数，不读取产品文件、不引入运行时输入比较。首次失联按既有接续规则处理；最近一次实际重启到再次 `uncaught_exception` 之间，若没有真实完成交回且无已核实的恢复条件，则 `no_op`，删除错误全文相等判据。完成交回复用既有调用/检查结束语义（调用使用 `invocationCompleted`），不把任意 end、启动、超时、waiting 或旧原件的重复消费当作完成。

有真实完成交回时，只说明恢复执行已经推进，允许在原 disposition 与存活规则下接续；是否出现新的可派发业务仍由运行时比较，不据此声称验收改善。保留原启动尚未交回不重复启动、原探针恢复和用户明确继续的入口；真实输入变化由运行时恢复入口消费。原件不足时说明未知执行条件，保全现场并沿原恢复入口接回，不按累计重启次数停机。

旧请求缺少 `workInput` 或其中的冻结 `material` 时，沿用既有严格比较。历史侧只取该请求及关联原件当时保存的指令和结构化事实，无法核实的输入保留为未知。不得用当前报告补写旧原件，也不因补字段而重跑已完成工作。下一次因真实新条件签发的请求自然带上冻结值，此后的恢复直接读取该请求，继续承接有效完成结果、作者产出和已有停点。

仍未结束、没有新检查观察的原生调用不因缺记录就被判为死循环；它继续受原调用回收、工具超时、用户取消及明确截止约束。业务无改善暂停继续使用 `no_progress_guard`，未知条件使用原 `executor_waiting/no_op`，不新增停机原因或计数额度。

## 验收与交付

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| 同一作者输入仅变日志路径、时间、处置重渲、历史答复展示或原会话重建提示 | 真实正常交回后无新业务输入不多派；展示内容位于处置段之外时也不能重新获得派发资格。 |
| 处置投影相同，非处置部分出现真实新输入 | repair notes、获准能力块或设计拒修反馈改变时，相关职责仍能收到新工作；初设作者转拆分/范围补充不被误合并。只改展示措辞的对照仍等待。 |
| verifier 同一 subject 仅变审计字段、错误位置或坏输出措辞 | 不产生新的审查对象或重复补格式机会；实际 material/规则变化后仅补所需核验。 |
| 同一对象首次坏交回，且 purpose 不变 | 正常首次调用后，第一次不可用交回仍能派发一次明确补格式反馈；补回有效对象即消费，再次坏交回且无新条件则等待。重复 report、next/resume 不再派第三次；覆盖 verifier 与两条设计质询路径。 |
| 有效否定、同对象无改善与部分改善 | 首次否定送达作者；真实作者交回和有效复核后同差额暂停，关闭一项后继续；未知评估保持未知并停止无条件重派。 |
| 框架归档、投影与真实产物 | 自身输出归档/重渲不购买同 producer 的再次调用；真实代码、需求、候选、契约或相关证据变化可被消费；越界写入仍由原检查发现。 |
| supervisor 重启后再次异常，错误相同或仅改调用路径 | 重启至再次异常之间无完成交回且无恢复条件时均为 no_op；有真实完成交回时按原 disposition 允许接续，业务是否重派仍由运行时判断。启动/超时/waiting 不冒充完成；原探针恢复或用户明确继续可接回，保留原启动未交回不重复启动的断言。 |
| 冷恢复与运输等价 | process、session、重复 report、next/resume 和缺冻结材料的旧请求均承接已有成果与反馈。两次调用准备之间，用相同业务事实覆盖同一路径的检查报告，使作者反馈的展示文字变化。以保留旧报告的运行为对照，进程内及冷恢复的派发比较结果均与对照一致，继续等待。 |
