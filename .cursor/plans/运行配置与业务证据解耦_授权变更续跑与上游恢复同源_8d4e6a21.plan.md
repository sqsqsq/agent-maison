# 运行配置与业务证据解耦 — 授权变更续跑与上游恢复同源

## 1. 目标与冻结边界

将已获授权的运行配置变化与业务内容变化分开处理，使合法续跑沿既有恢复链完成。依据为 `docs/overview.md §1.2.1` 四条总设计原则及 AGENTS.md 的可靠性验收口径，不另立总纲。

本批处理一个已证实的故障类别：**运行控制文件被重复当作业务输入，失效判断与实际恢复责任脱节**。以视觉 provider 切换为真实验收场景，修共同的依赖和恢复消费链，不做仅对 be091c 或某个模型生效的例外。

| 保留 | 收编或删除 | 不扩展 |
|---|---|---|
| manifest 身份授权、需求/范围绑定、源码/测试/构建/截图/参考图证据、硬预算、写边界、owner/fencing | 历史 run manifest 的重复内容字节依赖；在无 executor 机会时重复 gate 的内容重试；只在提示文字中存在的上游恢复责任 | 新 provider 探测系统、模型名单、运行配置注册表、通用依赖图平台、新回执/签名/状态机、其他停机家族的大审计 |

当前版本为根 `package.json.version=3.1.0`；基础提交为 `39664b14`。不重开已完成的 b7d2e9f4 / c3f8a2d7，不改变它们已接受的阶段延迟与资源归属规则。初次起草阶段仅产出本 plan 和 OpenSpec；用户现已授权本次 plan→review→修复及代码→review→修复循环，plan 评审收口后由调度直接下发实施，不再询问一次实施许可。当前文档轮不实施运行时代码、提交、打包或运行宿主；H1 仍受 §5.4 的真实外部条件和授权边界约束。

## 4. 设计

### 4.1 当前业务输入为内容依赖，run manifest 回归运行控制（t1）

1. `productionEvidence` 继续使用当前 run 的 `computeRunRequirementSha`；收集器复用 `resolveCurrentRequirementSource` 的当前 run 选择，取该 run 的 `requirement` 解引用结果与 `requirement_source_files`，保留原 `ux-reference` 图片收集，不再返回历史 run JSON 或历史引用并集。`computeRunRequirementSha` / `computeRequirementShaFromText` 算法与旧签发值不改；原始 source_files 继续以文件依赖保真，不能假定已有文本 hash 覆盖了它们。
2. 有 `resolvedInputs` 时复用其实际 requirement 值和 binding.dependencies；无 resolved inputs 时用同一当前需求解析补足。无 run 显式文件需求取 `resolveRequirementInput` 或身份匹配的 `fidelity-intent` SSOT 的原文件，inline 取调用方已解析正文，蓝图/CU 取已有 derive binding；不把只面向授权引文的 `collectCurrentRequirementText` 当作能恢复所有 inline 需求的入口，不回读任意历史 run 猜需求。无当前来源继续既有无需求上下文语义，不因本批把 runless 接口升级成 goal 强制门禁。
3. manifest 的有效性、存在性、身份授权与预算由既有入口负责；有效范围由已有冻结记录、修订和 bindings 负责。删去内容字节依赖不删除这些检查，也不改变身份字段集合、授权 flag 或预算折叠。
4. 生产 writer 汇合 `extraInputs`、resolved input dependencies 与 facts baseline 时，不得把退休的自动 run-manifest 输入再次写回。过滤发生在已区分自动/继承控制依赖与真实 binding 的汇合点，`addBoundInput` 对真实业务 binding 的 exists/SHA 严格检查保留；`phaseEvidenceManifestCandidatePaths` 同步使用该输入视图，避免材料归属又认回退休输入。真实显式声明为业务来源的文件仍保留原绑定；不按 `.json` 后缀、任意 `manifest.json` basename 或任意 `goal-runs` 子串做全局忽略。
5. 新产物不引入新的“业务指纹”平行真源，继续用既有 requirement、范围、输入内容和视觉绑定。需求文本、原始需求文件、acceptance/contracts、产品源码、测试输入、构建或参考图变化仍按原职责重验。
6. `computeRequirementSsotAggregate` 的有 scope 分支保持原 `requirement + readBoundInput` 口径；legacy/无 scope 回落改消费同一当前 requirement 与实际来源集，不能在收集器移除 manifests 后把纯 inline 需求变成空集/null。不改旧 completion 原件的 aggregate 值：它们按原记录契约核验，无法证明当前业务等价时沿既有完成义务重验。`collectRequirementIntentText` 的历史对账用途不属于这次内容收集器修复，不顺手重构。

### 4.2 旧现场自动兼容，统一所有证据读者（t2）

只改 writer 会把 be091c 留在原处，兼容是本批必做项。

- **先完整性、后解释。** 原 schema/aggregate、环境与当前需求核验仍先于输入投影；不修改旧 evidence、summary、回执、completion 原件或 events 来制造匹配。共享入口放在现有 evidence 模块，返回本次可消费的业务输入视图，不让低层 `evidenceEntryMatchesCurrentFile` 在没有 manifest/environment/当前语义上下文时自行放行。
- **识别边界可执行。** 按已有项目路径规范化和配置的 `features_dir` / `featureRelativePath` 构造该 feature 的 `goal-runs/<run_id>/manifest.json` 精确路径集，run_id 只取 `listAuthoritativeGoalRuns` 的权威项；`.dry`、bootstrap 残留、损坏/缺失 run、别的 feature 与其它同名 JSON 都不退休。原 entry 必须是 `role=input`，无 `facts_phase`、`identity_neutral` 或源码 owner 语义；outputs / both 仍逐字节验证。由于旧格式未记自动来源，兼容只对这个旧收集器固定控制面作解释，且排除当前 requirement 解引用、source_files、facts 显式来源和既有有效 scope / resolved input 中明确声明为业务来源的路径。合法 fixture 直接声明规范 run manifest 为业务输入时也不能退休；不发明事后 provenance 标记。
- **当前语义来源明确。** 优先用调用方当前 run / requirement 与 resolved bindings；goal CLI 沿 `MAISON_GOAL_RUN_ID`，独立入口沿现有 feature 冻结范围及原始需求 SSOT，范围统一走 `resolveEffectiveScopeSource`，保留既有 revisions/transfer/binding 校验。只读、component 或 closure 消费某份既有产物且调用方没有另一当前执行身份时，可用该产物的 canonical summary / completion 所携带的确切 run_id 解析它的需求与范围；不得从一个退休路径、最大 run_id 或历史并集挑替代身份。`--sync-closure` 复用已核 canonical summary.run_id，仅补证据解释上下文，不顺带打开 `goalRunId` 的其它强制语义。
- **退休不代替业务核验。** 当前 requirement 必须按原算法可重算，并等于原 evidence.environment.requirement_sha256 的非空值；有效 scope 与实际业务 binding 仍走原读取/校验链，未提供 `currentRequirementSha` 不能等同校验已通过。只有待退休控制项需要这份等价依据；没有控制项的既有 runless/legacy 入口保持原契约。框架版本、gate、workflow、framework.config、真实业务依赖变化仍按原 freshness 失效，不能因 manifest 退休跳过环境差异。
- **facts 回连同一证据。** 旧 exact-start 和 completed-start context 的 baseline 依赖回连 `baseline.established_by` 的原完整 evidence；仅当 path/exists/SHA 对应上述退休 input 时，在核对循环中使用同一消费视图。独立添加、无法回连或与 evidence 值不同的依赖仍走原检查。原 `baseline.dependencies`、fingerprint、subject 与 `established_by` 不改，`stableStringify(prior.baseline)` 等同基线判据不改；新生成的继承基线与正常 evidence 写入不再追加已退休项。确切 invocation / 未撤销窗口、owned 写链和业务依赖的原 SHA 都保留。

### 4.3 有责任恢复时先恢复，无修复机会不做内容重试（t3）

本批不重排所有 FAIL 优先级。只闭合已发生的输入阻塞路径：**当前 gate 在 facts/输入入场处失败，盘面存在同链内明确的更早责任 gap**。

1. `assess` 从当前新鲜 summary 的 `blockers[].id`（或同一轮已提供的 `reconcile.blockers`）识别正式 facts 入场失败 ID `context_exploration_facts_source_stale`；使用已有 `gapsFromObservation` 的链序与 earlier stale/missing/invalid evidence gap，在当前普通 FAIL 重试之前调用 `recommendationForGap`。`current_summary_fresh=false` 时历史 blocker 不作本轮路由依据；结构化 upstream producer 继续走 `producerOwnedInputGap`。不得从 suggestion/details 正则提取“回 coding”，不新增 failure_kind、gap kind、summary 字段或产品缺陷 candidate，也不让任意当前 FAIL 都优先回最早历史 gap。
2. 责任阶段为实际建立/持有输入的阶段，不能写死 coding。目标在链内且可由既有事务失效时，沿 `backtrack_to_phase`；目标不可执行时沿原有明示原因的停止出口，不能靠多跑一次相同 gate 创造可恢复性。
3. runtime 保留全部硬/进程/授权 guard 的原优先级，复用 `factsAdmissionError` / `skipExecutor`；把这一路的内容 no-progress 判定移到同一次 `runAssess` 已形成推荐之后。仅当本轮确无 executor 机会，且该推荐有 earlier 链内目标、现有 `runner_action=backtrack_to_phase` / 可补完 closure、失效面允许执行时，内容 guard 让位给该恢复。仍经唯一 `decideAndEmit` 与 `selectRunnerActionFromAssess` 提交，不能在 runtime 另写一套路由或先标 fused 再强行解熔断。责任目标未知/不可执行时保持原准确停止，真正执行后无进展、产品 FAIL、外部等待和原预算/回退重复保护仍有效。
4. 回退使用既有失效事务更新事件窗口；resume 起点、validation-only、facts admission 同窗。目标至当前阶段的失效集合必须覆盖先前会话的已完成阶段，不能仅由本次 `outcomes` 非空推断；同进程内同步删除这些阶段的 `resumePostAgentPhases` / attempt 缓存，重启按同一 revocation 事件重算。旧 settled 事实不能跳过本次必须执行的责任阶段。目标首个 facts 责任方利用已有 `factsRebuildReason` 真读受影响来源并建立新事实，不把“改个 hash/run_id”当作研究；回退次数、重复指纹及总预算仍从原 lineage 累计。
5. 纯闭环补完且内容输入仍有效时，继续保持 validation-only，避免为了本次事故把所有 resume 改成重调 agent。
6. `resume 跳过 coding agent invoke` 的日志改为实际 phase 和实际原因（已完成仅补验，或入场输入阻塞）；不新增事件字段，不把零 agent gate 重试写成模型失败。
