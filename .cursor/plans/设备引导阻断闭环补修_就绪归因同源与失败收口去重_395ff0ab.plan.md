# 设备引导阻断闭环补修

## 1. 定位与授权边界

本 plan 挂 [a47c9d62](../goals/效率与准确率平衡总体目标_默认基线自主交付与可调精细度及可靠恢复_a47c9d62.goal.md) 的 R6，遵守 [四条总原则](../../docs/overview.md#121-四条总设计原则) 和 [AGENTS.md](../../AGENTS.md) 的可靠性、机制准入及按风险验证要求。目标是让这类明确的设备前置阻断进入既有恢复闭环，而不是仅换一个停机标签。

起草基线为 `8deb32d0`，在研版本 `3.1.0`。`252ce328` 对应的 [28e31f53](宿主全链恢复补修_义务重开与授权交接_设备及预算同源_28e31f53.plan.md) 已完成内容与状态不改；本批承接其 t5 暴露的遗漏与签名标题回归，不重新设计义务模型、预算、设计 owner 或路径规则。其它会话改动不纳入本批。

**本轮只写计划和同步路标**：不实施、不提交、不打包，不清理宿主 Feature，不操作手机或解除 OOBE，不执行“先修好手机再试”的专项。开发期也保留这台手机的自然故障现场；只读取证安排在 t5。后续代码修改全部在 Maison，宿主只接收正式构建并校验的发布件，不手改宿主 framework、业务源码、ohosTest 或 TestRunner 来绕过问题。

现有 `38 t7、664 t7、4f t10、c6 t9、e9 t7` 均保持 pending。新 t6 只登记本补修必须观察的恢复结果，和这些待办共用一次联合验收，不增加另一轮宿主长跑或交付前彩排。

## 3. 四项修复

### 3.1 系统引导判据与既有设备恢复同源（t1）

**责任入口**：在 `harness/scripts/utils/device-readiness-deps.ts` 的现有设备取样/解析链收编前台窗口归属；复用 `dumpLayoutJson`、`readLockScreenSnapshot` 的采样能力。同一状态下共享取样结果；唤醒、解锁等改变界面的操作后使用复验时的新取样，不能继续消费操作前的树。不另外建状态文件或后台探测服务。锁屏判定与引导判定保持不同含义，不能把 OOBE 冒充 `device_locked`。

| 消费面 | 现有入口及本批接线 |
|---|---|
| 阶段开始前就绪 | `device-readiness-gate.ts::ensureDeviceReady`、`evaluateDeviceReadinessProbe`；不需要解锁时用首次未锁屏取样，需要解锁时用解锁后的复验取样；引导阻断返回原 BLOCKED |
| UT 运行前及无结果归因 | `device-runtime-recovery.ts::ensureDeviceReadyAtRuntime` → `profiles/hmos-app/harness/device-recovery-bridge.ts::ensureReadyBefore` → `hdc-runner.ts::runAaTest/runOnDeviceUt` → `ut-hvigor-test-failure.ts` 与 `ut-host-impl.ts`；运行期解锁成功也必须复验前台，不能仅凭 ensureUnlocked 的 ok 返回已就绪 |
| testing 运行及失败归因 | `providers/device-test-install.ts`、`providers/device-test-run.ts` 的既有 bridge；`check-testing.ts` 的 device_test_run/设备及视觉失败消费；不能把引导画面当目标 UI 的 selector、业务或视觉无进展问题 |
| 等待与恢复探针 | `device-readiness-deps.ts::probeDeviceReadiness` → `condition-wait.ts::runConditionProbe/waitForConditionRecovery` → runtime 原 recheck；探针维持只读，ready 只表示可以交原门复查，最终设备可执行性仍由原门确认 |

范围仅限**系统开机/升级引导正在阻止目标 UI 启动**。按**焦点窗口**归属判定：未锁屏取样中，读取顶层下 `focused=true` 的窗口节点所属应用（本例 `com.huawei.hmos.hwstartupguide`），不读取属性为空的最外层容器，也不把旁侧 `focused=false` 的 SceneBoard 窗口当作前台。不做页面文字、截图或 OCR 识别，不扫描已安装包或存活进程，不把普通应用前台当阻断。hilog 白名单拒绝只作佐证，第二次没有该行仍可依据前台归属判断。查询失败如实保留未知，不猜成引导，也不借未知取消原锁屏、设备可达性检查。

**锁屏覆盖时序**：锁屏树只能证明仍在锁屏，不能证明背后不存在引导。无需解锁时用首次未锁屏取样；解锁后使用复验取得的未锁屏取样再判引导。`ensureDeviceReady` 与 `ensureDeviceReadyAtRuntime` 两条解锁出口都遵守此顺序，不仅复验 locked，也不只信解锁函数返回 ok；若既有 helper 没有返回复验树，就沿原采样入口重新读取。只读探针看见锁屏时保持原锁屏/凭据语义，不唤醒或解锁；允许重查时交给原门按既有授权解锁，再依据新取样复查。解锁露出引导则继续等待，不能放行，也不存“上次看到引导”的跨取样状态。

复用 `externalBlocked/device_blocked`、`device_not_ready`、`device_readiness` 和现有设备门/等待流程；不新增停机原因、probe 名称或机器状态。跨调用只在既有诊断结果/报告内透传同一观察的必要事实，不新建持久设备账本、引导流程或分类注册表。阻断事实和来源进入现有 details/日志，显示“请在手机上完成系统开机/升级引导”。不自动点击系统同意、账号或隐私选项，不重置、重启、清数据或改测试包来绕过。

必须同时覆盖运行前已阻断、以及阶段已启动后才遇到引导的入口。已有真实断言失败不能被事后看到的引导画面覆盖；保留原 trace/失败记录，只将明确由引导导致的未执行、未进入目标界面交给设备恢复，UT/testing 义务仍待完成。

**阶段内阻断的确切去向**：不能止于将检查标成 externalBlocked。当前 `report-generator.ts` 可把唯一外部阻断投影为 INCOMPLETE，`phase-transition-policy.ts::classifyPhaseVerdict` 的默认策略再给出 `defer_external_and_continue_if_allowed`，runtime 的该分支会直接推进且不挂探针。本批必须在此分支之前，把已确认的引导阻断接回**本阶段入口已有的** `runDeviceReadinessGate` → `awaitProbeRecovery` → `waitForConditionRecovery` → 原门 recheck；复用或提取原调用块，不复制一条等待路径。

解除后重执行未完成的本阶段，保留原失败记录、已用时间/轮次，依赖 UT 的 testing 只能在 UT 真实通过后启动；重执行不是把旧 FAIL 改写为 PASS。若重查时引导已解除，也回本阶段执行，不能把“设备 READY”当作 UT 已完成。超时则沿设备门原样停放为 WAITING，携带原 `device_readiness` 探针和原因，不走延迟继续。此处只收编引导阻断，不全局修改默认依赖策略，不影响其他原本合法的 defer、授权或预算停机。

**等待开始即显示原因**：沿既有 `condition_wait_started` 事件传递设备门的准确说明（复用 reason 含义），立即进入原控制台/进度写出；`goal-progress.ts` 的状态文本与 Markdown 消费这条尚未结束的等待记录，能看到“设备处于开机/升级引导，请在手机上完成引导”。不等到超时或下一次阶段结束才显示，也不提前发出被暂存的 phase_halt 来冒充停放；`condition_wait_ready/timeout` 结束该等待展示。不新建通知器、监控或状态文件。

**恢复边界**：进程 owner 沿现有 `min(15 分钟, 剩余墙钟预算)` 等待，探针就绪后再由原 gate 确认；session owner、超时、预算不足或其它原停放条件不改。窗口外走现有重发/接续入口或已配置的 supervisor，不承诺无限期自动唤醒。依赖 UT 的 testing 必须在 UT 真正完成后再执行。

### 3.2 签名标题只说明真实失败阶段（t2）

**责任入口**：`profiles/hmos-app/harness/ut-hvigor-test-failure.ts::classifyFailure/singleToolchainHeader/buildHapHeader`。沿原结构化 failedAt/runDiagnosis/failureKind 选标题；只有实际 `hap_not_found` 等包发现/签名证据才能进入包缺失说明。`unsignedPresent=true` 只表示发现 unsigned 包，不能推出 signed 不存在。

真实 `unsignedPresent=true + failedAt=run + aa_test_no_result` 直接进入测试：明确 OOBE 时标题写设备引导阻断，未知时写执行未取得结果；二者都不报 signed 缺失。保留真正包缺失、签名配置缺失/跳签、安装失败及真实断言失败原分支；不改编译、签名、安装或用例通过标准，不补造包发现字段。

### 3.3 原因未知时保持未知（t3）

**责任入口**：`goal-phase-runtime.ts` 的 `await_operator_toolchain` 说明、`hdc-runner.ts::classifyAaTestFailure` 的无结果建议、UT 格式器及对应运维/Skill 指引。

明确引导态沿 t1 给准确动作；确有包、签名、工具缺失等证据时仍可说明对应故障。仅无结果或诊断不可用时，保留“未确认原因”，删除“这不是产物内容问题、agent 修不了环境”等断言，不把修改 TestRunner 路径排成已确定修法。已确认的 UT 载体问题沿既有 UT 责任处理，涉及业务源码仍回 coding，不扩大写授权。

报告首行、详细诊断、NEXT 与 runner 最终说明保持一致；不以再加一个 verifier/裁决环节替代事实判断。不扩成全仓文案普查，只同步本条失败链触及的 `docs/operations/goal-mode-runbook.md`、`skills/reference/business-ut-workflow-detail.md` 等直接引用处。

### 3.4 同次失败收口不再重复真跑（t4）

**责任入口**：`goal-phase-runtime.ts::runHarnessPhase` 已把 run/phase/attempt 身份给 agent 自检和正式 gate；在 `profiles/hmos-app/harness/ut-host-impl.ts` 的真机 dispatch 前，结合 `execution-key.ts::listExecutionKeyRuns/utFrozenRunArtifacts`、冻结 `ut-result/hdc-test` 与原调用记录判断该次失败是否可供正式裁决。仍执行正式 harness 的当前检查与报告生成，只减少无新依据的设备重执行，不跳过整个 gate。

当前 `ExecutionKeyRecord` 没有 goal run/phase/attempt 字段，执行键也没有 OOBE 状态，`reset_mode` 为 n/a。本批将已经签发的 `MAISON_GOAL_RUN_ID/MAISON_GOAL_ATTEMPT_PHASE/MAISON_GOAL_ATTEMPT` 原样透传到现有 UT 冻结记录：一个可选 `goal_invocation: { run_id, phase, attempt_id }`，不生成第二种身份，不从目录名、时间戳或事件时间窗推断“同轮”。生产写入使用 harness 已绑定的调用上下文；正式 gate 比较同一三元组及当前执行键、冻结件完整性，沿现有报告生成 FAIL。

这是既有执行记录的可选归属信息，不是新的失败缓存或复用协议。原 schema_version、成功复用规则及 Hylyre 分支不改；旧记录或普通调用没有该身份时，不采用同轮失败收口优化，正常执行，不因字段缺失新增阻断。参照 `visual-rounds-ledger.ts` 已有“同 attempt、同输入重放结论”的身份语义，不复制视觉账本、追加事件类型或引入第二套轮次算法。

允许的是：同一受管 run/phase/attempt 中已完整落盘的失败，正式 gate 只是在接收该次结果，当前源码/测试/包/目标设备及执行配置仍适用，且没有新的恢复或真跑请求。消费结果仍为 FAIL/open，原始失败时间和日志不改，不能写成“成功复用”或减少质量分母。仅有日志片段、材料缺失、归属不明或输入变化时，不声明已消费本次失败；沿原检查/执行入口处理，不新增过程材料门禁。普通独立 UT 请求没有这段受管调用交接时，保持原执行语义。

**设备重查先于失败沿用**：如果引导已解除、观察到原阻断已恢复，或者进入新的恢复/执行请求，即使执行键完全相同，也必须允许重新真跑。旧 FAIL 不是永久负缓存。新的请求不能借旧 FAIL 直接结束；同次材料无法证明环境恢复时也不得宣称“故障依旧确定存在”。成功复用仍走原 `decideReuse` 规则，不把 outcome=failed 纳入它的成功候选。

正常重跑本阶段会获得新的 attempt，三元组自然不匹配旧失败，不需要另判“恢复以来”或新增恢复状态。只有 `resumePostAgent` 恢复已结束调用的验证边界时会沿用原 attempt：这条路先按 §3.1 复查当前设备条件；引导已解除就允许实际重执行，不能仅凭旧三元组/执行键重放 FAIL、重新停回原处。

收口提示同步 t3：无变化时解释已采纳该次失败，不要求再执行以刷新回执；已修输入/环境或取得新依据时允许沿现有入口执行。验收统计实际设备执行次数，不能只断言“停止上报”这句话出现。
