# 实例扩展的本地安装、启停与真实时机消费

**安装时能说明一项扩展为什么能参与，执行时能指出它在本次请求中实际给谁送了什么、产生了什么结果。** 跳过和失败分别说明原因。协议适用于发布时点的各个 Maison 入口。本期为蓝图新增一个设计前时点。前门、免蓝图的直修和独立调用保留各自的请求边界。

## 1. 依据、范围与新增机制的收益

沿用[总纲 §11.2](../goals/复杂能力建设目标_能力架构蓝图到部件演进与变更单元闭环_75411223.goal.md#112-稳定内核与-provider-接缝语义)的定义、提供者、消费者三方接缝，以及 required/optional、冲突和四类退出规则。Cordis 的时间可组合性用于判定停用后能撤回谁拥有的影响，空间可组合性用于判定依赖的时点、能力与配置在本次操作中是否可用。Maison 在安装、请求准备和实际交回这些离散时点处理变化。总纲沿用原文，本期范围是本地静态声明与接入，不建设动态插件加载器、热重载、远程分发或市场。[论文 §3.1–3.3、§5.2、§6.1](https://arxiv.org/pdf/2608.25512)

| 已发生的场景 | 所需改动 | 能观察到的收益 |
|---|---|---|
| 钱包已有宿主知识或 profile 设计背景，安装 UX 要手工改正文、拼指针 | 每项绑定归属明确。同一时点能接收多份知识，绑定与整项能力可分别启停 | 安装两次后原知识、UX 与 `story` 共存，宿主手写正文逐字节保留。[原安装说明](../../extensions/manifest.yaml) |
| `517b63fe` 隔离宿主已通过安装和物化，检视为 `scheduled`，受管作者两次签发均无 intake 正文或路径 | 由真实入口交付请求输入，用本次作者收到的材料和交回物验收 | 能指出是声明未生效、材料未送到，还是动作执行失败。[历史实施记录](UX行为说明_上游独立使用与蓝图前按需提取_ad5c222f.plan.md) · [首轮原件与签发审计](../../.codex/reports/ux-behavior-ad5c222f/wallet/first/evidence/wallet-host-first-author-acceptance.md) |
| 将钱包 `spec.on_context_load` 改为 `spec.on_context_loda`，当前检视仍把三条路径列为 `scheduled` | loader 与检视按发布件支持的时点及消费者校验，诊断归到声明条目 | 可在运行前指出错误名并停用这一项，健康贡献继续工作。[loader](../../harness/extension-loader.ts) · [检视](../../harness/scripts/utils/extension-inspect.ts) |
| 目前 `post_verifier` 发出后才判定本轮是否启动验证者 | 将原生验证前供料和真实结果交回各归到对应入口，旧监听器保留兼容时序 | 验证者尚未运行或被跳过时，扩展不会提前通知用户“验证已结束”。[harness 调用顺序](../../harness/harness-runner.ts) |
| 源码目录、安装副本、生成桥接与业务产物散在不同位置 | 在原宿主清单的安装条目记归属与导入指纹，重用桥接的漂移保护 | 停用或卸载一项后，其他扩展、人工修改和已交付 UX 均保留。[现有桥接所有权](../../harness/scripts/utils/instance-skill-bridge.ts) |

范围包括 `instance-extension-management` 的 OpenSpec、既有发布件规格与 harness、适配器入口、可选 UX 源样例和钱包副本验收。开发仓的 `extensions/` 仍是按 skills、knowledge、hooks 等维度组织的选装来源。管理协议随 Maison 发布，UX 独立目录可交上游使用。完成事实继续由原 request、events、receipt、evidence 负责。以上场景通过即收口，其他时点需另有真实生产者、消费者和用例才扩展。[实例扩展规格](../../openspec/specs/instance-extension-management/spec.md) · [发布排除表](../../scripts/release-excludes.json)

## 2. 一份声明怎样到达一个真实消费者

**分工。** 拥有操作的 Maison 入口发布时点，扩展作者声明要在这里交付的知识或动作。宿主维护者选装、配置和启停，本次请求的消费者判断业务适用性并报告结果。稳定识别一条绑定要能定位来源、能力和能力内的绑定 ID。每张接缝卡在现有 OpenSpec 说明真实调用位置、输入、预期输出、接收者、允许的贡献类型、组合次序、缺失与退出语义。发布件的 [lifecycle-hooks-schema.yaml](../../specs/lifecycle-hooks-schema.yaml) 承载封闭的时点定义，包含现有生命周期事件、三个 Feature 槽位及本次新时点。loader 读这份定义做校验，检视据此展示真实绑定。拥有操作的代码负责调度。扩展可以向已支持的时点新增贡献。声明一个新名字本身不能产生调用。

**原生格式建议使用 manifest `2.0`。** 变更涉及默认合并行为和事件时序，版本按[既有演进规则](../../docs/evolution/extension-protocol-v1.md)区分。实施时在[原 manifest schema](../../specs/instance-extension-manifest.schema.yaml)定义新分支，在现有 OpenSpec 写兼容场景。以下为 UX 来源清单的最小形状，ref 按来源根解析。发布目录仍可包含多项能力。

```yaml
schema_version: "2.0"
name: maison-optional-extensions
provides:
  skills: [ux-behavior-spec]
bindings:
  ux-behavior-spec:
    read-upstream:
      at: component-design.before_discovery@1
      kind: knowledge
      ref: skills/ux-behavior-spec/reference/intake.md
      enabled_by_default: true
    fill-missing:
      at: component-design.before_discovery@1
      kind: action
      ref: ux-behavior-spec
      enabled_by_default: true
```

**声明与执行。** 宿主原生声明和老版本兼容输入经同一 loader 归一后，传给原作者、harness checker 或 receipt consumer。Feature 原有 `knowledge` 和 Markdown 片段映射为知识，`skill / mcp` 及有执行行为的脚本映射为动作，实际验证和收口仍由原消费者处理。绑定可用性取决于入口支持的时点版本、实际资源及所需的既有配置或工具。缺少哪项就点名哪项，补齐后在下次请求准备时重算。发布者明确哪些组合能执行。多份知识按消费方约定的稳定顺序追加，同一绑定去重，独立来源可追溯。UX 先查适用旧稿，再判断是否缺项。独占事实遇冲突交其原责任方，禁止按最后安装覆盖。诊断标来源、绑定 ID、时点和原因。

| 兼容输入 | 新读器的处理 |
|---|---|
| 合法 `1.0` / `1.1` | 保留 1.0 按目录发现 skill、旧 knowledge 的消费边界，以及 1.1 按 `provides.skills` 选装和按 audience 路由的行为。首次需要写新选择时，用原清单原位迁移，显式保留当时生效的旧项、宿主身份、规则、手写资料和已接入适配器。直接读取、检视不触发迁移。 |
| `phase_bindings` | 三个槽位归一到相应真实时点。保留 `before_phase_work` 的作者交付、`before_phase_verify` 的 produces 检查、`after_phase_verify_before_close` 的原 receipt 责任及严重度。[现有消费逻辑](../../harness/scripts/utils/extension-runtime.ts) |
| `skill_assets.component-design.knowledge` | 将旧配置按原优先级解析为一份设计背景，保留 extension 覆盖同键 profile 的旧行为。新贡献追加到这份背景，不占其槽位。旧 UX 指针和原生 UX 绑定指到同一项时复用同一来源和绑定身份，不会触发两次。宿主文档中的手写链接可以继续读取，链接本身不授权启动已停用的动作。其余 skill 资产仍按原职责解析。[知识装配器](../../harness/scripts/utils/knowledge-context.ts) |
| `provides.hooks` 的旧事件名 | 在统一时点定义上识别兼容名，保留框架、profile、实例原有来源次序、脚本上下文和失败语义。保留旧供料行为和真实完成通知的区别，详见第 4 节。 |

未知时点、坏引用、缺配置或绑定内容损坏，隔离到可归因的贡献，检视和校验均标明未启用。依赖该项的 required 工作报告具体缺口，optional 按入口约定降级。其他项可继续被投递。整份清单语法、根结构或协议版本无法被可信解析时，才整体报告不可用。识别 2.0 的安装端先核对目标发布件的读取能力。若目标整体不识别该清单版本，就保留原清单并报告兼容性缺口。若仅缺某个时点，只停用相应绑定。合法旧输入保持原行为，可归因的无效条目从整体退出改为局部诊断，写入迁移说明。[现行整体退出位置](../../harness/scripts/utils/knowledge-context.ts)

## 3. 用户能看到什么，安装如何生效

`/extension` 保持一个管理入口。`/extension install <本地来源> ux-behavior-spec` 和“从这个本地来源安装 UX 行为说明”产生同一操作、对象和作用范围。脚本可凭稳定 ID 直接调用同一 [extension CLI](../../harness/scripts/extension.ts)，启停动词按目标值设置，重复执行不会反转开关。已有 `init / materialize / verify` 作为维护入口兼容。新操作共享物化、检视和校验逻辑。手工维护清单的用户在下次载入时也得到相同诊断。

| 正式操作 | 用户也可以说 | 可观察结果 |
|---|---|---|
| `install <本地来源> [能力ID]` | “从这个目录装上 UX” | 一次完成缺失骨架初始化、选择能力所需资源的导入、校验、适配器入口刷新与检视。回复列出可手动调用的入口、已启用绑定、缺配置或目标发布件不支持的具体原因。首次采用来源声明的默认值，未声明默认值的自动绑定保持关闭。重装保留宿主开关，更新新添的自动绑定默认关闭并列出供选择。 |
| `enable <能力> [绑定ID]` | “以后让蓝图在缺稿时自动提取 UX” | 显式设为启用。整项选择决定能力是否可用，单条选择决定该时点的参与方式。缺依赖的绑定报告未生效。 |
| `disable <能力> [绑定ID]` | “以后关闭自动提取，手动保留” | 仅关闭指定范围，保留安装和原有其他选择。整项停用时撤下该能力在 Maison 的手动和自动参与。自然语言“这次别提取”只作用于当前请求。 |
| `uninstall <能力>` | “卸掉这个 UX 扩展” | 对账并撤下该项所拥有的安装副本和入口，列出因宿主修改、共享或不属于此次安装而保留的路径。 |
| `inspect [能力]` | “现在能在哪儿用？上次为什么没提取？” | 当前配置解释能否参与。问及过去则读取对应请求、实际输入、输出或交回。历史记录不足时如实说明。裸入口可展示当前状况及常用说法。 |

所有项目已接入的 agent 都支持这五个操作和同义自然语言。Claude Code、Cursor、CodeAgent 等沿其适配配置进命令或 skill。Codex、DeepSeek Harness、OpenCode 等通过 skill 接受同一动词。Generic 等按项目配置的既有 bundle/根入口定位同一 skill。是否有原生斜杠模板不改变操作语义。[管理 skill](../../skills/project/extension/SKILL.md) · [各适配器](../../agents/README.md)

**来源和写权。** 输入限显式本地目录或含同一根清单的本地包（ZIP）。来源清单提供资源和默认绑定，安装后运行读宿主清单及受管理副本，原始来源可离线。安装操作一次合并所选声明与引用资源，保留 `story` 等原有条目。宿主 `paths.extension_dir/manifest.yaml`（通常是 `doc/extensions/manifest.yaml`）是持久选择的唯一真源。安装条目记录来源身份、选中能力、宿主显式开关、所拥有文件的宿主相对路径和导入字节的 SHA-256。源码正文、生成桥和运行结果各自保留原有真源。运行时写入仅限本次调用授权的产物目录。

**重试和卸载。** 入口统一校验资源解析后的根边界、归属、绑定字段及实际支持的时点。包条目和链接不能使导入、覆盖或清理越过选定根。遇同名无归属文件或宿主已改写的副本，保留文件并指出冲突。原地来源始终按源文件保护。沿用[桥接归属与漂移保护](../../harness/scripts/utils/instance-skill-bridge.ts)，导入文件按安装指纹复算。并发或中断时保留已提交的宿主选择及可对账的归属，防止覆盖另一项配置或将同一贡献注册两次。中断后重试同一操作应能按原归属完成导入或清理。停用只撤参与，卸载仅清理仍由本安装独占且内容未漂移的副本，业务产物和手写正文继续归项目。持久选择和指纹放在原清单，不加场外状态或第二份登记文件。

## 4. 时点、交回与证据

| 要发布的事实 | 真实位置和行为 |
|---|---|
| `component-design.before_discovery@1` | 蓝图 ID、需求来源和写入范围绑定后，P1 事实发现及首次设计写作前，直接和受管入口实际调用同一准备逻辑。受管入口把准备结果交入签发的作者请求。直接创建或修订时，按调用参数或正式绑定的 ID 在正常入口完成只读准备，以真实调用及返回给作者的内容验收。兼容命令 `--design-knowledge` 复用该解析，只读查询本身不执行补稿。两条入口均由本次有写权的作者执行适用动作，纯查看保持只读。[直接入口](../../skills/project/component-design/SKILL.md) · [只读准备](../../harness/scripts/check-component-blueprint.ts) · [受管请求装配](../../harness/scripts/utils/initial-design-delivery.ts) |
| 验证前供料 | 在现行普通检查分支，`pre_verifier → on_context_load → post_verifier → post_phase` 接连发生，随后才判签发资格和组装 verifier prompt。旧监听器按原顺序和实参在这个旧时点运行并标明兼容用途，旧脚本产生的检查仍归原 checker。文档和检视分别写明“旧回调已发生”和“有资格时片段才进入 verifier”。原生 `verifier.before_prompt@1` 在签发资格通过、组装验证者输入时交付供料。作者知识在作者入口投递。[实际发出位置](../../harness/harness-runner.ts) · [既有调度器](../../harness/hooks-dispatcher.ts) |
| 真正的验证完成 | 原生 `verifier.after_result@1` 由收到并接受本次签发 request/subject 对应的完整真实结果的消费者发布。验证结论 PASS 或 FAIL 均可完成一次验证。尚未签发、被跳过、传输失败或只有不完整报告，各沿现有路径说明，不发“验证完成”。覆盖受管、独立验证和有效原件恢复。重复读取已消费结果不重复触发副作用。旧 `post_verifier` 监听器保持旧供料用途，显式迁移后才接新完成语义。[受管执行](../../harness/scripts/goal-phase-runtime.ts) · [独立执行](../../harness/scripts/utils/standalone-stage-verifier.ts) · [原件验收](../../harness/scripts/utils/stage-verifier-execution.ts) |

参与判断依次核对安装与绑定开关、当前入口对时点的支持、本次请求的适用条件。依赖撤回或恢复在下一次准备时重算。已签请求继续消费当时冻结的材料、绑定及写入范围。交回前还要读取的必需正文或动作资源随既有请求材料留存，或绑定到在途可读的不可变版本。单独记录一个指向可覆盖文件的路径或哈希，不足以保证旧请求可执行。

**知识与动作的完成判据不同。** 知识以所需内容实际送达目标角色为交付完成，超预算按冻结来源分段读取并核对。只有路由指针时，只能说明材料可定位。动作报告复用已有稿、生成并回读、按业务条件跳过，或执行失败及原因。将结果写入该次已有请求/交回说明，标出接收者与产物。要声称业务已采用，还须在用例或验收中找到相应元素的实际引用。

保留 `inspect` 的 `available / scheduled / evidenced` 作为既有证据强度。上面的三个判断不能与三个标签机械一一对应。不存在的时点显示未启用及原因。磁盘上存在旧产物不能证明本次收到材料。安装回复和相关请求的参与说明均从现有事实派生。前门或直修在自己的请求内报告与本次有关的复用、生成、跳过或失败，不为纯文案修改启动蓝图或另建专用回执。[检视实现](../../harness/scripts/utils/extension-inspect.ts) · [项目请求分流](../../docs/operations/project-entry.md)

## 5. UX 的消费与权威

- 独立手动调用使用调用者指定的输出目录。蓝图的 `read-upstream` 按显式输入或本次原始需求目录选择 `*.ux.yaml`，连同相关屏、流程、出处和裁决交给作者。将现有 intake 的读稿说明与实际补稿动作分清，单启读稿时只复用，不启动提取。缺稿且 `fill-missing` 启用、请求涉及相应 UI 行为时，由本次有写权的作者在蓝图目录 `ux/` 先生成、解析回读，再引用到用例和验收。同一材料和有效草稿可复用，原始 PRD 和上游稿只读。[UX 取用规则](../../extensions/skills/ux-behavior-spec/reference/intake.md) · [开卡样例](../../extensions/skills/ux-behavior-spec/examples/bc-openCard-2/README.md)
- 输入渠道与业务权威分别判定。实际进入蓝图的正式需求来源由宿主需求系统或外部 provider 输送时，沿 M7 `requirement-source-materialization@1`。直接交给入口的本地文件沿现有 builder 规范化。本轮 AI 的 UX 推导稿是辅助材料，保留真实出处、证据强度与待决项，不能自行增加已签范围或升级为产品决定。未进蓝图的直修以其原 request 为依据。[宿主适配 §3.0](../../docs/operations/component-design-host-adaptation.md#30-什么时候必须用这条接缝) · [M7 schema](../../harness/schemas/requirement-source-materialization.schema.json)

## 6. 分项验收与交付

钱包业务验收使用已集成可核验 Maison **发布件**的隔离宿主，保留既有 `story` 等扩展。若取到的钱包快照尚无设计背景，先在副本装入一份独立、可辨认来源的宿主背景，并记录为本次测试输入。保留原配置、文件指纹和 PRD/图，按正常入口调用。第 1 节列的旧签发原件是开发机归档，入库的 `ad5c222f` 实施记录也给出了版本、材料和失败结果。本轮需取得新请求自己的证据。对照用例不要求重跑整条开卡施工或真机上线。

| 项 | 操作 | 通过依据 |
|---|---|---|
| A. 合法绑定、作者未收到 | 以 `517b63fe` 原件为失败基线。在新钱包受管入口给实际作者 PRD 和设计图，开启读稿与补稿但不预置 UX。直接入口另给预制稿 | 核对两条入口各自第一轮实际收到的正文或已回读原件、请求 ID、交回文件和元素引用。受管先产生有效 UX 再消费，直接复用预制稿且正式蓝图属于指定 ID。仅有安装 PASS、根 skill 指针或作者自述均不足以通过。 |
| B. 不存在的时点 | 在保有健康贡献的钱包清单，令一条路径正确的 hook 绑定指向 `on_context_loda`，对自然语言、具名操作和手工清单载入走同一校验 | 安装/检视给出具体绑定、未知时点与未启用原因，不标 `scheduled`。相邻健康项实际可用，要求该坏项的操作报告缺口。与 A 分开记结果。 |
| C. 三种使用方式共存 | 同一宿主开启手动 UX、开启蓝图读上游稿、关闭缺稿自动写。分别手动取用、给蓝图已确认稿，并经前门提交一项可直接完成的纯文案修改 | 手动调用交付一份可读 UX 稿，蓝图实际引用上游元素，免蓝图直修完成本来工作并给出相关跳过原因，没有 UX 提取或多余蓝图。核对宿主及扩展的手写说明字节未因安装被改写。 |
| D. 已有宿主重复安装 | 在含 `story` 和独立设计知识的副本安装 UX 连续两次。首次装好后只关闭缺稿自动提取，第二次安装核对该选择。给正常蓝图入口预置适用 UX 以及某银行仅支持信用卡的需求数据 | 宿主背景和 UX 说明均送到本次作者，每个适用绑定只执行一次，停用的补稿动作不执行，原 `story` 可用。首稿在卡类型元素的验收写出“只支持信用卡时只显示信用卡一行”，能核对来源及稳定元素 ID。截图相似不能替代这项业务观察。[原始材料](../../harness/tests/fixtures/component-selection-handoff/dependencies/doc/features/原始需求/1-2-银行卡) |
| E. 停用、卸载与在途请求 | 发出一份已绑定 UX 的请求，在它交回前停用或卸载，再另开新请求。卸载前改一份归属本安装的文件，保留已交付 UX、原始来源和蓝图 | 已签请求仍按当时输入交回，新请求不再调度被停用的能力。单独停用提取时手动入口仍可用。卸载只清理归属明确且未漂移的资源，宿主改过的文件有提示并保留，原 `story` 和设计知识照常工作。 |

配套定向用例复用现有 extension-loader、extension-management、hooks-dispatcher、knowledge-context、initial-design-delivery、stage verifier 及 UX 测试。定向核对合法 1.0/1.1、新格式和旧新同项去重，验证 required/optional、无法解析整表与真实验证完成/跳过/恢复，以及本地导入时的路径碰撞、越界拒绝、中断重试和有归属的清理。全部已接入适配器按其正式入口检验五个动词及等价自然语言能到达同一操作。本机具备的各客户端用短例实跑，至少含一条命令型入口和一条 skill 型入口。逐适配器列明实测、可重放契约与缺少真实环境，不能以文件出现代替真实客户端运行。
