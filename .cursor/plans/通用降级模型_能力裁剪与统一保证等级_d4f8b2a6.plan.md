# 通用降级模型（能力裁剪 + 统一保证等级）

> 定位：[7c4e9a2b](skill契约化与调和循环_7c4e9a2b.plan.md) L1.2（tiers/when 部分）、L1.3（门禁⑤）、L3（全层）的**继任设计**；其余层（L1.1 registry、L2 closure 事务/assess/next.json、L4 循环化/handoff、L5）不受影响，两版在删除旧 `verifies.depth_field` 后的 contract.yaml `inputs/produces/verifies` 交集段一致。
> 围栏结果（2026-07-30 确认）：**未生效**——codex 已实现三块 hold 项。本 plan 按**基线迁移**实施：保留（inputs/produces/verifies 交集，删除 verifies.depth_field）/ 搬迁（三阶梯行为实现→输入 resolver 素材，测试成搬迁回归基线）/ 拆除（tiers/when 声明面+穷举门禁⑤）/ 一次性改名（summary.depth→summary.assurance）；现有 profile capability-registry 保持不动；迁移评估见文末「基线迁移评估」节，t1/t4/t5/t8 已改迁移语态。
> 改档声明：本设计**推翻 codex 四轮冻结的 when 受限 DSL + 穷举门禁**——档位改为机械推导后不存在手写 when，互斥穷尽 by construction 成立，门禁失去对象。这是替代不是回退。

## 动机实锤（为什么手写阶梯是错误路线）

- **check-ut 对 plan.md 的消费包装是死代码**：`loadDesignMd`（check-ut.ts:304）只被同样无调用点的 `designMentionsUseCaseChapter` 包装，plan.md 不构成当前质量档位 SSOT；两者一并删除。L3 手写阶梯「无 plan.md 降 basic」patch 的是 harness 层不存在的依赖——手写策略基于对代码的想象，机械推导基于代码本身。
- **缺失政策已散落失控**：review 当前 acceptance 缺失是 MAJOR+WARN，testing 支持 acceptance/adhoc 替代输入，三 phase 不能被强行写成同一状态；政策仍埋在各 check 手写代码无集中声明。review 视觉维度的 `return []`（check-review.ts:760）混合了非 UI、缺输入和解析失败三种语义；check-ut 仍存在「BLOCKER 严重级 + SKIP 状态」的覆盖率门静默失能（check-ut.ts:1956）。
- **每个新场景都要特批**：plan-start（plan 无 spec）、起点假定的档位上限、即席双轨——逐场景打补丁无穷尽。

## 三条元原则（六个业界体系收敛，均经 web 核实）

1. **公共状态词表全局唯一，assurance 只作机械投影**（quality_axes 的状态/原因语义跨 phase 共用；assurance 的名称与序关系仅用于能力集合比较，等级由 resolver 判定而非生产者自声明）。
2. **assurance 由数据推导，绝不手工声明**（K8s QoS：从 spec 机械推导 Guaranteed/Burstable/BestEffort，用户无自报通道。本仓 3.0.0 fake-pass 事故 semantic_layout 自声明绕视觉门=手工声明档位的实锤反例）。
3. **「缺失」是独立状态，不是成功也不是失败**（JUnit Assumptions：前置不满足=skipped-with-reason≠failed；Airflow：upstream_failed/skipped 独立终态+声明式 trigger rule 传播，防「上游缺失被下游当成功消费」）。

辅助锚点：Progressive enhancement（core/enhancement 边界必须成为数据而非作者临场判断）；SRE criticality（全局统一裁剪序数，「结果质量降级先于整体拒绝」）；resilience4j（仅借鉴 fallback 链的显式顺序，本 plan 不采用动态最具体匹配）；Bazel optional toolchains（mandatory/optional 分析期统一解析 fail-fast，optional 缺失以 None 进执行）；brownout（吸收 mandatory/optional 二分，**拒绝**概率 dimmer——验证结论必须可复现）。


## 冻结契约（implementation freeze）

- **Assurance 枚举与序数：** 实际状态只允许 `blocked < degraded < full`；`actual >= minimum_assurance` 只决定是否产生 `insufficient_assurance` 与额外 assess goal-level gap，`blocked` 永不满足 `degraded` 或 `full`。它不得放宽既有 quality_axes、phase advance、顶层 PASS closure 或 release readiness。
- **Applicability 前置与两级解析状态：** `CapabilityApplicability` 必须在任何 input source 前由 `tracks` 与命名纯 `applicability_provider_id` 判定；不适用即 capability=not_applicable、跳过全部 inputs，因此不存在一个 input=N/A、另一个 input=invalid 的顺序竞争，也不引入通用条件 DSL。随后才有 `InputResolution.state = resolved | absent | invalid | not_applicable` 与 `CapabilityResolution.state = resolved | pruned | blocked | not_applicable`，二者不得混名；已适用 capability 的 input 若返回 `not_applicable` 即契约错误→blocked。source chain 严格规则：`absent` 才继续下一个 source，`resolved` 即停止，`invalid` 立即停止并令 capability=blocked（不得用低优先级派生输入掩盖损坏的权威输入）。capability 的 `on_missing:prune` 将输入 absent 投影为 pruned，`on_missing:fail` 将其投影为 blocked；任一 invalid 均为 blocked。
- **聚合真值表：** `not_applicable` 不进入 applicable capability 集；所有 applicable capability 为 `resolved` 时为 `full`；没有 `blocked` 且至少一个 `pruned` 时为 `degraded`；任一 `blocked` 时为 `blocked`。因此 `invalid` 永不被 `prune` 或 fallback 掩盖。
- **最低保证字段形状：** `goal-manifest.minimum_assurance?: Partial<Record<phaseId, MinimumAssurance>>`，其中实际 `AssuranceLevel = blocked | degraded | full`，最低要求 `MinimumAssurance = degraded | full`（`blocked` 只能是实际观测值，不能写成最低要求）；它是可选稀疏 phase map，不是全局标量，也不是能力集合自报。缺整个字段或某 phase key 表示无额外 goal-level floor，既有 closure/release 门禁照常执行；已提供的 key/value 非法才使 manifest 无效。
- **输入模型单一来源：** `inputs` 仅为 `{id, sources[]}` 目录；旧 `required/optional`、`artifact/kind`、`alternatives/normalizer`、`absent_effect` 的政策含义一次性删除。capability 通过 input id 引用并独占 `on_missing`，`tracks` 明确 applicability（例如 coding full/lite）；每个迁移 gate 要求 `capability.id === CheckResult.id`，否则声明不得视为已消费。
- **前置单次权威报告与新鲜度：** phase 在 checker 执行前只生成一次 `CapabilityResolutionReport`，只记录 artifact/derive 输入可用性；build/install/run 的成功、失败、外部阻断继续属于运行时 `CheckResult`/holder，绝不写回报告。报告的 `capability_resolutions[]` 规范化记录 `capability_id`、`axis`、capability `state`、每个 `input_id` 的 InputResolution state/source attempts/selected source/provider 与 `selected_source_fingerprint`、受控 reason_code 及可选 upstream producer 指针；报告级记录 `contract_fingerprint`，derive 另记录规范化输入 fingerprint。每个 capability 还必须绑定其 applicability provider 输入和从首个 source 到 resolved/invalid 终止点的全部实际 attempts 依赖：含 absent 高优先 artifact（以 exists:false/sha256:null 登记）、absent/invalid derive 输入和最终选中源；未尝试的低优先源不绑定。它写入 `summary.capability_resolutions[]` 与 `capability_resolution_contract_fingerprint`，由 checker、quality_axes、script-report 与 assess 共同消费；contract 和全部实际 attempts 依赖纳入 evidence manifest.extraInputs/gate freshness，变化即 stale；任何出口不得重新解析。
- **裁剪桥接与传播（2026-08-01 修订，见文末「pruned 投影修订」）：** 前置报告经适配器进入 `deriveQualityAxes`，不能伪装成 `CheckResult` 的 SKIP。**`pruned` 不参与 quality_axes 投影**：它只体现为 `summary.assurance` 降档、`summary.capability_resolutions[]` 留痕、`assess.observed.degradations[]` 与报告头披露——不改任何 `AxisVerdict`，不写 `AxisResolution`，不影响 advance / closure / release。`AxisResolution.reason_code`（唯一枚举 `capability_pruned`）随之无生产者，一并删除，不留死字段。`blocked` 行为不变：任一 blocked capability 强制对应 axis=UNVERIFIED、release=BLOCKED、resolution=`needs_fix/agent/current_phase`，并令顶层 projected verdict 至少为 INCOMPLETE，不受 visual/asset advance 豁免或 minimum_assurance 影响；assess 复用既有非 PASS gap。迁移 gate 的 capability `axis` 是轴 SSOT，旧 `mapCheckToAxis()` 只给未声明 capability 的 gate 作 fallback。**pruned 的唯一门禁入口是 `minimum_assurance`**：actual 低于该 phase 的 floor → `insufficient_assurance`；上游 pruned 阻断下游 core → 带 producer 指针的 blocking `gap.kind=pruned`。除此之外 pruned 不阻断任何东西。
- **声明消费两段门禁：** 扩展既有 `check-contract-consistency`，但它只做静态声明校验：capability input id、track 子集、axis/on_missing/applicability provider/derive provider、artifact source 注册与 workflow producer 可达性、active-track id 唯一性。checker 收尾在 phase runner/checker 附近调用小型纯函数 `assertCapabilityConsumption(report, checks)` 做严格双向对账：每个 active resolved capability 恰有一个同 id `CheckResult`；pruned/blocked/not_applicable capability 均为零个；重复 id 失败；每个 capability-backed check 必须反查到 active resolved capability，且轴只能来自 contract。不得把运行时对象塞入静态脚本，也不新建子系统。
- **Provider 选择：** 每个 `derive` source 精确指定 `provider_id`，严格按 source chain 声明顺序尝试，首个 resolved 结果胜出；不做“最具体 provider”动态匹配，也不引入 `ask`/`absent` source 节点。

## 红线（反假 PASS 的通用化，比手写阶梯更硬）

- core 能力（`on_missing:fail` 输入）缺失 → phase **不可闭合 gap**，推荐指向 producer 最小回补——判真标准永不降。
- 非 core 能力缺失 → **裁剪**：resolver 内部为 pruned，**不投影进 quality_axes**（2026-08-01 修订）；出口是 `summary.assurance` 降档 + `capability_resolutions[]` 留痕 + `assess.observed.degradations[]` + 报告头披露——**绝不静默，但也绝不阻断**。绝不投影为 PASS 或 FAIL，也不放宽既有 quality/closure/release 门禁（它根本不碰这些）。要让某 phase 的裁剪构成阻断，唯一手段是声明 `minimum_assurance`；上游 pruned 阻断下游 core 时另成 gap.kind=pruned（防归因误判）。
- assurance 无自报通道：同一输入集合必得同一 assurance（可复现、可审计）。
- 现有场景全部消化为同一机制实例，零特批：plan 无 spec 的 requirement 由 change.md/goal manifest 的结构化输入或 derive provider 提供；起点假定=保证上限的推导自然结果；即席=cases 源链 adhoc 段；lite 轨=track 过滤（不变）。

## pruned 投影修订（2026-08-01，用户拍板）

> 本节是对上文冻结契约「裁剪桥接与传播」的**定向修订**，落 t10。修订前的表述（pruned 强制轴 UNVERIFIED + `capability_pruned` reason_code + needs_human/needs_fix 路由）整段作废。

### 为什么改：prune 与 fail 的后果塌缩成同一个

实证（同一份全 PASS 的 checks，只换 capability 状态）：

```
无 capability 报告    | projected= PASS       | release= READY   | completion= COMPLETE
evidence 轴 pruned  | projected= INCOMPLETE | release= BLOCKED | completion= EVIDENCE_PENDING
functional 轴 pruned | projected= INCOMPLETE | release= BLOCKED | completion= FUNCTIONAL_PENDING
visual 轴 pruned    | projected= PASS       | release= BLOCKED | completion= FUNCTIONALLY_COMPLETE_VISUAL_PENDING
```

**functional / evidence 轴上任意一个 pruned，phase 就 advance 不了**——与 `on_missing: fail` 的后果无异。契约里写 `prune` 的意思是"非 core、缺了可以裁剪"，实际等于不可缺。已存在的受害面：`capability_ut_use_case_context`（evidence, prune）→ 一个没有 `use-cases.yaml` 的 feature，ut 永远 INCOMPLETE；review/testing 的 design_context、spec 的 codebase 同理。

**根因不是实现走样，是本 plan 的冻结契约自相矛盾**：一边写元原则 3「缺失是独立状态，不是成功也不是失败」，一边把 pruned 接到 `UNVERIFIED`——而 `UNVERIFIED` 在既有 lattice 里的语义是「**本该验证却没验成**」，它当然要拦。两个不同语义压到同一根线上，只能二选一：误拦（修订前）或放水。

### 改成什么

`pruned` **完全退出 quality_axes 投影**。它的全部出口是：

| 出口 | 内容 |
|---|---|
| `summary.assurance` | 降档 full → degraded（机械推导不变） |
| `summary.capability_resolutions[]` | 完整 InputResolution / attempts 留痕（不变） |
| `assess.observed.degradations[]` | 逐条 capability + axis（不变） |
| 报告头披露 | 人可见（不变） |
| **quality_axes** | **不碰**：不改 AxisVerdict、不写 AxisResolution、不影响 advance / closure / release |

`blocked` 行为**一字不改**：axis=UNVERIFIED + release=BLOCKED + resolution=needs_fix/agent/current_phase + projected verdict 至少 INCOMPLETE + 不得 PASS closure。

`AxisResolution.reason_code`（唯一枚举 `capability_pruned`）随之无生产者，**连同 summary.schema.json 定义与 validateQualityAxes 分支一并删除**，不留死字段。

### 两条不变量（防误读为"放水"）

1. **绝不静默 ≠ 必须阻断。** 可见性由 assurance + capability_resolutions + degradations + 报告头四处承担，一处不减；红线原文「绝不静默」得到满足。
2. **pruned 的门禁入口收敛为唯一一个：`minimum_assurance`。** 要让某 phase 的裁剪构成阻断，就为它声明 floor（→ `insufficient_assurance`）。修订前 quality_axes 与 minimum_assurance 各拦一遍是**双真源**，且**不可配置的那一遍**在拦，把设计好的旋钮架空了；本次修订同时消掉这个双真源。上游 pruned 阻断下游 core 的 `gap.kind=pruned` 不受影响。

### 核心回归（t10 验收线）

**同一份 PASS checks，带 pruned capability 与不带，`projected_verdict` / `release_readiness` / `completion_status` 必须逐字段相等。** 另需保留 blocked 侧全部既有断言。
