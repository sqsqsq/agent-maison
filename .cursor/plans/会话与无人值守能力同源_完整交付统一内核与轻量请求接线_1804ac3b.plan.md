# 会话与无人值守能力同源

## 1. 目标、裁决与范围

基线为 `2552159715c95311a146d00285e1b0facb482f9f`（3.1.0）。7d9c2e41 及其 M1 返修已单独提交，本批不重开它及 28/395/5bdd/371/8a/c2 的完成范围。父目标是 [a47c9d62](../goals/效率与准确率平衡总体目标_默认基线自主交付与可调精细度及可靠恢复_a47c9d62.goal.md) R6；架构沿 [91c4e7a2](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md) 的既有阶段执行内核，不另起平行总纲。遵守 AGENTS 和 overview §1.2.1 四条原文，不改四条总原则。

用户 2026-10-23 确认、10-24 补清入口语义的口径：

1. 本轮结构性裁决取代上一版驱动/降级方案：所有能运行框架命令的适配器，会话完整交付均以“一步一交接、进程不常驻”进入同一 GoalPhaseRuntime。CLI 签发请求后退出，执行者完成工作后再上报，由原 runtime 正式核验并决定下一步；不保留新无 run 完整交付或完整交付 manual_fallback 分流。进程内 AttendedGoalPhaseExecutor 回调可保留给程序化宿主与测试。后台仍走 detached，义务决定阶段，不强求六阶段全开。
2. 修一个函数并验证、单独编译/review/UT/用例设计等仍为轻量任务，不强塞蓝图、Feature、Goal run 或完整流程。这里的“request 轻路径”是任务语义，不代表把所有任务改塞进当前只支持 review/ut/testing 的 request JSON。
3. 自动化程度与运行方式分开。明确授权完整交付并要求“别问我/全权处理”时，会话内也可按原需求静默完成设计/CU及必要架构修订，沿既有渠道提高框架默认额度；未授权仍走原确认规则。这扩展 10-19 的无人值守裁决，不扩大产品目标或实质验收，不授权凭据泄露、外部不可逆动作或突破用户明确的总时间/轮次/费用上限。
4. “在预算内自扩”指提高框架默认额度但受用户总上限约束；不是重置累计消耗、解除无进展或自动无界增额。已有更明确的禁止/范围限制优先。
5. 入口判类沿宿主 AGENTS「需求路由」的两问：本轮改动范围是什么、按什么验收语义算对。主 Agent 判前先查蓝图、既有验收、catalog 和约束知识；正式需求进入 component-design 并由蓝图/CU 义务决定阶段，恢复既有预期的维护和单职责请求保留轻路径。两种运行方式同一判据，不新增需求判定器。

目标是：同一适用任务、同一授权和事实，在不同交互方式下得到同等质量、复用和可恢复性。只报告缺口而无法恢复不算闭环，没有执行或证据缺失不得冒称通过。本方案消除双路径反复接线的根因，不承诺“一劳永逸”：模型误判、真实设备/存储故障、无法证明的授权仍有边界。框架保证有据恢复、正式核验与幂等消费，不宣称能让任意外部副作用恰好执行一次。

本轮只写本 plan、同步 a47；不实施、不提交、不打包、不修改宿主或手机，不新建 `.cursor/` 目录，不混入其它会话改动。实施须另获指令；老规矩为主会话调度，实际 gpt-6.1-sol/xhigh 开发及返修，实际 Claude Code CLI 检视。实施 t1–t7 一次做完、统一验收，中间核对不设用户停点；提交须用户批准且无署名尾注。

## 2. 已核事实与三个执行入口

本轮代码核查及进程内反例未修改生产文件、现场或手机。下列定位以基线函数为准，行号仅便于检索。

| 入口 | 当前真实行为 | 本批终点 |
|---|---|---|
| detached Goal | 同一 runtime 负责调用前后、gate、派修、预算与恢复，executor 负责 CLI 运输 | 保留原运输与进程收容，接共同授权语义 |
| 会话 Goal | 现有 stdio 桥接需常驻等回复，进程内状态不能直接跨命令 | 新 next/report 交接调用同一 runtime；全部能运行命令的适配器使用，t7 真跑后发布 |
| 旧无 run Feature / 轻量任务 | 旧范围/evidence 可读，轻请求有明确目标与报告 | 旧完整交付正式转入 run，不新增手动完整交付出口；轻量维护/设计/编译/request 保留原终点 |

- `buildPhasePrompt` 的生产调用只有 runtime 一处；调用点另外追加自检命令、确定投影、review 复审、facts 基线、testing 缺陷、核实候选与拒修返回。不能只搬函数正文漏追加段。
- `goal-mode-entry.ts::prepareGoalModeRun` 在 attended 出生也构造 `unattended: { approval_mode: never, ... }`；`authorization.mode=goal_mode` 也是桥接默认值。因此二者均不能单独证明用户授予了静默设计修订/扩预算权限。
- `invokeOutOfChain` 当前直接生成 headless plan 并调用 CLI。只删除 `process + detached` 条件会让 attended 修复仍偷偷走 headless，遇无 CLI 的会话无法闭环。
- 普通路径并非无 facts 承接：`capability-resolution-entry-input.ts:538` 有无 run evidence/pendingOwnerPaths 路径；`check-coding.ts::codingTestChanges` 也能排除有效 UT 产出。差距是调用级写入与中断/多次返修的精确归因，不据此推倒已有 reader。
- 同一 TypeError 在 catalog/glossary 旧 `safeRun` 中成为 MINOR/SKIP，真实结论函数返回 PASS；共享 `executeCheck` 对阻断检查返回明确框架缺口、INCOMPLETE。request 的 checker catch 经 `requestFailure` 返回 BLOCKER/FAIL、无 failure_kind。均已用进程内真实函数对照，不是宿主事故复现。
- request provider 的普通 Error 同时承载输入拒绝、能力缺失和意外异常；不能把整个 catch 原样替换后全称 framework_bug。原生断言失败必须继续 FAIL。
- 当前 stdio bridge 常驻等回复，maxRounds 只在轮间交回，waiting 是真实未完成停放。Codex 可写 stdin 工具握手已通过，但新公共方案不依赖该特性；所有会话统一非驻留交接。phase_execute_request 既是 stdout 消息，也会以 command=phase_execute_request 记入 agent_invoke_start（goal-phase-runtime.ts:8133/8431）；不能只查同名事件类型来断言从未运行 attended，真实会话交付仍须 t7 验证。

| runless 新完整交付与 manual_fallback | 退役新执行出口 | 旧范围/完成原件读取和正式转交保留；不再为无隔离能力分出另一完整交付运行路径 |
| request 清除 Goal env、禁止 Feature/receipt 混入 | 按设计保留 | 复用规则不等于复用不相干 Feature 证据；普通测试不借已有 Goal 放宽权限 |
| 后台进程收容、模型 CLI 钉与心跳 | 按设计保留 | 运输专属事实不伪装成 attended 事实；预算、真实质量、责任与恢复规则仍共用 |

## 4. 实施方案与边界

### 4.1 完整交付统一入口，保留轻量性与存量读取

入口判类继续沿 `templates/AGENTS.md.template` §4.0 两问，由主 Agent 先查蓝图、acceptance、catalog 和约束知识再判范围/验收语义。正式需求进 component-design，由蓝图/CU 义务决定阶段；恢复既有预期的维护、纯编译和单职责 request 不扩成完整实现，不新增判定器。

会话完整交付不要求用户学习 Goal 命令。主 Agent 按既有入口准备/接回同一 run，再调用下述短命令领取和报告工作。`in_session_reconcile` 不再是能否使用内核的门槛；已物化且能执行框架命令的 claude/codex/cursor/codeagent/opencode/chrys/generic/deepseek-harness 共用同一入口。`phase_context_isolation` 仅决定阶段交给隔离子代理还是在主上下文执行，并如实披露差异；不能把 YAML 的 false 改成 true 假装有能力。不能运行框架命令或配置无效时如实报告真实能力缺口，不虚构另一条完成路径。

退役新无 run 完整交付推荐及 `manual_fallback` 完整交付出口。旧未完成无 run Feature 经既有 `resolveBirthExecutionScope/registerFeatureScopeTransfer` 从有效范围与证据转入 run，未失效成果复用；旧完成原件与 reader 保留，不补造历史事件。已有活跃 run 优先接回，不并发另起新 run 或倒退为无 run 施工。单独的只读阶段检查仍可提供检查结果，不能借此签发新的无 run Feature 完成。

轻量入口保持原样：普通函数修复按维护授权实施，再执行必要编译/专项验证；纯编译用 compile CLI，纯用例设计只交用例，review/UT/testing 用现有 request JSON/reportDir。只设计 spec/plan 止于原职责，需要确定导出时仅写本阶段产物。在途正式交付的测试仍消费其有效范围，不拆成 request 绕义务；“全权”不把单职责变为完整实现。

### 4.1.1 一步一交接：共用 runtime，不常驻等 stdin

新会话 CLI 只保留有界命令驱动，不常驻等待 AI；退役公开的常驻 stdin 循环及上一稿 `--drive-round` 方案，不同时维护三套运输。命令可以执行真实编译/测试等较长 gate，不承诺固定几秒退出。进程内 `runGoalModeHostBridge/AttendedGoalPhaseExecutor` 回调接口可以保留给程序化宿主和测试，仍调用同一 runtime。

入口复用 `goal-mode-entry` 的项目/Feature/run/授权参数，补两个互斥动作 `--next` 与 `--report-result <JSON>`，报告以 `--request <已签发请求路径>` 指向机器保存的那份请求。回复沿既有 `{status: passed|failed|waiting, phase, details?}`；run/phase/attempt/owner/epoch 从该请求及事件交叉核对，不信任调用方自编元组。框架输出可直接复制的命令，用户不手拼参数；当前调用已明确传入的 --authorize-autonomy 可在同一会话命令提示中原样回显，但它不是凭证，新会话仍由主 Agent 从有效原授权确认后重传，不从打印文本自动提权。请求/结果路径须在本 run 的既有目录中，执行者不得直接编辑 `goal-runs`：请求和报告归档均由 CLI writer 写。

1. **领取**：同一 GoalPhaseRuntime 从真实范围/历史驱动到需执行者的位置，沿原门完成准备、作者完整上下文与写前快照。先原子落盘完整请求材料并提交签发事实，再向 stdout 返回精简交接摘要及请求引用（§4.1.5），进程协作退出；进程内回调 API 仍传完整 instruction。没有 stdin 等待、后台代理守候或第二调度循环。
2. **执行**：有阶段隔离能力就派子代理，无则在主上下文按同一 instruction 执行；两者均传原身份运行自检和 sync-closure。主 Agent 不自行选下一 phase，不改事件/manifest，不把自检当正式通过。主上下文中的控制职责和执行职责按请求边界切换，执行阶段期间不得另派新请求。
3. **上报**：主 Agent 以已签发请求引用提交 passed/failed/waiting。入口先核请求存在、元组/摘要、当前 owner/fence、时限与是否已消费，再采集写后事实、归因和归档结果。`passed` 只是执行者交回，正式 gate/finalizer 仍由 runtime 决定；failed 保留真实失败，waiting 仍为工作未完成。
4. **继续**：报告后 runtime 从同一“执行者已结束、需正式验证”的边界继续，不再调用已完成的执行者；正式门、派修、完成判定均沿原代码。到下一执行需要时再交出一个请求，或返回现有完成/等待结果。主 Agent 只消费该结果，不在 Skill 再写 assess/回退循环。
5. **重入**：请求未报告时 `--next` 返回同一有效请求/恢复提示，不新建 attempt、不重复计次，也不覆盖原快照。执行者先检查已产生的材料再续作，不能因为重复领取就从头重做。报告已消费但 gate 未完成时直接续 gate；已有 finalizer 结果时返回原结果，不重复验证或推进。

协议交回是非终态的 runtime 控制结果，不是 executor 的 waiting，也不发 `phase_halt`/run_end/INTERRUPTED。真实 waiting 才沿现有 `executor_waiting`/外部等待语义停放。改造单一生产生命周期的暂停/继续边界，不通过伪造异常、PASS 或进程已退出事实获得资格。

### 4.1.2 跨交接身份、快照与预算

当前 `releaseAllLocks` 会释放 session owner，而 `validateAttendedGoalContext` 要求 active owner 和有效 lease；两处必须一并接线。签发交接后保留逻辑 session owner/fence，不能走普通终态释放。进程内互斥锁在短事务后释放，不留下依赖死亡 PID/常驻 heartbeat 的锁；同 run 报告以有效请求/fence 重新进入短事务，不无条件 CAS 出新 epoch。原启动、接管、设计发布入口共用当前 owner/挂起请求判据，不能看到 CLI 退出就认定执行者已结束。

session lease 至少覆盖本次签发的有效执行窗口、最多受该请求 deadline 与剩余预算约束；沿原 lease 字段维护，不新增租约体系。命令内心跳不能把已签发窗口缩回默认 60 秒，反复领取也不能把 deadline 向后滚动。新会话能恢复仍有效的原请求时继续同一授权窗口；真实接管仍沿原 owner/epoch 规则，不给普通“新会话”自动 force 权。

**到期不等于必须人工接管**：在普通 lease 拒绝/取 owner 之前，共同交接读取器先核同一未消费请求、原签发依据和当前 fence。若请求 deadline 已过，但 run-control 仍是该 owner/epoch、没有他人接管或后续取消/失效，`--report-result` 或 `--next` 可在短事务中把本窗口按既有 agent_timeout 收口；即使它因自然到期被标为 orphaned_session，也不走 force takeover。记真实 agent_invoke_end.timed_out、已发生写入与消耗，不声称杀过进程，不补 settled，不赋予验证优先；保留产物，按原超时续作/新 attempt 规则继续。总预算耗尽仍停在原预算出口，不能借这条续作提额。超时收口且原执行窗口/受管作业已终结后，把该 owner 沿既有 released 状态交还，再正常 CAS 进入新 epoch；这是同一已到期请求的收口，不是通用孤儿强接管。只有不同 owner/epoch 已接管的旧报告，或不能证明对应当前未消费请求时，才拒绝这条到期收口例外。

到期处理不证明后台作业已消失：主上下文提交报告表示交回该执行窗口；使用子代理/工具后台作业时，主 Agent 须先消费其实际终态或取消结果，已知仍活的受管进程沿原收容处理，不能同时启动新 attempt。不是要求模型主会话进程退出，也不以“lease 过期”冒充物理停止。真实接管后只追加重签当前请求的 fence、保留原 attempt/原快照和计次，不能覆盖原签发文件；旧未消费回包拒绝。

写前快照、原写界及来源绑定必须在签发前落到本 run 的现有调用目录，报告时只能读那一份，不能重新拍“写前”把已经发生的改动洗掉。复用 `capturePhaseInvocationSnapshot/diffPhaseInvocationSnapshots/classifyPhaseInvocationChanges` 生成原 `phase_write_observed`，facts 再准入、测试归属、新鲜度读同一事实。原快照取得失败时保持既有降级或设计修复拒绝语义，不能自报干净；普通审计缺口不另加常态硬门。

派发沿原 `agent_invoke_start` 计一次；重领、重报、补 gate 不再计一次。阶段从签发至交回的实际执行时间必须计入原活跃墙钟，CLI 退出不当作停机等待免费扣时，睡眠仍计时；真实 waiting 停放之后才沿原停机等待口径。统一预算折叠与截止判据，不能靠反复启动 CLI 重置 sessionStart/turns。派发预算与已派发工作的归档/验证分开：合法最后一轮把调用次数用满后仍可报告并在原验证预留时限内 gate，不能被下一轮的派发门误拦；总墙钟真正用尽时可归档事实但不超额执行 gate/新模型调用，保留待验证产物走原预算恢复。

非驻留框架不具备凭空杀掉宿主主会话模型的能力：执行者须消费明确剩余时限，工具/子代理有真实取消或超时能力时使用它；没有该能力不得声称物理强制终止已经发生。硬预算仍约束框架派发/报告/接续，不通过编造 process-settled、计时归零或免费等待掩盖超限。

### 4.1.3 报告幂等、正式 gate 与故障恢复

挂起请求是既有事件的派生视图，唯一读写边界收编在 `session-execution-handoff.ts`，只负责交接事实；阶段选择与推进仍在 GoalPhaseRuntime。每 run 最多一个未消费执行请求。没有对应签发、旧 epoch/错误 phase、材料引用不匹配的首次报告在副作用前拒绝，不因此给原任务另写终态。

请求材料先落盘，带引用的 session `phase_start` 签发事件最后提交；崩溃于两者之间时未提交文件不授予执行资格。原 `agent_invoke_start` 与 session `phase_start` 的半完成窗口可按同一 attempt 补齐后再发请求，不重复计次；尚无签发时不能把临时文件当已执行，必要时重新准备未派发窗口并如实记录。接管/重签追加新的 session phase_start 请求引用，原 agent_invoke_start 只计一次；原快照与输入不被重签替换。当前有效请求只读同一未失效 attempt 的最新合法签发，不能读到一份旧引用继续授旧 fence。时间起点与权限签发分开：同一 attempt 的原执行起点取原 agent_invoke_start（旧记录保留原兼容读法），当前 fence 取最新合法 session phase_start。重签不能后移预算或修复比对窗口；同步核对 goal-progress、相关输入比对、完成检查及 attended-goal-context 的直接读点，不另写一套起点算法。

报告只消费一次：先由原快照形成可核对的写后事实，再提交结果；同一 invoke 的 `phase_write_observed` 按已有 invoke/pre/post 标识幂等补写，不能重复接进源码哈希链。报告同内容重发返回已收回执；不同内容重报不得覆盖旧结果。已接受旧报告的纯查询不重新取得当前 owner 权或触发新动作。

扩展共同的“执行完成/验证优先”读取，使**已核身份且已归档的会话报告**与真实进程执行完成成为两种明确来源。不得伪造 `agent_process_settled`，也不能对旧事件全局删除 settled/harness_end 要求。会话首次回报时尚无正式 harness_end 是正常的：进入同一 post-agent 正式 gate 路径；若在收报、写入归因、gate 或 finalizer 之间崩溃，再接入只补未完成部分。waiting 不构成执行完成，后续恢复沿原判断决定续作/新 attempt；真实产品失败不能因运输恢复变成 PASS。

需要的新持久内容仅为 §5 表中不可从既有事件重建的原始材料和引用。结果是否完成仍由正式 summary/evidence/finalizer 决定；不另建 pending.json、会话状态库、检查级补跑状态机或第二份完成结论。

### 4.1.4 正式 gate 的命令时长与进程收容

这里“不常驻”仅指不挂着进程等 AI 回包，不能解释成正式 gate 必须短于宿主工具默认时限。本批选择**复用各宿主原生长命令/后台任务句柄并等待该次命令终态**，不把 gate 再切成新的任务队列。Skill/适配说明按当前工具实际能力设置 timeout，覆盖 runtime 的本次 gate 有效时限和取消清理预留；可用后台句柄时一直等待同一命令，不重复提交 report 来“催进度”。请求/报告命令提示直接给出同一预算解析得到的本次 gate 时限与工具清理预留，执行者不靠猜测设置 timeout；这是调用提示，不延长任何 deadline，正式运行仍重核当前预算。不把未经本机核实的固定两分钟/十分钟当统一配置。工具既不能给足时限也不能提供可等待句柄时，在不可分 gate 启动前如实报告执行能力缺口，不用反复被杀证明进展；可命令会话接入内核不等于机器一定具备所有构建/设备能力。

正式 harness 子进程也要接既有进程树/guardian 的身份绑定、取消和结束确认，不只保留进程内 activeHarnessKill 引用。相关 PID/启动身份/令牌沿现有过程记录承载，标明它是 harness 验证进程，不能被执行者完成 reader 当成 agent_process_settled。报告命令被外部工具杀掉后，再入先确认上一 gate 已结束；仍活则沿原等待/有界回收，不启动第二个 gate、不按旧 PID 杀不相干进程。无法证明已结束保持既有收容缺口，不能重叠写 summary/账本。

已接受执行报告后发生 gate 中断，只续正式验证，不能重新调模型。已有 harness_end/finalizer 事实可核实时复用；没有正式结束事实先解决旧进程，再在正确的工具时长内续 gate。t7 必须模拟报告进程在慢 gate 中被宿主杀掉并恢复到一次正式完成，不能只跑很快的设备替身。

### 4.1.5 精简交接输出与重复启动成本

`--next` / `--report-result` 的 stdout 仅保留请求原件路径与 sha、phase/attempt、一行真实状态和下一条可复制命令；进入等待或完成时返回相应原因/结论与报告路径，不重复打印完整 instruction。完整作者上下文（包括 buildPhasePrompt 及追加段、原身份、时限和执行命令）只保存在同一请求原件中；隔离子代理按路径读取，主上下文执行者在需要执行时读取。进程内回调 API 保留完整 instruction，CLI 精简的是显示投影，不建立第二份上下文真源，也不删减执行者应知的授权与质量要求。

会话正式 gate 的 harness stdout/stderr 长输出写入本 run 现有调用日志，CLI 仅回结论及报告/日志路径；等待原因、能力缺口和失败状态要当场可见，不藏到日志里。按原日志脱敏要求保存，不能把完整输出转到 stderr 后继续灌进主会话。沿既有 logger/输出回调接线，detached 原日志行为保留，不新造日志系统。记录主会话每阶段实际接收的输出字节，控制交接输出与执行者主动读取原件分别计量，不把主上下文必需读取的提示成本算成已消失。

运行时 ts-node 统一只转译：优先在 `harness/tsconfig.json` 配置 `"ts-node": {"transpileOnly": true}`，供本仓 runtime、正式 gate、自检及文档示例命令共用，不逐处重复带参数。实施时核对实际 tsconfig 解析：从工程根或 harness 目录运行两类入口必须读到本配置；确有绕过该配置的调用，仅在该调用显式指定本仓配置。不得影响宿主业务代码的编译检查。`npm test` 原有 `tsc --noEmit -p tsconfig.typecheck.json` 与发布门独立类型检查完整保留，不减 schema、业务或运行时检查。

Claude 提供的 goal-mode-entry 5.5s→2.8s、harness-runner 3.9s→1.9s 是评审参考数据，尚非本轮复测结果，也不作为硬耗时门槛。t7 在同工程同输入记录实际启动次数和前后耗时，并确认语义输出一致；不新建基准系统，不为每次窄返修重复长链。

### 4.2 授权与执行方式分离，预算仍有界

唯一读取落点是在现有 `runtime-policy.ts` 新增纯内存函数 `resolveTaskAutomationPolicy`，runtime、桥接和提示消费同一结果，不各写判断。现有 `authorization.mode/through_phase` 只管阶段推进，manifest.unattended 的 full-access/never 只表技术执行能力，不能复用为业务裁决权。

补一项非持久启动输入 `--authorize-autonomy`：主 Agent 根据可信用户原请求及更正确认“完整交付＋别问/全权处理”后，向 `goal-mode-entry --prepare-run` 和随后的 attach 明确传入；入口经内存 options/已有 runtime authorization 选项的 `autonomyAuthorized` 传递，缺省 false，不写 manifest、run-control、execution-scope 或新的授权账本。prepare 输出不能被当作凭证；attach 必须有本次输入。阶段执行者不自行授予此项，既有嵌套运行和 owner fence 边界保留。审计仍引用已有原请求来源，账本不授予权限。

每次会话重新接入，主 Agent从仍有效的原用户授权重新传递，不重复问已经明确授权的用户；没有可信会话上下文/输入的重启、后继或 supervisor 拉起，不自动继承 attended 的全权位，沿既有确认或能力恢复路径处理。原请求含“全自动”等文字、默认 never/goal_mode、引用文档、日志或 Agent 自写决定，都不由 runtime 直接推成授权，不新增关键词口令表。

接回时若缺本次全权输入，提示“本次按需确认；主 Agent 应先核对已有可信原授权再重传”。没有该输入不等于撤销原用户授权；只有原授权不可恢复或有冲突才向用户澄清，不要求每次换会话重复说“别问我”。

detached 的兼容来源单列：保留 10-19 “用户选择无人值守完整交付”已授予原目标内自动设计修订的政策和既有入口，不要求旧 detached 另带新开关。它不是“任意后台进程都有全权”；局部任务、手工启动的 phase 子进程和原请求明确禁止均不适用。默认额度自扩仍额外要求原请求明确不要询问；不得仅凭 detached 或默认配置扩预算。内存共同判定同时表达这条既有来源与 attended 显式来源，不能删掉旧来源导致已交付自动恢复回退。

有完整交付及明确全权授权时，原目标内设计、CU、architecture_impact 各种既有类型仍由设计 owner 正式草稿、独立质询、检查、发布和重绑。默认额度由主 Agent 的既有维护动作明确更新 manifest；runner 不自己循环增额。必须披露来源、前后额度与累计消耗，守用户总上限、不清零；不存在总上限也不是无限消耗授权。

预算接线必须实际补通：`goal-mode-entry` 接受并透传既有 `--override-manifest`。prepare-run 将其作为 budgetOverride 传入 decideRunContinuation，预算继承调用共用 resolveCycleEffectiveBudget 的 override 语义；attach/host bridge 将其传给 GoalPhaseRuntime，复用现有身份核对、budget_changed 和累计额度。不能只改 manifest 后重发普通 attach，也不能在预算停机时先出生空后继。仅在原请求全权授权或用户单独明确批准本次额度变更时使用；预算专属批准不授予设计全权。没有该覆盖参数的漂移仍拒绝，request 入口仍不接受 Goal 参数。

沿现有停机指引说明 `--override-manifest` 是整体身份覆盖参数，不是预算专用开关；主 Agent 使用前核对差异属于本次授权，不能以只批预算夹带需求、范围或 adapter 变更。不另加覆盖字段或授权登记。

确认不是质量判据：普通会话不应因运输方式损失已授权的修复能力；全权也不允许改弱验收、藏掉失败、换题或修改 framework 发布件。设计内容改变超出原目标、凭据与外部不可逆动作仍按实际授权处理。

### 4.3 准备与作者上下文同源，避免复制大提示

完整交付直接消费当前 `buildPhasePrompt` 及调用点追加段，不另抄一份“普通 prompt”。如为 request 复用需要抽出片段，将原函数本身移到现有共享工具层并让原调用者改读；只输出适用知识、目标、失败与当前命令，不把 Goal 编排约束整段灌入轻请求。

逐项锁定 §3 中的重试分类、testing 缺陷、review 复审、本阶段写界、冻结义务、facts 基线、目标简报、作者知识、UT 格式、精确命令、上游延期和能力降级。准备只发生在合法作者窗口；dry-run、post-agent 收尾、只读 review/用例设计不意外写三份产物。已有增量与冲突保护不变。检查器仍不因为“准备”而悄悄写上游。

两种完整交付共用原 pre/post snapshot、agent_invoke_start/end、phase_write_observed 与 evidence；会话仅把必须跨进程保留的原件和引用落到既有 run 内，不另造调用账本。轻量请求已有 `request_sha256 + baseline/bindings + reportDir` 只证明本次目标，不证明某个阶段曾执行；只有真实前后原件才能比较，归属不明时如实说明，不将全 Git diff 冒称本次 Agent 贡献。

### 4.4 链外修复、隔离与等待使用同一交接

`design-repair-author`、`design-repair-questioning`、`<当前阶段>-verifier-format-repair` 使用同一 next/report 运输。既有用途标签、草稿写界、同 run/owner/epoch/调用编号仍由 runtime 签发；它们不是新工作流阶段，不补入 chain。普通阶段的 chain 校验保持，链外只接受当前事务实际签发的用途。

设计修复不能在每次 CLI 重入时清空 draftDir 或重复发 attempted。把现有 `runUnattendedDesignRepair` 的草稿准备、作者、独立质询、校验、发布/重绑拆成**可从原事件和草稿恢复的同一事务步骤**，detached 也消费同一实现。原 signature、canonical/CU/架构依据、原写前快照和必要的每用途原始草稿结果保留在原 design-repair/调用目录；步骤是否已完成从已签发请求/已接受报告和既有 design_authority_repair 事件派生，不写第二份进度状态。

作者与质询之间交回时，仅处理草稿，不能提前改 canonical/DSL。短 CLI 重新取得既有蓝图/CU/Feature 发布锁并核原始依据，再继续；期间别的合法修订使依据变化时沿原 stale/owner 路径重评，不覆盖新设计。发布后、published 事件前若崩溃，以当前 canonical 身份、目标 revision/内容及既有发布记录核对是否已经发布，只补重绑/原事件，不二次升版或重新调用模型。发布本身、CU 调和和回滚仍由原事务负责，不新增跨工程事务框架。

普通阶段缺隔离能力时可在主上下文执行并披露；**这不放宽原本要求独立的 verifier/设计质询**。这些职责仍必须使用实际独立上下文/已获准独立 provider；缺必需能力沿原缺口策略，不靠改 role 名或自报“已质询”通过，也不额外将所有可选审查升级为硬门。无隔离阶段的完整交付验收必须同时证明所需独立核验是真的独立。

链外只执行 instruction，不跑普通阶段 harness/receipt；用途报告 passed 不等于 published。格式修复沿原报告/subject 身份处理，之后由 runtime 携原阶段 attempt 正式重验；不能拿链外编号替代 verifier subject。waiting/失败/中断按既有尝试与预算规则保留事实；因运输交回而暂停不能记成失败并删除草稿，也不能重置修复机会。

会话等待在本次短命令里输出具体原因与原探针/恢复指引后交回；不再为它维持 15 分钟常驻 stdin。用户或已有外层跟进再次发起同一请求时由同一探针和原门复验；不新建每轮后台 watcher。detached 保留原进程内有界等待。设备恢复必须先补原 UT，再执行依赖 testing；人工设备动作和凭据授权不能因“别问”被伪造。

### 4.5 轻请求的异常与复用，以及全局检查

异常落点：`request-phase.ts` 的 checker catch、provider catch；profile request UT/testing 中被普通 Error 混装的输入拒绝/执行结果；catalog/glossary 的旧 safeRun。先在知道真实事实的生产点保留明确输入错误、能力/环境阻塞、原生断言失败及不可识别程序异常，复用已有 CheckResult 分类和 `executeCheck` 语义，不在 catch 中用错误散文正则猜归因。纯编译已有结构化工具链结果沿原路径，不借本批改写全部编译协议。

真实断言 FAIL、错误目标/计划/缺少必需输入仍按原语义返回；provider 不支持/设备不就绪等明确缺口使用已有分类；未执行的程序异常如实标明框架缺口，不能假 PASS 或默认代码回归。catalog/glossary 保留原检查严重级别，加载失败仍是原错误。不得重新把未分类 BLOCKER/SKIP 全局升级、不得把所有 MAJOR 异常变成必需阻断。request 报告沿同一明确缺口判定且保持 request 终点，原本独立的输入拒绝不改成“框架坏了”。

复用落点为 `execution-key.ts` 及现有 frozen artifacts，而非新 request 缓存。接通 hmos `providers/ut-run.ts`、`providers/device-test-request.ts` 对现有复用判据的消费：用本次实际选择的模块/用例、构建与测试包、设备/显示、步骤/预期、工具版本、flags 构成既有执行输入；冻结本次全部原生证据，在 request 独立 reportDir 内归约。不能把其它用例或 Feature 的成功借给当前请求，也不能用请求文本哈希替代真实执行输入。已有结果真正等价时只重算派生报告；输入改变、较新失败、证据不全或显式 fresh 时真实执行。

同轮失败重放和成功复用分开：attended 与 detached 都有真实 run/phase/attempt，原失败继续判失败；设备解除或新 attempt 必须重新执行。request 一次 provider 执行结果可在同一调用内继续消费，普通 request 没有“作者自检后 runtime 正式 gate”的第二调用，不为制造同轮身份新建协议。独立重发没有可靠同次身份时不重放旧 FAIL，沿同一失败/成功裁决规则真实执行。native 测试结果复用必须仍包含所选用例全部断言，不能以元素出现或 missing/manual/skipped 当通过。

## 5. 规格同步、裁剪与必要持久内容准入

同步 project-entry、AGENTS 模板、Goal Skill/operations/runbook、request-harness、全部 adapter 会话能力说明及 schema、OpenSpec goal-runner/goal-mode-skill/能力路由/恢复/预算与 MIGRATION。Goal Skill 的等待禁令同步收窄：允许宿主原生工具等待同一条长命令句柄，仍禁止自造 sleep/轮询等待器及重复提交报告；不能让两条指引互相冲突。`phase_context_isolation` 只描述阶段上下文安排，不再与 `in_session_reconcile` 合取决定是否能进入内核；代码配置校验中两者的强依赖一起移除，不修改值虚报能力。框架交接恢复不依赖模型 CLI 的原生会话 resume 功能；保留后者对真实原生运输/handoff 的含义，不能混称一回事。

裁剪清单：公开 CLI 常驻 stdin/readline 循环、上一稿 `--drive-round` 双运输方案、新无 run 完整交付推荐、完整交付 `manual_fallback` 出口及对应手动推进文案。保留清单：同一 GoalPhaseRuntime、进程内回调 API、detached 运输、request/纯编译/纯设计轻入口、原 gate/finalizer、已有历史 reader 与旧范围转交。P8/91/P2/P7 中仍生效的双载体说明加本轮政策替代说明，历史验收和 completed todo 不重写；7d9 已完成范围不重开。

旧活跃 stdio 调用不能热换协议或由新 CLI 假报结果；先用旧发布件收尾当前调用或按原机制安全停放，再从同一请求/已验证记录迁入。旧无 run 未完成范围正式转交后才继续完整施工，旧 completion 原件只读。新用户始终只表达需求，命令和身份由主 Agent 按框架输出使用。

本批挂起事实只由既有 events 派生，不新增 Goal 状态枚举、停机原因或运行时注册表。以下字段名为计划约定，属于既有事件/材料的必要扩展，实施时保持唯一 writer：

| 增量 | 不能只用现有信息的具体原因 | 最小承载与规则 |
|---|---|---|
| 一步一交接 CLI / 内部非终态交回 | 命令式会话不能依赖常驻 stdin；waiting 会停机，不能代表“尚待执行” | goal-mode-entry 的 next/report/request 引用；同一 runtime 的显式交回结果，完整 phase_execute_request 落原件、CLI 仅回引用与精简状态，不新增并行运行器或 Goal 状态 |
| session `phase_start.handoff_request` 可选引用 | 原事件仅有部分 facts/命令，不能重建完整上下文/前快照；接管需追加重签而不能改旧 invoke_start | `{path, sha256}` 指向不可变请求原件；复用原 run/phase/invoke、owner/epoch 与 invoke_start 的时限，最新合法签发唯一决定当前请求，不新增请求 ID |
| 请求原件的快照/原写界引用 | 当前 PhaseInvocationSnapshot.entries 与写界只在内存；摘要不能重建逐文件前态 | 原调用目录保存原 snapshot/解析写界及必要来源引用；请求原件绑定其摘要。不是新的事实 SSOT，只持久化原调用输入；不重捕替代，不保存秘密环境/凭据值 |
| `agent_invoke_end.handoff_report` 可选引用 | 会话没有进程 settled 事实，旧验证优先路径不能证明已收到哪个结果；重复提交不能重复归因/计次 | `{request_sha256, path, sha256}` 指向 CLI 归档的原 passed/failed/waiting 报告及写后核对；旧终态字段继续使用；不伪造 process-settled，不以报告当质量 PASS |
| `design_authority_repair.handoff_context` 可选引用 | 设计事务的原 canonical/CU/架构依据、eventsBefore 与草稿阶段原件是局部变量，重入当前函数会清草稿并重复 attempted | 仅在原 design-repair/调用目录保留必要基线/合法追加事实及各用途原始草稿结果，现有 attempted 事件引用；进度由同一签名的调用/报告及发布事实推导，不另写事务状态账本 |
| 非持久授权与预算覆盖 | attended 默认 never/goal_mode 不是业务授权；现有桥接漏预算覆盖参数 | 保留已定 --authorize-autonomy/内存判断与 --override-manifest 透传，不落新权限或预算字段；每次新控制调用按原有效授权重传 |
| 正式 gate 的进程收容接线 | 外部工具杀报告 CLI 后，内存 kill 回调丢失，可能重复启动仍存活 gate | 扩展既有进程树/guardian 在 harness 调用处的消费，复用原身份/结束事实，不新增守护服务、进程状态库或停机原因 |

只保存已签发调用实际需要的材料，禁止序列化 process.env、凭据值或额外全工程源码副本；源码前态用原快照，设计小草稿保留必要原字节用于后续规范化/质询，不用仅有摘要的现状冒充旧草稿。事件的有序事实和正式完成证据仍是唯一依据，不建 pending.json 或跨 run 队列。现有审计/文件不可核的处理边界保留，不借新增引用把所有过程异常升级成硬门。

收益是：全部可命令会话使用同一执行内核，原调用信息跨交接不丢，新能力不再分别接到手动无 run 路径；报告重试、进程重启和阶段执行不再依赖一根常驻 stdin。新增的只有不能从原记录重建的必要原件/引用，逐条由上述实际故障边界验收；若还需其它持久字段/状态/消息类型，先说明场景与不可复用原因，不能以“自愈”名义扩成通用工作流平台。

## 6. 开发验收：真实会话与跨交接故障

三路径为 detached、非驻留会话交接、轻量 request/专用入口。使用仓内已保全的 fe4512、179a73、20261019 和 3.1.0 快照，原件及来源哈希保留，环境适配单列。对照适用的事实、归属、真实执行次数与恢复终点，不要求 request 产生 Goal 事件/设计链/completion。

| 场景 | 必须观察到的结果 |
|---|---|
| 路由和裁剪 | 既有两问在全部适配器一致；正式需求先设计，维护/单职责不强塞蓝图/完整链；所有命令式会话走 next/report，不回 manual_fallback 或新无 run 完整交付 |
| 命令返回与工具适配 | --next 在输出已提交请求后进程退出，不等 stdin；执行期间无常驻 bridge/后台代理。全部八类基线 adapter 用相同请求/报告形状；有无隔离只改变上下文安排和披露 |
| 精简输出与类型门 | stdout 无完整 instruction/harness 长日志，原件和本 run 日志齐全，状态与下一命令可直接使用；进程内回调上下文不变。根目录/harness 两种调用均命中只转译配置，独立 typecheck 仍会拒绝类型错误，业务检查结果不变 |
| 真实 Claude 会话完整交付 | 两条实际 Claude Code CLI 主会话分别经子代理隔离和主上下文执行阶段，调用生产 next/report，真实 gate/finalizer 产出完成；测试脚本不能代写报告或预设 passed |
| 真实 Codex CLI 单阶段冒烟 | 实际 Codex CLI 会话自行 --next、读取请求、执行/自检、--report-result，走到真实正式 gate；不以桌面工具握手或测试程序代回包替代，证明交接不依赖 Claude 特性 |
| 旧范围转交 | 旧无 run 有效范围/成果可读并正式转入 run，原件不改写，不新开第二个活跃运行；已有完成证据按原条件复用 |
| 前置准备与上下文 | 两完整路径投影/作者追加段同源，重复准备零写入，现有冲突不覆盖；精确自检/报告命令来自本次签发上下文，不能手拼新身份 |
| 授权与预算 | 已定的全权/默认值/旧 detached 正反例保持；--override-manifest 正确透传，累计不清零，硬上限有效，单独调预算不授设计全权 |
