# 统一目标上下文与权威判定

上位：[任务完成可靠性总纲 272acb5f](./任务完成可靠性总纲_统一原则与恢复闭环及可靠性验收_272acb5f.plan.md) §3、§5.2。
前置：[P1 可靠性基线与任务集 1dbe4fa4](./可靠性基线与任务集_指标口径与十三场景及基线记录_1dbe4fa4.plan.md)。

## 1. 目标与冻结范围

**目标**：所有参与方拿到同一份目标；冲突由执行者按目标裁决并留痕；任何一方的判断都能被同一权威的正确解释或实测证据纠正；
已经做出来的越权内容能被发现并移除。

**做**
- 目标简报的组装、渲染与同源注入。
- 拒修与反驳两个环节的运行时处理，以及它们的回放语义。
- 缺陷类别的反方向。
- 行为规约的权威判定，以及被替代旧指引的清理。

**不做**
- 不新建 manifest、持久文件、输入绑定。目标简报每次现算，不落盘。
- 不改 headless-assumptions 的 schema，不新增停机原因，不加回退预算。
- 不改停机后的恢复与接续（P3），不改失败检查的处置策略（P4）。
- 不放宽没有拒修记录的零改动终局判定。
- 不动真人授权类的停等条目（设备策略、人审闸门等）。
- 不做语义判定。引文核验只证明来源，不证明拒修正确。

## 3. 目标简报（t1）

### 3.1 内容与来源

| 栏目 | 来源 | 取不到时 |
|---|---|---|
| 需求原文 | goal run 取本 run 冻结的 `manifest.requirement`，含后继 run 的"本轮修复增量"；无 run 取既有的无 run 分支 | 写明"需求原文不可得"，其余栏目照常，不猜 |
| 请求结果与完成目标 | 有效执行范围，已叠加范围修订 | 省略该栏 |
| 明确不做 | `ref-elements` 里登记为 excluded 的条目及其引文；spec 的出范围模块 | 省略该栏 |
| 已授予的权限 | `effectiveHeadlessUnattended` 给出的审批与写入模式 | 省略该栏 |
| 已裁决的冲突 | §4 的拒修记录 | 省略该栏 |
| 判定办法 | 一句话加指向行为规约"权威判定"的链接 | 恒有 |

"明确不做"一栏写明：需求原文里明确写了不要或本次不做的内容同样是排除项，即使尚未登记。

### 3.2 实现约束

- 新文件 `harness/scripts/utils/goal-brief.ts`：一个组装函数返回结构化对象，一个渲染函数返回文本。所有注入点调用同一对函数。
- 当前执行身份与需求来源的解析只有一处。把 `collectCurrentRequirementText` 里"解析身份与来源"的部分提出共用。
  既有函数保持原行为：解引用、拼接 `requirement_source_files`、无 run 时的来源与哈希校验都不变，`check-spec.ts:1739` 的核验行为不变。
  简报单独使用冻结文本，不重读源文件。
- 装配去重：执行者提示词保留现有的需求行与冻结范围段，简报块只补"明确不做、已裁决的冲突、判定办法"；
  verifier 的已解析输入里已有需求时，简报不再重复需求正文。这是装配要求，不是对偶然重复字句的计数规则。
- 简报不落盘，不进证据清单，不成为新的输入绑定。

### 3.4 verifier 的契约

1. **简报内容参与材料摘要**。材料视图新增分量 `goal_brief_sha256`，取渲染后简报文本的摘要。简报为空时分量为空串，
   此时 subject 与改动前相同。
2. **简报变化即换 subject**。需求、排除项、拒修记录任何一项变化，当前 subject 都没有报告。
3. **沿用历史评审的规则不变**。当前 subject 没有报告且历史有过 PASS 时，仍走既有的沿用分支并出 MAJOR 警告；
   从未 PASS 过的阶段本来就要评审；当前报告是 FAIL 或其他校验错误时不走沿用分支。
4. **沿用不等于看过**。沿用的历史评审没有看过本轮的拒修。有拒修在案的候选要成为返修候选，确认它的 verifier 证据
   必须属于当前 subject，见 §4.5。
5. **送达路径**。回退之后 review 与 testing 阶段会重新调用执行者并重跑 harness，harness 以新 subject 签发评审请求，
   阶段执行者按既有指引调用 verifier。本 plan 不新增调用路径。

已完成 feature 的完成记录不读 verifier 的 subject，不受影响，由 §8 的 C1 守护。

### 3.5 行为规约

`skills/reference/agent-behavioral-principles.md` 新增一节"权威判定"，作为唯一出处，内容对应总纲原则 2、3、4：

1. 目标由当前有效的授权与明确修订确定，有权者最新的明确表述为准。
2. 证据不定义目标，但能证明实现是否符合目标。
3. 裁判的缺陷与修法、执行者的裁决记录，都是可纠正的判断。
4. 下位与上位冲突时按上位执行并留一行裁决记录；只有上位表述彼此冲突且现有授权无法裁决时才问人。

| `agent-behavioral-principles.md:25` | 不确定时停下来问用户 | 能由当前目标裁决的不确定，按目标裁决并留痕；目标本身冲突或缺失且无法裁决时才问 |

## 4. 判断双向可纠正（t2）

### 4.1 术语

| 术语 | 含义 |
|---|---|
| 回修轮 | 一条 `phase_backtrack_requested` 事件及其窗口。窗口从该事件起，到同一 run 内下一条同类事件或 run 结束为止 |
| 本轮下发的候选 | 回修轮事件里记录的候选中，责任阶段等于本次被回退到的阶段的那些，也就是实际注入该阶段提示词的候选 |
| 拒修记录 | 账本里的一行，形状见 4.2 |
| 拒修动作 | 一条拒修记录，其 `run_id` 等于回修轮所在 run，时间落在该回修轮窗口内 |
| 来源核验通过 | 拒修记录指向本轮下发的某个候选，且引文逐字出现在当前目标文本中 |
| 反驳 | 某候选在一个有来源核验通过的拒修动作的回修轮之后，再次出现在候选里 |

### 4.2 拒修记录

写入责任阶段的既有账本 `<阶段>/headless-assumptions.jsonl`，一条候选一行，不改 schema：

| 键 | 取值 |
|---|---|
| `gate_id` | `repair_candidate:<候选的 item_fingerprint>` |
| `class` | `goal_conflict` |
| `decision` | `declined: ` 加依据，依据中用「」逐字引用目标里的一句话 |
| `must_review` | `true` |
| `source` | `agent` |

写法说明放在返修候选段里，该段在有人在场与无人值守两种模式下都会注入。再次拒修必须追加新的一行。

引文核对与 `ref_elements_excluded` 是同一个函数，从 `check-spec.ts` 提出共用。需求被明确修订后，引文若不再逐字存在，该记录失效。

### 4.3 唯一的状态来源

新增一个纯函数，放在 `repair-candidates.ts`。输入是交付周期内的事件与各责任阶段的账本，输出是每个候选的状态：

| 输出 | 含义 |
|---|---|
| `declined_rounds` | 该候选有来源核验通过的拒修动作的回修轮数 |
| `rebuttal_used` | 该候选是否已经用过反驳轮 |
| `basis` | 最近一次拒修的依据原文与所在 run |

约束：

- 交付周期内的事件取法与预算折叠同源，复用 `foldBudgetLineage`。祖先 run 里的拒修与反驳同样计入。
- 状态只由事件与账本得出。内存里的回退待办状态、完成事件上的拒修清单都不是来源；完成事件上的清单只供诊断。
- 旧的拒修记录在后面的回修轮里仍然存在，但不落在新窗口内，不算新的拒修动作。

### 4.4 消费点

四处判定消费同一个函数的输出：

| 判定 | 位置 | 规则 |
|---|---|---|
| 已尝试记录 | `:2044-2069` | 某候选在一个回修轮里有来源核验通过的拒修动作，且 `declined_rounds` 为 1：该轮不计入已尝试。第二次拒修起照常计入 |
| 可修集合与收敛 | `:2076-2084`、`:8824-8890` | 随已尝试记录自然得出，不另写规则 |
| 整轮重复 | `:9872-9890` | 计算整轮指纹时，排除"`declined_rounds` 为 1 且 `rebuttal_used` 为否"的候选，它们这次出现就是反驳轮。排除后集合为空则本轮不做重复判断。继承自祖先的指纹按同一规则处理 |
| 零改动 | `:8456-8501` | 判为 no-op 时，本轮下发的候选**全部**有来源核验通过的拒修动作：不停机，完成事件的结果记为 `declined`，继续下游。只要有一条没有，保持现状 |

覆盖的情形：

| 情形 | 结果 |
|---|---|
| 信号级候选全部拒修，零改动 | 不停机，继续下游 |
| 修好 B，拒修 A，非零改动 | 普通完成。A 不计入已尝试；裁判再次提出 A 时进入反驳轮 |
| 其余候选（review、断言路由、provider、纯文本）拒修 | 不经过零改动判定。裁判再次提出时，整轮重复判断按上表排除，进入反驳轮 |
| 混合批次 | 按本轮下发给当前责任阶段的候选逐条判断，不要求其他责任阶段已经表态 |
| 没有拒修记录的零改动 | 保持 `repair_not_converging` |
| 拒修记录的引文不逐字 | 视同没有拒修 |

回退预算上限不变。一次"拒修、反驳、修复"占两次回退，前提是此前本周期没有消耗过回退。

下游照现状全部重跑。零改动时 review 与 ut 的重跑是无影响阶段重跑，会如实计入 P1 的指标；减少它属于 P3。

### 4.5 反驳轮与未收敛

- 反驳轮下发给执行者的候选段里，逐条写明：上一轮以什么依据拒修，裁判在看过依据后仍然提出。
- 执行者在反驳轮修复，则正常推进。
- 有拒修在案的候选来自 review 时，确认它的 verifier 证据必须属于当前 subject。沿用的历史评审不能确认它，
  该候选本轮不成立，也就不构成反驳。
- 执行者在反驳轮再次拒修、裁判仍然提出：这只说明没有收敛，不说明目标本身冲突。此时既有规则照常生效，
  停在 `repair_not_converging`、`backtrack_fingerprint_repeat` 或 `backtrack_limit`。停机说明里并列双方的原文：

## 10. 放弃的准确性与已知代价

1. 引文核验只证明来源，不证明拒修正确。引用一句无关的原文也能获得一次拒修机会。它不删除候选、不改测试结果、不签发通过；
   正确的裁判可以再次提出，执行者在反驳轮还能修复。无人值守下的最坏情况是耗尽剩余回退预算后仍未完成。
   双方都判断错时，仍然依靠独立结果验收。
2. 来源核验通过的拒修之后下游照旧全部重跑，一次拒修约多出三次无影响的阶段调用。
3. 拒修轮与反驳轮各占一次回退，一个交付周期内只容得下一次完整的"拒修、反驳、修复"，且前提是此前没有消耗过回退。
4. 材料摘要随简报变化，在途 feature 的各阶段会重新请求一次 verifier。
5. 确定性层验证不了"AI 是否正确理解了目标"，只验证框架是否把目标送到、是否尊重有来源的判断。
