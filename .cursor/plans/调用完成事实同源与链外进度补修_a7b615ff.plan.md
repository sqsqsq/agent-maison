## 2. 架构约束

- 共用 GoalPhaseRuntime。会话交接与后台进程只在运输处有差别；运输完成之后，业务决定只读共同授权、能力与调用事实。

- “调用完成”不等于门禁 PASS、质询通过、Feature 完成或发布许可。现有统一处置和正式门禁保留职责。
- 进度是事实投影，不成为第二处控制裁决。WAITING、RECOVERY_PENDING、TERMINAL 等既有处置优先；活动子步只能细化“现在等谁”。
- 授权不看模式。预算累计、轮数、显式硬上限、截止、暂停语义和监控熔断不变。棘轮只修正已完成样本的资格，不修改倍率和封顶规则。
- 不新增状态枚举、事件类型、持久字段、注册表、模型特例、监控机制或门禁。新增的局部纯函数/类型只收编既有判据，不成为新的事实载体。

## 4. 实施设计

### 4.1 共享调用完成判据（探测、设计修复、棘轮）

唯一布尔实现放在 **harness/scripts/utils/invocation-completion.ts 的 invocationCompleted**。这是从既有执行器/正式阶段规则抽出的低依赖纯函数，不读取磁盘、不调用模型、不写事件，不引入调用管理器。输入仅为当前已有的 status、exitCode、completion_observed、terminal_failure_observed、timed_out、silent_killed、skipped、spawn_error、kill_reason 等字段的子集；事件的 exit_code 只在边缘适配为 exitCode，不复制算法。

判断顺序固定：

1. 明确 status=waiting 或 failed，以及 skipped，均不算完成；沿原等待/跳过路径，不能把未完成一律转成产品失败。
2. timed_out、kill_reason=agent_timeout、silent_killed、terminal_failure_observed 或 spawn_error 成立时，不算完成。失败事实优先于成功信号。
3. 上述否定事实均不存在，且 exitCode===0 或 completion_observed===true，才算完成；没有这些事实不猜成功。
4. kill_attempted、非零退出和 lingering_pipe 单独都不是失败结论。完成后收尾清理可以进入后续核验；未经完成的外杀不能靠这条获得通过。

会话 passed 经原报告转换提供 exit0，不要求补造 completion_observed；waiting 继续保留 waiting。后台仍由原 adapter 产出完成/失败终态；运输层不得改写 exit1 为 exit0。共享函数的 false 只表达“没有完成资格”，具体等待、失败、跳过或诊断由原调用者的职责决定。

历史事件只读：exit0 且无否定事实的旧记录仍可识别；缺完成字段的 exit1 不被事后推成成功。repairInvocationCompleted 仍先定位原回退窗口和同 invoke 的 end/settled/verdict，再按既有兼容规则形成可用事实；不得删除其旧记录兼容或借另一次 PASS 补证。正式阶段的 dry-run/skipped、验证优先、超时/收口处理维持原语义。

探测生产顺序不变：**原硬 CLI 分类及获准替代政策 → 调用完成资格 → 原答卷解析/判卷 → 原缓存写入**。400/401/403、spawn 错误及已授权替代型号的路径保持；有效答卷压制无关参数 WARN 的既有规则不扩大成压制真实硬失败。完整但答错仍按原 classifier 得到对应能力结论；回显、残卷或无有效信封不缓存。

失败说明使用明确终态错误或现有 spawn/超时/退出事实；没有终态原文时只写这些事实，不再把 stderr 任意末行当原因。完整 stderr 可保留排障，但不新增 WARN 黑名单或第二套错误分类器。

链外设计修复继续执行草稿编写→独立质询→完整检查→发布/重绑→原恢复。完成判据只消除运输误失败；坏草稿、质询否定、越权和未授权发布仍按原出口处理。既有 agent_invoke_end 可透传原结果中已有的完成/失败字段，不新增字段名、事件或记录文件，也不补写旧事件。会话报告/后台结果与超时历史各自保留原始事实。

棘轮不把 chain_phase 当样本归属：辅助调用映射到 plan 展示，不表示其耗时应计入 plan 作者样本。保留原 phase 过滤、grantedHighwaterMs、最大值算法、OBSERVED_RATCHET_FACTOR、显式上限、剩余墙钟钳制和已有提示；本批仅把“确已完成”的样本判断收编。

### 4.2 进度投影读取同一次调用

在 goal-progress.ts 的现有事件读取中形成一个**临时调用视图**，由 buildPhaseSpans 和工作面读取共用；不写入 progress 新字段或持久记录。视图包含已有事实的引用：所属阶段、实际 label、invoke_id、开始/对应结束事件、effective_timeout_ms、既有交接材料引用及可用日志。

- 所属阶段用 chain_phase（有值且属于当前链）或原 phase。阶段窗口限定调用；开始和结束两端都有 invoke_id 时必须同 ID 配对，编号不同不得降级为匿名匹配。任一端缺少 invoke_id 的旧事件，沿用现有“下一个结束关闭最近开始”的配对规则，不补造编号。沿原 resume/回退重置规则，旧调用不得遮住本次调用。
- 带 chain_phase 的链外开始映射为所属未结束 span 的 AGENT_RUNNING/agent_invoke；对应结束映射 AGENT_DONE。不得改阶段 started_at、attempt、已结束状态或原始事件 phase。后续 harness_start、phase_verdict 按原规则回到 HARNESS_RUNNING、PASSED 等状态。
- 后台普通阶段仍读原日志；链外后台读本调用 phases/<label>/<invoke_id>/agent-output.log。日志、mtime、bytes、phases_summary.evidence 和硬超时取自同一次调用，不能一处用 label、另一处用所属阶段。
- 会话交接使用现有请求/报告引用表达工作证据，不假定有后台日志；没有日志时 agent_output_log=null/信号missing，不借旧阶段日志，不把静态请求文件的 mtime 当流式输出。实际工具流的既有用途不变，不新增日志协议。
- vision-canary 无日志时同样按 missing。若探测发生在 phase_start 之前，或所属 span 已结束，不伪造阶段开始、不重开 PASSED span、不调整 run_start 时机。
- 有本调用 effective_timeout_ms 就读它；旧调用缺字段时沿现有 fallback，不借另一 invocation 的已授予超时。进度中的超时仅观测原截止，不能重新授予预算。
- computeLiveness 保留控制面心跳/锁、实际 output_delivery 和软硬阈值。流式日志真的过期仍报 SUSPECTED_STALL；会话无日志或 buffered 输出不得被假定为停滞，也不能因此清掉真实死进程/超时信号。
