# 实例扩展的动态启停与生效阶段选择

**启用成功的判据是提供方声明的步骤已经产生预期效果，宿主选择的绑定已经可以消费这些效果。停用成功的判据是相应绑定已经撤下，本次启用负责的效果已退出，保留项均可解释。** 本文是 [5247db24](实例扩展协议_安装启停与真实时机消费_5247db24.plan.md) 的增量草案。安装来源、既有时点、请求权威、业务产物归属和适配器入口继续沿用该协议。退出规则承接[总纲 §11.2](../goals/复杂能力建设目标_能力架构蓝图到部件演进与变更单元闭环_75411223.goal.md#112-稳定内核与-provider-接缝语义)。

## 1. 改善的场景与收益

| 用户提出的场景 | 现有行为 | 增量和可观察收益 |
|---|---|---|
| 外部提供方要查包结构、可注入的阶段和退出责任。简单 Skill 的作者只有目录和用途说明 | 发布件已有协议说明和两份规范，当前安装命令要求来源目录有清单 | 提供方可从一个随包入口独立开发。简单扩展由接入方代写最小声明，能从回执核对选择的阶段及依据。 |
| 知识扩展随包交付原料，须在宿主跑脚本才能得到 `knowledge/` 下的文档 | 加载器检查绑定引用的文件。首次安装时，待生成文件还不存在，该绑定无法投递 | 清单先声明哪一步生成哪份文件。启用时运行脚本并按宿主选择登记阶段，真实作者能收到生成正文。停用后新作者收不到它，框架能清理自己的生成物。 |
| 脚本扩展随包交付 `package.json` 和锁文件，需要在自己的安装目录安装依赖 | 目标脚本存在即可通过文件引用检查，缺模块可能直到执行脚本才暴露 | 启用按顺序装依赖、运行实际检查，再开放入口。安装失败能重试，重启用无需人为补目录，退出能定位依赖树及需要关闭的资源。 |
| 钱包同时有 Story、UX 和后台受管作者 | 既有安装文件有归属，已签请求继续使用安装副本。新增主动清理后，旧请求可能在执行中失去文件或服务 | 动态退出先停止新调度，再等待使用旧效果的请求。只影响被操作的能力，保留宿主手写资料和已交付蓝图。 |

复用 [extension CLI](../../harness/scripts/extension.ts)、[生命周期实现](../../harness/scripts/utils/extension-lifecycle.ts)、[请求占用判定](../../harness/scripts/utils/extension-requests.ts)及现有时点目录。提供方交付步骤和默认绑定，宿主维护者授权并选择阶段，框架管理入口执行与补偿，各业务入口消费生效后的绑定。按能力记录执行结果是为了处理失败重试和有据清理。管理操作发生时才执行步骤。

## 2. 包作者写什么，宿主选择什么

### 2.1 提供方从哪里开始

提供方从发布件 README 或管理 Skill 打开《Extension 接入协议》。将目标宿主已有的 `framework/docs/evolution/extension-protocol-v1.md` 整理为该入口，供外部作者随发布件获取。[现行协议说明](../../docs/evolution/extension-protocol-v1.md) · [管理 Skill](../../skills/project/extension/SKILL.md)

| 作者的问题 | 协议入口给出的答案 |
|---|---|
| 要交什么，最低写到什么程度？ | 标明本版支持的清单版本与兼容边界，给出最小包目录、可手动调用的 Skill、单项知识绑定和一对动态启停步骤的完整示例。字段和类型以[清单规范](../../specs/instance-extension-manifest.schema.yaml)为准。 |
| 哪些阶段可以接入，谁会收到？ | 指到本发布件[时点清单](../../specs/lifecycle-hooks-schema.yaml)中的 `contribution_timings`、`hook_events`、`hook_contributions`，说明如何查实际触发位置、消费者、资源种类及 `phase` 约束。Feature 阶段以目标宿主启用的 workflow 为准。 |
| enable、disable 各自保证什么？ | 按第 3～5 节给出触发顺序、命令输入、文件归属、关闭与回滚责任、在途等待和回执示例。示范如何用 `inspect` 查实际绑定，以及如何在消费者处核实投递。 |

示例放在随包说明内或链接发布件内实存的文件。第三方可独立使用发布件。开发仓的 OpenSpec 供框架演进使用。时点名称和许可资源沿用加载器读取的清单。

### 2.2 成品包与简单扩展怎样接入

成品包直接使用作者提供的 `manifest.yaml`，格式损坏或版本不支持时给出对应诊断。对于没有清单的本地目录，`/extension` 可以读取 `SKILL.md`、README、实际资源及用户的本次要求，代为整理出目标版本支持的最小清单与目录布局，然后调用同一安装器。当前已发布的安装器要求本地来源目录带清单，按描述整理输入属于本次增量。[现行安装入口](../../harness/scripts/utils/extension-lifecycle.ts)

- **选择依据。** 在目标宿主支持的时点与资源范围内，优先采用用户明确的选择，其次沿用已保存的宿主选择，再按提供方的清单或明确使用意图取默认值。例如 README 写“编码前交给作者”，用户要求“这个项目只在评审前用”，最终投递给 `feature.before_phase_work@1 / review`。新装回执说明所用资源、最终消费者和依据，重装复用原身份及既有选择。
- **简单接入。** 只有可识别的 `SKILL.md` 且用途是点名调用，就登记手动入口。只有一份 `rules.md`，用户或提供方描述明确“在编码作者动笔前读”，就生成 `knowledge` 绑定和 `phase: coding`。“编码规范”这个标题无法单独确定自动投递意图。可手动使用的 Skill 先按手动接入。若请求明确要自动挂接且仍缺阶段，只问决定投递所需的那一项。
- **动态效果。** 初装或启停需要执行命令时，可帮助作者把明确给出的命令、输出及非文件效果的关闭方式整理成第 2.3 节的契约。仅看到 `package.json` 或 `install.sh`，不足以授权执行或推断清理路径。关键项缺失时列出具体缺口，动态步骤保持未执行。整理输入可使用调用期间的本地暂存目录，原始包保持只读。安装后的身份、选择和归属仍由宿主原清单承担。

### 2.3 动态步骤与生效阶段

草案使用扩展清单 `2.1` 添加可选的 `activation.<能力ID>.steps`。框架发布窗口仍为 `3.1.0`。步骤按数组顺序执行，使用稳定 ID、工作目录、可执行程序和参数数组。`outputs` 列出本步独占创建的文件或目录，路径统一相对扩展根。会产生非文件效果的步骤必须同时声明 `undo` 命令及参数，执行和撤回共享本次实例标识。例如启动本地监听的步骤配对 `undo: [node, scripts/stop-listener.mjs]`，退出时只关闭本次建立的监听。以下是知识扩展的清单示意。

```yaml
schema_version: "2.1"
name: wallet-rules
provides:
  skills: [wallet-rules]
bindings:
  wallet-rules:
    guide:
      at: feature.before_phase_work@1
      phase: coding
      kind: knowledge
      ref: knowledge/wallet-rules/guide.md
      enabled_by_default: true
activation:
  wallet-rules:
    steps:
      - id: build-guide
        cwd: skills/wallet-rules
        run: [node, scripts/build-guide.mjs]
        outputs: [knowledge/wallet-rules/guide.md]
```

- **发现与执行分开。** 安装能先解析步骤、锁文件和静态脚本，认出 `guide.md` 由 `build-guide` 产生。启用前允许声明这样的输出。步骤成功后重新解析实际文件与绑定，作者才能收到正文。没有生产步骤的坏引用沿既有诊断处理。
- **阶段在启用时确定。** 来源 `bindings` 提供默认 `at/phase`。宿主可以说“启用钱包知识，这个项目只发给 review 作者”。管理入口在原 `installations.<能力ID>` 下按绑定 ID 保存宿主覆盖，向步骤传入解析后的选择。建议在原 `enable` 上增加 `--at`、`--phase`。有多个候选绑定时须按 ID 定位要调整的一项。校验复用[已发布时点、消费者和资源种类](../../specs/lifecycle-hooks-schema.yaml)，检查目标 workflow 的阶段。覆盖合法时该例只投递给 `review` 作者；升级后覆盖已不兼容时点名受影响绑定，保留选择供维护者调整。
- **整项与单条绑定。** 能力级步骤由整项启用执行一次。只开关或改投一条绑定时保留其他选择和共用依赖。关闭总开关后单调绑定只保存选择。改变时点通常只需重新投递已有资源；若使能步骤使用了改变的阶段作为生成输入，则按同一能力的安全退出、重新启用流程更新产物。用户明确要求整项启用并指定阶段时，在同一次管理操作内应用选择。
- **兼容。** 新框架继续读 `1.0/1.1/2.0`。静态能力沿用原有入口、开关和资源归属，Story、UX 无须补空步骤。新版管理入口对静态和动态能力都按第 3 节处理在途停用；这是对旧停用回执的明确增量。包声明动态步骤，或宿主首次为旧包的合法绑定保存新时点覆盖时，才需要对应的新格式。管理入口先检查目标发布件的读取能力，再迁移宿主清单或导入文件。已有宿主选择、手写资料和已签请求继续有效。[现行清单](../../specs/instance-extension-manifest.schema.yaml) · [现行 OpenSpec](../../openspec/specs/instance-extension-management/spec.md)

## 3. 管理操作何时触发

| 入口 | 对用户的承诺 |
|---|---|
| 首次 `install` | 从第 2.2 节的规范输入导入后，默认在同次操作调用整项 `enable`，按本次有效选择启用绑定。提供“只安装，暂不启用”（建议 `install --no-enable`），此时保留包，等待显式启用。启用失败回执区分“包已安装”和“能力未生效”。 |
| `enable` | 先解析选择、列出将执行的命令，按顺序运行步骤并确认效果，最后公布手动入口和选中的绑定。重复启用同一版本、同一输入且效果完好时复用已有结果。任一步失败，停止后续步骤并按第 4 节逆序回滚。 |
| `disable` | 整项停用先撤新绑定与手动入口，单条停用只撤该绑定的新调度。列出仍占用目标的请求 ID 并等待退出，期间保留已签资源。占用结束后按步骤逆序清理应撤的效果，保留其他绑定仍在使用的效果。清理结束才报告停用完成。重复停用可继续未完成的退出。 |
| 同来源重装与升级 | 同版同内容保留选择并幂等重用。新版本先预检来源、时点、写入冲突及命令，再按“停用旧版 → 替换安装资源 → 启用新版”执行。旧版的关闭程序和归属资料保留到退出完成。宿主原已停用的能力升级后继续停用，新增自动绑定默认关闭。 |
| `uninstall` | 复用 `disable` 并等到退出完成，再按既有指纹与共享归属清理安装副本和桥接入口。停用已完成时跳过已撤回步骤。用户改过的文件、来源目录和已交付的需求、UX、蓝图均保留并说明。 |

**在途等待。** 停止接新请求与实际释放资源分两步。对受影响的能力、绑定或资源，复用 5247 的受管蓝图/CU 作者签发原件、有效执行窗、`run_end` 和旧锁判定。报告活跃请求 ID 及保留资源。已结束、锁已失效的请求仅提示。覆盖停用与签发并发时的边界，使已取得旧资源的签发计入保护，新签发读取已关闭的选择。等待期间释放管理锁，其他能力照常工作。沿用现有可重试回执，原管理调用等待交回后继续，调用中断后重试同一命令也能完成。直接交互会话沿用 5247 的非受管边界，在回执标明可检查范围。

**升级失败的落点。** 先暂存并核对待替换文件。以宿主清单提交新版安装身份为界：此前替换失败，恢复旧安装文件和原选择，已退出的旧能力走原启用步骤恢复并如实回报结果；此后新版启用失败，撤回新版此次效果，保留“新版已安装、启用失败”，列出重试原因。恢复只保留这次操作涉及的文件及记录。

## 4. 如何执行、逆序退出和恢复

1. **先显示，再运行。** 首次执行前，管理入口列出能力、版本、实际工作目录、按顺序解析的命令和将写入的资源。人读 CLI 与 Agent 在子进程启动前展示，`--json` 保留最终单个结构化回执，可在 stderr 输出预告。沿用本次管理操作已有授权。后台受管作者只能 inspect/verify，连带执行使能或退出的 install、升级和卸载都经过同一管理写权检查。凭据不进入命令回显。
2. **限定执行边界。** 每步只在本能力拥有的安装目录或私有暂存区运行，可写位置限于其私有工作区及声明并核对归属的输出，例如 `knowledge/wallet-rules/`。npm 在本能力的包目录执行，缓存、临时写入和日志归该能力管理。框架负责发布产物和修改宿主清单。沿用[路径及文件归属检查](../../harness/scripts/utils/extension-files.ts)，检查真实路径、已有文件和其他能力的所有权。对 Node、npm 及其子进程，执行端必须能实际约束写入边界；仅设置 `cwd` 不能提供这个保证。先在目标 Windows 环境验证该路径，缺执行条件时只对该动态能力报因，静态扩展继续工作。
3. **文件与非文件效果各有退出依据。** 框架在本步专属输出区核对实际生成的文件/独占目录，自动登记路径、步骤和生成指纹，再发布到获准的目标。安装条目中区分导入的源文件与启用生成物。停用自动撤回本轮生成且归属、内容相符的文件，安装的源脚本留到卸载。大依赖树按专属目录记归属，在管理操作中校验，日常请求不遍历 `node_modules`。宿主改写、共享或归属不明的内容保留并标明路径。非文件效果须由提供方声明能重复调用的关闭命令及可定位本次实例的依据。
4. **回滚涵盖失败步骤本身。** 每步启动前在原安装条目原子记录正在处理的步骤与可恢复定位，成功后登记实际效果。抛错、非零退出、子进程中断或效果校验失败时，先撤下该步已经产生的部分效果，再逆序撤销先前步骤。对带 `undo` 的步骤先关闭服务，再清理它的文件，避免删除后找不到关闭程序。启用过程中维持未调度。补偿成功后保留包和失败原因；补偿本身失败则列出残留和重试动作，继续保持不调度，直到清理有据。能在命令退出前产生外部效果的步骤，应可用预先确定的实例标识查回和撤销。无法保证退出的副作用不符合这份动态启停契约。
5. **复用原有锁与记录。** 管理写入、同一能力的重复或并发操作沿[宿主清单锁与原子写入](../../harness/scripts/utils/extension-lifecycle.ts)串行认领效果，进程中断后重试从原记录和实际结果继续。异步步骤执行完毕才可释放对应操作的所有权。每项能力分别提交结果，单项失败只撤本项，多能力安装回执逐项列出成功、失败和保留项。全部持久事实放在 `paths.extension_dir/manifest.yaml` 的原安装条目及其实际资源中。

## 5. 检视、命令回执与漂移

`inspect` 展示三个用户可区分的结果：**已安装未启用、启用失败、已启用**。同时列出宿主选择的时点/阶段、已执行步骤及产物、失败原因、在途或待清理详情。启用失败且回滚干净时实际未启用；仍有补偿待做时明确展示残留。等待在途退出时同时写明“新请求已停用，资源仍由哪些请求占用”。继续沿用 `available / scheduled / evidenced` 表示贡献的证据强度，历史请求按原件解读。[现有检视器](../../harness/scripts/utils/extension-inspect.ts)

原先设想的“就绪条件”用作**启用后的漂移检查**。例如已成功启用后知识文件被删、npm 模块不可解析，检视指出上次结果与当前事实的差异、受影响的绑定和修复入口。首次尚待生成的知识、尚待安装的依赖都可以进入启用流程。`inspect / verify` 保持只读，启用后的轻量校验及显式修复复用同一判据。下一次管理端 `enable` 可补缺并复核；现存人工改写保留并报告冲突。

## 6. 交付与验收

实施顺序为协议/兼容读入 → 管理执行与补偿 → 在途保护、投递和检视 → 宿主验收。更新既有 [instance-extension-management OpenSpec](../../openspec/specs/instance-extension-management/spec.md)、[扩展包规范](../../specs/instance-extension-manifest.schema.yaml)、[发布件说明](../../docs/evolution/extension-protocol-v1.md)、[管理 Skill](../../skills/project/extension/SKILL.md) 和 [迁移说明](../../MIGRATION.md)。步骤属于管理生命周期，业务消费沿[既有时点目录](../../specs/lifecycle-hooks-schema.yaml)。本期使用本地来源、已有管理动词及真实宿主发布件，不增加常驻插件服务。

**接入协议可独立使用。** 从解压后的发布件 README 找到提供方协议，仅凭随包规范与示例准备下述样例并安装。另用无清单的本地资源走正常 `/extension`，核对安装回执、原件指纹和实际消费者。手动 Skill 可点名使用。README 指明编码阶段的知识会投递给编码作者，用户改为评审时只有评审作者收到正文。描述含糊时保留手动入口或列出待选阶段。带未说明副作用的脚本报告缺口且未执行。缺时点或格式损坏的显式清单应保留原诊断。

在保留 Story、UX 和原有知识的隔离宿主集成校验发布件，以两份独立样例从正式入口实跑。**K（知识）** 用实际 Node 脚本将内置材料生成到能力专属的 `knowledge/` 目录，以作者收到的正文验证投递。**N（npm）** 携带包清单、锁文件和本地依赖 tarball，在安装副本内真实执行 `npm ci`，用正式脚本实际加载该依赖，核对模块路径。N 另含一个可关闭的本地监听，用它证明非文件效果真的退出。下表每行均在 K、N 两例上验证，保留原命令/回执、前后资源及实际消费结果。

| 验收 | K、N 共同通过条件 |
|---|---|
| 首装和只装后启用 | 首次默认启用，预告先于脚本运行，命令实际执行。“只安装”时无生成物、依赖树或监听，显式启用后二者分别可读、可调用。K 将默认 `coding` 改为 `review`，新阶段收到正文，原阶段不再接收；N 从本地安装的模块执行业务。 |
| 中途失败和故障隔离 | K 写出部分文件后失败，N 安装依赖并启动监听后令后一步失败。两例均逆序回滚，K 无半成品，N 依赖和监听退出。检视给出“启用失败”、失败步骤及回滚结果。一次补偿失败或进程中断后，重试能继续清理。有一项失败时相邻健康能力可正常使用。 |
| 停用、重启用、漂移 | 完整停用清理可归属的全部效果，再启用可以重复得到相同结果；重复 enable 不重复启动监听或生成副本。分别移走知识或模块后，inspect 只报告漂移，显式修复恢复。宿主改过的内容保留并指出。 |
| 在途停用 | 受管请求已绑定 K 的知识或 N 的动作资源、仍未交回。此时停用显示请求 ID，新签发已撤绑定，原签发还能读取知识或执行原脚本。交回或有效运行结束后完成清理。失效锁只提示，健康扩展可另行管理。 |
| 升级与卸载 | 两例均从启用的 v1 升到 v2，观察旧效果先退出、新资源替换、新效果才参与；旧版已停用时保留选择。新版启用失败按第 3 节收口。对启用中的能力执行卸载，先完成退出，再删自有副本。原始包、宿主改写、已交付产物和另一能力均保留。 |

另外用小型定向用例覆盖命令先展示、后台作者启停被拒、同能力并发和子进程写入其他能力目录被拒。用同一宿主复验旧 2.0 UX 的开关/读稿和旧 Story 共存。两个动态样例保留为开发期夹具。实现收口按当前仓规运行 `npm run openspec:validate` 和仓根 `npm test`；本次计划评审检查 frontmatter、引用与文档差异。
