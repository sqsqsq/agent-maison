# 测试基建提速

## 1. 目标、前置条件与权限边界

用户提出三个要求：函数级只验证函数可靠性，能力级验证端到端能力；每轮开发结束后按实际影响制定测试计划，无关的不测，能合并的一起测；可并行的工作并行，只有实际存在共享约束的工作串行。

本计划先解决测试基础设施问题，不迁移、重写、合并或删除业务用例。目标是完整全量约 **30 分钟**，只改函数级代码时按需测试在**几分钟**完成；是否达到以实测为准，不能通过漏跑、少断言、降低门禁或缩短业务时限达标。

实施前置条件：本 plan 评审通过，且 [P3 入口切换与旧编排退役](持续执行重构P3_入口切换与旧编排退役_0ce4a781.plan.md) 已提交。记录该提交为基线 **B**，不以当前混合工作区或更早的 R4 源码替代。若实施时版本窗口已变化，先按当时的根 `package.json.version` 调整本 plan 窗口归属，不修改 P3 的内容。

当前仅起草：只读现有代码、日志与结果文件，不跑测试、编译、基准或依赖安装，不改源码、测试、配置和其它计划，不操作 P3 进程，不还原、暂存或提交其未提交改动。唯一写入是本 plan 文件，使用既有 `.cursor/plans/`，不新建目录。

P3 提交后，本计划一次实施、统一验收。同一工作区同一时段只能有一批测试/runner 改造；计时安排在机器空闲时，不能停掉别的任务来制造空闲。P4 或其它任务如正在使用相同文件或占用测量资源，应协调时段，不并行改写或混算计时。

本计划不承担生产编排改造、真实模型/CLI 服务质量验收、真宿主或设备操作，不执行发版。生产门禁运行方式若需改变，按 §4.2 单独提交影响说明，由用户决定。

## 3. 用例组并行调度

### 3.1 调度单位与真源

将任务从“一个套件”改为“一个可独立执行的用例组”。单用例是默认组；共享一次 setup/run/teardown、一次运行中做多处断言的块保持一个组，其所有 `caseNames` 一起执行、计时、汇总，不为并行重复该运行或拆散前后依赖。

用例集合来自 **B 之后当前代码的注册与枚举**，不从历史 `executionTimings` 反推全部测试。对已有 cases 数组及共同执行块补最小的只读枚举、精确组选择和计时接线；不改业务输入、断言含义、异常期望或执行块内部顺序。当前不支持选择的套件先是一个完整组；慢套件须补齐必要的执行边界接线，不能用“旧接口不支持”保留所有已知长尾。剩余不可拆组在报告中说明原因。

分派复用 `suiteId` 和组内用例名，必要时用同名出现位置区分，避免新造另一套全局用例编号注册表。分组必须支持“只枚举、不执行用例”，含加载副作用的模块保持保守整组。内部采用精确组/用例集合匹配，不用包含关系猜测分片，外部既有 `--filter` / `--case` 语义保持兼容。

历史计时只作优先级提示：有数据时按组时长从长到短派发，空闲 worker 立即领取下一组；短组可合批以摊薄加载成本。新组或缺少计时的组按确定顺序优先探测或使用套件估计，不跳过、不报错停工、不补造时长。结果继续记录逐组耗时，复用或替换现有 `unit-suite-timings.json` 的用途，不同时维护两份手工计时真源。

### 3.2 串行边界与隔离

在现有登记处显式标出串行组和原因：共享进程内全局状态、必须连续使用的 fixture、固定输出路径或端口等。共享执行状态的用例放在同一进程内顺序执行；跨组使用同一固定资源的任务互斥，不能只限制组内顺序却让两个冲突组并行。无关联的组继续并行，不因少数共享用例把整轮串行化。

保留当前 worker 私有 TMP、trust 根与临时宿主隔离。分组后 stdout/stderr、失败报告、覆盖目录也要归属于各组，父 runner 统一合并；不能让多组覆盖同一报告文件。进程内全局状态只在独立进程间隔离，不在同一个进程里对既有用例随意 `Promise.all`。

保留 worker 非零退出、超时、加载失败、结果后异常、未派发和清理失败的现有结果语义。收到 IPC 结果不等于进程已成功结束；不能因改调度而丢失失败，也不能用自动重试把偶发失败洗绿。回收只针对本轮产生的进程与临时根。

实际墙钟下限为 `max(累计工作量 / 有效并发数, 最长不可拆组, 共享资源串行链)`，另加启动和争抢开销。拆分充分时长尾由最长套件降为最长独立用例/共享执行组；不宣称存在共享约束时仍能降到最长单条断言。

### 3.3 并发数与 fixture

不把 24 逻辑核等同于 24 worker 的最优值。实施阶段先在代表性慢组上比较小规模候选（例如 8、12、16、24），记录父进程及后代的 CPU 使用、峰值内存/工作集、墙钟、失败和串行等待；出现内存压力或吞吐恶化即停止加并发。选定默认值后用全量确认，保留 `--workers` 手动覆盖，不建设自动调参服务或长期性能平台。

`run-tests.ts` 中 fixture 也是独立任务候选，能确认独立临时目录和无共享状态的可复用同一进程调度能力并行；确有共享约束的显式串行。unit 和 fixture 使用同一整轮并发预算，不能各自开满形成两倍负载。不迁移 fixture 内容，不把 fixture 从全量中消失当成加速。

## 4. 启动成本与等待时间

### 4.1 测试专用启动方案的受控 A/B

先在 B 基线后、机器空闲时，选一条有代表性的 goal run 用例，用现有进程/事件计时加必要的临时观测，拆出门禁 ts-node 加载、PowerShell guardian 的启动与 `Add-Type`、身份查询、假 agent、固定等待/轮询和门禁实际执行的耗时。标明重叠区间，不能把并发窗口相加当墙钟；无法分离的部分列出测量缺口，不建设长期探针系统。本轮起草不实测。

据此比较下列测试侧候选，保留当前 transpile-only 启动作为参考。每个候选必须列出实际启动命令和作用进程；只优化 worker 加载时，收益范围就只写 worker 加载：

| 候选 | 实施边界 | 必须计入的成本与兼容性 |
|---|---|---|
| ts-node SWC | 对测试入口及 worker 显式使用 `--swc`、测试专用 tsconfig 或注册选项；若胜出，`@swc/core` 仅放仓根 `package.json.devDependencies` | 这些进程的加载及其导入模块转换；异常、动态 import、JSON/资源定位与 source map。显式由生产入口启动的门禁不自动获得 SWC |
| 测试前预编译一次 JS | 一次生成测试专用产物，由测试入口及 worker 运行 JS；覆盖其加载的源码、测试和相关 profile 代码 | 编译和资源准备也算墙钟；`__dirname`、相对资产路径、模块发现及原始 TS 路径映射。仍由生产入口启动的 `.ts` 门禁保持原状 |

SWC 的开关和依赖以 [ts-node 官方说明](https://typestrong.org/ts-node/docs/swc/)及仓内安装版本为准。已核对 ts-node 10.9.2 的 `DEFAULTS` 没有 `TS_NODE_SWC` 环境变量开关，不能用不存在的开关假设跨进程生效。测试专用依赖从仓根安装并由测试接线明确解析；不放进消费者会执行 `npm install` 的 `harness/package.json.devDependencies`，根级 devDependencies 按现有发布 sanitize 删除。

独立 `typecheck` 保留，不能用 SWC 或 JS 执行代替类型检查。预编译不得直接用包含报告快照和故意错误 fixture 源码的宽泛范围；沿用 `tsconfig.typecheck.json` 已明确的源码/测试边界，产物写入现有 `harness/dist/` 排除范围。

A/B 固定相同源码、用例、worker 数、环境和覆盖采集设置，使用少量包含真实入口及子进程的代表组，记录冷/暖启动及端到端结果；不只量空进程。不做全部方案、全部 worker 数、全部用例的笛卡尔积。差异接近噪声时只补必要复测，语义等价前提下选实测更快、维护成本合理的一种，移除未选方案的日常接线。

### 4.2 真实门禁与消费者边界

默认优化范围是**测试侧能直接控制的入口、worker 和测试 helper**。门禁仍执行同一实现、参数、解析、授权和判定，不 mock 检查结果，不把能力测试改成函数调用。现有 `runHarnessPhase` 写死 ts-node bin、生产 `--project` 和 `harness-runner.ts`；用仓库本身作为框架根时，切换顶层 worker 不能改变这些门禁子进程的加载方式。不得预设“测试环境”足以绕过这个边界。

通过测试专用启动接线/构建产物实现上述测试侧优化，不在生产共享 tsconfig 中直接启用 SWC，不改 `runHarnessPhase` 的生产启动路径，不取消 guardian、身份绑定、`sanitizeSpawnEnv` 或进程完整性检查，不注入 `NODE_OPTIONS` 绕过入口。若成本大头落在这些测试侧够不着的路径，带 §4.1 的实测数字和具体受影响进程单独报告，其他调度、选测和测试侧优化继续推进，不等待该决定。

若确实需要把方案扩到消费者使用的生产门禁进程，单独说明：预计和实测收益、`@swc/core` 的安装与平台要求、依赖落点、发布件 JS/资源体积及源码定位、升级/回退影响。用户决定后才能扩展，不将其暗含在本 plan 的测试授权内。消费者仍按发布件集成，只在 `framework/harness` 安装运行依赖。

### 4.3 固定等待与轮询

盘点测试 setup、假 agent、退出等待和轮询的固定值，优先复用现有参数或测试 helper。把真正用于测试节奏的等待/间隔变为显式可配置，测试取较小非零值；生产默认值、业务截止时间、授权、预算和超时判定不变。

不全局缩放时钟，不把“验证超时行为”的等待删掉，不把等待结束当作完成证据。能等真实状态/事件的已有路径继续用状态/事件；必要的时间负例使用独立明确的小时间窗。若需给生产工具补可选间隔参数，只做最小参数化、保持缺省行为，验证未传参数时与 B 相同。

## 5. 两层登记与执行边界

在 `run-unit` 的同一注册来源为每个核心套件及自动发现的 profile 套件产生明确的 `layer: function | capability`，不建平行测试目录或第二注册表。混合套件整体保守登记为 capability，不按文件名里的 `unit` 判断层级。

| 层 | 目标契约 | 本次基建动作 |
|---|---|---|
| function | 一次用例执行只在一个 worker 进程内；不启动 goal run，不启动 node/ts-node 或其它子进程；验证函数的输入输出和边界 | 仅按执行事实登记现有套件，runner 机械检查执行边界；本次不检查或改造历史夹具来源 |
| capability | 经真实入口和真实门禁进程验证能力；脚本化假 agent，不联网，不用真模型或设备；一次运行做多处结果断言，不钉内部步骤顺序 | 保持真实入口、进程与现有断言，登记覆盖归属并参与组调度和选测；真模型、真宿主验收不进入日常开发循环 |

“单进程”指 function 用例自身不创建子进程，不限制外层调度器启动多个独立 function worker。机械检查放在测试 runner：加载测试前识别实际 goal 入口依赖/调用路径，拦截 `child_process` 的 `spawn/exec/fork` 及同步变体（含经 helper 间接调用），检测到误标按现有测试执行错误报告，修正 layer；不能悄悄替它跑子进程并仍统计成 function。直接进程内调用 goal 入口也必须被识别，不能只检查 `spawn`。复用依赖图与入口信息，不为此新建生产注册表。

本次交付是**按执行事实分层登记与执行基础设施**，不是“所有历史用例已完成两层迁移”的声明。起 goal run 或子进程的混合套件整体归 capability，不借本计划重写业务用例，也不把重新贴标签当作能力验证已改好。真实事件/产物来源的要求及其核对留给 §10 的后续迁移计划，本期不盘点“手工事件输入”或建立迁移清单。新增基础设施自测遵守执行边界。

`run-tests.ts` 的 fixture 回归保留独立入口，其测试对象按 capability 纳入选测与全量统计，无需为实现登记而搬入 `unit/`。真实模型和真实宿主验收保持原有独立责任，不由这些脚本替身结果代替。

## 6. 按需测试计划

### 6.1 输入、输出与逐组通过事实

新增轻量选测工具，复用现有 runner 注册/选择模块和结果 JSON；提供生成计划与执行计划入口，不建设常驻服务。

输入包括：上次完整运行的受测输入及逐组结果、此后有效的逐组通过结果、当前 Git 变更、注册表、TypeScript import 图，以及 §6.3 的逐组执行/读取映射。差异覆盖相应受测快照之后的已提交、staged、unstaged、未跟踪输入及删除/重命名两端；不能只看 `HEAD` 的未提交 diff，也不能只扫描 TS 而漏掉被读取的文档。

在现有结果中记录“上次完整运行的输入快照 + 各组通过/未通过事实”。完整运行有红也保留这个增量起点；未通过、未执行或因中断缺结果的组每轮必选，在真正通过之前不计为已过，其余有效通过组照常增量。失败不推进该组通过事实，但不让一条旧红阻止其他组复用；当轮仍报告失败，不能借增量起点把红基线变绿。只有结果完全缺失、历史无法对应或公共格式不可读时回退完整全量建立起点；局部缺结果只补相应组。

受测输入摘要**开跑前**取得，覆盖 Git 纳管及未跟踪的候选输入（已确认仅为测试输出的产物除外）；结束后用同一范围再比较。运行中变化或新出现的输入不得以结束时字节冒充已测字节，受影响组不推进通过事实，变化留入下一轮计划；其余有效结果保留。实际读取了未纳入开始快照的仓库输入时，也保留该影响为待验证。这里只处理可观测的工作区漂移，不建设持续文件监控或防篡改系统。

这些信息只附在既有仓内结果/派生缓存中，不写 `~/.maison`，不增加独立状态库或签名清单。全量后的增量成功只更新实际执行且输入未漂移的组，并保留未覆盖项；“本轮按需计划全过”和“已完成一次完整全量全过”分别报告。

输出使用易读报告和可执行结构数据，逐条包含：变更文件、选中的套件/组或 fixture、layer、选择原因（import 链、执行/读取命中、覆盖未知、既有未通过项或保守回退）、附加项、已复用的有效通过项。明确输出免测依据及整体范围；不能给“看情况测一下”的自由文本建议。

工具计算的必选集合是执行下限，开发者只可加测，不可删除。执行入口按当前差异重新核对/生成集合，再与加测项取并集，不能靠编辑计划 JSON 或过滤参数删掉必选项。发现计划过时自动重算，不新增人工确认或阶段停机原因。

### 6.2 选择规则（混合改动取并集，共享输入规则优先）

| 改动 | 必选范围 |
|---|---|
| 仅明确免测清单内的路径，且无残留未通过项 | 不跑测试；清单中的路径须有 §6.3 的无消费者依据。不能按“文档/plan/报告”名称或 `.md` 后缀直接放行，必要的 diff/plan 校验仍保留 |
| 仅独立测试文件 | 跑对应测试套件/fixture；不因为改了测试名称而重跑所有测试。共用 helper、runner、注册机制变化不适用此窄规则 |
| TS 生产源码 | function：按 import 反向闭包及文件读取、目录枚举命中选测试；capability：按同一组映射里的执行文件、文件读取及目录枚举命中，并结合 §6.3 的局部 import 更新选组；两层均补相应覆盖/读取关系未知组，加一次适用的 typecheck。只读取源码文本而不执行该文件的能力组也必须选中 |
| 文档、plan、JSON/YAML 等非代码文件，已确认仅由测试侧消费 | 用 §6.3 的文件/目录读取关系选择两层中命中的组，并补读取关系未知组；文件名或目录成员变化也算命中。不能只靠 V8 覆盖或 import 图 |
| 部分组覆盖缺失/不完整，或局部测试实现变化使该组记录失效 | 仅这些组标覆盖未知；生产代码或运行输入变化时必选这些组，其余组继续按有效映射选；function 同理使用其可靠 import/读取关系 |
| 新生产文件未进入映射、整张映射缺失或全局失效 | capability 全量，function 按可靠依赖图和读取关系选；这些关系也无法建立时 function 全量。新文件的静态推导不作为本期必做优化 |
| 规则 YAML、profile 配置、模板、skill 等生产非代码运行输入 | capability 全量；function 按测试侧读取关系命中，读取关系未知的 function 也纳入。profile 中普通 TS 源码仍按 TS 规则；不依赖测试 worker 的读取记录推断门禁子进程读取范围 |
| runner、共用 helper、依赖及锁文件、tsconfig、测试调度/构建配置 | capability 全量，并选受影响 function；无法收窄影响时 function 全量。保留必要 typecheck 和既有相关脚本校验 |
| 既不在有依据的免测清单、也无法可靠确定消费者的文件，或动态依赖/删除/重命名影响无法解析 | 视为未识别输入，扩大到可能消费它的两层；无法收窄则两层全量，不能按“零命中”不测 |

用已安装 TypeScript 的解析/模块解析能力建立图，覆盖静态 import、export-from、可解析的 require/import()，沿当前及相应受测快照的删除/重命名前依赖关系追溯。动态路径无法解析时只在受影响范围内保守扩大；不引入完整代码图服务。文件粒度足够，大文件改一点选中很多能力场景是预期结果，不增加行级覆盖、符号影响或复杂评分。

### 6.3 按组的执行与读取映射

完整全量运行开启 `NODE_V8_COVERAGE`。按 [Node 官方说明](https://nodejs.org/api/cli.html#node_v8_coveragedir)，该变量会传播到子进程；实施仍须核对各启动处没有替换 env 或清空它。采集父执行组及真实门禁后代的覆盖，不依赖“父进程有报告”推断后代已覆盖。

**执行与非代码读取的来源。** 每个执行组使用独立覆盖目录，子进程继承该目录，合并为“组 → 执行过的仓库文件”。同一次全量中，在**测试 worker 内、加载测试模块之前**记录文件读取、存在性/属性查询和目录枚举（含同步、异步、promises、流入口及失败的不存在路径）；归并为同一组映射中的文件/目录输入。两层均采集，组间共用的模块加载读取保守归给相关全部组。目录枚举关联成员增删/重命名，不能只记录现存文件，否则新增被扫描文件会漏选。不记录文件内容，不改生产，不加 `NODE_OPTIONS`。

共享一次运行的多个断言共用映射，不伪装成逐断言精度。若多个场景无法可靠分开，将文件集合归到这些场景的并集。门禁子进程的 `fs` 读取不在上述测试侧观测内，不能声称已采集；规则、模板、skill 等生产运行输入仍 capability 全量。文件读取入口未覆盖或记录无法归属的组标读取关系未知，相关非代码改动时保守选入。

**免测需要正证据。** 选测工具内保留一份明确的路径清单；每项在 B 上用 `rg` 搜路径/文件名及路径拼接、目录扫描消费者，查看命中代码，结合读取记录确认不存在测试或运行时消费后才登记，说明保存在同一工具注释/验收报告，不另建注册表。检索无命中本身不能排除动态读取；证明不了就不列入。新发现的读取关系、目录扫描命中或运行输入属性优先于免测清单，相关消费者代码变化时复核清单。

`.cursor/plans/`、`harness/reports/`、`RELEASE-NOTES-v*.md` 仅是待核对候选，不能整类预先免测。例如当前 `component-blueprint.unit.test.ts` 会枚举 `.cursor/plans` 并读取特定 plan，故不能豁免整个目录。已确认仅生成、不被读取的报告可按具体路径纳入；未获此证据的普通文档按读取映射或未识别输入处理。`context-facts` 读取 `goal-mode-runbook.md`、`component-design-handoff` 读取宿主适配说明等关系必须落入映射。

**完整性按组判断。** 归一化 Windows 路径、file URL、临时宿主副本和预编译 JS 到仓库源文件，利用 source map/构建布局，不以缓存目录名猜源码。已加载文件可保守计入；强杀、缺少后代报告或无法归源只使对应组覆盖未知，不能拖整张映射失效。包括通过的 kill/timeout 用例在内，这些组遇到生产代码或运行输入改动就必选，其他组仍正常选测；不改变 kill 行为来强求覆盖文件落盘。报告未知组数量、原因及其累计耗时占比，不把缺报告算“未执行该文件”。

**import 变化局部合并。** “import 拓扑”专指当前及原快照中静态可解析的 import、export-from、require/import() 边；单增删一条边不使整张映射过期。新增 `A → B` 时，选中原来执行 A 的组，并把这些组并入 B 及 B 的当前传递依赖闭包的反向覆盖集合；结合两版图处理多条新边。移除边先保留旧覆盖，不因本轮推导删减，待完整采集再收窄。动态路径无法解析只将可能受影响组置未知；无法定位这些组才扩大。普通函数体修改照常命中文件；新文件未在映射中仍采用 §6.2 的全量回退，本期不增加可选的新文件推导。

只有注册/组身份或执行入口、编译/归源方式等公共结构变化，或映射整体损坏、无法对应当前历史时，才整张重建。个别测试文件变化只失效该组；共享 helper 变化按 §6.2 保守选测并刷新受影响组，不将任意业务 import 变化混称“全局拓扑失效”。

**原始覆盖及时归并。** 每组及其后代退出后立即合并成文件/目录清单，留下完整性与必要诊断，删除该组原始 V8 文件；异常退出也尽力归并并标未知，不积存整轮巨量原始覆盖。只清理本轮私有覆盖目录。报告累计生成字节、峰值磁盘占用、归并成本；用代表组有/无采集的受控对比估计墙钟增量，不为测采集成本重复整轮全量。

映射仍是现有结果的可丢弃派生物。完整全量刷新全部；按需运行若已开启采集，可顺带更新实际执行且输入未漂移的组，保留其他组，并与旧关系保守取并集，不能凭一次窄选测缩减覆盖。采集失败只保留该组未知，不把它发布成完整记录，也不引入覆盖率门禁。

映射只用于保守选择，不宣称静态图加历史覆盖能数学证明任意改动无遗漏；用 §9 的真实改动/注入缺陷检验已知风险，并保留收口与发布全量兜底。

### 6.4 合并测试与返修

一轮内先合并相关实现与多个修复，再生成一次计划、对相同用例去重执行；不能每改一个文件就启动整套。失败后优先跑失败项与直接受返修影响的测试，复用本轮仍对应相同输入的通过项。

“返修只跑失败项和直接依赖”不能成为删除工具必选项的理由：若返修引入新文件、共享 helper、入口或非代码输入变化，按上表重新计算，自动扩大必要范围；未受影响的已通过项继续复用。逐组更新有效结果，残留未通过项继续必选；只有当轮必选集合全部获得有效通过结果，才报告本轮通过。

## 7. 新增机制的场景与收益

依据 `AGENTS.md`「新增机制的准入」，本次只增加解决用户已明确问题所必需的开发工具信息：

| 机制/字段 | 改善的具体场景 | 收益与最小实现 |
|---|---|---|
| 现有注册项的 layer | 名为 unit 的套件实际起 goal/子进程，函数改动也被拖进长链 | 按执行事实分层；复用注册表及 runner 检查，不建新目录体系 |
| 用例组与串行关系 | 57.6 分钟单套件卡住整轮，部分用例共享固定资源不能安全并行 | 释放可并行部分并保留真实串行约束；复用现有 selector、执行块和 worker |
| 耗时驱动排序 | 后派发的大组形成长尾，手调套件切片失效 | 复用 `executionTimings`，缺失数据仅降级排序，不影响是否执行 |
| Git 影响选测工具及逐项原因 | 每轮开发和窄返修反复启动无关长测 | 自动生成可解释的最小必选集合，执行只增不减，复用有效结果 |

| 结果中的受测输入摘要与逐组结果 | 运行中源码漂移会误标已测，单条旧红又会让全局通过点永远建不起来 | 开跑前摘要、结束复核；未通过组持续必选，其他组增量复用；不建独立 checkpoint/审计服务 |

不新增会阻断产品阶段通过的检查、`BLOCKER`、`haltReason`、INCIDENT_REGISTRY 条目或新签名/授权协议。function 边界和漏跑等错误通过既有测试结果/退出码呈现，是测试自身有效性要求，不进入生产阶段判定。缓存/计时异常优先按组丢弃、补跑、重建，只有公共信息不可用才全量回退，不向用户转交可恢复的小问题。

## 8. 规则、入口与改动面

### 8.1 固定开发与全量入口

开发仓入口固定为两条：仓根及 `harness/` 的 **`npm test` 保持全量语义，并扩为本 plan 定义的完整全量**；**`npm run test:changed` 生成并执行按需测试计划**，根脚本委托 harness 同名入口。不另设第三个全量入口，避免既有 P3/P4 plan 所承诺的“官方 npm test”收口证据被悄悄改为选测。`test:unit` / `test:fixtures` 及筛选参数可作为底层诊断命令保留，但其成功不能代替按需入口的必选计划或全量收口。

**`npm test` 的完整全量**包含 typecheck 一次、所有当前注册的 unit/profile 套件（含 release-only）及全部 fixture 回归。`npm run test:changed` 只执行本轮必要的 typecheck 和测试；必选命中 release-only 时明确执行，不让原先的默认跳过吞掉必选项。

plan 收口、`release:all` 和 `candidate:build` 各显式调用一次 `npm test` 全量入口；发布脚本原先单独执行的 typecheck、unit、fixture 接线收编到这一次调用，保持各一轮，不能再重复执行这些步骤。选测结果或缓存不得把收口或发布全量变为选测。后续 pack/verify/consumer smoke 顺序和要求保留。

此入口变更仅针对开发仓。发布件继续按现有 `sanitizeHarnessPackageJson` 将消费者 `npm test` 转成 `check:global`；将新增开发专用 `test:changed` 等脚本纳入既有 sanitize，避免发布件残留指向已排除测试文件的命令。根级对应开发脚本同步处理，不改变消费者安装与运行契约。

测试总耗时与整个发布链耗时分开报告。约 30 分钟是完整测试目标，不是 `release:all` 包含打包、校验、consumer smoke 后的承诺；R4 的日常 unit 60.5 分钟不能直接作为此完整范围的同比基线。

### 8.2 实施时的最小改动面

## 9. 实施与统一验收

所有实测仅在 P3 提交后、机器空闲时进行。先冻结 B 的源码与清单，完成全部基建改造和必要的小范围验证，再在最终同一提交 **S** 上作统一验收；提交本身按届时授权办理。

### 9.1 新旧 runner 完整性与性能

1. 旧行为取自 B 的套件调度/启动实现，仅作为临时比较工具；在 **S 同一份注册表、生产源码和测试源码** 上分别跑旧行为及新 runner。不能拿 B 的旧用例与 S 的新用例比较后声称逐条一致，也不长期保留双 runner。比较适配只接当前清单/结果输出，不改变旧执行规则。
2. 以 `suiteId + 原用例显示名（重名含出现位置）` 逐条核对多重集合和结果，而非只看总数；fixture 同样逐条核对。通过数、失败/跳过状态一致，无漏跑、无重复跑抵消漏跑。基础设施错误单列，不算业务用例；全部既有用例和本次新增基础设施自测均须有归属。
3. 新旧完整全量按相同集合对比，报告 `npm test` 的完整全量耗时、`npm run test:changed` 的代表性按需耗时及 release-only/fixture 分项。新旧使用相同覆盖采集设置、依赖版本、Node/OS、硬件和空闲条件；编译、加载、执行、归并和清理均计入总墙钟。记录 worker 数、进程树 CPU/峰值内存、覆盖原始数据累计量/峰值磁盘占用及代表组估计的墙钟增量，说明不可拆组和长尾。
4. 与旧默认 runner 的最终对比体现本次整体收益；局部 A/B 则固定 worker 数隔离启动方案影响。不把并发提高的收益全部归因于 SWC/预编译，不用忙机与空闲机作同比。
5. 新 runner 在 S 的完整全量全部通过，可同时作为“测试基建改动本身一次全量”和本 plan 收口证据。若基线存在失败，先如实归属并处理真实回归；不能删除用例或将其标 skip 来制造同数全绿。窄返修仅补影响范围，不因 review 轮数重复全量；影响最终完整性或测试执行机制时才补必要全量。

### 9.2 选测正确性：3 个真实改动 + 3 个注入缺陷

从真实历史/P3 已提交改动中挑 3 个有实际回归证据的代表改动，覆盖函数逻辑、跨模块调用、能力链路或运行输入。另构造 3 个能让已有断言失败的最小缺陷，分别覆盖函数返回/边界错误、真实门禁或能力结果错误，以及**只改被测试读取的文档**（例如修改 `goal-mode-runbook.md` 中 `context-facts` 断言的内容，测试和 TS 源码不改）。不增加第七个长测样本，也不只挑同一类易命中的例子。

在隔离副本内应用，每个样本固定源码快照并产生自动测试计划，记录：改动 diff、已知受影响契约、自动选择集合及原因、实际全量失败集合、所选运行的失败结果。

验收关系是 **该样本全量会失败的用例集合 ⊆ 工具自动选择集合**，且实际选测能复现失败，修复后通过。不能靠开发者手工加测来弥补必选遗漏，也不能只运行已选测试再用其失败集合自证“没有漏选”。优先复用与样本完全对应的已有全量红绿结果；缺少独立参照时，在实施阶段空闲机器上补该样本的全量对照。这是一次性选择器验收成本，不加入日常循环，不建持续变异测试平台。

基础设施的目标测试同时覆盖：未提交/未跟踪输入、开跑前后漂移、删除/重命名及目录成员变化、capability 只读取而不执行的 TS 源码命中（如 adjudication 的停机原因扫描）、部分组缺后代覆盖、import 新增边的局部合并、残留失败持续必选而其他组增量复用、profile 自动发现、fixture、release-only 必选、串行资源、精确分组与无计时组、误标 function、开发者只加不减。将可共用的输入集中验证，不为每条规则都起一次长 goal run。

必须用正常包含强杀/超时用例的完整运行证明：未知只影响相应组，一次普通 import 新增不使整张映射作废；至少一个受影响范围可收窄的真实生产代码样本确实省掉无关 capability 组。报告覆盖未知和读取关系未知的组数、原因、累计耗时及占比，并给出本轮必选中的占用。若所有代表性代码改动仍机械退回能力层全量，按需能力未实现，不能只披露耗时原因便收口。

### 9.3 交付与通过条件

- 正确性：逐条无漏跑，新旧同集合同结果，新 runner 完整全量通过；现有进程/隔离/失败语义保持；6 个选测样本无漏选已知失败。
- 使用效果：`npm run test:changed` 实际选测并有逐项理由，`npm test` 始终完整全量；一轮去重、返修复用，局部未知组必选而其余组仍可收窄，既有红不让增量起点永久失效；两层登记覆盖全部注册来源，真实模型/宿主不混入开发循环。
- 性能：报告完整全量是否接近 30 分钟、函数级改动是否几分钟完成；包括覆盖采集、预编译等实际成本。未达标则明确最长组、启动成本、串行资源或内存限制及各自占比，不写“达标”，不为达数字扩面或改变生产语义。
- 材料：一份仓内简明报告即可，含 B/S 提交、命令与环境、全量结果位置、逐条差异（预期为空）、单例成本拆解及 A/B 实际作用进程、worker/资源与覆盖磁盘结果、未知组数量/耗时占比、6 个样本及剩余风险。不编制本期之外的迁移清单，不引入新的签收/身份协议。

性能目标、选测功能和正确性分别报告。时间未达标须按原要求解释原因并给出最小后续选择，不擅自扩展生产优化；但 §9.2 的选测可用性是交付条件，不能用“未达标已说明”替代。尚未实现该能力时 t7 保持未完成。本期分层登记不能当作历史用例迁移已完成。
