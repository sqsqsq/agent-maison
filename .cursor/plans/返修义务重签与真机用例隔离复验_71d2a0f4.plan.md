## 2. 返修范围的实质比较及续作

范围指纹有两个用途：证明“正是已签发的那份范围”，以及决定“这次提案是否需要重新签发”。实施时从 `executionScopeFingerprint`、义务 ID/集合比较和它们的间接调用列出所有实际读写点，按下表落到同一修订判定。附上覆盖清单及复核到的其他入口。

| 消费路径 | 要保持的语义 |
|---|---|
| 出生/冻结、事件前后指纹链、投影、交接与已有回执 | 按原始对象校验已签身份；对旧事件的改动仍会被发现。持久化格式、哈希算法和已发原件沿用原契约。[原指纹](../../harness/scripts/utils/execution-scope.ts) · [事件回放](../../harness/scripts/utils/goal-run-creation.ts) |
| 正式 Review/UT 返修候选、真实输入刷新、检查前后、重进时的提案生产者 | 复用已解析来源和当前责任。已落盘的旧式提案也交给同一消费判定。完整最新说明继续进入实际报告和当前返修任务。[候选生产](../../harness/scripts/utils/repair-candidates.ts) · [运行入口](../../harness/scripts/goal-phase-runtime.ts) |
| 决定是否追加 `scope_revised` 的写入前入口 | 在 `resolveScopeRevisionProposal` 使用已登记 previous 和充分解析后的提案。各调用方共享这里的“实质等价”判定，继续复用既有 `null` 无变更返回。原本合法的授权、重签、责任方交回、重新打开的否决和证明撤销先按现行规则处置。[修订与证明](../../harness/scripts/utils/feature-track.ts) |

正式候选生成处更新已存在义务时优先保持原位置；正式消费仍须处理已经落盘的旧顺序。按唯一义务 ID 配对，保留 kind、适用性、责任方、完整 basis（含来源与指纹）、satisfied_by（含签发者和真实证明），以及其余实质字段。只忽略可证明是已登记未满足返修义务的展示说明（来自该责任方当前正式候选摘要）和对实际调度、所选绑定及证据没有影响的排列。要求无重复 ID，保留当前报告里的新措辞。unknown/unresolved 的理由、用户控制、显式请求、执行链/有序选择、控制边、reused_phases、policy、契约和影响范围仍按原语义比较；只要顺序会改变实际选择或下一动作，就属于实质变化。不可辨明时走原校验。完整身份指纹继续可检测对旧记录的任何改写。历史签名、Feature 转交、完成回执、工作输入摘要及 Testing 的出生验收比较保持精确；`projectScopeSchedule` 的 phase_chain、绑定首选和可复用证明投影是校验业务顺序的依据。

已有范围本来可签的真实新增事实、有效用户授权、新 owner 证明、撤销或重新打开，优先走原分支。在原本将因“无新来源”而拒绝的地方，若上述比较证明只是已登记义务的展示变化，沿用原修订和所有未决结论。新增或删除义务、负责人/依据/适用性/证明变化均继续走原重签及授权校验；受保护的删减仍需真实权限。复用 3bc1f4ed 的已有根/CU 接回、返回的正式结果及责任方交接。[既有恢复约定](原CU恢复交付_两道重签与后继接回及存储验收_3bc1f4ed.plan.md)

## 3. 依据构建输入复用主 HAP

正式入口 `runDeviceTestAppBuild → evaluateDeviceTestBuildReuse` 对所选 product/mode、模块源码与资源、配置、构建脚本、锁文件、实际依赖和签名配置计算内容摘要，将它记入已有成功构建结果的 `buildInputsSha256`。公开证书、授权及别名按既有公开输入取证，私钥与口令使用 SDK 的现有边界。摘要让保留 mtime 的实质变更也能失效，并让单纯重写生成物的 UT 复用原 HAP。旧结果缺少可信输入可重新建立一次绑定。实际内容变化时通过 Hvigor 的非增量路径重建，核对产物确实带上新内容。[构建输入](../../profiles/hmos-app/harness/device-test-build-reuse.ts) · [构建出口](../../profiles/hmos-app/harness/providers/device-test-build.ts)

生成物的认定同时核模块归属、标准 task、目标、精确位置和模板。现场包括四个 HAR 模块根的标准 `BuildProfile.ets`，以及 Phone、WalletMain 各六个与已安装 SDK 模板逐字一致的模块根 `.test/<target>/intermediates` 文件。手写或不匹配模板、其他位置、其他 target 及实际源码与资源照常计入。阶段写权限沿既有规则执行。[生成物识别](../../profiles/hmos-app/harness/generated-source-classifier.ts)

设备继续用既有完整 SHA 执行键。同一包及其余输入满足原条件时复用，完整 SHA 改变时走正常装机与真验，`--force-device` 仍强制实际执行。现有失败优先、截图身份、证据读回和提交沿原消费链。verifier 材料引用 HAP 时保留其完整 SHA，二进制另由既有构建/装机产物定位。[执行键](../../profiles/hmos-app/harness/execution-key.ts) · [verifier 材料](../../harness/scripts/utils/verifier-material.ts)

2026-11-23 的范围裁决撤回不同 SHA 的签名等价比较，以及专为它增加的原 HAP、构建结果和实装范围冻结。两轮登记机实测均拒绝读回主模块与两个同包模块的 HAP，包管理器的 `hashValue`、`buildHash` 也为空。签名与版本能确认送装目标，无法证明三个当前在机模块的完整字节。真实 Hvigor 回放已在构建端消除 UT 生成物引起的额外打包，保住原 SHA 就能走既有设备复用。

真实宿主 `SimulatedWalletForHmos` 在 `3af5f7c1` 的 `default/debug` 上只读执行一次该快照函数，耗时 **129.5099 ms**。实现取自 `2840d55d`，与本轮保留版本逐字节一致。Node v24.15.0 的单调时钟只计函数调用，模块加载和依赖核对另计，未主动预热或控制操作系统缓存。5 个声明模块的 13 条生产依赖均指向 `file:`；存在 `oh_modules` 目录，此样本没有从其中解析生产包。

## 6. Adapter 与操作边界

| Adapter | 范围与接续 | 设备与证据 |
|---|---|---|
| claude | 同一 Goal 的提案解析、正式返回及原 CU 接回 | 使用同一 hmos-app profile、设备键和前置证据 |

| codex | 同一判定，覆盖 11-22 原根/CU 的旧停机与后续合法派发 | 同上，按真实设备原件统计 |
| DSH（deepseek-harness） | 同一真实责任方、已有 handoff/缺席回传与接续路径 | 同一设备规则。沿既有 adapter 能力签发，保持 DSH 的阶段 verifier 适用性 |

四种 adapter 通过各自现有运输入口覆盖重复提案的同 CU 接续、完整 SHA 相同的主包复用和测试前置的计划校验与结果读回；实际 HAP 安装和原生应用流程集中在同一获准的真机与隔离宿主上计量。

开发、隔离副本、测试用包和回归可在本地独立进行。**合入 main、推送远端、改动原宿主工程、制作正式发版包或最终候选包**均逐次取得用户明确同意。设备上覆盖原宿主或未知归属的同名安装按 §4 的额外授权处理。测试用包经现有打包与同包校验，只安装到隔离副本；宿主实例保持 `framework/` 发布件集成拓扑。敏感签名配置使用宿主既有获准路径，测试包保留来源及 SHA。临时分支、工作树由用户决定是否清理。

1. **原件与原入口。** 校验 611 项归档和索引摘要，使用隔离副本重建原根、CU、已签修订、Review i17 交回、正式 FAIL、构建日志与两轮 trace。真实输入带绝对路径时走既有绑定重定位，或在受控的等效路径环境中运行；保留原件原路径/内容/指纹，记录适配。复演旧版两次同错误，修复后通过正式解析、写入与 `--resume` 或已有 handoff 接入原根和同一 CU，旧历史仍可严格验签，#10 的重复提案不追加，实际下一授权动作可执行，原 Review FAIL 和六条返修义务可读，首次送达责任方的任务仍含 i17 对应的最新候选摘要。
2. **范围正反例。** 分别改变说明、顺序和两者，单独验证同事实复用。注入新/删义务、owner/kind/applicability、basis、来源角色、证明、真实策略、用户控制或有业务含义的顺序变化；按原规则追加、撤证或拒绝越权。变异移去等价分支应复现原停机，放宽保护字段、忽略旧事件篡改或真实撤销应命中对应断言。
3. **构建与设备身份。** 从真实 UT 与应用构建入口验证四个标准 HAR 根输出、两个模块 12 份标准测试中间件重新生成后，正式 App 复用原 HAP，额外 Hvigor 调用为 0。用手写/错误目录等反例和保持 mtime 的输入变更验证实际重建，在已签 HAP 内读回新资源。通过原装机、设备执行和证据入口分别核对同 SHA 复用、不同 SHA 真验、同调用失败优先及显式强制执行。移除生成物识别或强制非增量重编的变异应命中断言。在真实宿主只读测一次 `snapshotDeviceTestBuildInputs`，以单调时钟包住正式函数调用，报告 product/mode、计时边界、实际依赖形态与耗时。
4. **测试专库的双轮复验。** 在获准的同一登记设备和隔离宿主，使用同一测试 HAP、同一计划和固定候选，从 standalone Testing 入口以 `--force-device` 执行两次。逐轮核对独立 run、装机事实、同一执行键、原生真实派发、真实首页投影和同轮 duplicate，按原生 case 与原 P0 检查点计算结果。复用现有两轮实际设备原件时，写明当时使用的运行时版本。删减后的官方 0.6.2 另用相同派生与原件走生产读回，核标准启动、准备、等待和原断言；准备失败仍为整轮 FAIL，`BLOCKED_BY` 不得贡献 PASS。错误就绪、错库、重复写入等反例逐项区分实机、归档回放或隔离变异。完整业务阶段若另缺 verifier/Goal 回执，照实列出。此项不以失败后跨用例零派发为验收条件。

5. **工程和交付。** 删减后先完成数据前置代码的独立检视，随后按顺序运行变更门禁和日常全集。每轮开发跑 `npm run test:changed`，收口跑 `npm run test:daily` 和必要定向验证；同输入的有效结果按仓规复用。静态夹具、生产入口回放、真实安装/真跑及未知量分别记录，变异仅在隔离环境施加。计划与实现经独立检视。一次结算所有 todo，依据实际结果保留未满足项。
