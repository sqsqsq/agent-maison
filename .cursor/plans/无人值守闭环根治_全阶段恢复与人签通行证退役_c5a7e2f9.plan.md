name: 无人值守闭环根治 — 全阶段恢复与人签通行证退役（autonomous recovery without human pass keys）
version: 3.0.0
overview: >
  宿主 bc-openCard 已给出反例：一次由 plan 阶段越权改写 spec 所属 acceptance 产物，
  会把已完成 spec 变 stale；assess 虽能描述 rerun_phase:spec，goal driver 却只把可信
  repair_candidates[] 投影成可执行 backtrack_to_phase，最终在 plan 17% HALTED。问题不只
  是 rerun_phase:spec，而是所有阶段都缺少统一的「产物归属—改写归因—恢复动作」闭环；
  同时视觉、人签 waiver、source mutation authorization 等 confirmed_by/receipt 又把机器
  可判断的质量事实变成等待用户签字的通行证。两者共同破坏 Maison 的目标：自动、循环、
  可靠地完成开发。本 plan 一次收口两条根因，但不另造状态机、owner manifest、视觉真值
  枚举、签名账本或第二套回退执行器：阶段所有权复用 phase-evidence manifest、resolved
  workflow 与现有 scope；责任事实复用 summary.repair_candidates[]；恢复只走既有
  backtrack_to_phase 事务；质量只走既有 quality_axes/verdict lattice；机器证明保留为证据，
  不再伪装成人类确认。FEATURE_COMPLETED 表示冻结需求下所有适用且发布必需的机器门禁
  已闭合、没有已知阻断缺陷；用户交付后的 UX 意见开启新一轮修正，不回写上一轮人签。
  真正的外部秘密、不可逆操作及法律/预算授权仍是外部前置条件，但不得被命名或消费为
  质量 confirmed_by。实施前须清点并处理全部重叠 OpenSpec change（不只 delegated provider），
  让已完成 delta 先 archive、冲突中的 delta finish/archive、withdraw 或由单一新 change 明确
  supersede，再修订 canonical specs；禁止在多个活跃 change 之间维护冲突契约。

# 无人值守闭环根治：全阶段恢复与人签通行证退役

## 1. 问题边界

这不是一个 `rerun_phase:spec` 拼写或单分支问题。

bc-openCard 的失败链是：plan agent 为了修正自己看到的矛盾，越权改写了 spec 所属的
`acceptance.yaml`；phase evidence 因而把 spec 判为 stale；assess 产出描述性
`rerun_phase:spec`，但 goal driver 只接受经过可信 `repair_candidates[]` 形成的
`backtrack_to_phase`，所以恢复链在 plan 阶段断开。把 spec 特判补通，只会让同一缺口在
plan→coding、review→coding、ut→coding 或 testing→任意 owner 时再次出现。

另一个根因是把“机器能判断的质量”与“用户是否签过字”混为一谈。当前 confirmed_by、
human_confirmed、visual-confirm、waiver receipt 等机制允许以下反模式：

- 机器证据不足时等用户签名，而不是补证据、回修或如实声明能力缺失；
- 机器已发现 FAIL 时允许签名改变推进结论；
- 下游越权改源文件后，用授权 receipt 将违规改写洗成合法；
- 已知 BLOCKER/MAJOR 可以被“接受风险”转换成完成；
- 同一个用户决定在 requirement、manifest、receipt 多处重复，形成平行真源。

本 plan 的范围是 feature/goal 开发闭环。它删除“人工确认作为质量或恢复通行证”，不删除普通
用户输入，也不假装秘密、付款、发布、法律承诺等外部权限可以由模型自行取得。

## 2. 冻结不变量

1. **一个责任事实源**：缺陷责任只来自可信 machine check 投影的
   `summary.repair_candidates[]`；agent 文字不得自报 owner 并驱动回退。
2. **一个回退执行器**：所有 earlier-phase 修复只走既有 `backtrack_to_phase` 事务；
   recommendation 文案不是第二个执行协议。
3. **一个阶段所有权解析链**：workflow 只给 phase chain；artifact owner 来自 skill contract
   `produces` + artifact/evidence resolver，source owner 来自既有 scope/profile resolver；不新增
   owner manifest 或硬编码 full workflow 表。
4. **一个质量真源**：继续使用现有 `quality_axes`、`PASS/UNVERIFIED/FAIL`；phase advance 走
   phase matrix + `projectPhaseAdvanceVerdict`，release/completion 走 `required_for_release` +
   `projectReleaseReadiness`/`verify-feature-completion`，不新增 axis 字段或视觉平行枚举。
5. **机器 FAIL 不可签字变 PASS**：人名、receipt、菜单选择均不得改变确定性结果。
6. **用户反馈不是上一轮签名**：交付后的 UX 不一致是新 correction/successor run 的输入。
7. **缺能力就如实缺能力**：strict 目标没有可用视觉证据时自动重试授权能力，仍失败则
   capability defer；不得静默 FEATURE_COMPLETED，也不得要求用户用 waiver 放行。
8. **不洗白但自动恢复越权字节**：下游实际写上游/产品源会作废本 invocation 与旧 closure；
   保留字节但不承认其可信，自动回 owner 做全量机器重验/必要重写后才能重签。正常协作仍必须
   先产 candidate，再由 owner 写入。
9. **不破坏性猜测恢复**：不自动覆盖用户文件；无可证归因但已经稳定的字节交 owner 重验，
   只有持续并发、不可读或重复不收敛才进入现有 integrity/external/fuse 终止。这属于完整性故障，
   不是“等待人工确认质量”。
10. **兼容读取、停止生成**：旧人签字段可读但不 gate，新 writer 不再生成；无需批量重写宿主。

## 3. 目标闭环

```text
phase machine checks / trusted verifier
                 │
                 ├─ current phase 自身问题 ───────────────► bounded retry
                 │
                 ├─ 上游真实缺陷 ─► repair_candidates[] ─► assess
                 │                                      │
                 │                                      ▼
                 │                           backtrack_to_phase
                 │                                      │
                 │                         invalidate downstream
                 │                                      │
                 └──────────────────────────────► owner 修复后重走

write-boundary observation
                 ├─ runner-owned 等价改写 ─► 原子 refresh/re-sign
                 ├─ 调用外稳定的新上游输入 ─► owner 重验后重走
                 ├─ downstream 越权写入 ───► 失效旧信任 ─► owner 重验
                 ├─ provenance unknown 但稳定 ► owner 重验
                 └─ 持续并发/不可读/不收敛 ─► precise integrity/fuse terminal

quality axes
                 ├─ required PASS + 无 open blocker ─► FEATURE_COMPLETED
                 ├─ 可修 FAIL ───────────────────────► owner repair loop
                 ├─ strict capability missing ───────► DEFERRED_CAPABILITY_MISSING
                 └─ optional UNVERIFIED ─────────────► advisory（按既有 release 规则）
```

## 4. 阶段写权限矩阵

矩阵表达语义，实际实现必须由现有 SSOT 动态派生，不能把这张表复制成运行时配置。resolved
workflow/runtime-policy 只确定 phase 集和顺序；owner 解析还必须消费 `loadFeatureContracts` /
`phaseContractIndex` 的 `produces`、artifact registry/phase evidence、coding 的 plan scope +
contracts module path、当前 profile 的 UT test-root resolver，以及 testing 已有 write boundary。

| phase | 可写内容 | 必须只读的已存在内容 | 发现问题时的动作 |
|---|---|---|---|
| spec | 当前 feature 的 spec、acceptance 与 spec evidence | 用户输入、其他 feature、runner state | 在 spec 内修；外部事实不足走既有 prerequisite |
| plan | plan 产物与 plan evidence | spec、acceptance、产品源、测试源 | `scope_consistency_with_spec` 产 spec candidate |
| coding | scope 内产品源、配置和 coding evidence | spec、plan、既有测试契约（除 workflow 明确授权） | 上游矛盾产 spec/plan candidate |
| review | review report/evidence | spec、plan、产品源、测试源 | 可信 issue 产 owner candidate |
| ut | UT 测试源与 UT evidence | 产品源、spec、plan、review evidence | 产品缺陷产 coding candidate；已改源即 violation |
| testing | 运行、设备、截图、visual 与 testing evidence | 产品源、UT 源及全部上游契约 | 产品缺陷产 coding candidate；已改源即 violation |

runner 的 summary、event、manifest、closure、签名刷新不属于 agent 可写域；必须在 agent invocation
边界外写并以 runner-owned 事实标记，避免自己制造 stale 后又让 phase 背锅。新文件只有唯一命中
当前 contract producer + path resolver 时才可写；无 owner/多 owner 均 fail-closed。custom phase 若
只有 `produces: source` 而没有现成 profile/scope resolver，不获得无限 source 写权，须先完善既有
contract/provider 解析链。调用前后比较只复用内存 diff/既有 source snapshot，不恢复持久 pass snapshot。

## 5. earlier-phase gap 决策表

| gap / 归因 | 唯一处理 | 禁止行为 |
|---|---|---|
| missing | 回退 owner，失效其下游并运行 | 只打印 `run_phase:<owner>` 后 HALT |
| failed / legacy_unverified | 回退 owner 重新生成当前可信 evidence | 当成未知 framework_bug |
| unclosed + 可证明的 partial finalization | freshness 通用拒绝前幂等补完 staged→canonical 事务 | 把中途 crash 误判普通 stale |
| unclosed 且 evidence fresh | `complete_closure` 可恢复闭合协议 | 重新调用 agent 制造无意义 token |
| unclosed 但 evidence stale/invalid | 回退 owner | 给 stale evidence 补签 |
| pruned / assurance 不足且可确定性恢复 | runner 恢复、验 hash、重签 | 创建新的恢复 sidecar |
| pruned / assurance 不足且不可恢复 | 回退 owner；真实工具能力缺失则 capability defer | 模糊“外部等待” |
| stale + trusted repair candidate | 回退 candidate owner | 依据文件名猜 owner |
| stale + 调用外稳定新输入 | 回退 owner 做完整重验 | 沿用旧 PASS/closure |
| stale + runner-owned 等价写入 | runner 原子 refresh/re-sign | 让 agent rerun |
| stale + 当前下游越权写入 | 记录 violation，作废 invocation/旧 closure，保留字节并回退 owner 全量重验 | 直接补签、求人签、破坏性回滚 |
| stale + unknown 但字节稳定 | 标注 provenance unknown，回退 owner 全量重验 | 沿用旧 PASS 或 catch-all framework_bug |
| stale + 持续 concurrent/unreadable/corrupt | 复用 integrity/external-wait/fuse 精确终止 | 无限回退、模糊外部等待或破坏性回滚 |

“调用外稳定新输入”必须证明变化发生在受控 agent invocation 之外且当前文件已稳定；若无法证明，
归 unknown-stable 并同样回 owner 重验，但诊断不能冒充用户输入。下游越权改完的字节也可以在 owner
全量门禁下重新取得信任，因为旧 PASS、当前 invocation 和下游 closure 已先失效；这与“按当前字节
直接重绑 evidence”不同。只有同一恢复中内容继续变化、不可读或触发既有预算/指纹熔断才停止。

`complete_closure` 不是普通“fresh 后再调一次 finalizer”即可满足的动作。finalizer 在 canonical
summary rename 前可能已发布 manifest、pointer 和 phase state；resume 必须先识别并核验同一 staged
summary 对应的 partial publication，再决定幂等补完或回 owner。closed summary 的 hash 漂移默认是
信任失效，禁止沿用当前 `evidence_rebound` 泛化成功语义；只有 runner-owned 等价改写具有明确证明时
才允许窄 refresh。

## 6. 人签与 receipt 迁移表

| 旧机制 | 新语义 | 结论 |
|---|---|---|
| `confirmed_by` / `human_confirmed` | legacy provenance only，不参与 verdict | 停止生成，兼容读取 |
| `confirmed_by_user`（setup/catalog 等） | 普通选择若仍需溯源，改用中性的既有 input/selection provenance；冗余则删除 | 新 writer 不再使用 confirmed_by 命名 |
| `visual-confirm` / human visual acceptance | 用户反馈进入新 correction run | 删除 CLI、gate、receipt |
| `visual_diff_human_confirm_required` | 当前机器 evidence + quality axis | 删除 |
| `repair_adjudication_pending` | 确定性/合法 critic evidence 产 candidate；不确定且 required 则 UNVERIFIED/FAIL/defer | 删除 WAITING(human) 与人签 resume |
| `repair_not_converging` 的 human release | 保留 bounded fuse；仅新机器证据或 successor 新 run 可重验 | resume 不清 attempted/fingerprint，不改 verdict |
| `--allow-blind-visual` | 由 requirement 严格度和能力事实自动裁决 | 删除 waiver；strict 缺能力 defer |
| `fidelity_downgrade` | fidelity 是冻结需求；改变目标是新输入 | 删除 receipt |
| `p0_skip_waiver` | P0 未闭合就是 FAIL | 删除 receipt |
| `conditional_review_authorization` | open BLOCKER/MAJOR 回 owner 修复 | 删除 receipt |
| `behavior_switch_waiver` | 修实现或变更需求并开启新 run | 删除 receipt |
| `flow_contract` receipt | spec-owned hash-bound contract | 收编到 spec evidence |
| `source_mutation_authorization` | 发现需求→coding candidate；实际越权→violation | 删除 receipt |
| crop/bbox/baked-text 人签 | 内容 hash + tool/algorithm provenance | 去人名，机器不可证则 FAIL/defer |
| runtime fidelity attestation | Hylyre/runtime provider 逐 step 结构化 observation，hash 绑定 flow/plan/HAP/source/run/attempt/device | 扩展已有 trace/device evidence；缺能力 defer，旧 receipt 不 gate |
| critic receipt | 机器身份、输入 hash、freshness 披露 | 可保留证据，绝非签名权威 |

视觉 signal 不再采用“producer 与 primary 争议后交给人”的第三裁决层。满足适用前提的 deterministic
producer 自己就是机器事实；合法 delegated provider 输出按现有 critic candidate 语义消费；其余
uncertain/invalid 只说明证据不足，required 轴 fail-closed/defer、optional 轴 advisory。收敛熔断仍保护
预算，但 same-run 人工 resume 不得把 attempted 清空或把旧信号改判为已解决。

P0 runtime fidelity 选择本期落机器证据，不选择“先删 receipt、以后再补”。现有 Hylyre trace/device
evidence 扩展为 runner/provider-owned 逐 step observation。preflight 先独立判断 provider/profile 是否
支持 step telemetry：不支持或 bounded probe 后仍 unavailable 才是 capability missing/defer；已经声明
支持后，本次却没有实际 target、屏幕迁移、required/forbidden 观察或载荷不合法，是 testing evidence
FAIL/retry。两者不得共用 `on_missing=fail` contract input，也不得退回人签。

普通 setup 菜单、adapter/model 选择、需求选择并非 quality receipt。它们可以作为 attended UX 保留，
但 unattended 必须从 manifest/config/默认策略得出确定结果；不得创建“必须用户再点一次才能继续”的
隐式完成门。

## 7. 完成语义

`FEATURE_COMPLETED` 的充分条件是：

- requirement/spec/plan 身份冻结且 evidence fresh；
- workflow 中所有适用 phase 已按当前 chain 闭合；
- 各 phase 的 matrix 经 `projectPhaseAdvanceVerdict` 已允许推进；
- 所有 applicable 且 `required_for_release` 的轴经 `projectReleaseReadiness` 判定 PASS；
- 没有可信 open BLOCKER/MAJOR 或未执行的 P0；
- strict 视觉目标具备当前 attempt/hash 绑定的可采信机器 evidence；
- P0 device flow 具备当前 flow/plan/HAP/source/run/attempt/device 绑定的逐 step runtime evidence；
- 所有 recovery/backtrack 事务已提交，且不存在 provenance/write-boundary invariant failure。

`QualityAxis` 不新增 `required_for_phase_advance`。phase matrix 和 `projectPhaseAdvanceVerdict` 是推进
唯一真源；axis 的 `required_for_release`、`projectReleaseReadiness` 与
`verify-feature-completion` 是完成/发布唯一真源。

以下事实不能单独制造完成：用户名字、用户点击、旧 receipt、旧 attempt 的 provider 输出、agent 自称
“已确认”、对已知缺陷的风险接受、blind waiver。用户验收发现问题时，上一 run 的历史结论保持可审计，
新问题进入 successor/correction run，系统继续同一责任路由。

## 9. 验收场景

### 9.1 bc-openCard 正向复现

### 9.2 越权写入反例

plan 实际修改 acceptance 时，invocation boundary 立即记录精确路径和 spec owner，输出
`phase_write_violation` 诊断，作废 plan invocation evidence、旧 spec closure 与其下游，保留当前文件
字节但自动发起既有 `backtrack_to_phase:spec`。spec 必须在当前字节上完整重跑全部机器门禁、必要时
重写，成功后重新签发 closure，再重走 plan 及下游。首次事故不得永久 HALT，也不得沿用旧 PASS、
直接重绑被改内容或用 source mutation/visual waiver 放行；同一改写反复、字节持续变化或不可读时，
才由既有 fingerprint/budget/integrity 语义终止。

### 9.3 视觉能力反例

pixel_1to1 目标下 provider 超时或输出 hash 不匹配：bounded retry 当前 pin；仍失败则
DEFERRED_CAPABILITY_MISSING，绝不 FEATURE_COMPLETED。普通非 strict 且视觉不属于 release 必需轴时，
可保留 UNVERIFIED advisory 并按既有政策完成；两者都不询问 confirmed_by。

### 9.4 用户事后反馈

已完成 feature 被用户指出按钮间距不一致：记录为新 correction 输入，责任解析到 coding（若需求未变）
或 spec（若用户改变目标），创建 successor 后自动回修；不得给旧 artifact 补/撤人签。

### 9.5 P0 runtime fidelity

有 P0 device flow 时，Hylyre/runtime provider 逐 step 事件与 `device-test-evidence.json` 完整绑定当前
acceptance flow、派生 plan、HAP/source、run/attempt/device，verifier 复算 target 命中、屏幕迁移与
required/forbidden 观察后才允许完成。provider/profile 在 preflight 明确不支持 step telemetry 或
bounded capability probe 后仍 unavailable 时，spawn 前自动 `DEFERRED_CAPABILITY_MISSING`；provider
已经声明支持但本轮 evidence 缺失、伪造、stale、乱序或跨 run 重放时，testing BLOCKER FAIL 并重跑，
不得标 capability missing。任何分支都不接受旧 runtime receipt 或人签替代。

## 10. 非目标与审查红线

- 不引入通用自治权限系统、provider 池、自动换模型或新视觉评级枚举。
- 不用“一律 rerun 上游”替代原因归因；那会掩盖越权写入和 runner 自己制造的 stale。
- 不为防 agent 伪造人名建设更强签名、密钥或账本；正确修复是删除人签权力。
- 不把真正外部权限说成质量确认，也不让 receipt 规避安全/法律边界。
- 不自动回滚无法证明归属的工作区变化，不覆盖用户并发修改。
- 不恢复已退役的持久 pass-snapshot、restore 或 authorization 状态；写归因只服务当前 invocation，
  crash 后由 owner 全量重验重新取得信任。
- 不修改已归档 OpenSpec 历史来伪装过去从未有人签；canonical spec 用新 change 正向 supersede。
- 不因该 plan 与当前 provider worktree 并存而修改、格式化或提交对方文件。

## 11. 给下一位 reviewer 的冻结检查点

review 请优先验证七件事：

1. 越权写入是否先失效信任再自动回 owner 全量重验，既不首次永久 HALT，也不直接 rebind 洗白；
2. 所有 earlier gap 是否都能落到唯一可执行结果，且 closure partial publication/crash 可恢复；
3. `repair_adjudication_pending`/`repair_not_converging` 是否已失去人签 release 权力；
4. runtime fidelity 是否已有真实逐 step 机器 evidence 合同，缺能力时仍 defer；
5. owner resolver 是否复用 contract/scope/profile SSOT，并正确处理新文件/custom phase；
6. phase advance 与 release/completion 是否分别复用现有 projector，没有新增 axis required 字段；
7. 全部重叠 OpenSpec change 与 legacy receipt/field 是否被显式处理，且 legacy 只读、不 gate。

若这七项成立，后续实现应按 todos 收口；可选加固（隔离 worktree、更多 provider、额外 UI）不得扩入
本 plan。
