## 3. 改造点与责任链

### 3.1 素材复用优先（t1）

修改 `harness/scripts/goal-phase-runtime.ts` 的无视觉素材提示（调查时约 1878 行）：先复用工程已有、用途可由代码或资源引用确定的素材（repo_ref），确实缺失或用途无法确定时再占位并披露。无视觉不等于没有可用素材；复用不宣称视觉验真。

核对直接消费该提示的 spec/coding 指引，删掉同场景下冲突的“一律占位”说法。保留现有 auto_crop、明确素材要求、逐项降级和视觉能力披露，不扩大到素材系统改造。

### 3.2 review 差异处置同源（t2）

**机器载体固定为现有问题表的“分类”列，新增允许值“视觉保真”**；不增加报告字段。该分类仅承载视觉问题，不把功能/数据错误移入其中以取得放行。旧报告的“其他”不靠关键词自动转换；由报告责任方依据当前材料更正，verifier 核对分类和严重级别。coding-rules 追溯按“其他”的现有处理方式处理“视觉保真”，不伪造一条 coding 规则。

**严重级别按实际影响判定，闭环与返修按有效范围、严格度和问题共同判定。** 视觉三级定义与 `profiles/hmos-app/harness/visual-provider-review.ts` 一致；P0/pixel_1to1 的覆盖要求可保留，但不能单凭目标名将细节判为 BLOCKER。在有效 best_effort 下，分类为“视觉保真”的非关键 MAJOR 可披露，不计入必须返修的未关闭 MAJOR；有效 hard 要求照旧阻断。BLOCKER 和非视觉 MAJOR 仍按真实问题处理；缺失/不可解析的有效目标不能自行解释为宽松授权。

在现有 review 解析和保真工具中提取同一处置判断，供报告结论一致性、`conditional_pass_closure` 和 `repair-candidates.ts` 的候选过滤消费；verifier 提示使用相同定义并逐条核验。问题统计保留全部真实数量，不把披露项写成“已关闭”。仅剩可披露视觉 MAJOR 时，报告保留差异披露，结论一致性检查同时接受“通过”和“有条件通过”；闭环与候选按同一处置判断允许推进、不派返修，不能仅因这两个裁决词的措辞差异要求重写报告，也不能因原始 MAJOR 总数仍大于零而强制返修。旧报告仍写“不通过”或把问题错误判为 BLOCKER 时，先由 verifier 指出并由报告责任方纠正，再重验；`negative_verdict_closure` 不得因 verifier PASS 直接覆盖尚未纠正的负面产品结论。

复用有效保真目标、`spec/ref-elements.yaml`、排除引文核验与债务读取。defer/excluded 的元素对应与登记正当性由现有 verifier 逐条裁决：有效 defer 不派 coding；错误登记指向 spec；有效 excluded 仍核对原文引文。闭环检查不另建元素查表器。被驳回的问题先更正报告，不将 refuted 当成“已修复的产品缺陷”。

**债务记录者保持唯一**：已有 defer 仍由现有保真延后读取；本批新增任一阶段的 summary 将非空 spec fidelity_deferrals 投影为 release_readiness=BLOCKED，不影响正常完成，直到 spec 撤掉延后登记；设备视觉残差由现有 testing 视觉门禁登记。review 只在原报告披露，不写第二份视觉债务账。新 review 差异尚未经 testing 判定时保持视觉未验证，不由 review 预签视觉 PASS/release READY。

|---|---|
| 有效 excluded，且现有引文核验成立 | 不要求实现被排除内容；核验不成立时沿既有 spec 责任路径澄清 |

### 3.4 复审边界（t4）

确定性放行复用 t2：新增可披露视觉打磨由分类/严格度共享判断处理，不另做“是否新问题”的机器裁决。非视觉意见的事实与严重级别由现有 verifier 逐条核验，证据不足或级别虚高时驳回并交报告责任方纠正。新问题确属确定性正确性、真实授权、硬预算、完成与自动恢复必停风险，或满足有效 blocker 定义时，照常阻断并说明证据；“非功能”不构成豁免。

本项验收分工：测试 runtime 确实消费真实前轮材料构造上下文；再用两个报告夹具穿过实际闭环与候选链，分别证明新增视觉打磨可披露、改动引入的功能回归仍失败。模型能否持续遵守窄审范围留给宿主观察，不把提示/夹具测试说成模型行为保证。

### 3.5 完整交付在同一 run 衔接（t5）

沿用 `execution-scope.ts` 的义务派生、`phase_chain`、`reused_phases` 及 runtime 的 `scope_revised`。unknown 不得仅移除责任阶段却让依赖未满足的下游执行，也不得使用户明确授权的完整交付义务在后续修订中丢失。

需要调查才能确定的工作先交现有 owner；补齐后通过现有修订继续同一 run。已满足且证据有效的阶段仍复用，不把 requested_phases 无条件变成全量执行清单，不新增“目标链”字段。

回退需进入当前链外的责任阶段时，在既有完整交付授权内形成并应用范围修订，接入同一循环和恢复回放；保留其他 fresh 阶段与有效产物。真实新增业务范围或缺授权仍按现有边界处理，不承诺所有链外请求无条件放行。不能仅修改停机提示让宿主继续手工 supersede。

准入：场景是本次定义缺口切段、UT 缺口不能回 plan、链外回退停机；收益是减少无效下游调用、人工救场与新 run 接续成本。复用现有 revision 事件、基线冻结、责任无遗漏校验和预算折叠，不新增状态机或恢复文件。

### 3.6 verifier 的局部恢复（t6）

复用 `verifier-plan.ts` D1 资格、现有 verifier request/subject、调用和 `repair-candidates.ts` 解析链。对缺逐条块、缺绑定或格式无效提供具体诊断，在本次尝试内最多重新请求一次；合法 refuted/unclear 不因结论不利而重投。

纠错与产品返修分开：纠错调用及活跃时间照实纳入既有预算，不伪装免费；一次有界的格式恢复完成前，不把同一次格式故障重复计算为产品无进展。用已有尝试控制表达这次机会；恢复/重进不得无条件重新发放机会。仍无有效结果则沿既有准确失败/恢复出口，不无限重试。

逐条 confirmed 且材料/归属绑定有效的条目可产生候选；其他条目被驳回或局部格式不完整不应自动清空它们。整份材料确实无法识别、过期或相关条目不能可信对应时仍不产该候选。保留过滤“扩至 100 家”等误报的能力，不能绕过 verifier 直接从问题表派修复。

准入：本次已有有效产品发现与局部误报/格式缺失并存，整轮清零造成完整 review 重跑；收益是把报告协作失误在本次尝试内修复，让可信缺陷进入有效返修。不是新增失败诊断资格、宽泛重试层或第二种报告协议。

### 3.7 默认预算扩容授权（t7，用户已确认）

用户在本会话确认：**明确无人值守＋不要询问＋授权完整交付，可自动提高框架默认预算；仍不得突破用户另行指定的最终时间、轮次或费用上限。** 不推广到所有静默调用、普通“继续”或局部任务。

runner 到当前 manifest 上限照常停止；主 Agent 根据既有请求中的授权与任务剩余工作，显式通过现有预算修改/`--override-manifest` 恢复入口提高默认额度，继续同一 run。不新增 runner 自动无限增额循环，不清零 lineage 累计，不借提额绕过 no_progress_guard、重复回退、外部条件或其他真实授权。

采用预算前读取原始有效请求和已有更正，明确默认值与用户总上限的来源；“不要问”不覆盖用户同时给出的“最多 N 轮/费用/截止时间”。原有授权无法证明或相互冲突时，保持既有授权边界。扩容前后值来自现有 manifest 和 `budget_changed` 记录，累计消耗来自既有预算折叠；扩容原因和授权依据由主 Agent 按 Skill 在最终用户回复中说明。不给 `--override-manifest` 增加“原因/授权”参数或新字段。费用仅有可靠数据才报数值，不将 token 猜成账单。

同步 `docs/operations/project-entry.md:42`、goal-mode Skill/reference、相关运行手册与直接相关 OpenSpec；路标 a47c9d62 的“硬预算”统一解释为用户明确总上限与当前生效额度，默认额度可按上述授权显式调整。移除这些直接消费处“每次提额必问”与“静默一律可提额”两种冲突说法，不改其他权限面，不另建授权字段或预算账本。

准入：已获完整自主交付授权却因框架默认额度耗尽反复让用户救场；收益是已有授权不重复询问，同时保留真实总上限。复审收敛减少空转，但不作为总消耗必然有界的数学保证；提额不得代替修复已识别的无进展原因。
