## 1. 目标与范围

目标：UT 编译 / 测试失败时，框架能认出"agent 这一轮改过 UT 相关源码"，不再把正在推进的修复误判为零进展；agent 确实什么都没改时，照旧第二次就停。

范围：`profiles/hmos-app/harness/` 里产出这两类 blocker 的代码；`harness/scripts/utils/goal-failure-classifier.ts` 的产物快照；`harness/scripts/goal-run-creation.ts` 接续决策对目录条目的展开；相关测试。不改无进展守卫的判据（`shouldHaltNoProgress`）、失败签名、重试预算、停机原因与文案模板。

## 3. 方案

### 3.1 受影响文件改为真实路径（t1）

- `ut_hvigor_build`：`affected_files` = 解析出的 error 中、规范化后位于工程根内的源文件路径（工程根相对，去重）+ 该模块的 ohosTest 源码目录（`<srcPath>/src/ohosTest`）。
- `ut_hvigor_test`：同理，测试失败能定位到用例文件的给文件；再加模块的 ohosTest 源码目录。
- 模块路径优先沿用测试执行已经拿到的 `package_path`（`findModulesWithUt` 的结果沿 perModule 透传），拿不到再经 build-profile 解析；都拿不到时保留占位写法并在 details 写明"未能解析模块源码路径"——行为与现状相同，不更差。
- 错误里解析出的文件若落在构建产物或生成物目录（与 §3.2 同一排除规则），不进 affected_files，只留模块 ohosTest 目录。
- **接续决策**（`findChangedRelatedRepair`）：affected_files 里的目录条目，用来筛选既有基线（`phase_write_observed` 的 owned / observations）中位于该目录下的后代文件，再逐文件按原有方式比哈希。不新增目录基线、不新增状态；"没有可信基线就不能证明修复"的现有语义不变。
- **先盘点消费方**：`affected_files` 还被提示词里的"Files:"行、修复候选、报告、接续决策、可能的写边界 / 范围检查读取。实施第一步逐个列出，确认改成真实路径（含目录）后不会误触别的检查（例如把目录当文件读、把模块目录判成越界写入），有问题的在消费处按既有规则处理，不另建通道。

### 3.2 产物快照支持目录（t2）

- `snapshotArtifacts` 遇到目录：遍历目录树，按排序后的"相对路径 + 文件内容哈希"求一个摘要作为该条目的 `contentHash`；跳过 `build`、`.preview`、`oh_modules`、`node_modules` 等构建与依赖目录（复用既有的排除段，不另起一份清单）。
- 键仍是工程根相对路径；`artifactsProgressed`、`shouldHaltNoProgress` 的判据不变。
- 遍历以 `src/ohosTest` 为根，沿用现有 `lstat`、不跟随 symlink / junction 的做法；排除规则复用既有一份（实施时写明复用的是哪一份），不另起清单。
- 目录超限或读取失败时，**本轮整份快照为空**（而不是给该条目一个空哈希）：保持 `relevantEvidenceKnown=true`，由既有"缺少可比基线"的分支走有界重试。不改守卫判据，不新增停机原因或登记字段。

### 3.3 不做

- 不改失败签名（不把错误明细纳入签名）：签名变化会牵动累计熔断、回退去重等多处，收益靠快照已能拿到。
- 不改重试预算与停机原因。

## 5. 准入两问

- 场景：宿主 run fe7afc 的 UT 编译 / 测试连续失败；2026-10-03 诊断确认现行规则下占位路径让"agent 改过 UT 源码"永远认不出。
- 收益：UT 阶段真正推进中的修复不再被第二轮掐掉（少一次停机与人工重发）；什么都没改的空转照旧第二轮就停（不多花预算）。
- 新增：无新停机原因、状态、检查或登记字段；只改两个 blocker 的数据内容、快照对目录的支持、接续决策对目录条目的展开。

## 6. 风险

- 目录摘要的开销：ohosTest 目录通常很小；设遍历上限兜住异常大的目录。
- 真实路径进入提示词与报告后，可能让 agent 更倾向去改这些文件——这正是期望的修复位置，不另设限制。
- 消费方误把目录当文件：§3.1 的盘点与 U5 兜住。
