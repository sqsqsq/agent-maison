## 3. 修复内容、责任与边界

### 3.1 L3 可测性缺口进入现有责任链（t1）

落点：`harness/scripts/check-ut.ts` 的审计解析与 `checkUtUnsupportedTargetsHandled`、`utils/repair-candidates.ts`、runner 的候选消费/范围修订，以及 business-ut 的直接指引与 overlay。

复用已解析的 testability-audit、当前 acceptance 和源码定位；合法 unit/both 项为 L3、selected=option_b 时，由检查器提供现有候选结构所需的责任与位置，统一候选装配产出 coding 候选，沿既有 coding→review→ut 接续。可以合并同一根因，不把每条 AC 变成独立修复系统。候选是交给责任方核查的发现，不是授权或已确认产品功能缺陷。

在同一个候选生产点补齐 option_a：合法 L3 记录指出验收层级或 device_focus 定义需要裁定时，产出 spec 类候选，携带对应 AC/BD、acceptance 路径及问题依据。复用 `scopeRevisionInputFromRepairCandidates` 的 spec→acceptance-definition 映射与 `resolveScopeRevisionProposal`，将链外 spec 补入完整交付链，由 spec 裁定后重签并回到 UT；同步修改检查器和 Skill 中直接让 UT 改 acceptance 的建议。现有 verifier 的 device_ac_delegation→spec 路径保留，不能以“已有另一条 spec 路由”为由漏接 option_a。

option_a 只提交定义裁决，不自动批准改为 device-only，也不因已有 device_focus 就豁免未解除的 unit 义务。spec 按有效目标判断：补定义、纠正层级或驳回降级并保留 unit/both；用户明确要求的单测不能自行取消。确需改变冻结请求或撤销 required 义务时，沿原需求修订/后继与授权规则处理，不能借普通 scope revision 原地减项。仅请求 UT 的局部任务不得自动获得链外 spec/coding 写权限。

这两个可测性交接分支不以测试已执行、UT 结构全通过或 verifier 的真实断言失败合取为前提：它们解决的正是测试尚无法按当前定义继续的问题。保留原真实断言失败分支的验真要求，不用 L3 为任意业务失败开旁路。无 L3、错误 ID、无法解析审计或未选择合法处置时，不凭自由文本派修。

UT 不改业务源码或冻结契约。coding 只在既有授权内补最小生产可测接缝并重验；若发现是定义/设计冲突，回原 spec/plan 责任方，不倒改验收追认实现。coding/spec 缺于当前链时，复用既有候选驱动 scope revision 补入；有有效证据的阶段继续复用。候选到修订的必要接线必须通过真实消费回归，不能以声明了 category 就视作路由成立。无候选、同签名且输入无变化时保留熔断，不通过盲目 resume 或新 run 重置消耗。

**验收**：真实审计与 acceptance 经 UT checker→summary 候选→runner：option_b 下一责任调用为 coding，之后 review→UT；option_a 在 spec 不在链的形状下进入 spec 定义裁决，重签后继续 UT，过程中 UT 未改 acceptance。覆盖两类候选混合、链内/链外 owner、合法定义修订、降级被驳回/无授权时原 unit 义务仍在、误判可撤回及真实断言失败原路径；不是手填 summary 或仅断言提示词。

**验收**：源范围有 required coding/review、因 unknown 定义暂时仅执行 spec/plan；定义补齐后走真实 successor 创建路径，后继仍含编码与审查义务并按依赖执行。覆盖有效证据复用、缺口仍未补齐、局部 request 不扩成完整交付；不得只测试同 run 的 scope_revised。

### 3.4 定义责任与输入投影同源（t4）

落点：`utils/capability-resolution-entry-input.ts`、`capability-resolution.ts`、`execution-scope.ts`、spec/plan 直接消费与定义重签。

当前阶段被有效缺口指定为定义 owner 时，应能补齐自己 produces 中的产物；支持尚待判定的 unknown 定义义务，不仅支持 required 未满足项。该判断与恢复消费者共用；不扩展到其它阶段产物、任意 unknown 或已完成定义的无依据改写。蓝图投影物化为本阶段产物后，沿既有当前内容解析和 scope revision 重签，保留权威对齐和真实下游失效处理。

冻结绑定与阶段解析使用一致的源码/测试文件集合语义。复用已有集合规范化、源/测试分类及当前 Research 的事实来源，修正 expected binding 与实际输入的投影接线，不维护另一份文件清单。以下两种变化同属可对齐的输入记录差异，不直接判源码过期：

- 15→13：测试文件被既有分类规则分入测试输入。源码/测试两侧按同一集合规则消费；冻结文件本身未丢失或变化，不能因列表分组不同判 stale。
- 15→18：本阶段合法调研将已存在、未改动的源码加入只读资料。增量须来自同一 feature/run、当前阶段的既有 Research 声明（含 currentResearch 身份判断），复用现有 facts/基线及阶段观测核对来源与未改写事实；公共文件按原绑定逐字节一致即可对齐这类增补，不把阅读范围扩大成 contracts 写集。

不得只比交集而忽略冻结文件缺失或字节变化；非本阶段调研声明的新增、实际新建/改写的源码及非 owner 输入漂移不自动接受，继续沿现有 stale/责任修复处理。排序兼容保持；不忽略真实哈希、不靠路径相似或改写旧凭证消除 stale，不为普通调研增建授权/签名机制。

不因最终语义尚待判定而禁止 owner 补定义；也不能让任一调用方以“我在修复”为由接受陈旧输入。spec 的已生成 UI 定义按其真实产物消费，不把原需求文本当 Visual Handoff 块去复查、再诱导生成重复 spec 副本；仅同步本路径必要的直接消费。

**验收**：新蓝图/CU、有视觉定义缺口、源码与测试混合的输入，经过 scope freeze→spec 合法调研增补并物化 acceptance/UI→阶段 harness→重签继续。分别覆盖本次 15→13 和 R5 15→18，证明当前 owner 物化、文件分组和未改源码的只读增补不会假 stale；冻结文件缺失/字节变化、无当前调研来源的新增及非 owner 输入漂移仍被准确识别并回责任方。

### 3.5 审查责任唯一，闭环缺口局部处理（t5）

受管阶段沿现有 verifier request/报告/receipt 链发起独立核验并落盘；主 Agent 负责目标与运行编排，不在活跃受管阶段另派同一工作的 verifier 或并发写其报告。确需接管时先按既有交接确认当前 owner 已让出，再处理缺口，不增加锁、租约或审查身份层。

对齐 `goal-phase-runtime.ts`、现有 phase closure/finalizer/upstream-closure 与相关 Skill/运行手册：已存在当前有效的 verifier 结果时，只补回执/闭环；缺有效语义核验时，只做该核验；核验发现真实缺陷时才交回内容责任阶段。不能将 PASS 等同闭环，也不把材料未变的 closure_open 一律变成完整 review/coding 重试。

点名复用对象并订正现状：`goal-runner-phase.ts` 的 `classifyClosureKind` 已有 passed→deterministic_recheck、missing/failed→receipt_repair_with_verifier；`goal-phase-runtime.ts` 的 `isClosureOnlyRetryPending`/`closureOnlyAttempt` 已能识别收口重试，但当前仍拼完整阶段提示再附收口要求，并不存在已经可用的“只跑语义核验”窄分支。本批直接收窄这个既有 closure-only attempt 的提示与工作职责，继续复用现有 adapter 调用、预算/超时、verifier request 和 receipt/finalizer，不新增 phase、CLI、用途状态或平行调用协议。有效回执沿原 deterministic sync-closure；缺核验的窄提示按原 request 取得必要核验和回执，不重发完整 coding/review 作业。

目标是减少重复整阶段工作，不强制所有处理都在原 Agent 调用内完成；模板或输入已变化时不复用旧 PASS，旧报告身份不改写。格式无效仍复用 c6 t6 的有界格式纠错调用，不将格式纠错冒充新语义核验。

**验收**：通过真实调度入口核对调用次数、实际 prompt 与产物：有效核验存在而仅缺回执时无完整阶段再调用；missing/failed 走收窄后的既有 closure-only attempt，仅含当前 request/依据与所缺核验/回执工作，不再次拼接完整阶段作业；失败核验保留失败。覆盖当前阶段及既有上游关环、预算/超时消费不重置。提示/文档责任一致与实际模型不重复派审查分别由开发回归和宿主观察证明。

### 3.6 明确完整交付请求的无人值守接续（t6）

“只启动后台任务”仍可在有界启动确认后结束轮次；“无人值守完成、结束后一次性回报”已经表达跟到终态的目标，不再要求用户另外选择盯守。修正 `goal-mode-runbook.md`、goal-mode 入口/operations 指引及直接消费者，消除启动即离场的无条件指令与完整交付承诺的冲突。

本批已知路径由 t1/t3/t4 的机器候选、范围修订及 t5 的收口接线自动接续。主 Agent 用现有 bounded monitor/状态事件确认实际结果，有变化才读详细日志；不以百次 status/sleep 代替调度。当前 `--resume` 不能任意改起止，correction-init 的建议也不是把停下的受管 run 重新派到 coding 的调度入口；本批不承诺主 Agent 可以通过这些入口补任意缺失路由。

repair-notes 继续只是诊断，不承担改阶段、扩大授权或改变需求的功能；当前只在存在本阶段返修候选的窗口消费，这一适用条件在原指引/诊断中如实说明，不能宣称加上它就已路由。按实际事件核实下一 owner/phase；没有有效机器候选/修订且原入口无法合法接续时，主 Agent 准确停放并回报缺口，不代写产品或阶段报告，不强改起止，不原样 resume，不新增人工派阶段入口或用换 run 绕过熔断。

只在真实外部条件、授权/预算不足或既有有界恢复无法继续时准确停放并给终态报告。保留既有硬预算和重试约束；不新增常驻服务、任务调度注册、跨会话唤醒、独立监控账本或默认无限重试。宿主会话终止后的自动唤醒仍以实际已有能力为限，不在本批承诺永久在线。

**验收**：完整交付请求与仅启动请求分别走真实入口；前者对本批已知可恢复失败能继续且最终回报，后者不被强制长驻。没有用户第二次“继续”也能处理 t1/t3/t4 的已知路径；无合法机器恢复路径、真实预算/外部缺口准确停放并说明，repair-notes 不产生虚假路由，同输入无进展不得无限重启。自动化回归不冒充模型对未知故障的持续恢复保证。

### 3.7 在设计阶段统一按风险分层的验收（t7）

范围限定为正式蓝图/spec/plan/coding/business-ut 的现有直接指引、模板与 verifier 消费。复用 `ut_layer`、`device_focus`、use-cases 分支、contracts 及 plan 的可测性说明，不新增一份覆盖登记表、必填字段或前置门禁。

|---|---|
| 可隔离的纯逻辑、业务状态/异常分支 | UT 调真实生产入口，必要时隔离外部依赖；不能只测未覆盖业务路径的 helper |

在已有设计与计划步骤内核对声明的 unit/both 与计划 seam、业务入口/分支是否可实现；coding 交付相应最小可测性，UT 按同一预期验证。真实模型判断由原 verifier 核查，不新增一遍全量可测性审批。

已冻结任务发现层级或设计冲突时，验收定义问题通过 §3.1 的 option_a→spec 候选裁定，其他设计缺口沿已有 plan 责任路径处理；测试失败不是降低验收的理由。用户明确要求的单测/设备验证保持，下游不能擅改 ut_layer，不能自动把全部 L3 改 device-only；触及冻结请求/required 义务的修改仍走原需求修订授权，不借候选自批。

**验收**：代表性 UI 路由、纯业务、存储异常和 both 的设计→plan→UT 消费一致；设计没有承诺的范围不被 UT 临时扩大，已承诺的业务断言也不被纯函数计数替代。具体 prompt/解析回归与模型分工实跑结果分开记录。

**验收**：沿既有结果记录实际删掉的重复装配/读取/调用及保留依据；目标验证证明消费不缺失，并披露局部耗时与缓存等限制。若没有进一步可安全裁剪项，明确说明依据，不虚报节省；本项不要求达到预设字节数、百分比或工期。
