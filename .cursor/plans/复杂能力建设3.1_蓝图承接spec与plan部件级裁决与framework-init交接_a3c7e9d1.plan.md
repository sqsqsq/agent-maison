| 内容 | 归属 | 本 plan 动作 |

- 消息：来自 index 条目 `invoke.neutral`，harness 在其后追加一行披露 `paths.conventions` 与 `paths.component_index` 文件是否存在（复用 `loadFrameworkConfig` + 存在性探测，不建新 readiness 类型，缺失不生成 required 步骤、不阻断）。
- `skills.index.yaml`：component-design 增一条 `init_next_steps`（priority 34，介于 graph 30 与 plan 35 之间；`command_id: component-design`，与已物化 command 同名）；spec/plan 两条 `feature_ready` 的 `neutral` 改为「Feature Spec（存量平铺 Feature / 非正式维护动作）」「Feature Plan（同上）」，priority 不变。`findFirstLaunchableFeatureArtifact` 不改。

### 4.2 t2 术语与模块范围进蓝图

**获准模块解析（唯一 helper，三处同源消费）**

- `resolveAdmittedModules(root, blueprint)` = `module-catalog.yaml` 当前模块 ∪ 本蓝图 t3 `add_module` / `move_module` 决策声明的目标模块（含 `layer`，layer 必须 ∈ 当前 DSL `outer_layers`）。catalog 保持当前态语义（蓝图期不改），声明的新模块只在蓝图与 CU 施工期作"获准目标"，落地后由 closure 归位并复核。
- 消费者：① P1 节点 `module` 校验；② 术语 `canonical_module` 校验；③ `componentDependencyAllowed` 增可选 `declared: Map<module, layer>` 参数（蓝图侧传决策声明，plan 侧传 `contracts.modules[]` 的 name/layer），新模块作 consumer 复用既有组件时按声明 layer 走同一 DSL 判定，不再因"consumer 不在 catalog"恒 false。

**蓝图侧（P1）**

- development 视图 `applicable ∧ changed` 的每个节点：既有附加字段 `module` 升为必填并解析为获准模块；`owner` 保留责任归属语义不动（夹具 `ledger-team` 不受影响）。catalog 不可读沿既有 unknown|degraded + 当前切片 blocker 语义。`verified_unchanged` 节点按当前事实处理不重判。不新增第二个模块字段。
- 术语映射 = `discovery.facts` 条目：`subject: term:<原始术语>`，`value: {canonical_module, confidence: high|medium|low, easily_confused_with: []}`，`provenance.source_kind: glossary|catalog`，`SOURCE_AUTHORITY_RANK` 补 `glossary: 2`。`canonical_module` 必须为获准模块（同 `scope_matches_catalog` 语义，但允许本蓝图声明的新模块）。
- 确认：`spec.terminology` registry 条目改挂 `skill: component-design`、`harness: check-component-blueprint terminology_facts_confirmed`。真实用户确认记 `provenance.extraction_method: user_confirmed`；headless 沿 [user-confirmation-ux §9.2](../../skills/reference/user-confirmation-ux.md) 自动继续时记 `headless_assumed` 并入 must-review，**不得**记成 `user_confirmed`。`medium|low` 且非 `user_confirmed` → 交互态当前切片 blocker，headless 态按 §9.2 不停步。`high` 由 glossary 精确命中直确认。`project_scale=small` 的一次性整体确认沿 harness-gates「Terminology gate degrades on small scale」同样适用于蓝图。
- glossary 回写：只对 `user_confirmed` 的事实，admitted 后按既有 Step 1.5 第 6 条回写（`confidence_hint: user-approved on …`）；`headless_assumed` 不回写，留给 must-review 人工处理。归位规则 §5.3，路径与 writer 不变。
- 独立质询 scope 增一项：current_scope_items 引用的业务名词是否都有术语事实（disposition 由质询给，机器不做全覆盖判定）。

**下游（共享投影校验链，不只接 check-plan）**

- 派生「可修改模块集合」：**只从 CU `touches[].design_ref`** 经既有 addressing resolver 解析到 development 节点，取 `module` 去重；`design_refs` 只是设计依赖闭包（既有 `change_unit_touch_not_in_design_refs` 已保证 touches ⊆ design_refs），引用共享模块但不修改它的 CU 不得把共享模块带进可修改集合。同一 resolver、同一 stale 语义。
- 检查 `cu_scope_matches_blueprint` 放进 `validateChangeUnitFeatureProjection`（[change-unit-feature-projection.ts:472](../../harness/scripts/utils/change-unit-feature-projection.ts:472)）：`contracts.modules[].name` ⊆ 可修改集合；越出 → issue，指回 `/component-design` 调和（不提供 plan 内扩展出口）。该函数是直接投影（`blueprint-skill-projection.ts:229`）、check-plan、completion、ready-set、closure-inputs 的共同消费点，因此**不执行 plan 直接投影进 coding 的路径同样被拦**。`contracts.files` 仍是唯一精确写集授权，模块集合不替代它。
- 叙述路径（CU-bound 且 spec.md / plan.md required）：`Scope 声明` 的 `in_scope_modules` 必须集合等于可修改集合、`expansions_with_user_approval` 必须为空；`## 0. 术语映射表` 行集合 = 术语事实投影，`[x]` 由投影直接写、不再问人。既有 `terminology_mapping_table` / `terminology_modules_within_scope` / `scope_matches_catalog` / `scope_declaration` 在 CU-bound 下改为核对投影（同 id，details 注明来源=蓝图），非 CU-bound 原样。
- `plan.scope_expansion`：CU-bound 不适用，registry 条目加一行说明；plan SKILL Step 4 写明 CU-bound 走蓝图 revision。非 CU-bound 保留。

### 4.3 t3 架构影响判定迁蓝图决策

- decision 扁平子类型 `kind: architecture_impact`（沿 b9 `component_asset_selection` 先例，既有 decision validator 加条件字段）。**一条决策 = 一个具体变化项**，复合架构变化（新增模块 + 调整依赖 + 迁移职责）用多条决策表达，各自承担生效与归位义务，不新增时点字段或状态机。字段：`change` 枚举 + 条件字段 + `rationale` + 既有 `owner/provenance/verification_refs/status`：

| `change` | 条件字段 | 生效与归位 | 机器核对 |
|---|---|---|---|
| `add_module` | `module`、`layer` | 蓝图/CU 期作获准目标模块（§4.2 helper）；对应 CU 落地后 closure 归位到 catalog / architecture.md 模块行 | `layer` ∈ 当前 DSL `outer_layers`；未归位 → closure gap，不是 CU 失败 |
| `retire_module` | `module` | 旧模块仍承担职责期间 catalog 不得提前退役；对应 CU 落地后 closure 归位 | `module` ∈ catalog |
| `move_module` | `module`、`from_layer`、`to_layer` | 同 add_module；施工期按 `to_layer` 判依赖 | 两层 ∈ DSL |
| `responsibility_rewrite` | `module` | 实现成立并验证后 closure 归位 catalog `primary_responsibility` 等 | `module` 为获准模块 |
| `dependency_edge` | `from`、`to`（外层 id 或模块名）、`direction: add\|remove` | 施工前 DSL 须已达目标许可（add = 已允许该边，remove = 已不允许该边）且决策 `status` 达 decided_with_authority；未裁决即 open_decision，当前 CU 不得施工（同 b9 新边语义） | 既有端点解析后用 `isOuterDepAllowed` / `isIntraLayerDepAllowed` 取当前许可（helper 只返回当前关系、不解释操作），按操作核对：**`add` 当前不允许即 FAIL；`remove` 当前仍允许即 FAIL（删除未生效）** |
| `dsl_other` | `affected_items[]`（内层顺序、出口文件名等） | 施工前须经权威批准落盘 | 只登记不机检；以 init UPDATE registry（`init.intra_layer_deps` 等）确认为权威，投影 WARN 提示人工核对 |

- development 视图 `changed` 且节点 `module` 含非 catalog 模块 → 必须有对应 `add_module` / `move_module` 决策；`verified_unchanged` 视图 → 不得存在 architecture_impact 决策。无决策 = none，从严判 none 的原则不变。
- 检查位置：`dependency_edge` / `add_module` / `move_module` 的 DSL 核对与"决策已裁决"核对放进共享 `validateChangeUnitFeatureProjection`（与 §4.2 同点），直接投影、typed plan、completion、ready-set、closure 同一判据；coding 期依赖门禁继续兜底。
- plan：CU-bound `architecture_impact` 段 = 决策投影（typed 路径无 plan.md 即无此段）；`plan.arch_impact` registry 对 CU-bound 不适用。
- DSL 写路径：plan 不再是 DSL writer。既有两条获准路径保留——init 预设（`init.architecture_preset`）与 [手工编辑 config 后重跑 UPDATE](../../skills/project/framework-init/templates/custom-architecture-questionnaire.md)；统一要求 = 变更有权威批准（蓝图决策 decided_with_authority 或用户在 init registry 确认）+ 落盘后过 `validateArchitectureDsl`。`plan-workflow-detail.md` 删除「`dsl_change` 时同步改 framework.config.json」，改为「DSL 改写走 framework-init 既有获准路径；需要刷新物化产物时再跑 UPDATE」。非 CU-bound 的五分支判定本身保留。
