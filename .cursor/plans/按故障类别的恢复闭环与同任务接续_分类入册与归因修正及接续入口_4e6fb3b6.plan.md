# 按故障类别的恢复闭环与同任务接续

上位：[任务完成可靠性总纲 272acb5f](./任务完成可靠性总纲_统一原则与恢复闭环及可靠性验收_272acb5f.plan.md) §3 原则 5、§5.3。
前置：[P1 1dbe4fa4](./可靠性基线与任务集_指标口径与十三场景及基线记录_1dbe4fa4.plan.md)、
[P2 33784ed1](./统一目标上下文与权威判定_目标简报同源注入与判断双向可纠正_33784ed1.plan.md)。

## 1. 目标与冻结范围

**目标**：停机之后，能由框架带走的由框架带走；需要人的时候，人补上缺的那样东西，再重新发起请求即可，不需要拼恢复命令、
枚举 run、选技术分支。

**做**
- 停机原因的故障类别入册与归因修正。
- 带探针等待的进程内有界等待，以及探针到最终投影的贯通。
- 模型不受支持时的获准替代。
- 接续决策函数，以及全部入口对它的消费。

**不做**
- 不新建错误注册中心，类别写在既有注册表条目上。
- 不新增授权系统。重新发起请求不等于授权，不等于阻断解除。
- supervisor 不新增业务路由，仍然只看进程活性与处置状态。不自动安装计划任务。
- 不做无限重试，不自动加预算，预算不因新 run 清零。
- 不覆盖用户显式钉死的模型。不处理视觉 provider 的型号。
- 不为没有真实样本的 adapter 猜错误信封。
- 不改失败检查的处置策略（P4）。不减少拒修之后的下游重跑，该项等 P1 指标显示占比显著时再立项。

## 3. 停机原因分类入册（t1）

### 3.1 六类故障

类别取自总纲 §5.3。它是默认解释：告诉读者这类故障通常怎么恢复、什么时候交还。**处置仍以注册表既有的类别、结构终局
与处置投影为真源**，类别不改变任何处置。

| 类别 | 默认恢复动作 | 交还条件 |
|---|---|---|
| 瞬时与进程中断 | 有界退避，从失败动作继续 | 持续不可用且没有获准替代路径 |
| 模型或工具参数永久不兼容 | 停止重复相同调用，在获准替代范围内换参数并重探 | 无获准替代，型号被用户钉死，或替代会改变成本与授权边界 |
| 文件格式、投影、机器身份漂移 | 确定性修复或交既有责任阶段重建 | 关键原件无法恢复或归属无法确定 |
| 需求与设计或观察矛盾 | 按责任阶段调和后局部验证，见 P2 | 上位表述本身冲突且现有授权无法裁决 |
| 产品测试失败 | 依据可复现证据修根因 | 硬预算耗尽，或已无可执行的新策略 |
| 权限、秘密、不可逆操作、硬预算 | 停止对应动作，保留恢复上下文 | 必须由有权者授权或改变约束 |

六类不是完备互斥的根因分类。框架程序异常、汇总性的停机原因归不进任何一类时，类别一项留空并在注释里写明原因，
不硬塞。

### 3.2 入册

- `IncidentSpec` 增加可选的一项 `fault_category`。既有各项不动，处置投影的规则不动。
- 补登四个原因：

| 原因 | 处置 | 类别 |
|---|---|---|
| `budget_turns` | 与 `budget_wall_clock` 相同 | 硬预算 |
| `receipt_missing` | 可恢复，重试闭环事务 | 文件格式、投影、机器身份漂移 |
| `legacy_run_requires_manual_cleanup` | 等人 | 权限与不可逆操作 |
| `guardian_termination_failed` | 等外部。它可能出自权限或句柄占用，不认定为可自动重试 | 权限与不可逆操作 |

- 元门禁补两处：扫描启动期阻断函数的实参；预算停机变量的赋值。未登记的原因让元门禁变红。

### 3.3 停机说明的内容要求

需要人介入的停机说明应当让人读得出四件事：影响哪个结果、谁能修、做什么能恢复、怎样确认已恢复。这是内容要求，
不规定固定的四段格式。说明里不要求用户枚举 run 或拼旗标；诊断信息里出现 run id 不受限制。

## 4. 归因修正（t2）

| 问题 | 改为 |
|---|---|
| 外部阻断只看 summary 顶层或第一个 blocker | 看全部 blocker。存在外部阻断类 blocker 即按外部处理 |
| 框架缺陷须全部 blocker 都是才成立，混有内容 blocker 时落到代码回归 | 存在框架阻断类 blocker 时按框架缺陷处理，做法与既有的工具链阻断聚合相同。内容 blocker 保留在清单里，外部或框架问题解除之后仍须修复 |
| codex 的错误信封只识别 400 模型不受支持 | 同一信封按状态码区分：429 与 5xx 走瞬时重试；401 与 403 计入 CLI 硬失败，属于外部；400 保持现状 |
| 正式调用硬失败的归因字面量 `external` 不在取值范围 | 改用取值范围内的值 |
| 兜底代码回归 | 保留。它只在上述判定都不成立时生效 |

关于样本：宿主 run 0457a6 与 be091c 的事件提供了 codex 信封的真实形状，两者都是 400。401、403、429、5xx 目前没有真实样本。
新增的状态码分支以该信封形状加状态码变体实现，测试里把真实样本与合成变体分开标注。识别复用既有的终态契约：
只有终态失败才参与判定，"出现过错误但随后重试成功"不算失败。

cursor 与 opencode 没有真实的错误信封样本，本 plan 不处理，在实施记录里记为未覆盖。

## 5. 可恢复等待（t3）

### 5.1 进程内有界等待

带探针的停机在停放之前先等：

| 项 | 规定 |
|---|---|
| 适用 | 停机事件带探针的三种：设备未就绪、能力预检缺口、候选写回不可用 |
| 探针实现 | 从 supervisor 里提出共用，supervisor 与 runtime 调同一份 |
| 等待上限 | 取固定上限与剩余墙钟预算的较小者。固定上限 15 分钟 |
| 轮询间隔 | 30 秒 |
| 计时 | 异步等待，期间照常写 heartbeat。等待时间经既有的会话分段计入活跃时长，不另建累计 |
| 事件 | 开始等待、探针就绪、等待超时各一条 |
| 超时之后 | 按现状停放 |
| 有人在场 | 默认立即交回会话 |

候选写回的探针只检查报告目录可写，不证明 summary 文件可写。探针就绪只是重试的提示，是否恢复仍由原来的写回事务确认。

### 5.2 探针贯通到最终投影

- 停机事件上的探针与责任阶段，随处置字段一起复制到 `run_end`，包括结果投影补全的那一处。
- supervisor 的消费者接受带探针的 `run_end` 作来源事件，判据与对停机事件相同。
- 等待类、进程活性、重启次数上限三项限制不变。

### 5.3 删除死分支

supervisor 的后继分支没有生产产出方，删除。supervisor 对结构终局的 run 仍然不拉起。

### 5.4 进程中断

进程崩溃后的无人自动拉起仍然依赖用户手动启用的 supervisor，本 plan 不改。没有 supervisor 时，重新发起请求由 §7 重新接入，
计一次操作者动作。

## 6. 获准替代模型（t4）

### 6.1 配置

本机配置 `framework.local.json` 增加一项：

```
adapters.<adapter>.approved_models: [型号, 型号, …]
```

按序尝试。没有这一项就没有替代，行为与现状相同。字段归属与解析器随之更新，解析不了的值按没有配置处理并给出提示。

### 6.2 行为

| 情形 | 行为 |
|---|---|
| 金丝雀或正式调用判为模型不受支持，用户显式钉了型号 | 交还，说明里写明型号由用户钉死 |
| 同上，用户没有钉型号，获准清单里还有没试过的，且预算未尽 | 取下一个型号，写事件，重探金丝雀，继续。不消耗内容重试 |
| 同上，清单为空、已全部试过、或预算已尽 | 交还，说明里列出试过的型号 |
| 其它 CLI 硬失败 | 保持现状 |

### 6.3 预算

- 替代尝试与每次探测都消耗墙钟预算，受本次执行的同一截止时刻约束。
- 金丝雀的单次超时取固定值与剩余额度的较小者。剩余额度短于固定值时按剩余额度结束。
- 预算耗尽后不再尝试下一个型号。
- 启动阶段的探测发生在正式预算初始化之前：把预算与截止时刻的建立提前到首次探测之前，沿用既有的交付周期折叠，
  不另建计量来源。
- 恢复与后继不重置已消耗的额度。

"不消耗内容重试"只指不占用阶段的内容重试次数，不表示不受运行预算约束。

### 6.4 钉值来源

模型钉值增加来源一项：用户显式钉值，或获准替代。

- 替代值写入 manifest 走既有的身份改写授权路径，授权来源记为获准替代配置，只授权这一个字段。
- 后继 run 继承钉值时连同来源一起继承。来源为获准替代的钉值不算用户钉死，再次不受支持时可以继续替代。
- 旧 manifest 没有来源一项，读取时按用户显式钉值对待。这是读取语义：不回写，不改变既有 manifest 的身份摘要。
- 换了钉值之后，既有的金丝雀缓存因为绑定了钉值而不再被采信，会重新探测。

## 7. 同任务接续（t5）

### 7.1 原则

重新发起请求表示重新接入这个任务。条件是否解除，由原来负责该条件的检查判断：设备探针、凭据探针、产品选择检查、
金丝雀探测、预算检查。决策函数不替它们判断，也不因为请求被重复而跳过它们。

### 7.2 接续决策函数

只读函数。输入：工程、feature、**本次调用事实**（是否显式给了需求或需求增量、是否显式给了型号、是否显式给了预算改动、
显式的恢复、接续、强制新开旗标、是否有人在场）。输出四种结果之一：

| 结果 | 条件 | 执行 |
|---|---|---|
| 新开 | 上一次可信完成之后没有未终局的 run | 照现状出生 |
| 重新接入 | 最新的未终局 run 不是结构终局 | 回到这个 run：已有正式开始的走恢复，启动即失败的走附着。随后由原责任检查判断条件。条件未解除则以原来的原因再次停下，**不新建 run** |
| 起后继 | 最新的未终局 run 是结构终局，且存在变化 | 出生一个后继，见 7.4 |
| 保持停止 | 最新的未终局 run 是结构终局，且没有任何变化；或者仍在冷却期内且没有任何变化 | 不新建 run，不写事件，返回原来的停止原因，并说明补上什么之后可以继续 |

"存在变化"只认下列可核验的事实：

| 变化 | 依据 |
|---|---|
| 绑定的需求来源变了 | 既有的接续守卫判据 |
| 相关修复变了 | 既有的接续守卫判据 |
| 本次调用显式给了需求增量 | 本次调用事实 |
| 本次调用显式给了与钉值不同的型号 | 本次调用事实 |
| 本次调用显式改了预算 | 本次调用事实，走既有的预算授权 |
| 本次调用带了显式的接续或强制新开旗标 | 本次调用事实，行为与现状相同 |

预算耗尽的结构终局，没有显式的预算改动时属于保持停止。

### 7.3 执行位置

决策在选择入口、生成出生范围**之前**执行。下列各处改为消费决策结果，不再各自拒绝：

| 位置 | 现状 |
|---|---|
| detach 的孤儿 run 守卫 | 在接续守卫之前拒绝，要求恢复或强制新开旗标 |
| 前台的出生范围解析 | 范围已转交时拒绝 |
| 有人在场入口的出生范围解析 | 同上 |
| 新 run 接续守卫 | 拒绝并让用户在三条出路里选 |
| `createGoalRun` 内部的接续检查 | 同上 |
| 恢复守卫 | HALTED 与 DEFERRED 一律要强制恢复旗标，先过冷却 |
| 模型钉值裁决 | 恢复时新增或换值要整体改写授权 |

规定：

- 重新接入不要强制恢复旗标。冷却期只在"没有任何变化"时生效，对应保持停止。
- 本次调用显式给了新型号：走后继出生，沿用既有的"后继出生时可以直接覆盖继承钉值"，不暗加整体改写授权。
- 真实的锁、身份核对、授权检查全部保留。决策函数只决定走哪条路，不替任何检查放行。
- 前台、detach、有人在场三个入口共用同一个函数。

### 7.4 起后继

- 合同来源取当前持有范围转交的 run。没有 feature 转交记录时，取上一次可信完成的 run。持有者已经完成而最新失败的 run
  尚未接管范围时，仍以持有者为来源。不以未终局列表的第一项为来源。
- 承接目标是交付周期内全部未终局且尚未被承接的 run，含启动即失败的。每个目标照旧写审计事件，照旧核对身份。
- 被承接的 run 的场外信任状态会被删除，其中可能包含本来可以恢复的 run。run 目录与事件保留。
- 预算沿交付周期折叠，不清零。

## 12. 放弃的准确性与已知代价

1. 进程内等待占用墙钟预算。设备长时间不可用时，等待会消耗掉一部分本可用于修复的时间。
2. 获准替代会改变实际使用的型号，成本与产出质量随之变化。它只在用户配置了清单时发生，并且每次都有事件。
3. 起后继会删除被承接 run 的场外信任状态，包括本来可以在原地恢复的 run。
4. 进程崩溃的无人自动拉起仍然需要用户手动启用 supervisor。
5. cursor 与 opencode 的瞬时错误仍然识别不出。codex 的 401、403、429、5xx 分支没有真实样本，实际形态若与 400 的信封不同会识别不出，
   此时落回既有路径。
6. "存在变化"只认列出的六种事实。框架发布件更新本身不在其中：run 没有记录它出生时的框架指纹。宿主更新框架之后要继续
   结构终局的任务，需要带上显式的接续旗标或其它变化。

#### 二、从未正式开始过的 run 不作后继的合同来源（选甲）

理由：没有执行证据的 run 没有可继承的东西；从它冻结的范围恢复请求动作会在现场变化后制造拒绝，并忽略用户刚准备的候选。甲不破坏已通过评审的行为：
- "启动即失败的 run 重发即附着重检"是同一需求（没有需求增量）→ 仍附着；
- "型号不受支持后显式换型号起后继并承接启动失败的 run"只有型号变化 → 仍起后继（需求没变，来源冻结的请求仍是本次请求）；
- 持有范围转交的 run 仍作来源：出生段 `resolveBirthExecutionScope` 对已转交的记录拒绝新开（"范围已转交给 run X"），不改出生段结构就只能走后继。
实现：`goal-run-creation.ts:777-782` 决策的后继分支——没有范围转交、没有上一次完成、最新未终局 run 从未正式开始、且变化含需求增量 → 返回 `fresh`（非显式）。
新开走既有出生：范围由当前输入重新解析；决策驱动的新开本来就不经孤儿/失败续跑两道守卫。那个没开始的 run 不登记承接：它不持有转交，不挡新 run 的出生；
新 run 成为最新的未终局 run；下一次完成之后按交付周期边界（`deliveryCycleView` 的 since 过滤）自然移出，不挡完成判定；若之后起后继，它会作为未终局 run 被一并承接。
- 用例：`goal-run-birth-contract`"全量回归（甲）"（从未开始 + 需求不同 → 新开；同一需求 → 附着；只换型号 → 仍起后继）；standalone 两例原断言原样恢复通过，未改。

   失败的阶段没有闭环证据（阶段证据 manifest、闭环回执、pass snapshot 都只在 PASS 闭环时写），所以没有现成的写后哈希可消费——走任务书第 2 种做法。
2. summary：runtime 只在推进（advance）与外部阻塞停机（defer_external_and_halt）时把阶段 harness 报告归档进 run 目录（`snapshotPhaseHarness`），
   真实用例里 spec 以 `no_progress_guard` 停下，run 目录下没有 `phases/spec/harness/summary.json`，`findChangedRelatedRepair` 直接返回 null。这一处是评审意见之外、实跑发现的。

做法：
- `goal-phase-runtime.ts`（约 :8375）：`phase_write_observed.owned` 除 ut 的源码写入外，再记任何阶段对带 artifact 角色路径的 allowed 写入（字段沿用 path / how / pre_sha256 / post_sha256）；
  其它 allowed 写入不记（coding 源码由 review closure attestation 承接）。变量改名 `ownedWrites`。`replayUtOwnedWrites` 只读 ut 阶段的 owned，check-coding 行为不变。
- `goal-run-creation.ts` `findChangedRelatedRepair`：基线同时读 owned 与 observations；summary 先读 run 目录归档，没有时退回阶段报告目录里的现行 summary（该阶段最近一次 harness 的结论）。
  放弃的准确性：现行 summary 可能被之后对同一阶段的手动 harness 覆盖；那时读到的是更新的结论——修好后 PASS 则没有相关文件、保持原判断，不会冒充已修复。
- 行为说明：`no_progress_guard` 不是结构终局，相关修复成立时决策是**重新接入（恢复）该 run**，不是起后继；它的实际作用是让无人值守调用越过 5 分钟冷却（未修时冷却期内保持停止）。结构终局的停机才会起后继。
