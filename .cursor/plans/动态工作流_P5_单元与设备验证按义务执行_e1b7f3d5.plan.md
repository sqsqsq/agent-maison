# P5：单元、设备与视觉验证

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；前置：[P1](动态工作流_P1_输入契约与事实承接_a6d3b8f1.plan.md)–[P4](动态工作流_P4_实现与审查独立闭环_d9a6e2c4.plan.md)。
> 本 plan 是原需求 R7 的主 owner，也是 R8 兼容 owner。
> 不重写已完成 R8，不在本 plan 建一套设备租约、权限或多 Agent 系统。

## 1. 问题与层级澄清

原案例的框架问题是“固定 testing 责任逼迫纯 unit 验收制造设备 TC”。
测试是否在设备上运行与验收证明属于哪一层是不同事实：
ohosTest HAP 可以承载 UT；某个 UT 使用设备环境，不自动生成第二次 testing 验收义务。
UT toolchain 的 build/install/device 仍归相应 provider 与授权机制。
R7 的“零设备调用”在该现场应验证为“不额外启动 testing 的设备流水线”，
不能声称连 UT 必要的设备环境也不使用。

当前 acceptance.performance 只有指标等字段，没有明确层级；
原需求正文说“需要真机的性能项”，验收却说“任何 performance 不裁剪”，需在此统一。
当前 R8 已在 main 设备前短路，继续作为计划写偏的兜底。

## 2. business-ut 独立合同

两种合法输入使用同一 UT 核心：

| 输入目标 | 必需内容 | 能声明的结果 |
|---|---|---|
| 完整 Feature/CU 的 unit 义务 | 有效 AC/BD 的 unit/both 分层、代码/测试目标、实际 toolchain | 本次应覆盖验收与边界的证据 |
| 用户只跑/补指定 UT | 明确测试符号/文件/行为目标、预期或现有断言、运行配置 | 指定目标的结果，completion_target=request |

第二种不强制补整份 acceptance；但补写新行为断言时必须有目标依据，不能从实现猜正确结果。
用户明确要求 characterization 可记录现状行为，不能自动成为正式验收的期望语义。
测试报告应区分“执行了哪些现有断言”和“证明了哪些验收”。

use-cases、mock-plan、testability-audit 由实际义务决定：
涉及真实分支/依赖隔离时提供必要内容；只运行现有测试不强制新写 mock-plan。
不能为了省文档跳过 mock 的真实性、边界覆盖、真实符号引用或 provider 运行失败。

## 3. 验证层级与性能合同

AC/BD 继续复用 UtLayer=unit|device|both、isUnitUtLayer/isDeviceUtLayer 与
acceptance_ut_layer_complete；缺失/非法层级不是 unit。
P1/P3 的 typed acceptance 与物理 acceptance 必须经过同一校验。

performance 在现有数组中复用 ut_layer 字段，使用同一枚举（新可选字段，旧数据不强制回写）：

~~~yaml
performance:
  - id: NFR-QUERY-LATENCY
    metric: query_latency_p95
    threshold: "20"
    unit: ms
    description: 已获准的测试负载及指标定义
    ut_layer: unit
~~~

本例仅说明结构，真实阈值与环境必须来自授权验收，不能照抄数字。
ut_layer=device/both 时明确需要的设备环境与 device_focus；
unit 表示能由隔离测试/相应基准证明，不声称可替代真实设备资源与交互指标。
旧 performance 缺层级且没有同源明确证明方法 → unknown，不裁剪 testing；
由 spec 责任方补足判断，不能在 testing 失败后改标 unit。
同一 NFR 在不同文件有冲突层级按 P1 冲突规则处理，不另建 NFR 归属表。

NFR/性能引用解析复用真实 ID 解析，不在 TC→验收提取时过滤掉 NFR。
验证层级、测试环境与 execution channel 分开：
manual 只表示该用例机器执行能力受限，不能消除验收义务，也不能成为 PASS。

## 4. 零设备义务的完整判定

允许 testing 不进入 Feature 执行范围必须同时成立：

1. 当前验收内容有效且覆盖本次范围；可以来自物理产物或 P3 等价投影。
2. AC 与 BD 无 device/both，所需分层全部合法。
3. 无需要设备证明的 performance/NFR；缺性能层级/方法是 unknown。
4. 已消费当前范围所需的蓝图/CU/代码影响事实，没有未解释的用户可见行为设备验证缺口。
5. 无显式设备测试请求、无未满足的当前视觉证据义务。
6. 没有尚待澄清且可能改变上述判定的相关缺口。

合法无蓝图入口只需要该范围适用的真实事实，不为裁剪创建蓝图；
已声明必须消费的蓝图/Graph 不可读则 unknown。
文件属于 UI 或数据库目录都不是决定性证据；机械 UI 改名不自动跑机，
数据库改动若实际影响恢复/UI 刷新等高风险行为，仍需按真实验收决定。

当前事实足以证明“无设备义务”与“没有测试环境”绝不等价。
未知时先补依据，不能先要求空 testing 计划再等它失败。

## 5. device-testing 独立与组合合同

独立请求：显式测试目标、预期结果、可运行目标与需要的环境。
通过 P6 §3.1 的 request-file/report-dir 进入同一 UT/testing checker，先由现有上下文收集
步骤按 P1 §6.1 建立/承接本次 request facts，再执行本次验证。
复用 derive.adhoc-cases 及已有即席实现的用例解析与 provider，归一检查与真实证据；
不借用现有即席脚本的 _adhoc 身份或固定 reportsBase，显式传入本次目标/基线及报告目录，
不要求为单独检查建立蓝图/完整 Feature。
专项目标缺少必要预期/操作语义时报告缺口，不随机生成 TC。

组合请求：消费 P3 验收及当前 scope 必需设备/视觉义务，
TC→AC/BD/NFR→目标→证据必须可解析。
spec 阶段缺席不影响追溯；无可解析验收内容则阻塞，不只记录来源路径。

内部顺序保留：
静态用例/通道/计划契约检查 → 必要 build/install → 设备运行 → trace/结果 → 证据关环。
新 scope 决定是否调用 testing，不绕过 testing 内已适用的安全、执行和证据检查。
本阶段需要的 test-plan/test-report 写真实内容；未进入阶段不产生任何占位文件。

## 6. R8、reconcile-only 与视觉边界

R8 保持当前语义：
非空且全部可解析、全部显式 unit 的 AC/BD、无 NFR/性能引用 → BLOCKER；
混合引用保持 MINOR；空/未知引用由其它契约门处理；
门禁在设备动作前，不能执行“合法子集”，不能用 manual 逃逸。

--report-reconcile-only：
先解析当前调用的有效范围；
若明确没有 testing 义务，不要求 trace/test-report，也不触发 build/install/device；
历史已有报告可以读取诊断，不能覆盖历史 scope 或伪造新 PASS。
若当前确有设备义务，照常核对所需证据；旧 scope 缺失按 P7 legacy 语义。

视觉轴：
fidelity SSOT、参考图、运行时交互与现有视觉 provider 缺失规则保持；
缺 provider/图片/设备不能改判无视觉义务。
本 plan 不改变 applicability.pixel_fidelity 既有定档边界，
但明确视觉请求尚未完成意图解析时，必须先完成相关输入准备，不能借“SSOT 未生成”跳过请求。

## 7. 证据复用与完成

已有 UT/设备证据只有当目标集合、源码/构建、环境与既有 fresh/closure 规则匹配时可复用。
复用范围来自 P2 scope，结果仍从既有 evidence 读取。
P0 runtime fidelity 继续只认机器观察，不用报告文字或旧人工 attestation 替代。

所有失败进入既有归因与回修，scope 不因失败而缩减。
测试执行成功但覆盖不足，对应义务仍未完成。
UT 是末段时，只要其它 required 义务也已被证明，允许 Feature 完成；
不能仅看到 UT PASS 就签发。

## 8. 必须覆盖的反例

| 场景 | 预期 |
|---|---|
| 全 unit AC/BD、无 NFR、充分影响依据 | 不启动 testing；ut 末段可完成 |
| 同上但 UT provider 本身使用 ohosTest HAP | UT 按需使用环境，无额外 testing 调用 |
| 缺 acceptance 文件但有完整合法投影 | 与物理输入同判 |
| 无有效验收来源或层级非法 | unknown/blocked，不能给出零设备结论 |
| device/both BD 但 AC 全 unit | testing 保留 |
| performance 明确 unit 且有证明方法 | 可不安排设备，仍执行所需单元基准 |
| performance 缺层级或需要真机 | unknown 或 testing required |
| 非机械 UI 行为变化存在缺口 | 补设备义务或回设计澄清 |
| 单独运行现有 UT | 无新 mock-plan/整份 acceptance；不冒充 CU 完成 |
| 单独设备任务有明确用例 | 无 spec/plan 历史也可执行，但只报告专项结果 |
| R8 纯 unit / 混合 / NFR / 未知引用 | 与当前护栏语义一致，纯 unit 零 testing 设备动作 |
| 设备离线 / manual / trace failed | 义务存在，不改 N/A、不假 PASS |
| 无 testing 的 reconcile-only | 不要求 trace，不写空 test-report |
| 源码/构建变化后的旧证据 | stale，不复用 |
| 视觉证据缺失 | 保留未完成义务，不被“未定档”旁路吞掉 |
| 无 Feature 的真实 UT CLI | 从 request.tests 到实际 provider、同一 checker 与 reportDir，全程无假 Feature |
| 首次 UT/testing 无 facts | 现有准备步骤建立 request/Feature 实际事实，不要求回 spec/change |
| 活跃 Feature 存在时运行独立 UT | 原 facts/reports/receipt/attestation/events 不被专项输出覆盖 |

## 9. 文件与验证

重点：business-ut/device-testing SKILL 与 contract、check-ut.ts、check-testing.ts、
check-acceptance.ts、acceptance-layering.ts、execution-channel.ts、
测试计划/用例引用解析、相关 reports/verifier、performance 类型与 schema。
P0 runtime 证据完成消费者与 P2/P7 联调，不另写完成算法。

现有测试框架与 fixtures 扩展以上输入，设备调用用已有 provider mock 验证“未启动”，
真实设备效果只由宿主证明。cd harness && npm test 与 npm run openspec:validate 必须通过。
P5 即可尽早向 P7 的真实宿主阶段提供候选，正式默认切换仍由 P7 负责。

父目标 G6/G7：本单元证据与部件组合证据各守边界；
不新增证据库或自动分层 AI 进程。只有真机相关义务才增加对应执行成本。
