    content: >
      **用户确认的 product 由专用机器路径落盘，成为唯一可信的配置来源**。
      review 2 实锤 v3 设计的两个**不可达场景**：原方案要求"local 确认值与 config 现值逐字相等"
      才升级 `explicit_config`，于是——config 无 `preferredProduct` 时用户选任何值都永远不相等；
      config 是错误的 `rom` 时用户选正确值也不相等 → registry 给出"全部候选"实际只有
      "确认原值"能生效。且 t2b 禁止 AI payload 写 `preferredProduct`，plan 里又没有专用 writer。
      改为：
      ① **确认入口**：新增 registry 项 `init.product_selection`（enum，选项＝`listAvailableProducts`
      枚举 + "暂不确认"），**仅在多候选且未确认时出现**——单候选工程零新增交互；
      格式对齐 `skills/reference/confirmation-registry.yaml` schema 2.0
      （id / skill / class / ssot_anchor / skill_step / portable_menu / notes / options[value,label,portable]）；
      ② **专用机器写入路径**（非 AI payload、不走 t2b 白名单）：用户确认后**同时**写
      `framework.config.json > toolchain.preferredProduct = <所选值>`（项目级、可提交、团队共享）
      **与** `framework.local.json > toolchain.productSelection.confirmed = { value, confirmed_at }`
      （本机确认凭证）。两者由同一次操作写入并保证一致；
      **覆写 config 原值是合法的**——这是用户在 registry 里的显式选择，不是静默改写；
      ③ **可信判据**：config 值 **且** local 确认值**逐字相等** → `explicit_config`；
      其余（无 local 记录 / 值不等）→ `legacy_unverified_config`，**不作为可信来源**（见 t5）。
      经 ② 写入后天然相等，故"用户选新值"路径通畅；他人 clone 后 local 无记录 →
      各自确认一次（届时 config 已有值，一次交互即确认该值）；
      ④ **不静默删除**磁盘上来源不明的 `preferredProduct`（配置所有权，与 c9e3f7d1 对
      `analyze: advanced` 的裁定一致）——只是不再当作可信来源；
      ⑤ **local schema 扩展**：`framework-local-config.ts:390` 的
      `LOCAL_TOOLCHAIN_KEYS = new Set(['devEcoStudio','probe'])` 会**拒绝** `productSelection`，
      须扩展该白名单 + 新增叶子键校验（对齐既有 `LOCAL_PROBE_KEYS` 的写法）+ 扩展类型定义；
      写回**必须用 `updateLocalConfig`（`:469`）做无损写回**，不得整体覆盖；
      ⑥ init 的 S1 诊断与 S4 摘要列出：当前 `preferredProduct` 值、确认状态、全部候选。
      unit：(a) config 无值 + 用户选 X → 写盘后 config 与 local 均为 X → 重新加载 →
      resolver 得 `explicit_config`（**生产链验收，非纯函数**）；
      (b) config 为 `rom` + 用户选 `product` → 覆写后一致 → resolver 得 `product`；
      (c) config 有值 + local 无记录 → `legacy_unverified_config`；
      (d) config 有值 + local 记录值不等（用户手改了 config）→ 回落未验证；
      (e) 写 `productSelection` 后 local 其他字段（`devEcoStudio` / `probe`）**逐字不丢**；
      (f) 单候选工程不触发 registry 项。

## 一、"DevEco 能编、framework 编不过"已被证伪

round3 严格控制变量（三样本同起点：Clean → `build_dependency.bat` → `--stop-daemon`）：

→ `--analyze` normal/advanced 无影响；`buildMode` 有无无影响；`rom` 在 DevEco 自己的 UI 里同样编不过。
"DevEco 能过"只对 **product** 成立（round2：同一条 product 命令，`build_dependency.bat` 前 FAILED、后 SUCCESSFUL）。

rom 失败的宿主侧根因（**不在本 plan 范围**）：`hvigorfile.ts` 的 `applyRomHpcOverrides()`

## 二、`preferredProduct: "rom"` 的写入链（t2b/t3 的立项依据）

1. `preferredProduct` 的代码契约写的是"用户显式覆盖渠道"（`hvigor-runner.ts:1075`）；
2. `framework-init/SKILL.md` S2.1 只在**文档层**约束 AI，表格列出的可写字段不含 `toolchain`；
3. **实现无机器约束**：`configWritePayload?: Record<string, unknown>`（任意对象），
   `buildProjectConfigForWrite` 直接 `merged = deepMergeRecords(merged, inputs)`，零字段过滤；
   `specs/framework.config.schema.json:78` 又放行 `preferredProduct` → AI 推断值合法落盘；
4. **来源无法在写盘点区分**（review 1 实锤，`payloadOrigin` 方案作废的依据）：
   `buildInitStagingTemplate`（`init-orchestrate.ts:415`）把磁盘派生结果预填进给 AI 的 staging 模板；
   `deriveContextForExecution`（`:402`）在外部已提供 payload 时直接采用、不再 derive；
   → AI 拿到预填模板、改动任意字段后送回，orchestrator 认不出。
5. 每次 UPDATE 的 `deriveUpdateConfigWritePayload` 原样搬运整个 toolchain
   （`payload.toolchain = JSON.parse(JSON.stringify(existing.toolchain))`）→ 错误值**永久固化**。

→ **init 把一次 AI 推断，升级成了最高优先级的"用户显式覆盖"配置。**
缺 init 当轮 staging/context 日志，**无法还原是哪一轮、哪个 agent 首次写入 `rom`**；
但实现路径已坐实，不依赖该还原。

## 三、UPDATE 的无损性缺陷（t2a 的立项依据，review 2 实锤）

`deriveUpdateConfigWritePayload` 仅保留 9 个字段，`buildProjectConfigForWrite` 对 existing
只补回 3 个；实测宿主 config 有 **13 个顶层键**，`active_workflow` / `lifecycle_hooks_enabled` /
`schema_version` 两侧都不覆盖 → **现状 UPDATE 就会丢字段**。
该缺陷独立于本次事故，但 t2b 的"未变更字段原样保留"以它为前提，故必须先修。

## 四、猜错之后完全不可见，且猜对猜错都可能签发 PASS（t4/t5 的立项依据）

`detectProduct` 的名称启发式按**名字**猜，不按可用性；猜完不验证、不记录来源、不在任何报告里出现。
本次五条编译错误中没有任何线索指向"product 选错了"，agent 只能在源码与依赖里空转——
这是"三轮排查"的直接成因。

更严重的是：**错误 product 若恰好编译成功，framework 会直接签发 PASS**，失败归因提示根本不会出现
——门禁签发的是"错误形态下的通过"。这条决定了 D1 不能靠"失败时提示"兜底，
必须在**选定阶段**就要求可信来源。

## 五、终态判据回归的独立性（t1 的立项依据）

t1 与 product 治理**无因果关系**，只是同一次取证顺带实锤：本次宿主未爆（停在父提交），
但任何**打印非致命 `> hvigor ERROR:` 行的宿主自定义插件**升级后都会中招，
且症状是"构建明明成功却被判失败"，比本次事故更难查。故排在最前、无依赖、可独立合入。

# 裁定（原 D1/D2）

**D1 — 多候选且无可信来源 → `unresolved` 停止，不猜。**
"自动选 + 标记未确认 + 归因声明"被 review 证伪：该方案只在**失败路径**兜底，

"排除 framework 自己的记录"物理上做不到。将来若做须先满足四条前提，另行立项。
