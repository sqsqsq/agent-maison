# 代码库输入顺序指纹修复

## 1. 事实与目标

2026-10-11 在宿主 `D:/1.code/SimulatedWalletForHmos` 的 `bc-openCard-2/bank-card-issue-v2/feature.yaml` 只读复算：两份代码库绑定都是 14 个文件，各文件字节哈希相同，冻结的内容指纹却分别为 `fd03cc81…` 与 `fec226ec…`；按各自 source_refs 的顺序重算可匹配，换顺序即不同。

经真实 resolveCapabilityInputs 读取相同两个宿主源码文件，正序、逆序分别 resolved；带正序冻结绑定读取逆序时，返回 invalid / input binding stale。该报错不是内容变化，也不是设计 owner 能修复的问题，不能靠重新写 spec 或开新 CU 吸收。

目标是：**同一来源、同一源文件集合、同样的字节与身份，无论枚举顺序如何，均被解释成相同输入。** 真实文件增删、内容变化、存在性变化、来源或 role 变化仍触发原失效处理。

## 2. 最小修复边界

- 优先收编 `harness/scripts/utils/capability-resolution.ts` 的 derive.codebase 文件值构造及其共用消费链。按现有路径规范化结果稳定排列文件记录，再使用原指纹算法；候选准备、实际阶段、恢复和独立 request 对相同集合采用同一口径，不能各自加一份排序规则。
- 同一实现分支涉及 derive.test-targets 时，保持同一源文件集合语义并做相称回归；不因此扩成通用输入归一化系统。
- **不修改全局 stableStringify 的数组语义。** verification_steps、ordered_steps、用例调用/分支等有序业务数组不得排序或按集合比较；路径校验、二进制处理、范围与写权限照旧。
- 旧绑定不能仅因采用了新顺序规则就要求重写。复用冻结记录已有的路径、role、exists、sha256 和 source_refs，限定在本类源文件集合内，核对集合与字节完全一致，并按旧记录顺序复算原值指纹；只有能证明是排列差异才沿既有同内容复用路径通过。不得泛化为忽略 content_fingerprint，也不改旧 manifest/事件或增加迁移标志。
- 如果现有读侧已具备上述判据则只补接线。无法证明同内容时保留原 stale/责任诊断，不假定等价。

## 3. 必要验收

| 场景 | 必须观察到的结果 |
|---|---|
| 新绑定：同文件、同字节、顺序互换 | 真实候选与阶段解析获得相同内容指纹，带冻结绑定也 resolved |
| 旧绑定：宿主两种历史顺序 | 原记录不改写，真实消费均能验证；包含本次 14 文件材料，不能只测试排序 helper |
| 内容/集合/来源真实变化 | 改一字节、增删文件、文件消失、role/source 改变均不得因顺序兼容被放过 |
| 共用入口 | 候选准备与恢复/阶段消费采用同一集合口径；request 与同分支 test-targets 不发生反向回归 |
| 有序业务内容 | 验收步骤或用例调用顺序改变仍被原内容校验识别，不因本修复当作相同 |

生产修改运行 typecheck 与直接受影响套件，复用仍有效的其它结果；仓库明确要求的开发/发布门禁按实际改动执行。本次仅创建 plan，不运行测试或操作宿主。
