# 复杂能力建设 3.1：P3 部件组装与覆盖闭环

## 1. 计划定位

P3 位于 P1 部件蓝图和 P2 Change Unit 连续推进之后，负责回答一个更严格的问题：同一部件内的目标、
设计、施工、执行与证据是否已经真实组装为闭环，而不是仅有若干各自全绿的 Feature。它消费既有权威，
机械派生 Component closure 和剩余缺口，不反向拥有蓝图、ready set、Feature completion 或恢复事实。

本 plan 与 OpenSpec change `component-assembly-and-coverage-closure` 成对。当前批次只冻结设计、规格、
实施清单与真实宿主入口，不实施 P3 生产代码、不勾选 todo，也不进入跨部件 Capability E2E closure。

## 2. 权威输入、输出与消费者

权威输入：

1. 复杂能力总纲，重点 §6.1、§6.5、§6.6、§9.2、§9.4、§11.2、§11.3、§14 和 §15；
2. 3.1 总计划 §6.4、§9、§11–§13；
3. P0 元模型的单向引用、权威分位、Provider/Consumer/Definition 和三命名空间契约；
4. P1 current-scope 原始需求/目标/不变量/高风险来源清单、canonical component blueprint、稳定地址、
   跨视图/runtime 完整性、准入及 revision/fingerprint；
5. P2 canonical CU、确定性 Feature identity、ID-only 施工映射、exact dependency、四态 completion、
   carry-forward 与现有 Goal Mode 执行事实；
6. 既有 Feature plan/contracts/acceptance/use-cases、实现和 canonical reports/receipts/evidence。

唯一新输出是 component-owned、可删除重建的 `component-closure@1` YAML 及其单向派生 Markdown 评审视图。
下游可消费 loader 返回的 component/blueprint/input/artifact identity，但不得把 projection 当执行账本或跨部件
完成事实。

## 3. 权威边界

| 事实 | 权威 | P3 行为 |
|---|---|---|
| 当前范围需求、目标、不变量和高风险 | P1 discovery traceability 绑定的原始来源与稳定蓝图映射 | 校验来源和闭集，派生 source obligation，不解释任意 PRD prose |
| 当前/目标设计、视图、关系、flow、decision、contract | P1 canonical blueprint | 解析、派生 obligation、检测未消费或冲突，不改写 |
| CU 定义、依赖、设计引用、Feature identity | P2 canonical CU | 校验并聚合，不重定义 predicate/provide/design |
| Feature 施工映射与运行时施工事实 | 既有 Feature artifacts，尤其 `contracts.state_management` | 复用既有 consumer gate，不复制 runtime 细节 |
| 执行、恢复、completion 与 evidence | Goal Mode events/reducer/receipt/evidence 和 completion verifier | 观察四态，不写入或降级历史事实 |
| Component closure verdict/gaps | P3 稳定聚合规则 | 从精确输入重算；provider 和作者不能直接设置 |
| 稳定工程知识 | architecture/catalog/conventions/spec/scenarios/ADR 等既有真源 | 只验证稳定 ref 已归位，不复制正文 |

## 4. Canonical projection 与输入绑定

正式路径固定为：

```text
blueprint/component/<component_id>/component-closure.yaml
blueprint/component/<component_id>/component-closure.md
```

YAML 根对象为 `component-closure@1`。路径、`component_id`、target=blueprint 的完整
`component_blueprint_ref` 必须一致；loader 对原始字节计算 `artifact_sha256`。`input_fingerprint` 由排序后的
P1 current-scope traceability/source revision/hash、蓝图/CU 原始 hash、Feature identity、contracts/acceptance、
completion/carry-forward、可信 evidence/receipt 及影响裁决的 provider observation identity 计算，时间戳和
Markdown 不参与。旧 fingerprint、遗漏输入或 authored verdict 与重算结果不一致均失败。

P1 `source_fingerprint` 只从规范化 discovery facts、`current_scope_items` 及其 source/provenance/revision/hash
重算，不包含 requirement→blueprint mappings。mapping 仍严格校验，但变化由 blueprint revision、原始
`artifact_sha256` 和上述 P3 `input_fingerprint` 捕获；不新增 `traceability_fingerprint` 或其它状态。

稳定内核先校验 `discovery.inputs.current_scope_items` 中每个 current-scope
`requirement|goal|invariant|high_risk` 的稳定 ID、project-safe 可解析来源、可得 revision/hash，并要求
`discovery.requirement_traceability` 以相同 ID 双向一一覆盖且提供至少一个同蓝图真实 stable-address mapping，
再只枚举同一 component 下的 canonical `change-units/*.yaml`。来源或 mapping 无法解析即 blocker；不建设
通用 PRD 解析器、source registry 或可替换
collector Provider。独立 Feature、外部 component、无蓝图 CU、任意 legacy 文件或目录扫描猜测不得进入。精确
`supersedes` 可以退休旧 CU 的当前责任；`revises` 不能。冲突、hash 不匹配和环 fail-closed，首期不建设迁移表或
semantic diff。

## 5. Completion、carry-forward 与当前集合

当前蓝图 identity 上的 CU 必须通过 P2 设计/施工映射门并观察为 `VALID`。历史蓝图上的完成 CU 仅在 P2
carry-forward 对其全部 stable target 判定 allowed 时贡献覆盖；`ABSENT`、`STALE`、`INVALID` 分别形成未完成、
重派生/重执行和证据修复路由。P3 不修改 CU revision、ready set、completion 或历史 identity。

## 6. Obligation 与 coverage 模型

obligation id 由 authority artifact identity、kind 和稳定 local address/id 机械生成。来源闭集包括：

- P1 discovery 中每个当前范围 requirement/goal/invariant/high-risk 的 source identity 与全部 blueprint mappings；
- P1 当前目标/delta、适用视图节点、跨视图关系、关键 scenario、条件式 runtime flow/edge、decision、contract、
  NFR、当前相关 gap 与 validation ref；
- P2 target predicate、invariant、touch、provide/require、safe state、verification ref 与 blocker；
- Feature acceptance、ID-only construction mapping、`contracts.state_management`、条件式 use-case/DAG 义务和
  completion 所绑定的 phase/evidence；
- 组合层跨 CU 调用/数据/状态/发布边、迁移/兼容/回滚/flag/双写/临时资产、剩余风险与知识归位。

稳定内核从 requirement→blueprint mappings、stable relation/flow、CU design/dependency refs、确定性 Feature
identity/mapping、分层义务与 canonical evidence identity 唯一派生每个 coverage row 的单 CU/组合 owner、施工
mapping、evidence level/identity 和 observation。YAML 只物化结果，checker 逐字段重算；无法唯一派生就返回
P1/P2/Feature 修复，closure 内不允许人工补选。纯当前态且本次未改变的节点只需权威事实证据，不强造 CU；
不影响当前 closure 的远期 gap 保持带 owner/needed-by 的 non-blocking frontier。

## 7. 适配 4+1 与跨视图闭环

P3 既复用 P1 的结构一致性，也验证设计真的被 P2/Feature 消费。每个影响目标态/delta 的适用节点和关系必须有
CU/组合 owner；scenario 要贯穿 logical 对象/契约、runtime 交互、development owner，跨运行边界时还要有
deployment 映射。runtime relation 必须回到 logical contract 与 development mapping，development module 必须有
design basis；术语、契约版本、state owner 和 failure semantics 跨蓝图、CU、Feature 与证据不得冲突。

蓝图已有设计却无施工消费是 design bypass；CU/Feature 引入共同设计却无当前蓝图权威同样失败。修复路由回 P1
调和或 P2/Feature mapping，不由 closure 改蓝图。

## 8. Runtime 数据流与组合证明

每个当前 `flow_id` 按实际行为条件式派生 trigger、initial load、state owner、mutation、
publication/invalidation、subscription、consumer、failure/recovery 义务。只读流不伪造 mutation 或 subscription；
但已存在的 mutation 必须追到 persistence/recovery 与 publication，publication 必须到全部受影响 consumer，
subscription 必须证明 snapshot/replay/order/cleanup，consumer 必须证明 initial load、update source 和可观察刷新。

若 producer、owner、consumer、recovery 或生命周期行为跨多个 CU/Feature，则额外生成 combination obligation，
要求一个贯穿真实组装路径的 scenario/use-case/integration/UI/device observation。各 Feature 单独 `VALID` 不能替代。

## 9. Dependency、迁移、NFR 与临时资产

requires/provides 继续使用 P2 exact dependency 规则，只有当前 `VALID` 或合法 carry-forward provider 可满足依赖。
新跨 CU 调用、数据、状态和发布边仍需真实组合验证，名称匹配不等于闭环。

迁移、兼容、回滚、feature flag、双写、受控 fake、临时 adapter/asset、NFR 和剩余风险必须由结构化权威事实
派生，并有 disposition、owner、needed-by/gate 与 verification 或 knowledge ref。缺失即精确 gap；不从 prose 或
“未出现”猜 PASS。

## 10. 宿主演进接缝

P1 把 evolution candidate 的 `human_decision` 冻结为 `establish_seam|keep_direct`。只有 resolver 同时确认
`kind=evolution_candidate`、`status=decided_with_authority`、`human_decision=establish_seam` 的 decision 才进入
P2 接缝纵切和 P3 接缝闭环；`keep_direct` 保留再提取条件但只走普通 CU/dependency/coverage 规则。对明确建缝项
验证四件事：

1. operation/DTO/mapping/error/NFR 契约兼容；
2. 新增或替换 Provider 时既有 Consumer contract binding 不变；
3. Provider 缺失/失败符合 `degrade|disable|block|fail_closed` 裁决；
4. Consumer implementation/dependency 未绕过稳定契约直连具体 Provider。

普通 decision 和 `keep_direct` 不被推断为 seam。若契约或 Consumer 必须变化，返回 P1 调和、版本化或迁移缺口，
不增加 provider registry。

## 11. Verdict、gap 与团队评审视图

稳定聚合器只输出：

- `PASS`：所有 required obligation 被 current/valid 事实覆盖且无 degradation；
- `PASS_WITH_DEGRADATION`：required obligation 全覆盖，仅有不影响当前声明的 optional provider 缺失，且影响、
  owner、retrigger 明确；
- `FAIL`：存在 uncovered obligation、blocker、stale/invalid、权威冲突、required provider 缺失或未接受风险。

gap 仅是结构化报告，分类为 `incomplete|blocked|stale|invalid|conflict`，带 source/obligation、owner、needed-by、
reason、unlock 和 repair route，不形成状态机。Markdown 在评审前由已校验 YAML 单向生成，完整展示输入、覆盖、
跨视图/runtime/assembly/seam、degradation、gap、owner、route 与 knowledge refs，不能反向参与裁决。

## 12. Provider seam 与生命周期

P3 稳定部分是 canonical input enumeration、输入绑定、obligation/完整 row derivation 与最终 verdict；input
collector 不是 Provider。静态 provider 只把稳定内核已选定的既有证据转成 provider-neutral observation。三张证据
Seam Card 的 Definition、Consumer、Provider、required/optional、缺失、替换、退出、冲突和权威来源由 capability
spec 表格唯一冻结，本 plan 不复制第二份规则。

required provider/层级缺失形成 blocker；optional 缺失仅在其维度没有 required obligation 时诚实降级。重复权威、
同 evidence identity 冲突或 observation hash 不符均 fail-closed。provider 退出只清理临时 observation/cache 并使
projection stale；正式蓝图、CU、Feature、receipt/evidence 保留。

## 13. 实施顺序与边界

后续实施按 OpenSpec `tasks.md` 顺序：先收紧 P1 traceability/evolution 与 P2 seam 判定，再做 artifact/input binding、
obligation/coverage、completion/evidence，随后
cross-view/runtime、dependency/migration/seam、verdict/projection/Skill，最后补完整反例和门禁。实现应复用现有
YAML/schema/hash、P1 stable resolver、P2 loader/dependency/completion/carry-forward、Feature consumer gate 与 Goal Mode
verifier。

明确不做：registry、执行账本、checkpoint、锁、daemon、动态插件运行时、通用 evidence/ref 系统、semantic diff、
新恢复目录、P2 ready 写回、五视图完成台账或 Capability E2E closure。

## 14. 验收与反例

P3 framework 完成至少证明：

- 完整多 CU fixture 可由相同输入确定性重建 closure；
- 从 current-scope input 清单中漏映射一项，或删除/破坏原始需求来源、蓝图 mapping、目标/设计 owner、契约
  provider、施工 mapping、分层 evidence、迁移收口或组合结果即失败并定位；
- 调换到另一个有效 CU owner，或用无关但通过的 evidence 冒充覆盖，完整 row 对账必须失败；
- 蓝图设计未被 CU 消费、CU 绕过共同设计、跨视图关系断裂或语义冲突不能被单元绿灯掩盖；
- runtime 分别删除 initial load、写后传播、晚订阅 snapshot、后台 persistence/recovery、subscription cleanup、
  state owner 或 consumer refresh 时定位到稳定 flow；
- read-only flow 不被迫伪造 mutation/publication/subscription；
- evolution seam 的兼容、替换、缺失/失败和绕过四证明有正反例，`keep_direct` 与 ordinary decision 不被误挡；
- required provider 缺失阻塞，optional 缺失只产生有边界 degradation，冲突权威确定性失败；
- projection 不修改 P1/P2/Feature/Goal Mode 事实，也不宣称跨部件完成。

实施验收运行 P3 专项、受影响 typecheck、完整 harness、OpenSpec strict validate、default plan scan 和
`git diff --check`。整仓 `--release` 与 `npm run release:verify` 保留给总计划 m5/MG，在实际运行前不宣称通过。

## 15. 真实宿主入口

AI 记账 App 需要提供真实当前蓝图、多个具有依赖和运行传播的 CU、对应 Feature completion、构建/运行/恢复结果，
以及当前 obligation 所要求的 UI/device/manual 证据。宿主验证应覆盖至少一条跨 CU 数据流和一个批准的演进接缝。
材料未到位时，P3 只可报告 framework 机械 readiness 与缺失材料，不制造语义 PASS。

## 16. 待决点与本轮停止条件

实施前仍需由真实宿主事实决定：

1. AI 记账多 CU、运行/恢复及界面材料何时齐备；
2. c2 视觉/真机 provider 在首批宿主中是否可用，以及蓝图/acceptance 是否把对应层级列为 required；
3. 每项稳定结论按既有职责归入 architecture、catalog、conventions、长期 spec/scenario 或 ADR 的具体位置。

这些待决点不改变 framework 的机械契约；缺材料时只形成 blocker/degradation，不发明新权威。本轮在 plan 与
OpenSpec 四件套通过静态校验后停止，等待 review，不开始 P3 实施、不勾选任何 todo。
