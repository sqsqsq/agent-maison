# A：统一前门、四档规则与直接修改

## 1. 目标、边界与实施依赖

用户目标：所有改产品的需求默认先进Maison；只有用户明确“不走Maison”才豁免。特别简单/小型/中型/复杂由统一规则计算，用户可升可降；流程投入不能使需求开发比当前更慢。判档在建蓝图之前，外框决定蓝图、CU、独立质询、评审文档，框内按真实缺口和证据安排工作。

本计划与[B：短蓝图与CU映射收编](需求设计按规模减负_短蓝图与CU映射收编_c8d6f1a3.plan.md)一次起草、联合检视。当前仅起草和修订计划，不实施、不提交、不打包、不更改宿主或设备。

实施必须同时满足：用户另行通知开工；[72b6f0d9](../goals/持续执行与单一完成闭环_原生会话及证据同源重构_72b6f0d9.goal.md)对应[P4](持续执行重构P4_全链验收与宿主真实交付_9b52d6f0.plan.md)的`p4-t5-clean-host-delivery`、`p4-t6-joint-evidence-close`已按真实证据收口；[3f8a6c21](持续执行现场收口_恢复承接与独立复审_3f8a6c21.plan.md)全部职责及既有检视已收口。起草和检视不受此实施顺序限制。A完整实施并通过开发验收后再实施B；两批内部一次做完、统一验收，不设人为中途确认停点。A不单独上业务宿主，联合验收在B统一进行。

起草快照为`bd06421c`及当前未提交工作区，不能把在途改动当成本批成果；实施前核对上述前置实际最终代码。文本中的文件定位用于查找责任接缝，不依赖历史行号。

消费者始终使用Maison发布件集成到`framework/`。不恢复lite轨，不新增Goal、入口注册表、请求账本、平行manifest或场外状态。不以本次需求授权提交、发布、安装客户端插件或操作真实设备。

## 3. 唯一规则与判例

### 3.1 规则来源、事实与判断方向

将用户可读规则及判例集中写入现有`docs/operations/project-entry.md`；机器谓词在现有`execution-scope.ts`邻近接线，所有adapter引用相同规则，不各自维护档位表。四档是同一流程的外框结果，不是四套执行器。机器结果与文档判例由同组输入/输出测试锁定。

Agent提供语义事实和原文/源码依据；工具读取路径、模块、配置键、实际导出和diff；规则决定结果。未知不是“否”，缺依据不是已验证。禁止仅接受Agent填入的档位名作为机器裁决，也不要求用户填表。

用户原稿第二问使用“能否闭合”的正向问法，但同时规定“三问任一是即中型”与三个非中型锚点；本计划按锚点统一为风险方向，语义不变：

| 风险问 | 是的判据 | 否的判据/必要反例 |
|---|---|---|
| Q1：有影响用户或其它模块的实质设计取舍吗？ | 至少两种合理做法，选择影响用户结果或其它模块契约；新页面交互需设计也属于此类 | 无此取舍；只影响本模块内部实现的局部选择不计Q1 |
| Q2：影响是否无法在本次改动内闭合并由适用机器验证覆盖？ | 有仓外消费者；不能在本次同步全部受影响调用方；或没有足以证明该闭合的适用验证 | 消费者可定位且均在仓内，本次同步，编译/静态检查或相应自动测试能证明关联未漏。不能仅因编译绿就推定反射、字符串路由、数据语义已验证 |
| Q3：是否包含不可逆的存量变换？ | 修改/删除既有数据、字段类型转换、需要回填存量数据等 | 不重写既有值、兼容的新增默认列；只改声明且真实兼容验证可成立 |

复杂优先：存在多个可独立交付、独立验证的结果，且有真实依赖、共享决策或分批落地要求；或跨部件。模块数量不等于部件数量；部件从现有catalog/蓝图归属读取。其次三问任一“是”为中型。三问全“否”时：预期可逐条检验且能指明来源、做法唯一→特别简单；预期待补明确或仅有模块内部局部选择→小型。不按行数/文件数定档。

未知只补影响当前选择的事实，复用已有调研，不另开分类模型会话、不因一个未知把全单永久升档。调查期间可以读取/定位；缺少会影响正确实现的预期或设计，先补对应缺口再做依赖它的修改。

### 3.2 用户指定、双向调整与完成口径

优先级：用户明确指定的流程/验证范围 > 规则自动推荐。原始输入保留，不能用模型转述替代。用户可升档、降档、指定略去某项验证；说明实际范围一次即可，之后不重复争论，也不因新自动推荐偷偷恢复被用户排除的流程。

用户只说“按小型”而未排除专项验证时，§6内容专项照常适用；用户同时明确限制验证时，未执行项如实披露，不冒充PASS或完整验证。未改变的真实产品失败仍是失败。真实秘密、不可逆外部动作、权限和用户硬预算不因流程选择而扩大。

无用户固定选择时，只有可核对的新依据或对原错误事实的有据纠正才可双向重算；自然语言换说法、删除负面结果、临时改任务名均不算新依据。已有满足证明复用，只修订受影响的未执行工作；不推倒已写代码，不洗掉原检查失败。

### 3.3 外框结果（A负责规则，B负责轻设计落地）

| 结果 | 蓝图 | CU/准入 | 独立设计质询 | 评审文档 |
|---|---|---|---|---|
| 特别简单 | 无新增设计文件 | 无 | 无 | 无 |
| 小型 | 同协议短蓝图 | 不拆CU、不走CU准入 | 无 | 无独立评审投影 |
| 中型 | 适用视图与必要决定完整 | 单CU，沿原准入 | 有，复用有效结论、只核真实变化 | 原评审投影 |
| 复杂 | 共享蓝图 | 多CU及依赖；各自按义务施工 | 有，按共享与各单元责任 | 原评审投影及必要组合说明 |

蓝图、CU、质询、文档也是规则输出，不留给Agent任选。外框不等于固定`spec→plan→coding→review→ut→testing`；验收与设计缺口可在同一次作者工作中补齐，阶段只选择方法/检查族。小型不以“所有接口/路由/持久化都未变”为前提，必须容纳以下锚点；对应专项验证与设计深度正交。

| 两个已有页面之间新增明确的A→B跳转 | 特别简单；仅局部选择时小型 | 既有交互无新取舍；真实路由专项，不因触及路由文件升档 |

## 4. 前门输入、豁免与零额外判档步骤

### 4.1 本次请求是最小作用域

建议默认豁免仅作用于当前独立请求（含该请求的续作），新请求恢复Maison默认。用户明确“本会话都不走”时才扩大到原生会话范围，撤销后立即恢复；新会话不继承未经用户说明的豁免。理由：既尊重明确持续指令，也不把一次临时选择变成所有后续任务的隐藏开关。本建议随两份plan交用户审阅，未获实施通知不改变现行行为。

豁免必须读取原生会话中真实`user`消息的原文、消息定位和本次请求边界；文件、网页、日志、引用代码块里的话及assistant“用户已同意”均不授豁免。含糊、否定或仅讨论“不走Maison”的话不自动豁免，继续正常入口，不额外追问以制造停点。支持日常明确表达，不要求用户学专用slash。跨会话恢复沿原请求原件；无法核实来源不伪称豁免。

### 4.2 已有会话原件承载，不建前门票据

前门不是新CLI。根指令、已物化常驻规则和现有Skill跳板共同指向`project-entry.md`；首轮正常调研完整消费本次适用规则，首次修改前一句话说明结果及依据。允许普通自然语言表达，不新增人工JSON/表单，不另派判档Agent。

原生会话reader读取用户消息、已发生的规则读取、工具实际读到的源码/配置以及首次调研结论；在内存规范化已有request输入，保留来源定位。确定的路径、模块、配置键等由工具核实；语义事实沿Agent本轮带来源的调研判断，不能把来源可定位误称其语义已被机器证明。

**请求边界的职责**：原生消息id/turn是机械边界，“继续原任务”还是“新独立需求”由接任务的Agent在原正常推理中解释，给出原始user消息定位，后续沿已有request/Goal原件续接；不在hook里另调模型猜测。hook只保证会话中前门规则已加载，不能保证每个语义新请求都重新判档。默认本请求豁免的解释由原入口负责，首次compile/request再次核对来源及所指请求；无法据原文支持的豁免不被机器采信。会话级豁免只有真实user明确指定才可机械复用。此边界纳入A2/A4，不把会话级钩子声称为逐请求语义强制器。

必须区分：前门已消费、Agent按统一规则给出的初判、机器按可用事实算出的结果、专项验收通过。首句是解释，不作为伪造机器判定凭证。已有hook能读取上述原件时，在同次原生hook内调用纯规则；其它客户端在首次已有编译/request调用中完成机器核对，说明其写前等级只能依赖指引。仅把档位名读出来不算机器判档。语义归一无法唯一完成时保留具体unknown，使用同一作者已有调研补充，不能另开分类模型或因格式小错要求用户填表。

结果需要跨调用复用时，定位到原生transcript/已有request或Goal原件；机器输出写入本来就会产生的request报告/运行输入，只有已有载体才扩其上下文，不为特别简单新建Feature、run或状态文件。`~/.maison`不增加任何类型；不能靠全局`entered=true`冒充支持。

**原件定位生产者→消费者**：adapter的原生事件payload提供transcript路径、session id和当前用户消息/turn定位；在已有hook返回的原生上下文中附这组非秘密定位，支持原生环境传递时直接传递。compile/request增加同一可选`--session-ref`定位参数，由入口从这份原生定位复制到本来要执行的命令，不增调用、不让Agent制造JSON。参数只是定位，reader必须核原件session、工作目录和角色；路径/文件存在不代表可信用户。原生会话有自身session/thread环境变量时优先直接解析，只在该session的已知存储范围定位，不扫描其它用户会话。

| adapter来源 | CLI承接与必须实测内容 |
|---|---|
| Claude Code / CodeAgent | 从本机真实hook payload取得transcript/session标识，沿原生上下文或环境交给既有命令；分别实测fork字段与事件格式，不能只写候选环境变量名 |
| Cursor | 从实际hook payload取得conversation/transcript定位；验证人读/结构化日志是否同时保留用户角色、消息时间和编辑目标；能消费的字段才接入reader |
| Codex Desktop | 优先实际thread/session环境及受支持的原生会话记录；hook可用时同上，不可用仍测该定位能否由已有会话工具/环境传给CLI；Desktop和CLI分开给结论 |
| 没有可用原生原件的adapter | 编译仍可按项目能力执行，局部显式目标检查也可执行；不得把模型转述当豁免/固定档位来源，不能签完整diff已对账或完整review PASS。短蓝图只报结构可解析、档位未核。A8必须标此能力缺口，不能把这种降级当小型全链通过 |

规范化结果由同一自动request writer写入`reportDir`的原request JSON：原用户输入/定位、请求边界解释及依据、精确base/head与初始dirty归属、规则事实及来源、用户覆盖与派生外框。B只消费此正式输入及原件绑定，不另靠一句档位文本选short分支。语义边界仍由Agent解释并可纠正，机器只核可核对的原件关系，不宣称能从任意自然语言确定任务身份。

### 4.3 基线与既有修改

起始提交优先取首轮已有仓库调查/原生hook实际取得且留在原生会话中的HEAD；没有直接捕获时，以已定位原始user消息的开始时间查询当前worktree的HEAD reflog，只有历史连续、时间能唯一定位且Git对象仍存在时才重建起始HEAD；同秒多次移动、reflog缺失/过期或分支归属不清时保持unknown，不能简单拿当前HEAD代替。没有中途移动也须有覆盖开始时刻的reflog依据，不能把“没读到记录”当“没有移动”。首轮常规git调查可在同一已有调用里附HEAD/dirty信息，不增判档命令。

本次候选改动集由可读原生编辑工具的真实目标与该精确起始提交到当前工作区的diff共同取得；删除、重命名、未跟踪文件沿原diff parser处理。与本请求编辑目标及显式范围无关的初始dirty不纳入；重叠且无可恢复前像的部分标归属unknown。Shell写入只能由diff补发现；没有写事件不证明没改，也不能据此吞掉用户旧修改。初始dirty前像优先复用原生读取/工具结果，不新增全仓副本或状态库。

同一请求内不因提交、恢复或返修重置基线。初始dirty且与本次目标重叠时，按已有前像/当前内容核本次变化；无法隔离则明确归属unknown，保留文件并只请求真正缺失的信息，不把用户旧改动算成本次或替其清理。无Git工程沿既有显式目标输入，不能伪造提交；缺起始依据时不得签“全部修改已对账”。

## 5. 前门拦截与adapter边界

只在支持的产品文件编辑写入前核“本原生会话可消费的上下文中是否已有前门规则”，不新增“碰敏感文件/第二模块就必须中型”的文件锁。未加载则拒绝当前写入并给一行可执行恢复提示：读根入口及`project-entry.md`、沿原请求继续；不要求用户重发需求或安装新框架。允许正常研究读取；框架文件继续先受原只读边界保护。

产品路径取现有catalog/config的源码、资源、产品构建/运行配置及本次明确产品目标。按解析后的实际路径排除Maison蓝图、报告、run、开发文档和客户端配置目录；不能一概排除所有`doc/`（宿主可能把产品内容放在那里）。framework路径始终先交原写保护，非产品写入不触发前门拦截。未分类的新产品目标先沿原请求/现有路径解析补定位，不新增路径注册表。

判断以同一原生会话最近压缩后的规则加载/原件阅读为依据，不能用别的会话或assistant自称替代；若原生压缩明确保留已加载指令则复用该记录，不为压缩重复补读。被拒绝后补读即恢复，既有成果保留。普通“继续”不会单因新增一条user消息再被拒绝。同会话新请求的判档由根入口处理，hook不尝试语义分辨。明确本会话豁免可沿真实user原文及撤销消息复用；仅本请求豁免只在其已有请求关联可核实时采用，不把一句旧豁免扩成整会话。无关联的续作由正常入口承接/解释，不声称hook能独自证明豁免仍适用。

Maison派出的作者沿现有`hasGoalExecutionSignal()`同源语义识别（现有RUN_ID、ATTEMPT、ATTEMPT_PHASE、HEADLESS信号并集），不只认`MAISON_GOAL_HEADLESS=1`。Cursor工具子进程丢HEADLESS但保留运行/attempt信号的既有场景须正常放行。JS hook壳需要共享时提取原小谓词供两侧调用，不复制出另一套判据。这只豁免重复入口，不解除framework写保护、工作单元授权和真实完成核验；合作标记不声称抵抗任意Shell伪造，不新增令牌或身份层。

| adapter | 实施接点与验证 |
|---|---|
| Claude Code | 已有PreToolUse编辑matcher、settings与hook壳，读取真实payload/transcript，不覆盖宿主其它hooks |
| CodeAgent | 沿`.cac`已有同族壳，实际验证变量与transcript字段，不凭Claude支持推定fork支持 |
| Cursor | 沿现有`hooks_config`结构化合并，复用写守卫壳；实际验证编辑工具名、用户消息和规则读取原件能否取得 |
| Codex | 当前Maison adapter未物化前门hook。官方文档已支持项目`.codex/hooks.json`/inline hooks及信任要求；实施时用临时工程实际测Desktop的加载、信任、事件、拒绝与恢复。仅CLI测试不代Desktop。可用则经adapter原有物化接缝加入；不可用/无法取证则常驻规则＋事后核对，明确较弱边界 |
| 其它adapter | 同源根入口及原生资料读取；只有真实证明的hook能力才声称写前拦截；其余后验路径 |

官方资料（2026-11-11查阅）：[OpenAI Hooks](https://learn.chatgpt.com/docs/hooks)。项目受信任、hook定义获原生批准才执行；不自动跳过信任、不修改用户全局配置。环境缺失与未获安装授权如实记录；不可把未测伪写成不支持。

Shell重定向、脚本、场外进程及未覆盖编辑工具为明确盲区；后验只能核对进入编译/检查的调用，不能保证完全绕过框架且不再调用检查的会话被发现。本计划提供已接入客户端的默认与合作式拦截，不承诺任意客户端强隔离。能力结果记在现有adapter文档/验证结果，不另建注册表。

## 6. 实际内容变化与专项义务

### 6.1 输入和适用性

复用`git-diff.ts`、`diff-scope.ts`、catalog/config及已有profile解析。比较本请求基线与最终实际内容，过滤未触及的历史改动；路径只负责候选定位。内容改变才产生专项事实，注释/排版不触发接口、权限或支付逻辑检查。动态/解析不支持时保留unknown，交原作者带依据判断，不能仅凭AST未找到就判无影响。

| 内容 | 机器可做部分 | 语义/能力边界与必须得到的证据 |
|---|---|---|
| 路由、权限、依赖JSON/JSON5 | 经原解析器比较实际键值、目标、参数与许可项；忽略键顺序和注释 | 路由在代码里或权限由业务条件实现时不能宣称配置覆盖全部；补相关跳转/权限回归。依赖校验沿原架构规则 |
| 导出签名/接口 | 评估并复用`component-assets.ts`所调profile导出抽取和`ast-analyzer.ts`；在共享抽取器补真实导出名、参数/返回和重导出关系的前后差异 | 组件清单不是完整API解析器；动态导出、反射、仓外消费者明确保留边界，不新建平行索引。确认仓内调用同步及实际兼容验证 |
| 持久化 | schema/配置键变化可检测，源码字段可给候选 | 默认值是否兼容、字段含义/回填/既有值是否改变由Agent引用schema、迁移和读写代码回答；用存量数据样本/既有测试验证升级，不只看编译 |
| 金额、幂等及数据正确性修复 | diff定位、已有用例和验收来源可绑定 | 识别真实行为由作者/相关检查承担；轻量档仍须执行能验证修复的针对性用例，除非用户明确排除且如实不作完整验证声明 |
| 新增影响面 | 复用实际修改文件与catalog归属、调用方依据 | 只补新增相关范围，不因模块数量升级、不无条件重做全仓调研 |

专项是各档均适用的义务，档位不是豁免。已有等价检查/有效证据可复用；“内容未变”只免本专项，不取消用户明确要求的验证。

### 6.2 接入现有编译/检查而非新增对账步骤

在原compile/request/harness入口准备上下文时统一调用差异派生，补进已有义务及结果；没有独立对账CLI或新模型调用。发现漏判时由原作者处理具体设计/验证缺口，保留代码、原请求和有效结果。编译命令只报告编译及其实际检查，需review/UT/真机时返回既有可执行下一步并由原入口持续完成，不能把编译绿当作专项已跑。

用户固定档位时不自动加重外框；用户明确限制验证时只说明新增影响与未执行项。未限制验证的自动任务补上适用专项。若返修再改变相关输入，仅更新该受影响事实与验证，不重做整轮判档。收口消费最终diff和最新有效结果，保留此前真实FAIL；新内容修复后才能由原检查核销。

## 7. 直接修改的能力入口

特别简单直接修改后走Maison compile；review、UT、真机可按用户请求或专项义务直接调用。沿现有compile CLI、request CLI加自动准备路径：从原请求、原生调查结果、实际修改、开始提交和可用蓝图输入生成同一request schema，Agent不手写JSON、不拼harness内部脚本。已有显式request-file保持兼容；自动与显式请求用同一parser/provider/报告，不新增通用执行器。

请求文件若执行器确需落盘，由原writer放已有`reportDir`内，或复用现有project request位置；它是执行派生件，不是与蓝图并列的设计产物。原request JSON同时保存本请求所需的真实用户原文及原生出处，特别简单的针对性UT可用该JSON的项目相对路径作为预期来源，不能只有一个未核实AC标签。只复制本请求所需内容，不导出整段会话。运行恢复读原请求与基线，不每次生成一个新任务。目标、测试载体和允许写入均由原prepare规则确认，不能用假Feature号绕行。UT首次写入之前仍完成载体准备，但把准备并入首次既有能力调用；没有载体时在本授权内补齐或准确说明缺口。

架构检查从`check-coding.ts`复用依赖方向、跨模块经出口等纯检查；为无Feature直接修改提供项目根、实际文件、catalog/architecture输入，在现有compile/request入口可单独选择调用。只提取判据与上下文适配，不把Feature专有的蓝图、CU、scope文档等前置连带搬入；原Feature调用也使用提取后的同一实现。已配置架构时直接修改也执行相关检查，不能因轻量而失去原约束。

review/UT/testing的预期来源：特别简单消费原始需求及现有有效行为来源；小型在B后消费短蓝图验收。旧行为断言测试随本次修改更新；在途需求的验收/契约变化走该需求既有修正入口，不把正式运行切成独立request绕过职责。已完成需求蓝图作为历史施工图保留，不为每次小修改重写；源码与当前测试是本次核对材料。
