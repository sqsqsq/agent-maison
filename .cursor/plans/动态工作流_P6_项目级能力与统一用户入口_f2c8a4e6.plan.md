# P6：项目级能力与统一入口

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；前置：[P1](动态工作流_P1_输入契约与事实承接_a6d3b8f1.plan.md)、[P2](动态工作流_P2_执行范围与运行时统一编排_b7e4c9a2.plan.md)。
> 完整 Feature 联调消费 [P3](动态工作流_P3_需求设计与蓝图施工投影_c8f5d1b3.plan.md)–[P5](动态工作流_P5_单元与设备验证按义务执行_e1b7f3d5.plan.md)。
> 本 plan 覆盖全部现有 project Skill 与 global phase；不承担新平台 lens 或宿主 SDK 开发。

## 1. 背景

仅改 Feature 六阶段仍留下项目级固定仪式：
init 后可能被误解为必须 bootstrap 所有知识；Graph 可能因缺 catalog 被要求先做全工程画像；
用户只查看蓝图可能被误推进到 CU/施工；公开 Skill 与 phase 不是严格一一对应。

现有 component-design 已按请求区分查看、质询、调和、设计准备和完整交接，
可作为本次复用基础。不能把它重新改成每次从第 0 步全跑。

## 2. 全覆盖输入/输出合同

| 既有入口 | 最小适用输入 | 必要结果 | 禁止隐式追加 |
|---|---|---|---|
| framework-init / init | 显式接入或更新意图、Maison 发布件、宿主配置/adapter | 本次集成与物化结果 | 全 catalog/glossary/Graph/业务设计 |
| catalog-bootstrap / catalog | 指定模块与当前代码/已有 catalog | 该范围模块职责事实 | 重新生成全工程画像 |
| catalog-bootstrap / glossary | 指定术语/上下文与现有词表、语义 owner | 本次词条或冲突 | 为模块画像补空词条 |
| code-graph / module-graph | 指定模块代码、可用画像/入口事实 | 有来源的节点与边/漂移结果 | 所有模块建图 |
| docs | 请求路径/文档检查范围、链接与当前规则 | 文档检查/修订结果 | 启动 Feature 六阶段 |
| extension / extensions | 实例扩展 manifest、指定知识/动作/绑定 | 合法扩展或精确诊断 | 安装 MCP、索取凭据、修改 framework 发布件 |
| conventions-bootstrap | 已有惯例、候选与策展授权 | 本次确认后的知识资产 | 自动把建议写成组织约束 |
| component-catalog-bootstrap | 组件索引/代码、用途与限制裁决 | 本次组件策展内容 | 自动批准跨层依赖 |
| component-design | 当前请求、来源、蓝图/CU（按存在性与目标） | 局部结果或完整设计交接 | 仅设计请求启动 Goal 施工 |
| change-unit-progression | 当前蓝图与 canonical CU/已有运行事实 | 准备、选择/恢复一个 CU 或闭环交接 | 自签 Component closure |
| component-closure | 蓝图/CU/实际证据与目标覆盖 | 派生整体闭环缺口/结果 | 用 CU 绿灯替代组装验证 |
| goal-mode | 本次明确目标/授权与 Feature 执行上下文 | 运行协调和真实状态 | 单独制定阶段链或证据豁免 |

catalog/glossary 共享 Skill 但可执行不同职责；不能为了 1:1 新建重复 Skill。
docs/extensions 等已有 CLI 可以直接作为执行入口，不为统一外观新增无内容包装。
本表须由现有 skills.index 与 active workflow 枚举做一次完整性核对，未来新增入口按同合同登记。

## 3. 作用域与调用上下文

复用既有 projectRoot、feature、blueprintId、显式阶段/命令参数，
在调用边界构成上下文；无 Feature 专项调用必须使用下方 §3.1 的实际 CLI 合同，
不能仅靠测试手动构造下述内存形状，不新增 invocation.json 控制文件：

~~~ts
// 概念合同：实现复用各入口已有参数类型，不必另造公共 DTO。
InvocationContext = {
  subject: project | component(blueprint_id) | feature(feature_id),
  requested_result,
  authorized_boundary,
  resolved_inputs,   // P1
  execution_scope   // P2；仅调用期或既有 Feature/run 持久载体
}
~~~

global phase 继续使用 global 的既有报告/哨兵规则；
有真实 Blueprint 的请求保留 blueprintId；只读检查不创建它。
一项任务没有 CU/Feature 时，不创建“临时正式需求”来适配 runner。
调用期 scope 可按 P2 语义确定本次项目职责，不能写进不存在的 Goal manifest。

phase 已有 contract 机制可泛化 scope 识别并复用 P1；
非 phase 的项目 Skill 继续使用当前 Skill/CLI 的输入合同与 validator，
不建第二个 operations 注册表。共同的是输入、终点与实际结果语义，
不是强制所有能力都变成同一 executor 的节点。

### 3.1 无 Feature 的实际 CLI 合同（意见 4，P4/P5 的共同入口）

在现有 harness-runner.ts / npm run check 增加显式请求分支，使用以下新增参数；
这是待实施接口，当前 CLI 尚不支持。该分支在当前“Feature phase 必须 --feature”的检查之前处理：

~~~bash
npm run check -- --project-root <host> --phase review --request-file doc/requests/review-rdb.json --report-dir doc/reports/review-rdb-01 --prepare-request
npm run check -- --project-root <host> --phase review --request-file doc/requests/review-rdb.json --report-dir doc/reports/review-rdb-01
npm run check -- --project-root <host> --phase ut --request-file doc/requests/test-rdb.json --report-dir doc/reports/test-rdb-01
~~~

--request-file 与 --report-dir 必须同时给出；不与 --feature、显式 Goal run 身份并用。
request 分支不继承环境里的 Feature/Goal 身份；不把 feature 设为 _adhoc、_global 或临时 slug。
首批本合同覆盖 review、ut、testing；项目 native CLI 保持本节之前的既有合同，不另包通用执行器。

请求 JSON 形状（扩展既有 entry-input parser 的一个分支，不建立新 registry）：

~~~json
{
  "schema_version": "1.0",
  "phase": "review",
  "requested_result": "检查 RDB 查询代码的正确性",
  "targets": {
    "files": ["src/rdb/Repository.ts"],
    "tests": []
  },
  "baseline": {"base": "HEAD", "head": "WORKTREE"},
  "inputs": {
    "review_report": "doc/reports/review-rdb-01/review-report.md"
  },
  "allowed_test_writes": []
}
~~~

- CLI phase 必须与 request.phase 一致；requested_result 非空并冻结为 request 完成边界。
- files 为项目内明确文件；tests 为现有 provider 能解析的测试文件/稳定 ID。
  review 至少有代码目标；UT 至少有测试目标或明确待补测试的行为来源。
  testing 复用已有 adhoc cases 输入解析，inputs 提供现有格式的用例文件。
- baseline 的 Git refs 在准备时解析为具体 commit；WORKTREE 绑定实际目标文件内容哈希，
  有 base 时审查相应差异，无 Git 项目允许省略 base、以实际文件哈希作基线。
  不把“HEAD 这个字符串相同”当成同一版本。
- inputs 只映射 P1 已支持的输入 ID 到项目内文件；格式/内容由相同来源校验器读取。
  review_report 为 review 的实际产出，不能因为文件缺失就在 checker 内写一份通过报告。
  UT/设备的执行结果由现有 provider 返回，不能通过 request 指定命令字符串或假造成功。
- 默认 review 与 run-existing-tests 不授权源码写入；确需新增/修订 UT 时，
  allowed_test_writes 只列本次已授权测试路径，不授权更改产品实现。
  新测试预期必须有实际行为来源；空字段不能作为从实现猜需求的许可。

--prepare-request 只解析目标/基线、检查可读来源与报告落点，向 stdout 返回
request_sha256、解析后的基线、目标清单、facts 路径、报告路径与待补输入；
不运行 checker，不生成 PASS、Feature 状态或控制文件。request_sha256 由规范化请求、
解析后的 refs 和目标内容绑定计算。显式的待创建测试路径按已有 absent 来源语义记录。
目标声明错误直接失败；尚待 Skill 产出的 facts/review_report 作为准备缺口返回。

adapter 的实际调用顺序：准备命令 → 当前 Skill 的 Research/上下文收集
在报告目录生成 P1 facts → review 产出真实报告，或 UT/testing 准备其必要输入
→ 不带 --prepare-request 运行同一 CLI → 读取实际结果。
目标/基线在此期间发生未授权变化时，facts 的请求绑定不再匹配，重新准备并审查/测试；
不以继续使用同一个 JSON 文件绕过新鲜度核验。由 adapter 执行命令，不把命令清单当交付推给用户。

### 3.2 同一 checker 的接线与报告落点

request 分支复用 active workflow 的 phase→checker 解析与同一 check-review/check-ut/check-testing，
共同校验由 P1 输入上下文注入；新增入口不复制一套简化检查器。
CheckContext 改为 subject 区分的 Feature/request 联合：
Feature 分支仍有真实 feature；request 分支仅有解析请求、目标/基线、显式 reportDir、
P1 resolved inputs 与 request facts。不能用空 feature 或虚构 FeatureSpec.feature 填类型。

request 分支的 loadReviewReport、目标清单、facts、report writer、基线读取必须接收
这些显式路径；只有 Feature 分支才能调用 featureRelativePath、CU 映射、上游 phase verdict、
Feature attestation/receipt/completion 写入。内容、代码引用、负面结论、预期与实际证据检查仍共用。
专项审查的目标基线绑定写入本次 summary，不能更新 Feature review-closure-attestation.json。
UT/testing provider 同样将报告/coverage/trace 落点传入本次目录，不回落到某个 Feature 的默认目录。

report-dir 是必填的项目相对路径，先解析真实绝对路径并校验：
必须在宿主内，不能落在 framework 发布件、.git、配置的 features_dir、
或实际解析的任何 Feature receipt/report/goal-run 目录内；不能覆盖 request/源代码文件。
未指定时失败，不猜测当前活跃 Feature。已有机器输出只有本次请求绑定与基线一致才可更新；
其它请求的目录拒绝复用，由 adapter 选择另一明确目录，不静默覆盖。

沿用既有报告文件格式与 serializer：
- context/facts.md：P1 request 形状，真实调查及来源；
- review-report.md / UT 或 testing 的既有专业报告：真实请求产出；
- script-report.json、summary.json：检查结果、请求/基线/输入绑定及 evidence 引用；
  复用聚合/格式化函数的明确 request 分支，不硬套必需 feature/closure 的 Feature summary 形状；
  由 subject=request 与 completion_target=request 区分，Feature validator 不把它当阶段凭证；
- provider 原生 coverage/trace 等：置于此目录或原 provider 的独立运行目录，并记录真实引用。

summary 只表示 completion_target=request；不创建 goal-runs、Feature completion、
Feature receipt 或带虚假 closed 的阶段状态。P7 不把该目录枚举为 CU/Feature 完成记录。
复用现有结果/退出码分类，适用检查有 FAIL/未解决缺口时不得返回成功。
本入口不负责恢复多阶段任务；完整 Feature 仍按 P2 的真实 Goal 身份执行。

## 4. 项目能力按缺口调用

既有资源足够时直接使用，缺少时只补当前职责需要的部分。

例如 Graph 需要模块身份：
先消费有效 catalog 或已有配置/源码映射；若当前模块职责确实未明确，
调用 catalog 的对应模块任务，不能要求完成所有模块后才建图。
适用的稳定术语或组织惯例必须遵守，不因独立调用而忽略。

显式配置路径不可读与未配置可选知识分开：
前者报告 unknown/具体缺口，后者按现有 optional provider 规则降级。
发布件 framework/ 写保护与配置路径规则保持，不能让 bootstrap 改框架自身文件。

项目操作执行后返回结果、来源与剩余缺口，由外层协调选择是否继续；
子 Skill 正文删除无条件“下一步必须调用某 Skill”的指令。
真实依赖补足也必须符合用户授权范围，不能借补输入执行外部发布或新增架构边。

## 5. 用户入口与授权终点

三类入口共用 P2 计算：

1. 自然语言目标：主 Agent 阅读请求及现有事实，必要时进入现有正式性判断，
   形成规范化输入后调用范围解析；不新增路由 Skill 让用户先选。
2. 显式 Skill/phase：对应职责就是本次请求起点；查真实输入，不默认启动其它阶段。
3. “继续”：先识别已有任务/活跃 run，恢复其冻结范围，不再询问 track 或重新设计。

正式需求判据与信息不足时的 design.formality_routing 继续保留，
不因“用户不承担流程仪式”取消真实产品/授权确认。
纯文档机械维护保持合法无蓝图入口；其他正式实现仍经蓝图。

component-design 本身保持设计交接停止点。
如果用户授权的是完整实现，外层协调可在设计交接完成后调用
change-unit-progression/Goal，交互也必须按 P2 §5.1 先取得真实 in-session Goal 身份；
子 Skill 不越界启动。续建后继按 P2 §6.3 的事件关系定位，不重选一个新 run。
如果用户只要求讨论/设计/查看，外层同样必须停在请求终点。
现有授权可复用，不因跨 Skill 再问一遍；缺真实授权仍沿原确认点。

用户一句话范围与理由从 P2 结果生成，例如：
“已有设计与验收可用，本次实现、审查并运行相关 UT。”
运行中发现新的设计责任，说明新事实与需补工作，不要求用户理解 track/phase 名称。

## 6. 索引、adapter 与确认项

skills/skills.index.yaml 保持 Skill ID→路径唯一索引。
更新现有 description、触发条件、commands、bridge 和 templates，
使隐式选择与显式调用能够到达同一职责；不添加另一张机器路由表。

init-next-steps/skills-index-init-steps 继续派生可选后续任务；
提示建议不能变成已获授权或必须完成全部列表。

confirmation-registry：
新任务删除 feature.track 等轨道选择消费与用户菜单；
保留设备/外部副作用/架构 DSL/新依赖/真实语义裁决等既有边界。
“花钱动作”不能作为唯一确认判据。
P7 在旧 run 可恢复的前提下退役旧公共入口；不要先删除恢复所需 loader。

已有 adapter 的模板/render 单测与 bridge 路径检查覆盖所有受影响适配器。
不规定用户改用某家模型、SDK 或托管系统；仅复用当前 adapter 接口。

## 7. 验收

| 请求 | 应有行为 |
|---|---|
| 更新某模块 catalog | 仅相关范围，现有其它模块保留 |
| 只补 glossary 术语 | 不重复 catalog/Graph |
| 刷新已有模块 Graph | 使用可用事实，不要求全工程 bootstrap |
| framework-init UPDATE | 更新发布件集成/配置/桥接，后续知识只作建议 |
| 查看蓝图 | 零 canonical 修改、零 revision 增加、零 CU/run 创建 |
| 继续草稿设计 | 仅补缺设计/质询 |
| 完整设计交接 | 复用已有 CU 或接受合法分解，止于 readiness |
| 完整实现 | 外层在授权内从设计交接继续推进 |
| 只 review / UT / testing | 正确到 P4/P5，完成目标是 request |
| 非正式机械维护 | 不造蓝图/CU，仍遵守原生检查 |
| 扩展配置缺失/冲突 | 原有具体诊断，不能假成功 |
| 同 Feature 已有活跃 run 后说继续 | 读取原 run scope，不另起旁路 |
| 所有 adapter 渲染 | 无新任务 lite/full 菜单，真实授权点仍可达 |
| 无 Feature review 的 prepare→Research→check | 真 CLI 解析代码/基线，report-dir 有事实与报告，同一 review checker 被调用 |
| 无 Feature UT 的 prepare→check/provider | 真 CLI 传递测试目标、原生 provider 执行并返回报告，不创建 Feature |
| 已有活跃 Feature 时运行独立 review/UT | 其 reports/facts/attestation/receipt/events 的前后字节相同 |
| request/report-dir/基线错误或缺必需产出 | 明确失败，不回落成 _adhoc/_global/当前 Feature |

先按现有入口枚举冻结矩阵，再清理项目 Skill 的无条件后续指令，
