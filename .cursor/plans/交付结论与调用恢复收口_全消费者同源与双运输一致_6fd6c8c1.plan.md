## 4. 三条主线的实施设计

### 4.1 当前问题处置与全部完成消费者收编（t2）

**唯一落点**：在既有 check-disposition.ts 内扩充当前处置读取，以内部纯函数 resolveCurrentDisposition 汇合已有有效检查、已核实问题/缺口、债务和责任结果；现有 resolveCheckDisposition/isRequiredCheckGap 继续提供基础语义。责任解析仍唯一使用 repair-responsibility.resolveRepairResponsibility；不把其规则复制到新函数，不由 quality-axes 的文字猜 owner。该入口只处理内存事实，不读写文件、不持有缓存/历史、不 import runtime，避免与 report/quality/scope 的循环依赖。

**唯一输入组装处**：在既有 verify-feature-completion.ts 收编为 readCurrentDispositionInput，复用原 summary/script-report、verifier subject/问题、债务、能力、证据新鲜度与责任 reader，统一选择当前适用事实和来源关系。§3.1 的 gate/closure、有效范围、assess、完成、Feature/CU 与展示消费者不得各自挑选事实子集后直接调用纯判定。产出中的 gate/closure 将本轮尚未落盘的完整原始结果交给同一组装入口，由该入口按原 run/phase/attempt 规则覆盖相应旧材料；不能把任意缺项解释为没有问题。普通读取与复用阶段走相同组装规则，不另存第二份处置文件或为 summary 增加新必填字段。

输入组装显式接收本次请求终点、workflow、原授权及已读取的冻结/修订范围上下文，不能反向调用 assess、resolveCurrentScopeView 或 loadEffectiveExecutionScope 再求一次自己依赖的有效结论；纯判定仍不做 I/O。一次评估内复用同一组装结果及现有 readers，不跨写入、scope 修订或新报告发布保留；事实变化后重新组装。消费者可按自身用途投影该结果，不能重选事实或重判处置。对同一 phase 的缺失/旧版材料使用同一兼容与缺口规则，而不是各自省略。

这里的范围和身份按现有任务载体适用，不是统一必填 Goal 参数：完整交付使用原 run/冻结范围/phase/attempt；单职责 request 使用已有 requested_result、targets、baseline、request_sha256、报告及适用输入绑定，不要求 run、Feature scope 或虚构 attempt；旧无 run 成果按原载体读取。共同入口决定哪些来源对该终点适用，调用者不能自行少读；不适用的 Goal 材料缺省不产生缺口，真正必需的材料缺失仍沿原规则处理。

组装后的事实包含适用目标/严格度、来源引用或指纹、核实状态与合法责任结果。能由既有引用证明同源的记录才汇合；一个实际问题可有多个展示来源，不因质量轴/债务投影再派一单，不按标题近似合并不相关问题。无法确认同源的记录保留，不能猜测消失。

内部返回本次处置及依据、真实修复/验证责任、未满足条件、对本职责/请求完成和 release 的影响。继续用现有 action/verdict/resolution/runner_action 等输出载体，修/等/披露/补验不是新增序列化枚举或文件。终点判断还消费原授权、预算、义务和真实依赖，不能仅凭处置列表为空放行。

**调用契约与顺序**：先取得原始范围/修订和调用上下文，交 readCurrentDispositionInput 统一读事实；再由 resolveCurrentDisposition 计算处置；最后分别投影队列/下一步、普通完成、发布与展示。不能先算有效队列，再让输入组装反向读这个队列决定哪些问题存在。以下是内部职责约定，不是新增持久 schema：

| 边界 | 输入 | 输出与禁止事项 |
|---|---|---|
| 输入组装 | 请求终点、原授权、适用 workflow 与任务载体上下文；Goal 用原范围及调用身份，request 用既有目标/基线/绑定；既有产物及生产中的完整本轮结果 | 同一事实集合及来源、适用性、有效性、责任依据；不做派修/终态决定，不漏掉与同一问题相关的 verifier/债务/能力事实，不强迫轻量请求具备 Goal 材料 |
| 纯处置 | 组装结果、现有规则、共享责任解析结果 | 当前问题的依据、合法修改/验证方、待满足条件、完成/release 影响；不读写文件，不执行模型，不重算另一套 owner |
| 消费者投影 | 同次处置结果和自己的合法终点 | 仅转成现有 summary/scope/next/终态/完成/展示形式；不得再按 severity、required_for_release 或 mode 独立决定同一问题 |

gate 尚在执行时，其未完成步骤不能被当成最终“没有问题”；正式 closure 和完成核验必须在所需事实形成后读取。事实缺失按既有适用性与缺口规则处理，不为本接口新加“输入必须全字段齐全”的阻断检查。事实变化后重读；不同任务终点可有不同合法投影，不要求所有消费者输出相同标签。

**容易混淆的预期**（“可完成”仅表示该项不再阻断，仍须其余必需义务和正式完成链通过）：

| 当前事实 | 普通任务完成 | 发布与行动 |
|---|---|---|
| 有效软降级视觉残差，既有规则明确披露 | 可完成，不因该项重排 testing/coding | 债务保留、release BLOCKED；不伪造视觉 PASS |
| 同时有披露项和真实必修失败 | 仍不可完成 | 修真实对象并复验；不能因其中一项可披露而覆盖其它失败 |
| 必需检查因框架异常未完成 | 不可据此完成 | 沿既有缺口恢复；无依赖工作可继续，修好后补验证，不当作产品代码失败 |
| 原问题由正确验证方按当前事实确认解决 | 该问题不再阻断 | 移除当前派修/原因，保留历史；不是删除旧报告 |
| 只有修改方 PASS、拒修或 backtrack_completed | 不能据此认定原问题已解决 | 原核实/复验链继续处理，不提前清除当前问题 |
| request 已达到其明确终点 | 按请求契约收口 | 不生成 Feature completion，不要求补全无关阶段 |

必须收编的旧逻辑：

1. 视觉软降级在事实源已经明确为披露，债务管线只保留债务及 release 影响，不再把 open 数量无差别改成 agent/retry testing。blocker、现有 T8 确定性 major、文本存在性和明确 hard 要求仍沿原门禁；不恢复 debt accepted，不改质量分母。
2. quality-axes 只投影事实及当前处置，零执行/能力缺失不自动代表本阶段代码错；素材继承保留实际 upstreamPhase，按失效原因补材料、重验或交 owner。能力已有 producerOwnedInputGap 时共用原结论，不能既派上游又派当前阶段。
3. collectPhaseCompletionIssues/collectCleanPassIssues 删除“所有 required_for_release 非 PASS 都阻断普通完成”这条用途错误的规则。普通完成读当前必需问题，发布资格继续 BLOCKED；schema/closure/freshness/必要 attestation、明确执行缺口、真实负面结论和发布投影一致性仍核。原 DEBT_PIPELINE_ERROR 须按实际故障处理，不能当普通视觉披露。
4. resolveCurrentScopeView 不再把发布债务当 stale。真实输入/成果过期按已有 freshness；新问题按责任义务重开；合法未过期成果继续复用。request-only 仍不得签 Feature completion，阶段不在队列不等于无责任或未授权。
5. assess 缺口、有效范围和 finalizer 从同次当前判断派生。runtime 阶段中途、末尾和接续统一决定：可修且在原授权/预算内就沿既有候选、回退或范围修订；外部条件走原等待；达终点就正式完成。不得在 for 循环外另设“只算 PARTIAL 不行动”的出口，也不新增收尾修复循环或重试计数。
6. 完成原件资格、生成和消费必须贯通。资格未满足或生成故障不得作为 Feature 已完成对外宣称；沿已有可恢复收口处理并保留有效工作，不为此另造完成提交协议。CHAIN_SLICE_COMPLETED 与完整 Feature/请求终点保持原职责区别。
7. 当前指导从未闭合的有效问题与条件派生。原验证方有效复核后撤掉相关当前 recovery；历史事件保留。coding PASS、backtrack_completed、无变化或拒修不能单独证明原问题解决。缺材料时不能猜已解决，也不能拿最近一次旧派修充当新停机原因。

设备真实性同样进这条处置链：当前有效验收确需真机而只有模拟器/unknown 时保留已有过程证据，按既有 device_blocked/外部条件等待，不在运行末尾独立封成裸 PARTIAL。探针必须核目标可用且满足所需真实性，不是“任意设备在线”；恢复后重查原 gate，仅补真实欠缺验证。预算/授权不足照实停放，不能承诺永远自动唤醒。能力不要求真机的任务不凭本项新增义务。

### 4.2 调用事实、恢复和执行结果消费统一（t3）

**恢复落点**：在 goal-runner-phase 的既有事件回放链归一两种运输的调用事实，复用原 resumePostAgentPhases/applyInvalidationsToResume 与正式 gate 路径。deriveHaltValidationOnlyEligibility 和 sessionValidationOnlyEligibility 不再各自决定业务资格；前者的 phase_halt 形状、后者的 handoff_report 只是取事实的适配。需要 shared helper 时留在该既有回放模块，以 run/phase/invoke、原执行截止、有效完成观察、产物/写入快照及后来失效事实为输入，不保存第三份资格状态。

“作者已完成”不能仅凭进程退出或自报 passed；沿已有完成观察、报告接收与修复义务判定。旧 coding-i3 的有效执行事实、产物及无后续失效证明资格后直接正式 gate；若 gate 发现真实缺陷仍派修。超时、作者修复未完成、新目标/输入变化、后续回退/失效不得被旧 settled 覆盖。补 gate 不新计作者轮次，真实 gate 耗时仍计入原预算。

**失败事实消费落点**：将 ut-host-impl.sameInvocationUtFailure 的共同读取判据收进现有 execution-key.ts，UT 与 check-testing 的设备执行前入口共同使用；UT 专属结果格式与设备复查保持各自现有 reader。testing 写入现成 goal_invocation 三元组，不造新身份。成功复用仍用 decideReuse；失败消费独立于成功资格，不能把 outcome=failed 加入成功候选。

仅在最新记录归属同一 run/phase/attempt、输入键一致、冻结执行事实完整且仍适用时，正式 gate 读取原执行事实并继续当前检查/报告/候选生成，不重复真机执行。区分工具未执行、工具失败与 runner ok 但产品断言失败，不能套成功重建分支强写 run.ok=true。保留原失败时间、用例/步骤、日志与归因。

新 attempt、源码/测试/包/目标/config 变化、显式 force、已知设备阻断解除均允许真跑；同次失败的环境复查先于采用。材料或身份不足不猜同轮，按原入口执行/诊断；不跳过最新失败挑旧成功。可从冻结事实重建的派生统计优先重建，不为刷新展示再次跑设备。

覆盖 testing 的执行、截图/视觉事实消费以及 providers/device-test-request、providers/ut-run 的直接复用路径。轻量 request 没有 Goal 调用身份时继续原成功复用与独立执行语义，不用 request_sha 或相邻时间冒充同次 author→gate。两运输有共同真实调用身份时同样消费，不因会话或后台重新执行。

### 4.3 授权、实际能力和复用阶段遗留问题接通（t4/t5）

#### 4.3.1 复用阶段的发现不随 PASS 被吞掉

进入恢复/阶段复用之前，沿 readPhaseRepairIssues、verifier subject/发现 reader、collectPhaseRepairCandidates 与既有独立核实链读取已登记且仍未处置的问题。原 PASS 是阶段执行事实，不代表其中所有发现已解决；也不能只因原 MAJOR 存在就自动撤销 PASS。

对 S0 倒计时/导航发现，以它引用的 acceptance/contracts/use-cases/plan 和当前目标验证适用性。已核实且仍影响必需验收的问题，经原候选交真实责任方修订或有据拒修；原 subject/材料已失效或缺核实格式时，仅补所需核实步骤，不为了读问题先重跑整个 plan 作者。已由当前实现解决的发现有据关闭。复验原修复时消费拒修理由，无新事实的往返由既有预算/无进展控制。

定义矛盾归设计或定义责任方；单纯缺业务测试接缝归实际实现责任方。coding/UT 共同消费既有 unit/both 验收和可测性要求，确定投影复用已有字段及 materializeBlueprintSkillInputs，不新加固定类名/目录/Port。Page 命名入口可以承接 UI 事件但不证明无需 UI 的可测性；25521597 已有这一说明，最多清理其相邻残留措辞。不得因本批强迫简单请求造 DAG/interfaces，也不自动降低 unit 到 device。

#### 4.3.2 共同请求与授权入口

两运输在同一个 createPhaseExecutionContext 和请求材料构造处取得完整 instruction（含调用点追加段）、身份、输入、写前快照、原截止、自检命令和报告要求。将 session-execution-handoff 已有原件构造与 session 专属 lease/收发拆清：后台也消费并留存同结构的原件，不在 executor 再拼业务要求；CLI argv、PID、owner kind、输出传输和会话隔离安排仅为运输资料。原件仍在既有 run/phase/invoke 目录，沿用已有请求/报告引用和身份，不另建请求 manifest、协议版本或双份正文。

共同结果解释来自实际执行/报告事实；作者自报只是输入，正式 gate 才验证。写前/写后 snapshot 和 phase_write_observed 同源，后台不伪造 session 签发或报告，session 不伪造进程 settled。现有 session_issue/read/guardian 的身份规则在抽共享构造时保留，只把运输解析和业务资格分开，不能为了同一原件放宽 fence 或重签时限。必要独立 verifier/设计质询仍独立，不能由无隔离主上下文自行替代。

授权承载写实如下：后台 goal-runner 的 --detach 启动、--resume … --detach 续接，以及 goal-supervise:434–442 的同式重启，均在启动入口按用户无人值守裁决归一为 authorization.autonomyAuthorized=true；会话入口将 --authorize-autonomy 归一为同一输入，未带全权时按需确认。共同 resolveTaskAutomationPolicy 只读任务终点和该授权输入，不再读取 runtimeOwnerKind+executorMode+manifest.unattended 合取。对完整交付，两种获准入口都允许原需求内静默设计修订及默认预算调整，不要求 supervisor 或用户再补后台全权参数，不在恢复时丢掉原有能力。

后台父进程会在 buildDetachedChildArgv:4570 剥离 --detach，不能让子进程再次从剥离后的 argv 猜授权。在父入口转换后，沿现有非持久 --authorize-autonomy 参数透传给子进程，并让后台 CLI 与会话 CLI 共同解析到原 authorization 输入；不新增旗标、manifest 字段或授权账本。--detached-child 只作运输标记，本身不授权；supervisor 每次通过既有 --detach 入口重新完成相同归一。原 supervisor 的 owner/handoff 守卫保持，不把 session owner 擅自转成后台授权任务。有人在场 manifest 的默认 unattended 对象、approval_mode、进程 owner 和 Agent 账本都不能产生授权。

| 实际入口 | 共同授权输入 | 对完整交付的预期 |
|---|---|---|
| goal-runner --detach，或 --resume <原 run> --detach | true；父进程转换并透传既有参数 | 原需求内静默设计修订、允许按原渠道调整默认预算 |
| supervisor 合法选中后台 run 后发出 --resume <原 run> --detach | 与上一行相同 | 重启不丢权限、不清累计，不要求额外授权参数 |
| 会话 prepare/next/report 带 --authorize-autonomy | true | 同等全权；原需独立验证仍独立 |
| 会话未带全权输入；即使 manifest 有默认 unattended/approval_mode=never | false | 需授权的决定按原确认处理，不能静默修改设计 |
| 只有 --detached-child 或 process owner，没有入口转换/显式授权输入 | 不从这些标记推出 true | 仅识别运输，不能取得设计/预算全权 |

所有行都保留用户的更具体限制、真实凭据/不可逆动作要求和硬预算；授权不会把单职责请求变成完整交付。true 不是“无条件运行所有动作”，也不是“允许修改用户验收”。

授权来源沿既有启动记录/自动决议披露，实际权限仍受原请求范围、明确禁止及硬上限约束；轻量终点不因全权升级为完整交付。没有 --detach 选择或会话全权等可信原依据时沿原确认；已有真实授权由入口如实传递，不因运输变更重复询问。

设计修订、默认预算调整、确认点统一读该政策；真实凭据、不可逆动作、明确禁止、原目标/实质验收变化和用户硬上限保留。允许调整的是框架默认额度且累计不清零；不让选择后台等于无限增额，不更改 goal-timeout 既有 floor 及显式/默认预算兼容。用户回答后同请求恢复，不能靠新 run 刷新机会。

#### 4.3.3 能力与等待按实际事实

删除 attended→dryRun 的能力跳过。视觉金丝雀、读图工具与逐图材料只判断实际执行者；共同原件/工具事件 reader 接收本次真实能力和证据，不能探测未使用的后台模型，也不能把上轮 detached 的输出签成会话材料。已有 provider 可提供所需证据时沿原 provider；无法取得能力时仍为未知/缺口，不能假绿，也不另造全仓模型基准系统。

运行/进入阶段后才发现条件障碍，均回同一个设备/能力等待入口，先恢复欠缺的职责再进入依赖它的阶段。waiting 条件、截止、预算及复查语义两运输相同。后台进程内等、会话返回等待信息和恢复命令属于承载/呈现；不得因 session availableMs=0 就宣称等待结束或改成别的业务处置。沿现有 condition-wait/probe/supervisor 接续，真实探针就绪后仍由原 gate 复查；没有可运行的 supervisor/会话时如实说明需同请求接回，不新增常驻服务或假承诺即时唤醒。

#### 4.3.4 截止、异常与呈现

作者窗口起点沿原 agent_invoke_start，截止、预算预留和写入归因由共同原件给定；后台 invoke 不另起一个更晚的业务期限。窗口内正常工作和睡眠照计；超过原截止的会话离开时间不计；正式 gate 实际耗时照计，重领/重签/重复报告不重置。统一经 partitionExecutionSessions 折算，保留过夜、迟到事件、最后一轮补 gate、PID 复用、junction 和 PowerShell 报告文件回归。

异常和通知使用同一当前处置。有人在场可以即时显示/回答，后台通过报告/通知呈现同样原因与条件；是否需要确认只由授权决定。CLI 继续精简输出完整原件路径和摘要，日志留运行目录；不为统一把每阶段大 prompt 全灌主会话。

## 6. 开发验收：证明真实终点与恢复可达（t7）

### 6.1 共同验收口径
