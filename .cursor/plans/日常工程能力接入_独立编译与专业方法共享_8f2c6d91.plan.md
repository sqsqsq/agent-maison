# 日常工程能力接入

让宿主用户直接提出“编译一下”“review 当前修改”“给这个函数补 UT”“设计用例并真机验证”，
Agent 就能使用 Maison 的工程知识和执行能力。用户无须先取得需求号，也无须额外提醒“使用 Maison”。

本计划按 **两批实施 + 一次真实宿主收口** 组织。批次 1 可先用候选发布件试用；完整目标覆盖四类请求。
工具、方法、编排是职责划分，不对应三套新目录、三套状态或三个新框架。

## 0. 范围与决策

需求来源：2026-10-14 本会话的宿主痛点讨论、Claude/Codex 交叉核对，以及用户确认
“直接一份 plan，内部按批次实施”。本轮只编写此 plan，不修改生产实现或已有定稿 plan。

版本固定为 **3.1.0**，不设置 deferred_to。两批实施和 H1–H4 宿主收口均留在该窗口；
本文件 8 项待办全部完成才满足它在 3.1.0 正式发布门禁中的完成条件。

已收敛的边界：

1. **操作约束随动作执行，交付流程约束随交付责任启用。** 工具链、设备授权、真实测试预期、
   写范围和已有硬预算继续有效；普通操作不附带 Feature 出生、阶段凭证和整条交付流程。
2. **独立操作产生真实结果，不自动代表 Feature 完成。** 本批不实现独立结果进入
   Feature/CU completion 的转换、认领、签发或复用机制，也不为其预留新状态。
3. 恢复明确既有预期的普通维护可以直接实施和做适用验证；对已完成 Feature 的此类维护
   不自动创建 supersede run。仍在进行中的任务承接现有范围与修正路径。
4. 需要新增/改变验收、契约或作出新的设计决定时，进入对应设计职责，优先复用已有设计。
   上游已明确要求正式交付时保持其权威；不靠“bug”或“无 Feature”字样扩大授权。
5. 复用已有 profile/provider、输入解析、知识与恢复机制。旧代码中的确定性不一致须一并修正；
   不以缩小 diff 为由保留平行执行逻辑，也不把所有旧机制重构列入本批。

非目标：MCP、自动 lint/编译 hooks、新 lite/full 轨、通用任务状态机、意图分类器、
新的 capability registry、全局证据账本、跨宿主调度、蓝图/CU 协议重做、新平台编译适配、
按模块编译及“模块类型→构建任务”解析器。
hmos 为首个真实编译/UT/设备验收 profile；generic 当前不提供编译，须如实报告能力缺失。

父目标对齐：本计划为 G6 提供独立操作与正式阶段共用的执行/方法底座，为 G8 补真实宿主可用性；
不把日常维护重新绑定到 CU。与旧计划相关句子冲突时，以本计划承接的用户裁决为本批目标，
实施时同步现行入口/规范；历史计划正文保留。

## 2. 目标行为

| 请求 | 最小必要输入 | 使用 Maison 的内容 | 完成边界 |
|---|---|---|---|
| 编译当前工程 | 宿主配置、已有工程构建形态 | 工具链环境、product/参数解析、工程级构建、日志和失败诊断 | 本次真实编译结果 |
| review 当前 diff/提交/文件 | 明确范围与可读取代码，比较时有基线 | 调用链阅读、正确性/边界/项目惯例等共享审查方法 | 本次审查发现与覆盖说明；默认不改代码 |
| 给指定代码补/修/跑 UT | 目标代码/测试、预期依据、授权测试写集与可用载体 | 可测性判断、替身策略、断言设计、原生执行 | 所选测试的实际结果，区分现状刻画 |
| 从 bug/行为描述设计用例并真机验证 | 目标行为、预期、应用/场景及实际执行条件 | 场景设计、测试层级选择、步骤/断言派生、设备执行 | 已验证/失败/未执行分开；只设计时不操作设备 |

形式上“读取了 Skill”不足以验收。方法是否使用，要看是否据目标代码和项目知识做了相应判断；
执行是否完成，要看构建/测试的真实结果；请求是否完成，要看终点和未覆盖内容是否准确。

## 3. 日常维护与正式交付

| 情况 | 处理 |
|---|---|
| 预期明确，只修实现偏差，当前无相关在途任务 | 普通维护；无需新蓝图/Feature/correction 登记，验证按实际影响选择 |
| 代码来自已完成 Feature，现在修回既有预期 | 同上；不自动 supersede，不改写旧完成原件，本次结果不声明旧 Feature 重新通过 |
| 修复属于相关在途 Feature/CU | 沿既有范围、owner 与修正/恢复路径；`--revalidate` 只承担其原有机械重验，不签新完成 |
| 新增/改变验收、契约或必须补新的设计决定 | 回对应设计责任方；不先写实现再追认；不因局部问题重建全部已有设计 |
| 用户明确要求正式重新交付/验收，或上游已明确归属正式任务 | 保留正式路径与必要 successor/范围规则，不按普通维护降级 |
| 预期或目标不足以判断 | 先查已有依据，只问影响本次工作的具体缺口，不反复问“正式还是非正式” |

历史归属与当前交付责任分开：代码曾属于某 Feature 不构成本次维护必须重开该 Feature 的依据。
关联的在途任务不能通过换无 Feature 入口规避写范围或预算。纯编译可以读取当前工作树，
但不写 Feature 状态、不替正式阶段签发通过；不会因碰巧存在旧 `.current-phase.json` 就改投 supersede。

同步面包括全局模板、各 Skill、`agents-entry-detail.md`、`project-entry.md`、
`confirmation-registry.yaml` 与现行 OpenSpec。父 goal 只同步维护边界及 L0/L1 残留语句，
不改目标表、蓝图协议或正式需求责任。历史 plan/归档材料不批量改写。

## 4. 批次 1：独立编译与日常入口

### 4.1 一个独立编译入口，共享已有构建能力

新增薄入口 `harness/scripts/compile.ts` 和 harness npm script `compile`。
以下是本计划拟交付的命令，当前仓库尚未提供：

```text
cd framework/harness
npm run compile -- --project-root <宿主根> --json
```

- 只交付工程级编译，使用宿主已有 coding 构建配置与 `runHvigorAssembleApp`。
  不提供 `--module`，不根据 diff/catalog 缩小目标，不新增 HAP/HAR/HSP 任务选择。
  不要求 Feature、contracts、catalog 或工作区存在 diff；零 diff 仍真实编译。
- 复用 config/profile、product selection、环境派生、hvigor 参数/调用、成功判据与日志。
  工程级调用保持当前 coding 默认编译形态，显式目标和实际执行范围在输出中可见。
- 编译执行提取为仅消费真实工程配置/报告落点的共享调用。现有 dispatcher 若只用
  resolvedProfile 就收窄其参数类型；不为了符合 CheckContext 构造假 Feature/假 contracts。
  不新增 capability key、provider registry 或跨平台万能 build 协议。
- Feature coding 在调用前保留其契约/写集检查，在调用后保持原阶段裁决；独立入口不承担
  整个 coding checker。旧 adhoc compile 直接调用同一工程级内核，不用 catalog 模块集
  合成契约，也不再通过空契约进入正式 coding checker。
  旧维护综合检查的 lint/架构职责保留，但不成为独立 compile 的前置。
- 移动代码时保留当前可用的环境失败分类、已声明依赖安装与有界构建重试行为；只有该目标
  真正适用的恢复才执行。缺依赖声明、产品选择或真实权限时准确报缺口，不自动改业务源码/
  构建声明，不扩展重试次数，不为独立操作新开预算。
- setup 按实际 capability 的 prerequisite 使用已有解析与 ensure；不要求设备、视觉、
  verifier 或无关阶段材料。无需 Agent 先完整跑一遍全局 setup 再让执行器重复同一检查。
  无配置的真实缺口按既有路径提示，不安装新 IDE 或替用户登记凭据。
- 默认日志落宿主 `doc/reports/compile/<本次目录>/`；可显式 `--report-dir`。
  复用已有项目内真实路径/保护目录检查，禁止落到 framework、.git 或正式 Feature 证据目录。
  现有 adhoc 外层报告及其内部构建日志同步改到宿主独立目录，旧报告只读保留、不迁移删除。
- 默认输出简短目标/结果/诊断与精确报告路径；`--json` 投影同一真实调用结果
  （executed、退出码、实际命令/目标、日志与 meta 路径）。不建新证据 schema/manifest，
  不要求 Agent 按时间戳搜索“最新日志”。
- 仅真实执行成功才 exit 0。编译失败、缺工具、目标错误、profile 不支持或显式 skip 均
  如实返回非成功和具体原因，不把 capability SKIP 当“编译通过”。沿用已有失败语义，
  不为此添加 Goal halt reason 或新的 BLOCKER 登记体系。
- 不读取/写入 correction state 作为编译前置，不创建 Feature、Goal、facts、receipt、
  attestation 或 completion；不改已有阶段状态。编译请求只编译，不自动修源码、lint、UT
  或装机；用户已请求修复的后续动作由同一 Agent 在原授权内继续。

旧 `--adhoc-correction` 继续服务显式综合维护检查，不作为日常编译必经入口。
本批修复其共享编译和落盘问题，不扩展为新轻量轨。

### 5.3 UT

共享顺序为：明确预期与被测入口 → 按需做 L0–L3 可测性判断 → 识别真实依赖并选择
Spy/mock/fake 等必要替身 → 设计正常/边界/失败断言 → 在授权范围内写入并实际执行。

- 新改的本地代码同样可测；简单纯函数不强造 UseCase、DAG、mock-plan 或可测性报告。
  复杂流程适用的状态序列、依赖调用与失败恢复检查继续保留。
- 用户明确的预期原文与已有有效要求均可提供断言依据；可复用本次请求原文/既有文件记录，
  不为此制造 acceptance 或虚假 AC 编号。实现/旧测试只证明现状时明确标 characterization。
  复用现有逐用例来源登记和结果区分，不新增来源账本或语义 verifier。
- hmos 在第一次写测试前用已有 prepare/target probe 确认模块和 ohosTest 载体。
  缺载体、需改构建声明时先判断既有授权是否覆盖；覆盖则继续，未覆盖才说明并取得授权，
  不写到不能执行的目录，不以其它模块通过代替。
- 写测试的授权不自动包含改产品源码、改验收或改变架构。可测性缺口按责任方处理；
  所需授权已经存在时不重复请求确认。
- 只设计测试时交付用例与可测性判断后结束；要求执行时保留真实编译/测试失败，不改期望洗绿。

touch 成功或截图存在不等于预期通过；设备/视觉/断言能力缺失时交付已设计内容并明确未验证项。

| H4 | “给这个修复设计用例，再去真机验证”，提供 bug/预期与目标应用 | Agent 自行形成步骤与预期，验证当前目标版本；区分已设计/通过/失败/未验证，不要求用户先给点击脚本 |

同时保留三个停止点/边界反例：只设计用例不跑机；只 review 不改代码；只恢复已完成
Feature 的既有预期不新建 successor（该 Feature 具有可信完成记录，并保留其旧 phase 指针实跑）。
需要改变预期或处理真实授权缺口时，按 §3 处理，
必要澄清不算失败；让用户补需求号、重复授权或替 Agent 拼命令则是本批回灌问题。

复用现有报告与对话记录，至少记录：宿主/agent/发布件版本、入口已刷新、原话与目标、
实际 Skill/命令、结果/日志、额外人工步骤、无关产物/重跑与未完成事项。描述优化只能增加
被选择的机会，验收必须看实际调用；不承诺所有模型和版本都必然命中。

实际部署的主要宿主完成 H1–H4；其它已支持 adapter 先通过物化/入口检查，未实跑的版本
明确列出，不外推为全面通过。设备或材料不可用时相关 todo 保持未完成并记录解除条件，
不以 fixture 替代，不反复要求用户重新批准相同工作。
