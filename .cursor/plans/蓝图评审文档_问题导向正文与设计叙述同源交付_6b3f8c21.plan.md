## 1. 目标与边界

交接仍交付同一个 `component-blueprint.review.md`。正文可供评审人连续阅读；参考部分保留开发者所需的精确数据与追溯，业务施工拆分留在正文。canonical 蓝图与 canonical CU 仍是唯一设计来源，Markdown 不接受独立事实编辑。

4+1 继续用于设计、质询和覆盖检查，展示不再强制按五个视图逐字段排。正文不以 CU 数量决定篇幅，不用字数、图中参与者数量或表格数做门禁。代码标识符、必要文件路径和验收编号可以出现，但首次出现要有中文解释；正文不堆“谓词”“合并声明集合”等内部交接词。

本批不做：第二份评审文件、用户可配置模板系统、代码骨架、通用导航模型、运行时新增审批/停机原因、语义一致性机器证明、自动无限改稿。没有素材时不补造失败页、上线渠道、回退策略或具体性能指标。

## 2. 阅读契约

正文按问题组织，按实际内容省略没有意义的空小节。主顺序如下，样稿中的具体银行名称和模块数量不进入框架模板。

| 章节 | 要回答的问题 | 表达方式 |
|---|---|---|
| 方案摘要 | 改什么、结果由谁确认、主要边界与评审重点是什么 | 先讲用户得到什么的简短段落；施工安排只留一句到施工章的链接，不重复 CU 目的全文 |
| 背景、目标与边界 | 为什么做、目标与非目标是什么 | 解释与短列表，不把背景塞进长单元格 |
| 术语 | 阅读前必须理解哪些概念 | 精选释义；精确类型放参考 |
| 用户旅程与界面 | 用户怎样走完、取消和失败后去哪 | 先用已有旅程/显式顺序画总览，再分界面说明并紧跟原截图；导航前后例子带实际决策出处 |
| 整体方案 | 哪些角色负责什么、相互怎样协作 | 中文角色解释与关系总览，类名作对照；图的边只用已声明的调用或关系 |
| 关键流程 | 页面如何调用业务对象、Repository 和存储，在哪里成功或失败 | 每个代表性流程先导读再配图；完整分支放参考 |
| 数据与存储 | 保存什么、唯一键、加密、隔离和升级怎样工作 | 正文解释选择与约束，完整字段一次列在参考 |
| 关键取舍 | 为什么选它、否了什么、代价是什么 | 用已有决定的背景、结论、后果组成短段落 |
| 失败与恢复 | 数据失败、导航失败、取消、切号、销毁分别如何处理 | 作者用短表解释发生什么、用户看到什么、数据是否保存、如何继续；每行带实际 BD 编号链接，不改 BD 精确预期；不足时明确提问 |
| 质量与安全 | 兼容、隐私、可观测性、可用性、性能有哪些结论 | 有设计就解释，无依据就标未决，不造数字 |
| 施工与上线 | 每步交付什么、哪些模块和文件、依赖、安全中间态 | 当前 CU 的业务说明、依赖、目录树及已声明上线安排 |
| 验收 | 如何证明用户目标实现 | 主题导读带原 AC/BD/NFR 链接，全文参考唯一 |
| 待补问题 | 哪些事情材料还不能回答 | 问题、现有依据、缺什么，不自动变成 blocker |

参考部分按查询目的组织：字段与类型、接口和存储明细、完整验收、全部用例分支、施工精确映射、需求追溯、质询与稳定地址、4+1↔章节对照。身份、准入、内容来源及机制说明集中在参考入口；必要的文档过期提示仍应在文首可见，不能藏起来。

数字只帮助编辑发现问题。长段落不硬塞表格；图先讲一个问题，参与者多或嵌套深时由作者考虑拆图，渲染器不机械截断或删分支。缺失、不适用、未知仍区别表达，不输出空表或把可选空项都报缺口。

## 3. 叙述放在哪里，如何更新

### 3.1 最小承载：蓝图里的说明，不是第二份设计

已有 background/problem/summary、视图 current/target/delta、decision conclusion/rationale 等字段继续承载各自事实。原字段已经可读就直接使用，不要求再抄一份；改原字段仍是设计修订，会使说明摘要过期，也可能改变整蓝图引用 CU 的摘要。仅改表达时优先使用 `review_summary.reader_guide`，不为了润色改权威事实；确有设计变化才改回原承载并沿既有修订与调和。

建议最小形状如下，字段名在本 plan 定稿后固定，不开发模板语言：

```yaml
review_summary:
  reader_guide:
    source_digest: sha256:<框架按3.2计算>
    sections:
      - section: solution
        title: 整体方案与责任边界
        prose: |
          面向评审人的段落；只解释下面来源中已有的决定。
        source_refs:
          - /design_views/1/runtime_data_flows/0/ordered_steps
        graph_ids:
          - sequence:submit
```

`section` 只选择 §2 的既有正文位置，不控制任意渲染逻辑。同位置允许多个小节，例如多个关键流程；顺序就是作者讲述顺序。`source_refs` 是当前蓝图内 JSON Pointer，机器只检查能否解析；不注册为新的设计稳定地址，也不要求逐句话建证据。验收主题可引用单条，或对应目标的 acceptance 对象及 criteria/boundaries/performance 数组；编号链接只从这些已引用范围展开，仍按“来源目标＋条目编号”定位，不按裸 AC-1 全局猜归属。`graph_ids` 引用已有 generated_graphs，不在 prose 内保存另一份 Mermaid 图或截图。

prose 用普通 Markdown 段落、列表、解释性短表和代码名称，不写 Markdown 标题，章节标题由 section/title 统一编排。恢复速查表是作者对已有 BD/恢复事实的解释，不是新验收真源，每行引用实际 BD 编号并以 source_refs 定位。若正文仍含标题，renderer 将实际标题块降为加粗段落并给 WARN，保留文字，不改代码块内的字面内容，不阻断交接。需要精确字段表、方法签名、写入文件集合时使用确定性参考，不在此再维护一套。展示引用以来源对象名称作为文字。无效小节或引用仅提示并跳过受影响部分，不新增蓝图 schema 必填或 BLOCKER。

**蓝图说明不依赖 CU 身份或 CU 修订。** 业务施工拆分的文字沿用 CU 的 purpose、目标描述、touches、requires、安全中间态等现有字段，由设计者在既有候选/修订流程内写清；renderer 按当前有效集合展示。不能把“有一张 CU”“第二步依赖 CU-X”固化进 reader_guide，造成反向绑定。新建、修订、替代 CU 后照旧自动刷新正文中的施工段与参考，不为此改蓝图。

### 3.2 新鲜度：一个说明摘要，不做逐段依赖系统

现有图的新鲜度只看 revision/source_fingerprint/decision_fingerprint，不能单独覆盖草稿同 revision 的内容修改；CU 的 identityNeutralDigest 又会展开目标，不适合给整份叙述做自引用摘要。因此新增一个**只用于 reader_guide 是否可展示**的 source_digest，复用现有 stableStringify 与 SHA256，不改全局摘要算法、不作施工证据。

摘要输入为当前解析后的蓝图副本，仅删除：根 revision、derived_results，以及 review_summary 内 reader_guide、authored_by、questioning、admission、reconciliation。其它字段保留，包括 title/background/summary、设计目标、契约、决策、需求来源指纹和 generated_graphs 的实际内容。删除只按上述精确位置，不递归按同名键删除。数组保留顺序。

这是一份说明的保守新鲜度，不声称最小影响分析。未参与某个段落的设计变化也可能要求复核整份 guide；本批接受这点，避免新增每段依赖图与版本状态。身份升版和质询记录更新不触发改稿；质询真正改了结论、契约或流程会触发。图自身是否新鲜仍沿原机制判断，叙述摘要匹配不能使过期图恢复展示。

写入时机：设计者完成可渲染的事实/图草稿和说明后，使用共享摘要入口记录 source_digest，先 `--write-review` 产出草稿供独立质询；质询后定向修订并按实际来源变化复核摘要，交付前再重渲。摘要命令只返回当前值，不自动盖章或声称作者已读过；生成/校验文档绝不能替作者更新这一值。

| 状况 | 输出行为 | 谁处理 |
|---|---|---|
| 没有 reader_guide | 按新正文顺序直接展示已有字段和参考，在文首说明“尚未补写评审说明” | 下次设计写作补齐 |
| 摘要一致且引用有效 | 使用叙述与确定性事实块，输出完整参考 | 正常交付 |
| 事实变化或摘要缺失/错误 | 不把旧叙述当当前方案展示；回退到当前字段，文首说明“评审说明需更新” | 原设计 owner 复核后改稿 |
| 个别引用或图无效 | 保留其它有效内容，在相应位置说明缺口；图按既有 WARN/不展示规则 | 原作者定向修订 |
| CU 内容或集合变化 | 更新 CU 业务说明、顺序与参考；不影响蓝图 guide 摘要 | 既有 CU 接受/修订与物化接线 |

上述情况均不改变 admission、readiness、run 或原函数结果。文档文件“当前”只说明它忠实投影当前输入；不能据此宣称评审说明完整。输出报告分别说明文件生成结果和叙述缺口，不新增持久化的通过状态。

### 3.3 不让润色导致施工重跑

reader_guide 是解释性投影，不承载 acceptance/contracts/use_cases/调用事实。CU 直接引用整份蓝图时，现有摘要会展开整份目标；必须在这种**蓝图目标**进入 identityNeutralDigest 的位置，仅去掉 `review_summary.reader_guide`，同时覆盖 CU 引用和 Feature 内蓝图引用两条路径。不能递归删除任意同名对象，不能顺便剔除 rationale、alternatives 或其它既有事实字段。

纯改 guide 后，文档的精确蓝图 SHA 与正文必须变化；CU 的业务摘要不变，既有指针调和照常处理。改现有流程、契约、验收等设计事实仍影响原摘要与施工恢复，不以“写作”绕过。纯 guide 改动不反向创建 closure 决策或新义务，不要求重做原设计质询；独立读者发现事实有误时必须回原字段修设计，再按已有 revision/准入规则处理。

这里不能只验证 identityNeutralDigest。`capability-resolution.ts` 对带 `derive.blueprint-*` 戳的文件还会比较包含蓝图原始 SHA 的完整 source；已有 spec/plan 文件必须通过原调和与安全刷新接线更新来源身份，之后实际解析仍为 resolved。正例先经现有消费/冻结路径建立原完整 contracts 的等价依据，不手造摘要、不在测试中手改戳；正文及合法阶段补充保持原字节，只更新来源戳与相应身份指针。缺少原有安全刷新依据时仍沿既有责任阶段重建规则，不借润色放宽刷新条件。真实 ordered_steps 内容变化不得按说明润色刷戳放行，反例见 §7。

## 4. 渲染与参考：一个函数、一次编排

保留 collectBlueprintReviewInputs、共用目标选择/合并、renderBlueprintReviewMarkdown、原子物化与发布校验的职责。renderer 不读产品源码、需求文件内容或 Feature 派生产物，不调用模型；图片继续使用已登记路径。新 reader_guide 在 canonical 蓝图内，因此现有来源字节复核和文档精确绑定仍覆盖它。

正文优先放当前有效的作者说明，在相同位置补事实表、截图和图；不要再把同一段 summary 在概述和总览印两次。缺少说明时也使用新的阅读顺序，并明确素材局限，不保留第二套旧版渲染器。

参考仍直接取蓝图和 CU，必须保留精确集合。迁移现有渲染能力而非另写 acceptance/contracts/use_cases 解释器；禁止用模型重新生成字段、默认值、方法、文件或验收明细。共享目标、多 CU 同名编号使用“来源目标＋条目编号”身份；正文编号指向正确条目，参考全量保留。

目录树合并公共前缀，能还原全部精确文件路径。用途只用已声明组件/接口说明；长说明可链接接口明细，不自动归纳成新责任。作者需要短说明时，放在其已有职责说明里；本批不加 files 用途映射字段。同名 index.ets 显示所属模块，目录不扩成授权。

业务施工段逐个当前 CU 讲交付、模块、依赖和安全中间态。精确谓词、provides 编码、继承验收集合、文件授权映射、替代历史在参考可查；不把整体一并隐藏。ready、run 状态、完成结论继续在原输出/closure，不混进设计事实。

图沿用 generated_graphs 和现有 parser。代表性流程的选取、拆图与标签由设计 agent 完成，node_refs/已有调用设计与图文一致由原质询/独立读者核对。静态图只画已经声明的调用；不得从 ui_bindings、data_boundaries、名称或目录猜调用者。图的放置用 graph_ids，不造另一份图真源；旧图是否搬至参考按它的阅读目的决定，不能重复画两份充数。

同一 graph_id 在正文多处引用时仍只绘制一次；首次绘制处建立可定位锚点，后续引用显示带图名的可读回链，不返回空内容。当前放置由作者已有 graph_ids 和正文顺序决定，本批不新增章节优先级、图归属字段或按名称猜主责章节；图放错位置由质询指出后作者修正。坏图/过期图沿既有规则原位说明，后续引用指向该说明，不能制造悬空链接；根本不存在的 graph_id 沿原诊断处理。

source_refs 指向某目标的 acceptance 或其 criteria/boundaries/performance 集合时，复用现有目标解析及条目索引展开可链接编号。只展开该引用范围，不借机枚举整份蓝图；单条与集合重叠按完整来源地址去重，多目标同名编号保持区分，无效引用仍按原诊断，不链接到未引用的其它目标。范围表述如“AC-1 至 AC-8”不引入新的区间解析协议。

“成功衡量”数组按条展示或在该展示位置处理拼接分隔符，避免生成“。；”；不改原条目语义。中文多余空格由渲染端在普通叙述中处理：去掉全角标点（含逗号、顿号、句号、分号、冒号等）后面行内连续的半角空格，不限制后面必须是中文。代码围栏、行内代码、链接和 URL 原样保留；不动其它位置的标识符间空格、换行、缩进及 Markdown 硬换行，不改 canonical。单换 YAML 字面块不能保证消除预览中的折行空格，不把本项交给作者规避；不能安全区分的内容保留原文，不靠格式修复改写事实。

旅程总览和角色关系图也走上述已有承载，不新增图类型字段或自动推断生成器。作者根据明确的旅程顺序、调用及责任关系选择总览边，中文角色和动作在前，代码名仅必要时括注；不能把用户流转、代码调用和归属关系混画成同一种含义。写作指引列出当前 flowchart 子集：方向声明、ASCII 节点 id、`id["标签"]`、`-->` 与 `-->|标签|`；不支持 `{}` 判断、subgraph 或注释。时序图继续使用既有 participant/actor、消息、Note、alt/else/end、注释子集。

图校验按既有事实引用分类：sequenceDiagram 沿原 WARN；未声明关系引用（relation_refs 缺省或空数组）的作者展示图也按 WARN，不展示坏图、在 graph_ids 对应位置说明原因，不影响 admission/readiness。声明了 relation_refs 的关系结构图保持原 BLOCKER；不更改关系事实自身校验，不新增作者图标记。反例须经过真实蓝图准入与 readiness，不能只断言 severity 字符串。

新格式提升既有 BLUEPRINT_REVIEW_FORMAT；旧 review 只提示按当前格式重建。复用原来源变化/集合变化/格式升级诊断，不新增准入状态。所有自动生成接点继续调用相同的确定性 renderer。

## 5. 谁写、何时写、怎样控制成本

| 时机 | 责任与操作 | 额外成本 |
|---|---|---|
| 首次 component-design / 请求交付可评审蓝图 | 原设计 agent 写事实、图和说明后，先用 --write-review 生成草稿，再派已有独立质询；仅定稿蓝图、尚无 CU 也适用 | 同一设计任务内写作，不另派专职写作 agent 作为默认路径 |
| 草稿/局部修订 | 实际改事实则复核说明；纯字段格式变化不盲目重写全文；最终重渲并读成品 | 按变更定向编辑，摘要只做一次文件级失效判断 |
| 独立质询 | 派出前草稿文档已生成；独立会话先读首屏和正文答八问，完成前不读 YAML 或承接父会话设计事实摘要，再按原 scope 定向核源；作者修订一轮后重渲 | 仍是一轮既有质询与一轮定向修订，不另起阅读管线、不循环打分 |
| 接受 CU、readiness、指针调和 | 只刷新确定性文档；不会调用写作或阅读 agent | 零新增模型调用 |
| B1 自动修复 | 修复 agent 仍只改授权草稿，可按 source_refs 在授权内定向复核；当前公开摘要命令只读 canonical，框架发布时还会改根 provenance，因此 B1 不记录新说明摘要。成功发布使原摘要失效后提示“评审说明需更新”、展示当前事实与完整参考；后续设计 owner 复核已发布 canonical 后刷新说明摘要 | 框架持锁段零新增模型调用；不扩 B1 授权、不自动盖戳、不加通知机制、不因文档观感停止 run |
| 只读检查/发布校验 | 只重算、比对，不写 guide、不发起阅读 | 零新增模型调用 |

一次阅读后仍有非关键表达问题，可以如实报告后继续交接，不要求用户额外签字，不新增评分、次数状态或停机原因；不能把“readiness 已 ready”报告为“人读验收通过”。发现真正授权或事实错误则沿现有责任方修正，不以阅读非阻断为由容忍错误设计。

执行顺序就地改写 `component-design/SKILL.md` 的现有生成/交付句和 P1 §4 第三条，不在文末追加相反规则。入口当前148行，本次替换原句不增加行数，预算仍150。保留“本次改 canonical，结束前重建”的最终新鲜度约束，同时明确“质询前先生成”，不是二选一。

这里的草稿结构可用指已有加载/渲染入口能生成文档，不要求先通过含质询结果的完整准入。现有 `--write-review --json` 可在 checker 未准入时仍返回已生成的 review_document；应分别看文档生成状态和准入问题，不能以整体非零退出码一概判没有草稿，也不能反过来把文档生成成功当准入通过。尚待质询的草稿可交读者，实际解析/来源或其它设计错误仍按原规则修，不新增检查种类或吞掉原 BLOCKER。

独立读者需具体标出缺少图示解释的关键链路、普通宽度仍需放大的图、放错章节的图，以及只有一段且没有回答本章问题的位置；段落少本身不是缺陷。先读实际首屏/正文，再核 YAML 中的决定、被否方案、调用和边界，不能用 YAML 已写齐代替正文已讲清。普通宽度的图像实读使用宿主已有可用预览能力；看不到渲染图时，仍须从评审文档内的 Mermaid 图源检查既有“一图一事”规则，指出混讲的独立问题及应拆开的段落，不提前读取 YAML，也不能把整项图审查跳过。例如提交、入库、账号复核、结果页与退出导航挤在一张实现时序图时，按子问题提出拆分与衔接建议；总览图讲完整旅程不因跨阶段就机械判错。只有字号、布局及是否需放大等视觉可读性标为“未核验”，不以语法通过、源代码审查或参与者计数冒充视觉实读。仅记录于已有质询输出/会话报告，不新增预览依赖、凭证、状态或机器停机门。

写作要求：段落讲完整因果；首次解释代码角色；避免斜杠串、省略主语和“已实读/F1 已修复”等过程话术。指引只纳入写法规则：导航清理用前后页面栈的例子说明，S4 与加密分开写，验收主题标注原编号；不放目标样稿原文或银行卡开卡栈例子，避免 t5 写作者提前看到答案。

首屏必须使不了解本项目实现的读者知道现状、变化、结果与边界；先使用可读的原字段，仅改表达时优先写 guide，不强制填满所有 guide 小节。中文名优先，图中消息先讲调用意图、必要时括注原方法；关键取舍逐项讲问题、选择、理由与代价，不用决定编号串代替解释。产品非目标与本次只执行设计的阶段状态分开。独立读者第一项先只读首屏复述方案，再沿正文回答八问，不靠熟悉框架替正文补全含义。本轮定向补上已知页面栈例子的实际 source_refs，不改其设计事实。

发布件写作指引附一对明确标注“仅示例”的好坏表达，使用与本次宿主无关的场景，不把目标样稿当提示词。示例先给定事实“用户点击保存；Repository 写入成功才通知页面；写入失败保留输入”，再对照坏写法“保存/成功/失败由 Repo 处理”和好写法“用户点击保存后，页面等待 Repository 写入。写入成功才显示保存完成；失败时保留输入，供用户重试。”示例只示范表达，不为消费者增加业务要求。

来源原文和截图只供设计阶段核读；新事实先进入原设计承载，不能只写在 guide。素材不支持的解释按 C 类列为缺口。独立读者先只看正文回答，再有针对性核源；机器只能核编号/引用/集合，不能保证“解释无新增事实”。沿用既有质询输出/报告存问题，不新增一份签章记录。

成本记录随 §7 的真实 component-design 回归完成：记录原设计任务、既有独立质询和定向修订的起止/调用次数，以及首次文档生成、派出质询和正文读取的实际顺序；底层模型请求数不可见则标明，不以工具次数代替。不另派写作 agent 做成绩更好的样稿，不另建计费仪表、A/B 基准系统、阅读凭证或预算状态；不以耗时长短解释质量，自动物化接线仍零新增模型调用。

## 7. 验收与必要反例

| 场景 | 必须观察到的结果 |
|---|---|
| 原 -br 副本没有 guide | 按新顺序生成，素材不足明确说明；原事实/截图/全部参考不丢；不编造完整叙述 |
| 同话术的新需求真实设计路径 | 用户从-br干净基线按本轮相同话术/任务边界回归；原设计 agent 同次完成设计与说明，先有草稿文档再派独立质询；先正文八问后核 YAML，一轮修订后重渲；不用另一个专职写作者补稿证明默认流程 |
| 同 revision 改原契约/流程 | guide 过期、不以旧说明交付当前方案；参考立即使用新事实；readiness 不因说明过期改变 |
| 只升 revision、只更新质询/准入记录 | guide 内容无需重写，图按自身原 freshness 处理；无额外模型调用 |
| CU 增加、同 ID 修订、替代 | 正文施工拆分和参考反映真实集合；guide 不反向要求改蓝图，无 CU 也合法 |
| 改 guide、正文来源摘要缺失/错误、删除 guide | 文档分别更新或回退；生成器不得自动盖有效戳；不存在重新准入或运行停机 |
| CU 或 Feature 引用整份蓝图 | 只润色 guide，原业务摘要不变；改 acceptance/contracts/use_cases/ordered_steps 时仍变化；同名业务键不能被误删 |
| 已有带戳 spec/plan，纯 guide 修改后走真实调和与消费 | 使用真实已物化 acceptance.yaml/contracts.yaml 及原消费链建立的安全刷新依据；仅改 reader_guide，调用现有 readiness 调和或 B1 发布，再经 capability-resolution 解析 spec/plan 输入仍为 resolved，无 blueprint artifact source stale；文件仅刷新戳和身份指针，正文、合法补充与格式保持原字节，不在测试中预改戳或 mock resolver |
| 同样带戳文件，真实修改被引用的 ordered_steps | 走相同调和与消费路径，旧产物仍判过期/需责任阶段重建，不按润色自动刷戳成为 resolved；保留实际原因，不能仅凭摘要变化断言通过 |
| 引用失效、两个目标各有 AC-1、原记录增删 | 定位出问题；链接不串目标；参考及文件集合与来源精确一致，不把自然语言判断冒充机器验证 |
| prose 内误写 Markdown 标题 | 标题文字保留但降为加粗段落，给 WARN，不破坏正文/参考层级；代码块内的 # 原样保留，不改变准入/readiness |
