# P4：实现与审查

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；前置：[P1](动态工作流_P1_输入契约与事实承接_a6d3b8f1.plan.md)、[P2](动态工作流_P2_执行范围与运行时统一编排_b7e4c9a2.plan.md)、[P3](动态工作流_P3_需求设计与蓝图施工投影_c8f5d1b3.plan.md)。
> 本 plan 不拥有验收/契约投影 writer，也不决定 UT/testing 是否适用；两者分别归 P3/P5。

## 1. 背景

coding 当前 full capability 把 codebase/plan/contracts/acceptance 捆绑为必需输入。
review 虽能在设计输入缺失时降级，但 workflow.requires=[coding] 与
control_dependencies=[coding] 仍表达“本次必须先 coding”。
因此独立调用与蓝图充分输入场景不能仅靠缩短 chain 成立。

目标是保留真正的实现/审查质量要求，消除与本次无关的上游仪式。
coding 成功不等于 Feature 完成，review 独立报告也不为其它未完成义务背书。

## 2. coding 契约

| 内容 | 必需性与来源 |
|---|---|
| 明确目标与不变量 | 请求/获准蓝图与 CU/有效验收；不能从代码现状猜目标 |
| 当前代码、可识别基线 | 现有代码与 run_base_sha/对应交互基线 |
| 写集与文件引用闭包 | 受契约管理的实现使用 P3 物化的 contracts.files；合法 L0 保持既有路径 |
| 相关接口/数据/运行语义 | P3 typed contracts；不存在新设计义务时可复用旧合法内容 |
| 必需验收判据 | P1 resolved acceptance 或合法专项实现目标；完整 CU 必须具备对应覆盖 |
| 可选解释文档 | plan.md/spec.md 只有本次具体消费需要时适用 |

新协议内消除 capability_coding_full_context/lite_context 的分轨选择，
按所需职责组合输入。真实基础项缺失依然 blocked。
不能把 contract 缺失统一判“不适用”；尤其 CU sidecar、写集、runtime owner 与外部契约不能丢失。

编码范围必须与蓝图/CU 获准边界一致。
读到新的接口/模块拆分问题时提交具体发现，进入 P2 的设计回退；
禁止 coding 自己扩大 contracts.files、architecture DSL 或外部边后继续声称原授权有效。

## 3. review 契约

独立 review 的最小输入：
目标代码或明确 diff/基线、用户要求检查的维度、适用项目规则。
如果请求是“检查实现是否满足此设计/验收”，对应设计/验收自然成为必需输入；
若请求是“检查这段代码的正确性”，不得为形式完整强造 Feature spec/plan。

组合交付 review：
对本次实现检查需求、契约、蓝图 design_refs、runtime flow、组件资产/惯例与写集，
适用项不能因来源来自蓝图而降级。
缺少必需对照资料形成具体缺口，可在报告中披露已完成的其它审查，
但该 required 义务不通过。

review 的真实前提是“审查对象已经存在且基线明确”。
用户显式审查已有代码时不要求本次 coding；
本次有新增实现时必须绑定对应实现基线，不能借审查旧版本替代。

## 4. 消费与产物

check-coding/check-review 使用 P1 注入的 resolved context。
移除新协议中直接读取旧 plan/spec 固定路径的前置；
仍需读文档的语义检查通过 binding 定位来源，无法适用的章节检查不运行。

coding 产出实际源码与原生编译/必要检查证据；
review 产出覆盖范围、基线、发现与结果；Feature 分支复用既有 review closure attestation，
request 分支按 P6 §3.2 记录本次基线绑定，不能更新 Feature 的 attestation。
输出包含 requested completion target 的投影，不能手填 scope 或完成状态成为新权威。

独立、非 Feature 的 review 固定使用 P6 §3.1 的
npm run check -- --phase review --request-file <path> --report-dir <path>，
由 --prepare-request 返回目标/基线和输出路径，现有 Research 步骤建立 request facts，
真实 review-report 生成后调用同一个 checker。P6 的该入口段是本 plan 集成前置。
loadReviewReport、checkReviewContext、目标文件检查、事实检查和报告回写统一读取 request context；
Feature 路径助手、CU/上游 verdict 及 Feature receipt/attestation 只在真实 Feature 分支调用。
不能创建假 feature，也不能以禁用内容/负面结论检查来适配无 Feature 请求。
对 Feature 的专项审查可复用现有报告机制，但更新报告前按既有单写者/活跃 run 规则处理，
不能破坏正在运行任务的证据。

## 5. 实现与审查的控制边

- 先取得合法施工输入，再改代码；不是“先运行 plan 名称对应的阶段”。
- 审查基于真实代码版本；若本次 coding 未完成所需对象，review 不能假审查通过。
- review 发现根因归 spec/plan/蓝图时沿已有归因回退，不把所有问题塞给 coding。
- review 后新增实现按现有 drift/freshness 分类处理，不因动态编排另加全量重审。
- 新 public API 引入测试义务由 P2/P5 对新设计重判，review 不自行裁剪测试。

## 6. 与旧 lite 的关系

旧 run 的 change/exit 闭环按 P7 兼容。
新请求中 exit 原来承担的 scope/编译/验收检查，迁入其真实责任：
写集/构建归 coding，审查归 review，单元证据归 UT，完成归现有 completion。
不得先删 exit 再遗失其检查；也不新建“新 exit”把所有工作重新打包。

现有 L0 合法直接维护保留原生验证要求，不为了支持独立 coding 升格为全部正式 CU。
正式性判据保持上位规则，修复规模小并不自动是 L0。

## 7. 验收

| 场景 | 应有结果 |
|---|---|
| 真实契约/验收已充分，缺 spec.md/plan.md | coding 与组合 review 正常消费，零空文档 |
| CU sidecar 或 contracts.files 缺失 | 施工前缺口被发现，不能以“省 plan”放行 |
| 只审查已存在代码 | 不启动 coding，完成目标为 request |
| 请求按契约审查但契约不可读 | 对应义务未完成，不能降级报告 PASS |
| 新 API 与获准契约不符 | 回 plan/蓝图，新范围签发后继续 |
| 越界文件、非法模块依赖或资源路径 | 原有真实检查仍失败 |
| review 基线与实际代码不一致 | 不能复用历史 PASS |
| review 后纯文案/注释小改 | 复用既有风险分类，不触发新全测机制 |
| 源自蓝图的 runtime/组件设计 | 逐项对照真实实现，不能因无 plan.md 跳过 |
| coding 已完成而 required UT 未完成 | Feature completion 仍失败 |
| 新 Feature 直接 coding 且无 facts | 真实入口先建立 coding facts，再写源码；无 spec/change 产物 |
| 无 Feature 的 prepare/Research/review/check CLI | 同一 checker 校验真实报告/基线/request facts，零 Feature 路径 |
| 活跃 Feature 存在时的独立 review | 原 reports/facts/attestation/receipt/events 字节不变 |

## 8. 文件与验证

重点：skills/feature/coding、skills/feature/code-review、
check-coding.ts、check-review.ts、相关 phase-rules、verify-coding/verify-review prompts，
review attestation、contract-reference-closure 及 source baseline 消费方。
scope/义务实现只在 P2 修改；设计输入 writer 只在 P3 修改。

契约与 checker 同批接线；用真实最小源码与有效 typed 契约验证，
不写“缺文件就 return PASS”的镜像测试。
运行 npm run openspec:validate 与 cd harness && npm test；后续纯文字改动仅检查 diff。

父目标 G6：恢复 CU 设计与实际施工的一致性；无新运行权威。
真实宿主验证直接 RDB 修复与专项 review，结果由 P7 汇总。
若额外基线/身份机制与既有 attestation 重叠，复用原机制，不另立记录。
