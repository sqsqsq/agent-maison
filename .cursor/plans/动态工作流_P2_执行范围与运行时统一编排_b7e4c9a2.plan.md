# P2：执行范围与统一编排

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；前置：[P1](动态工作流_P1_输入契约与事实承接_a6d3b8f1.plan.md)。
> 本 plan 唯一维护义务规则、ExecutionScope、身份与修订合同。
> P3–P6 提供业务事实与消费者；不能自行加第二套阶段选择器。
> 以下为新协议设计，当前只有 phase_chain 冻结等基础机制已经存在。

## 1. 根因与责任

当前 resolveAutoChain 在预设链上截取区间，validateFeatureChainDag 要求 required phase 出现；
assess 在 workflow/track 全阶段上检查缺口。现代 Goal run 已冻结 phase_chain，
但冻结的是预先选出的固定链，不能解释为什么某项义务适用或被已有事实满足。

本次扩展既有计算和出生接口：先回答请求终点与义务，再输出执行阶段。
不重写整个 goal-runner，不将进程预算、设备调度、授权和缺陷归因搬入 assess。

## 2. 义务规则唯一来源

在 runtime-policy 邻近的一个纯计算模块维护内置义务规则，工作名称 execution-scope.ts。
这是从既有模块提取的单一职责实现，不是新服务。
workflow.artifacts[] 用 obligation_provider_id 绑定该阶段的静态规则；
contract.capabilities[].obligation_kinds 只引用规则输出种类，不复制谓词。

workflow 新版本采用 1.2；旧 1.0/1.1 按旧链兼容。新增可选字段：

~~~yaml
schema_version: "1.2"
artifacts:
  - id: testing
    scope: feature
    obligation_provider_id: obligations.testing
    # 其余 check/rule/skill_doc 沿现有定义
~~~

新协议内 auto_chain 只提供无冲突时的稳定默认次序；不使缺席阶段自动变为义务。
requires 中旧信息依赖由 P1 输入闭包替代；真实控制约束使用现有 workflow/contract 表达，
需要条件化时由同一 provider 返回本次 applicable control edges。
不可把完整旧 requires 数组直接当“不可跳控制边”。

| 义务种类 | required 条件 | 可用事实 | 责任阶段 |
|---|---|---|---|
| acceptance-context / acceptance-definition | 下游需行为判据；既有内容未覆盖则需补定义 | 请求、蓝图、有效验收、CU predicates | spec |
| design-context / design-decision | 下游需施工契约；新接口、数据语义等未裁决则需设计 | 获准 decisions、contracts、真实影响面 | plan |
| implementation | 用户要求改变行为/结构且未有有效实现 | 明确请求、CU delta、代码 | coding |
| code-review | 本次实现需审查，或用户显式要求 review | diff/目标代码、审查目标 | review |
| unit-evidence | 变更逻辑风险、unit/both 验收，或显式 UT 请求 | 验收、目标代码/测试、有效历史证据 | ut |
| device-evidence | device/both AC/BD、真实设备 NFR、行为影响需要设备证明，或显式设备请求 | 有效验收、蓝图切片、影响证据、专项用例 | testing |
| visual-evidence | 当前 fidelity 与真实视觉验收要求 | 既有 fidelity SSOT，不扩大其原有语义 | testing |
| project 能力 | 用户请求或当前输入缺口需要指定项目职责 | P6 的既有知识/配置事实 | 原项目入口 |

代码/文件位置/规模只作为线索；不以“触及 UI 文件”直接生成设备义务。
AI 在已有阅读过程中提交有来源的影响判断，机器检查引用与明确规则，
不宣称能机械证明任意语义判断正确。未知判据保留具体缺口。

## 3. ExecutionScope 结构

~~~ts
interface ExecutionScope {
  schema_version: "1.0";
  completion_target: "request" | "feature";
  requested_results: string[];       // 从明确请求冻结的结果边界，不能由 checker 缩写
  obligations: Array<{
    id: string;                     // kind + 本次稳定验收/CU/目标地址
    kind: string;                   // 静态内置规则种类
    owner_phase: string;
    applicability: "required" | "not_applicable" | "unknown";
    reason: string;
    basis: InputBinding[];          // P1；输入来源及判定所用事实
    satisfied_by?: EvidenceOrInputRef[];
  }>;
  phase_chain: string[];             // 本次需执行的阶段，稳定拓扑序
  reused_phases: Array<{
    phase: string;
    obligation_ids: string[];
    evidence_refs: EvidenceRef[];   // 复用现有证据引用形状
  }>;
  unresolved: Array<{
    obligation_id: string;
    needed_by: string[];            // 只阻塞真正依赖它的步骤
    owner: string;                  // phase、蓝图或既有外部 owner
    reason: string;
  }>;
  policy_fingerprint: string;       // 规则/workflow/contract 既有指纹组合
}
~~~

InputBinding/EvidenceRef 是既有形状的组合或 P1 类型，不新建引用注册表。
satisfied_by 只表达采用哪份满足依据，不能写 satisfied:true；完成时重验来源与证据。
phase_chain 不含已完整复用的阶段，也不含不存在的义务；
not_applicable 记录只解释本次规则候选，不给无限未出现 Skill 生成记录。

completion_target=request 用于仅设计/审查/测试等请求，完成时不能签发 Feature completion；
completion_target=feature 用于完整实现交付，必须覆盖当前适用目标与全部必需义务。
不能仅凭用户没有说“全部阶段”将正式实现降为 request。
已有显式授权终点继续有效；本字段描述完成语义，绝不产生新执行授权。

空执行链：允许全部由既有事实满足或只读任务完成；直接返回已有请求结果，
不启动要求非空 start/end 的 Goal run，不制造 exit 阶段。
Feature 完成若完全复用历史证据，走既有完成验证入口核验，不造零阶段假 run。

## 4. 计算、依赖与未知

统一入口 resolveExecutionScope 接受 normalized request、有效 P1 输入、已知当前事实、
workflow 和已有证据观察；输出上述纯结果。
交互、Goal 出生、显式 Skill 调用都复用；assess 后续只观察已冻结范围。

计算步骤：

1. 明确请求终点和正式性；正式实现仍经蓝图/CU，不新增规模评分逃逸。
2. 按当前任务范围选适用规则，求 required/not_applicable/unknown。
3. 用 P1 输入和既有证据判断哪些责任已被满足，列出真实剩余工作。
4. 对执行候选求信息闭包与真实控制边；已满足的信息不补 producer 阶段。
5. 稳定拓扑排序；同级默认串行，既有并行能力也必须遵守写集/设备约束。
6. 输出 unresolved 与首个可推进动作；请求范围不能在排序时扩大。
7. 冻结结果和理由，phase.next_step 从同一结果投影。

未知不裁掉责任，但也不强行执行未知阶段：例如验收尚未定，只执行已明确需要的 spec，
设备义务保持 unresolved；禁止在缺乏用例时先启动 testing。
只影响远期阶段的未知不能阻塞本来可安全完成的前置调查；依赖未知的写入必须等待。
默认不额外问人，先用已有事实调查；确需授权或产品语义裁决时复用已有确认点。

真正顺序示例：需新设计裁决时先 plan 后 coding；构建后才能安装；变更后才有对应审查证据。
独立 review 读取已有代码，不要求本次 coding；独立 UT/testing 读取明确目标，
不能因旧 control_dependencies=[coding/ut] 强迫先跑不适用步骤。

## 5. 持久化与身份

沿总纲 §7 单一上下文权威：

- feature.yaml.execution_scope 仅是运行前候选，不能为无 run 的阶段报告提供完成血缘。
- 完整 Feature 交互交付在首个阶段前使用 goal-mode-entry.ts --prepare-run 创建
  manifest + run_created + run-control，再通过 attended attach 使用同一 GoalPhaseRuntime；
  无人值守走既有 detached 入口。两者均有真实 run_id、phase_start/attempt/run_end。
- manifest.execution_scope 是运行权威；既有 manifest.phase_chain 必须与其 phase_chain 一致，
  出生时同值绑定 run_created 与 computeManifestIdentityFields。P1 facts 基线在其后、施工前建立。
- explicit runId 时只读该 run；现代恢复只消费被冻结范围，不读取 Feature 候选作覆盖。
- 有活跃 run 的 Feature 普通“继续”先走既有 run 识别，不另写 Feature 范围开旁路。
- 旧 scope 缺失与新 scope 损坏严格区分。前者按 P7 legacy 语义，后者报告损坏并走恢复。
- policy 更新不直接重排旧 run；确需重验时按既有证据 stale 规则诊断并修正。
- 下发 hook 的 policy 快照携带必要的范围绑定；hook 只消费，不独立计算义务。

不新增 manifest 文件族、全局运行登记或跨模式同步协议。
feature.yaml 中的候选可以作为新 run 的出生输入，之后不是该 run 的活跃权威。

### 5.1 交互 Feature 的合法完成路径（意见 1）

采用已有 in-session Goal 身份，不建设无 run 完成协议。使用现有两步 CLI：

~~~bash
npx ts-node scripts/goal-mode-entry.ts --prepare-run --run-mode attended --project-root <host> --feature <f> --adapter <adapter> --requirement-file <request>
npx ts-node scripts/goal-mode-entry.ts --run-mode attended --project-root <host> --feature <f> --adapter <adapter> --run-id <prepared-run-id>
~~~

P2 修改 prepareGoalModeRun 的默认 start/end 来源：由已校验 scope 计算，
不能继续使用当前 CLI 的 spec/testing 缺省值覆盖动态链。其余回调和授权协议复用。
主会话仍是 transport，runtime 真实记录每个阶段执行、收敛和封卷；不用已有报告补造 phase_start。
collectCleanPassIssues、generateFeatureCompletion 与 verifyFeatureCompletion 使用同一 scope，
原件仍位于 goal-runs/<run_id>/feature-completion.json，Feature 根只放既有投影。
CU 只消费 VALID completion；只有 feature.yaml 或裸阶段报告必须无法通过。

adapter 缺 in-session/隔离能力时，报告已有能力缺口或使用用户已经授权的现有可用 transport；
不得静默制造运行历史或把任务降为无 run 完整交付。专项 request 沿 P6 §3.1，不受此要求牵连。
全复用场景只复核真实既有完成记录；没有合法 run 血缘不能凭空生成新的 completion。

## 6. 新事实、回退与证据复用

区分“进展变化”和“责任变化”：
阶段 PASS、测试 FAIL 只更新现有运行观察；新验收/接口/用户范围/蓝图事实才可能改变责任。

受影响集合由实际输入 binding、contract 消费关系与真实 control 依赖派生。
不构建任意语义 diff 引擎；若现有 binding 只能证明到一整个 artifact，则诚实失效其实际消费者，
不声称字段级精准，但不扩为整仓/整蓝图重跑。

- 相同范围内返修：沿现有 backtrack/correction，保留 scope。
- 必須补阶段或改冻结范围：由对应责任方形成新事实，沿现有 successor/重签路径创建新代范围；
  原 manifest、事件和旧完成事实保持不变。
- successor 继承既有预算/失败指纹治理，不能靠改范围清空重试预算或摆脱已知失败。
- 未受影响的 phase 仅在现有 freshness/closure 规则通过时复用，不靠“新代沿用”自动 PASS。
- spec 后补足验收属于合法局部修订；不要求入口预判所有后继。
- testing FAIL 本身不是删除 device-evidence 的新事实。缺设备、manual 或超时同理。
- 显式需求取消按既有授权处理并留下取消事实，不将其描述成“原本不适用”。

### 6.1 正常后继的边界交接（意见 3）

现状：inheritSuccessorManifest 主要替换身份和 start，旧 end/chain 仍继承；
harness/scripts/goal-phase-runtime.ts 的 acquireGoalLocks 持有 Feature/run 锁与 fenced owner。
本 plan 必须补接交接控制流，不能将“有 successor 函数”当成已经支持自动续建。
实现位置为 scripts/goal-phase-runtime.ts 的唯一 runtime；utils/goal-phase-runtime.ts 是兼容桥，
不得在那里另建阶段循环。attended host bridge 与 detached CLI 都调用同一后继创建函数。

顺序固定：

1. 当前 owner 在 phase 边界先接收真实产物与 closure；assess 根据新事实提出相关义务修订。
   无新事实、只有测试失败时不走范围续建。
2. runtime 校验修订依据及既有授权终点，确定一次后继 run_id。
   在原 events.jsonl 追加 scope_revision_requested，内容仅包含后继 ID、源范围指纹、
   新范围及其来源绑定、允许变更字段。此事件是既有日志中的交接意图，不新增状态文件。
3. 停止派发旧 phase，等待在途 callback/设备动作收束、完成既有写恢复/收尾。
   全部已执行阶段真实 closed 时以 CHAIN_SLICE_COMPLETED 封卷，但 unresolved 尚在，
   不生成 Feature completion；因设计缺口中止的真实失败仍按原 PARTIAL/HALTED 语义封卷，
   不将失败涂成成功。将“尚需后继继续”写入已有报告和返回结果。
4. 通过现有 finally/releaseAllLocks 与 releaseRunOwner 释放旧 run、Feature 执行权；
   不删活锁、不使用 force takeover。旧 runtime 完成释放后，薄宿主/进程壳才将交接结果
   交回同一个后继创建函数，不能趁旧锁还在先 spawn 后继。
5. 后继创建函数重新核对源封卷、交接意图和来源，再走原 manifest/run_created/run-control
   出生机制，写入现有 successor_of 与 supersede 审计关系；仅“带合法范围交接事件的成功切片”
   扩展为可续建来源。旧失败修复型 supersede 的规则不被全局放宽。
6. 后继正常获取同一 Feature 锁和新 run owner 后才能派发；attended 复用当前合法 transport，
   detached 复用当前进程执行入口。是否可继续仍使用既有授权/预算，不增加用户轨道确认。

成功前驱的历史证据不因记录后继关系被改成失败或删除；完成验证只在原规则认可的
CHAIN_SLICE_COMPLETED/COMPLETED 血缘上复用。PARTIAL/HALTED 前驱中的裸 PASS
不能被本次修订变为合法完成证据；需要时重验相关职责，保留原失败事实与累计预算。
被后继引用的事实/快照按既有恢复生命周期保留，不在正常续建时执行失败废弃型的误清理。

### 6.2 后继允许重签的字段

复用 inheritSuccessorManifest 继承后，由同一受校验出生入口应用范围修订：
execution_scope、phase_chain、start_phase、end_phase，以及与其严格同源的 chain_override 投影。
新起止必须取新执行链，不能沿用旧 end=spec；若需要首个实现/UT 基线，
按原出生规则在首次该类执行前冻结 run_base_sha，之后沿既有基线继承，不能重置漂移事实。

新 run_id/report_dir/created_at/successor_of 按原身份规则生成。
requirement、requirement_source_files、授权上下文、adapter/model/provider pin、
budget、fidelity、dependency_policy、pre_authorized_mutations 默认继承；
仅有已授权新需求等原机制允许的独立变更时才能按原合并入口修改。
scope 从 [spec] 扩展后继不构成修改预算/权限/fidelity 的理由。
新范围仍冻结原 completion_target=feature 与原请求目标，不能缩成“只完成 spec”。

### 6.3 “继续”、重复交接与中断窗口

普通“继续”按原 run 的 scope_revision_requested 与后继的 successor_of/出生事件定位，
不以目录 mtime 或“最新 run”猜测，不分配第二个后继 ID。

| 重入时的事实 | 唯一动作 |
|---|---|
| 已有新事实，但尚未写交接意图 | 原 owner 恢复到 phase 边界，再校验并登记一次 |
| 意图在，旧 owner 仍活跃/尚未合法收束 | 不启动后继；沿原 owner/中断恢复协议完成收尾，不强抢锁 |
| 旧 run 已封卷释放，后继尚不存在 | 用已登记 ID 补出生，重新检查新范围来源仍有效 |
| 后继只有 manifest 等部分出生文件 | 走既有 creation-incomplete 修复/诊断，不能当可 resume 或换新 ID |
| 后继出生完整但未执行 | attach-created 同一后继，Feature 锁确保只启动一个执行者 |
| 后继已执行或处于等待 | resume 同一后继，不重跑前驱 spec |
| 后继已完成 | 验证该后继完成资格并返回；不再次创建 successor |

重复请求必须复用同一交接意图和后继；冲突的意图/来源按已有损坏恢复处理。
不得为了实现事务完美再添加交接 manifest、租约或新 registry。

## 7. assess、driver 与完成

observeFeatureState 读取有效范围及 executed/reused 证据，不再用全 track 阶段作日常全集。
assess 统一产生继续、修复、回责任方、请求已授权动作或结束建议；
driver 保留权限、预算、进程生存和设备动作边界。不能新增另一份“下一 Skill”条件树。

verify-feature-completion/collectCleanPassIssues 必须从一开始支持新范围：
验证输入闭包、required 义务覆盖、所有执行阶段 closure 和所有复用证据有效性；
范围外阶段不要求 summary/report，范围内未知不能通过。
scope/phase_chain 从独立的出生权威取得，不能从 completion 自报 chain 反推。
P7 再把这一完成结果接到 CU/P3，不能放宽此处判据。

“最后阶段 PASS”“assess 无可执行下一步”“工具返回 completed”均不是完整完成证明。
未知阻塞与真正完成须产生不同推荐；phase.next_step 不出现范围外义务。

## 8. 验收矩阵

- 同一输入在交互/Goal 得到同一 scope、顺序、理由；仅执行授权方式不同。
- 只有 UT 所需目标且用户只跑 UT，chain=[ut]，completion_target=request。
- 已有有效设计与验收的实现任务，scope 不因缺叙述 spec/plan 生成上游阶段。
- spec 后新增 device AC，仅重判受影响后继并签发新范围。
- coding 发现新公共接口，返回 plan 或蓝图责任方，完成后回施工；未受影响审查/测试按证据复用。
- testing FAIL、设备离线、manual、report 失败均不缩减 scope。
- 当前 workflow/模型配置改变后 resume，读取冻结结果；manifest 损坏不回退。
- completion 自填 chain=[ut] 而有效 scope 还需 review，验证失败。
- 无设备义务，完成与提示不读 test-report；R8 失败仍无法绕过。
- 新 custom phase 未登记适用规则/输入，不能静默忽略；旧 workflow 保持历史语义。
- 全部证据可复用时不创建空 run，仍验证当前目标覆盖。
- scope 修订预算不清零、原历史不被改成 pending。
- 真实 goal-mode-entry --prepare-run/attach 交互执行 coding→review→ut，
  原件/phase_start/attempt/run_end 血缘完整，verifyFeatureCompletion=VALID 且 CU 可消费。
  只有 feature.yaml 与裸报告的负例必须 INVALID，不能由测试伪造 events 证明通过。
- 从真实 CLI/bridge 执行仅已确定 [spec] 的完整交付请求，spec 产出 device AC 后触发
  §6.1 后继：核验旧锁已释放、新 end/phase_chain 正确、自动进入后继并最终完成；
  在意图后、释放后、出生后/派发前分别中断重入，只有一个后继和一次首 phase 执行。
- 仅缺远期依据时当前可安全调查推进，依赖未知的施工不会启动。
