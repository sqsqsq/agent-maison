# 复杂能力建设 3.1：P2 Change Unit、设计消费与连续推进

## 1. 计划定位

P2 位于 P1 部件演进蓝图之后、P3 Component closure 之前。它把已经评审和准入的蓝图设计切片登记为
可独立施工、验证和安全合入的 Change Unit，让现有 Feature/Goal Mode 一次精确执行一个 CU，并在每个
单元结束后根据蓝图、依赖、blocker 与既有完成事实重新派生下一步。

本 plan 与 OpenSpec `change-unit-and-continuous-progression` 成对：plan 约束实施顺序、权责、真实宿主
入口和验收；OpenSpec 锁定 schema、design gate、Feature 投影、ready/blocker 与推进语义。本轮只完成
设计起草和校验，不实施 P2 生产代码、不勾选上述 todo，也不进入 P3。

## 2. 权威输入、输出与消费者

权威输入为：

1. 复杂能力建设总纲 `complex-capability-construction-75411223`，重点 §3.3、§4.3–§4.5、§6.1、
   §6.6、§7、§8、§11.2、§11.3、§12、§14 和 §15；
2. 3.1.0 总计划 §6.3、§8.1、§8.2、§9、§12 和 §13；
3. 已归档 `openspec/specs/complex-capability-meta-model/spec.md` 的单向引用、权威边界、provider
   生命周期、三依赖命名空间和宿主演进接缝约束；
4. P1 change `app-component-blueprint-and-reconciliation` 的 `app-component-blueprint` capability，
   尤其 canonical artifact、stable address、设计准入、runtime flow、调和与 P1/P2 边界；
5. 既有 Feature artifact schema/loader/checker、Goal Mode manifest/events/reducer/receipt/evidence、
   `verifyFeatureCompletion()` 与恢复链。

P2 交付：

- `change-unit@1` canonical artifact/ref 与最小有界变换契约；
- P1 `component_blueprint_ref` 的统一 `design_refs` 消费和当前 delta 设计可施工门；
- 当前 CU 到既有 spec/acceptance/plan/contracts/use-cases/UT DAG 的 ID-only 施工映射与机械派生义务；
- exact requires/provides、结构化 blocker、execution-precedence 环检、ready set 与稳定单选；
- 复用既有 Goal Mode 的单并发薄推进循环和滚动重派生；
- 正常、失败、阻塞、恢复、stale、completion 四态、重复 Feature identity、provenance/provider 生命周期和宿主演进接缝纵切 fixture。

P2 的直接消费者是当前 CU 的 Feature spec/plan/coding/review/UT/testing/Goal Mode，以及后续 P3
Component closure。P2 不替 P3 聚合目标、风险、全部视图/运行时边和组合证据。

## 3. 边界与唯一权威

| 信息 | 权威位置 | P2 行为 |
|---|---|---|
| 当前实现事实 | 代码/schema/接口/配置/测试 | 通过蓝图/current facts 和施工检查引用，不复制 |
| 部件目标态、共同决策、适配 4+1 与 runtime flow | P1 canonical blueprint | 只用稳定 ref 消费，不回写 CU 状态 |
| 当前 CU 设计定义 | `change-unit@1` | 定义 predicate/provide/design ref、验证义务、provenance 与安全中间态，不写施工落点 |
| 当前 Feature 施工映射与运行时事实 | `contracts.yaml` ID mappings + `contracts.state_management` | 映射 CU ID 到文件/符号/测试；运行时细节只写 state_management，不重定义 CU/蓝图 |
| run、恢复和完成事实 | Goal Mode events/reducer/receipt/evidence/completion | 只读和验证，不直接写 done |
| requires/provides、ready/blocker | CU 契约 + blocker probes + 既有完成事实的派生 | 不落可编辑队列或 ledger |
| Component closure | P3 后续 change | P2 只返回可交给 P3 评估，不宣称 closure |

`goal_requires/goal_provides`、CU `requires/provides`、Maison capability seam 依赖保持三个独立命名空间；
宿主演进接缝仍是蓝图内的宿主设计内容，不进入任何 Maison provider registry。

## 4. Change Unit canonical 契约

### 4.1 路径与身份

```text
blueprint/component/<component_id>/change-units/<change_unit_id>.yaml
```

只增加 component/unit 到上述路径的最小解析。部件单元枚举只读取该目录并稳定排序；不扫描 Feature、
legacy 或任意 path，不新增全局 manifest。蓝图不反向持有 CU 列表或运行状态。

根对象必须包含 `artifact/component_id/change_unit_id/revision/priority/component_blueprint_ref/provenance`
及最小有界变换字段。`provenance` 复用 P1 的来源结构，正式来源指向蓝图/权威事实，Provider 只可记录于
extraction method。`component_blueprint_ref` 必须 target blueprint；Feature 通过包含 revision 和 CU 原始字节
hash 的 `change_unit_ref` 绑定当前施工版本。根对象禁止 `execution.feature_id/ready/status/completed/closure`。

Feature identity 由 `cu-` + `base64url(UTF-8(component_id + "\0" + change_unit_id))` 单射派生；schema
拒绝 authored override。派生 Feature 路径若已绑定其它 CU 或存在不匹配的非空 Feature，必须报 identity
冲突而不接管。fixture 同时覆盖两个 CU 复用 Feature、未执行、有效完成和篡改完成事实。

### 4.2 最小语义

- `purpose` 与 `target_predicates` 说明本单元改变什么能力/风险以及完成谓词；
- `preconditions`、`requires/provides` 和 blocker 说明可进入施工的真实前置；
- `touches` 说明写集、owner 与相关 development node；
- `preserved_invariants`、`safe_intermediate_state` 证明单独合入仍正确；
- `verification_refs` 绑定适当层级验证；
- `provenance` 说明正式 CU 依据的蓝图/权威事实与消费者接受过程；Feature identity 按 §4.1 派生。

CU 定义 predicate/provide/design ref 及验证义务，设计可施工门只证明有界 delta；它不要求尚未规划的
文件、符号或测试落点。具体施工映射由 Feature gate 独立验证，禁止把施工坐标反写成 CU 的第二定义。

纯横切只有具备稳定契约、真实 consumer/可执行验证、安全中间态且无需后继推翻核心设计时才成立。

## 5. `design_refs` 与设计可施工门

所有设计切片继续使用 P1 `component_blueprint_ref`，不增加 logical/runtime 等 per-view 字段。owner ref
与 design refs 的 blueprint identity、revision、source/artifact fingerprints 必须一致，并先通过 P1
canonical schema/完整性门再解析 target。

设计门从 target predicates、touches 和 design roots 派生闭包，至少核对：

- touches 是否映射到真实 development owner/node；
- 被改变节点的 relation、decision、contract design basis 是否齐全；
- 关键 scenario 是否贯穿相关 logical/runtime/development/适用 deployment；
- runtime flow 的条件式 owner、producer/consumer、恢复与验证是否进入施工切片；
- 当前闭包内的 unknown/open decision/blocker 是否已合法处置。

闭包外远期 open decision 有 owner/needed-by 时不阻塞。施工发现新事实推翻蓝图时先路由 P1 调和，
不让 Feature plan 用 TBD 或无权威推断继续。

## 6. Feature 施工映射与运行时真源

- spec/acceptance 通过 CU ref 解释 purpose、用户可见语义和目标谓词；
- plan 展开当前 CU 的数据、接口、控制/领域、展示、文件、测试和安全中间态；
- contracts 绑定 `change_unit_ref`，仅以 `predicate_mappings/provide_mappings/design_ref_mappings` 将
  canonical CU 中已有的 ID/ref 映射到真实文件、符号、测试和 verification refs；禁止复制或重定义
  purpose、predicate/provide 描述及验证义务；
- `contracts.state_management` 继续作为 Feature 施工阶段运行时事实唯一权威；CU 只存 P1 flow/design
  稳定引用，不新增 `runtime_flow_slices` 或复制 trigger/mutation/publication/subscription/consumer；
- coding/review/UT/testing 对 canonical CU required ID、真实符号、写集、跨视图关系和 runtime 边反查。

CU-bound `use-cases.yaml` 必需性从多步顺序、失败/重试/恢复/补偿、共享状态多消费者、生命周期/后台/
定时/外部恢复等事实机械派生；ephemeral DAG 必需性从 unit/both 目标的多实现/边界步骤、分支恢复或多
consumer 传播独立派生。必需却缺失时 BLOCKER，不接受 authored opt-out；简单单步可沿用 UT tags/AC
coverage。use-case/DAG 只是施工测试投影，不反向定义 state_management。

只读/首次加载流不伪造 mutation/订阅；声明写入后必须闭合 publication/invalidation 到受影响 consumer；
声明订阅后必须有 snapshot/replay 与 cleanup；后台/外部写入必须有持久化和恢复。首次建立共享主链或
宿主演进接缝的 CU 必须纵切包含真实 owner/Provider、Consumer 和验证，禁止空 Store/EventBus/接口。

## 7. 依赖、blocker、ready set 与选序

首版 `provides` 使用稳定 `provide_id`；`requires` 显式指定同 blueprint 下的 `from_change_unit_id` 和
精确 `provide_id`。provider CU 的派生 Feature completion 经权威入口为 VALID，且该 CU 的全部历史稳定
target 在当前蓝图仍可解析并获准时才满足依赖。外部契约/当前代码/人工裁决进入 precondition/design
ref/probe，不伪装成 CU provides。

blocker 必须有 owner、影响门槛、原因、解除条件和来源；机器可观测条件带 probe。ready set 每次从
CU、当前蓝图、design gate、blocker、active Goal runs 和四态 completion observation 重建，不读自报
ready/done。Feature id 按 §4.1 派生；expected workflow/track/chain 分别由 `resolveWorkflowSpec()`、
`resolveFeatureTrack(loadFeatureTrackDecl())`、`featurePhasesFromWorkflow()` 从现有 SSOT 解析。

无 completion projection 且没有权威终局 run 声称跨过 completion 生成边界时为 `ABSENT/not_completed`
（包括从未执行、active、failed、paused）；终局完成事实存在但 projection/original 缺失为 `INVALID`；
projection 存在时调用 `verifyFeatureCompletion()` 并保留 `VALID|STALE|INVALID`。`ABSENT` 可在其它门
通过后成为首次/继续执行候选；`STALE` 仅在当前 CU/design/Feature mapping 已重校验后成为重执行候选；
`INVALID` 作为证据完整性故障阻塞，损坏事实不得伪装成从未执行。
严格 requires 投影必须无环；环内单元不 ready，并路由契约冻结/seed/fake/协调/合并或重拆。存在未完成
目标但既无 ready、active run 又无合法 blocker 时报告 silent stall，不能当作完成。

选择按较小 priority、再按 `change_unit_id` 稳定升序；一次最多选一个。priority 与实际执行顺序不写回
依赖。ready set 可含多个候选，但 3.1.0 不因此引入并发、锁或多 writer 恢复。

## 8. 薄 Goal Mode 推进循环

```text
读取 canonical blueprint/CU 与既有 Goal Mode facts
  → 校验设计可施工并派生 ready/blocker
  → active run 存在则恢复/等待，否则稳定选择一个 CU
  → 以 CU path/ref/hash 与派生 Feature id 调用既有 Goal Mode Feature
  → 用 workflow/track-derived expected chain 和 verifyFeatureCompletion() 形成四态完成观察
  → 重新读取 blueprint/CU/facts 并派生下一步
  → 无未完成 CU 时交给 P3，或以明确 blocker/停滞结束
```

循环不持久化自身状态。失败、暂停、待人工、retry/backtrack/resume 继续由 Goal Mode 处理；中断后重读
事实即可恢复。蓝图或 CU revision 改变使未实施 CU 的施工/ready projection stale；已完成单元保留原始
绑定和历史事实。首期只把其全部历史 stable target 交给当前 P1 resolver/admission：全部仍可解析且获准
才整体 carry-forward；任一缺失、替换、unknown、open decision、blocker 或未准入都阻塞依赖并回 P1
调和。P2 不建设 semantic diff/`invalidates` 引擎；需要纠正时创建新的 revising/superseding CU，不原位
改写历史单元。

## 9. Provider 接缝

按 P0 三角色契约，P2 只设拆分策略、关系/ready 分析器、候选 selector 三个 capability seam；完整
Seam Card 以 OpenSpec capability spec 为唯一规格。首期均静态内置：拆分 provider optional，缺失时允许
提交人工/Agent 候选走同一消费者校验；自动推进所需 analyzer/selector required，缺失或权威冲突时
fail-closed。拆分 Provider 只产出内存/临时报告候选，consumer 校验 schema、设计闭包、provenance 和
来源权威后才写 canonical CU；Provider 退出只清理未接受候选/派生报告并重算，不删除正式 CU 或 Goal
Mode 完成事实。全程不新增 registry/ledger。

## 10. 实施顺序

1. 落 `change-unit@1` schema、provenance、path/ref/loader/validator、单射 Feature id 和 identity 反例；
2. 接 P1 resolver、当前 delta 引用闭包与 constructability checker；
3. 同源扩展 Feature contracts/type/loader/use-cases/plan/UT 检查与 Skill，落实 ID-only 映射、
   `contracts.state_management` 权威及机械 use-case/DAG 义务，不改变无 CU Feature；
4. 实现 exact dependencies、blocker probe、四态 completion adapter、cycle/stall、ready set 和 selector；
5. 实现派生 Feature id、workflow/track-derived expected chain 的无状态 Goal Mode 薄调用与 completion 对账；
6. 接入静态 provider/Skill index，补正反 fixture 和集成测试；
7. 在真实 AI 记账蓝图材料到位后执行首个纵向 CU，记录 framework 缺口并回灌。

## 11. 完成判据与反例

P2 framework 至少证明：

- 三个有真实前置关系的 fixture CU 由同一薄循环逐个完成；
- 多 ready 时只选择一个，tie-break 确定且不制造依赖；
- 悬空/混 revision `design_refs`、遗漏当前 delta 关系/场景、当前相关未决项均阻塞；
- Feature mapping 能抓缺失/未知 ID、复制定义和重复 Feature 绑定；`contracts.state_management` 保持唯一
  运行时施工真源，use-case/DAG 必需性由事实机械派生；
- runtime 施工门能抓 orphan publication/consumer、缺 snapshot/cleanup、后台恢复断链，同时不迫使
  简单只读流伪造写入、订阅或 flow artifact；
- 空 Store/EventBus/接口横切、无安全中间态和首次接缝非纵切均失败；
- requires 环、未满足依赖、结构化 blocker、silent stall 有明确诊断；
- CU 自报 ready/done 不得放行；never-run=ABSENT、有效=VALID、篡改/缺失完成证据=INVALID、漂移=STALE
  的反例必须分明，expected chain/track 只从现有 workflow/track SSOT 解析；
- 已完成 CU 只有全部历史 target 当前可解析且获准时 carry-forward，缺失/替换/unknown/open/blocker
  回 P1 调和，不建设语义 diff；
- Goal Mode 失败/暂停/恢复使用既有事实，外层不启动第二 CU；
- decomposition Provider 退出只清临时候选，正式 provenance-bearing CU 保留；
- P2 不创建 P3 closure、跨单元 ledger、锁、daemon、第二恢复目录或全局 registry。

本地实施验收按实际改动运行专项 unit/fixtures、Goal Mode 集成和受影响 harness；设计/状态返修只运行
相称门禁。整仓 `--release` 与 `release:verify` 继续由总计划 m5/MG 承担。

## 12. 真实宿主验证

首个宿主固定为 AI 记账 App 的真实账目数据域，但 CU 顺序不在本 plan 预定。材料到位后从 P1 蓝图派生

## 13. 父目标必答七问

1. **推进目标**：G5 Change Unit 关系/分解与 G6 Feature/Goal Mode 接入。
2. **所属层**：change-unit 执行层；P1 负责共同设计，P3 负责组装覆盖，P2 只负责有界施工与推进。
3. **输入/消费者**：输入为 P1 canonical blueprint/CU artifacts、Feature schemas 和 Goal Mode facts；消费者
   为 Feature phases、薄推进循环与后续 P3。
4. **新增状态/索引/裁决**：新增正式 provenance-bearing CU artifact 和可重建派生结果；Feature id 单射
   派生，completion 四态不落盘；不新增完成状态、全局索引、registry 或恢复权威。CU artifact 是施工
   契约所必需，既有 Feature plan 不能承担跨单元身份与依赖。
5. **避免双真值**：目标设计只引用蓝图，CU 定义义务，Feature contracts 只做 ID→施工坐标映射且
   `contracts.state_management` 保持运行时施工真源；完成只认 Goal Mode，ready/cycle/selection 可重建。
6. **真实宿主证明**：AI 记账真实依赖 CU 经现有 Goal Mode 连续推进，运行时流和演进接缝落到真实代码、
   build/test/evidence，而不是只让 fixture 变绿。
7. **退出条件**：若机制不能比现有单 Feature 路径多发现 design ref/依赖/运行时断链，或真实宿主没有
   多单元消费点，则不扩展关系或调度机制；保留稳定 CU/蓝图引用，撤去无消费者 provider/投影。
