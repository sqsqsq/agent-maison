# 知识统一发现、采纳与维护闭环

## 1. 目标与范围

让 Agent 在动笔前找到适用知识，沿既有权威链用于设计、施工与独立审查；任务完成后，已授权的派生刷新和稳定结论归位能落实到原资产，下一任务直接复用。改善的是“资料已经存在但入口没送到、现代调用漏审、维护只剩 checker 没有生产者”三个实际缺口，不另建知识治理系统。

本 plan 是知识层贡献，不替代蓝图设计权威、CU 施工契约或 Goal 完成事实。遵守 [四条总原则](../../docs/overview.md#121-四条总设计原则)：一次装配、现算现用；错误回已有责任方修复；自动恢复不扩大授权。

保留 `doc/module-catalog.yaml`、`glossary.yaml`、`architecture.md`、`conventions.md`、`component-index.yaml`、`component-catalog.yaml`、`<module>/code-graph.yaml`、`doc/extensions/knowledge/` 及发布件 `framework/docs` / `profiles`。实际路径一律经配置与现有 resolver；上述仅是默认位置。“内部 / 周边 / 通用”用于描述语境，不增加必填分类或目录。

不新增 `doc/knowledge`、向量库、动态 registry、知识状态机、已读证明、维护台账、新 phase/CLI、场外状态、全局知识版本或全量失效机制。不将全部知识变成 InputBinding，不复制 manifest 文件条目、阶段义务、权限和 checker 规则。gate 是验证责任，不是知识送达方式。

## 3. 共享装配及送达

### 3.1 一份运行时视图

新增 `harness/scripts/utils/knowledge-context.ts`，集中小型静态种类表、`assembleKnowledge(context)` 和共享 renderer；规模无需拆成插件框架。表只登记原生种类、路径解析及默认送达。extension 条目从 `loadInstanceExtensions` 现读，profile 资产从 `profile-skill-assets.ts` 现读，不再列一份文件清单。

context 复用调用者已有的 project/framework root、实际 skill/phase、subject（feature、request 或尚无 feature 的 component-design）、需求原文/已有来源、目标模块/文件、author/verifier 角色及预算。静态入口无任务正文时只渲染路径和读取职责，不猜当前任务、不造 Feature。准备期拿不到的字段保持缺省，不能为了凑 context 提前冻结范围。

结果是稳定排序、去重的内存条目和文本：来源路径、原有条目/锚点、用途、送达形态、缺失或未展开原因。只有既有 prepare 输出、prompt、入口文件等载体落盘；它们都是可重建投影。发现/背景不具有新权威，真正采纳仍进入既有 facts、provenance、design_refs 或 contracts 投影。

| 知识 | 解析与送达规则 |
|---|---|
| 画像 + 术语 | 复用 `loadCatalog`、`loadGlossary`、`allKnownTerms` / `lookupTerm` / `findModulesByTerm`。从需求原文发现 term/alias 字面候选，只保留与本次 query/命中条目相关的易混项，连同反例/不负责范围和关联画像送达；不沿用与 query 无关的易混命中污染预算。候选不自动变成确认结果，alias 不冒充精确 high。无命中仍给完整索引路径供探索 |
| architecture | 用 `architectureMdPath` / `relArchitectureMd`；设计、plan 与确有架构上下文的审查读取适用正文/段落，保留 config DSL 与架构说明原来的职责 |
| conventions | `conventionsPath` / `relConventions`；按现有小规模全文阅读要求送达。review 独立读完整文件和适用范例，不能只拿作者的 `conventions_applied`。缺省不存在=未启用，显式配置不可读=如实缺失，沿原有检查处置 |
| 组件资产 | `readComponentIndex` + `readComponentCatalog` 按稳定 id join；复用 `componentReviewContext` 的 live 检索，明确样本上限不是全量引用数。保留完整库存/策展卡可达、源码反查、P1 选型权威与 contracts 投影，不复制 index 字段进 catalog |
| CodeGraph | 复用 `resolveGraphModule` / `moduleGraphPath`、`parseCodeGraphFile`；按相关模块与目标文件导航 signatures、nodes 和关联边。core 只高亮，非 core 也可命中；无图回源码探索，不强制建全仓图。core anchor/drift/UT 原义务不变 |
| extension | 保留 `safeResolve(extRoot, ref)`。global、Feature phase audience、显式 bindings 都从原 manifest 派生；同一路径去重，槽位标签保留。manifest 非法继续复用既有诊断，不在装配器再设阻断门 |
| framework / profile 背景 | 给发布件 `docs/README.md`、当前 profile 的知识/Skill 入口；具体材料沿当前 Skill 的现有 `profile-addendum.md`、`skill-assets.yaml` 和链接解析。读取相关资料，不扫全文 vendor/docs，也不把资料复制进宿主资产 |

pointer/index/inline 按用途与预算选择：候选带足够信息供首次判断，路径始终完整；过大正文改为原路径和分批读取指令。必须材料不能静默截断、丢失或借预算豁免；确实没读完如实说明。conventions 全文、设计所需完整组件库存等是阅读要求，不等于必须一次塞进 prompt。能力、权限及失败处置沿原机制，装配器不裁定“知识充分/任务通过”。

### 3.2 全部实际入口

- **Goal 作者**：用 manifest 原始 requirement、真实 phase 与目标构造 context，`buildPhasePrompt` 接受共享渲染块，替换 extension-only 装配。保留非法 manifest 警示与作者继续的既定行为；不触碰本文件其它执行、恢复和超时逻辑。
- **交互**：`--prepare-scope` 按求得的 phase chain 给任务候选，`--prepare-request` 用实际 targets、需求/请求原文和 inputs 给候选。后续 Skill 在主产物前按该输出读取；prepare 未传递的新鲜正文不复制进持久绑定。request 保持其现有能力和报告边界，不借本任务新建独立 request verifier 管线。
- **AGENTS/CLAUDE**：共享 `templates/AGENTS.md.template` 保留原生路径，增补 phase audience 表（包括 1.1 字符串面向全部 Feature phase），与 global、before-work 统一呈现。新增模板变量须同步 `LegacyRenderEnv` / `legacyRenderEnvToTemplateVars` 和 `check-init.buildRenderEnv` 的映射，保证 init 与 render-agents-md 同源。“现在可读的知识”与“未来槽位要执行的动作”分开描述，after 槽位不得提前执行。phase 名来自 active workflow，禁止硬编码仅内置七阶段。
- **extension inspect**：复用同一 entry/routing view，保留 available/scheduled/evidenced 的现有含义；有路径/指令仅证明可用或送达，不声称 Agent 已读/已完成。
- **verifier**：见 §4；自定义 workflow 启用 global verifier 时，catalog/glossary/docs/init 的既有上下文仍可达，不能以默认未启用为由删分支或混入 Feature 材料。

### 3.3 component-design 的前置接线

选择一个静态投影位置，避免逐 adapter 复制资料表：`buildAgentsTemplateVars` 调用共享装配器的 `skill=component-design` 静态视图，在 AGENTS/CLAUDE 输出“component-design 设计前知识”段。`agents/shared/agent-bundle/templates/skills-bridge/component-design/SKILL.md` 与 `agents/{cursor,claude,codeagent}/templates/commands/component-design.md` 显式指向该段和根 Skill。`materialize-agent-bundle-skills.ts` 的 bridge/inline 入口保持同一读取指引，不把 verbatim 模板误当已调用动态 renderer。

**实际 asset key 与读取协议**：可选 `provides.skill_assets.component-design.knowledge`。先查当前 extension manifest 中此 key，由 loader 按 `safeResolve(extRoot, ref)` 解析扩展根相对路径；未声明才查当前 profile 的 `skill-assets.yaml` 中 `assets.component-design.knowledge`，按既有 profile 路径规则解析。两处均未声明＝合法无此资产，根 Skill 与入口如实说明；已声明但不可读沿既有错误诊断，不假装未声明或静默回退。`assembleKnowledge` 的 component-design 分支用已加载 bundle 与 `resolveSkillAssetPath(..., 'component-design', 'knowledge', ..., bundle.skillAssetAbsPaths)` 实现这一顺序，renderer 输出真实项目路径。

根 `component-design/SKILL.md` 用上述文字步骤，在 P1 discovery 前打开实际文件并保留原文路径；**不写会被 docs 硬解析的 `profile-skill-asset:component-design/knowledge` 引用**。直接调用根 Skill 同样先查当前 extension、再 profile，AGENTS 投影只作导航。同步 `skills/README.md` 的 asset 协议说明（补实际 extension 优先规则）、`docs/operations/component-design-host-adaptation.md` 与 `skills/project/extension/SKILL.md` 的具体 key/caller；不修改 docs 校验器，不发明 optional 标记，不为未启用的宿主补占位资产。

`current-facts-discovery` 取得 catalog/glossary/graph/architecture 和已物化周边资料；`conventions-knowledge`、`component-assets` 保留各自专业消费与验证，`app-design-lens`、独立质询不充当事实源。六静态 provider 是职责/校验接缝，不是机器自动执行器。设计读取发生在蓝图生成前，而 `evaluateDesignPreparationEntry` / `acceptChangeUnitDecomposition` 仍只处理 admitted 之后的工作。

`requirement-source-materialization@1` 只负责正式需求来源到 `current_scope_items` 的 requirement/goal/invariant/high_risk，不吞并所有外部接口契约。`blueprint-contracts.ts` 继续逐段解析项目内 `source_ref`、权威 operation/DTO/mapping 等；直接人工/inline/本地来源仍合法。同一份原始资料可被多个消费者引用，不复制为第二份契约或扩大其 authority。

### 3.4 兼容

- schema 1.0 `provides.knowledge` 维持现有“声明可检视、无 1.1 自动路由”语义；不能在本次偷偷转成全部阶段或设计前输入。
- schema 1.1 对象按 audience，1.1 字符串按全部 Feature phase；`skill_assets` 延续其现有版本支持和 extension 覆盖规则，不增加 audience 值。
- phase bindings 三槽位、hooks lifecycle、MCP action 的调用与产物门禁均不变。发现时可展示后续槽位但不得说它已经执行；`before_phase_verify` / `after_phase_verify_before_close` 的时序仍由现有 harness / receipt 调用负责。
- 迁移说明给出 1.0→1.1 的显式适配示例和 component-design key；本次不编辑真实宿主 manifest，不把隔离副本适配称为宿主已升级。

## 4. 独立审查与指纹闭环

将 `collectContextFiles` 内知识分支收编至共享装配，typed 输入/产物读取与 legacy 读取保持原职责，二者都接知识与相关目标源码。`componentReviewContext` 的专业 join/live 检索可以保留为 reader，删除外围重复路由/渲染；审查不只看作者挑出的条目。global 分支继续使用其适用材料，缺 Feature 合法。

Step 4 的 `assembleAIPrompt` 和 `buildVerifierMaterialView` 消费**同一次装配**的内容及真实路径。pointer 的实际相关材料也进入既有 `files` 哈希；不要继续只 hash 一段相同的路径文本。合成的候选/live 样本须能关联到其源文件，必要时使用实际渲染文本进入既有材料分量，不能给虚构 label 当文件。独立核对要打开的 conventions 范例、组件定义/调用样本按本次实际送达来源绑定，不全仓入材料。

保留 `extension_sha256`、`goal_brief_sha256`、input bindings 与既有 material schema/subject 链，复用已有字段，不新增全局 knowledge hash。路由/正文变化只影响相关审查；无关阶段资料变更不让所有 run 失效。当前按整份小文件提供的素材，文件内变化导致该次材料变化是允许的保守粒度，不引入 semantic diff。

验收须区分两件事：材料变后不得当作 **same-material PASS** 复用；若现有 policy 允许 `completed_with_prior_review`，仍按既有规则明确披露 `current_material_not_reverified`，本次不改成一律重审或取消旧政策。材料与 authority 是否相关按实际内容/消费者判断，不按文件名是否含“契约”一刀切。

## 5. 维护与生产侧归位

| 动作与责任方 | 时机 / 写入边界 |
|---|---|
| Agent 读取最新知识用于当次判断 | 每次实际 prepare、作者/审查装配和 P1 discovery 现读；不把发现、读取等同长期规范写入 |
| 派生资产 writer | 复用 `bootstrap-code-graph.ts` 的 derived-only、`bootstrap-component-index.ts` 的源码重扫；默认在相关 Feature/CU 的 run 收口后、P3 closure 前，通过原维护入口执行**已获授权**的刷新并用原 checker 校验。收口本身不授予新写权限；同模块仍有受影响活跃 run 时不在其工作树写入。run 内确需刷新图文件，须先由既有权责链把它明确纳入 `contracts.files`；不能仅凭模块目录或“机械更新”取得授权。未授权只读场景不写，verifier 不刷新资产，不覆盖 graph nodes、策展 catalog 或静默刷新 core hash 掩盖漂移 |
| 术语/画像 writer | `catalog-bootstrap` 与现有 spec/P1 已确认术语回写。已确认同一决定不重复确认；新增映射、职责/易混项、core/intent 等语义变化仍走现有策展确认与 diff。catalog/architecture 不提前把蓝图目标写成当前事实 |
| 惯例/组件策展 writer | 继续 `conventions-bootstrap`、`component-catalog-bootstrap`；重复 review 意见只形成候选，不能自动变成规范。已有明确授权覆盖精确条目时复用授权；仅“继续执行”或临时推测不能补成确认。组件合并复用 `mergeComponentCatalog`，不新增审批字段/台账 |
| extension / framework / profile | 宿主 extension 由其 owner 在既有 scope 内维护、verify/materialize；发布件背景由 framework/profile 维护者随发布更新。消费者不编辑 framework 资料，统一 reader 不成为万能 writer |
