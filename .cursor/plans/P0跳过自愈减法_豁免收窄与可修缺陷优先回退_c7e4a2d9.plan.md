## 0. Review 冻结面

### 0.1 宿主事实

实例目录：`D:/1.code/SimulatedWalletForHmos/doc/features/bc-openCard-1`。

本次不是设备进程卡死，而是 testing 真实执行完成后，被框架主动停放：

1. `testing/reports/summary.json` 为 `verdict=FAIL`；
2. `p0_coverage_integrity` 因 `TC-018` 未执行且无 waiver 失败；
3. 同一份 summary 已有 3 个可信 `repair_candidates`，均指向产品视觉修复；
4. assess 已给出 `rerun_phase:coding` / `runner_action=backtrack_to_phase`；
5. `goal-runner` 的 `await_human_p0_skip` 专用 guard 先写死 `halt`，
   `goal-assess-driver` 按契约不得覆盖 guard halt，于是正确的 assess 建议失效；
6. `TC-018` 的实际原因也是仓内可修：`BankRepository` 被页面直接实例化，空数据与异常态
   无注入接缝，testing 又被禁止改产品源码。这里需要回 coding，不需要人替框架判断
   “要不要先修”。

另有一个会在回退后继续阻塞的确定性矛盾：

- `report_trace_reconciliation` 要求报告表逐条等于 trace；trace 的成功状态名是“通过”；
- `pass_rate_calculated` 在 `--skip-assert-expected` 存在时要求报告表“通过”条数为 0；
- goal 真机路径又恒开该旗标。三者同时成立时，无论 agent 怎么写报告都至少失败一条门禁。

### 0.2 根因，不把症状当方案

根因有五层，但只需一条主线修复：

| 层 | 当前问题 | 本 plan 的收口 |
|---|---|---|
| 权限语义 | “不能自签 waiver”被扩大成“不能自主修复” | 默认修复；只有降低标准才求人 |
| 决策优先级 | 专用 P0 halt 抢在可信候选与 assess 之前 | 删除抢跑特例，走统一候选路由 |
| 事实供给 | `report_validity!=PASS` 清空所有候选，包括机器 check | 只抑制报告文本候选，不抑制机器事实 |
| 优先级锚 | P0 分母信任 agent 自写的 TC 优先级，P0→P2 可令缺口消失 | 用冻结 acceptance 的 P0 AC 反校验 P0 TC 覆盖 |
| 报告口径 | trace 状态必须写“通过”，另一门禁又禁止写“通过” | 保留 trace SSOT，删除互斥断言 |

不采用以下“补丁式方案”：

- halt 后自动 `--resume`：仍然会命中同一专用 halt，只是制造循环；
- 给 `await_human_p0_skip` 再加一个例外白名单：继续扩大平行路由；
- 新造 `skip_reason_class` / `repairability` / `responsible_phase` 让 agent 自报：增加不可信真源；
- 自动签发或伪造 `p0_skip_waiver`：直接越过人类授权边界；
- 为这一个事故建设新状态机、队列、supervisor 或场外恢复账本：既有 assess/backtrack 已完整；
- 依赖候选指纹发现 P0→P2 降档：降档会让候选根本不产生，指纹无从比较；
- 要求报告把 trace 的“通过”改成“阻塞/跳过”：会破坏证据对账，属于为过门禁改事实。

### 0.3 最小目标流

```text
冻结 acceptance 优先级锚
  ├─ device/both P0 AC 有至少一条 P0 TC → 进入 P0 全分母门禁
  └─ 仅被 P1/P2/P3 TC 覆盖或无覆盖          → acceptance_to_test_case BLOCKER FAIL；testing 修复

P0 全分母门禁
  ├─ 全执行通过                     → PASS
  ├─ 有效真人 waiver                → WARN；封顶 AWAITING_HUMAN_REVIEW
  ├─ 已登记外部依赖                 → 既有 DEFERRED / external 路径
  ├─ status 为空/未登记 trace skip   → FAIL；testing 修复执行或派生计划
  └─ 未豁免且全为 explicit skip     → FAIL + repair_candidate(coding)
                                           ↓
                              assess: backtrack_to_phase(coding)
                                           ↓
                              coding 修最小可测性/产品缺陷并重跑
                                           ↓
                        同指纹无进展或预算耗尽才由既有熔断停下
```

核心判定只有一句：**不降低验收标准的修复不是授权行为。**

### 1.3 唯一新增接线

不把整个 `p0_coverage_integrity` 注册为 coding。只增加一个 testing 条件生产点，条件
完全来自 gate 已有事实与既有 failure kind：

```text
evaluateP0CoverageIntegrity
  ├─ unwaived 缺口全部 ∈ explicit_skip_tc_ids
  │    → FAIL + failure_kind=code_regression + actionability=agent_fixable
  └─ 含 status 为空或未经登记的 trace skip
       → FAIL；留在 testing 修复，不产 coding candidate

testing candidate producer
  └─ id=p0_coverage_integrity + FAIL + code_regression
       → RepairCandidate(category=coding)
       → summary.repair_candidates[]
```

候选组装复用 `itemFingerprintOf`、`RepairCandidate` 和现有 UT product assertion 的直接
组装模式；不增加 `CHECK_ID_OWNER_REGISTRY` 的全局 check 归属，不新增分类枚举或字段。

理由：

- “测试计划没写完/派生覆盖缺失”可能表现为 P0 status 为空，必须留在 testing，不能仅靠
  check id 把它误投 coding；
- “工具/设备不可用”必须进入现有 external/DEFERRED；
- “已经得到真人豁免”由 receipt 判定并降为 WARN；
- 因而只有“全部未豁免缺口均已明确登记为 explicit skip”的合取才表示仓内需要恢复
  可执行性的缺陷；默认 coding 是最小、可回滚且不降低标准的动作。

候选不要求 agent 猜根因或自报 owner。`check id + TC 列表 + 原有 details` 足够让 coding
读取 `testing/test-plan.md` / `test-report.md` 定位最小接缝；找不到正确修复时由既有同指纹
熔断停下，而不是第一轮就把可恢复问题升级成人工授权。

优先级降档不进入 candidate 路由，而由既有 traceability check 原地拦截：

```text
parsePlanTcEntries(test-plan.md)
  + collectDeviceScopeP0P1(acceptance.yaml).criteria
  → 对每个 priority=P0 且 ut_layer∈{device,both} 的 AC
     至少存在一条 priority=P0 且 acRefs 命中该 AC 的 TC
  → 否则 acceptance_to_test_case BLOCKER FAIL（owner=testing）
```

继续复用 `acceptance_to_test_case` 的 check id、严重级别和 testing 责任，不新增
`p0_priority_alignment` check、第二套 Markdown parser 或 coding candidate。已有普通 AC
覆盖率与新增“P0 优先级对齐覆盖率”应在同一 details 中并列，便于解释“有引用但优先级
不够”的失败。

## 2. 目标行为与优先级

### 2.1 runner 决策梯

runner 只保留下面的优先级，不为 P0 skip 再开旁路：

1. **硬安全/完整性终止**：framework integrity、越权写、operator interrupt、硬预算等；
2. **可信 repair candidates**：交 assess，按最上游责任阶段回退；
3. **零候选且全 human-only**：通用 `await_human_gate_deferral`；
4. **普通内容失败/暂态失败**：走既有 retry、advance、defer 与熔断。

若同轮同时存在真正 human-only blocker 和可修 candidate，先修候选。修复并重验后：

- human-only blocker 消失，则无需人介入；
- human-only blocker 仍在且没有任何可修候选，才停下求人；
- 这不是替人授权，而是避免在尚有确定性工作可做时过早停工。

硬安全终止条件不受候选覆盖，repair candidate 也不能越过完整性/授权边界。

### 2.2 P0 语义矩阵

| 场景 | check | candidate | run 行为 |
|---|---|---|---|
| P0 全执行通过 | PASS | 无 | 正常进入后续裁决 |
| device/both P0 AC 仅被 P1/P2/P3 TC 引用 | `acceptance_to_test_case` BLOCKER FAIL | 无 | 留在 testing 恢复 P0 对齐，不进入 P0 分母裁剪 |
| P0 skip + 有效 waiver | WARN | 无 | 不洗白；封顶人工复核态 |
| P0 因外部条件未执行且已登记 DEFERRED | 外部路径 | 无 coding 候选 | 等外部条件，不要求改产品 |
| P0 status 为空或未经登记的 trace skip | BLOCKER FAIL / agent_fixable | 无 coding 候选 | 留在 testing 补执行/派生事实 |
| P0 全部 unwaived 缺口均为 explicit skip | BLOCKER FAIL / code_regression | coding | 自动回 coding 修复并重测 |
| 同一 P0 candidate 原样重现 | FAIL | 同指纹 | 既有 no-progress/backtrack budget 收口 |
| 候选写入失败 | FAIL | 不可用 | 既有 `repair_candidates_unwritable`，不静默丢失 |

### 2.3 `report_validity` 的职责边界

`report_validity` 只能回答“这份 agent 报告能否作为可信自由文本事实源”，不能否定机器自己
已经算出的 check：

- review 问题表、自由文本文件清单等依赖报告内容的候选：`report_validity!==PASS` 时继续抑制；
- `p0_coverage_integrity`、`scope_consistency_with_spec` 等机器 check，以及 verifier 合取后已
  机器确认的候选：不因产品结论为负或 phase 未完成而被清空；
- `envBlocked` 仍只认机器 `failure_kind/blocking_class`；报告散文出现 external/DEFERRED
  字样不得抑制 candidate；
- 不新增第二个 validity 字段。只把现有 early return 移到正确的消费分支。

这也修复了一个概念倒置：**负面产品结论恰恰是回修候选最需要存活的时刻**，不能因为
summary 是 FAIL 就把修复事实抹掉。

## 3. `--skip-assert-expected` 的最小口径修复

### 3.1 两种事实各守一层

| 层 | SSOT | 含义 |
|---|---|---|
| 动作执行 | `trace.cases[].status` + 报告执行结果表 | 步骤是否执行成功；状态词保持四枚举 |
| 验收结论 | P0、视觉、NFR、质量轴与报告结论 | 是否满足完整 acceptance；不得由动作 success 单独推出 |

在弱化旗标下，报告允许按 trace 写“通过”，但必须沿用既有披露：该词表示动作链通过，
不是完整验收通过。以下门禁继续防假绿：

- 旗标必须原文披露；
- 报告必须明确“动作链执行完成 ≠ 验收通过”；
- trace 的失败/阻塞/跳过不得计入动作通过分子；
- P0 skip 继续进入全分母；
- 视觉、性能/NFR、业务状态等未验证轴不得声称通过；
- summary 为负且证据新鲜时，报告不得声称 clean sweep / 达标；
- report/trace 任一 TC 状态不一致仍 BLOCKER FAIL。

把“只要表里出现 trace 的合法状态‘通过’就失败”原位替换为“弱化旗标在场且报告结论为
达标就失败”。前者只会制造两条门禁不可同时满足，后者直接守住不得把动作 success 洗成
完整验收的真实边界；一删一换，不增加第二套状态或协议。

### 3.2 明确不做

- 不加“执行完成”第五状态；
- 不复制一张“动作状态表”和一张“验收状态表”；
- 不新增 `acceptance_numerator.json` 或其它 sidecar；
- 不把自然语言 expected 当作已经执行；
- 不在本 plan 强行关闭 `--skip-assert-expected`，因为无 VLM 环境下它有既有兼容目的；
- 不降低 P0、视觉或 NFR 的完成标准。

## 5. 验收矩阵

### 5.1 单元与组合行为

1. `acceptance_to_test_case`：
   - device/both P0 AC 被至少一条 P0 TC 引用 → PASS；
   - 唯一关联 TC 从 P0 降为 P2、AC 引用不变 → BLOCKER FAIL；
   - 降档 TC 之外另有一条 P0 TC 引用同 AC → PASS；
   - details 同时给出普通 AC 覆盖率与 P0 优先级对齐覆盖率；
   - 测试调用既有 `parsePlanTcEntries`，不复制 Markdown 优先级解析。
2. `p0-semantic-gates`：
   - 全执行通过 → PASS；
   - 有效 waiver → WARN，且不产修复候选；
   - unwaived 缺口全属于 explicit skip → FAIL + code-regression；
   - status 为空或含未经登记的 trace skip → FAIL，但不冒充 coding 缺陷；
   - 任何 skip 在报告声称“达标”时仍触发双口径失败。
3. `repair-candidates`：
   - testing 的 `p0_coverage_integrity FAIL + code_regression` 产 `category=coding`；
   - 同 check 仅 FAIL、但没有 code_regression 时不产 coding candidate；
   - 即使 summary `report_validity=FAIL`，该机器候选仍存在；
   - 有机器 `envBlocked` 时候选被抑制；仅报告散文声称 external、无机器信号时仍产候选；
   - review 自由文本候选在 report invalid 时仍被抑制；
   - candidate 形状、指纹、去重继续过正式 schema。
4. runner/assess：
   - P0 candidate 单独存在 → `phase_backtrack_requested(reason=repair_candidates, target=coding)`；
   - P0 + 视觉 candidates 混合 → 仍回 coding，不产生 `phase_halt(await_human_p0_skip)`；
   - 真正的 all-human-only 且零 candidate → `await_human_gate_deferral`；
   - integrity/越权/硬预算在场 → 仍先 halt；
   - 同一 candidate 集合无进展 → 复用既有指纹/预算熔断，不无限回退；
   - c6 的 events-only resume 与 guardian/legacy-run 回归保持通过；不得从 report 恢复
     `phase_backtrack_requested`，也不得为跑通 P0 用例删除测试夹具中的 bound/settled 对账。
5. 报告口径与质量轴：
   - `--skip-assert-expected` + trace 16 条“通过” + 报告逐条一致 + 明确披露 + 负面结论
     不再被 `reportedPass>0` 单独打死；
   - 同样证据下报告结论改为“达标”直接 FAIL，不依赖已有 fresh 负面 summary；
   - 缺披露、总体通过率高报、trace/report 不一致仍 FAIL；
   - `pass_rate_calculated` 的新 PASS/FAIL 结果经真实 summary writer 进入
     `quality-axes.ts` 结构轴后保持同一裁决，不只测试孤立函数；
   - 无弱化旗标路径行为不变。
