# 复杂能力建设 3.1：P1 App 部件发现、适配 4+1 蓝图与调和

## 1. 计划定位

P1 是 P0 元模型和权威边界之后、P2 Change Unit 之前的部件设计层。目标不是把五个视图拆成五份文档，
而是让一次 App 部件复杂需求从真实当前事实、原始产品需求和已提供的外部权威输入，形成一份由 SE、
开发、测试共同评审、可由下游稳定引用、能主动暴露断链并可滚动调和的部件演进蓝图。

本 plan 与 OpenSpec `app-component-blueprint-and-reconciliation` 成对：plan 约束实施边界、责任、
验收和真实宿主入口；OpenSpec 锁定可执行的行为契约与反例。立项批次先冻结两份设计资产；设计通过复核后，
本批次已按 OpenSpec tasks 进入 P1 framework 实施，仍不推进 Change Unit/P2 或 Component closure/P3。

## 2. 权威输入、输出与消费者

权威输入为：

1. 复杂能力建设总纲 `complex-capability-construction-75411223`，尤其 §3.2、§4、§6.1、§6.5、§6.6、
   §11.2、§11.3、§12、§14 和 §15；
2. 3.1.0 总计划 §6.2 的 P1 输入、必须交付和完成判据；
3. 已归档的 `openspec/specs/complex-capability-meta-model/spec.md`，包括对象单向引用、权威边界、
   provider 三角色、三命名空间分离和宿主演进接缝约束；
4. 产品原始需求/原型、已存在的 feature spec、SE 人工提供的部件职责/外部契约/全局不变量/端到端
   验收分工，以及可访问的代码、schema、接口、配置、测试、architecture、catalog、code-graph、
   conventions 和组件资产。

P1 交付：

- App 部件蓝图协议和适配 4+1 view instance 约束；
- 公共发现内核、App design lens、独立质询 provider 的责任与稳定接缝；
- 跨视图关系、权威 operation/DTO/mapping/provenance、runtime data flow 和分层准入门；
- 蓝图调和、revision/decision fingerprint、stale 失效/重算和决策卡语义；
- 正常/失败/反例 fixture 设计及下游 P2 `design_refs` 的消费边界。

P2 消费稳定节点、关键场景、决策、外部契约和 runtime flow 的引用，不复制蓝图正文；P3 消费跨视图完整性
和覆盖要求；总计划 m5/MG 消费 fixture 和发布门禁结果；真实宿主批次消费 App lens 的产物并回灌新事实。

## 3. 范围与明确非目标

### 3.1 范围

- 以 provenance-first 发现规则分离当前事实、目标设计、外部权责、运行事实和验证证据；冲突报告，未知保留。
- 固定 `logical`、`runtime`、`development`、条件式 `deployment`、`scenarios` 的适用性和最小内容，
  区分 viewpoint contract 与 blueprint view instance。
- 以单一 canonical YAML 承载评审摘要、设计视图、决策与缺口；团队评审前的 Markdown 只是由 YAML 生成的 derived
  projection；用稳定地址和结构化关系支撑 P2/P3 消费。
- 固定 App lens 必答题：模块边界、能力接缝、特性开关、数据生产者/消费者、生命周期触发、状态 owner、
  初始化、发布订阅、UI 刷新和进程恢复。
- 对外部权威契约检查 operation、request/response DTO、wire/domain/UI mapping、错误/幂等/NFR、
  owner、needed-by、source provenance 和 verification refs；缺失只进入需求/提案或合法 disposition。
- 对 runtime data flow 检查 source/producer/trigger/initial load/state owner/mutation/publication/
  subscription/consumer/failure/recovery 的闭环，并执行 consumer 反向追来源、producer 正向追影响、
  lifecycle matrix 交叉校验。
- 以独立质询 provider 检查视图内、跨视图、跨契约和逐边静默假设；以分层准入区别可送评审、当前 CU 可施工、
  远期 CU 可延期。
- 以 revision 和 decision fingerprint 实现受控调和：决策翻转先使 P1 自身受影响派生结果 stale，再按新输入
  重算；历史证据和旧结论保留 provenance 但不继续当当前 P1 事实，P2/P3 不由 P1 代写状态。
- 生成图时只校验生成物可解析、节点地址和边引用；图不是真源，不生成图不绕过完整性门。

### 3.2 非目标

- 不写生产代码，不接入现有 workflow/Goal Mode，不新建 runtime state、ledger、registry、graph executor、
  plugin loader 或动态发现；P1 provider 只静态内置。
- 不实现 Change Unit 契约、`requires/provides`、ready set、选序/连续推进、Goal Mode 执行或 `design_refs`
  的施工侧 checker；这些留给 P2。
- 不聚合 Component closure、覆盖矩阵、组合证据、迁移和最终宿主闭环；这些留给 P3。
- 不替 SE/其它部件裁决云侧、跨部件架构、产品语义、风险接受或不可逆取舍；缺失输入形成可追溯 frontier。
- 不因适配 4+1 强制生成五张图，不以图 parser 通过替代结构化对象、证据、mapping、provenance 和跨视图完整性。

## 4. 设计与责任分解

### 4.1 稳定内核

稳定内核负责蓝图 schema、view applicability、稳定寻址、provenance、unknown/disposition、跨视图关系、
契约校验、runtime flow 完整性、质询结果、分层准入和调和/新鲜度语义。它只消费 provider 产出的统一输入，
不拥有 Goal Mode 完成裁决，不写 events/receipt/evidence。

### 4.2 四个静态内置 provider

1. **当前事实发现 provider**：查证仓内代码、schema、接口、配置、测试和已登记知识资产；当前事实以可复核仓内
   来源为权威，每项返回 `source_ref`、evidence、可得 source revision/hash、冲突和 unknown。
2. **SE/人工契约 provider**：承载部件职责、外部 operation/DTO/mapping、不变量和 E2E 分工；SE/授权 owner 的契约
   才是权威，必须带契约 source ref、verification ref 和 provenance，不能由 Maison 或模型补造。
3. **App design lens provider**：按 App 特有根问题把同一发现输入投影到适用 view instance；lens 不是事实权威，
   只能引用输入、viewpoint contract 和 lens rule/version provenance，不定义第二套蓝图。
4. **独立设计质询 provider**：在隔离上下文读取草稿、结构化证据包和已登记外部输入，逐 view、关系、flow 和必答题
   反证；质询不是事实或决策权威，每个结果须带 evidence/source ref，缺失即 blocker。

四个静态 provider id 必须唯一，requirement 只允许 `required|optional`，其 authority/source rule 按 capability
spec 的 Seam Card 固定校验，不能由蓝图作者覆盖；P1 Skill 只登记到既有 `skills/skills.index.yaml` 真源，不新增
第二注册表。

e4 conventions、b9 组件资产、code-graph 等属于可选输入 provider；有则消费并保留来源，无则按具体触发条件诚实
降级或 unknown。宿主演进接缝是蓝图设计内容，不进入 Maison provider 注册面和三类依赖命名空间。

### 4.3 蓝图对象与稳定地址

canonical YAML 根对象必须有 `component_id`、`review_summary`、`design_views`、`decisions_and_gaps` 三组同源内容，
以及 `blueprint_id`、`revision`、`source_fingerprint` 和整体 provenance；每个适用 view 有稳定 `view_id`，节点/关系/
flow/决策有稳定 id，外部契约有稳定 `contract_id`。语义保持时跨 revision 复用 id；语义替换分配新 id 并以
`supersedes` 连接。所有派生结论记录输入
revision 和 decision fingerprint；引用另外携带 canonical YAML 的 `artifact_sha256`，不得把它与
`source_fingerprint` 混用。根与 discovery 的 `source_fingerprint` 从规范化 discovery facts/provenance 确定性重算
并保持一致，不能自报。P2 只引用这些稳定地址，不复制三组内容或 per-view 文档。

### 4.4 正式产物、`component_blueprint_ref` 与解析

机器可校验的蓝图 SSOT 必须落在 blueprint/component 归属的唯一 canonical 路径
`<project_root>/blueprint/component/<component-id>/component-blueprint.yaml`。`component-id` 是组件身份的路径键，
不从 feature 名称、feature 目录或 feature artifact 推导。实施时复用既有 YAML 解析、schema 校验和 SHA-256 文件
hash 能力，只增加最小的 `component-id`→canonical path 解析器；不得新增全局 registry、独立索引、动态注册系统
或第二 loader。解析器拒绝空值、路径分隔符和 `..`，不接受调用方任意 path，不做 legacy fallback，也不扫描 feature 目录。

`component_blueprint_ref` 必须是可序列化的结构化引用，至少包含 `artifact: component-blueprint@1`、`component_id`、
`blueprint_id`、正整数 `revision`、`source_fingerprint: sha256:<hex>`、`artifact_sha256: sha256:<hex>` 和
`target: { kind: blueprint|view|node|relation|flow|decision|contract, id, view_id? }`。`source_fingerprint` 是规范化来源/权威
输入集合的语义指纹；`artifact_sha256` 是 canonical YAML 原始字节的文件 hash，必须分开计算、分开比对，不能互换。
解析顺序固定为：校验 ref 形状 → 由 `component_id` 解析唯一 canonical path → 读取原始字节并计算
`artifact_sha256` → 按既有 schema/YAML loader 解析 → 校验 path 中 component-id、YAML 根 `component_id`、ref
`component_id` 三者完全一致，再精确比对 blueprint、revision、source/artifact fingerprint，运行 canonical schema/
完整性门后才解析 target；hash 匹配但结构非法的蓝图也必须拒绝。`blueprint`
target 的 id 等于 `blueprint_id`；`view` target 的 id 等于 view id；只有 `node`/`flow` 必须提供 `view_id` 并在该 view
下存在；`relation` 在蓝图关系集合中稳定寻址；`decision` 与 `contract` 是顶层稳定对象，分别按 decision id 与
`contract_id` 寻址，`view_id` 仅作可选关联且存在时必须可解析。canonical YAML 内含
`review_summary`、`design_views`、`decisions_and_gaps`；评审前生成的 Markdown/HTML 只是不反向写入 YAML 的 derived
projection，必须带 `derived_from`（artifact、component_id、blueprint_id、revision、source_fingerprint、artifact_sha256），
并完整投影视图 current/target/delta、runtime flow、契约 mapping、跨视图关系、逐 scope 质询和派生准入。

## 5. 核心契约锁定

### 5.1 适配 4+1 与跨视图

`logical`、`development`、`scenarios` 必需；可执行 App 的 `runtime` 必需；`deployment` 按平台、进程、
持久化、外部边界和运行拓扑证据裁决。每个适用 view instance 都要表达非 unknown 的当前态、目标态、delta、至少
一个可寻址节点及非空验证引用，并表达关注者/用途、
决策/缺口和验证义务。关键 scenario 步骤必须连到 logical 元素、runtime 交互、development owner 和适用时
deployment 节点；runtime 边必须连 logical 契约和实现 owner；模块/运行节点要有设计依据；术语、契约、状态
owner、失败语义冲突必须失败。

### 5.2 权威契约 operation/DTO/mapping/provenance

外部契约输入按以下链校验：

```text
operation（稳定标识/方向/版本）
  → request/response DTO（字段、类型、必填/可空、业务语义）
  → mapping（wire ↔ domain/UI、转换、默认、丢弃）
  → error / idempotency / NFR / owner / needed-by
```

每段必须有可复核 source ref、版本/hash（可得时）和 verification ref；checker 从项目根安全读取 source ref 指向的
Swagger/IDL/YAML/JSON 权威文件与 fragment，真实比对 operation、DTO 字段、mapping、error/idempotency/NFR；
路径越界、来源/fragment 不存在或语义不一致都 fail-closed。只存在 endpoint、接口标题或 DTO 名称不算
闭合。禁止把 wire DTO 与领域/聚合/持久化模型做逐字段同形 diff；`parent_level_id` 等派生字段必须以显式
derivation/mapping 边表达，provenance 只强制绑定外部权威字段与显式转换/派生边，不编造内部派生字段的外部来源。
字段方向、版本、必填性、转换、错误或幂等不一致时 fail-closed。权威输入缺失时生成消费需求/提案并落 `open_decision`
或 `blocker`，不生成已批准的 request/response。

### 5.3 Runtime 数据流

满足以下任一条件时，runtime view 固定生成 `runtime_data_flow`：持久化或远端数据被 UI 展示、同一数据被多个
页面/组件/聚合 projection 消费、存在后台/系统/外部/定时写入、冷启动/恢复前台/页面挂载/账号切换需要加载刷新
调和、一处用户修改需要刷新其它消费者、存在缓存/云同步/freshness/一致性/进程重建要求；六项均不满足时仅数据
闭环子模型可凭证据标 `not_applicable`，runtime view 仍须覆盖其它运行交互。每条流有稳定 `flow_id`，并至少
包含 `data_domain_refs`、`external_contract_refs`、source-of-truth 的 authority/persistence/projections_and_caches/
reconciliation、trigger 的 kind/timing/idempotency、initial load 的稳定 id/strategy/owner/data_scope/freshness、state owner、
mutation、publication/invalidation、subscription 的 replay/snapshot/顺序/并发/attach/detach/cleanup、consumer、
带稳定 id 的 failure/recovery、decisions/gaps、provenance 和 verification refs。trigger/evidence/verification 等流级
依据不得为空；mutation/publication/subscription/consumer 保留为必需数组，但是否有条目由实际 trigger 与行为决定，
只读/首次加载流不得伪造写入或订阅。flow 局部 id 必须唯一；一旦声明 mutation、publication、subscription 或 consumer，
其 mutation→publication/recovery→受影响 consumer、subscription→consumer、consumer→initial-load/适用时 update 引用必须真实闭合。
构建时做三向交叉：consumer 反向追首次加载/更新
来源，producer 正向追幂等/影响消费者，cold start/warm resume/page attach/detach/account switch/process recreation/
background write lifecycle matrix 交叉检查。缺首次加载、写入传播、晚订阅快照、后台持久化/恢复、订阅清理、freshness/
reconciliation 或 owner 都形成 frontier，不以“状态管理自动刷新”补齐。

### 5.4 质询、unknown 与分层准入

质询过程报告只是过程证据，不是新的 SSOT；稳定事实、设计决策和外部契约结论只回写蓝图及既有 ADR/契约真源。
质询覆盖从 canonical YAML 派生，必须唯一覆盖每个适用 view、relation/runtime flow 和十个 App 根问题；一个问题不能自报
覆盖全部范围。root questions、contracts/design refs readiness 与 admission status 从实际质询/App lens 及契约、
地址、视图、runtime checker 结果和所有其它准入前 BLOCKER 派生，不接受编写方填写的布尔值或忽略 schema/artifact/source 问题。
质询结果只允许 `answered_with_evidence`、`decided_with_authority`、`open_decision`、`blocker`、
`not_applicable`；`unknown` 是内容级认知标记。送评审前根问题必须有合法 disposition；当前 CU 所需设计切片
和关键外部输入必须冻结或有受控 fake；远期 CU 可保留带 owner/needed-by 的 `unknown + open_decision`。当前依赖
未知必须是 `unknown + blocker`，不得用权威裁决或不适用洗掉证据缺口。

### 5.5 调和、决策翻转与图边界

新事实或权威裁决生成新 revision，不改已完成 Goal Mode 事实。决策翻转、契约版本/错误语义变化或 view 适用性变化
只会使 P1 自身的完整性、mapping、flow、graph、质询/准入等派生结果 stale，再按新 revision 重算；P1 不创建、
修改或移除 P2 ready set 或 P3 closure 状态。下游通过 `component_blueprint_ref` 的 revision/source_fingerprint/artifact_sha256 不匹配
自行触发其所属权威的重新派生，P1 不代写下游状态；历史结论保留 provenance 和 superseding 指针。无法重算只能
unknown/open_decision/blocker。

若本轮生成 Mermaid 或其它图，检查生成物可解析、节点可定位、边可落地；未生成图不失败。图永远不能替代蓝图对象、
关系、证据、契约 mapping、provenance、disposition 或 runtime flow 完整性，也不能反向写入 SSOT。

### 5.6 P1/P2/P3 状态边界

P1 只拥有蓝图 `revision`、`source_fingerprint` 以及 P1 自身派生结果的 freshness/stale/recompute 语义；
`artifact_sha256` 是 canonical YAML 字节完整性校验，不替代来源语义指纹。P1 不创建、
修改或移除 P2 ready set，也不创建、修改或移除 P3 Component closure 状态。P2/P3 消费带 revision/source_fingerprint/artifact_sha256
的 `component_blueprint_ref`；发现 revision/source_fingerprint/artifact_sha256 不匹配时，各自在自己的权威内重新派生，不能把下游状态写回 P1 蓝图。

## 6. 实施顺序（后续 P1 实施批次）

第一步冻结 schema、稳定地址、provenance、view applicability、disposition 和契约链；以小型 fixture 锁定非法输入
和冲突语义。第二步实现发现内核和 App lens，生成单一蓝图及适用 4+1。第三步实现跨视图、contract mapping 和
runtime flow 完整性，并只在生成图时接入 parse checker。第四步接入隔离质询、分层准入、变化轴决策卡和静态 provider
缺失/替换语义。第五步实现 revision/fingerprint 调和，完成决策翻转旧结论残留反例。第六步注册受影响测试并运行
OpenSpec strict validate、default plan 扫描和 P1 专项 fixture；fixture 只验证 release 语义（例如当前窗口与未完成
P1 todo 的委托披露），不替代整仓 release 门禁。整仓 `--release` 检查与 `release:verify` 由总计划 m5/MG 批次
收尾承担，不在 P1 局部实施中执行或宣称完成。

每一步都必须复用 P0 已冻结的唯一权威和现有测试/报告通道；若发现现有契约不足，先形成蓝图 frontier 或另开受限
变更，不顺手新增跨单元状态、全局注册表或通用执行器。

## 7. 反例与完成判据

### 7.1 必须失败的反例

- 视图缺失或适用视图为空壳、scenario/runtime/关系引用非空但悬空、module/运行节点无设计依据；
- deployment 以“单部件”为理由伪造不适用，或同一状态 owner/失败语义跨视图冲突；
- operation 存在但权威 source file/fragment 不存在或与 request/response DTO、field mapping、错误/幂等/NFR 不一致；
- runtime 必需依据为空壳、局部 id 重复/引用悬空、consumer 无首次加载、mutation publication 无受影响 consumer、孤立 publication/consumer、晚订阅无快照、后台写入无持久化/恢复、订阅无清理；同时验证只读/首次加载流不伪造 mutation/publication/subscription；
- 质询 provider/scope 缺失、一个问题自报全覆盖、准入布尔自报、重复/非法 provider、frontier 重复/超预算或 unknown 被 `not_applicable` 洗掉；
- ref hash 匹配但 canonical schema/完整性不通过，或 Skill 未登记到既有索引真源；
- 图可解析但结构化对象不完整，或旧手写图覆盖蓝图真源；
- 决策从直接实现翻转为接缝、DTO v1 翻转为 v2 或 deployment applicability 翻转后，旧 PASS/mapping/flow/
  graph/质询/准入仍被当作当前输入；下游 ready/closure 未按引用 mismatch 自行重算。

### 7.2 P1 完成判据

- OpenSpec `proposal/design/spec/tasks` 全部存在并通过 strict validate；default plan 扫描识别到完整父目标声明，
  P1 专项 fixture 验证 release 语义而不代替整仓 `--release` 门禁；
- 正常 fixture 生成可供 SE、开发、测试共同评审的单一 App 蓝图，包含真实可读取的权威契约来源、实质适用 4+1、
  可解析跨视图/flow 引用、runtime flow、逐 scope 质询、派生准入、决策/缺口和稳定地址；Markdown 对这些内容完整投影；
- 失败 fixture 能定位上述每类缺口，图解析通过不能掩盖结构化不完整，未生成图不绕过完整性门；
- 质询、unknown/disposition、分层准入、provider 缺失/替换和决策翻转 stale 语义都有可执行反例；
- 新事实只调和蓝图和后续工作，不修改完成事实；旧 P1 结论保留历史 provenance 但不进入当前 P1 准入集合；
- 真实宿主材料到位后，AI 记账首批能用真实 operation/DTO/mapping、代码事实、生命周期和测试证据回灌蓝图；材料
  未到位时只宣称 fixture/framework 机制完成，不宣称真实复杂能力已成立；
- 不进入 P2 Change Unit、P3 Component closure，也不把总计划 m5/MG 的 release 模式整仓检查和 release 结果提前
  记作 P1 完成事实。

## 8. 父目标七问与退出条件

1. **推进哪个目标**：本 plan 只推进 `g3-component-discovery-and-design-lenses` 与
   `g4-component-evolution-blueprint`；P0 只作为已冻结输入，不在本 plan 重做元模型。
2. **解决哪一层**：解决部件 blueprint/design 层的发现、4+1 观察面、跨视图一致性和调和；不放到 P2，因为施工
   前必须先有稳定 design refs；不放到 P3，因为闭环只能消费已稳定的设计与证据。
3. **输入真源与输出消费者**：输入是产品/SE/代码/接口/schema/测试/知识资产及 P0 契约；输出是同一蓝图和结构化
   frontier，消费者是 P2、P3、m5/MG 和真实宿主评审。
4. **是否新增状态/索引/注册表/证据/裁决入口**：只增加正式蓝图 revision、节点/flow provenance 和派生结论
   freshness 所需的产物字段；产物复用既有 artifact schema/loader，不增加全局 registry、第二 loader、运行时状态、
   手工完成台账或新的裁决入口，决策仍归蓝图/权威 owner，完成事实仍归 events/receipt/evidence。
5. **如何避免双真值**：当前态引用代码/schema/接口/测试，目标态/共同决策归蓝图，施工契约归 P2 spec/plan/contracts，
   运行事实归 events/reducer/receipt/evidence，长期知识归 architecture/catalog/conventions；五个 view 不复制成
   五份文档，图只是生成时派生。
6. **真实宿主如何证明结果**：以 AI 记账为首批，真实代码/接口/测试和 SE 契约证明 operation/DTO/mapping、首次加载、
   写入传播、订阅快照/清理、后台恢复、UI refresh 和跨视图关系；缺真实材料时只做 fixture 机制验收并明确未验证。
7. **何时退出**：如果真实案例未找到新的断链、未减少遗漏或未提高闭环可信度，停止扩展 lens/视图/图机制，保留已证明
   的最小协议，后续通过真实 frontier 或新的 OpenSpec 再立项；不为“以后可能需要”扩建通用执行器。
