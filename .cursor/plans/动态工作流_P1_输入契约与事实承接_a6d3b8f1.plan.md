# P1：输入契约与事实承接

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；输出消费者：P2–P6。
> 本 plan 冻结输入结构与解析语义。具体 acceptance/蓝图字段映射由 P3，
> UT/testing 追溯消费由 P5，各方不得再定义自己的输入协议。
> 以下新增字段是待实施合同，不表示当前代码已经支持。

## 1. 问题背景

当前 contract 有 sources 与 on_missing，但强耦合至少存在三处：
coding/plan 将多个输入组成必需 capability；SpecLoader 固定检查物理文件；
静态一致性门要求每个 artifact 输入的 producer 必须位于阶段祖先。
因此“旧产物已满足”“蓝图已提供内容”“独立审查无本次 coding”仍可能被前置阶段限制。

现有 CapabilityResolutionReport 只负责前置解析，build/install/device 结果归 checker。
这一边界保留；不把执行结果塞回前置报告，不用可选输入降级替代必需义务。

## 2. 输入审计矩阵与分类

每个被读输入至少登记：consumer、使用字段/语义、现有 reader、来源、缺失后果、
对应义务、是否要求本次新产出、是否要求真实先行操作、证据绑定方式、改造 owner。

| 输入族 | 允许承接来源 | 不允许的替代 | 本次 owner |
|---|---|---|---|
| 需求/范围 | 用户原文、已获准蓝图 scope、CU purpose/target predicates、既有正式需求 | 模型转述冒充需求原文 | P1/P3 |
| 验收 | 有效 acceptance；具备同等字段且可验证的蓝图/CU 投影；专项测试显式目标 | 仅 verification_refs、把现状代码推断成预期 | P3/P5 |
| 施工契约 | 当前有效 contracts；完整的获准蓝图切片投影 | 未裁决外部 DTO、从字段同名猜 mapping | P3 |
| 代码/测试目标 | 代码、明确 diff/基线、现有测试注册和调用 | 无效路径被换成全仓扫描而不披露 | P4/P5 |
| 历史验证 | 现有 evidence/closure 的有效证据 | 旧 PASS 文本、mtime、模型承诺 | P2/P5/P7 |
| 全局知识 | catalog/glossary/Graph/conventions/extension 既有真源 | 因任一可选知识缺失强造完整 bootstrap | P6 |
| 事实上下文 | 既有 facts/有效调查；当前首 Skill 的真实 Research | 假写 established_by=spec、只有引用没有事实 | P1；P4/P5/P6 接线 |

分类后保留真实要求；不能对所有 required 文件统一改 optional。
“本阶段应产出的 acceptance/test-report”与“上游应已存在的 acceptance”必须分开，
同一个文件名不能靠同一存在性规则同时裁决两个责任。

## 3. Contract 结构增量

保持 sources 的两个 kind：artifact 与 derive；新增来源使用现有静态 provider ID 集。
新 contract schema 采用 1.1，旧 1.0 reader 维持旧行为；不把新字段偷偷塞入旧严格 schema。

示意（字段名为本 plan 的设计合同，实施时需同步 YAML schema 与 TS parser）：

~~~yaml
schema_version: "1.1"
skill: coding
skill_doc: SKILL.md
phases:
  coding:
    inputs:
      - id: acceptance
        sources:
          - kind: artifact
            artifact: acceptance@1
          - kind: derive
            provider_id: derive.blueprint-acceptance
    capabilities:
      - id: capability_coding_acceptance_context
        axis: functional
        inputs: [acceptance]
        obligation_kinds: [acceptance-context]
        on_missing: fail
    produces:
      - kind: source
        id: implementation
    verifies:
      check: check-coding.ts
~~~

1.1 的 phases 不再以 tracks 判断适用性；1.0 tracks 限制只在 legacy context 生效。
obligation_kinds 是对 P2 规则种类的引用，不在 contract 中复制触发谓词。
未绑定义务的 capability 只允许明确的基础输入或可选增强；静态门要求说明归属，
不能通过删 obligation_kinds 将一个必需能力变成可 prune。

capability 的 on_missing 继续表达缺失默认策略：
绑定到当前 required 义务的输入缺失必须 blocked，不被 prune 覆盖；
明确不适用不尝试其来源；unknown 不能被当作 not_applicable。
optional 增强可以保持 prune 并呈现降级。坏输入始终 invalid/blocked。

保持 existing produces 作为“这种职责可产出什么”，不要求每次调用全部产出。
具体 required outputs 从本次义务派生；P3/P5 负责将输出存在性门同源化。

## 4. 类型化内容与来源绑定

不创造一份万能 YAML。复用 AcceptanceSpec、ContractsSpec、UseCasesSpec、FeatureSpec 等现有类型。
调用期维护 ResolvedPhaseInputs，传给既有 CheckContext/SpecLoader 消费；无需把全部内容再序列化进 report。

~~~ts
type InputBinding = {
  input_id: string;
  source: ContractInputSource;          // 保留 artifact/derive
  dependencies: SourceDependency[];     // 复用现有路径、存在性、哈希与角色
  source_refs: string[];                // 已有稳定地址；不得自创寻址语法
  content_fingerprint: string;          // 对规范化内容，复用既有哈希工具
};

type ResolvedInput<T> =
  | { state: "resolved"; value: T; binding: InputBinding }
  | { state: "absent"; attempts: SourceAttempt[]; detail: string }
  | { state: "invalid"; attempts: SourceAttempt[]; detail: string };
~~~

这些类型表达的是现有解析结果增量，不新增 input 数据库。
报告持久化 binding/attempts/诊断；真实内容在调用期从来源解析。
Binding 的 fingerprint 证明内容绑定，不能替代语义校验或用户授权。
依赖仍按项目路径治理；不把 framework 自身文件写入 consumer evidence，
framework contract/规则用既有 contract fingerprint 绑定。

新增 derive provider 限于有实际消费者的静态函数：
derive.blueprint-acceptance、derive.blueprint-contracts 由 P3 实现；
专项显式输入优先扩展现有 derive.requirement/derive.adhoc-cases/derive.test-targets。
不建立可脚本执行的 predicate DSL、通用反射源或动态 loader。

## 5. 解析算法与冲突语义

1. 从显式调用身份读取请求与有效范围，不扫描所有历史 run 拼接需求。
2. 先检查 capability 是否适用；未知只允许补依据或返回具体缺口。
3. 按 contract 顺序尝试来源；absent 继续，resolved 停止，invalid 停止并报告。
4. 解析后先运行同一内容 schema/semantic validator，再注入 checker。
5. 一次 phase 调用只生成一份不可变 resolution report；所有消费者复用。
6. scope 记录的 binding 与本次实际解析不一致，进入既有 stale/correction 路径，
   不静默使用另一来源继续施工。

来源优先级解决可选来源顺序，不解决权威冲突：
当当前请求/已绑定蓝图明确表明旧 acceptance 或 contracts 已过期时，
必须先失效旧来源并回责任方修订。不得因 artifact 来源排第一而吞掉新事实。
未被选中且不影响判定的低优先级来源不用额外读取/哈希；
已尝试的 absent 来源保留 exists:false，新出现时按既有规则导致相关证据 stale。

## 6. 消费者与物理产物

共享入口应交付内容而不只是“文件存在”：
SpecLoader 可以增加接收已解析输入的入口，并保留旧物理读取入口供旧任务使用；
CheckContext 的 featureSpec 必须从同一解析结果构造。
禁止“capability 解析 PASS，checker 另开 YAML 文件”的第二读取真源。

REQUIRED_FEATURE_FILES_BY_PHASE / OPTIONAL_FEATURE_FILES_BY_PHASE 的新协议作用被收编：
输入要求由 contract+scope 派生；本阶段输出由 required outputs 派生；
evidence 真实读取面来自尝试过的 sources 和实际输出。
更新所有复用这些表的消费者；旧表仅服务 legacy adapter，不保持新旧两套日常真源。

只在已有消费者确实需要物理文件时物化投影：
保留现有 artifact schema/路径，写入真实语义和来源，不写“跳过”“N/A”占位文档。
一个投影只有一个确定性 writer，不能让每个下游 Skill 都写一遍。
无新增设计决策的投影是输入准备，不产生“spec/plan 已执行”的 summary/receipt。
需要新验收预期或设计决定时，将缺口交回 P3，不由 resolver 猜测。

### 6.1 Context Facts Gate 的建立与承接（意见 2）

context-facts.ts 独立于 SpecLoader 必需文件表；必须在本 plan 同步接管。
现代范围的事实建立责任归“首个实际调用 Skill 的既有 Research Sub-Phase/上下文收集步骤”，
由 P2 runtime 或 P6 专项入口在派发时明确交给该 Skill，checker 负责验证而不替 Agent 编造事实。
直接 coding 时在写第一个实现文件前完成；review 在审查前、UT 在规划/执行前、
testing 在派生计划/设备动作前完成。无需为建立 facts 补跑 spec/change。

保留 context/facts.md、既有 Code Facts 表、source_code_paths、必要阅读与覆盖风险语义。
有有效已建立事实时按其来源与当前目标验证后只追加本次 phase_delta；
无有效 facts 时，本次首个 phase 可以建立全量基线，不能要求 delta 依赖不存在的基线。
已有可复用代码/蓝图调查可引用承接，但必须读到实际事实、验证当前范围和路径，
不能以一行“已在蓝图研究”替代 Code Facts。

facts 新形状用 schema_version=1.1，复用原 parser 与检查入口：

- established_by 记录真正建立它的 phase，不再限定 spec/change。
- Feature facts 继续保留 feature，按实际 run/scope 血缘校验建立资格。
- 无 Feature 的 request facts 使用 request_sha256（P6 规范化请求指纹），不填虚构 feature；
  两类身份互斥。目标/基线由 P6 resolved request 与事实来源绑定，不仅比较一个自报哈希。
- 原 ready_to_produce、覆盖风险、源码可读性等检查仍生效；
  新 schema 不沿旧“full 必须 spec”的身份规则判定。
- 旧 facts 1.0 只通过明确 legacy reader 解释；已被新请求采用的旧事实仍需核对实际范围，
  不改 established_by 为不存在的阶段，也不因旧文件在场而自动满足。

isFactsEstablishingPhase 与 checkFactsArtifact 改为接收实际 subject、facts 来源和本次建立/增量上下文：
新 facts 建立资格来自当前首个合法调用，后续阶段验证已有基线+自身 delta；
继承自成功前驱的 facts 保留原 established_by，不能与后继首阶段机械要求相等。
runQuantitativeChecks/ContextExplorationPhase、profile snippets 与阈值读取同步接受实际 phase，
不能把 coding/testing 强制 cast 成 spec 来触发旧全流程门槛。
沿既有当前 phase/请求范围的规则检查实际阅读覆盖，不扩大本轮为探索策略重构。

路径：Feature 使用现有 resolveFactsAbsPath；request 使用 P6 明确的 report-dir/context/facts.md。
同一解析/语义检查内核接收显式路径与 subject，禁止无 Feature 时调用 featureRelativePath。
P4/P5 不再自行追加“必须由 spec 建立”的提示，P6 Skill 负责在该专项目录准备真实事实。

证据：建立阶段把 facts 及其来源绑定为输出/输入，后续阶段绑定实际消费基线与增量；
receipt、phase-evidence-manifest、pass snapshot/恢复和 verifier 使用同一实际路径。
增量追加对旧证据的影响沿现有事实增量/新鲜度规则处理，不为本修复增加整链反复重跑。
request 报告保存相同来源信息但不调用 Feature receipt/completion writer。

## 7. 静态与运行一致性

新协议静态校验：

- 每个引用 artifact 有注册 schema，每个 derive 有静态实现与已声明返回类型。
- 每个来源分支独立可验证；有有效 external/derived 来源时，不再要求本次必有 producer 祖先。
- 仍需生成的输入必须存在合法责任 producer；未解析输入不得因“有一个 producer”而算满足。
- 真实 control 约束由 P2 的有条件顺序规则校验；不把所有旧 requires 都重命名为 control。
- capability ID 与实际 CheckResult 的双向对账保持；not_applicable/pruned 不伪造 PASS。
- contract/Skill/workflow/checker 的互指保持，project 非 Feature 入口按 P6 的真实作用域验证。

## 8. 验收

| 输入 | 应证明 |
|---|---|
| 有效 artifact | 内容到达 checker，来源与内容 fingerprint 一致 |
| artifact absent + 有效蓝图投影 | 同一 checker 得到等价 typed 内容，无上游阶段 summary |
| artifact invalid + 有效后备 | blocked，不掩盖坏输入 |
| 蓝图 refs 存在但无预期结果 | 未 resolved，报告具体语义缺口 |
| 上层新决策与旧契约冲突 | 不取旧契约假完成 |
| 来源缺失后补齐 | 相关绑定/证据失效重建，未消费文件不误触发 |
| checker 使用投影输入 | 不再因旧固定路径缺失失败 |
| 必需义务输入缺失但旧策略 prune | blocked，无法降级洗掉责任 |
| 跳过 spec/plan | 不生成其空报告，也不伪造本阶段执行凭证 |
| 新旧 schema 混用 | 显式按版本裁决，坏新记录不回退成旧 full |
| 新 Feature 无 facts、无 spec/change，直接 coding | 经真实入口建立 coding facts 后施工，不指回 spec/change |
| 无 Feature 的独立 review | request facts 与目标/基线相符，同一语义检查，零 Feature 路径访问 |
| 成功前驱 facts 被后继采用 | 保留原建立身份，验证实际来源，仅补后继当前 delta |

依次修改 specs/skill-contract-schema.yaml、utils/skill-contract.ts、
capability-resolution.ts、capability-resolution-entry-input.ts、
utils/spec-loader.ts、utils/types.ts、harness-runner.ts、

以及所有 checkFactsArtifact、isFactsEstablishingPhase、resolveFactsAbsPath 和凭证/快照调用点。
具体 phase consumer 由 P3/P4/P5 在这些共享入口上接线；P1 的验收夹具需实际调用至少一个现有 checker，
不能仅证明 resolver 类型能编译。

各 schema 与 reader 同提交，旧 reader 可用；此时不切换所有新请求默认。
文档使用 docs/concepts/skill-contracts.md，测试扩展现有 skill-contract/capability-resolution 单测与 fixtures。

## 10. 验证与父目标对齐

运行 npm run openspec:validate；发布内容变更运行 cd harness && npm test。
后续仅补文案不重复全测。推进 G4/G6，输入真源见 §2，输出是调用期解析值与既有报告绑定。
没有新状态中心，投影不争设计权威。真实宿主结果由 P3/P5/P7 验收；
无法改善真实输入承接的抽象、字段与 provider 退出本 plan，不以“可扩展”为由保留。
