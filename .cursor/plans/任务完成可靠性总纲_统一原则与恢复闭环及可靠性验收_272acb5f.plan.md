# 任务完成可靠性总纲

## 0. 一页读完

**要解决什么**：宿主全部 37 个 run 只完成 3 个。其中开卡需求一个 feature 就占 29 个 run、完成 1 个，而它的真实工作量约 1 小时。
停下来的原因绝大多数不是产品写错了，是框架自己的账本、登记、描述冲突。

**怎么解决**：不再按事故逐个加规则。把"当前目标是什么、坏了怎么恢复、什么才算必须停"写成一套统一原则，
让它同时进入 AI 的上下文、裁判的输入和机械执行，框架只守住真正的边界，并用任务级结果来验收。

**后续开发由几份 plan 完成**：五份子 plan，加一次真实宿主收口。

| 序 | 子 plan | 一句话 | 改运行时行为 |
|---|---|---|---|
| P1 | 可靠性基线与任务集 | 先量：定指标、定 13 个场景、记基线 | 否 |
| P2 | 统一目标上下文与权威判定 | 一份目标发给所有执行者和裁判，双方的判断都可被证据纠正 | 是，上下文与裁判输入 |
| P3 | 按故障类别的恢复闭环与同任务接续 | 能自动恢复的不交回用户，底层接力对用户隐藏 | 是，运行层 |
| P4 | 处置策略同源 | 同一处策略决定披露、补验还是交还，推进与判定都听它的 | 是，聚合层 |
| P5 | 规则减法与评审换尺 | 清理余量，评审用同一把尺 | 是，删减 |
| H1 | 真实宿主收口 | 同一现场同一请求重跑，对比基线 | 验收 |

**不变的东西**：编译、单测、真机断言、P0 验收、review MAJOR 这类产品真值照旧阻断；真人授权、凭据、硬预算照旧 fail-closed；
预算不因新开 run 而清零；不建新的 manifest、账本、状态机、benchmark 平台。

## 1. 可靠性定义与边界

定义以根 `AGENTS.md`「可靠性验收口径」为准，本纲不复述第二份。四条读法：

1. **正确停下不算可靠**。检测准确只证明防护生效。2026-09-28 宿主 run be091c 被正确判为模型不可用并停机，
   但仍然需要用户换模型、在下一条命令里多写一个 supersede 目标。按定义这不计入可靠。
2. **完成不能靠忽略真实失败换来**。
3. **不停车不等于旧证据自动有效**。允许继续推进，和允许宣称完成，是两件事。
4. **尽最大可能不等于无限重试**。重复动作必须有条件变化、修复变化或新增证据；硬预算不自动加额。

什么情况下交还用户，以 §5.3 故障类别表的"何时交还用户"一列为唯一出处，本纲其余各处只引用、不另行枚举。

### 2.2 一个完整的例子：NFC

需求原文写"再往下的激活nfc部分本次先不需要"，参考图上有这张卡。

1. spec 没把它写进 ui-spec，做对了，但"不要"这个决定没有载体。
2. 视觉裁判只拿到参考图、截图和必备元素清单，拿不到需求原文，于是判"缺 NFC 卡"。
3. run ae92d8 给 coding 的提示词第 39 行是需求原文，第 156 行是返修候选"Render the NFC activation card"。
   AI 手里两样都有，框架没告诉它听谁的。它照做了。
4. 即便它拒修，视觉裁判下一轮仍会判缺失，直到预算耗尽停机。正确的判断会被结构惩罚。
5. plan c4e7a9b2 的修法是新增 excluded 登记、逐字引用校验和一个阻断项。这套东西依赖 spec 阶段去登记，
   后继 run 的链从 coding 起，没人登记，已经补上去的卡也没有任何路径回收。

这不是五个缺陷，是同一个病的五次发作：目标没有贯通到所有参与方，冲突只能靠再加一个门。

### 2.4 为什么上一份可靠性总纲没治好

`e5d8a2c4`（3.0.0）的立项动因是"到处漏风的工厂"，模型是"证据只约束可以宣称什么，不决定还能不能修"。
它的四个 todo 全部完成，单一下一步裁决、可唤醒停放、真实发布件整机冒烟都已落地，本纲全部复用。它没做的三件事正是本纲要做的：

1. **没有度量任务完成**。验收仍是"机制按设计工作"，所以新接入的执行底座可以在全绿下把完成率拉低。
2. **原则没有贯通**。四条总设计原则早已写进 `skills/reference/agent-behavioral-principles.md` 并被六个阶段 skill 引用，
   执行 AI 读得到。但它们没有进入每次调用的具体上下文，没有给到裁判，也没有约束机械执行：原则说不以过程证据完美为目标，
   门禁照样因此阻断。所以只增加提示词不足以闭环，P2 必须连同裁判输入验收，并由 P4 让机械执行听同一套处置。
3. **没有约束新增**。此后主干 234 笔提交里规则继续净增长，检查项从 501 到 537，可阻断写点从 766 到 838。

## 3. 统一指引原则

下列六条是既有四条总设计原则（`docs/overview.md §1.2.1`）的运行期落法，不是新公理。它们同时约束执行者、裁判和机械执行。

1. **目标唯一**。每次调用拿到同一份目标：要达到的结果、明确不做的内容、已授予的权限、实际环境能力、终点与硬预算。
   目标从既有需求、蓝图、CU、执行范围、验收组装，不新建 manifest。
2. **目标由当前有效的授权与明确修订确定**。有权者最新的明确表述为准，它可以是需求原文，也可以是之后明确的修订；
   其下依次是 spec 产物、设计参考、既往诊断候选。下位与上位冲突时按上位执行并留一行裁决记录。
   只有上位表述彼此冲突且现有授权无法裁决时才问人。
3. **证据不定义目标，但能证明实现是否符合目标**。截图、测试结果、真机断言的来源位置再低，也不能因此被排除。
4. **判断都可纠正**。裁判给出的缺陷与修法是待核验的假设，执行者可以依目标拒绝并留下依据；执行者的裁决记录同样只是判断，
   裁判可以用同一权威的正确解释或新的实测证据反驳，不必寻找更高位的文件。
5. **约束与办法分离，恢复优先**。确定性代码负责可靠读取、身份与授权边界、事务安全、预算计量、真实检查、结果发布。
   AI 负责理解冲突、找原因、在范围内修复、选择下一项有信息增益的验证。AI 不得自报测试成功或扩大授权；
   框架不得要求 AI 为可恢复的小错误手抄哈希、发明凭证或请用户选技术恢复分支。故障按 §5.3 的类别处理，
   交还用户的条件只有该表"何时交还用户"一列所列。
6. **结果验证**。完成由独立的结果证据证明，同时覆盖"要求有的"和"要求没有的"。文件存在、schema 合法、图片相似、
   子门全绿都不能单独冒充完成。

与现有指引的已知冲突须在 P2 调和，例如行为规约原则 1 第 5 条"不确定时停下来问用户"。
按本纲，能由当前目标裁决的不确定不再是停下来的理由。

goal 模式与普通模式共用同一套原则与同一份代码，只有"下一步由谁执行"不同。

## 4. 度量

| 指标 | 最小可计算口径 | 性质 |
|---|---|---|
| 正确自主完成率 | 无非必要人工救场且通过独立结果验收的任务，除以启动的任务；真实外部阻塞单列，不从分母删除 | 目标 |
| 自动恢复率 | 事先登记为可恢复的故障里，框架自行恢复并最终完成的比例 | 目标 |
| 人工救场次数 | 每个任务里用户提供恢复命令、改机器状态、重复授权的次数；真正的产品决策单列 | 目标 |
| 观察到的错误完成数 | 宣称完成但独立验收失败的次数 | **约束，本次验收须为 0** |
| 恢复成本 | 从故障到恢复的墙钟时间、调用数、无影响阶段的重跑数 | 观察 |
| 重复运行稳定性 | 同一场景多次独立运行的结果 | 观察，首轮暂记未测 |

口径约束：

- 人工救场与错误完成不一定进入框架自己的产物。用户在外部手工改文件、提供恢复命令、独立验收发现产品不符合需求，
  都要由测试驱动或人工验收补一条观察记录。只靠框架自有记录计算，等于用框架证明自己正确。
- "观察到的错误完成数为 0"只描述本次验收，不推导总体错误概率。
- 基线与改后运行须恢复到同一初始现场，并记录模型、配置、环境差异。同一句请求本身不足以保证可比。
- 先取得基线再设数值目标，本纲不预设百分比。"顺利停机"不计入自主完成；已定义的合理停止在对应场景里算通过。

## 5. 计划分解

### 5.1 P1 可靠性基线与任务集

**目标**：让"可靠性"可计算、可回归。后面每一份 plan 的收益都用这一份的场景与指标说明。

**范围**
- 指标计算读既有 `events.jsonl`、完成记录与 goal-report，加 §4 所述的少量观察记录。观察记录放进开发仓既有报告
  （本纲与子 plan 的实施记录），不进发布件，不新建存储。
- 冻结 13 个场景，全部取自已发生的事故，每个场景写明前提：

| 编号 | 场景 | 来源 | 前提与期望 |
|---|---|---|---|
| S1 | 模型或工具参数永久不兼容 | be091c | 有获准替代则自动恢复；无获准替代或型号被钉死则带明确理由交还，算通过 |

| S11 | 真实产品回归 | 半模态溢出致按钮被裁 | 修复后完成，或如实失败，**不得宣称完成** |
| S12 | 合法人工暂停 | 需要授权的操作 | 正确停下并保留恢复上下文 |
| S13 | 执行者错误拒修后被纠正 | 例：声称已移除 NFC 而截图仍有 | 裁判凭同一需求加实测证据纠正，最终符合目标 |

  S4 与 S10 是一对：表面都可能呈现为绑定或新鲜度问题，一个必须补验，一个不得重跑。

- 两层验证。确定性重放层复用 `real-chain`、`lifecycle-evolution` 与 `host-snapshot-3.1.0` 夹具，登记为 release-only 套件。
  真实 agent 层在真实宿主从一句简短请求起跑，不给逐步救场话术；首轮 4 个场景各 1 次，定位为冒烟，
  不据此评价重复稳定性，之后按失败反馈增加重复。替身测试不能代替后一层。
- 记录当前基线，写入本纲实施记录。

**不做**：不建 benchmark 平台，不建 A/B 系统，不建新的持久层。

**验收**：13 个场景在当前 HEAD 上各有一条可复跑的结果；S11、S12 以及 S1 的无替代分支在基线中表现为正确失败或正确停下。

**目标**：落实原则 1 至 4 与原则 6。这是成本最低、对宿主当前问题见效最快的一份。

**范围**
- 一个组装函数产出目标简报，来源全部是既有真源：manifest 的需求原文与明确修订、执行范围的请求结果、验收、
  ui-spec 与 ref-elements 中的排除、已授予的权限。

- 权威判定办法写入 `skills/reference/agent-behavioral-principles.md` 作为唯一出处，其余文档只引用。
- 拒绝通道复用既有 `headless-assumptions`。已裁决的冲突连同依据带入下一轮裁判输入；裁判可按原则 4 反驳。

- 随做随清：被本 plan 替代的旧指引同步删除或改写，不留新旧两套。

**不做**：不新建 manifest，不建语义 diff 引擎，不新增登记字段。c4e7a9b2 的 excluded 登记保留为记录裁决的一种方式，

**验收场景**：S5、S6、S7、S13。验收走公开入口看实际产品结果与推进结果，提示词里出现了目标不算通过。

### 5.3 P3 按故障类别的恢复闭环与同任务接续

**目标**：落实原则 5。检测到之后，能恢复的由框架恢复。

**范围**
- 盘点对象限定为"会让 run 结束或阻止交付的条件"，以 events 中实际出现的停机原因为准。不对五百多个检查项逐个标注，
  那会成为新的登记制度。
- 每个条件归入下表一类，并接到既有出口：重试策略、`run_disposition` 的可唤醒等待、责任阶段回退、`adjudication`。

| 故障类别 | 默认恢复动作 | 何时交还用户 |
|---|---|---|
| 瞬时网络、进程中断 | 有界退避，恢复已完成工作，从失败动作继续 | 持续不可用且没有获准替代路径 |
| 模型或工具参数永久不兼容 | 停止重复相同调用；在获准替代范围内换参数并重探 | 无获准替代，型号被用户钉死，或替代会改变成本与授权边界 |
| 文件格式、投影、机器身份漂移 | 确定性修复或交既有 owner 重建，保留有效成果 | 关键原件无法恢复或归属无法确定 |
| 需求与设计或观察矛盾 | AI 读当前目标，按责任阶段调和后局部验证 | 上位表述本身冲突且现有授权无法裁决 |
| 产品测试失败 | 依据可复现证据修根因，先跑相关验证再做必要回归 | 硬预算耗尽，或已无可执行的新策略 |
| 权限、秘密、不可逆操作、硬预算 | 停止对应动作，保留恢复上下文 | 必须由有权者授权或改变约束 |

- 获准替代范围在已有配置中表达。用户用 `--adapter-model` 显式钉死的型号不被默认覆盖。不另建候选管理系统。
- 同任务接续：同一 feature 在上一次可信完成之后的未终局 run，由新 run 出生时自动承接。用户面对的是一个交付目标，
  不是一串 run id。
- 归因：框架自身造成的阻断走既有 `failure_kind` 与 actionability 注册表，不得落到 code_regression。
- 随做随清：被本 plan 替代的旧规则同步删除。

**不做**：supervisor 不新增第二套业务路由；不做无限重试；预算按 c4e7a9b2 的交付周期口径，不因新 run 清零。

**验收场景**：S1、S2、S8、S9、S12。正例：重演 be091c 且配置里有获准替代，用户不需要发第二条命令。

### 5.4 P4 处置策略同源

**目标**：把 09-21 的三档裁决从逐条降级变成结构默认，并且让推进、判定、诊断听同一处策略。
宿主 26 次停机里 14 次是内容重试耗尽，根子在检查层的处置。

**范围**
- 一处策略，三种去向：

| 去向 | 适用 | 后果 |
|---|---|---|
| 披露 | 非关键差异，不影响结果依据。例：时间戳漂移、同内容的身份变化、文档间命名不一致 | 继续推进，写入既有披露渠道 |
| 自动修复或补验 | 缺口影响结果依据。例：验收内容已变而旧测试未覆盖新要求 | 继续推进，但对应义务保持未覆盖，直到责任阶段修复或补验 |
| 交还用户 | §5.3 表"何时交还用户"一列所列的条件 | 停下并保留恢复上下文 |

  产品真值照旧阻断并回 owner。能力缺口沿用 unsupported_gap。未登记的新检查默认披露。
- "影响结果依据"的判别复用既有表达，不另造：`assessFeature` 的逐义务缺口分类（binding、evidence、result、unknown）
  与 c4e7a9b2 的身份中立摘要。
- 策略必须被实际的推进、结果判定和诊断消费。需要收编的聚合消费者以检索为准，`074a4c3c` 上是 9 个文件 16 处，包括
  [`report-generator.ts`](../../harness/scripts/utils/report-generator.ts) 的 `resolveVerdictFromChecks`、
  [`quality-axes.ts`](../../harness/scripts/utils/quality-axes.ts)、
  [`summary-blockers.ts`](../../harness/scripts/utils/summary-blockers.ts)、`repair-candidates.ts`、`correction-commands.ts`、

  落点由子 plan 沿实际消费链确定，本纲不预先认定某一个文件就足够。
- 清单基础复用 e7a2c4f1 §2 的全量门禁清单并补全。c4e7a9b2 新增的两个阻断项在此重新归档。
- 随做随清：被策略取代的逐条降级分支同步删除。

**不做**：不逐个改写八百多个检查写点；不放宽产品真值；不改变检查本身的判定逻辑。
