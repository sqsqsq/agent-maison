# 立项事实（08-13 宿主反馈）

宿主：`D:\work\AtomicServiceDistributionEngine`，maison **2.3.0**，DevEco 升级到物理目录
`deveco-studio-6.1.1.180FULL`（日志实测 `etsLoaderVersion: '6.1.1.125'`）。
现象：maison 编译失败、DevEco 里编译成功。

## 一、异常抛在 SDK/hvigor 内部，但触发条件未证明

`build_maison_fail.txt` 对应的 `.hvigor/outputs/build-logs/build.log` 完整堆栈：

```
Error Code: 00308018 Unknown Error
t.isReferencedAliasDeclaration is not a function
  at .../sdk/default/openharmony/ets/build-tools/ets-loader/lib/process_lazy_import.js
  at eliminateTypeSymbol (process_lazy_import.js)
  at .../ets-loader/node_modules/typescript/lib/typescript.js
```

崩点在 ets-loader（6.1.1.125）内部：lazy-import 处理调用了它自带 typescript 里不存在的
`isReferencedAliasDeclaration`。三次 product/debug 运行（11:03 / 11:10 / 11:30）全崩同一处。

**诚实边界**：异常在 SDK/hvigor 内部抛出是事实；但 **maison 传入的调用参数是否构成触发条件
尚未证明**，因此不写"不是 maison 造成的"。剩余差异变量见下节。

## 二、早期"product/debug 触发"的假说已被证伪

`build_ide_product_debug.txt`（宿主 08-13 18:36 补取）：

```

> hvigor BUILD SUCCESSFUL in 51 s 710 ms
```

同一 product、同一 buildMode、entry **真实编译**且成功。故差异变量收窄为
`mode` / `task` / `analyze`，**不是** product/buildMode。

# maison 侧两条缺陷实锤

## D1 — `00308018` 单码定性

`hvigor-runner.ts:870`（parse）与 `:893-894`（diagnostics）：

```ts
/00308018|Failed to find the incremental input file/i    // parse
/00308018/i.test(log) || /Failed to .../i.test(log)      // hasIncrementalInputMissing
```

对本次日志复刻判据实跑：`hasIncrementalInputMissing = true`，
且 `onlineSign|SignHap|archivePackage = true` → 再叠一条"优先核对自定义签名任务是否声明
inputs/outputs"。真因是 ets-loader 内部崩溃，两条指引都把 agent 引向无关方向。

`00308018` 在 hvigor 里的字面含义就是 **Unknown Error**（日志原文
`00308018 Unknown Error` + `This error is unknown, view the detailed error logs ...`），
本就不该拿来定性。

## D2 — 失败任务在报告里不存在

ANSI 剥离后 grep 全量日志，`> hvigor ERROR` 共三处：

```
L202 :  > hvigor ERROR: Failed :entry:product@CompileArkTS...   ← 失败任务
L1488:  > hvigor ERROR: Error Code: 00308018 Unknown Error      ← 实质错误
L1501:  > hvigor ERROR: BUILD FAILED in 55 s 595 ms             ← 包装行
```

两重失联：
1. **ANSI**：原文是 `> hvigor ^[[91mERROR:`，`parseBuildErrors` 不剥 ANSI，三处全部失配
   （L1488 只是碰巧被 00308018 兜底规则捞到，实测该日志最终只解析出 **1 条** error）。
   同文件 `detectHvigorConfigError`（`:344`/`:356`）早已剥 ANSI 并留注释说明此坑，
   parse 路径没跟上。
2. **窗口**：details 里的日志尾部只有 8KB，被 430 条 ArkTS WARN 占满，L202 在窗外。
   → 故失败任务须走 `diagnostics`（渲染位置在 errors 与尾部日志之前），
   而不是指望它出现在尾窗里；**不加宽尾窗**。

> 附注（不作为必测场景）：IDE 侧 `.hvigor` 详细日志里，主编译失败（11:30:30）之后
> PackageHap 收尾还抛了一条 `getName` 的 00308018（11:30:32）。它**不在** maison 实际捕获的
> `build_maison_fail.txt` 中，故不做本次必测；采用"errors 保持日志顺序、第一条即主错误"
> 的口径后，这类靠后的连带异常天然不会被当成根因。

# 非阻断后续记录（本次不做，供后续立项）

**ArkTS 错误行的定位能力缺失**。实测宿主 08-13 10:57 那次失败（75 条真实源码错，均在
`PosterGenerator.ets`）：错误行格式为 `<N> ERROR: 10505001 ArkTS Compiler Error` +
`Error Message: <msg>. At File: <abs>:<line>:<col>`，只命中通用 `^ERROR` 兜底规则，
`file`/`line` 被丢弃（行号就在同一行文本里），于是
`profiles/hmos-app/harness/coding-host-rules.ts:1148` 的 `hasLocatedError=false` 分支触发，
对 agent 宣称「日志中没有可定位的文件/行……不是某一行源码的问题」——对 75 条源码错误是反向
指引。`harness/harness-runner.ts:1691` 虽有 `At File:` 兜底，但它读的是 details 里的 8KB
摘录，只能捞到尾部那条且不参与分类。

本次范围已冻结，**不在本 plan 处理**；t2 完成后该路径行为不变（前导数字使
`<N> ERROR:` 头行仍不匹配）。若后续要修，须与 `harness-runner.ts:1691` 同源判据，避免两处
正则漂移。
