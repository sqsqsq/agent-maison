## 2. 六项必须闭环的问题

**① 蓝图闭包拒绝须到达设计写方。** i5 的闭包门已给出 `reconcile_blueprint`，两个契约来源不满足施工条件。抛出 `ChangeUnitCandidateRejected` 时，消息保留了原因，接收方却没有拿到 `designAuthority`，于是把相同前像重派给只能改候选的 i6。修改 `change-unit-provider-boundary.ts` 的异常产出和 `initial-design-delivery.ts` 的消费，把原门实际命中的对象、权威来源和已知责任送进已有 `designRepair`。同一反馈里既有蓝图又有候选问题时保留两者。回放 i5→i6，蓝图作者先补契约，候选作者只处理剩余映射。首次准入与修订后的待接受候选重新准入（`design-repair-unattended.ts` 调用 `acceptChangeUnitDecomposition`）都要回放。候选自己指错 design_ref 或映射时，即使门同样返回 reconcile_blueprint，异常只携带实际属于蓝图的 findings。合法蓝图上的候选错误仍交候选写方。同一候选、当前已齐的输入，由接受边界复用闭包门与无写入的投影检查，一次列出可以独立判定的问题并按写方分配。某个检查必须等修订后的权威字段才能运行时，只在得到新输入后检查剩项。回放 i5，同时报两条契约缺来源与当时可定位的投影冲突，避免同一事实反复拆分。

**② 修复提示须与事务预装的候选一致。** i9 收到“没有相关变化时保持空数组”，照做后被同一事务的候选保留规则拒收。以 `design-repair-unattended.ts` 载入的原事务内容生成提示。已有待接受候选时，无 CU 内容变化就保留原条目和身份；初始确为空且无新增项时才交空数组。确有获准修订时，在原候选上作最小修改。如果作者漏交预装候选，包括无 CU 改动时写成空数组，事务按已冻结身份直接沿用遗漏项的原字节，再连同实际改动走原准入检查，此次不重派作者。只有缺省才能沿用。重复或未知身份、主动改了不在写集的内容、公开候选已被并发修订，均沿原拒绝或重新核对路径。回放原来含一项的 i9，加空批次、混入新身份、重复交回三个对照。发布仍经原子接受与原独立核验。

**③ 验收投影与语义修改后的重签须连起来。** 首 CU 作者补 checkpoint 和 requirement_ref 后，13:41Z 冻结的 acceptance 绑定过期。13:50Z 前台回写旧派生文件，13:52Z 正式 spec 再报 28 项结构缺口。分别回放两次事件。先在原蓝图/CU 投影处复用 `p0-semantic-gates.ts` 的适用定义：能从已准入来源唯一生成的流程、检查点、需求引用直接生成，缺语义决定时交原有权写方补齐。不得猜造屏幕、断言或批准记录。

沿 `reviseCurrentScope`、`feature-track.ts` 的既有范围修订流程处理真实修改。区分等价依赖刷新和获准的验收内容变化。后者以签发的写界、当前 CU 身份和实际交回作为依据，由原范围责任方发布新绑定，再执行依赖新内容的正式检查。验收不能因为原 spec 尚未 PASS 而需要先 PASS 才能重签。旧 PASS 只在其输入仍适用时复用。反例是前台脚本直接回写、删掉 P0 义务或改变用户承诺，这些操作不能获得自动重签。复用 `assertRevisionKeepsRequiredObligations` 校验原必需义务的保留。可唯一派生的引用及检查点沿原批准来源补齐。变更 description、expected_result 或 ut_layer，包括 §3 的分层修订，交原验收责任方核对，再由范围写方发布。事务重试时保留同一 CU，并核对并发修订的当前输入。

**④ 后继 facts 的提示、读取和正式检查须采用同一次裁决。** 先回放 `f5c36d` 在 17:05/17:07Z 恢复 spec/plan PASS 的片段，再分别回放 18:07 产品写入、18:14 外部 facts 补记、`0e4889` 首次签发及最后一次受管作者交回。记录每个时点的来源差异、获准写方、baseline、实际调用身份和正式门结论，定位首次分歧。已有获准写入可以推进，具体丢失继承资格的条件仍待上述回放定因。

**⑤ 测试准备、派生计划和拒修反馈须在原 runtime 内收敛。** `f5c36d` 的 work-unit-author-i3 与 i7 都已收到编写 Hylyre 计划的指令。作者因持久化用例的初始数据态未知、规则禁止 clear_app、安装证据不确定而拒写。复用 `check-testing.ts` 的 `derive_hint`、原测试准备职责和 `goal-phase-runtime.ts` 的当前处置。在调用 `supplementTestingEvidence` 前，辨别缺的是计划、具体数据前置、已执行后的证据，还是实际设备条件。让作者在已有授权和能力内给出可执行步骤、可核对的前置事实或只影响个别义务的具体缺口。未受阻的工作继续。由既有 check id、derive_hint、正式构建/安装结果、数据准备事实和当前义务区分工作。作者的自然语言拒修说明供责任方核实，调度不依赖对“空库”等措辞作关键词分类。所有修复派工在原签发处用既有写界解析确认待写对象属于实际作者。对象属于其他责任方时按其现有授权交回，不扩大写集。相同原因、输入、权限下不重复购买同一调用。

回放 i3/i7 与 17 时段两次等待，在可采用隔离测试数据或已知卡号状态的样本里，由原请求产生计划并进入正式验证。数据状态确实不可得时，记录究竟哪条用例缺什么；已有授权且构建或正式安装可执行时走原生产链。仅当此项确需当前 HAP、原构建或安装链实测缺少具体外部条件，才按该条件等待。`resolveCurrentHapSha256Full` 返回空本身不能证明是外部障碍。本地用 i3/i7 的真实拒修交回核实派工和处置，真实作者能产出计划并上机执行的结论取自联合验收。停应用再启动只复位进程，不能据此认定 RDB 已空。沿正式设备执行和证据写方交回，早期缺身份的外围执行可作诊断。保留用户授权、应用数据和原硬预算边界。

**⑥ 让合格复验关掉旧失败。** 使用 5 份 trace、各轮派生计划、末轮当时的 HAP `54feb517…`。TC-02、06、18 最新均有完整 PASS，19:16 正式报告仍保留四条旧 BLOCKER。检查现由 testing 消费，历史路由中的 codingCandidate 描述原失败的产品嫌疑。按具体问题分别处理。

- **TC-06 s17 属 testing/selector。** 复用 `testing-trace-gates.ts` 的测试修正分支。原失败诊断明确是对唯一文案命中取下标 1。机器规则按选择器修复的一般条件判断：原失败域为 selector，选择器本体、匹配方式、断言谓词和验收前置保留，仅改变既有消歧字段。原生诊断或当时 UI 原件能核对原本要找的对象，适用构建的新结果唯一命中该对象且同一断言真实通过，才允许关闭。TC-06 的 index 变化是该规则的一例。原有多个匹配且无法证明对象身份、换目标、弱化谓词、只有 PASS 摘要时保留发现。

- **例外核验的派工和消费。** 当前 DSH 未声明 `verifier_subagent`，阶段 `resolveVerifierPlan` 会返回 disabled，宿主 summary 也记录了 `verifier_not_reviewed`。当前 `independentlyCovered` 只读 testing 的 verifier subject，单靠这个读取点无法交付。对于严格等价判断无法裁决的既有旧发现，以及 §3 中确需独立判断的测试强度，统一从当前工作单元的真实差额派工。各 adapter 都走 Goal runtime 已有的无头独立审查执行路径（`goal-phase-runtime.ts` 的 `invokeWork` 独立报告写方，`goal-phase-executor.ts` 的 verifier 角色）。把同次材料中这些具体问题合并给独立审查者。在既有审查工作中可以一次回答时直接复用；须单独派出时沿原调用预算、模型绑定、独立上下文、只写指定报告和交回机制。派工资格来自已有验收差额与原授权，常规各阶段的 verifier 开关照常裁决，DSH 的常规 verifier 仍可如实为 disabled。
- **测试强度差额由既有独立审查主动产生。** 在各宿主共用的 CU 独立审查请求组装处（`goal-phase-runtime.ts` 的 review 指令与签发材料），取当前必需验收 ID 中仅凭测试标签声明覆盖、且缺少针对同一 ID 及同一输入的适用强度结论的条目。直接在本轮既有审查中给出这些 ID、验收预期、测试源码、执行原件，以及 `collectTestStrengthContext` 和 `independentVerificationContext` 已有的“验收→用例→实际断言、mock 与产品真值”材料。此步骤独立于阶段 verifier 开关及 `coding_existing_test_preserved` 是否触发。审查者按原问题表或 `issue-verification` 说清是否经过生产路径、对哪一个实际结果作了断言。替身、未走写库或缺证据时，由这次审查产出具体差额，交原修复责任及完成判定消费。已有同 ID、同输入的有效独立判断直接复用。这项主动核对并入已有调用，不增加通用门禁或单独的常规审查轮次。

## 3. TC-11 与 TC-08 的验收归属

**TC-11 在验收投影中调整。** [当前 AC-11](D:/1.code/SimulatedWalletForHmos/doc/features/bc-openCard-2/open-card-vertical-slice/acceptance.yaml:206) 已为 `both`。其 `device_focus` 把沙箱内逐字段查库交给 Hylyre，而当前执行通道没有该原语。修订原验收定义及其投影，使测试计划与 `ut_focus`、`device_focus` 逐项对应：

| 用户义务 | 实际验证与可签结论 |
|---|---|
| 完整卡号、请求到字段的映射与默认值 | 现有 UT 调用生产 `recordOf`，保留这些已验证的断言。 |
| 真正写入、按卡号读回正确字段、适用的重复写入不增行 | 交给有应用存储访问权的仓库集成测试，例如应用内的 ohosTest 使用隔离测试库调用生产 `openCard` 后查回。验收引用实际执行原件，并保留同一用例所需的初始数据状态。能力尚未具备时该项保持未验证。 |
| 用户提交、结果展示、返回与清栈 | Hylyre 观察 UI 可见行为。结果页出现只证明对应 UI 义务。 |

**从干净设计入口生成。** 修改 `skills/reference/app-component-blueprint-workflow.md` 中“平台集成用设备证据”的分层指引，连同实际产生 acceptance 的蓝图选择、`blueprint-skill-projection.ts` 及已有 Hylyre 计划派生指引/规则一起修订。对每一项用户承诺，写明要观察哪一个结果，以及当前项目已有哪种测试能观察它。应用内的集成测试可以跑在设备上并使用存储上下文；外部 UI 驱动按其可观察的界面元素、动作和状态变化取证。能力取自既有 profile/provider、用例和实际原件。

**让每个验证点能单独决定完成。** 由原设计责任方沿用现有 criterion/boundary 的 ID 结构，为不同证据的新义务登记独立必需 ID。不同证据才能证明的必需行为分开登记，沿用原始需求引用、优先级与关联。保留原 AC 的可追溯关系，为真实持久化明确独立必需 ID。TC-08 同理，将 UI 的实际倒计时变化与禁发期间发送次数分别绑定到可验证的 ID。旧 AC-19 或 BD-3 的历史通过只服务其原义务。ID 从批准的验收产生，运行器按已有覆盖规则消费。沿 `check-testing.ts` 派生提示、`hylyre-standard-derive-knowledge.ts` 到 `p0-semantic-gates.ts` 的消费链，UI 用例只认领确有对应可执行断言的 UI 义务。只有 ac_ref 标签、页面存在、输入动作或套件 PASS 时，不为读库或调用次数记 verified_pass。缺少专属执行证据时保持未验。仅有标签覆盖的必需 ID 由 §2⑥ 的既有独立审查主动核对，签发时直接提供材料。修订后重签受影响的 scope 及其证据要求。

正例从两个入口验：已有映射用例只覆盖字段映射，隔离存储用例通过生产 `openCard` 写入、查询并对实际行作断言后，才形成持久化 ID 的覆盖证据。校验当前执行原件并沿既有测试强度核验检查所调用的生产路径、替身及断言。反例只给原有五个 `[AC-11]` 用例的 PASS 与结果页出现，即使给 Spy 用例补上持久化标签，正式完成判定仍须保留缺少真实读回的必需项。TC-08 只出现两次“秒后重试”或只有计数标签时，也不能覆盖实际递减和禁发两个义务。从隔离的干净产品基线开始，只给原始需求、参考图、已有 profile 与源码，通过正式设计、蓝图准入、验收投影、用例派生及覆盖/完成判定走通。同一次设计输出应为 UI、字段映射、真实持久化、倒计时变化和重复发送生成可追溯且可分别消费的义务。不得拷贝本次宿主蓝图或改写已生成的 acceptance 来充当前门生成。用一个非银行卡的存储/界面样例验证同一分配规则。回放三种情形：只有 UI presence 和带标签的 Spy 时真实持久化项未满足；有合格的存储集成原件时仅对应项可关闭；UI 断言或真实存储原件不适用于当前输入时保持缺口。本地验证强度结论能经 §2⑥ 正式路径传到完成判定；真实核验方对 Spy 的辨识、银行卡实际写入读回及界面表现另以宿主联合验收签收。不按类名或文件名增加静态替身检测门。

框架改造点是原投影与已有测试准备对职责及能力的消费。银行卡的库名、字段、卡号及页面 ID 仅作宿主回放输入。避免增加 Hylyre 的数据库接口或新增全局能力登记。宿主承担存储集成用例和产品验证。TC-08 单列断言强度：UI 取得两个有时序的计数值以验证递减，状态机/应用测试验证禁发期间发送次数未增加；两次出现相同提示文字不够。实际源码、用例及当前签名 HAP 的修后真机验证在宿主验收时安排。

## 4. 两项非阻断修正与外部去向

- **前台等待。** `goal-status-wait.ts` 的 `readWaitView` 需保留显式 CU 请求和根交付的对应关系。用 14:41:03Z 明确指定仍活跃的 `f5c36d` 却在 2 秒后返回根 HALTED 的原生调用回放。等待条件跟随实际请求的活跃、经审计后继；整项完成仍以根交付为准。真实停止、根与所有适用子任务确需外界处理、不同交付周期、过期游标及已有单次超时保留原语义。共享命令覆盖全部 adapter，不另设通知服务。
- **材料归属。** 将 coding 指引要求的 `coding/structure-conformance.yaml` 与已有产物声明及签发写集对齐，核对其真实引用。验 visual 导航的生产者指引、模板和消费路径 `device-testing/visual-diff-nav.json`。本次宿主已有适用写权，文件却落在 `testing/`。有可用旧输入时由获准写方核对后写到正式位置。台账披露和缺少实际视觉证据分别判定。
- **外部去向。** Hylyre 滑动终点 y=-27 使用已冻结的失败 trace、屏幕几何与派生操作交上游复现。银行卡最后一版验证码界面、TC-08 与 TC-11 业务验收归宿主。已撤回的 `OpenCardRequest/LocalCardQuery` 字段冲突不再登记。最终汇报按最后一次正式裁决和当前构建关联核对，分别列出历史 PASS、当前 FAIL 与未执行项。

## 5. 一次实施、统一验收

独立审查用一张表逐项回答全部仅靠测试标签声称覆盖的必需 ID。验收覆盖全答、漏答、替身和真实生产路径四种情况。漏答的 ID 保留为完成缺口。强度结论只绑定验收文本、测试源码与被调用的生产路径内容，UT 执行证据另按当前输入核对新鲜度。回放先审查后运行 UT、仅更新执行证据和修改生产路径三种情况，核实是否只在强度依据变化后重审。

干净设计入口的模型替身只能证明设计输出到覆盖及完成判定的消费链。真实模型能否从原始需求自行拆出 UI、字段映射及真实持久化等独立义务，以真实独立调用原件或宿主联合验收为准。

- **准入两问。** 每项改动的场景和收益已列于对应条目：①②消除无权作者重派和空候选停机，③④消除获准修改后的循环失效，⑤让未完成的准备工作回到责任人，⑥关闭有充分证据的旧失败。实现优先补齐原异常、原指引、既有范围修订和证据消费。沿用现有 run、游标、原子发布与预算，不新增旁路接收、停机原因、登记表、场外存储或固定的阶段跳转。
- **开发验收。** 在隔离副本用上述原件经真实生产入口重现失败，修复后验证正常与反例。至少一条串联设计拒绝、原作者修订、候选准入、验收重签及后继复验的恢复链，核实无前台代写、无手工 force-resume、无重复作者交回。保留短蓝图和直接修改的轻量对照。各次开发执行 `npm run test:changed`，收口执行 `npm run test:daily` 与计划校验。涉及门禁指纹时复用既有快照迁移测试。
- **效率。** 继续以 ≤9 次设计调用、≤100 分钟到首次正常施工作为宿主目标，另记整项交付时长、无效重派、人工接手和设备实跑次数。从事件分别统计作者修后复审轮次、独立调用与检查耗时，以及上一次交回至下一次派工的间隔，单列外部等待，避免重叠相加。同一轮核对快捷路径首次修改前是否增加模型轮次或命令。局部质询仅在受影响项 ≤首轮一半的可比原生样本中，按输出 ≤50%、墙钟 ≤70% 验证。测试读取 7 份 trace 的已有热调用中位约 209 ms，可复用已有计量检查⑥对常走路径的影响，不为计时新增运行时机制。
- **真实联合验收。** 经另行安排，在同需求、代码基线、模型、授权、设备及验收义务下干净重跑，沿用前计划 p6。真实交付需当前 HAP 的设备、UI、实际存储等适用证据、原审查结论和正式完成投影。源码回放、编译或 UT 单项只签相应层级。开发仓内的框架修复与宿主产品待验分别记录，一次联合验收共用原件。

## 本轮返修验收补充

正式 UT 的覆盖口径与测试强度审查共用同一解析结果，包含直接 AC 标签、关联分支、DAG 和 AC 覆盖映射。审查与执行回执指向实际测试文件中的具体 it。带分支标签、仅由 DAG 映射到必需 ID 的替身用例仍须核验；经关联分支覆盖的真实生产测试，其独立裁决和当前执行结果都合格后可关闭。读取适用证据失败须保留可归属的缺口。

初始蓝图和质询确定独立业务义务、可观察结果及其验证归属。具体测试入口、隔离数据前置、断言形式和强度由 CU 施工和独立强度审查承担。初始质询中，义务没有拆开、通道观察不到所分配的结果或真实设计矛盾可构成阻断。只缺测试实现细节时随 CU 接下去。使用与原 16 轮相同的干净基线、原始材料和模型推进到 CU 准入；按同一观测窗口记录实际调用数、墙钟、每轮阻断及是否签发 CU。
