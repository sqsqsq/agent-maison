## 3. 内容契约 v2：示例映射与最小字段增量

### 3.1 示例的使用方式

t1 逐节对照示例，形成“评审关切 → 4+1 主责位置 → canonical 字段/目标 → 渲染形式 → 验收”的映射，覆盖背景、旅程、参与方、功能、模型、状态/流程、持久化、取舍、质量与上线协同。

采纳示例的细致程度与图文叙事，不照抄业务事实、重复章节、历史矛盾或未来占位实现。t1 的共享变体仍供渲染、交接与 docs 样例使用，不改广泛复用的原 Ledger fixture。本轮另保留宿主失败材料的隔离副本，按原写法验证缺陷；不能为了适配 renderer 先把它改成与共享变体一样。样稿不代替最终机器产物或真实宿主执行，t2–t4 可先完成。

验收展示身份固定为“来源目标 + 条目编号”，不以 `AC-1` 等裸编号全局去重；既有投影行身份与冲突规则不变，不新加门禁。持久化、打点与 Visual Handoff 使用既有承载；完整调用事实写入现有有序步骤/接口/恢复设计，设计 agent 据此生成时序图，renderer 只展示该派生图；有序步骤和分支仍供施工与测试消费。

### 3.2 设计目标上的三类结构化内容

复用 [蓝图设计输入与物化](../../docs/concepts/blueprint-design-inputs.md) 及 `harness/scripts/utils/types.ts` 的原结构；承载目标的 provenance 必须满足现有 authoritative 要求，不因作者写了这些字段就自授外部权威。

| 内容 | 既有结构与应包含的细节 | 挂载约定，由 t1 样本细化 |
|---|---|---|
| `acceptance` | `AcceptanceSpec` / `acceptance@1`：criteria、boundaries、performance；设计期写 AC/BD/NFR 的 ID、优先级、验证步骤、预期、分层与关注点；UI 流程关联按下述分工 | scenarios 或 logical 设计目标；仅所有引用者共同承担的验收可放共享目标，专属 AC/BD/NFR 放仅由对应 CU 引用的目标 |
| `contracts` | `ContractsSpec` / `contracts@1` 的设计部分：modules、module_dependencies、data_models、interfaces、components、files、integration_points、state_management；不含 contracts.change_unit | development 节点和 runtime flow；共享目标只放所有引用者都应继承的设计和文件声明，专属 files 放对应独占目标；施工/测试映射由 plan 生成 |
| `use_cases` | 目标字段承载 `UseCasesSpec`（下游 artifact 为 `use-cases@1`）：阶段、UI/数据边界、触发调用、分支序列与预期、linked_acceptance | runtime flow；共同用例才放共享目标，单 CU 专属用例放其独占引用目标；未触发的义务不造占位内容 |

**共同继承规则**：一个 CU 的 design_refs 选中目标后，目标上的三类设计内容整体参与投影。数组按原行身份/内容去重、同标识冲突拒绝，其余行并入；对象不逐键合并，重复声明只有完全相同时接受，否则报 authority_content_conflict。contracts 的 module_dependencies/navigation/resource_keys 和 acceptance.flows 等对象集中在一个目标，不拆成共享部分与专属部分等待拼接。没有按 predicate 自动过滤其它 AC/文件的行为；contracts.change_unit 不再属于这份设计合并输入。

专属 AC/BD/NFR、只由该 CU 写入的 contracts.files 及专属用例，仍放在只被该 CU 引用的设计目标上。共享目标只放所有引用者共同承担的内容。复用页面/模块不等于共享全部写集，不新增 selector 或内容切片协议。**设计节点按设计语义保持稳定，不因 CU 修订或替代就复制带版本号的节点来承载映射。**

“单向依赖”限定为设计事实不依赖具体 CU 身份/映射：CU 引用蓝图，认领关系由这些引用反向派生。现有 admission.current_slice.slice_id、gap/contract.needed_by 使用稳定的设计切片/需要方含义，不以 CU revision 或目录后缀作为必须同步的身份，不因此删除既有准入字段或改协议。蓝图真正的设计变化仍升版，关联 CU 的精确指针仍由原调和同步；不能承诺 CU 修订涉及真实设计变化时蓝图也永远不变。

t1 样稿保留 S+A、S+B 的共享/专属设计：分别展示真实合并验收与文件；plan 再为 A/B 的 Feature 生成各自完整映射。替代 A 但设计本身未变时，沿同一稳定目标投影，由替代 CU 的 plan 生成新映射，不回写目标中的 CU 名称或映射。反例分别验证设计对象冲突、误继承专属 AC/文件，以及 plan 映射中的未知/缺失 predicate；保留既有原因码，不把映射错误重新推回蓝图。合法重叠写集不新增门禁。

**P0 真机验收分工**：设计期保留 ID、优先级、步骤、预期、ut_layer 与 UT/device focus。无 ui-spec 依据时不编 linked_flow、checkpoint 或屏幕流程；spec 得到真实依据后补缺，保留原权威内容，并经过真实 resolveArtifact、输入绑定和 P0 检查。不能只在无来源戳的 A1 分支证明补充可行，物化路径必须按 §4.4 打通。不得编元素 ID、删 acceptance 或降低门禁。

feature 与机器来源身份按原解析/投影规则生成，不在蓝图手填自指 hash。**整个 contracts.change_unit 设计期不写**；plan 产出其 predicate_mappings、provide_mappings、design_ref_mappings，change_unit_ref 通过现有 canonical resolver 取得。映射只引用已有 CU 定义，不复制职责、制造新谓词或以 touches 猜测真实实现/测试落点。

`contracts.files` 仍是唯一施工写集；`touches`、目录树、设计图或节点名称不能扩大授权。模块目录展示取自 `contracts.modules[].package_path/layer`，依赖取自 **contracts 根级** `module_dependencies`，文件来自 `contracts.files`；分层约束引用已消费 DSL 的事实，不在展示时新裁决架构。代码骨架不进入蓝图。

### 3.4 可选内容的校验与缺失语义

- 所有表格单元格按 §6.1 共用取值规则；有业务值不得显示“未记录”，`false`、`0` 是非空值。六类可选字段及注释字段真正缺失时，只在每节一行集中列出缺项，不产表头空表、整空列或重复占位行；不造内容、不新增缺字段检查。三类机器内容未写入时使用 §4 的专门提示。
- “未记录”仅表示实际缺失；明确空对象 `{}`、空数组 `[]` 展示“无”，不同于未写、未知或不适用；仅确有来源键且过滤后无业务键的对象才可称“仅来源信息”。false/0 及业务字段中的显式空字符串预期均保留，不用空集合规则抹去。缺项诊断保留可追溯源路径，与正文可读标签分开；深层已有声明暂未展开时如实说明展示范围，不误报未记录。
- 缺项汇总只消费 renderer 生成的显式缺项标记，复用已有标记入口，不扫描作者自然语言中的“未记录”做字面替换；标题、正文、来源行均不得被后处理改坏。标题优先真实表名/label，无名称时用已有契约 ID 作为上下文，不把缺失值拼入标题。不靠隐藏声明或把未知结构当缺失清零指标。
- 六类可选字段存在但形状不合法：给出位置与原因的**非阻断**诊断，文档显示未能表达的项及有值事实，不假装内容有效；只做已有形状校验，不增设语义审批。上述注释字段不新增校验。
- 本批不改 schema，也不添加 type/required 等约束；六类新增可选子树的形状问题仅由现有 validator 以 WARN 非阻断诊断承载，不放入会导致 publication 失败的 CU `sourceGaps`。
- 原有强契约不降级：`acceptance/contracts/use_cases` 的真实机器结构、来源权威、写集、CU 映射、引用解析、设计准入仍按既有 checker。可选字段的宽容不豁免既有路径/授权边界，也不证明设计已足够。

## 4. 设计期写作与交接前校验

### 4.1 写作责任

完整交接前，`/component-design`、P1 workflow 的“写入同一蓝图”、App lens 与独立质询共同覆盖 §3：按 4+1 形成设计解释、三类结构化细节、真实选择及被否方案，适用信息展开到可评审粒度。

标题与固定说明用中文；新写叙述使用项目语言（本项目为中文），包括 App lens 与质询问题/结论；保留 API/类型/路径等原名，不新增 locale 配置。不把所有内容塞进 summary，不为凑文档新造会产生 closure 义务的 decision；新增真实决策仍经原权责与 revision 规则。

本轮明确既有字段的写作位置：review_summary.title 为可读需求标题，summary 解释本次改变；通用决策的获准结论写在 renderer 已支持的 conclusion，rationale 只解释理由，各已定义决策类型仍使用自身结论字段。术语 meaning、模型字段 description 按已有来源写入。该约定同步主 Skill/reference/示例与 renderer，不新增缺字段阻断；对于存量 rationale，renderer 如实展示原文，不能把作者没有结构化分开的选择自行裁决成新事实。

t8 只补既有 component-design/reference/App lens/质询的写作问题，不加机器阻断，也不降低原强门：

| 关切 | 现有承载与写作责任 |
|---|---|
| 方案总览 | 概述末用一段话连起场景、主要模块、运行、开发和部署职责，配 §6.2 跨视图图。已有 canonical 叙述足够时直接编排；真缺叙述时在设计期补既有 review_summary，不增加总览字段或由 renderer 生造方案 |
| 完整调用时序 | 在 runtime flow 承载的 contracts.state_management[].ordered_steps 写明页面/业务对象/Repository/存储 helper/数据库的真实调用顺序、参数、结果、等待、失败与完成返回。typed components/interfaces、根契约/table_schema、failure_recovery/use_cases 提供同源细节；设计 agent 生成 generated_graphs，现有 runtime 质询逐段核图文一致，详见 §6.2。不能用“先后动作都有了”代替“谁调用谁已明确” |

| 真实失败与用户中断 | 逐项核真实依赖失败、用户返回/取消、selection 丢失、OTP 等场景；已有内容归回现有 boundaries/failure_recovery 主责位置，真实缺失才补。mock/本地场景不编外部服务故障或新业务 |
| 错误与幂等 | 写清约定错误、幂等键及作用范围；对跨会话重复卡给出已有需求支持的处理策略和主键/唯一约束，不能仅“重试”而不解释重复提交结果 |
| 质量结论 | 使用现有 quality_attributes，对兼容、安全隐私、UX（深浅色/无障碍）、打点、性能逐项给结论与落点；不涉及给理由，不为凑覆盖杜撰量化阈值，精确阈值仍归 acceptance |

这些是写作与独立质询的既有问题，框架 instructions 落地后可完成 t8 的实施项；其真实效果必须由 t5 干净 1-2 需求重跑实读证明。当前隔离副本不会因为 renderer 修复自动长出缺失的设计，不得把 t7 的通过冒充写作已充分。

流程发布、恢复、持久化与用例的既有承载位置按 §6.4 收准。新样例必须包含真实宿主写法，不能只挑 renderer 当前认识的字段再宣布内容完整。

只要 canonical 内容改变，本次结束前仍重建文档。未变、未决、缺失与不适用分别如实表达；需要有权者裁决的事实不能由 renderer 或下游自行补定。

### 4.2 提前调用同一投影内核

`prepare-blueprint-design.ts` 调用 materializeBlueprintSkillInputs，会写文件，不能当交接只读检查。指针调和非 busy 后，交接复用 deriveBlueprintSkillInput 的设计解析及既有校验；按 §4.5 分离设计内容校验与 plan 映射校验，缺少未来阶段才负责的 contracts.change_unit 不使设计未就绪。原设计事实、来源、写集、用例及本来就应具备的 CU 职责不因分离而免检，不另写解析器。

**-br B1 修复（t9）**：validateChangeUnitFeatureProjection 的 designOnly 分支同样不调用 componentProjectionErrors；它依赖未来 plan 的 design_ref_mappings，不能在设计阶段提前要求。plan 及后续调用保持原样，已有组件选型设计校验不削弱，也不在本次另造设计期替代检查。有组件索引、合法 typed UI 组件、无 change_unit 的真实 readiness 反例必须消除该原因；同一输入按正常 plan 投影检查仍报 component_asset_projection。真正无效的 canonical、来源、范围和职责检查照常执行。

投影保持 canonical-only 且只读：只检查 canonical CU/蓝图的设计内容，不读取 Feature use-cases.yaml 反向判断设计有效性，已删除无实际职责的 `pure` 模式参数。阶段用例与当前设计不对齐时，由既有定义缺口、评估/范围派生及 plan 对齐门安排 plan 重建；不报蓝图 `authority_use_cases_conflict`，不路由设计 owner。canonical 目标之间的真实冲突仍报原 `authority_content_conflict`；§4.4 的合法补充及物化覆盖前检查继续在自身责任入口执行。

在 `deriveDesignPreparationReadiness` 已有 per-CU 检查处接线；范围仍为全部未退役 CU，包括已经完成的旧 CU。仅对设计判定为 constructable 的 CU 运行设计投影检查，避免重复报告。validateChangeUnitDesign 承担设计闭包及 §4.6 复用的职责角色判定，不反向调用会再进入它的投影函数。只读校验不物化 sidecar、不写 Feature 产物或 phase PASS/receipt，不触发 selector/Goal；原指针调和与人读文档刷新照常执行。

旧 CU 引用的 canonical 内容非法时如实报告其 CU 与既有原因，通常需要设计 owner 修复被本次修改破坏的共享目标；不能跳过已完成 CU 换取 ready，也不自动重新启动旧 CU。真正 canonical 非法仍可在调和阶段抛出既有 `change_unit_blueprint_ref_bump_rejected`，真实写入失败/并发变化仍按原事务回滚；不回滚用户已修订的蓝图，不伪装成功。Feature 无安全刷新依据只保留该 Feature 文件原字节，合法 canonical 指针及兄弟 CU 仍可升版，旧阶段文件由既有缺口交回 plan/spec，不因阶段产物不能刷新整批回滚。

已声明的三类内容分别检查，不能因另一类 `absent` 而提前返回、漏掉所提供 use_cases 的形状/语义。若现有内核的提前返回妨碍这一点，在同一模块提取/复用已有 bundle 解析与检查供原消费者及交接共用；不构造假 acceptance/contracts 触发校验，也不复制规则。

| 原内核结果 | 交接处理 |
|---|---|
| `resolved` | 已写入内容通过原语义检查，可交现有 typed 投影消费；不代表整个产品完成 |
| `absent` | 不把缺字段升级成新增机器门禁。对应章节写“设计期未写入，将由 spec/plan 补”，交接如实列出已有设计缺口和责任，不声称这部分已能直接投影 |
| `invalid` | `perUnit.verdict` 使用现有 `blocked`，复用既有 `authority_*`/解析/设计检查原因进入原 readiness 的 not-ready 结果，交回原设计 owner；不新增检查 ID、停机原因或持久状态 |

已声明的空值、文字冒充机器内容、冲突、错误来源、写集不闭合仍是 invalid，不能冒充 absent。plan 映射在其责任入口完整校验，不能把“设计期不要求映射”扩成“施工期允许缺映射”。每 CU 保留原因码与 detail，无码异常仍 blocked，不伪造形状错误码。可选表达 WARN 与文档写失败仍不改变业务 readiness。

缺失内容由 spec/plan 在既有职责中补设计，不手工复制已有部分；§3.2 的 UI 流程/检查点沿现有不冲突补充路径完成，不要求先回填蓝图才能补写。需要改变已声明权威内容时，回原设计 owner 修订后再投影，按既有回退/重签处理。存量合法手写产物不强制批量迁移、不静默覆盖。写作自检与独立质询仍需对新需求的实际设计深度负责，不能把“机器没有加缺字段门禁”当成完整交接内容充分的证明。

### 4.3 下游消费

**正常设计交接不物化 Feature 文件。** component-design 到蓝图、CU、只读 readiness 和人读文档为止，不运行 prepare-blueprint-design CLI 来提前生成 acceptance/contracts/use-cases。spec 与 plan 直接消费已有 provider 推导的设计输入，按本阶段责任写产物；plan 在自己的 contracts.yaml 中完成专属映射。已有蓝图设计不重写，叙述文件仅按 required_outputs 产出。

**用例文件由 plan 负责交付。** 当前 CU 的合法设计投影携带 use_cases 时，plan 必须产出 use-cases.yaml，以规范化投影为初始内容，可按既有权威对齐规则作不冲突补充，不改写已有分支与预期。同步 capability-resolution-entry-input.ts 的 requiredOutputs：保留原文件已存在时必交的行为，并把“当前 CU 投影含 use-cases@1”也纳入必交条件，不能再只以文件存在性判断。复用现有投影内容和 plan 的 use-cases@1 产出声明，不新增 artifact/provider 或在交接阶段提前写文件；投影没有用例且原文件不存在时，不为本修复造空文件，其它既有用例产出义务仍照常判断。业务 UT 继续消费这一真实文件。

更新写作指引、CLI 用途说明和默认调用路径，使“交接不物化”成为默认行为。显式物化入口保留当前投影导出用途，不承担未发布旧交接数据的迁移兼容。§4.4 验证当前 spec/plan 产物的合法补充，不让正常任务先制造一份纯投影再改写。

### 4.4 当前阶段产物的合法补充与仅身份刷新

同一文件继续使用已有 acceptance@1/contracts@1/use-cases@1 和 source 身份，不新增 overlay 文件、补充登记表、审批或快照协议。现有按稳定 ID/字段比较的共用权威对齐内核供带来源戳的 resolveArtifact、无来源戳的 A1、plan 产物对齐及物化冲突判断消费；canonical-only derive 不比较阶段文件。

- 保留当前 canonical CU/蓝图的精确来源身份和原权威字段。允许 spec 补蓝图未声明的 UI/checkpoint/flows 等内容，plan 增加本 CU 映射；补充仍需通过原结构、P0、写集与映射检查。不能以“补充”覆盖/删除蓝图已有预期、重排有语义的步骤或扩大 files 授权。
- 不能仅删掉 derive 来源戳或把文件改称手写来通过；测试使用当前 spec/plan 按投影写出的真实产物，保留来源身份，经真实 resolveCapabilityInputs/readBoundInput 及阶段 checker 验证。
- **canonical 指针升版与 Feature 复用分开：通过原 canonical 校验的 CU 照常升版。只有证明设计及 CU 契约内容未变、仅身份变化时才刷新该 Feature 来源/引用身份，业务及补充字节不变。内容真变或无法证明时，该 Feature 文件保持原字节，旧 ref/输入缺口经已有 cu:feature-binding、authorityGapOf 等交回 spec/plan；不因一个 CU 无冻结证明而回滚全部 CU 或交设计 owner 补冻结记录。**
- 当前流程必须覆盖 plan 刚写完尚未冻结、CU 原地修订后 plan 重写尚未再次冻结两个窗口。保留下来的过期来源戳产物交责任阶段重建，不误报成 canonical 设计冲突；当前来源与手写内容的真实冲突检查保留。真正 canonical 非法、写入失败与依赖并发变化沿原校验和事务处理，不用宽泛 catch 吞错。
- 复用现有等价/来源判断，不以 revision 数字相近推定等价，不新增三方合并、补充归属登记或历史仓库。内容补充是否合法与旧产物能否原样刷新是两件事，不能用字段包含关系替代内容未变证明。
- 有效输入重新绑定仍走本阶段正式输出与原范围修订机制，不改冻结 manifest、跳过业务内容哈希或清零预算。本修复与代码库文件顺序误判是两个独立原因。

### 4.5 plan 生成专属映射，设计事实保持同源

canonical 设计 contracts 和 Feature 最终 contracts 继续使用同一既有结构。设计投影可不含 change_unit；plan 以该投影及当前 canonical CU 为输入，在 Feature contracts.yaml 补齐 change_unit_ref 和三类映射。接口、模型、验收、文件声明、状态与用例不重新手写；implementation/test refs 的真实落点由 plan 负责，不由 renderer 或设计投影猜造。

拆分现有检查的责任调用点，复用原函数和原因码：设计交接检查设计事实、CU 职责及可确定的授权边界；完整 changeUnitMappingIssues/Feature mapping、真实文件/符号/测试与运行映射检查继续在 plan 结束及其后消费者执行。不得用假 mapping 让设计 derive 通过，也不能直接跳过整个 validateChangeUnitFeatureProjection。

**contracts 的设计投影存在，不等于 plan 工作已完成。** 当前 CU 没有有效施工映射时，既有义务/范围派生必须安排 plan；有合法现存映射才可按已有证据复用。完整开发请求应能从设计交接进入 spec 的 UI 补充和 plan 映射，再继续施工，不把全部设计写在蓝图误解为可以越过这两项真实缺口。

新蓝图不承载 CU 专属 change_unit 映射，设计投影不把这个 plan 所有的字段带入下游；必要的字段剔除属于当前职责边界，不提供旧蓝图格式升级承诺。当前 Feature 映射按当前 CU 校验，缺失/过期交 plan 修复；CU 修订或替代不复制、删除稳定设计节点。当前来源戳产物、手写补充及合法 supersedes 的行为照常验证；不再要求未发布旧格式的兼容反例。

删除 decideRunContinuation 通过旧 contracts 字节反推出生 CU 的回退；CU 绑定直接记录并使用 canonical CU 依赖，不保留“旧绑定未登记依赖”的例外。仅维护已发布的普通 Feature、requirement、路径及代码库输入兼容，不按 legacy 字样泛删通用能力。

**随职责迁移删除失效分支，不保留双路径：**

- 删除设计投影里依赖蓝图 contracts.change_unit 的缺失/旧身份/冲突判断、身份注入及映射改写；必要的当前身份取得与映射校验移到 plan 产出/消费接点，Feature 映射检查保留。
- 删除不再有生产产出点的 authority_cu_mapping_stale、authority_cu_mapping_conflict、authority_cu_mapping_missing 设计修复分类行及相关修法；不把 plan 映射错误继续路由成“改蓝图”。
- 删除 design-repair-unattended 中专门允许删改蓝图旧映射引用的分支，以及仅证明这些旧行为的测试；历史报告原样保留，不为旧诊断新造兼容修复路由。
- 删除发布 Skill/reference/现行规格和样例中“专属映射放独占设计目标”等旧指引。全量检索调用方后仅保留仍有其它职责的共用函数，不能以兼容为由留下可被旧蓝图再触发的写回逻辑。

### 4.6 职责缺项在接受 CU 前发现

change-unit-feature-projection 的 runtime vertical slice 角色要求（behavior/owner/consumer/recovery）复用同一适用判定，移到/抽出给设计门及 acceptChangeUnitCandidates 的接受前路径调用；后续消费者继续共用，不能复制另一套角色规则。这里只前移不依赖施工产物的现有要求，真实文件/符号映射仍归 plan。

缺角色的内存候选整批拒绝且不写 canonical 目录；agent 在草稿中补齐后一次接受，不通过先落盘、再新增 v2 来修首次遗漏。已接受单元的后续补漏按 §4.7 判断同 ID 内容修订，不由 agent 直接覆盖 canonical，也不通过删除历史清理版本。

### 4.7 未完成 CU 的原地内容修订

本节“活动 CU”指尚未退役，不表示 run 正在执行；内容修订仅限无运行或运行已停住的情况。

#### 身份规则与适用边界

| 情况 | 处置 |
|---|---|
| 尚未接受的候选补漏 | 继续改内存/临时草稿，校验后首次接受；不落占位 CU，不需要新 ID |
| 同一未完成交付、尚未被精确替代的活动 CU，且无运行或运行已停住，修订职责/谓词/范围/设计引用等 | 经同一 consumer 的内容修订入口，保留 component_id、blueprint_id、change_unit_id、Feature identity 与目录，框架 revision +1 |
| CU 的运行仍在执行 | 返回现有 busy，保持原字节；不支持 runner 内借锁热修内容 |
| 仅蓝图身份变更，CU 内容不变 | 继续原指针调和，不把身份漂移误当内容变化或新工作 |
| 曾形成完成事实，当前因输入/证据变化变为 INCOMPLETE；只补原义务证据或修正原实现 | 沿既有同 Feature successor/责任恢复，保留原完成事实，不借“未完成修订”改写旧契约 |
| 已完成后新增/改变交付契约，或工作拆分、合并、归属迁移 | 新 CU 身份；适用时沿既有 supersedes/重新分解表达，不改历史前身 |
| 已被精确 supersedes 的旧 CU | 保持历史字节，修当前活动后继；不能为允许原地改历史而同步重写替代链的语义 |

同一业务切片的判定由既有设计职责和实际改动解释，不新增切片身份字段或由文件名猜测。需要真实扩权、改变需求或硬预算时仍遵守原授权规则。真实 N:M 拆分/合并的关系表达不在本批自动实现，不把单前身 supersedes 宣称为通用多前身协议。

#### 未完成资格按历史事实判断

在覆盖 canonical 之前复用 observeChangeUnitCompletion、assessFeature/inspectCompletionRecord 与既有 run/feature 载体读取：无完成事实、无未解释的成功终局且记录可判定时，才适用未完成内容修订。record=ok 但当前 uncovered/INCOMPLETE 不抹去曾完成；成功终局缺投影、broken 记录、损坏 run 按原恢复处理，不能以 state !== VALID 放行。无 run 的 feature 载体也检查已有 completion/ 原件，不因投影文件缺失就认定从未完成；不建立额外“曾完成”标志或账本。

#### 复用 consumer 与现有事务

在现有 change-unit-provider-boundary / change-unit-design-preparation 中补显式内容修订接点，输入为旧精确 ChangeUnitRef 和新候选，二者均使用已有格式。普通“接受新 CU”仍拒绝覆盖已有路径，不能改成通用 upsert 或让 agent 直接改 canonical。

复用蓝图锁和受影响 Feature 锁，持锁后重读当前 CU/蓝图、完成记录与替代关系；旧 ref 不匹配则返回原身份冲突，不覆盖他人修订。候选复用 schema、provenance、设计/角色/授权及依赖校验，通过后由框架计算 revision。无内容变化不增版，重复请求不产生额外目录或版本；批次任一失败不落盘，写出使用同一 temp→rename/回滚原语。内容修订只提交合法的新 CU，不顺手刷新旧 Feature 业务产物；它们保留原字节并由下述绑定缺口交回责任阶段。展示刷新失败仍不回滚已成功的 CU 修订。

复用现有运行状态和锁判断：仅无运行或已停住且锁可正常取得时执行；运行中一律 busy，不抢锁、不杀进程，也不实现 runner 内借锁内容修订。本轮修改实施方案不意味着授权停止或修改当前宿主 run。已有运行内的纯蓝图指针调和不属于本次内容修订，保持原职责。

#### 修订后派生、依赖与继续执行

- CU revision/hash 的真实内容变化继续使旧映射与有关输入 stale，旧产物保留给责任阶段处理；plan 按当前 CU 校验/更新映射，不自动合并 spec 补充。不能只换旧 contracts 的 change_unit_ref 就宣称承担了新增谓词，也不能把内容修订套进仅身份调和的等价捷径。
- requires 仍是 from_change_unit_id + provide_id，无版本语义。修订只补内部细节且提供承诺不变时复用原关系；改变已被引用的提供承诺时，在同一设计修订批次核对并对齐受影响消费者，或用新 provide_id 显式改线。不允许旧消费者仅因字符串相同就被判兼容；未完成 provider 仍不能满足需要有效完成证据的依赖。不新增 provide 版本注册表。
- 恢复只复用 feature-assessment 的现成信号：Feature 所绑 CU revision/hash 不匹配时，changeUnitBindingIssues 形成 binding 缺口；无既有合同义务承载时即 cu:feature-binding，owner_phase=plan，有合同义务时沿原分摊。**本批只补停住的 run 接到这一信号并进入原 plan 责任恢复的接点**，不增加第二套 stale 判定、调度或 scope 修订引擎。
- 无运行时由已有准备/义务路径安排 plan；停住的 run 沿原 continuation/assess 选择恢复或 successor，范围不能承接时使用已有范围修订机制。保留同一 CU/Feature 目录、原事件、有效证据和累计预算，不改 manifest 出生字节、不删除 required 义务或以 fresh run 清预算。内容修订本身不启动施工，也不手填 scope_revised。
- 契约内容修订本身不承诺旧证据全部可用或下游零重跑。已有等价/覆盖判定决定复用与未覆盖义务，只重做有实际失效的责任工作，不因保留同 ID 而把旧完成结果套在新要求上。

## 5. 部署视图的既有规则与外部方建模

不新增按单次需求切换适用性的判据。将 canonical `app-component-blueprint` 的 `Viewpoint contracts and App view instances are separate` requirement 中已有规则写进宿主可见的 `skills/reference/app-component-blueprint-workflow.md`：**按部件自身运行拓扑（平台、进程、独立持久化和外部边界）裁决 deployment 适用性，不随单次需求变化。** `applicability` 与本次 `evolution_impact` 仍正交；不适用保留依据，适用视图按原规则进入独立质询。

deployment 适用时，所有场景（包括纯本地场景）的 `deployment_refs` 都要指向本部件自己的实际运行/部署节点；外部节点表达上下文，不替代本部件落点。本部件自身的真实变化照常声明并由 CU 承担。

App lens、P1 写作与质询复用上述既有 applicability/evolution_impact 和 `requiredQuestioningScopes`，不新增平行 scope/检查项。只读渲染不自动改写历史适用性，真正设计修订仍归原 owner；§7 用现有跨视图检查与 closure 验证外部事实、内部施工的边界。

#### 6.2.1 完整调用时序：复用字段与阶段责任

**结论：现有字段足够承载，由设计 agent 生成 Mermaid，renderer 不从自然语言反推调用。** `ordered_steps` 现为 string[]，保留该类型，不塞对象或另造箭头文本解析 DSL；`generated_graphs.content` 现为 Mermaid 字符串，继续作为可重建的派生图。图不是调用关系的唯一记录，不能把设计遗漏只补进 Mermaid。

| 需要表达的事实 | 复用位置及责任 |
|---|---|
| 参与对象、方法、参数/结果类型 | canonical 目标上的 contracts.components / interfaces / data_models，既有 runtime 节点/owner 与根契约。只列本流程实际参与对象；页面、业务对象、Repository、存储 helper、数据库不能因同属一个模块就合并角色 |
| 调用方、被调用方及真实顺序 | runtime flow 承载的 contracts.state_management[].ordered_steps 是施工可投影的主责步骤；每条明确“调用方调用被调用方.操作，参数/结果，等待或回调，成立条件”。细粒度不足时由设计 owner 补设计，不由 renderer 分解大段叙述。原 flow.ordered_steps 若保留，同次设计调用同步，不建立另一条写作真源 |
| 落库确认、幂等、失败与返回 | 根 contracts[].operation/request_dto/response_dto/errors/idempotency/table_schema，flow 的 source_of_truth/publications/consumers/failure_recovery，以及 state_management 的既有恢复说明。说明写入、提交确认和页面成功之间的顺序，返回或错误必须有原设计依据 |
| 分支与完成 | use_cases 的 scenario/user_sequence/expected_phase_seq/expected_port_calls/not_called/linked_acceptance 作为设计核对材料；其本身不提供完整调用者关系。主成功时序须到结果后的完成、返回/清栈与实际消费者，不以 branches[0] 停在 Success 就宣称完整 |
| 图内容与追溯 | 设计 agent 在同次 component-design 中根据上述事实生成根 generated_graphs 的 graph_id/format/source_view_id/content/node_refs/relation_refs；不新建 interactions、participant registry、source map 或独立 mmd 权威文件 |

设计步骤示意（说明粒度，不替代宿主当前事实）：页面调用业务对象提交；业务对象按已声明顺序检查会话/账号并调用 Repository.save；Repository 经真实存储 helper 调用数据库写入并查询确认；数据库结果沿原调用链返回，确认成功才进入成功结果；结果页完成由已声明导航对象处理，首页再按当前账号查询 Repository。若设计实际没有 helper，不为凑“层数”添加一个；原调用是回调/异步时据实写清，不自行改为同步。数据库失败、导航失败、切号/销毁等分支与主路的分叉点由设计明确后再画。

生成流程是“写调用设计 → 设计 agent 生成图 → 现有 runtime/flow 独立质询核对 → 发布同一蓝图 → renderer 展示”。一条箭头对应已写的调用或返回，分支条件对应已有分支/恢复说明；可以在图标签或 Mermaid 注释使用步骤编号供审阅，不新建稳定步骤 ID。质询沿现有 scope 核实调用者、接口/参数、返回、等待、真实分支和完成链；语法/引用检查不证明语义一致，不新增自动自然语言比较器。正常新设计默认完成该图；缺图仍不是新增 readiness 机器门禁，但不能报告本项人读验收通过。

#### 6.2.2 图的保存、展示与最小校验

- 仍用 `format: mermaid`，`source_view_id: runtime`；graph_id 使用已有图 ID 机制。node_refs 包含所表达的 runtime flow 及参与对象的已有设计承载地址，允许多个类型由同一目标承载，不假装一地址一参与者。数据库可追到已有数据节点/根存储契约，不新造无法解析的“table:”地址。relation_refs 只引用真正已有关系，可以为空；不为每条调用或返回新建顶层 relation，否则会无必要地增加 CU/closure 认领义务。
- renderer 按 flow 引用把时序图放入运行章节相应流程；流程仍有自己的有序步骤与分支说明。直接输出已声明 content，不调模型、不读产品源码/Feature/外部文件来补边；禁止以 relation_refs 为空为由隐藏合法 sequenceDiagram，现有仅有关系边才展示的分支需按图类型区分。已有结构、模块、阶段、跨视图图不因此被替换或重复展示。
- 在原 `blueprint-graph-generator.ts` 的 parser/validate 入口增加小型 sequenceDiagram 子集：participant/actor 声明与 as 标签、调用 `->>`、返回 `-->>`、Note over、alt/else/end、空行与 `%%` 注释。核声明重复、消息/注记端点存在、分支块配对及原 node_refs/relation_refs 地址可解析；不支持的语法如实诊断，不静默截断。语法以 [Mermaid 官方时序图文档](https://mermaid.js.org/syntax/sequenceDiagram.html) 为据；不引入完整 Mermaid 编译器到业务校验路径。
- **时序图校验仅报 WARN**：超出子集、重复/未声明端点、alt 未闭合、图引用地址无法解析等图自身问题，在蓝图检查中均为 WARN，不报 BLOCKER。renderer 不展示该坏图，在原流程位置说明具体原因，保留其它图文；诊断不得经 sourceGaps、投影 invalid 或其它汇总间接阻断准入/readiness。缺图与坏图均不新增停机点。现有 flowchart 的校验级别保持不变；真正的 canonical 对象/契约/来源缺陷仍由原检查处理，不借图 WARN 降级。
- 主路与关键失败可以在同图用 alt/else 表达，或同 flow 的独立补充图；完整性以调用链及分支可审为准，不以恰好一图/四图限制真实内容。先做本次确实需要的语法，不顺手加 activation、loop、par、任意 HTML、外部 include 或主题配置。真正需要并发语义而当前子集不足时保留明确的步骤说明并披露，不假画成串行。
- 图的修订沿原 P1 派生流程：生成结果在既有 derived_results 中以同 graph_id 对应 result_id，使用已有 input_revision/source_fingerprint/decision_fingerprint/status（kind 归图派生结果），复用 evaluateDerivedConclusionFreshness，不新增 hash/签名/状态文件。设计事实变更时 owner 在同次调用重生成受影响图；不能只改来源戳证明语义未变。renderer 对本次新增时序图缺少对应结果或已 stale 时不显示旧图，单独提示重建，不改变 readiness；旧 flowchart 不新增迁移门槛。身份当前只证明来源版本一致，图文语义仍由既有质询核对。
- 图不能覆盖结构化设计，也不作为新的 Feature 输入或授权。ordered_steps/接口/恢复设计有真实变化时沿原蓝图修订、CU 调和和内容摘要语义处理，不新增“展示字段剔除”；本批不为规避重新派生而改变摘要算法。
