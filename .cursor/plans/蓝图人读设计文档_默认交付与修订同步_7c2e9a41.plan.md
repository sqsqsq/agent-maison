## 3. 内容契约 v2：示例映射与最小字段增量

### 3.1 示例的使用方式

t1 逐节对照示例，形成“评审关切 → 4+1 主责位置 → canonical 字段/目标 → 渲染形式 → 验收”的映射，覆盖背景、旅程、参与方、功能、模型、状态/流程、持久化、取舍、质量与上线协同。

采纳示例的细致程度与图文叙事，不照抄业务事实、重复章节、历史矛盾或未来占位实现。t1 使用用户示例逐节映射与**一个充实变体夹具**形成表达样稿，明确标注“不是真实需求”；不等待尚未到来的宿主任务。该变体同时供渲染测试、交接测试和 docs 样例使用，不修改广泛复用的原 Ledger fixture，也不在各测试中分散复制拼装独立版本。样稿不能代替最终机器生成产物；宿主新需求的目标样稿与权威来源对照归 t5，t2–t4 可先完成。

t1 明确验收 ID 的范围（全蓝图唯一或每个 CU 内唯一）及跨目标同标识的展示方式，沿用既有投影行身份与冲突规则，不新加门禁。示例中尚无明确落点的持久化配置（第 1028–1178 行）、数据打点（第 1766 行）、Visual Handoff（第 262 行），逐节裁决为“映射到具体既有结构”或“不纳入”，不得实施中再增第七类字段；端到端时序用有序步骤表与分支表表达。

### 3.2 设计目标上的三类结构化内容

复用 [蓝图设计输入与物化](../../docs/concepts/blueprint-design-inputs.md) 及 `harness/scripts/utils/types.ts` 的原结构；承载目标的 provenance 必须满足现有 authoritative 要求，不因作者写了这些字段就自授外部权威。

| 内容 | 既有结构与应包含的细节 | 挂载约定，由 t1 样本细化 |
|---|---|---|
| `acceptance` | `AcceptanceSpec` / `acceptance@1`：criteria、boundaries、performance；设计期写 AC/BD/NFR 的 ID、优先级、验证步骤、预期、分层与关注点；UI 流程关联按下述分工 | scenarios 或 logical 设计目标；仅所有引用者共同承担的验收可放共享目标，专属 AC/BD/NFR 放仅由对应 CU 引用的目标 |
| `contracts` | `ContractsSpec` / `contracts@1`：modules、module_dependencies、data_models、interfaces、components、files、integration_points、state_management 及既有 CU 映射 | development 节点和 runtime flow；共享目标只放所有引用者都应继承的内容，单 CU 的 change_unit 映射与专属 files 放其独占引用目标 |
| `use_cases` | 目标字段承载 `UseCasesSpec`（下游 artifact 为 `use-cases@1`）：阶段、UI/数据边界、触发调用、分支序列与预期、linked_acceptance | runtime flow；共同用例才放共享目标，单 CU 专属用例放其独占引用目标；未触发的义务不造占位内容 |

**共同继承规则**：一个 CU 的 `design_refs` 选中目标后，该目标上的三类内容会整体参与这个 CU 的投影合并；所有引用该目标的 CU 都会继承。只有数组型键按原行身份/内容去重、同标识冲突拒绝、其余行并入；对象型键不逐键合并，重复声明只有内容完全相同时才接受，否则报 `authority_content_conflict`。例如 contracts 的 `module_dependencies`、`navigation`、`resource_keys`、`change_unit` 和 acceptance 的 `flows` 应集中放在该 CU 引用的一个目标上，不能拆成共享部分与专属部分等待自动拼接。既有机制不支持从同一目标中只挑一部分验收、写集或映射，也不按该 CU 的 predicate 自动过滤其它 AC；t1 样稿与 t3 写作指引同步这一边界。

因此，`contracts.change_unit` 的单 CU 映射、专属 AC/BD/NFR、只由该 CU 写入的 `contracts.files` 及专属用例，必须放在**只被该 CU 引用的设计目标**上。共享目标只放所有引用者都应满足、都应拥有的内容。复用同一页面/模块不意味着共同获得其中全部施工授权，模块范围检查也不能代替同模块内的文件写集审查。作者按原节点/flow 与引用方式组织目标，不为内容切片新增 selector、过滤协议或映射文件。

t1 样稿至少包含一组共享目标与两个独占目标。例如 CU-A 引用 S+A，CU-B 引用 S+B：S 放双方共同的验收及双方都获准写入的文件，A/B 分别放各自专属验收、文件、用例及完整 change_unit 映射。样稿展示数组型内容分别得到 S∪A、S∪B，对象型键按上述规则集中承载。把 A 专属映射误挂到 S 的反例须写准实际原因：B 也声明不同映射时为 `authority_content_conflict`；B 未声明自身映射时，按具体缺失/未知谓词报 `change_unit_predicate_mapping_unknown` 或 `change_unit_predicate_mapping_missing`。同一文件被两 CU 合法先后修改可以保留，不加“写集重叠即失败”的门禁。

**P0 真机验收分工**：设计期保留验收条目的 ID、优先级、步骤、预期、`ut_layer` 与 `ut_focus/device_focus`。没有 ui-spec 依据时，不写 P0 真机条目的 `linked_flow`、checkpoint 和屏幕流程；由 spec 得到真实 UI 依据后，沿既有“不冲突补充”路径补齐。已有对齐检查只比较蓝图已声明的键，补充不能修改原预期或其它权威内容；有依据且写入流程关联时仍须满足现有完整检查。不得编造元素 ID，不得为避开检查删除整份 acceptance，不修改 P0 门禁。t1 样稿和 t3 写作指引均体现此分工。

`feature`、机器来源戳、当前 CU ref 等按原投影规则注入；不得把自指 hash 手填进蓝图，`contracts.change_unit.change_unit_ref` **设计期不写**，由投影补齐，避免蓝图与 CU 相互存储对方哈希。这项注入不会把属于另一 CU 的映射变成本 CU 的合法映射。

`contracts.files` 仍是唯一施工写集；`touches`、目录树、设计图或节点名称不能扩大授权。模块目录展示取自 `contracts.modules[].package_path/layer`，依赖取自 **contracts 根级** `module_dependencies`，文件来自 `contracts.files`；分层约束引用已消费 DSL 的事实，不在展示时新裁决架构。代码骨架不进入蓝图。

| 部署参与方与上线协同 | deployment 节点及视图 | 节点：`responsibilities?/inputs?/outputs?/not_responsible_for?: string[]`、`failure_impact?: string`；视图：`rollout?: [{order: number, unit: string, depends_on: string[], note: string}]`、`coordination?: [{counterpart: string, relation: string}]` | 第 118–203、1738–1792 行 |
| 部件级质量与数据生命周期 | 蓝图根 | `quality_attributes?: [{qa_id: string, category: string, requirement: string, landing: string, source_ref: string, verification_refs: string[]}]`；`data_domains?: [{data_domain_id: string, usage: string, retention: string, isolation: string, cleanup: string, security: string}]` | 第 1548–1556、1589–1651 行 |

`data_domains` 与已有 flow 的 `data_domain_refs` 使用同一标识口径；不新增数据域注册表或 `design_ref.target.kind`。质量属性描述部件级要求与落点，精确可执行阈值/预期由既有 acceptance 承载，通过原 ID/来源引用关联，不另维护一套 NFR 真源。部署 rollout 表示已声明的配套/上线顺序，不转换为 CU `requires` 或执行授权。

补充 `contracts.data_models[].fields[]` 的可选 `description: string` 与 `source_ref: string`，分别用于约束/说明和来源列（示例第 308–326 行）。现有 contracts schema 允许扩展、SpecLoader 已能透传，本批只补 `ContractsSpec` TS 类型和一条经现有加载/投影链的透传断言，不新增 schema、validator 或归一化处理。renderer 只展示字符串，非字符串显示“未能表达”，不使整份契约失效。

所有新增 `source_ref` 只指向设计期已经存在的需求、Swagger、DSL 等来源，不指向本 CU 将新建的文件，避免把未来施工产物收成输入依赖。t1 对照表核实该约定；来源引用不自动成为 `contracts.files` 的写入授权。外部部署节点及协同字段按 §5 建模，不把外部方待施工内容写成本部件节点的变化。

### 3.4 可选内容的校验与缺失语义

- 六类字段及上述注释字段缺失：相应位置显示“未记录”，不造内容、不新增缺字段检查。三类机器内容未写入时使用 §4 的专门提示。
- 六类可选字段存在但形状不合法：给出位置与原因的**非阻断**诊断，文档显示未能表达的项，不假装内容有效；只做形状校验，不增设语义审批。上述两项字段注释仅按 §3.3 显示字符串或“未能表达”，不新增校验。
- 本批不改 schema，也不添加 type/required 等约束；六类新增可选子树的形状问题仅由现有 validator 以 WARN 非阻断诊断承载，不放入会导致 publication 失败的 CU `sourceGaps`。
- 原有强契约不降级：`acceptance/contracts/use_cases` 的真实机器结构、来源权威、写集、CU 映射、引用解析、设计准入仍按既有 checker。可选字段的宽容不豁免既有路径/授权边界，也不证明设计已足够。

## 4. 设计期写作与交接前校验

### 4.1 写作责任

完整交接前，`/component-design`、P1 workflow 的“写入同一蓝图”、App lens 与独立质询共同覆盖 §3：按 4+1 形成设计解释、三类结构化细节、真实选择及被否方案，适用信息展开到可评审粒度。

标题与固定说明用中文；新写叙述使用项目语言，保留 API/类型/路径等原名，不新增 locale 配置。不把所有内容塞进 summary，不为凑文档新造会产生 closure 义务的 decision；新增真实决策仍经原权责与 revision 规则。

只要 canonical 内容改变，本次结束前仍重建文档。未变、未决、缺失与不适用分别如实表达；需要有权者裁决的事实不能由 renderer 或下游自行补定。

### 4.2 提前调用同一投影内核

`prepare-blueprint-design.ts` 现有 CLI 调用 `materializeBlueprintSkillInputs`，**它会写文件，不能直接当作交接只读检查使用**。在已有 CU 身份可解析、指针调和非 busy 后，复用其内核 `deriveBlueprintSkillInput(projectRoot, feature, frameworkRoot, kind)` 的默认模式，对 acceptance 与 contracts 读取、归一化和检查，连同现有 use_cases 校验；不另写一份设计解析器。

默认模式同样只读，不传 `'pure'`：后者会跳过既有 `use-cases.yaml` 与投影的冲突检查。指针调和及其原有派生刷新后仍存在的冲突，应在交接以现有 `authority_use_cases_conflict` 提前报出；不能留到后续物化才失败。其它调用方合法使用 `'pure'` 的职责不改变。

在 `deriveDesignPreparationReadiness` 已有 per-CU 检查处接线；范围仍为全部未退役 CU，包括已经完成的旧 CU。仅对原设计判定为 `constructable` 的 CU 运行投影检查，避免重复报告同一原因；保持 `validateChangeUnitDesign` 的原职责，避免把它再接回会调用它的投影函数形成循环。只读校验本身不物化 sidecar、不写 Feature 产物、不生成 phase PASS/receipt，不触发 selector/Goal。原 readiness 已有的指针调和与人读文档刷新照常执行。

旧 CU 引用内容非法时如实报告其 CU 与既有原因，通常需要设计 owner 修复被本次修改破坏的共享目标；不能跳过已完成 CU 换取 ready，也不自动重新启动旧 CU。已物化 CU 的新蓝图内容非法，还可能先在调和刷新阶段抛出既有 `change_unit_blueprint_ref_bump_rejected`，此时不会进入下面的正常结果表：沿用原异常传播及整批指针/派生文件回滚，保留修改前的这些字节，不回滚用户已经修订的 canonical 蓝图，不伪装成 readiness 成功。

已声明的三类内容分别检查，不能因另一类 `absent` 而提前返回、漏掉所提供 use_cases 的形状/语义。若现有内核的提前返回妨碍这一点，在同一模块提取/复用已有 bundle 解析与检查供原消费者及交接共用；不构造假 acceptance/contracts 触发校验，也不复制规则。

| 原内核结果 | 交接处理 |
|---|---|
| `resolved` | 已写入内容通过原语义检查，可交现有 typed 投影消费；不代表整个产品完成 |
| `absent` | 不把缺字段升级成新增机器门禁。对应章节写“设计期未写入，将由 spec/plan 补”，交接如实列出已有设计缺口和责任，不声称这部分已能直接投影 |
| `invalid` | `perUnit.verdict` 使用现有 `blocked`，复用既有 `authority_*`/解析/设计检查原因进入原 readiness 的 not-ready 结果，交回原设计 owner；不新增检查 ID、停机原因或持久状态 |

已声明的空值、文字冒充机器内容、冲突、错误来源、写集不闭合或映射不合法仍是 `invalid`，不能冒充 `absent`。不因 presentation 可选形状警告改变 ready；文档物化失败也继续与业务 readiness 分离。

缺失内容由 spec/plan 在既有职责中补设计，不手工复制已有部分；§3.2 的 UI 流程/检查点沿现有不冲突补充路径完成，不要求先回填蓝图才能补写。需要改变已声明权威内容时，回原设计 owner 修订后再投影，按既有回退/重签处理。存量合法手写产物不强制批量迁移、不静默覆盖。写作自检与独立质询仍需对新需求的实际设计深度负责，不能把“机器没有加缺字段门禁”当成完整交接内容充分的证明。

### 4.3 下游消费

有效的 acceptance/contracts/use_cases 由现有 provider 和唯一物化入口供 spec/plan 消费，版本/hash/权威校验保留。`spec.md`、`plan.md` 等叙述文件仅按 `required_outputs` 产出，不为名称齐全生成空文档，也不重写机器设计内容。

新需求的验收证据必须区分：设计者写入 canonical → 交接只读校验 → 后续实际需要时物化；机器来源戳、规范化内容与 CU 引用需可核对。已有 `authority_content_*` 等问题应在这一步回设计期解决，B1/B2 运行中恢复继续保留为后备。

## 5. 部署视图的既有规则与外部方建模

不新增按单次需求切换适用性的判据。将 canonical `app-component-blueprint` 的 `Viewpoint contracts and App view instances are separate` requirement 中已有规则写进宿主可见的 `skills/reference/app-component-blueprint-workflow.md`：**按部件自身运行拓扑（平台、进程、独立持久化和外部边界）裁决 deployment 适用性，不随单次需求变化。** `applicability` 与本次 `evolution_impact` 仍正交；不适用保留依据，适用视图按原规则进入独立质询。

外部参与方（云服务、HA、配置台等）节点只记录当前事实：`current_state` 与 `target_state` 相同，不声明变化；**蓝图根级 contracts 只登记本部件实际消费或提供的接口**，由消费该契约的 CU 在 `design_refs` 引用并承担本部件这一侧的证据，指向外部节点的 relation 同样由该 CU 引用，不以外部 owner 代替 CU 认领。外部方自己的施工中本部件不消费的部分，若阻挡当前切片则记为 gap 并按既有 CU blocker 表达解除条件，仅需说明的写进 `coordination` 或 `rollout`，不建根级 contract，不让本部件 CU 虚假认领外部施工。

deployment 适用时，所有场景（包括纯本地场景）的 `deployment_refs` 都要指向本部件自己的实际运行/部署节点；外部节点表达上下文，不替代本部件落点。本部件自身的真实变化照常声明并由 CU 承担。

App lens、P1 写作与质询复用上述既有 applicability/evolution_impact 和 `requiredQuestioningScopes`，不新增平行 scope/检查项。只读渲染不自动改写历史适用性，真正设计修订仍归原 owner；§7 用现有跨视图检查与 closure 验证外部事实、内部施工的边界。

## 8. 宿主新需求验收与收口

**不用已完成的 bc-openCard-2 补设计细节。** 不在其 canonical 目标上补 acceptance/contracts/use_cases，不改 CU、完成证据或原 run。旧目标的验收输入变化可能使 completion 变为 INCOMPLETE；不能为本计划演示触发旧业务返工。它仅用于隔离副本上的渲染、旧格式和兼容对照，后续也不以此替代新需求验收。

正式样本改为宿主下一项真实需求：当该任务实际到来时确定 blueprint/需求来源、授权和采用窗口，不臆造需求、不复用旧案例伪称新流程已验证。先按新流程完成设计写作和独立质询，形成目标承载的三类结构化内容及 CU，再只读前置校验和自动生成 4+1 文档。

沿用七问，但结合整份文档与各视图的实际内容检查：

1. 需求、目标、成功衡量、本次范围与非范围是什么？
2. 当前问题与目标变化是什么？
3. 方案如何运行，包括状态、分支、失败与恢复？
4. 哪些模块和外部参与方分别承担什么、边界在哪里？
5. 为什么选择当前方案，被否方案及代价是什么？
6. 分几个 CU 交付，各自结果、显式依赖和安全中间态是什么？
7. 质量、风险、待决项与 AC/BD/NFR 如何验证？

另逐个核对 4+1 内容及跨视图联系：场景能追到逻辑对象、运行流、开发落点与适用部署；契约、数据生命周期、目录与文件、组件选型、验收和 CU 指向一致。图文表不能互相矛盾，也不因一个视图标未变而丢失其它视图的真实变化。

验证后续 spec/plan 实际消费同一投影：对照 canonical 目标、只读检查结果、机器来源戳及物化字节，不允许先手写下游再倒填蓝图或用文本承诺替代实际消费。机器等价不代替人对完整设计文档的实读。

宿主只通过 Maison 构建并校验的发布件集成到 `framework/`。记录复用既有 verification，包括真实需求、来源身份、视图/子表定位、投影验证、缺口与修正；不新增签字、审批或验收登记系统。框架实现与宿主验收分别报告，下一项需求未到来时 t5 保持 pending，不假绿，也不因此无限等待而阻碍已完成框架工作的交付。

“框架工作可先完成”不等于本版可越过发版门禁：本 plan 仍绑定 3.1.0 且 t5 未完成时，`release:check-plans` 会失败。与同窗口其他宿主待办（如 1dbe4fa4 的 t5）一样按既有版本策略处理，不得为发版把 t5 标 completed/cancelled；若明确决定顺延，按既有 version/deferred_to 规则办理，不新设豁免。本轮不做顺延决定。
