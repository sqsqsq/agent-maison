# 扩展按插件分目录，存量按需手工接入

**交付目标**是在 Framework 3.1.0 首次对外发布前确定唯一的按插件布局。已对外发布的 Framework 3.0.0 使用平铺的清单 1.0。旧宿主只升级框架时，原有扩展保留在磁盘上，重新接入哪些能力由维护者决定。首版人工整理钱包的 Story，走所有插件共用的安装和启用入口。[3.0.0 发布说明](../../RELEASE-NOTES-v3.0.0.md) · [3.1.0 发布状态](../../RELEASE-NOTES-v3.1.0.md) · [总纲 §11.2](../goals/复杂能力建设目标_能力架构蓝图到部件演进与变更单元闭环_75411223.goal.md#112-稳定内核与-provider-接缝语义)

## 1. 为什么由提供方确定边界

钱包旧清单 `wallet-sdk-demo` 同时列有 `story`、`wallet-sdk-onboarding`、公共约束知识、阶段 Hook 和规则覆盖。`post_check.mjs` 引用 Story 的模板，可以据此确认依赖。清单没有记录这些资源应当跟谁一起发布、升级和卸载。按目录名猜，或把整个 `wallet-sdk-demo` 自动包进一个目录，都可能让停用 Story 连带撤下其他能力。

| 场景 | 改动及可观察收益 |
|---|---|
| 一个插件要一起管理脚本、知识和 Hook | 来源包与宿主副本按插件同形组织，能在一个目录找到声明和资源，单包生命周期可验。 |
| 存量注入少，平铺资产缺少可靠的插件归属 | 维护者只整理首批确实要用的 Story 资源。共用或归属未定的内容保留，由实际使用方决定后续如何接入。 |
| 用户更新框架或运行普通业务 | `framework-init` 不承担扩展升级。运行时只消费新注册的包，旧根不会触发搬移、命令执行或业务全局阻断。 |

本期撤销原草案里的通用 1.0 迁移器、暂存换根、自动路径改写，以及“迁移扩展目录”“刷新扩展入口”两个 init 专用任务。`1.1/2.0/2.1` 属于未对外发布的内测清单，同样按需要从来源整理。**新格式插件自身的同源版本升级**仍属于 `/extension` 的正常管理能力，沿用动态退出、替换和重新启用语义。[既有启停计划](实例扩展协议增量_动态启停与生效阶段选择_ee85b0d3.plan.md)

## 2. 唯一运行布局与清单分工

以下用默认 `doc/extensions/` 举例，实际使用宿主 `paths.extension_dir`。插件 ID 是稳定的包名，目录名与该插件清单的 `name` 一致。草案沿用新清单 `schema_version: "3.0"` 的提议，Framework 开发窗口为 `3.1.0`。

```text
doc/extensions/
├── manifest.yaml                        # 宿主登记已安装的插件与宿主选择
├── story/                               # 维护者手工整理后安装
│   ├── manifest.yaml                    # 仅声明确认随 Story 交付的内容
│   ├── skills/story/
│   └── hooks/                           # 本包选定的 Story Hook 及其资源
└── ux-behavior-spec/
    ├── manifest.yaml                    # UX 发布者的声明
    └── skills/ux-behavior-spec/         # 包含 SKILL.md、取用指引、schema 等
```

- **顶层清单由宿主写。** 按插件 ID 记录安装来源和版本、开关、绑定选择与阶段覆盖、受管文件归属和指纹。为安全退出所需的既有启用效果及待清理事实仍随该宿主的安装条目保存。提供方的 `provides`、默认绑定、启停命令和规则只存在于插件自己的清单及文件中。
- **插件清单由提供方或自有插件维护者写。** 一个包可提供多个 Skill。安装、整项启停、升级、卸载、漂移核对以插件 ID 和目录为单位，单个绑定仍可选择或改投阶段。保留业务入口、原作者 `extension-result` 和请求追溯。裸 Skill 在安装副本生成最小包清单，初装仅供手动调用。按描述推导的动态命令沿既有明确确认流程。
- **路径按插件定位。** `ref`、`cwd`、`outputs` 和脚本资源相对该插件根解析。`MAISON_EXTENSION_ROOT` 对该插件命令指向包根，业务交付继续使用项目相对路径与原写权。不同包可有同名内部文件。对外 Skill 名、独占能力及同一规则槽的冲突沿既有消费者的次序或冲突语义处理，诊断点名相关插件。
- **管理边界一致。** 安装将本地来源导入 `<扩展根>/<插件ID>/` 并登记宿主选择，消费者读取已登记包。重装、动态 `run/undo`、在途占用的非阻塞待清理回执和重试均按该插件处理。外部包只清理归属明确的受管资源，原地自有来源、宿主改写和已交付业务产物按原归属保留。

## 3. 旧宿主与 framework-init 的处理

- **空根或新根**沿正常 `/extension` 管理流程安装、校验和刷新入口。只读 `inspect / verify` 继续只读。通用 loader 只接受新宿主清单和已登记的插件清单，删除按 `1.0/1.1/2.0/2.1` 执行、扫描旧根级维度目录和合并来源声明的分支。
- **遇到旧根**时沿已有格式诊断指出路径，并提示“旧版扩展未加载，请按需手工整理后重新接入”。普通业务继续使用框架和 profile 自身输入。明确需要旧插件的请求能看到具体缺口，不能报告已投递。管理命令不会把非空旧根当空根覆盖，也不更改旧桥、运行记录或宿主手写资料。无需逐版本解析旧清单来给出这个提示。
- **`framework-init` 不办理扩展升级。** S1/S2/S3/S4 和 [init 任务计划](../../harness/scripts/utils/init-task-planner.ts)无需新增扩展任务或依赖。初始化已有的通用适配器渲染若读取扩展信息，只使用新 loader 返回的已登记包。人工接入后的入口物化由 `/extension install` 或现有 `materialize` 负责。
- **手工切换入口**由 `MIGRATION.md` 说明。选好需要接入的包，待使用旧路径的工作结束，再自行留存旧根并建立干净的新根，或按现有配置指定一个新的扩展根。按正常安装回执核对宿主清单和受管入口，检查旧桥中的遗留路径。保留旧副本供维护者对照，运行时只认当前配置下的新登记。

## 4. 首版只做一次真实的 Story 手工接入

1. 以钱包现有 `skills/story/SKILL.md` 为起点，维护者按实际调用确认脚本、模板、参考资料及 Hook。`wallet-sdk-onboarding` 保持独立，公共 `knowledge/constraints/` 和整组阶段规则不会因同处旧目录而自动划给 Story。确有需要的条目逐项确认资源、真实接收方和生效时点，剩余原件留存。
2. 在钱包或提供方维护的本地来源中整理 `story/manifest.yaml` 和包内文件。手工修正已确认的旧路径，例如 `post_check.mjs` 中对 Story 模板的引用、Hook 正文里的命令，以及 `story.js` 的 mock 数据路径和 `story_flow.py` 按父目录层数找宿主根的用法。包内资源按脚本或包根定位，业务数据按真实宿主根定位。宿主源码和业务凭据不随 Maison 主包分发。
3. 在隔离钱包用 `/extension` 从这个来源安装 Story。用本地测试数据点名调用 `story`，核对脚本确实读取包内模板。首版用 Story 专属的 `story_on_context_load.mjs` 验证 Hook 接入，分别核对有、无 `AR/story-flow.json` 时返回的片段以及 verifier 实际收到的内容。若维护者明确给 Feature 作者投递知识，用一次真实作者输入验所选路径或正文。验收以人工选入的 Story 资源为界。

## 6. 验收与完成条件

| 场景 | 通过条件 |
|---|---|
| 旧根遇到新发布件 | 在保留 3.0.0 平铺资料的隔离副本执行只读检视和一次普通业务请求。有手工接入提示，旧清单、脚本、业务资料及旧入口指纹一致。新运行没有投递这些旧项，普通业务继续。配置了新根后，旧资料不再参与查找。 |
| Story 从平铺资料手工接入 | 保留人工选入的资源清单与实际调用记录。`/story` 稳定入口可用，至少一个 Story 专属 Hook 与它实际读取的内容在正确场景送达，脚本可定位模板和宿主根。SDK 入口、未选中的公共知识及规则不会随 Story 注册。 |
| 再装 UX，与 Story 分别管理 | 同一钱包正常安装新版 UX，顶层可检视两个插件。蓝图作者实际复用或生成 UX 并交回。停用、升级或卸载 UX 时 Story 仍可用，Story 源文件、宿主自有内容和已交付 UX/蓝图保持原归属。 |
| 新协议与发布内容 | 空宿主安装来源包及裸 Skill，回归阶段选择、动态启用、逆序退出、在途待清理、漂移与按包隔离。随包示例可直接安装，源码仓的可选插件未进主包。正常用户不需要先运行专门的迁移或 init 任务。 |

实施收口运行 `npm run openspec:validate`、仓根 `npm test` 和上述隔离宿主验收。本次计划修订只校验计划结构、引用及文档差异。
