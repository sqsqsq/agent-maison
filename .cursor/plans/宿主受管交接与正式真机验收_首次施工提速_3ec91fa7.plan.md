# 宿主受管交接与正式真机验收、首次施工提速

## 1. 现场与范围

11 月 19 日银行卡宿主使用 Maison 3.1.0 发布件 `badbfd66`、DSH `volcengine/deepseek-v4.1-flash`。以下时间为 UTC。原始输入是需求正文、四张参考图、公开前门判定和原始用户的无人值守完整交付授权。核查材料均位于宿主 `doc/features/bc-openCard-2/`；根运行 `goal-runs/20261119T045043Z-4a2996`，CU 运行 `bank-card-open-flow/goal-runs/20261119T070626Z-30eaa8`。后文分别称根 i9、CU i9 等，两个序列独立编号。

## 2. 优先打通已签工作与实际写方

**前台领取与运行。** 梳理 `goal-mode-entry.ts` 返回的 `phase_execute_request`、`execute_command / observe_command` 与 `session-execution-handoff.ts` 对当前请求的核验。把“领取后执行”接到宿主实际进入的运输和主会话指引（`skills/project/goal-mode/SKILL.md`、`skills/reference/goal-mode-operations.md`、`docs/operations/project-entry.md`）。无人值守按既有 detached 运输自动执行，前台保留可见回执、带游标的等待和终点汇报。有人在场运输在已有授权下执行准确返回的命令。保留领取、只读观察、中断及人工接管各自的语义。相同请求已绑定活进程时接着观察；已合法交回时沿原游标消费；租约或输入确已失效时由 runtime 重读、重签或按现有真实条件等待。重复领取、进程重启、两个观察端都只产生一次有效执行，不手拼身份。前台仅凭目录、旧 HALTED 报告或助手总结不能签完成。

**运输由已核实的用户选择决定。** 现场是明确要求无人值守的原请求误入 attended：根和 CU 的 `phase_start.driver=session`，前台逐次 `--next`，最后读了 i15 的命令却没有执行。现在 `designDeliveryNextStep` 并列给两种命令，两个 session 分支会在签发后返回前台。实施时先让已有前门读者从本次真实用户输入或同一根请求已核实的运输选择，给出唯一适用的启动/续接动作；入口在创建或领取处复用同一判定。已核实的无人值守完整交付即使经 `goal-mode-entry --prepare-run/--next --run-mode attended` 进入，也由程序在原授权内接到既有 `goal-runner --detach` 启动或续跑路径。首次创建只生成一个根 run；已有 run 使用原 ID、原预算、当前 CU 和合法 owner。前台拿启动握手及 wait 命令，留在原对话等待，不承担后台推进。明确选择有人在场者仍按会话运输，`--authorize-autonomy` 授权范围内的自主决定，单凭此标志、默认 unattended 文件权限或模型转述均不能覆盖用户对运输的选择。旧 run 缺可信选择时维持已确定的运输；不能从未知来源推断新授权。

**在运输交界处验实际执行。** 优先在产生下一份签发前确定运输。若已有会话绑定的有效 i15，先按原请求的执行/观察接口消费或接回该份工作，待原执行权可正常交接时再接到同一 run 的后台续跑；当前有在途执行则接着观察，保留已有交回及完成事实。由入口的既有启动器/协调器负责这一交接；释放原会话写权与成功取得后台握手的顺序沿既有锁和 owner 合同核实。未成功接管时返回可恢复的真实状态。遇到启动与绑定之间崩溃、无法判断原进程是否仍有写权时，先观察与核原件，禁止盲目再执行。复用现有启动握手、run 锁、请求围栏与原 executor，避免并行启动两个写方、重签一份来冒充原请求或依赖前台再次调命令。只读状态查询始终只观察。用真实 DSH 前台自然请求覆盖“用户明确无人值守 + 从会话入口进入”；再用同一配置从已有未绑定请求进入，发起方取得回执后刻意只观察，不调用 `execute_command`。两例都须由受管原生进程留下同一次有效签发、一次绑定及受理交回，前台收到简单进度和终点。双观察端、重复领取、真正有人在场且明确不要后台、只有自主权但没有无人值守选择、前台退出后重新接回均作对照。替身只验证消费协议；仅修改文案或只看后台 PID 不通过此项。

**按对象派工。** 在 `initial-design-delivery.ts`、`design-repair-unattended.ts` 的原修订事务和 `goal-phase-runtime.ts` 的现有处置/写界匹配中，分别交付蓝图修改、候选引用修改、契约修正、UT 断言、测试计划。先核实际对象、可写路径、当前输入和上次交回。蓝图作者新增验收编号后保全已获准的草稿，让候选写方更新同一候选的引用，再走原消费者与需要的独立质询。合法遗漏继续复用预装候选；错误引用、并发修订、不同 CU、超写界的改动不能被接纳。测试作者只获准写一份派生计划时，把余下的弱测试或契约差额交给各自已获授权的写方；只要尚有另一写方的可执行工作，就不以当前作者“无新工作”结束全局推进。同一对象、原因、输入、写权都没变时保留原去重。新设计决定或真实授权缺口归既有责任流程。

**按三次快照区分改动时段。** 在两种运输的既有签发、进程绑定和交回接点，分别取得同一相关写界的前像、绑定时快照和后像。比较签发至绑定、绑定至交回两段。签发后、绑定前已经改变的字节不计在尚未启动的作者名下；绑定窗口内的越界仍拒绝采信。快照只能定位时间，出现并发、缺快照、旧 run 或相同文件两段均变时，不推断具体人员、不指令后任回滚他人的改动，保留冲突交权威方复核。所有 adapter 共用该判断，无须按各自原生工具日志归责。正常入口、前台等待及最终汇报的 goal-mode 指引均明确：运行期间前台不改受管文件，看到 FAIL 只等待或汇报；修复由有写权的受管请求执行。

**四个客户端短例。** 在独立本地测试工程，DSH、Claude Code、Codex、OpenCode 各从真实客户端发送自然的无人值守交付请求，实际经过会话入口并观察同一 run 由后台接续；记录四个客户端分别使用的接口、模型、run/请求、原生进程绑定、有效交回和前台回执。DSH 另验上述已有 i15 的场景。Cursor 暂缓真实短例，其余宿主保留公共合同回归与能力差异说明。客户端或本机确无可用后台执行时，回退到既有可用的受管会话执行请求，前台保留可见状态、如实披露依赖会话存活。连专用执行器也不可用时返回既有可恢复状态和原因，不签后台成功、不由前台施工。

**在设计作者原轮次交回确定性问题。** 对已经能从蓝图权威内容派生的验收与用例视图，复用既有 P0/spec 语义检查，一次给出 linked_flow/linked_branch 不能解析、P0 流程边缺适用 checkpoint、requirement_ref 的引文未逐字命中原始需求这三类具体位置及依据。新首稿、设计修订各轮在原有机器反馈中读取当前草稿，无须先建立 CU 或另外调用设计模型。必须等候选映射方能判断的检查保留在其责任接点。A 项以根 i9 原件验证同一反馈能发现当时已确定的三类问题，修好后不再为同一原因派 i10～i14，真实新设计矛盾仍需独立核实。该段约 35 分钟中包括真实设计工作，实际节省按重跑计量。

**场景与收益。** i10 因候选写权被拒后反复领相同工作，CU i9/i11/i13 仅能写计划，i14 窗口内前台先写，i15 有请求无执行。复用已签请求、变更原件及写界即可保留有效成果，减少空派、误恢复与人工代写，无须新增权限、登记表或停机原因。回放应包含“已有请求但还未绑定”“已有活进程”“前台先写”“作者自身越权”“确有剩余不同写方”“确实没有可执行工作”。

## 3. 让正式真机路径可执行

**计划位置。** 根 i9 的候选生成脚本把需求根路径展开为 57 条错误引用。沿 CU 身份与既有路径解析（`change-unit-path.ts`、`harness/config.ts`、`test-plan-derive-hint.ts`）为候选提示、施工映射、顶层计划和派生提示提供同源位置。候选尚未获准时按蓝图与 CU 身份计算预期位置；已准入时从相同身份解析实际产物。区分 CU 内长期引用的计划落点、当轮授权的 `testing/reports/<轮次>/hylyre/` 执行输入及其绑定，不冻结运行前尚不存在的时间戳。已有正确 `planned:` 引用仍可解析；多 CU 同名文件、旧单 Feature 合法路径不串用。旧错误只在可证明唯一语义时由原写方重签，其余给出根因、目标 CU 和受影响引用清单，一次修源并重验。

**动作定义。** 在现有 checkpoint 中用动作种类区分控件操作与无控件目标的系统动作。点击、输入等继续绑定真实选择器；系统返回绑定真实 `back`，无目标侧滑绑定当前设备原语可观测的侧滑（含适用方向、屏幕起点等辨识条件）。直接复用现有 Hylyre 步骤：系统返回使用 `{"back":{}}`，边缘返回使用 `{"back":{"mode":"swipe","side":"RIGHT"}}` 等与实际约定方向一致的返回手势。普通全屏横滑不能冒充导航返回，合法的控件内滑动保留原语义。补核 `derived-hylyre-plan.ts`、`runtime-step-evidence.ts` 旧轨迹路径和静态 selector 冲突检查；旧版有目标动作沿原判据，旧轨迹不能证明新动作时继续缺证。由同一规则供验收投影、spec 完整性、Hylyre 派生/身份注入和正式 native trace 判定消费，落在 `p0-semantic-gates.ts`、`p0-identity-injection.ts`、`check-testing.ts` 与现有 profile 指引。一个动作窗口须证明操作前屏幕、真实动作成功以及随后可辨识的页面状态/禁止节点；动作未执行、方向相反、从错误页面起步、只观察到已有页面、用点击或系统返回替代要求的侧滑均留缺口。若同屏没有导航（返回被拦截），仍要有可核对的前后证据。同一用例多次返回须按步骤次序和窗口分别关联。设备端确实缺必要的原语或证据时，按已有能力缺口处理，不签已验证。

**派生差异。** `derivedPlanStaleByTcTable` 及原 `derive_hint` 显示首个不一致的 TC、字段、顶层值及已选派生值，区分文本、行为、缺动作、缺原件与 HAP 条件；用同一比较规则供作者预查和正式检查。保留顶层约束与来源身份，只重做有差异的行，覆盖、身份和行为仍在正式入口重算。i9/i11/i13 三份计划复演，开发回放把第三份送入原执行器的正式装载/预检并核其剩余诊断，真实上机归 §6B 的独立授权。回放 `ui_entry_coverage` 的两个组件同名 `handleNext`，以调用归属、真实业务入口及既有 `entry_ui` 映射区分；确属多入口的仍须覆盖。AC-19 的数据库读回归应用内，UI 状态归设备，倒计时变化与发送次数分别取证。

**场景与收益。** TC-10/13 的动作没有控件目标，有目标时注入失败，去掉目标又过不了规格。补齐现有动作语义后，两例才能走到真实设备；精确的派生差异能省去相同 18 行的多轮重写。只扩既有校验与提示，不引入平行计划或给 Hylyre 新增数据库能力。

## 4. 格式返修、增量质询与审查

1. **设计质询。** 在 `parseIndependentQuestioningOutput` 复用原解析链，容纳唯一、完整的 Markdown JSON 围栏数组，继续支持既有对象和裸数组。保留签发源、独立回执与原字节，逐项核 ID、归属、证据。多块冲突、有歧义、重复身份或截断时由原独立方补充格式，禁止从散文猜 verdict。以根 i2 原件验解出 26 项、保留 3 个真实否定，不为同一份合法内容再付一次整轮质询。
2. **独立审查。** CU review-i4/i5 对同一材料重复签发 23 项；i4 的 YAML 有 22 个解析错误、正式读者收不到条目。复用 `repair-candidates.ts` 的逐项读取与已有补格式通道，反馈具体错误位置和原表片段。整块不可读时，原审查者基于原报告重新交一份可解析的完整回执，只修表示；整块未被解析之前不算任一条已通过。能独立核实的合法旧条目按 ID、签发范围、验收文本、测试源码和真实生产路径复用。正式执行证据仍单独核当前构建。不同输入、冲突或漏答只重开对应问题；真实负面结论交修复写方。实现时复用现有 verifier 格式补充的签发、交回、累计预算和无进展语义，将同一独立职责与原材料送原质询或 CU 独立审查者。现有 CU YAML 读取失败会返回空，应在该真实缺口组装处接回；不假定现有阶段 verifier 的开关或 attestation 已覆盖这两条路。后续整体 review 优先审查实际改动与未关闭问题，继续核对受影响的关联义务；已获适用结论的无关材料直接复用。回放 i4/i5 的 0→23 条、其中 5 条原始不足继续有效，及同源未变、改了断言、只变构建、重复 ID 和修后应关闭的对照。
3. **蓝图内部地址。** 在 `questioningDependencyChanges` 提取证据时先通过现有蓝图地址解析定位内部指针，再由 `selectQuestioningScopes` 沿业务引用求受影响范围；文件依赖继续以工程实际路径和原件比较。Windows 的 `/design_views/0/nodes` 被解释为盘根文件，i11→i14 的单项对照因此从 17 增到 26。用相同已签前像/回执验证内部地址只随拥有者和真实消费者传播；17 是排除文件依赖的诊断对照，实际选择还要加入真实变更的文件。指针消失、类别歧义、关系无法唯一还原或确有全局影响时保留保守复核。增加同名真实文件、POSIX 绝对路径、外部不可读引用及只改派生图的反例。i3→i5、i5→i8 另有变更权威引用未能对应范围，逐组标明全量理由，不能用一次 17 项回放代替全部验收。

这些改动在既有规则内减少重复读取和模型调用。能解释的包装问题无需重做业务判断；有真实设计矛盾、缺证、混用证据通道仍能阻止通过。沿用已有可比增量样本的输出与墙钟目标，列出每轮签发范围、实答、复用及原因。只有受影响范围不超过首轮一半的可比轮，才评输出量 ≤50%、墙钟 ≤70%。

## 5. 时间花在哪里

用根/CU 的既有 `events.jsonl`、调用和检查原件重建同一条不重叠时间线。现场 86.97 分钟内，`resume` 到下个活动 33.55 分钟，门禁到门禁 26.25，门禁到模型 11.54，模型交回到下一次 `resume` 13.88，其余约 1.75。优先剖析前两段。按会话运输与后台运输分列，特别区分前台收到结果后到下一条命令、runtime 冷启动到 resume、同一进程内的检查间投影。对比同种运输的分项成本；从会话切换到后台带来的端到端变化另报，不归功于某个检查函数。再在各段内部定位签发到绑定、重签、读证据、状态投影、外部等待与实际计算，明确嵌套关系；证据不足标“未归因”。需要细分时仅在开发回放短时采样，不新增常驻状态或运行门禁。

若证实相同输入在同一求值内重复计算，复用原结果；对真实变更或新请求仍重新取证。用相同输入、端点、并发口径与上限比较调用数和墙钟，保留异常恢复与新鲜度反例。86.97 分钟不是可承诺节省的时长。没有可证重复时交付分段结果并说明，避免把全部等待归给先前的 a21473 收口开销。

## 6. 统一验收，两项独立结论

**共同条件。** 在隔离副本先冻结最小必要的真实片段、源版本和原件哈希，原宿主只读。用公开入口回放各项正反例，增加非银行卡的候选/测试路径和返回动作样本；单测或模型替身只证明对应消费链。实现完成后执行 `npm run test:changed`、`npm run test:daily` 与 plan 校验；变更阶段规则指纹时同时跑既有快照迁移套件。保留轻量需求和无 plan 路径，不给首次产品修改新增 CLI 或模型轮次。宿主获准联合验收时，从需求实施前干净基线、原始需求及四图、核过的发布件与同一模型/配置出发。记录现场条件、设备与 HAP 身份，禁止引用旧交付作为新首稿。两个结论使用同一次运行和后续合法接续的原始时间线，所有尝试、人工介入、等待和失败均披露。

### A. 效率验收：到首次正常施工

- 起点取原请求根 `run_created`；终点取已准入 CU 与施工范围下首个真实施工作者的 `agent_process_bound`，核对该签发确实承担产品实施并有真实实施活动。单独列首次产品写入时间；只有签后差异时给出可证窗口，精确时点记未知。只有签发、只有 CU、范围准备、视觉 canary 或再次设计不充当施工终点。
- 同时报两个量：终点前实际启动的设计调用 **≤9 次**，以及起点至终点 **≤100 分钟**。含首稿、质询、分解、设计修订、施工范围准备的所有实际模型调用及失败重试；去重按签发/实际进程身份，另列未绑定的签发。首次正常施工作者本身与视觉 canary 单列。暂停、后继、执行器切换或前台重开均不截断墙钟或清零计数。
- 现场反推可以至少定位 i2→i3 的格式重问及 i10 之后的重复作者；候选写方仍需执行的工作必须计费。以少一次格式重问、减少三次修订往返、另加一次候选写方且模型是否过载为假设，估计约 11～12 次；这是定位剩余差额的假设，不能预签 ≤9。验证哪些可唯一投影的引用可由既有候选生产步骤一次生成，把同一批可判断的设计/投影问题在原有调用一次反馈，并保留真实独立质询。只有实跑能决定有无进一步节省；门槛不因预估调整。
- 在 A 项本地回放中分别核对首次设计作者收到的三类具体缺口、修订后准入结果与复问原因，标注消掉的原调用及仍必需的调查/质询；隔离回放不计作宿主 A 签收。
- 两量同时满足且全程按授权推进才签效率达标。超标列实值和原因；没启动正常施工则记录停点、已花时间与调用数。开发回放中较快到 CU 单列为中间结果。

### B. 交付验收：到同一需求正式完成

- 按根请求目标和当前 CU 范围执行到正式终点，要求根运行正式完成、适用阶段的当前结论、`feature-completion.json` 与适用的部件闭环相符，无尚未解决的必需义务。父子状态冲突、仍有待执行请求、只有聊天总结或只有单阶段 PASS 时均列明缺口。产品完成与发布就绪按原规则分别报告。
- 从真实修改到当前构建，核对编译、具名 UT 及独立强度结论、正式设备执行、视觉与其他适用义务的来源。正式派生计划与当前 HAP 上，按批准的验收 ID、行为和动作绑定定位“结果页返回拦截”与“清栈后侧滑”的可见结果；回放用旧 TC-10/13，新运行允许重新编号；正式计划内所有必需用例逐项结算。AC-19 由真实生产路径写入、读回、核字段和重复卡行数。倒计时 UI 用前后可比较的实际值，重复发送次数用能观察生产调用的应用内证据。最后一次修码后按影响重验，专项冒烟单列并保留其版本。
- **旧失败关闭单独举证。** 执行 TC-10/13 只覆盖测试准备和正式执行。另以有原始 FAIL 的历史 TC-02/06/18 及非银行卡对照经正式调度，核当前适用构建、原触发、目标与断言；合格复验或原签独立核验只关闭相应旧失败，换目标、弱断言、过期构建和只有摘要仍阻断。历史不可与本次新 CU 或 HAP 混签；新宿主未产生对应失败时，列清隔离回放已验和真机未覆盖项。
- 真实联合验收继续核实前台仅执行/观察获准请求、遇 FAIL 仅等待或汇报，且未代写受管产物、未用场外测试顶替正式 testing。核此次验收的前台实际操作与正式运输回执；运行时写入时段一律只以三快照判定。存在未解释的改动或不足以证明无前台代写时，将该项标未验证，B 不能签 PASS。需要人工凭据、设备动作或预算触顶时如实保全。若现场不具备授权设备或必需原件，保留交付待验与具体原因。分别报告 A 与 B 的 PASS、未达标或未验证，以及整项墙钟和未完成项。两项结论互不代签。
