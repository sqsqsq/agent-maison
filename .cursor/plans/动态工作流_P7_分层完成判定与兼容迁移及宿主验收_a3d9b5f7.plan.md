# P7：闭环、兼容与宿主验收

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；前置：P1–P6。
> P2 已拥有 scope/manifest/assess 与单任务完成基础；本 plan 接通 CU/Component、迁移及公开切换。
> 宿主材料准备与首批实跑可提前开展，公开默认切换须等完整消费面接线。

## 1. 背景

当前 change-unit-completion 从 workflow/track 推导 expectedChain，
即使 runner 使用新范围，CU 聚合仍可能要求完整旧链。
相反，若直接信任 completion 自报的 chain，又会重现“截断执行冒充完整完成”的旧事故。

旧 lite/full run 已有合法冻结历史，公开 change-lite 退役不能让这些任务无法恢复。
新任务去除 track，不等于删除历史轨道的 reader，也不允许自动把旧未完成阶段改成 N/A。

## 2. 完成层级与必要输入

| 完成层级 | 必需事实 | 不可宣称 |
|---|---|---|
| 请求/Skill | 请求终点、调用结果、对应实际证据 | 整个 Feature/CU 自动完成 |
| Feature | 有效执行范围、全部 required 义务、执行与复用证据、既有 closure | 仅末段 PASS 就完成 |
| CU | Feature completion VALID、canonical CU 目标与设计/提供映射、当前蓝图准入 | 无关联独立 Feature 自动算某 CU |
| Component | 蓝图目标、所有必要 CU/组合 owner、真实组装/风险/NFR 证据 | 单元都绿就没有整体缺口 |
| 跨部件能力 | 上游明确的跨部件验收责任与外部证据 | 其它部件未知时宣称整个能力通过 |

completion_target=request 的阶段结果可作为后续审查的事实输入，
但不能未经覆盖与 freshness 校验直接 credit 完整 CU。

## 3. 完成结构与消费者

保持现有 completion 文件、写入入口和验证接口，扩展必要的范围绑定。
新 schema 对 execution_scope_fingerprint 增加必填约束，
版本增量与 TS/schema/writer/reader 同提交；旧版本仍使用其旧完整链合同。

~~~ts
// 现有 FeatureCompletion 的新版本字段增量，非新文件/状态库。
execution_scope_fingerprint: string;
// 既有 chain / phases / requirement / source / evidence 等字段继续由唯一 writer 派生。
~~~

验证器独立解析有效 scope（P2 的真实 run 身份），不能信任 completion 自报指纹，
也不能从 feature.yaml 候选生成完整交付凭证。原 run_id、原件落点、phase_start/attempt/run_end
血缘检查继续成立；P6 的 request 报告只能作为专项结果。
验证责任：

1. scope、来源、requested completion target 与出生/修订权威相符。
2. chain 等于有效 scope 的执行链；reused_phases 证据按 P2 核验，不伪造当前执行记录。
3. 所有 required 义务均由当前执行或有效承接证明；unknown 不得完成。
4. CU 目标谓词、provides、design_refs 映射完整，未执行 spec/plan 不豁免机器映射。
5. 数据/代码/构建/运行时证据按既有 freshness、质量轴和授权规则验证。
6. 缺 testing 只有在设备/视觉义务确实已满足或不适用时合法。

change-unit-completion.resolveChangeUnitExpectedExecution、
buildChangeUnitGoalHandoff 和 verifyFeatureCompletion 调用方共用 P2 范围来源，
不再各自按当前 track 重算现代任务的预期链。
P2 应已提供此入口与基本完成检查，本项只收编这些上层调用点。

同时核对仍直接读取物理设计/验收文件的完成辅助函数，包括
computeRequirementSsotAggregate、loadAcceptanceFlowsDoc 与 runtimeFidelityEvidenceIssue 的调用链。
现代任务的需求聚合、P0 flow 判据与目标覆盖必须消费 P1 的实际绑定内容及来源；
不能因 acceptance.yaml 未物化而漏掉 P0 设备义务，也不能因省略 spec.md 得到空需求聚合。
已有源码/build aggregate 的实际含义保持，不能仅因字段名带 testing 就删除真实新鲜度检查。

Component closure：
复用 deriveComponentClosureObligations 及原有 source→blueprint→CU→contracts→evidence 关系。
不同 CU 可使用不同阶段集合，但必须覆盖各自目标；
多个 CU 共同形成的调用/数据/恢复/UI/NFR 关系仍要求真实组合证据。
合法无 testing 的 CU 不制造缺报告；需要整体设备证明的组合义务继续保留。

已完成 CU 的历史事实不改回 pending。蓝图修订后的 carry-forward
继续使用现有稳定目标解析与准入规则，不能借新动态 scope 放宽它。

## 4. 兼容矩阵与恢复

| 记录 | 解释与操作 |
|---|---|
| 旧 workflow 1.0/1.1 + 旧 contract/run | 沿冻结 phase_chain/原 track 与旧完成合同恢复 |
| 旧 manifest 无 phase_chain | 仅复用已有 legacy 恢复路径，不新增宽松 fallback |
| 新 manifest 有合法 execution_scope | 唯一消费该 scope，track 不参与新运行决策 |
| 新 scope 存在但 schema/hash/内容非法 | 明确损坏并恢复，不回退成 full 或零义务 |
| feature.yaml 有旧 track、无活跃 run 的新请求 | 新入口重新按本次事实建立新 scope，旧字段保留作历史 |
| 旧活跃 run 上用户说继续 | 恢复原 run，不自动转换 |
| 用户明确提出改变任务/范围 | 经既有 correction/successor 签发新范围，保留旧事实与预算治理 |
| 新旧任务同宿主共存 | 由各自出生版本/运行身份分派，禁止依据目录名猜测协议 |

新旧版本差异只在 reader/输入规范化/历史阶段执行边界集中处理，
不把 if(track) 分支继续散布进新业务判断。
不创建 migration-progress.json、全局迁移 ledger 或专用兼容运行器。
不自动移动、删除、重写 consumer 历史产物与 evidence。

旧 run 若要跨越不兼容发布件执行，按既有版本/发布件兼容治理明确选择：
使用可支持该历史协议的 reader/executor，或在合法修正后创建新 run。
不能默默用新 checker 改解释旧凭证，也不能声称任何跨版本证据永久有效。

## 5. 默认切换与清理

切换条件：P1–P6 的现代 contract/source/scope/phase/checker/verifier/evidence/resume/完成面全部接通。
新 active workflow 使用新协议，用户只见范围与理由；不提供长期 lite/full/dynamic 选择菜单。

逐项去留：

- track_scoring：新任务不再决定执行范围；仍有历史诊断需要的最小读逻辑保留。
- feature.track 确认点：从新公共 registry/入口移除，旧任务恢复不能触发已退役流程选择。
- change-lite 用户 Skill：停止新任务选择，旧 run 所需正文/执行语义通过内部兼容路径保留。
- exit：scope/编译/验收等真实检查已由 P4/P5/完成机制承接后停止新任务使用。
- change.md：有效历史来源或明确输入需要时可内部复用；不再是必经跳板或新映射真源。
- REQUIRED/OPTIONAL 文件表：现代消费由 P1 接管，剩余用途逐项限于 legacy。
- 旧固定后继文案/提示/模板：删除，全部从 P2 scope 投影。
- adapter bridge：沿现有 UPDATE/deprecated cleanup 先备份再清理旧公共入口，
  内部旧 run 读取不依赖用户 slash 跳板存活。

检查现行 README/MIGRATION/overview、phase-transition、skill-contracts、
各 Skill、agents 模板、现行 OpenSpec specs；历史 archive 保留。
不以“彻底去字样”为由破坏历史解释；新用户 smoke 不出现 lite/full，历史报告允许原文。

## 6. 机械验收与候选发布件

必须实际运行的组合场景：

1. 新 Feature 无 testing：runner 完成、verifyFeatureCompletion VALID、CU 完成合法、P3 聚合不报空报告。
2. scope 自报缩链/漏目标/引用坏证据：完成失败，不能从 completion 反向采信。
3. 同蓝图两个不同 scope 的 CU：ready、完成、组合义务均正确。
4. 旧 lite/full 中断恢复：保留原链、预算与凭证解释；新请求使用新 scope。
5. scope 新事实修订：旧 run 不改写；复用仅针对仍有效证据。
   通过真实 CLI/bridge 串通 spec 闭环→登记后继→旧 owner/锁释放→新范围出生→自动施工，
   在 P2 §6.3 指定窗口重入，验证只有一个后继、scope/end/chain 正确、预算未清零。
6. standalone review/UT/testing/project：只报告请求结果，不 credit Feature/CU。
7. 真实控制边违规或必需 provider 不可用：不静默剪枝。
8. fork workflow/extension 的新阶段：未知合同不默认忽略；旧合同按版本解释。
9. 所有受影响 adapter 的新/旧入口与 UPDATE 清理行为：兼容读不依赖被移除公共桥接。
10. attended prepare/attach 完整运行 coding→review→ut，验证真实事件与原件使 completion VALID，
    CU 及部件推进可正常消费；只有 Feature 候选和裸报告时不得生成或通过 completion。
11. 无 Feature 的 review/UT 从 P6 真 CLI/adapter 进入，实际使用 request facts 和独立报告路径，
    对照活跃 Feature 的 facts/reports/attestation/receipt/events，确认一个字节也未覆盖。

扩展现有 integration/fixtures，不新建 A/B 或基准平台。
根据候选构建现有命令生成发布件，在临时 consumer 目录解压、安装 harness 依赖并验入口。
宿主 framework/ 一律发布件落盘，不是 submodule；依赖仅在 framework/harness 安装。

## 7. 真实宿主验收与缺口回灌

资料最小集合：发布件版本、原请求、真实 acceptance/蓝图/CU（适用时）、代码/测试目标、
实际运行结果与相关 events/report 路径。已有报告可以直接引用，不新建证据账本。
现场 RDB 原先的推断项先用这些材料核实；不能补造事故发生顺序。

| 宿主场景 | 直接观察 |
|---|---|
| RDB 纯逻辑修复 | 运行实现/review/UT；无额外 testing TC/计划/报告/流水线 |
| UT 经 ohosTest HAP 执行 | 记录 UT 自身环境，不能误报完全未使用设备 |
| 页面交互/device AC | 真正执行所需设备验证与有效 trace |
| performance 单元可证明/真机必需 | 层级分配符合指标语义，未知不误裁剪 |
| 同蓝图数据库与页面两个 CU | 各自 scope 合理，真实组装责任仍闭合 |
| 单独 review/UT/设备测试 | 不补造上游材料，不冒充完整交付 |
| 只设计/查看/项目知识维护 | 在请求边界结束，不自动施工 |
| 中断恢复与新接口发现 | 沿冻结范围恢复，需要时回退重签 |
| testing 失败 | 按根因修复，不能消除义务 |

P5 可用时尽早开展 RDB 首批，后续补完整矩阵。
没有资料/设备时只保留相应 todo 未完成并列解除条件，不重复申请已获授权；
可继续完成不依赖环境的代码与机械验证。
缺陷回到唯一责任 plan：来源/P1，范围/P2，设计/P3，实现/P4，验证/P5，入口/P6，聚合/P7。
后续 review 只核既有问题修复及直接回归，不持续扩建机制。

## 8. 发布交接与验证比例

交付现行文档、MIGRATION 的旧 run 恢复说明、消费者采用说明和真实宿主结果引用。
纯计划与文案修订不运行生产单测；生产改动按 cd harness && npm test。
OpenSpec 变更运行 npm run openspec:validate；plan 状态运行 node scripts/check-plan-version.mjs。
总纲最终整合复核复用这些结果，不再创建第二轮同等整批验收。

实际发版时遵守 release:check-plans、changelog、release:all 及发布说明流程，
release:all 前台运行，测试/打包不重复。写完本 plan 不是发版授权。

父目标 G6/G7/G8：保证动态执行没有破坏整体交付证明。
所有完成事实仍归现有事件/证据/完成原语；没有手工 done 台账。
如果某兼容机制无法找到真实旧消费者，删除；若旧消费者确在使用，保留最窄边界并写清退出条件。
