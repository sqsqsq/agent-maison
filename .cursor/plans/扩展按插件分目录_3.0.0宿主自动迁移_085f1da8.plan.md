# 扩展按插件分目录与 3.0.0 宿主自动迁移

**交付目标：维护者把新发布件集成进正在使用 3.0.0 的钱包，运行一次 `framework-init`。原有 Story、知识、Hook 和规则在新位置可用，随后可独立安装、启停和升级 UX 插件。** 新建宿主与迁移完成的宿主使用同一加载路径。实现落在尚未对外发布的 Framework 3.1.0 窗口。[3.0.0 发布说明](../../RELEASE-NOTES-v3.0.0.md) · [3.1.0 发布状态](../../RELEASE-NOTES-v3.1.0.md) · [总纲 §11.2](../goals/复杂能力建设目标_能力架构蓝图到部件演进与变更单元闭环_75411223.goal.md#112-稳定内核与-provider-接缝语义)

## 1. 公开基线与新增机制的收益

对外自动迁移只有一条：Framework **3.0.0 的宿主清单 `1.0` → 新布局**。核验过的 `framework-3.0.0.zip` 的 SHA-256 为 `c4fa65ea6b796478d106ae05a28037e3889b6b7a11ae7b3edb14552221dbc345`，与发布 sidecar 一致，包内源提交为 `1feabd006fcd5b81d5d07190c1c1fe1c461ba3ca`。钱包工程只提供真实宿主输入；它当前的内测 `framework/` 不能替代该基线。

**作者知识索引单列取证。** 公共 ZIP 的 `extension-loader.ts` 校验并收集 `knowledgePaths`，其 `goal-runner.ts/buildPhasePrompt` 没有把这些路径直接送给作者。钱包 Hook 可以另行把知识引用送给 verifier。后续 3.0.x 的 `e1017f3f / 0143e21e` 才把有效 1.0 知识路径和读取指令放进 Feature 作者提示。按本次要求，迁出的插件也提供这项作者索引。验收将它标为相对公共 ZIP 的明确增量，独立于旧 Hook 投递等价性，不增加第二个可升级的发布版本。[作者索引原计划及历史判据](作者前置输入接线_goal作者prompt注入knowledge索引_接缝对齐主干cp_a7c3e9d2.plan.md)

| 已证实或已裁决的场景 | 设计增量 | 实施后看什么 |
|---|---|---|
| 一个插件的脚本、知识和 Hook 分落多个顶层目录，升级还要把来源声明合入宿主清单 | 每个插件有一个目录和一份提供方清单，保留一个宿主选择入口 | 升级或删除一个插件时能指出它的全部受管资源，其他插件的声明、资源和选择不变。 |
| 钱包的 `wallet-sdk-demo` 同时含两个 Skill、约束知识、阶段 Hook 与规则覆盖，脚本和说明内有旧路径 | 以原清单名整包迁移，在暂存区校验路径、语义和可刷新入口 | 钱包无需人工拆包，Story 的实际命令及模板引用在新位置可用。 |
| 更新 framework 后，现有 init 任务在 `harness-install` 后直接准备全局检查 | S1 只在命中时列出“迁移扩展目录”“刷新扩展入口”，S3 调用同一管理实现 | 正常升级只运行一次 init。单项迁移失败有原因和解除办法，其他 init 任务仍产生自己的结果。 |

## 2. 唯一运行布局与清单分工

以下用默认 `doc/extensions/` 举例，实际使用宿主 `paths.extension_dir`。插件 ID 是稳定的包名，目录名与该插件清单的 `name` 一致。草案将新清单的 `schema_version` 定为 `"3.0"`，与 Framework 的 `3.1.0` 版本号独立。

```text
doc/extensions/
├── manifest.yaml                        # 宿主登记已安装的插件与宿主选择
├── wallet-sdk-demo/
│   ├── manifest.yaml                    # 迁入的宿主自有插件
│   ├── skills/story/                    # 仍可点名使用 story
│   ├── skills/wallet-sdk-onboarding/
│   ├── knowledge/
│   ├── hooks/
│   └── rules/
└── ux-behavior-spec/
    ├── manifest.yaml                    # UX 发布者的声明
    └── skills/ux-behavior-spec/         # 包含 SKILL.md、取用指引、schema 等
```

- **顶层清单由宿主写。** 按插件 ID 记录安装来源和版本、开关、绑定选择与阶段覆盖、受管文件归属和指纹。为安全退出所需的既有启用效果及待清理事实仍随该宿主的安装条目保存。提供方的 `provides`、默认绑定、启停命令、规则正文只保存在插件自己的清单及文件中。顶层清单不再合并或抄录这些声明。
- **插件清单由提供方或自有插件维护者写。** 一个包可提供多个 Skill。安装、整项启停、升级、卸载、漂移核对以插件 ID 和目录为单位；单个绑定仍可选择或改投阶段。包内声明使用稳定绑定身份，保留业务入口、原作者 `extension-result` 和请求追溯。只装裸 Skill 时，安装器仍可在安装副本生成最小包清单，初装仅供手动调用。按描述推导的动态命令沿既有明确确认流程。
- **路径按插件定位。** `ref`、`cwd`、`outputs` 和插件脚本资源相对该插件根解析。`MAISON_EXTENSION_ROOT` 对该插件命令指向包根，宿主业务产物仍使用项目相对路径和原写权。两个插件可各有同名内部文件。对外 Skill 名、独占能力或同一规则槽的冲突按既有消费者的次序或冲突语义处理，并标明涉及的插件。
- **目录与声明一并切换。** 安装将一个本地来源包导入 `<扩展根>/<插件ID>/`，登记宿主选择，再从已登记包构造同一份内存贡献视图。重装、阶段调整、动态 `run/undo`、非阻塞在途退出与残留报告延续已验收的语义，作用域改为插件。迁入的宿主自写内容以原地来源保护，卸载撤登记、效果及生成入口，保留宿主原件。外部包只清理归属明确的受管资源。正式需求、UX 稿和蓝图继续归项目。[已交付的启停语义](实例扩展协议增量_动态启停与生效阶段选择_ee85b0d3.plan.md)

运行时只读新格式的顶层清单和已登记插件清单。根不存在且无旧资产时返回空集合。只有迁移入口含 1.0 解析器；通用探测只识别旧布局或版本以给出提示。删除 loader 内对 `1.0/1.1/2.0/2.1` 的执行分支、安装时合并来源声明的分支，以及根级 `skills/knowledge/hooks/rules` 的扫描和回退。不要以旧目录链接、双份资源或另一个常驻索引维持运行。

## 3. 一次性迁移如何保护原件

| 探测结论 | 管理入口处理 |
|---|---|
| 空宿主或已经是新布局 | 空宿主可按原请求初始化。新布局直接执行本次操作。重复迁移不改清单、指纹、宿主开关，也不重复运行启用步骤。 |
| 可解析的 1.0 维度清单 | 将该宿主旧目录作为一个以原 `name` 命名的原地插件，完整带入 Skill 和其他自有资料。按下表转换声明与引用。 |
| 旧 1.0 清单损坏、缺所引用资源、目标重名、名称不适合作为安全目录名，或只有旧目录而无法判断所有者 | 保留原始文件、入口和清单，指出文件/字段、原因和可执行的手工修正步骤，修正后重试同一入口。 |
| 内部试用的 1.1 或 2.x（含 2.0、2.1） | 识别版本并提示从原始插件来源按新协议重新安装。说明如何保留现存副本和宿主手改，再初始化新根。对此类输入不做自动转换、不据它投递贡献。 |

| 3.0.0 的输入 | 迁出后核对的行为 |
|---|---|
| Skill 目录、原 `provides.skills`、随附脚本和模板 | 依旧版**实际扫描到**的有效 `skills/<id>/SKILL.md` 明列可用 Skill，核对桥接名称。没有独立归属证据的资产留在同一个宿主自有包。 |
| `provides.knowledge` 的字符串路径 | 原文件可读、原顺序及可解析的宿主引用保留。在迁移时写出新格式的知识声明，面向全部 Feature phase 作者提供项目相对路径索引与读取提示，由作者取用适用的原文。按 3.0.x 补充口径核对，范围限于 Feature 作者索引。 |
| 各阶段 `provides.hooks` 的 Markdown 与 `.mjs` | 映射到相应真实事件，保留 phase、来源、声明顺序、脚本输入输出和失败严重度。Markdown/脚本片段仍按 3.0.0 的真实 verifier 消费链核对，脚本检查结果仍归 harness。 |
| `phase_rules_overlays`、`skill_assets`、`capabilities` | 保留有效阶段及别名归一、规则叠加、同键资产优先级、能力 provider 与严重度。在实际 profile/规则/资产消费者处核对。钱包未声明的种类用最小 1.0 夹具补验。 |

**迁移步骤。**

1. 在宿主管理锁内只读盘点。记录清单及待迁文件的指纹、已物化 adapter 和写入边界。宿主自有文件全部纳入去向，未知附属文件原样保留。若仍有工作使用旧路径，立即报告定位并保留旧布局，交回后重试。旧版本缺少逐插件签发明细时，用可核验的原运行及有效锁判定占用。已有正式交回、签发原件和历史记录保留原字节。
2. 在同卷、旧根以外的暂存区构造完整新根。按可验证的旧→新路径映射更新插件内引用，保留手写业务内容。钱包验收必须覆盖 `post_check.mjs` 里的 `doc/extensions/skills/story/templates/…`、Hook 正文中的知识链接，以及 Story 脚本依赖旧目录深度定位宿主根的调用。包内相对引用按文件实际位置保留，必要时使用明确的项目根参数。对可执行代码中无法判定意图的引用保留现场并指出位置，避免盲目全仓替换。项目外的调用者或历史签发按需提供路径对应说明。
3. 用**新**解析器验证暂存结构、实际资源、插件 ID、路径及链接边界、各已接入 adapter 的入口计划。在原件指纹仍匹配时切换目录。切换互斥覆盖重命名过程，暂存和可回退原件始终在同一受控父目录。提交前失败或中途退出可恢复到完整旧根，报告原因、受影响路径和手工步骤。提交后入口刷新若失败，明确区分“目录已迁移、入口待刷新”，重试只补尚缺的生成入口，保留宿主手改桥。成功后活动根内只剩顶层选择清单及插件目录。迁移动作本身不执行插件启用命令、npm 或业务 Hook。

## 4. 迁移由谁触发，业务怎样继续

宿主集成新发布件后的扩展刷新和所有常规 `/extension` 管理操作共用同一迁移实现。维护者从普通管理入口执行 `inspect` 或 `verify` 也触发升级前置：探测旧布局，必要时迁移，在同次调用刷新已配置入口，再继续原操作或返回结果。原操作本来就会刷新时复用一次最终投影。回执说明本次是否写盘。显式只读请求、受管作者只读入口及 S1 仅探测。对未成功迁移的旧根只返回诊断，原操作不得继续向其中写入新格式。

普通业务请求只走新 loader。遇未迁移、非法旧清单或内部旧格式时，本次扩展输入为空，沿 `inspect` 与实际请求/作者回执给出“扩展需迁移”、路径、原因及解除方式。残留的旧桥接、根说明片段或目录均不构成投递证据。框架和 profile 自身的上下文、检查及普通 run 继续。不要将这个诊断升级成全局 BLOCKER，也不要报告未投递的扩展已使用。没有请求对象的轻量入口沿原返回面说明相关缺口。新格式中的坏插件仍按既有局部隔离和 required/optional 语义处理。[现行检视](../../harness/scripts/utils/extension-inspect.ts) · [扩展检查](../../harness/scripts/check-extensions.ts)

**framework-init 接线。** 扩展管理操作和 init 的 S3 调用同一迁移、刷新函数。S1 在已有 project planner 中对配置的扩展根只读探测，任务顺序如下。个人 setup 沿原路径。

| S1 条件任务 | 位置与执行 |
|---|---|
| `migrate-extension-layout`（迁移扩展目录） | 检测到 1.0 维度布局时列出，疑似 1.0 但损坏的目录也给出可诊断结果。排在 `harness-install` 之后。S2 复述旧根、目标插件及迁移意图，S3 执行第 3 节并记录结果。 |
| `refresh-extension-entries`（刷新扩展入口） | 宿主有扩展（包括即将迁入的包）时列出，排在迁移之后、`run-global-phases` 之前。S2 复述目标 adapters，S3 使用最终获批的 `materialized_adapters[]` 重建受管桥与 AGENTS/CLAUDE 派生段。新布局已有扩展时可只刷新，空宿主不为扩展添加这两项任务。 |

在 [init-task-planner](../../harness/scripts/utils/init-task-planner.ts) 和 [executor](../../harness/scripts/utils/init-task-executor.ts) 注册两项，覆盖 UPDATE 智能/常规执行与 S2 调整 adapter 后的计划。两项沿用 `harness-install` 和有效配置前置。原有 `materialize-adapter:*` 在准备框架入口时，不得抢先按旧根重写或删除扩展桥。旧布局下刷新依赖迁移成功；S2 明确跳过迁移时，刷新报告旧布局待迁，不能借刷新绕过选择。

**全局检查和其他无关任务保留原依赖。** 一次迁移失败只记该任务 failed，依赖它的入口刷新记 skipped 并说明原因。其他任务继续并如实写 S4 run-log。S4 可报告部分失败，不能把未刷新入口算作成功。区分“排列在前”与硬依赖，沿用[现有任务执行循环](../../harness/scripts/init-orchestrate.ts)的逐项失败处理。[framework-init S1–S4](../../skills/project/framework-init/SKILL.md)

- 更新 [AGENTS.md 的目录边界](../../AGENTS.md)、初始化骨架、发布件 README、[接入协议](../../docs/evolution/extension-protocol-v1.md)、[管理 Skill](../../skills/project/extension/SKILL.md)、[MIGRATION.md](../../MIGRATION.md) 和 3.1.0 发行说明草稿。迁移手册写明正常的一次 UPDATE、实际旧路径改写、失败后的修正与重试，以及内测清单的保留和从来源重装。把现有动态启停/UX/适配器 fixture 改成新原生布局。旧输入仅留在迁移与诊断用例中。

## 6. 验收与完成条件

在隔离副本中固定钱包的 `doc/extensions/manifest.yaml`、原始资源和配置。本次核对的 `wallet-sdk-demo 0.21.0` 有两个 Skill、9 条知识、9 次 Hook 声明（4 个不同文件）和 6 个阶段的规则覆盖，引用均可定位。用有 SHA 证明的 3.0.0 ZIP 重建旧宿主，记录各入口、知识实际接收方、Hook 顺序/片段/结果、有效规则和手写文件指纹。再集成同一份经校验的新发布件。每项均记录版本、实际调用、原件和结果。

| 场景 | 通过条件 |
|---|---|
| 一次 framework-init 完成升级 | 只发起一次正常的项目 `framework-init`，保留正常 S2 计划批准。S1 在正确位置列两项且不写盘，S2 复述，S3 先迁移后刷新再跑原全局阶段，S4 对应同一 run。无需另行调用 `/extension` 才生效。`wallet-sdk-demo`、两个手动 Skill 和各 adapter 路径正确，根级旧维度目录已退出。再跑 UPDATE 幂等。 |
| 钱包迁移语义 | 实际调用 Story 与钱包 SDK 入口，执行一个引用 Story 模板的离线 Hook 场景，核对 verifier 实收的约束片段与脚本结果，并从原规则消费者对比有效规则（含六个阶段覆盖）。逐项对照 3.0.0。单独用实际 Feature 作者输入对照 `a7c3e9d2` 的索引路径、顺序及读取指令；每个新路径可打开原知识，索引只送一次。 |
| 管理入口与 UX 共存 | 在另一份同源旧副本从 `/extension` 正常入口开始，获得同一迁移结果，再安装新格式的 `ux-behavior-spec`。宿主总清单能检视两个插件。正常蓝图作者复用或生成 UX，已迁的 Story、知识与规则继续工作。单独启停/升级/卸载 UX 只动其目录、效果与宿主选择，宿主自有包和已交付 UX/蓝图保留。 |
| 非法 1.0 与失败恢复 | 用缺失的 Hook 文件或损坏的清单试迁移，回执给出明确路径与修正步骤，原目录、清单及手写文件字节不变，未发布半成品。再验证一次切换中断后可恢复、重跑不重复。init 中仅迁移失败及其依赖刷新受影响，其他可运行任务有独立结果。 |
| 尚未迁移与内部旧格式 | 新发布件已集成但尚未刷新时发普通业务请求，作者收“扩展需迁移”，正常业务继续，实测旧知识、Hook 和规则均未执行。只读检视同样可诊断。对 1.1、2.0、2.1 分别得到从来源重装的提示，旧文件无自动写入或执行。 |
| 新协议回归 | 新宿主从空根安装来源包/裸 Skill，核对时点清单、动态启用与逆序退出、绑定改投、在途退出与重试、文件漂移、插入两个插件时的 ID/资源归属。验证实际包外源码已排除、随包示例可独立安装，普通加载器仅接受新布局。 |

实施收口运行 `npm run openspec:validate`、仓根 `npm test` 以及上述同包宿主验收。本次计划草案只校验计划结构、引用和文本差异。
