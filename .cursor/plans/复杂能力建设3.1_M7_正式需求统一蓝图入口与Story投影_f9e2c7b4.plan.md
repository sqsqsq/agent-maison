# 复杂能力建设 3.1 · M7：正式需求统一蓝图入口、条件式设计义务与 Story 投影接缝

状态：**v3 定稿获批 → 已实施 → 已返修（2026-08-29）**。设计正文（§1–§10）自 v3 获批后未再改写；
实施与返修的事实见文末 §11 实施记录与 §12 review 返修记录。

## 1. 问题与定位

3.1.0 已交付"蓝图→CU→闭环"机械链（P0–P3、M5A、M6、宿主入口 c4d7e9a2 全部完成），但入口
语义在真实宿主面前被证伪：

- 现行模型把蓝图定位为"复杂多 CU 才启用的可选路线"（三条 AND 入口门），小正式需求不经过
  任何部件内设计环节；
- 组织现实（用户裁决）：**部件内设计环节（组织称 Story Design）对每一项正式需求都是必经
  的，区别只在内容多少**；
- 宿主同事在无蓝图可用时用 extension 造出 `/story`：上游拉料→AR/design.md（仅需求投影）
  →先做 spec→再从 spec 反向装配"设计文档"。流程别扭的根因正是中间缺一个部件内设计权威；
- 实锤：story SKILL 产物定位表写 story.md"派生物，零新事实"，红线却要求"有判断——写清
  被否方案与取舍理由"，设计语义被迫挤进评审载体，已成平行真源风险。

M7 裁决：**蓝图从"复杂需求可选路线"重定位为"正式需求必经的部件内设计阶段"**。单一蓝图
协议，内容深度由真实影响面派生（条件式设计义务），不设档位、无升级动作。3.1.0 发布前
纠偏（M5A 同款未发布窗口硬切先例）；m5 release 收口以 M7 为顺序前置。

**范围冻结（v2，吸收 review 一）**：M7 只负责把 Maison 做完整，并为宿主适配提供稳定接口、

## 3. 已定裁决（实施期不得改写）

1. **正式需求定义（D3 定案）**："有明确交付或验收责任，且拟改变部件行为、外部契约、
   数据/NFR、运行语义或架构责任的事项，按正式需求处理；不改变这些语义的纯文档和机械
   维护除外。"三条判定纪律：上游显式标为正式需求时该分类具有权威性；入口信息不足时由人
   确认、不猜测；当前不新增 track scoring 或机器 BLOCKER。兜底双入口：/spec 与
   /change-lite 首次冻结施工意图时均须识别"应先经 /component-design"并给回退入口。
2. **只有一种蓝图**：统一最小必答骨架，内容深度由影响面派生；不设 compact/full 档位、
   升级信号或状态机。
3. **applicability 与 evolution_impact 正交（新增设计裁决）**：`applicability` 保持二值
   （部件类型固有适用性）；本次演进影响用独立 `evolution_impact: changed|verified_unchanged`
   字段，仅 applicable 视图携带；至少一个 applicable+changed 视图；消费者
   （questioning/closure/schema/fixture）同步接线，不只改 schema。
4. **条件式设计义务（修正措辞）**：发现多个 CU→完成 CU 边界与关系分析（真实依赖、共享
   资源、可并行性、独立性），只有事实要求时才生成 requires 与顺序约束；发现共享部件级
   决策→蓝图裁决一次、CU 经 design_refs 消费；发现"单独绿≠整体完成"→closure 追加组装
   与组合证据。安全中间态是单/多 CU 通用义务，不挂 ≥2 CU 条件。
5. **合法蓝图与完整设计交付分层**：component-blueprint@1 合法性不含 CU 数量（P1 不反向
   依赖 P2）；"蓝图 admitted + 1..N CU + design_refs + readiness"是 /component-design
   编排层的交付验收。
6. **/component-design 终点=设计交接**：需求源物化→正式性确认→蓝图 admitted→1..N CU
   分解→CU readiness/后续施工入口→返回设计交付结果；CU 落盘经 P2"设计准备子流程"
   （decomposition provider 提临时候选→consumer validator 校验后原子写 canonical CU，
   admitted blueprint + 0 CU 是其合法入口），/component-design 自身不直接写 CU；可建议
   下一步，但**不进入 P2 selector、Goal Mode 施工循环和 P3 closure**（施工=既有
   /change-unit-progression，闭环=既有 /component-closure）。
7. **三条独立宿主接缝**：requirement-source-materialization（宿主→Maison）、
   blueprint-review-publication（Maison→宿主）、blueprint-review-feedback（宿主→
   Maison，四类反馈分类，仅带 authority+source revision+决策语义者进
   decided_with_authority，经 reconciliation 生成新 revision）。publication 与
   feedback 方向相反、owner 不同，不合卡。
8. **lite CU 绑定（D2 定案）**：CU-bound lite 复用既有 `contracts.yaml.change_unit`
   作为机器映射 sidecar（含三组 mappings）；lite 轻在施工阶段与文档规模，不免机器契约；
   不在 change.md 造降维映射（拒绝 Markdown/contracts 两套真源）。
9. **Story 投影（D1 定案）**：投影严格派生自一个 admitted blueprint revision；宿主可在
   其后附加 CU/spec 等施工附件，但附件不成为 Story Design 的事实来源；归档时点由宿主
   决定。Maison 只保证投影可寻址、derived_from 精确指向 revision、内容契约稳定、可供
   宿主消费。
10. **M7 不改宿主工程**：模拟钱包 story extension 是事实样本；t5 为仓内 mock 契约验收；
    真实接入是后续采用工作。
11. **App-only 诚实声明**：当前仅 App component profile 有 design lens；其它 component
    type 缺 lens 时明确返回 unsupported/missing design lens，不强行套 App 4+1。
12. **AR 拆分 ≠ CU 拆分**；**@1 原位纠正**（meta-model 新 change delta，P1/P2/P3 未归档
    change 内修订，零兼容层）；**m5 以 M7 为顺序前置**，M7 不执行任何 release 门禁项。
13. **发布件自足**：宿主开发者仅凭 3.1.0 发布件（交接指南+随包 schema/契约样例+校验
    命令）即可实现三个接缝 adapter，不需读取 .cursor/、openspec/ 或模拟钱包源码。
