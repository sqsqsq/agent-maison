# 单元测试提速

## 1. 范围与已有证据

2026-10-12 修订：目标是缩短全量 UT，约 **15 分钟**为优化目标，以实测为准。留在 `main`，只改测试 runner、必要的测试隔离与长尾套件；不减用例、不放宽断言、不增加 release-only 来换速度，不加框架或依赖。文件统一 LF。其他会话未提交改动不碰、不一起提交；用户通知后才实施，提交另须同意。

`run-unit.ts` 目前在一个进程里顺序执行 `require → runAll()`。前轮核对为 301 个 core（6 个 releaseOnly）和 48 个自动发现的 profile 套件，实施以当时登记为准。普通 `npm test` 跑 typecheck → unit → fixtures；`release:all` 与 `candidate:build` 的 unit 都传 `--release`，两种统计口径分开。

复用已完成的 [b0e0621c](设计权威修复套件提速_前缀缓存与去掉真实等待及场景去重_b0e0621c.plan.md)（提交 `526ba483`）：同路径前缀缓存、缩短测试等待、重复流程去重均已实现，不再做一遍。其最终记录为 design-authority-repair **1029 秒**、reliability-scenarios **1689 秒**；原记录注明存在同机负载，作为长尾证据，不能冒充本轮基线。约 15 分钟的 release 目标不能只靠增加 worker，必须处理长尾。

发布排除 SSOT 已排除 `harness/tests/**`、profile 测试和 reports；发布件的 `npm test` 被 sanitize 为 `check:global`。本批服务开发及发布前测试，保持消费者发布边界，不把 UT 重新加入发布件。

## 2. 先计时，只测一次全量串行基线

先不改调度，在原循环用单调时钟记录每个套件的加载及执行时间，输出完成耗时、最慢 Top 20 和整轮墙钟。缺失、跳过、异常分别显示，未执行不能计成零秒通过。

新增 **`--results-out <path>`**，仅显式传入时保存 suite/case/ok/error、选择范围、计时与运行方式，供基线、调度数据和最终对照使用。平常测试与嵌套 runner 不自动创建结果目录；沿用内存汇总和原失败报告。

计时小范围验证后，执行一次 `npm run test:unit -- --release --results-out reports/ut-baseline.json`，此时仍是原串行实现。记录 Node/OS、机器配置、相关代码版本和机器负载；不要求清空或提交其他会话的工作区。

从该结果剔除 release-only 后求和，得到普通套件的**耗时估算**，不将其称作独立实测墙钟：套件顺序、热缓存和 runner 开销可能有差异。不再额外跑一小时普通串行；typecheck/fixtures 在最终 `npm test` 中分别计时。已有失败照实保留，不删用例或改为跳过。

## 3. 按套件起进程，最长的先发

- 仍由 `run-unit.ts` 统一登记/发现/选择套件；复用 `selectSuites`，不再建一份登记表。父进程派发、汇总，worker 只加载一个套件并执行 `runAll()`，完成即退出，不复用进程。套件内部顺序不变。
- 新增 `--workers N`，默认先用 `min(8, 可用逻辑核数)`，至少为 1；用重套件小集合试跑，有实际内存/磁盘竞争再降低，不扫描全部并发档位。`--workers 1` 仍是一套件一进程、顺序派发；`--serial` 才是原进程内按登记顺序执行，两者用于区分进程隔离问题与并发冲突。
- 从基线提取简单的 `suite id → 耗时` 表，放 `tests/utils/unit-suite-timings.json`，仅作排序提示。未知耗时的套件优先、相互按登记顺序；已知项按耗时降序，空出名额就发下一个，避免新重套件拖到末尾。文件缺失或坏了回落登记顺序，不阻断测试、不漏套件。最终更新一次实测值，不在每次测试时改受控文件。
- worker 用结构化结果返回给父进程；stdout/stderr 按各自流缓冲到**整行**后转发，每行加 `[suite-id]` 前缀，流结束时补发未换行的尾部，内容不丢失、不把多个 worker 的半行拼接。保留 `TRUST_PROBE_ROOT=` 等黑盒解析内容。父进程按原登记顺序输出 `Suite [id]` 和 `结果：X passed, Y failed (共 N)`，不解析日志来决定 PASS。
- worker 启动失败、加载/runAll 抛错、无结果或非零退出均按 suite 失败汇总；收到结果后仍须等待退出，不能忽略清理失败。正常断言失败继续汇总，不自动重跑冲掉失败。
- `--filter` 的 suite id 子串匹配、未命中时 case-name 事后过滤，以及 `--release` 语义不变；release-only 默认不执行，但显式 core 文件缺失仍失败。串行/并行共用选择和结果汇总逻辑。

进程占用时间按 **启动 → 加载 → runAll → 清理并退出**记录，另输出“启动到 runAll 开始”，不漏掉 ts-node 成本。Claude 提供的裸启动 0.17 秒、加载 goal-phase-runtime 2.2 秒是试跑参考，本轮在实际 worker 上取数。并行下限估算为 `max(各任务完整占用时间之和 / worker 数, 最长任务完整占用时间)`；磁盘竞争和冷缓存增加的开销以墙钟校正。

## 4. 隔离只查进程边界之外的共享写入

每轮用 mkdtemp 建短临时根（如 `mu-XXXXXX`），每个 worker 一个短子目录；启动时设置其 TMP/TEMP/TMPDIR。已有 mkdtemp trust 根、PID 宿主目录与缓存继续复用。新进程已隔离 env、cwd、模块缓存、信号处理，不逐个重审全部套件，也不清空 require.cache。

用 `rg` 定向排查并结合小集合并行试跑处理三类实际风险：

| 风险 | 处理 |
|---|---|
| 写仓库树，尤其默认 harness/reports | 核实命中究竟是读还是写。实际共享写入使用既有 `HARNESS_REPORTS_ROOT_OVERRIDE` 或临时宿主；不无差别改所有测试。 |
| 回退真实用户目录 | 沿实际子进程 env 传递确认 trust 隔离。优先已有环境变量/测试注入点；不全局改 HOME/USERPROFILE，避免改变工具查找和用户配置语义。 |
| 机器级资源 | 复用 device-concurrency 的 PID 专属凭据名、假 provider 等。只有证明确实不能并行，才在现有登记处增加明确串行例外及理由；当前不预建 serialReason 或独占区段。 |

goalMain 的信号处理残留导致的 device-session 顺序要求会被独立进程消除；串行诊断仍保持旧顺序。前缀缓存保留在套件进程内，不做跨进程共享缓存。

本批不改 `HARNESS_LAYOUT_SMOKE` 的手工扩展模式，也不包装 `RELIABILITY_RESULTS_OUT`；标准测试/发布入口不会设置前者，后者仍由一个套件按既有语义输出。没有实际冲突不扩大范围。

**清理：** 保持 bootstrap 的导入次序和无条件覆盖外部 trust env。原 `cleanupStrict` 清理处加 Node 自带的有限重试（如 `maxRetries: 3, retryDelay: 100`），重试后 trust 仍存在则打印路径、退出 1；exit best-effort 后备保留。普通临时总根尽力回收并警告，不能把其中残留的 trust 也降为警告。父进程等 worker/其子进程收尾，异常或可捕获中断沿用已有 `killProcessTree` 等原语，仅处理本轮拥有的进程；用一个真实子孙进程回归证明收尾，不建进程监管服务。不可捕获强杀不承诺 finally 必达。

**报告与跨会话：** 父进程结束时照旧调用一次 `writeUnitFailureReport`；默认路径、schema、全绿删除旧报告的行为不改，不做兼容视图、自动独立报告或报告锁。跨会话不互扰来自用户原任务，保留一次小规模验证：两边临时资源独立，并用已有 `MAISON_UNIT_FAILURE_REPORT` 各自指定路径，需要完整结果时各传 `--results-out`。不承诺两个调用者共用一个固定报告路径还能同时保留两份文件；默认路径仍有现有的覆盖限制。现有嵌套 blackbox runner 在外层结束前完成，保持该时序，不额外建报告路由。

## 5. 长尾明确处理，保留已有提速收益

t4 以 design-authority-repair 和 reliability-scenarios 为确定对象；先从新基线确认耗时，再补场景分组计时，按独立场景拆成少量可调度套件。其余套件仅当新数据证明决定下限时处理。

拆分时把共用昂贵前缀的场景尽量留在同组，复用 b0e0621c 的 `cachedPrefix` 和现有 helper，比较尾部缩短与多进程重建前缀的代价；不做通用 case 调度、不重新复制流程、不并发操作同一可写宿主。保留 case 名、断言、releaseOnly 和原 id filter 覆盖，写清旧/新套件映射。若新基线已小于目标且不再决定下限，可据数据取消拆分；不能在已知超目标时只加 worker 就收口。

## 6. 验收：复用基线，不再跑第二次全量串行

| 验收 | 最小执行方式 |
|---|---|
| runner 契约 | 用现有 runAll/assert 和轻量模块验证选择/缺失套件、并发上限与长任务先发、恰好执行一次、worker 异常和清理失败。复用 filter、failure-report、trust 黑盒测试，不加框架。 |
| 诊断入口 | 小集合各跑 `--serial`、`--workers 1` 和多 worker，包含 env/cwd、信号和嵌套 runner，验证三条入口。 |
| 串并结果一致 | 最终 release 并行结果与 t1 串行基线按 `(suite id, case name, 同名次数)` 逐套件比较，拆分按映射保留原 case 身份。只对出现差异的套件在最终代码上用 `--filter <id> --serial` 补跑，不预判生产改动影响哪些套件。与并行一致则列明相对基线的变化及已确认原因；不一致则排查并修复执行模式差异，不直接断言必为并发冲突。复用无差异的基线与这些定向串行结果后，总数、通过/失败多重集差异须为 **0**；新增用例须列明，不能借对照更新删减原覆盖。 |
| 墙钟 | 一次 release 串行基线对一次 release 并行收口，保存显式 results-out；同机无另一场全量竞争时记录秒数、加速比、worker 数和 Top 20。目标约 900 秒，未达到如实写瓶颈和可达下限。普通基线只给估算，不冒充实测。 |
| 严格清理 | 正常、断言失败、worker 故障和可捕获中断后，本次 trust 根残留 **0**、本次测试进程残留 **0**；验证有限重试后仍删不掉会失败，不全机扫删。 |
| 双会话 | 同工作区两个定向测试同时跑，覆盖 trust、宿主临时根、设备凭据和一红一绿报告，使用各自报告路径；结果、清理相互不干扰。不为此再跑两个全量，也不把竞争资源的结果当性能测量。 |
| 仓库门禁 | 收口时 `cd harness && npm test` **全部 PASS**，记录普通 UT、typecheck、fixtures 耗时；另一次 `test:unit -- --release` 完成上述 release 并行验收并全部 PASS。release-all/candidate 只核对现有调用接线，不顺带打包或发布。 |

全量固定安排为：**改造前一次 release 串行；改造后一次 npm test、一次 release 并行**。只有实际失败或相关代码后续改变才补验证，不因 review 轮数加跑全量。结果文件只在这些测量/对照调用中显式生成。

## 7. 新增机制的场景与收益

| 机制 | 改善场景 | 实际收益 |
|---|---|---|
| 套件计时、可选结果文件、耗时排序表 | 不知道一小时花在哪、无数据调度 | 用一次基线定位与排长任务，平常调试不积累目录；计时数据不充当门禁。 |
| 有界子进程 + 私有 TMP | 多核闲置，套件改 env/cwd，固定临时名易冲突 | 同时执行且互不污染，不重写套件；异常仍失败，避免漏跑假绿。 |
| trust 清理有限重试 | 多 worker 增加 Windows 短暂文件占用机会 | 自动吸收短暂占用，保留最终严格清理契约。 |
| 对已知长尾按场景拆分 | 1029/1689 秒任务使 15 分钟目标受限 | 缩短最长任务，同时以实测保证不丢已有缓存收益。 |

删去上一版的自动运行报告目录、共享报告发布机制、预设串行区段、全面套件审计、手工 smoke 扩面、全局 HOME 改写及两次额外全量串行。跨会话只用已有隔离与路径覆盖完成用户明确要求；不新增状态、锁服务或生产门禁。

本轮仅修改此 plan，执行 plan 校验与 LF/差异检查；不改实现、不跑全量、不提交。
