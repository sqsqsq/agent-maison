# 视觉证据闭环与失败恢复收敛（宿主开卡回灌）

## 1. 冻结范围与根因

基线为 AgentMaison `3.1.0` / 宿主发布件 `e2a63bb8`。证据来自只读宿主目录
`doc/features/bc-openCard-2/open-card-flow-v2`、CLI identity
`cu-YmMtb3BlbkNhcmQtMgBvcGVuLWNhcmQtZmxvdy12Mg` 及 run
`20260920T074445Z-a70eb7`、`20260920T100035Z-f829b8`。旧 plan `6f2a9c41`、`c8b4e731`
只作已实现机制参考，其宿主 closure 仍未完成。

已确认的共同根因：

1. `visual-diff-check.ts` 在仅 advisory WARN 时把聚合 check id 改成
   `visual_diff_layout_invariants`；下游却只找 `visual_diff` 且只接受 PASS，导致同一视觉事实失去证据资格。
2. TC→AC 绑定精确匹配 checkpoint 的 base screen；真实 overlay capture 使用
   `card_type_sheet__overlay__cts_root`、`sms_verification_sheet__overlay__sms_root`。AC-8 checkpoint 只含两屏，
   而 test-plan、ui-spec 与实际 visual target 要求四个 P0 状态。
3. P0 gate 对所有非 gap P0 TC 强制走 native CaseResult，visual TC-007 因此必然被判未执行。
4. `test-report-writer.ts` 再次独立映射视觉用例，且 overall 只看 native functional 失败；于是 TC-007 blocked、
   P0 85.7% 仍可生成无缺陷、`COMPLETE_WITH_GAPS`、“功能可推进”，与 summary FAIL 冲突。
5. runner 可产生 `visual_round.disposition=journaled`，summary schema 未接受该真实值。
6. 未知 blocker 默认 `code_regression`；summary 的框架责任没有完整投影到 reconcile actionability。
   现有 no-progress 只监控 deterministic affected files 或 timeout 主产物，普通 code_regression 常为空；
   单独把它加入熔断集合会误停真实修复。累计重复计数仅对既有 toolchain 家族有意义。
7. 第一轮已暴露框架缺陷后，外层仍以“行为变化”重新 prepare，并由 goal-runner 直接创建无 successor lineage 的
   coding→testing fresh run。只拦 prepare-scope 或只看整个工作树是否变化都不能解决：环境恢复可能不改文件，
   notes/无关文件变化也不构成相关进展。

不使用失真的 token/纯推理时间归因；只记录可由事件时间戳、执行结果和 cache 字段证明的效率变化。

## 2. 批次 A：证据链正确性

1. 在 `finalizeVisualDiffHits` 的现有结构化 `visual_diff` payload 上形成唯一聚合裁决：聚合 identity 稳定；
   blocking hit、advisory hit 与可供通道消费的结论明确区分。advisory 不冒充 blocker，真实 WARN/FAIL、
   stale、schema/tamper 或缺图也不得因兼容 id 被洗成 PASS。
2. TC visual binding 复用 `visual-diff-targets.ts` 已有 P0/overlay canonical 映射，与 capture/nav 使用同一 target 集。
   每条 visual TC 只绑定其关联 AC 的 checkpoint 屏，overlay base 名通过 `parentScreenId→canonical id` 映射到真实 capture；
   结构化目标不完整或映射歧义时 fail closed，不靠 strip 后缀或模糊匹配。全 P0 target 完整性继续由
   `visual-diff-check.ts` 既有 `p0Uncovered` visual gate 承担，通道层不迁移、不复制这条 phase 责任。
3. execution-channel binding 产出的逐 TC 裁决进入 P0 五数与 AC 覆盖：Hylyre TC 仍消费 native trace，visual TC 消费
   本次 check 可用的当前视觉结论；绑定键保持截图 hash、当前 build fingerprint 与 `evaluation_invalidated`，合法同 build
   跨 attempt 复用，不新增 run/attempt 强绑。visual TC `covered` 同时计入 `passedCaseIds` 与 `acceptedAcIds`，使
   `p0_coverage_integrity`、`p0_semantic_coverage_integrity` 同源；`gapCaseIds/gapAcIds` 语义不变，不伪造 native trace，
   不删除 P0 分母。visual gate 不可用时不消费逐屏证据，phase 按既有 gate 失败。
4. 报告 writer 直接消费上述既有逐 TC 裁决，生成状态、缺陷、通过率、overall 与建议；不再独立重算 checkpoint 屏。
   任一 P0 visual blocked/failed 必须使报告、summary 与 assess 同向失败；仅 advisory WARN 可披露但不阻断已证明的 TC。
   逐 TC binding 在主链单次计算，由通道义务、P0 两门和报告共享，避免再次形成平行判定。
5. `summary.schema.json` 仅补真实生产值 `journaled`，并保留其他 disposition 的既有约束。

验收夹具必须走一次真实组合：6 条 Hylyre PASS + visual P0 TC + 两个 overlay + advisory WARN，贯通
visual gate→channel→P0/AC→report→assess。反例至少覆盖：TC 所绑 checkpoint 缺图/过期/真实 fail 时 TC 与 phase 均失败；
TC 所绑屏可用但其他 P0 target 缺失时 visual gate 仍使 phase 失败。无需在 global gate 失败时伪称 TC 仍 covered。

## 3. 批次 B：责任、重试与 fresh run 收敛

1. 复用 summary/check 已有 `framework_bug`、`framework_internal`、owner、failure kind 与 adjudication registry；只有 safeRun 等
   生产者已写出的结构化框架证据才归 framework owner。普通 gate FAIL 或来源不足不从散文/缺证猜框架 bug。本事故的
   `p0_*`、channel obligation 与 testing status 由批次 A 从生产端消除，不要求归因层事后识别。
2. 为避免把框架故障错喂给 agent、错归 toolchain 或复活人签，仅在现有 actionability 联合类型增加必要的
   `framework_blocked` / 观测投影 `framework`，由已登记为 `framework_fault` 的 `framework_bug/framework_internal` 单点映射；
   classifier、summary、reconcile、prompt/event/assess 共用该投影。runner 继续走既有 `failureKind=framework_bug` 首触 halt 和
   `halt_reason=framework_bug`，不新建队列、台账或恢复状态；未注册内容 blocker 保持现有兼容行为。
3. 扩展 `goal-phase-runtime.ts` 既有 `watchedFiles`/snapshot 组装：优先合并 blocker `affected_files`、
   `repair_candidates[].files`、责任阶段产物及 manifest/source/evidence 已绑定的相关路径，并复用现有内容 hash、事件变更记录和
   恢复裁决。只有“相关集合已知且非空 + 同签名 + 相关内容未变”才把 `code_regression` 送入既有 no-progress halt；
   相关源码/测试/证据真实变化则保留重试，notes、时间戳、无关提交或仅 HEAD 变化不算进展。相关集合未知时不得用空快照
   证明无改动，退回现有 `max_retries_per_phase` 有界重试/耗尽语义。瞬时 API 与可信环境恢复仍走原恢复语义；不扩大
   `CUMULATIVE_HALT_FAMILY`，重复 count=1 不单独构成缺陷，也不另造熔断系统。
4. fresh run 与 successor/resume 共用一个现有出生/continuation 判据，并接在实际创建前，覆盖 goal-runner fresh/detach 与
   goal-mode `--prepare-run`，不只拦 prepare-scope。判据读取前一终态 run 的 manifest/run base、已绑定 source/evidence、
   相关修复内容变化和可信恢复事实；prepare 期自声明的 `request_impact`/reason、无关 HEAD 变化都不是放行事实。
   无新 requirement/相关修复/可信恢复时指向 successor/resume；两入口沿用同名 `--force` 语义作为明确放弃旧结论并重跑的
   授权入口并记录来源，不新增旗标，且不得由主 agent 自写 request/impact 冒充用户授权。
5. 保留瞬时 API/连接故障的既有有界重试、真实代码修复后的复验和用户明确授权的恢复/重跑。

目标测试覆盖：结构化框架缺陷首轮为 `framework_blocked/framework` 并走既有 `framework_bug` halt，普通/unknown 缺证不误归；
相关修复可继续、已知相关面无变化停止、相关集合未知走有界重试、无文件变化但可信环境恢复可继续；notes/无关提交不能重置
进展；goal-runner 直接 fresh/detach 与 goal-mode prepare 入口都遵守同一 continuation/`--force` 判据。

## 4. Framework 验证

按实际落点运行受影响单测（至少 visual fidelity/channel/P0/report/schema 与 goal failure/reconcile/runtime/birth），再运行
typecheck 和 `cd harness && npm test`。随后运行 `node scripts/check-plan-version.mjs`、`git diff --check` 并检查 LF。
不运行 `release:pack` / `release:all`。纯 review 文本返修复用仍有效测试结果，不重复全测。

## 5. 宿主待验

Framework 内部全绿后才生成可供外部流程使用的发布件候选；本任务本身不打包、不写宿主。真实验收需确认：

- phase 的四个 P0 target（含两个 overlay canonical id）均以当前 build/hash 绑定，TC-007 的 AC-8 checkpoint 经 canonical
  映射通过，并与六条 Hylyre P0 同时成立；
- test-report、summary、assess 对 P0、缺陷、gap 和是否可推进完全一致；
- 同一失败若无相关新事实不再重复 testing 或创建 fresh run；有真实修复/可信恢复则能继续；
- 记录阶段调用数、testing 执行时间与被避免的无事实重试；不预写“40 分钟闭环”等未经验证承诺。
