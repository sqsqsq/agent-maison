# P3：spec、plan 与蓝图的责任承接

> 上位：[总纲](动态工作流_总纲_全阶段Skill独立组合与义务驱动编排_91c4e7a2.plan.md)；输入协议：[P1](动态工作流_P1_输入契约与事实承接_a6d3b8f1.plan.md)；编排：[P2](动态工作流_P2_执行范围与运行时统一编排_b7e4c9a2.plan.md)。
> 设计来源与字段映射由本 plan 负责，P4/P5 只消费，不再各写一份 projection。
> 父蓝图准入、独立质询与外部权威保持；本 plan 不开放正式需求绕过蓝图。

## 1. 背景

正式需求当前已先建蓝图/CU，但 spec/plan 仍要求传统文档全套；
已有设计经常被重新写成 spec/plan/contracts，导致来源漂移和额外返修。
另一方面，蓝图的 decisions/design_refs/verification_refs 不保证已经包含精确施工与验收字段。
直接跳过设计阶段可能遗漏真实需求、写集授权或 CU 闭环映射。

目标是在“已有内容直接使用”和“真实缺口必须补足”之间建立可验证边界。

## 2. 三层职责

| 层 | 独有职责 | 下游消费方式 |
|---|---|---|
| 蓝图 | 部件目标态、共同决策、外部契约、跨视图与本次演进边界 | CU design_refs 与已有 resolver |
| spec | 本次尚未明确的行为、边界、验收步骤与预期 | AcceptanceSpec 及必要叙述 |
| plan | 当前切片尚未明确的接口、数据、文件、控制与测试可行性 | ContractsSpec / UseCasesSpec 及必要叙述 |

spec/plan 可以只完成请求指定的设计任务；不自动追加 coding。
完整设计交接仍按 component-design 定义准入与 CU readiness，不以某次 spec PASS 替代。
发现足以改变部件设计的事实先回蓝图；外部 operation/DTO/error/NFR 不由下游自行裁决。

## 3. 输入准备与阶段执行的分界

确定性投影允许：选取 CU 引用的稳定目标；复制获准字段；规范化类型与 ID 映射；
将已明确的源码目标转换为现有 contracts.files 结构；运行同一语义检查。

必须运行责任 Skill 的情形：决定事务边界、补验收预期、指定未决定接口/错误语义、
确定新文件与模块拆分、解决产品含义冲突、批准外部依赖或架构责任变化。

输入准备不签发 spec/plan 的执行 summary、receipt 或人工批准记录。
产物的设计依据仍指向原蓝图/用户裁决，不能标“由 coding 批准”。
无需叙述文档时不生成空 spec.md/plan.md；必须存在的机器契约写入真实有效内容。

## 4. 验收承接结构

复用现有 AcceptanceSpec；artifact schema 只是兼容形状，semantic truth 仍归 check-acceptance。
derive.blueprint-acceptance 只能从当前 CU design_refs、target_predicates 与已获准蓝图内容
确定性构造；蓝图 current_scope/currentSlice 等具体读取沿当前 resolver，不复制一套寻址器。

| 现有字段 | 等价来源要求 |
|---|---|
| criteria[].id | 原有稳定验收标识，或既有 CU 映射明确的 ID；不得每次生成随机 ID |
| description / expected_result | 获准行为与精确结果；一句模糊目标不足 |
| verification_steps / testable | 真实可执行验证步骤与方法；refs 存在不能替代 |
| priority / ut_layer | 显式可验证的验收分级；未声明层级为缺口 |
| ut_focus / device_focus | 对应层级实际验证关注点 |
| boundaries[].scenario / handling / expected_behavior | 已明确边界条件与处理语义 |
| linked_flow / linked_branch | 需要时解析到实际 UseCasesSpec，不靠字符串非空通过 |
| performance[] | 真实指标、阈值与单位；设备证明归属由 P5 同源处理 |

合法空 boundaries/performance 按实际义务处理，不要求凑条目。
专项审查/测试的输入不必构造整份正式 AcceptanceSpec；该边界交给 P4/P5 的已有专项输入，
但不能将专项用例反向标成完整 CU 验收。

原文/蓝图有验收但尚未分层：交 spec 补层级判断，不把未声明默认 unit。
用户可观察变化的影响判断必须结合完整切片和证据，不能仅查节点类型。
源 revision/hash 不匹配则返回 stale/缺口，不使用旧投影顶替。

## 5. 施工契约与 CU 机器映射

复用 ContractsSpec、UseCasesSpec、contracts.change_unit sidecar、contract-reference-closure、
blueprint-contracts/runtime/data-flow 与 change-unit-feature-projection 既有 checker。

必须保留：

1. contracts.files 是受此机制管理的施工写集唯一授权集合。
   Blueprint/CU 的 touches 只说明影响面，不自动授权目录内任意文件。
   用户/获准设计已明确精确文件集合时可确定性物化；未明确时由 plan 补齐。
2. change_unit_ref 与 predicate_mappings/provide_mappings/design_ref_mappings
   使用既有 ID-only 映射，完整覆盖 canonical CU；不能另放在 change.md 或 execution_scope。
3. state_management 仍是当前 Feature runtime 施工权威；涉及 flow 时覆盖初始化、
   owner、mutation、publication/subscription、consumer、恢复等真实义务。
4. contracts 引用的所有 file-like 字段必须进入 normalized contracts.files；
   资源、导航、共享组件导出等不能被投影遗漏。
5. use-cases 只有在真实行为/UT 追溯需要时产出，但需要时必须具备可解析步骤/分支/符号。
6. 外部 DTO 到领域/持久化模型的 mapping 显式，不能依靠同形字段猜测。
7. 组件选型与 conventions 引用消费当前蓝图/知识的权威，不让 plan 再次作相反裁决。

物化位置使用 existing artifact path/resolver，兼容 phase-scoped 与 CU workspace，
不直接拼接 doc/features 或将所有物件放在 feature 根。
唯一 writer 先校验全部内容再写入；既有人工维护契约不得被派生投影静默覆盖。
有冲突走设计修订；投影缺失可以重建，真实人工决策不能通过重建替换。

## 6. Skill 与 checker 的具体改变

spec：入口读取已满足的行为与本次待澄清项，验证仅本次需要的输出；
既有术语/UI/fidelity/验收门按适用输入运行。没有视觉义务不生成 ui-spec/ref-elements 等占位件。

plan：将 contract 中全包 capability_plan_context 拆为真实必需输入与条件设计职责，
不因叙述 spec.md 缺失阻断已具备 typed 验收的任务。
当前所需设计全部有合法来源时，无 plan 调用也能提供施工输入；
所需设计只缺一块时完成该块，不重新组织整份部件蓝图。

check-spec/check-plan、prompts/verify-spec.md、verify-plan.md 与有关 phase rules
消费 P1 ResolvedPhaseInputs 和 P2 scope。文档格式检查仅作用于本次应产出的文档；
内容真实性、来源、授权、分层和映射检查不因文档可省而减弱。

## 7. 回退与范围变动

spec 新发现产品语义未被蓝图覆盖 → 返回 component-design 对应责任；
plan 新发现外部接口不明 → 指向该 owner 与解除条件；
coding 发现需改变接口 → P2 回退到 plan，部件共同决策变化则进一步回蓝图。

修订只针对相关 inputs/obligations；运行 scope 变化沿 P2 签发新代。
已完成 CU 不改回 pending；修正已完成行为按既有新 CU/supersedes 规则。
阅读、重入和重跑 checker 不自动修改 blueprint revision。

## 8. 验收

| 场景 | 结果 |
|---|---|
| 蓝图/CU 已有精确验收与施工内容 | typed 输入等价，spec/plan 无需执行，不生成两阶段空报告 |
| 只有 decisions/verification_refs 字符串 | 不通过内容完整性，明确缺字段 |
| 分层缺失或未知 AC/BD | 不能得到零设备结论 |
| 验收完整但新接口未设计 | 只 plan 补接口；已验收内容直接使用 |
| 完整设计但缺 CU sidecar | 输入准备生成真实映射并校验，不能跳过映射 |
| contracts.files 缺真实写入目标 | coding 前阻止；不从 touches 扩张授权 |
| 引用 runtime flow | 真实生命周期与数据边被投影和检查 |
| 蓝图 revision 变化 | 受影响旧投影失效，不拿旧 PASS 掩盖 |
| 用户只讨论/设计 | 不启动 coding/Goal 施工 |
| pixel_1to1 缺参考图 | 沿既有真实缺口，不伪造视觉产物 |
| 外部契约冲突 | 回权责 owner，不选较容易实现的一份 |
| 项目既有文本缺少机器结构 | 仅可确定内容被转换，语义缺口仍交责任 Skill |

check-spec.ts/check-plan.ts、check-acceptance.ts、blueprint-contracts.ts、
blueprint-addressing.ts、change-unit-feature-projection.ts、contract-reference-closure.ts、
contracts/acceptance/use-cases 相关 schema 与 verifier prompts。

也不把 fixture 结果宣称为宿主设计正确。

父目标推进 G4/G5/G6；没有新权威文件族，来源仍是蓝图/CU/正式产物，
消费者为所有施工与验证 Skill。新增投影若只复制正文而无真实消费，应删除。
