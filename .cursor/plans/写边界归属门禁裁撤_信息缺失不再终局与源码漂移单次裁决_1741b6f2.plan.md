### D2 第二处不合理阻断：写归因跑在 checker 之前（v2 新增，v1 的最大错误）

v1 写了"wrong_phase 逐字不动"。这是错的，已在代码中证实：

- `goal-phase-runtime.ts:7396` 的注释自陈：写归因块 "runs before critic receipts, journal replay and gate execution"。
- coding 以 `match: 'prefix'` 拥有产品源码域（`phase-write-boundary.ts:236`，`excludedPrefixes: utRoots`）。

于是 testing / UT 期修改产品源码，会先被判成 `owner=coding` 的 wrong_phase 唯一归属，直接触发 `phase_write_violation` 自动回退——**check-testing 的分级 WARN 根本走不到**。保留全部 wrong_phase 等于 T3 白做。

**v2 的分流**（复用既有路径角色，不新增任何表）：

| 变化类型 | 处置 |
|---|---|
| `no_owner` / `multiple_owners` | 记录诊断，不据此 HALT |
| owner 唯一，匹配角色只有 `source` / `phase_workspace`（产品源码、阶段工作区） | 不在写归因处抢先回退，交既有 checker |
| owner 唯一，匹配角色含 `artifact`（inventory 显式登记的需求 / 验收 / 契约等权责性产物） | 保留既有责任阶段回退，一字不改 |
| 明确的范围越界、功能失败、硬预算 | 不变 |

分流判据来自 `PhaseWriteDomain.kind` 与 `PhasePathOwnership.roles`，两者早就存在。

### D5 "框架共享"不能当通用排除原则

"这个文件由框架写"最多说明：这个变化不适合拿来判当前阶段 AI 越权。它不说明文件内容正确、谁都能改、质量检查可跳过。所以本 plan 不把 visual-debt 登记成 spec 所有（spec / coding / testing 都会重写它，多 owner 同样判违规），不给 feature 目录加"共享"标签，不扩 `isRunnerOwnedOrSharedPath` 名单。内容侧检查一条不动：账本损坏仍由 `loadVisualDebtEx` 的 invalid 态 fail-closed，coding 越界仍由 `check-coding.ts:428` 判 in_scope_modules，证据新鲜度仍由 evidence manifest 判。

### D8 v2 被否定的一处：报告读磁盘 script-report.json 有时序环（v3 修正）

v2 的 T3③ 让 `test-report-writer` 从磁盘读 `script-report.json` 的 `review_closure_attestation`。时序不成立，已复核：

1. `check-testing.ts:5784` 在真机跑完就调 `regenerateTestReport` 生成 `test-report.md`；
2. `check-testing.ts:5898` 才跑 `checkReviewClosureAttestationGate`；
3. 整个 checker 返回后 harness 才写本轮 `script-report.json`。

所以 writer 首次运行读不到，后续运行读到的是**上一轮**结果。这会重造"报告落后一轮"，而且一条旧 WARN 进 gaps 会把本轮总体结论错投影成 `COMPLETE_WITH_GAPS`。

**v3 改法**：不碰测试报告，改用既有 `buildReadinessSignals`（`harness-runner.ts:2405`，调用点 `:1762` 传入本轮完整 `ScriptReport`），在既有 `report.phase === 'testing'` 分支（`:2475`）内追加一条 `status='unknown'` 的 signal，message 直接用该 check 的 details（已含 `required_reviews`）。`readiness_signals` 的 status 联合类型本就有 `'unknown'`（`types.ts:651`），不新增 schema、不改结论派生、不读上一轮文件、无时序环。

### D9 v3 实施被否定的一处：漂移的第三次裁决（v4 修正）

v3 实施记录第 1 条把 `collectCleanPassIssues` 的 `attestation_reconciled` 说成"如实披露"。这是错的，reviewer 已核实：该 issue 的 `kind` 是 `needs_fix`，goal 在 `goal-phase-runtime.ts` 取作 `blockingFix`，于是

- `resolveGoalRunStatus` 把本可 `CHAIN_SLICE_COMPLETED` 的 run 压成 `PARTIAL`；
- 退出码 2；
- `issues.length === 0` 的凭证门不满足，**不生成 feature completion**。

各阶段全过、漂移已被 checker 分级为 WARN 的情况下，这三样合起来是阻断，不是披露——与"漂移只裁决一次"直接冲突，也不满足完成判据第 2 项。

**v4 改法**：`verify-feature-completion.ts` 的 ⑥ 只保留"基线缺失"（`attestation_present`，那是**没有证据**），删除"基线在场但对账不符"（`attestation_reconciled`，那是**有证据且已分级**）。披露面不变：责任 checker 的分级 WARN 进 script-report，`post_review_source_drift_unreviewed` readiness signal 进本轮 summary，两者各有独立单测。真实失败拦截不变（E2E-2a-neg 守）。

同时修正两处把 PARTIAL 固化为预期的断言：`assertRunFinishedWithDriftDisclosed` 改为复用 `assertRunReachedEnd`，`goal-post-harness-drift` 改断言 exit 0 + `CHAIN_SLICE_COMPLETED`。
