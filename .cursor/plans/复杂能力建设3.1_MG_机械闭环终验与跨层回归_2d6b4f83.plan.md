# 复杂能力建设 3.1：MG 机械闭环终验与跨层回归

## 1. 计划定位

MG 是 3.1.0 批次的**终验**，不是第五个实现层。P0–P3 已经各自完成并提交，它们的单层完整性由各自
的 plan、OpenSpec 与套件承担；MG 只做三件事：

1. 把 m5 的每一条验收项和**已经存在的证据**对上账，说清哪些已成立、哪些只在单层成立；
2. 只补真正跨层、当前无人证明的那部分，形成一条可回归的机械链；
3. 执行批次门禁，并如实冻结"哪些发布门因为 m0 未完成而不能宣称"。

MG 不新增 registry、ledger、daemon、并发调度器或第二真源，不新建 checker/CLI/schema/skill，
不新建 fixture 项目，默认也不新建 OpenSpec change（判据见 §7）。

## 3. 已实证的三个具体缺口（不是推断）

### 3.1 Goal Mode 完成事实在 P2/P3 测试里被两处桩短路

- P2 的 `completionAdapter(state)` 同时替换 `projectionExists`、`resolveExpected`、`verify` 三个入口，
  所有 `VALID` 都来自 `Map` 里的字符串；
- P3 的 `evaluationOptions()` 直接替换 `observeCompletion`，**38 个 P3 用例无一例外**；
- 生产 CLI（`check-component-closure.ts` 的 `main()`）走的是 `options = {}`，即真实
  `observeChangeUnitCompletion` → `verifyFeatureCompletion`。

精确表述（2026-08-20 review 修正）：不传桩的调用并非完全没有——
`change-unit-progression.unit.test.ts:632` 与 `:644` 两例就是真调用，但它们都在"缺 completion 投影"
的**早退分支**（成功终局缺投影 / corrupt run）就返回了 INVALID。真正零测试的是
**"投影在场 → 真实 `resolveExpected` → 真实 `verifyFeatureCompletion` → VALID"这段主路径**。
缺口结论不变；**MG-A 实施时不得把这两个已有早退用例当成重复覆盖删掉**。

已定位根因（不是"忘了写"）：fixture 项目 `tests/fixtures/component-blueprint/valid` 没有 framework 树，
实测 `resolveChangeUnitExpectedExecution` 抛
`No framework tree (skills/ or workflows/) under projectRoot=...`，真实 completion 路径在该项目上跑不起来。

已实测可解：把仓库 `workflows/`（12K，仅 `spec-driven.workflow.yaml` + schema）投影进临时项目根的
`framework/workflows`，`resolveChangeUnitExpectedExecution` 立即返回
`{"expectedTrack":"full","expectedChain":["spec","plan","coding","review","ut","testing"]}`。

### 3.3 宿主演进接缝的四项证明是占位

`tests/fixtures/component-blueprint/valid/test/ledger/closure.test.ts` 里

但 m5 要的是"fixture 证明契约兼容+替换+缺失失败裁决行为+绕过检查"，当前 fixture 一条都没真的证。
