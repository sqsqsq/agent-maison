## 二、关键决策记录

**D1：分类复用既有 SSOT，不造第三套；且不扩 summary 协议面。**
既有端到端契约为 `blocking_class='externalBlocked'` + `failure_kind='device_blocked'` → goal `external_block`（证据见 ④ 表）。

**精确原因不进 summary 顶层**：[summary.schema.json:6](../../harness/schemas/summary.schema.json:6) 是 `additionalProperties: false`，新增 `device_subkind` 会直接校验失败，且需同步改 writer / lite validator / 类型。既然该 subkind **只供人读**，就保留在 blocker 的 `details_excerpt` 或既有 HDC diagnosis 里；将来确有机器消费需求时再正式升 schema。

**混合场景**：同一 phase 内模块 A 锁屏、模块 B 用例真实失败 → 不得整体 defer，真实失败仍须 FAIL（否则设备问题会掩盖代码问题）。

**D3：结构性阻断优于行为禁令（本 plan 最重要的一条）。**
[agents-entry-detail.md:70](../../skills/reference/agents-entry-detail.md:70) 明写"AGENTS.md 全文未禁止主 agent 调用 shell/执行命令；空白处一律按'允许'理解"。**framework 无法技术性阻止 agent 用绝对路径调 hdc/Emulator.exe**，故"禁止猜密码"只能是指导，不能是保证。

正解：**设备就绪门**——未取得 READY target 就**不产生 `agent_invoke_start`**，agent 不进入"发现锁屏后自行处置"的场景。

**但只复用位置，不复用函数（v3 措辞已更正）**：[goal-runner.ts:550](../../harness/scripts/goal-runner.ts:550) 的 `runInvokeCapabilityGate` 是**同步**函数、只调静态 `runCapabilityPreflight`、缺口固定产出 `verdict='FAIL'` + `phase_halt(await_human_capability_gap)`（[:561](../../harness/scripts/goal-runner.ts:561)）。设备就绪需要**异步副作用**（模拟器 boot 等待、解锁、复验），且设备不可用应走既有 `external_block`/INCOMPLETE defer 契约，**不能冒充静态 capability FAIL**。故为两个相邻但独立的门：

```
runInvokeCapabilityGate          同步、纯探测（不动）
        │ PASS
        ▼
await runDeviceReadinessGate     异步、有界、按 requires_device 派生
        │
        ├─ READY     → 设 HARNESS_HDC_TARGET → agent_invoke_start
        ├─ BLOCKED   → INCOMPLETE / external_block，无 invoke
        └─ AMBIGUOUS → HALTED，无 invoke
```

**必须限定在声明需设备的 phase（至少 ut/testing）**：否则 spec/plan/coding 的每个 attempt 都会去检查手机——过早解锁、启动模拟器，甚至阻断与设备无关的工作。

**D3b：pre-invoke 门覆盖不了运行期再次锁屏（v3 的回归，此处补回）。**
用户原始场景正是"鸿蒙无法常亮 + 长时间无人值守"：pre-invoke READY 之后几分钟手机就会自动锁屏。而现有锁屏信号**只在设备操作期间才暴露**：

|------|---------|
| [hdc-runner.ts:1140](../../profiles/hmos-app/harness/hdc-runner.ts:1140) | `aa test` **启动测试 Ability 失败后**才识别 device_locked |

> v2 的 D4 本已识别"解锁必须能重复执行"，v3 改结构性阻断时删掉了 agent 侧封装命令，把该约束丢了。

故须补回 **agent 可调用但不接触密码的 `ensure-ready(serial)` wrapper**，接入所有 framework 控制的设备操作边界：`aa test` 前 / warmup 前 / device-testing install·run 前 / 已收到 `device_locked` 时允许一次有界恢复后重试原操作。helper **永不提供读取或返回凭据的接口**。

**锁存语义修正（原"全 goal 一次"是错的）**：

| 事件 | 行为 |
|------|------|
| 确认发生**新的锁屏事件** | 可用已登记凭据尝试 **一次** |
| 该次成功 | 未来再次锁屏**仍可**自动解锁 |
| 任意一次**失败** | `(serial, credential_version)` **机器级锁存**（见 D3g），跨 goal/项目/并发进程永不再试 |
| 锁定冷却 / 键盘无法确定 / 凭据类型不支持 | **零输入**，直接 fallback / INCOMPLETE |

原"全 goal 只尝试一次"会导致第一次成功解锁后、第二次正常自动锁屏无法恢复；而"每次都能无限试"又重新产生锁机风险。按"新锁屏事件"与"失败"分别计数才两边都成立。

**两阶段 write-ahead 记录（v5 缺口：只在拿到 outcome 后才写，留有崩溃窗口）。**
v5 的记录时机覆盖不了这条链：

```
开始输入 PIN → 手机判密码错误 → helper/runner 在写 outcome 前崩溃
→ resume 看不到失败记录 → 再输入一次 → 重新产生本次事故的锁机风险
```

故记录必须是事务性的：

| 步 | 动作 |
|----|------|
| 1 | 输入**第一个数字之前**先持久化 `attempt_started` |
| 2 | `attempt_started` 落盘失败 → **零输入**，直接 BLOCKED |
| 3 | 完成后追加 `attempt_succeeded` / `attempt_failed`，引用**同一 `event_id`** |
| 4 | resume 遇到**无终态**的 `attempt_started` → **保守判失败并锁存，绝不重试** |

第 4 条的取舍要说明白：**成功但终态丢失也会被保守锁存**——牺牲一次自动恢复能力，换"绝不会再次锁机"。这个方向是对的，因为误锁存的代价是人来解锁一次，误重试的代价是设备被锁死。

**D3g：锁存范围必须是机器级，不能是 goal 级（v6 安全模型错误，此处更正）。**
v6 把锁存范围定为 `(serial, credential_version) × 当前 goal`，并为守红线而"只写当前 goal events"。**该设计不成立**——留有两条重新锁机路径：

| 路径 | 后果 |
|------|------|
| Goal A 失败锁存 → 新建 Goal B 看不到 A 的 events | B 又试一次 |
| 两个 goal / 两个 wrapper 并发，各自账本都显示"尚未失败" | **同时**输入 PIN |

正确范围是 `(serial, credential_version) × **当前机器**`。状态机托管进已规划的 Credential Manager provider：

```
ready
  │ 取机器级互斥锁（framework namespace + serial + credential_version）
  ▼
in_flight ──输入成功且复验已解锁──▶ ready
  │
  ├─ 输入失败 ─────────────────▶ disabled
  └─ 进程崩溃 / 终态缺失 ───────▶ disabled
```

契约：

1. 输入前先取**跨进程 mutex**（有界等待，语义见下表）；
2. mutex 内**重新读** Credential Manager 状态（不信进程内缓存）；
3. 第一个数字前把状态 **durable commit** 为 `in_flight`；写入失败 → 零输入；
4. 成功**且复验已解锁**后才可回 `ready`；
5. 失败、或发现遗留 `in_flight` → `disabled`；
6. **解除只有一条路**：重新输入凭据 → 生成**新 `credential_version`** → `ready(v_new)`。

**mutex 未取得的语义（不是简单零输入）**：

| 情形 | 行为 |
|------|------|
| 有界等待期内 owner 释放 | 重新读**设备状态 + CM 状态**再决策 |
| owner 已成功解锁（设备已就绪） | **无需输入**，直接继续 |
| 读到 `in_flight` / `disabled` | **零输入** BLOCKED |
| 等待超时 | 零输入 BLOCKED |
| abandoned OS mutex（owner 进程已死） | 视同遗留 `in_flight` → `disabled`，零输入 |

若写成"未取得即零输入"，正常并发下第二个 wrapper 会在 owner 其实已解锁成功时白白 BLOCKED。

**`disabled` 不得同版本复位（否则锁存被架空）**：

```
✗ disabled(v1) ──受信恢复 CLI──▶ ready(v1)      ← 禁止：可反复重试同一错误 PIN
✓ disabled(v1) ──真实 TTY 重新登记──▶ ready(v2)  ← 唯一出路
```

锁存的语义是"**这个密码是错的**"，所以必须换密码才能继续，而不是重置计数器。恢复 CLI 同样须经真实 TTY / OS credential dialog 重新登记并产生新版本，**不提供同版本 reset 接口**。

**goal events / journal 降级为审计投影**：仍按 D3e 单写者模型记录同一 `event_id`，但**不承担跨 goal 协调**，不再是安全锁存的 SSOT。

**这是场外状态红线的第二项合法例外，论证独立于 PIN 本身**：该状态必须跨 **run / feature / 项目 / 并发进程**协调，单个 repo 内的 run 产物**结构上做不到**（run 产物按 feature 与 run 分区，互不可见）。且它与 PIN 同由 Credential Manager 托管，**不新增明文秘密面**。

**D3h：durable 与并发语义必须落到实处（v6 只说"持久化"）。**
既有追加路径都是**裸 `appendFileSync`**、无 fsync、无互斥：

| 位置 | 现状 |
|------|------|
| [goal-runner.ts:472](../../harness/scripts/goal-runner.ts:472) `appendEvent` | `fs.appendFileSync`，无 durable flush |
| [intermediate-rounds-journal.ts:130](../../harness/scripts/utils/intermediate-rounds-journal.ts:130) | 同上 |

（全库仅 [effective-vision-context.ts:729](../../harness/scripts/utils/effective-vision-context.ts:729) 一处用过 `fsyncSync`。）
故"断电/崩溃安全"不能靠现有 append 语义宣称。要求：

- `in_flight` / `attempt_started` 必须在**输入前完成 durable commit**；
- journal 半行、校验失败、状态歧义 → 一律 **fail-closed**；
- 采用 Credential Manager 状态 + OS 级 mutex 后，**per-run journal 不必独自承担断电一致性**（各司其职：CM 管安全，journal 管审计）。

**安全保证的三层诚实表述**（不得混为一谈）：

| 层级 | 内容 |
|------|------|
| **强保证** | framework 只使用用户登记凭据；任意失败即**机器级**锁存（跨 goal/项目/并发进程，非仅跨 retry/resume） |
| **防御性指导** | agent prompt 明确禁止直接输入 PIN、禁止直接启动模拟器，只能调 framework readiness 入口 |
| **不宣称** | 在不增加 OS 沙箱/独立用户的前提下，绝对阻止同用户任意 shell 绕过 |

因此验收项从"禁枚举行为被拦"（单测无法证明）改为**"锁屏且无授权时，runner 在调用 agent 前停止"**（可确定性验证）。

**D3c：PIN 输入机制的硬约束（Credential Manager 只解决存储，不解决输入）。**

- 仅支持**数字 PIN**；手势、字母密码明确 **unsupported**；
- 坐标**必须从当前设备 UI tree 解析**——禁止固定分辨率硬编码（本次事故 agent 用的正是硬编码坐标表）；
- 0–9 键未能完整识别 / 设备处于锁定冷却 / 页面非已确认的锁屏 UI → **零输入**直接 fallback；
- 通过坐标点击输入，子进程 argv **只出现坐标、不出现 PIN 字符串**；
- 输入后**重新探测锁屏状态**判定成功，不得凭命令退出码宣称成功。

**该项需真机 spike**：锁屏 UI 随 HarmonyOS 版本而异，纯单测无法证明输入安全，须随常规宿主真机回归验证（与其余五项同期交付）。

**D3d：启动即锁屏的死锁必须由共享核心解开（v4 设计缺陷，此处修正）。**
v4 让 Todo 3 的 gate"不含解锁"、Todo 6 的 `ensure-ready` 只挂运行期，结果是：

```
启动时手机已锁屏 → gate 判 BLOCKED → agent 不启动 → 运行期 wrapper 永无机会执行
```

而用户的原始场景恰恰是"**锁屏了没注意**"——goal 启动时手机大概率就是锁的，这条死锁直接毁掉核心诉求。

修正：gate 与运行期 wrapper **复用同一个可信 `ensureDeviceReady` 核心**，统一顺序：

```
非秘密 wake → 重新探测 → （已授权）尝试一次解锁 → 复验 → 必要时按策略选模拟器
```

Todo 3 的"不含解锁"应理解为**本 Todo 不实现凭据能力**；Todo 6 接入后 **gate 必须调用它**。
**wake 步骤不可省**：息屏时 UI tree 不完整，缺了它会直接落入"键位识别不全 → 零输入 fallback"，等于永远处理不了用户场景。wake 是非秘密操作，不涉及凭据。

**D3e：锁存落盘必须走单写者模型（架构红线，v4 违规）。**
v4 多处写"runtime helper 将锁存直接写 goal events"，直接违反既有架构：

| 约束 | 证据 |
|------|------|
| agent 侧 `goal-runs/` **只读**，禁 write/append/patch events.jsonl | [goal-runner.ts:2701](../../harness/scripts/goal-runner.ts:2701) agent prompt 原文 |
| 权威追加函数 `appendEvent` 为 runner **私有**，不导出 | [goal-runner.ts:469](../../harness/scripts/goal-runner.ts:469) |
| 已有单写者先例：agent 侧写 journal proposal → runner 收编 | [types.ts:583](../../harness/scripts/utils/types.ts:583) `disposition: 'journaled'` |

沿用该模型：

- **runner 侧** pre-invoke 解锁 → 直接追加正式事件；
- **agent 运行期 wrapper** → 只写原子 journal/latch proposal，绑 `event_id`/`run_id`/`invoke_id`/`serial`/`credential_version`/`outcome`；
- runner 在 **verdict 与 resume 启动**时幂等收编进正式 ledger；
- **职责边界（v7 遗留矛盾，此处更正）**：wrapper 判定"是否允许输入"**只读机器级 Credential Manager 状态**（D3g 的唯一安全 SSOT）；ledger/journal **仅用于审计事件去重**，不参与放行判定。v6 曾写"须同时读正式 ledger 与未收编 journal"，那是 goal 级锁存时代的产物，与 CM 作 SSOT 冲突，已废止。

**D3f：同一 attempt 内设备目标不可热切换。**
v4 未说明 fallback 是"结束当前 attempt"还是"真机跑一半切模拟器"。后者会产出**混合证据**，而 `target_kind`/serial 只记一个目标 → 假绿。钉死：

| 时点 | 规则 |
|------|------|
| `agent_invoke_start` 后 | 本 attempt 的 `{serial, target_kind}` **不可变** |
| 运行期锁屏 | 只允许**同 serial** 恢复并重试原操作一次 |
| 恢复失败 | 当前 attempt → INCOMPLETE / `external_block` |
| 下一 attempt / resume | 才由 readiness gate 选择模拟器，并**从阶段起点重跑** |

除非将来引入逐操作 provenance 与完整重启协议，否则不支持热切换。

**D4：完成判据只用确定性信号，且绑本 attempt。**

| 判据 | 性质 | 取舍 |
|------|------|------|
| 纯只读 validator + 本 attempt 新鲜度跃迁 | 确定性 | **采用** |

否决理由是实锤：`DEFAULT_SILENT_WATCHDOG_MS = 0` 既有注释写明"cursor-agent often streams little until phase end"，静默判据会误杀正常长任务；且本例根本不需要它。

`--skip-state-sync` 确实存在（[check-receipt.ts:184](../../harness/scripts/check-receipt.ts:184)）且挡住 1032 起的状态同步与 attestation 生成，但 [:1218](../../harness/scripts/check-receipt.ts:1218) 的 `soft_advisories` 回写**不受该开关保护**。既然 D2 已要求 in-process observer，正解是抽**纯只读 validator 函数**，与 CLI 共用判据但零写盘。

**D6：凭据方案拍板 + 授权入口 + 场外状态例外论证。**
拍板 **Windows Credential Manager**（不留"DPAPI/CM 二选一"给实施者，否则会出两套不兼容设计）：target name 绑 **framework namespace + 设备 serial + `credential_version`**（或不可变 UUID target——见 D6b，绝不可只绑 namespace+serial，那样轮换会原地覆盖）；`framework.local.json` 只存 opaque `credential_ref`；删除/轮换/重新登记有确定 CLI；**非 Windows 显式 unsupported**，走人工/模拟器降级。

**授权入口必须接既有 registry 机制（v5 只说"宿主交互层询问"，未指定消费方=落不了地）**：
现有 goal 入口是**主 agent 先做 personal setup，再 strip `--detach` 起后台 runner**（[goal-runner.ts:3098](../../harness/scripts/goal-runner.ts:3098)）——**后台 runner 结构上无法弹交互**，故询问只能发生在启动 detached child 之前、由主 agent 承担。接线：

1. 新增 registry 项 **`setup.device_policy`**（与既有 `setup.adapter` / `setup.deveco_path` 同款模式）；
2. 主 agent 启动 detached runner **之前**执行确定性 `check-device-policy --json`；

**enrollment 通道钉死**："masked CLI"不够——须在**用户控制的真实 TTY 或独立 OS credential dialog** 完成，PIN **禁止出现在 argv / env / pipe / agent stdin**。与 [capability-preflight.ts:11](../../harness/scripts/utils/capability-preflight.ts:11) "agent 对话确认不构成任何授权"一致。

**D6b：凭据身份必须不可变绑定（v7 缺口——target 只绑 namespace+serial，而锁存/mutex 按 `credential_version` 工作）。**
若轮换时**原地覆盖**同一 target，会出现：

```
Goal A 启动时读到 v1 → 用户轮换为 v2（同 target 被覆盖）
→ Goal A 再次读取拿到 v2 的 PIN，却仍按 v1 的 mutex / 锁存状态执行
```

这直接击穿"一个凭据版本只允许失败一次"的边界。契约：

1. 每次登记生成**不可变** `credential_ref` 与 `credential_version`；
2. Credential Manager target 至少绑 **namespace + serial + credential_version**（或用不可变 UUID）；
3. **轮换只能新建记录 + 原子切换配置，禁止原地覆盖**；
4. 每个 run/attempt **冻结 `{serial, credential_ref, credential_version}`**，运行中不得因配置轮换静默切到新 secret（与 D3f 的设备目标冻结同构）；
5. helper 读取后须**校验 serial / version 匹配**，不匹配即 fail-closed。

**provider 现状是真实工程风险（须 spike，不可假设可用）**：仓库当前**无任何 Credential Manager provider 或依赖**（只有尚未落地的后继 change `confirmation-credential-issuance` 的引用，见 [confirmation-receipt.ts:139](../../harness/scripts/utils/confirmation-receipt.ts:139)）。且 `cmdkey` 公开接口只能 add/list/delete、**不能读回 secret**，`/pass:` 还有 argv 泄露风险 → 须走 native bridge（`CredRead`/`CredWrite`）。spike 范围：选型与发布方式、clean Windows 安装验证、不依赖额外 PowerShell module、登记·读取·删除·轮换闭环、**轮换须生成新的不可变 `credential_version`**（否则旧失败锁存无法与新密码区分，等于永久封死）。

**场外状态红线的例外论证（v2 的 D5 解释有误，此处更正）**：
[AGENTS.md:64](../../AGENTS.md:64) 原文要求"新增任何场外状态类型须先证明「in-repo 产物 + 签名/哈希绑定」做不到，默认不允许"——**并未限定 per-run**，v2 称"该红线只针对 per-run 堆积"不准确。
本 plan 的例外论证：设备解锁凭据**无法** in-repo——项目根是 agent 可写区（[confirmation-receipt.ts:133](../../harness/scripts/utils/confirmation-receipt.ts:133) 同源理由），且凭据须由 OS 密钥库加密托管，签名/哈希绑定解决的是完整性而非机密性。故构成红线的合法例外。
**第二项例外：机器级失败锁存状态**（v6 曾试图靠"只写 goal events"规避新增场外状态，**已在 D3g 更正为不成立**——那样跨 goal 与并发场景都会重新输入 PIN）。论证：该状态须跨 run/feature/项目/并发进程协调，repo 内 run 产物按 feature 与 run 分区、结构上互不可见；且与 PIN 同由 Credential Manager 托管，不新增明文秘密面。goal events 保留为审计投影（`device_unlock_attempt`：serial / credential_version / outcome / attempted_at），但不作安全 SSOT。

**D7：诚实边界（不自欺）。**
OS 凭据库**无法对抗同一用户权限下的恶意任意代码**。保证边界须逐条说准，**不得笼统宣称"agent 无法去猜"**（v7 表述过度：运行期 agent 已启动后，仍可绕过 wrapper 直接调绝对路径的 hdc——就绪门只管启动前）：

| 能保证 | 内容 |
|--------|------|
| ✅ | **framework 管理的解锁路径绝不猜密码**（只用登记凭据，失败即机器级 `disabled`） |
| ✅ | 密码不出现在 transcript / argv / env / 普通配置 / 日志 |
| ✅ | **启动前**无授权且设备锁定 → readiness gate 不启动 agent |
| ⚠️ | 运行期只能靠 **prompt 强制要求走 framework wrapper**（指导，非强制力） |
| ❌ | **不宣称**在无 OS 沙箱时能硬阻断恶意或偏航 agent 的直接 shell 操作 |

与 D3 的三层表述、confirmation-receipt 已承认的边界一致。本 plan **不因此新增命令沙箱**（见非实施项），只要求把保证说准确。

**D8：模拟器能力判定改 phase 级最小规则（对 v2 逻辑漏洞的修正）。**
v2 把逐用例能力矩阵放 backlog，却要求"真机不可替代项未执行 → PARTIAL/DEFERRED"——**无规则定义何为不可替代，runner 无法判定**。仅记 `target_kind` 是证据，不是判定规则。

改为 phase 级保守规则：

| phase | 模拟器执行 | 结论上限 |
|-------|-----------|---------|
| `ut` | 允许 | **可 PASS** |
| `testing` | 允许执行并收集证据 | **默认只能 PARTIAL/DEFERRED**，不得整体 READY/COMPLETED |

**执行位置钉死（v4 只写规则未指定谁强制）**：由 **runner 依可信 device session 派生**——`testing` + `target_kind ∈ {emulator, unknown}` 时，**无论 agent summary 声称什么**，最终结论只能 PARTIAL/DEFERRED。不得依赖 agent 自报（自报即可绕过）。

**D8b：`target_kind=physical` 必须有正面证据路径（v5 漏洞）。**
v5 只禁止"`unknown` 推断为真机"，却没定义**什么证据能判为 physical**。后果是真机也会一直停在 `unknown` → `testing` 永远 PARTIAL → 整个功能不可用。故须给出正面分类表：

| 证据 | 判定 |
|------|------|
| 本 run 启动且绑定 serial 的模拟器 | `emulator` |
| 可验证关联到既有 Emulator profile / process 的 serial | `emulator` |
| 经**已验证的 HDC 属性组合**确认的真机 | `physical` |
| 其余 | `unknown` |

**禁止**"不是已知模拟器，所以是真机"这类反向推断。HDC 属性组合的具体取值需随真机 spike 一并确定（与 D3c 的锁屏 UI spike 同期）。

> **收窄已经用户确认（2026-07-28）**：用户原话是"通过模拟器完成 ut 和真机测试"，
> 经说明后确认接受——**默认就应该真机跑，模拟器是无奈的降级之举**。
> 故 testing 用模拟器只能得 PARTIAL/DEFERRED：没有能力判定规则时，模拟器结果冒充真机
> PASS 是假绿；PARTIAL 仍是完成度的诚实表达。
> 若将来出现确可完全由模拟器覆盖的 testing 场景，再加测试集级 `emulator_ok` 声明。

**D9：Todo 顺序按依赖重排。**
模拟器托管（Todo 2）先于就绪门（Todo 3）——就绪门的降级出路依赖托管能力；两者均先于完成观测（Todo 4），否则 observer 提前 kill agent 进程树会**连 agent 自起的模拟器一起杀**。

**D10：outer_layers 前移必须有条件、形态拍板、且时点精确。**
无条件早检会让 spec-only / plan-only / UT-only 任务因**永不访问**的目录失败 → 仅 chain 含 testing 时早检。
形态拍板（不留给实施时选）：**先建 run/manifest**，失败写 `phase_halt` + `run_end=HALTED`。若在建 run 前裸退，则无可监控 run，也无法自然表达 `--resume` 重检。
**时点精确化**：v3 写"第一个相关 `agent_invoke_start` 前"有歧义——会被读成"testing 自己的 invoke 前"，那仍要等 spec/plan/coding/ut 全跑完，事故照旧。准确表述是：**chain 解析完成并确认含 testing 后，紧接 run/manifest 创建之后、整个 run 的第一个 phase agent invocation 之前**。唯有如此才在 goal 启动阶段就暴露 `03-CommonBusiness`。

## 三、设计原则红线

1. **复用既有分类契约**——设备阻断走 `externalBlocked`/`device_blocked`/`external_block`，精确原因只留 blocker details（不扩 summary schema），不新建平行体系。
2. **结构性阻断优于行为禁令**——未 READY 不产生 `agent_invoke_start`；不宣称能拦住任意 shell。
3. **完成判据只用确定性信号**——纯只读 validator + 本 attempt 新鲜度跃迁，不引入静默类概率判据。
4. **凭据永不明文、永不进 agent 面**——OS 密钥库托管；不进 prompt / transcript / argv / env / agent 可控 stdin。
5. **长驻进程一律框架托管**——agent 不得成为长驻进程的父进程。
6. **降级不放水、不冒充**——`target_kind` 不可确认记 `unknown`（不得推断为真机）；testing 用模拟器不得整体 PASS。
7. **只回收本 run 启动的资源**——四元组确认所有权，绝不关闭用户已开实例。
8. **单写者账本**——agent 侧一律只写 journal proposal，正式 events.jsonl 只由 runner 追加并幂等收编。
9. **attempt 内设备目标不可变**——`agent_invoke_start` 后 `{serial,target_kind}` 冻结；换目标只能下一 attempt 从阶段起点重跑。
10. **凭据输入先记账后动作，且锁存是机器级**——`in_flight` 未 durable commit 则零输入；遗留 `in_flight`/失败一律 `disabled`，跨 goal、跨项目、跨并发进程一致。
11. **凭据身份不可变**——`credential_version` 只增不改，轮换新建禁覆盖，run/attempt 冻结身份；`disabled` **只能由新版本解除**，不存在同版本复位（否则锁存被架空）。

  - `setup.device_policy` 未配置时，**主 agent 在起 detached runner 前**完成询问（非 runner 打印后退出）；
  - agent 侧 wrapper **不直写 events.jsonl**，锁存经 journal proposal 被 runner 幂等收编；
  - 新锁屏事件可解、二次锁屏仍可解；**任意一次失败即机器级 `disabled`**，跨 goal/项目/并发进程；
  - **`disabled` 无同版本复位路径**（恢复 CLI 只能经真实 TTY 产出新 `credential_version`）；
  - **run/attempt 冻结凭据身份**：持有 v1 期间并发轮换到 v2 不会静默切 secret；
  - provider 集成：`in_flight` 落盘后强杀进程 → 下一进程零输入；
  - A 手机凭据不会用于 B 手机；键位不全 → 零输入 fallback；退出码 0 但仍锁屏 → 判失败。
