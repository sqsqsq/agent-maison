## 3. 改造边界

### 3.1 回到能修复问题的职责（A1–A3、D3）

在现有 `change-unit-provider-boundary` 接受候选时保留原子写出/回滚及原始投影 issue。用该 issue 的真实对象和已有 `current_disposition` / design repair 入口区分三类责任：候选自身缺映射仍交拆分方；已验证的蓝图契约缺口交同一 root 的 component-design 作者，给具体路径、期望/实际和仍可用的候选；外部真实授权缺口循原授权路径。消费者的机器证据决定路由，作者的一段自述只作诊断。蓝图缺口复用 `initial-design-delivery.ts:466–478` 已有的诊断 → `designRepair` → `author` 路径，将无 CU 时的接受失败接入同一处理；不再建第二套路由。先按责任交接再评价无进展；不得因“换 owner”清空历史、预算或失败、无限来回派工。重启/重试用原 run、原事务及既有检查结果，不重复接受 CU。修复后只重验受影响设计与候选，直至真实准入。

在 `selectBlueprintSkillContent` 的既有投影中，由程序从所属 flow 的权威字段生成施工镜像。flow 身份产生完整 `design_ref`；`state_owner.ref` 提供 owner；既有逻辑/外部契约引用提供 contract_refs；变更、发布、订阅、消费清单引用 flow 中已声明的同名事实。订阅若缺发布引用，只有已绑定消费者的 `update_ref` 能唯一确定该发布时才可填入。已填且等价的值归一，已填但矛盾、过期身份、跨 flow、引用缺失或多解，沿原校验退回其责任方。完整对象和旧 run 原有意义保留。i11 上述字段均有唯一来源，预期该 CU 投影直接通过；§5.2② 保留去掉唯一事实后的反例。

### 3.2 用已有质询身份作逐项复核（B1–B7、D5）

- 复用 `requiredQuestioningScopes`、稳定 scope/question_id、`latestUsableDesignQuestioning`、依赖变化计算、独立原件、现有来源引用。首次评审仍覆盖全部适用范围。修订时由程序用两份设计及引用输入计算受影响集合：变动的业务事实、原阻断/待决及关联消费者纳入；依赖不能证明未变时重审对应范围。评审者可以带具体新证据重开任何原结论。相同业务名词或哈希相近本身不能证明等价。
- 单次调用只给必要的变动、相关原件位置、未决问题及要求独立核实的来源；同一材料只传摘要或给路径，不把全文同时复制进 prompt。独立性靠原生独立上下文和来源核验；不通过接续作者会话加速。复核只交回本轮实际评的条目。机器把它们与经验证仍有效的旧项合并到现有 questioning 结构，使最终每个必答范围仍恰好一条，保留原始输出和每项出处。复用项不得标成刚刚新评。
- 解析后、业务裁定前，在同一校验入口规范化唯一地址；i5 的唯一有效结论可保留，无有效业务事实、无新增异议的占位项可剔除。两个都有效且结论不同、真实 blocker 与看似占位冲突、缺少独立来源、越权写入、不可唯一映射时，保全原件，局部交回精确错误及缺口；污染整份原件时仍按原独立性边界重新质询。禁止按文件名或 `-dup-placeholder` 后缀特判。只为格式返修不得重新调查全部页面。
- 正常机器 checker 由既有 owner 执行一次，评审读 UTF-8 结构化结果及所需证据；已有结果过期才重算。避免每个新会话自行查命令、重定向、转码、写临时 JSON 再复述。独立评审仍可为具体疑点取新证。据此缩短输出，不限定模型思考方式或牺牲证据。
- **用指引改善业务判断。** 修改 `component-design` 设计作者指引与生成独立质询说明的模板。作者从原需求提取用户可观察的结果；需求指定某个对象时，验收要能区分“本次对象正确”和“结果看起来成功但对象错误”。质询方对照原文，尝试构造能骗过该验收的反例，核实上下游取得的是同一个对象。失败返回落点按原文与已有路由说明依据，原图沿既有来源传到施工和视觉验收。上述内容指导模型撰写和质询，没有新增机器语义检查、打分或阻断。A/B 卡只作为本次宿主验收数据，通用指引和 runtime 均不含需求名、卡号字段或专用用例。真实授权、不可逆动作和硬预算仍按原规则处理。

### 3.3 让首次分档可消费（C1–C4）

同一作者在正常首轮调研的公开说明中引用已读来源；根入口模板、各 adapter 实际加载的指引和 `project-entry.md` 四档规则节给同一例句。规则仍由 `resolveDeliveryPolicy` 计算。**新完整开发请求**沿已有授权进入原入口命令时，先处理真实用户显式豁免或指定；其余请求若返回 `policy.selected=unknown`，命令在现有返回文字中直接提示“档位未知，按完整设计推进；如属小改，可按下列例句写出有来源的事实，再调用同一入口。”随即返回可执行的既有完整设计步骤，保留 `unknown`，无需等待用户、自动追问或自动重调。下面是一个预期明确、存在局部实现选择的小改示例。值和路径都须按本请求实际调研替换，不能把示例当默认事实：“Q1=否，Q2=否，Q3=否，依赖结果=否，跨部件=否，预期明确=是，做法唯一=否。依据：<已读需求相对路径>、<已读源码相对路径>。”这只是可选纠正方式；启动前原作者选择补充时，同一入口根据新证据重算。已有 run 沿原范围续作；仅设计、显式局部验证及真实用户指定保持各自原终点和授权。无新状态、无分类 CLI、无额外必跑的模型轮次。

同批在 `request-intake` 兼容真实的 `git -C … status --porcelain` 和可核对的当前工作树 reflog 行；旧行无说明但身份、时间、连续性可证时不丢整段，脏文件无前像时保留 unknown，绝不用当前状态冒充过去基线。保留公开判例供解释，在验收说明区分这是已知答案；分档验收含未见同类需求和能改变档位的近邻反例，不能通过把需求名写进规则来达标。

### 3.4 启动、状态与用量沿现有入口收口（D1–D4）

help、goal-mode-entry、goal-runner 的 fresh dry-run 与真实启动共用入口投影；新正式需求无需先有 feature.yaml。dry-run 只展示下一步/范围/已知缺口，不能签发设计、创建真实 run 或启动子进程；已有 feature 的原有 dry-run 隔离行为和恢复身份保留。文档提供正确的工作目录与 requirement 路径。正常路径无需向 framework 写探针。

保留 invoke_end 的调用语义，Goal 状态从已核原件/当前 disposition 投影“调用结束、交回可用性、有效范围/阻断/待决、当前阶段、下一责任方与来源”；restore 前旧终态不得压过后续 run_start 和有效当前状态。复用 `goal-status --watch`、当前事件和已有启动/恢复入口；状态变化即显示，需要外层动作时明确给同 run 的合法指引，不以固定长睡眠等待后台反馈。常规可恢复 A1 必须由 runtime 自己完成。禁止以自动 `--force-resume` 跨越授权、冷却或真实硬预算。

本次用量改动只涉及 DSH。在既有 usage capture 和 invoke_end 上按同一 invocation 的原生 step_end 汇总新增输入、缓存读取和输出；镜像日志、重复事件或重放不得重复入账。中断只计已观测部分；缺失保持 null 并标原因，不推断费用，也不以计数缺失停机。无损表达 DSH 缓存读取所需的可选字段只在现有 usage 对象增加，旧事件/消费者继续可读。其它 adapter 的采集行为沿用现状。

## 5. 一次完成、统一验收

1. **保全与回放**：实施时从 R 已结束调用提取最小原件，放入既有 host-recovery-history 夹具体系，保留来源哈希、前后顺序和必要 parent/run 关联；剥离绝对用户路径、原生私有内容、凭据和无关备份/快照。不能为了造绿改写原始返回。i2/i5 的 questioning-output.json SHA256 分别为 `619e03dec3a4c783da01bb4cdd27bb6024a2028a47c3bded64df729241f4824b`、`c185d3dcd7207636f470abe46fc1a1d1e62156e2731d4a49823c5c2a8478c19f`；i11 agent-events.jsonl 为 `2976f71fb961afbeefd68652198d3720b6f53a721a256fbd614faa362a2938f1`；i12 蓝图前像为 `d37fd1ed630843c450f9e1bdeac338858605f6b182dc46a6b79f8eedd516beb9`。从 i11 原生 final 截取诊断，不把作者自报当测试预期；预期独立来自失败投影和源需求。
2. **恢复正反例**：从同一公共入口验两条确定路径。① 原样 i11 用冻结、已准入的蓝图和候选，§3.1 的唯一映射直接通过 CU 投影，无候选重派；B6 对业务漏验的检验独立保留。② 仅去掉 home-card-state 的唯一 update_ref，保留两个语义不同的发布源且均可能被订阅。即使字符串已规范化，现有投影仍须拒绝；同一 run 立即交原蓝图 owner 补真实选择，再接纳同一 CU 并进入施工。两例零人工/零强制续跑、无重复已接纳 CU，该种可恢复缺口不得标 human；候选真错仍交候选作者，用户授权/秘密/不可逆/硬预算真实缺口仍正确等待。模拟返修中断后续作，沿同一 run 恢复、已有证据不丢、计数不重置；反复同输入无改善仍能收敛。
3. **质询正确性**：原件夹具只验机器职责。i2 唯一别名和 i5 冗余占位能局部恢复，五条真实 blocker 保留；双有效冲突、证据变更、新的独立异议能触发相应处理；依赖未变的结论沿用并可追溯。i10/i13 只作为历史对照，不让替身替模型“发现”业务漏验。§3.2 指引的效果只在获准的干净宿主真实重跑验：读真实需求、作者实际生成的验收、独立质询原件和最终证据。在获准的干净测试宿主用正常流程预置测试卡 A，再新开测试卡 B；验收必须能识别“首页仍有卡却交了 A”的错误，并验证真实成功链交 B；沿用现有 UT/设备观察，不把完整卡号写入日志。若作者首稿已覆盖，直接核其实测依据；若首稿漏掉，独立质询应在准入前指出并由作者补实。实际失败返回落点同样依据原文和既有路由核对。只通过文本/夹具检查、替身预填或在框架写银行卡特判，都不能签这项效果通过。
4. **入口与 CLI**：共享规则跑原件/夹具，实机按 §4 的四个客户端成对跑普通公开请求/用户升降档、真实来源/模拟 Agent 自述、已知档/有决定性未知、首次/同 run 续作；补覆盖未见名称的四档及边界近邻。新授权完整开发请求缺分档事实时断言结果仍为 unknown、返回既有完整设计步骤和可选例句、一次调用即返回；用户覆盖、局部请求和已有 run 用反例验其原终点。特别简单首写前新增 CLI/模型轮次为 0，小型走短蓝图。fresh dry-run、已有 feature dry-run、prepare-scope 和真实启动的入口选择一致；执行 dry-run 后宿主没有新真实 run 或产品/框架写入。
5. **状态与成本**：i13 的“调用结束、3 blocker、6 open_decision、下一责任方”在同一公开状态入口清晰可查；独立判断不能被 passed 覆盖。用停止/恢复原件验证 watch 在现有一个刷新周期内显示变化，恢复后显示最新活跃责任。用 i1–i14 原生原件复算 §2 D4 并与机器输出逐项比对；重复结束事件、跨 turn/会话、缺计数、中断和 provider 累计数各有反例。输出 UTF-8 机器可读；按同口径记录提示字节、原生步数、增量审查条目、工具调用和实际耗时，不把字节折成 token。
6. **干净宿主与目标**：一次同类重跑使用相同原始需求、4 图、产品基线、模型/provider/执行模式、同等验证义务；只更换待验发布件。用既有 events/产物分别报告根启动、第一次有效 CU 准入、首次正常施工作者、首个实际产品写入、首个 coding 检查和最终交付。首写用原生写工具成功且能核到产品字节变化的时间；缺此证据标未观测，不拿检查时间代填。**初始设计目标 ≤9 次模型调用，根启动至首次正常施工作者 ≤100 分钟**。预算依据是首稿约 21 分钟，容纳初评及两轮局部复评、两轮作者修订、拆分与范围准备并留一次真实返修；按本次调用时长量级留出非模型开销。与已观察到的 19 次/191 分钟同口径比较，14 次/约 149 分钟仅作中途参照。这两个总量目标与下述局部复核目标分别验收；目标均用于测量，不在 runtime 硬停。记录 provider 实际等待，超目标如实报告差额、不能用重置 run、降档、删质询或放宽业务断言达标。至原终点仍须管住旧路由、新卡身份、编译/UT/适用真机与视觉证据；到首次施工仅达成效率指标。宿主源需求/环境条件不同须另列，不能直接宣称目标已验。

   **局部复核另设可比指标。** 同一干净宿主、模型/provider、配置和等价独立性下，以首次完整独立质询为分母。比较其后发生业务修订的局部复核；格式纠正 i5→i6 单列，不能拿它充当修订样本。用实际前后蓝图、来源变更、前次未决项和关联消费者在看输出前列应复核的范围 ID；有具体新证时可注明并扩展。每轮交回 ID 必须恰好覆盖这些项，未受影响的答案由机器复用，最终清单仍完整。报告所有修订及各自的范围大小，不能删掉耗时长的轮次。
