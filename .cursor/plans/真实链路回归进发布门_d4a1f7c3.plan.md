## 1. 目标与冻结范围

**一句话**：发布件出厂前，至少有一次 spec→plan→coding→review→UT→testing 全链在框架内被**真实 harness 检查**跑过，
所有绑定、指纹、证据清单、verifier 材料、channel binding、visual 聚合由生产代码产出，夹具一行都不许手填。

本 plan 不负责：修任何一堵墙的生产缺陷（已分别归属 6f2a9c41 / c8b4e731 / 1f3d7a92 与姊妹 plan）、
提升宿主运行效率、覆盖真机与真实 agent 产物质量（口径见 §1.1）。

本 plan 负责：让下一堵墙在框架内就被撞到，而不是在宿主上花数小时撞到。

### 1.1 口径（必改 2，codex 第二轮收窄，全文以此为准）

**交付物名称：确定性输入下的生产验证链集成回归。** 不叫"真实链路端到端"。

| 真实的 | 是替身的 |
|---|---|
| goal 编排与阶段推进；六阶段检查的协调 | **整个作者行为**——`__testing_setInvokeAgent` 的桩（驱动 `:436–468`）返回 `command:'fake-agent'`、`exitCode:0`，替掉的是 agent 调用本身，不只是"LLM 文本" |
| 冻结、候选、绑定、facts 解析、evidence manifest、新鲜度 | **UT 执行**——照 `coverage-evidence.unit.test.ts:190–195` 先例，被返定值的不止 hvigor/tsc 三项工具链，还有 `checkUtFileNaming` / `checkUtFrameworkImport` / `checkTestRegistration`（`:194` 一行六个 `pass(...)`）。所以不能说"仅工具链替换" |
| verifier 材料与逐文件哈希、channel binding、P0 五数、AC 覆盖 | **设备侧零覆盖**（机制已按实跑更正，见 §10.4 偏差 5）——`test-chain` 确实不声明 `device_capabilities`，但**父进程根本读不到 test-chain**：`profile-loader.ts:24` 的 `FRAMEWORK_DIR` 是模块常量、指向源仓，于是 `:199–205` 静默回落 `hmos-app`，`phaseRequiresDevice('ut'|'testing')` 为真，`goal-phase-runtime.ts:7197` 的设备门**确实进了**，驱动注入的 READY(physical) 桩**确实执行了**。结论不变：发现、选择、就绪判定、身份传递一概未验，**真机零覆盖**；变的只是理由——不是"门没进"，是"进了门但门后站着桩" |
| report writer、summary writer、assess、receipt 校验、closure | **视觉采集与 OCR** |

**它证明什么**：材料在链上的消费、派生与推进一致——上游产出被下游以正确身份读到，失败时 owner 与 reason 正确。
**它不证明什么**：真实 agent 写得出合法产物、真实工具链能编过、真实设备能跑完、真实 OCR 能认出文本。

**再加一条覆盖上限（codex review 2026-09-22 建议 1）**：device_test.run 替身产出的 trace
用**生产 reducer**（`hylyre-crossrow-verifier.ts` 的 `reduceCase` / `toolCallsProjection`）算三轴与 `tool_calls`，
而消费侧 `verifyTraceCrossRow` 复算的是**同一个函数**——所以本套件对"reducer 本身是否正确"是**局部自证**，
不构成独立证明。reducer 的正确性由 `harness/tests/unit/hylyre-frozen-conformance.unit.test.ts`
用冻结包自带的 golden（valid / invalid-crossrow 全集）独立承担；**本 plan 不另造第二个 oracle**
（造了就是两份口径，正是 §7 要裁掉的东西）。本套件真正锁住的是：schema 校验、artifact/step 序列绑定、
版本链、evidence identity、P0 三方对账这些**跨模块接线**。

那是**估算，不是正例单独实测**，两次运行的冷热态差异也算在里面——记录时须如实标注为估算。
另外这个数**已经包含**真 harness 子进程、receipt 子进程（`goal-phase-runtime.ts:8393`）与 verifier 准备轮，
它们本身不单独计时：
```
cd harness && node -e "const{execSync}=require('child_process');const t=Date.now();
try{execSync('npm run test:unit -- --filter real-chain',{stdio:'pipe',encoding:'utf8'})}catch(e){console.log((e.stdout||'').slice(-4000))}
console.log('elapsed_ms',Date.now()-t)"
```
连测三次取中位数（首次含磁盘冷态）；同时记录全量 `npm test` 的前后差值，避免只看单套件。

**实测（2026-09-22，C2 第二笔；替代原 25–40 s 预估）**：`--filter real-chain` 连续两次
**63 385 ms / 63 117 ms**（`real-chain-seams` 尚未登记，故此数就是正例单独耗时，不是两套件合计）。
分解：provision ≈ 0.7 s；真 harness 单轮 ≈ 5–7 s；六阶段各 2 轮（第 1 轮 harness 才写出
`verifier_subject_id`，第 2 轮替身按该 subject 回填 verifier 报告后 `check-receipt` 才能闭环）。
**与既有最慢套件 `e2e-spec-requirement-closure`（118 966 ms）同量级且更快一半**，
远低于 §6.3 的 120 s 目标——正例这一半不构成发布门时长风险。
九条负例（C3）各自造工程但只重跑受影响阶段，两套件合计能否守住 120 s **待 C3 实测**，不预判。

**套件粒度（必改 6，已实读纠正）**：`--filter` 是**双语义**（`tests/utils/select-suites.ts:11–14`）——
命中 suite id 才只跑这些套件；否则回退 case-name 过滤并**跑全部套件**再筛显示（`run-unit.ts:448–449`）。
所以正负例放在同一个 `runAll()` 里按用例名过滤**一秒都不省**。

因此本 plan 从一开始就**按套件注册粒度拆两个**：
- `real-chain`：正例链（§4）
- `real-chain-seams`：RC-1 ~ RC-8（§5）

两个都登记进 `CORE_SUITES` 并标 `releaseOnly: true`：**进发布门，不进日常 `npm test`**。

**裁决已定（用户 2026-09-22，覆盖下列原规则）**：不再按"合计是否 ≤ 120 s"二选一，
两个套件一律 release-only。原文留档以便看清放弃了什么——
- 原 (a) 的代价分析（"追加一步会重复跑两遍""按名过滤会退化成跑全部套件"）**已被第三条路绕开**：
  跳过决策放在 `selectSuites` 里、发布入口传 `--release`，既不重复跑，也不丢
  "显式注册套件缺失即 FAIL"的保护（文件存在性仍对 release-only 套件生效）；
- 放弃的准确性：**日常改动不会立刻撞到真链回归**，反馈点从"每次 `npm test`"后移到"打包前"。
  这是用户明示接受的代价，不是本 plan 自行降级。

## 8. 风险与已知上限

先读 §1.1 的口径表；下列是它的风险面展开。

1. **整个作者调用是替身**（不只"产物是注入的"）。驱动 `:436–468` 返回 `fake-agent`，
   agent 的 argv/stdin 构造与真实响应全不在覆盖内。本链证明"合法材料能走通链"，
   证明不了"真实 agent 会产出合法材料"。宿主验收不可替代。
2. **UT 执行替身超出"工具链"**。照 `coverage-evidence.unit.test.ts:194` 先例，
   `checkUtFileNaming` / `checkUtFrameworkImport` / `checkTestRegistration` 也返定值——
   命名、框架导入、测试注册三项检查未覆盖。
3. **设备侧零覆盖**（机制按实跑更正，结论不变）。父进程读不到临时框架根里的 `test-chain`
   （`profile-loader.ts:24` `FRAMEWORK_DIR` 是模块常量 → `:199–205` 静默回落 `hmos-app`），于是
   `phaseRequiresDevice('ut'|'testing')` 为真、`goal-phase-runtime.ts:7197` 的设备门**确实进了**，
   门后是驱动注入的无条件 READY(physical) 桩。**"门没进"是错的，"没有任何设备覆盖"仍是对的**：
   设备发现、选择、就绪判定、身份传递一概未验。真机启动失败、hvigor 漂移、hylyre 协议变更、真 OCR 噪声
   同样不在覆盖内，不得被本链的绿色掩盖。
   此外 `device_test.build/install/run` 是本 plan 写的**可执行替身**：它们不编译、不装机、不操作设备，
   只产出下游要消费的三件事实（.hap 字节、装前摘要、native trace）。被真实覆盖的是
   trace→evidence→P0 五数→报告这条**消费链**，不是产生 trace 的那台设备。
4. **一条正例链是一条路径，不是矩阵**。九条负例是九个窄点，不冒充分支穷举。
   本 plan 的目标是"下一堵墙在框架内撞到"，不是"再也没有墙"。
5. **§3-N（junction 下子进程根检测）是最大单点风险**。若实验证明根检测解析回源仓，
   框架根造法要重选，可能被迫退回重法（整拷 harness + 资产、仅 junction `node_modules`，
   先例 `e2e-spec-requirement-closure.unit.test.ts:38–67`），直接冲击 §6.3 的时长预算。
   这是 T0 必须先办的原因。
6. **RC-6b 的精确诊断当前不存在**（`visual-diff-check.ts:1753` 丢掉 resolver 的 note）。
   本 plan 不在这里改生产行为，判据按 §5 的 (a)/(b) 二选一，选 (b) 时如实记"定位能力未验证"。
7. 运行时长可能超预算（§6.3 已给裁决规则，不预设）。
8. **日常 `npm test` 不再跑真链回归（用户 2026-09-22 裁决，见 §6.2）**。反馈点从"每次单测"
   后移到"打包前"：改了生产代码却没打包时，本链的红不会当场出现。
   作为补偿的最小保护有两条，都已落地并各有单测锁住：
   ① release-only 套件**仍参与"显式注册套件文件缺失即 FAIL"**（删文件照样红）；
   ② `release:all` / `candidate:build` 的 run-unit 调用**带 `--release`**（实跑取证见 §10.7）。
   **这不是"SKIP 出包"**：发布路径上它必跑且失败即挡包；被后移的只有日常反馈的时机。

**两个逃生口已删（必改 5）**：

- **不许"只推进到 testing"**。链必须跑到 **testing 的裁决与闭环**（真实 `check-testing` + 真实 `check-receipt`）。
  若 §3-M 实验证明 device/visual provider 不可替换，**本 plan 的这一段就是失败的**，要在 §10 如实写"未达成"
  并给替代方案，不得把目标降级成"链能推进到 testing"然后宣布绿。
- **不许 SKIP 出包**。`UnitCaseResult`（`run-unit.ts:26–30`）只有 `name`/`ok`/`error`，**没有阻断型 SKIP**；
  退出码只看失败数（`:490` `totalFail > 0 ? 1 : 0`）——所以"在摘要里报个 SKIP"照样出发布件。
  因此：**任一接缝不可用（含 `isJimpAvailable()` 为假、provider 加载失败、根检测异常）一律 FAIL**，
  不静默 `return`，不打 SKIP 标记。既有视觉套件的 `if (!isJimpAvailable()) return;` 范式**本链不照抄**。

### 10.1 T0 实验结论（2026-09-22，全部实跑取证，无一条推断）

**N（junction 下子进程根检测）——轻法失败，重法成立。这是本次最重要的结论。**

- **轻法（§3-F/§4.1 原定造法：`framework/harness` 用 junction 指回源仓）判定失败。** 实测：子进程里
  `require.resolve(<tmpFw>/harness/harness-runner.ts)` 返回 **`D:\1.code\agent-maison\harness\harness-runner.ts`**
  ——Node 默认对模块路径做 realpath，junction 被解开；`detectRepoLayout(__dirname)` 随之返回
  `{kind:'standalone', projectRoot:'D:\1.code\agent-maison', frameworkRoot:'D:\1.code\agent-maison'}`。
  生产 spawn（`goal-phase-runtime.ts` 的 `npx ts-node harness-runner.ts`，不传 `--project-root`，`cwd: harnessDir`）
  在这条造法下会**把 harness 跑在源仓上并往源仓写产物**。轻法作废，§6.3 的"轻法前提"随之作废。
- **重法（§3-F 备选、先例 `e2e-spec-requirement-closure.unit.test.ts:38–67`）实测成立**：
  复制 `harness/*.ts` + `tsconfig*` + `package.json` + 九个子目录（`scripts/schemas/templates/prompts/code-graph/framework/graph-extractor/state/trace`），
  **只** junction `harness/node_modules`；framework 资产（`skills/workflows/specs/templates/agents`）可继续 junction（其中无 `__dirname` 根检测）。
  实测 `detectRepoLayout` 从 harness 入口与 `scripts/` 两处都返回 `{kind:'consumer', projectRoot:<tmp>, frameworkRoot:<tmp>/framework}`，一致。
- **重法的成本远低于预期**：provision 实测 **153 ms**（纯 junction 版）/ **632–726 ms**（含整拷 `profiles/`，8.9 MB）。
  §3-F 说重法"是 119 s 那条套件的主成本"——**这句被证伪**，那 119 s 不在复制上，在它的多轮 ts-node 子进程上。
- **`profiles/` 取整拷而不是 junction**（比 §4.1 更保守）：`profiles/hmos-app/harness/*.ts` 普遍用
  `createRequire(path.resolve(__dirname,'../../../harness/harness-runner.ts'))`（如 `authoritative-ref-images.ts:21`、
  `structure-ledger.ts:29`、`image-toolkit.ts:18`）。若 profile 目录是 junction，这些模块会 realpath 回源仓并加载
  **源仓那份 harness 模块实例**——与入口那份形成两套模块级状态（正是 §3-I② 要写 `injectedVisualDiffOcrFn` 的那类状态）。整拷即无此裂缝，代价 ~0.5 s。

**P（新发现，plan 未列，属 N 的第二半）：框架根必须坐落在 goal 宿主根之下，即 `<hostRoot>/framework`。**
第一次 O 实验把框架根建在**独立**的 tmp 目录里，真 harness 子进程随即把 `projectRoot` 解析成**框架那个 tmp 根**
