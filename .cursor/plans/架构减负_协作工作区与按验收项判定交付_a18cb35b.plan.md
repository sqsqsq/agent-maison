## 二、改动后的正常执行路径

三项责任各有实际回答者。原用户消息与已受理的范围修订回答“AI 现在获准做什么”。验收条目、独立 review 与实际执行原件回答“最终成果满足了什么”。产物、输入与运行条件的绑定回答“原来的结论今天还能用在哪里”。会话时段和作者标签只在能够解释某项事实时使用。[总设计原则](../../docs/overview.md#121-四条总设计原则)

1. **接住原请求。** 从真实用户消息、明确引用的需求文件，或已经受理的 request／Goal 取得目标、边界、更正、排除项和终点。继续时用返回的原引用。另一个请求有自己的来源、报告及义务。用户授权不明时只搁置依赖这项授权的操作，继续可做的工作。只有确需用户决定的冲突才交还用户。
2. **承接现场，选本次工作。** AI 在首次选路前仍用七个公开标签说明判断与依据，按 §4.1 核当前来源。新请求可直接利用手头可读的需求和代码判档。特别简单走直接能力，小型走同一短蓝图和原 request，中型、复杂走正式设计准入与适用 CU，已有 Feature/run 续用其冻结范围。对已完成部分先验证。保留用户修正。待应用的补丁与当前字节冲突时，重读该处并合并。阅读与调研服务于眼前的决定。
3. **划清目标、依赖与写权。** 以用户绑定对象、AC／契约和实际实现定位目标。需求只点名行为时，由实现作者从既有蓝图、catalog、路由和验收定位业务入口，追到真正的调用方、注册、配置、资源及构建输入，由 review 复核遗漏。结构化 edit、Git 的新增／删除／重命名／未跟踪和 dirty 路径可帮助发现遗漏。浏览过的文件、目录里的 diff、影响本次结果的共享函数，都不会自动成为 AI 可写的对象。显式目标也不能排除实际依赖。无关路径留在现场，仅当有需求或依赖依据时计入这项工作。
4. **先核已有证据，再调工具。** 沿原请求及其报告目录，为原验收 ID 找到能回答该项问题的原件，按第五节核其现在能证明什么。阶段门禁指纹相同时，复用有效结论并执行仍缺的验收。升级导致指纹变化时，按第六节整段重跑。相关输入在执行中变化时保护旧报告，按最终字节复核受影响项。无关事件晚到时，也可结束当前工作。
5. **按原终点交付或继续。** 同一次判定给出已通过项、实际失败、必需欠验和用户明确排除项。每项欠验说明对应 ID、缺的原件或条件及下一步。只要求编译就可在编译结论收口。完整交付中剩一项必需 UI 行为，原单继续，只补这一项。回退、修订与重验均继承当前仍有效的工作和预算。[现有范围及依赖传播](../../harness/scripts/utils/execution-scope.ts#L732) · [公共完成处置](../../harness/scripts/utils/check-disposition.ts#L374)

**续作或新请求。** 以真实用户原话及其所指的交付对象作判据。已有 `--request-file`／`origin_request` 关联的原 user，或已受理的 Goal／Feature/run 绑定，能定位原任务。后续真实用户消息可以点名该任务，也可以通过原对话中唯一可辨的产物、验收项或失败结果指向它。例如，“刚才银行搜索仍区分大小写”可沿 AC-3 归回银行搜索。原生 parent/call 关系只把消息或工具接回对应的 user。若用户另给可独立验收的目标，例如“另外改卡片样式”，从该条真实 user 建新请求，仅继承仍有效、由用户明确授予的会话级控制。同一目录、相邻时间、AI 自述及固定口令均不授予续作或豁免。两个请求并行时，孤立的“继续”若无法唯一定位，先做归属已明确的工作，只在写入、豁免或范围更正必须据此决定时核清所指。历史回放沿已接受记录，新授权核新原话。[请求边界与 user 锚](../../harness/scripts/utils/request-intake.ts#L145) · [原 Goal 关联](../../harness/scripts/utils/delivery-origin.ts#L118) · [已受理控制](../../harness/scripts/utils/execution-scope.ts#L229)

**回退与重签。** AI 拟扩大写权或修改已签契约，先回原授权或设计责任方裁决。超出用户授权的操作须有真实用户的新指令。**验收、契约或蓝图无论谁改，原责任方都要拿当前字节对照原用户请求及已受理的更正重核。** 逐条核对目标、操作条件、预期行为和验收层级，确认承诺完整后由原 writer 签发新一代，再接受依赖它的交付。发现删项、降低预期或未经授权的豁免时，拒绝签发，列出原文、条目与差异。旧代保全，受影响的结论失效，其他工作继续。手改既无须回滚，也不使整单停机。

小型路径由现有 request review 承担当次重核，按原设计 request 传下的 `requested_result`（用户原话）和已受理的更正检查更改后的蓝图、验收和契约，沿原 writer 重签，无需另设独立设计质询或重签者。[原话进入专项 request](../../harness/scripts/utils/automatic-request.ts#L311)

人手写的代码即使超出原设计列出的文件或实现方案，只要影响本次交付，就随最终成果进入 review 与测试。对不上当前需求便如实报失败。另一需求的独立修改留在其原单。只有用户确实改变需求，才沿用户更正修订需求范围。[设计总则](../../docs/overview.md#121-四条总设计原则) · [冻结范围与修订](../../harness/scripts/utils/goal-run-creation.ts#L162)

从宿主 `framework/harness/` 进入时，直接编译沿 `npm run compile -- --project-root <宿主> --json`。小型请求沿 `npm run check -- --project-root <宿主> --phase testing --request-file <原设计request> --prepare-request` 看对应 AC，补齐所欠材料后沿同一入口去掉 `--prepare-request` 执行。正式运行用原 `goal-mode-entry --next` 返回的命令或 `goal-runner --resume` 续接其 run，正式 Feature 的回执用原 `--sync-closure` 收口。外部编辑或一次无关的工具失败不改变入口。[专项调用契约](../../docs/operations/request-harness.md#L17) · [正式入口](../../harness/scripts/goal-mode-entry.ts)

### 4.5 保留与裁剪

| 保留 | 裁剪 |
|---|---|
| 真实用户来源和操作授权，AI 可见文本中的七个判档标签、理由及当前可读的引用 | 以“继续原任务”口令认领授权、用此前成功读取作判档条件、按无关 edit/result 缺失拒绝整单 |
| 当前设计／实现、实际依赖、独立 review、验收条目和原生执行结果 | 将全树 diff 当本次工作、按目录推定作者、为普通交付核清每行归属 |
| 原责任方按原用户请求重核验收、契约和蓝图，通过后重新签发 | 用连续作者写链刷新冻结范围、把时段差异投影成回退或要求还原旧字节 |
| 当前项真正消费的输入、产物、运行条件与旧报告原件 | 用 HEAD、全树摘要、其他请求的改动使无关证据失效 |
| 公共完成判定、原目录兼容和终报的覆盖面披露 | 用过程诊断、未配对的无关调用或披露列表改变终态及身份 |

**不采用的补丁式方案**

- 首次 prepare 拍照或补存一份全树前像。该时点可能晚于用户动手。
- 新设逐文件的写前白名单。AI 的实际操作沿既有授权约束。
- 按调用内容分类 shell、猜测每条命令写了哪些文件。实际影响由产物和依赖核对。
- 给并行请求加工作区全局锁，或要求先切 worktree、stash。已有 run 与设备互斥只保护各自的真实资源。
- 新建作者登记表或逐行认领记录。必需验收由实际结果验证。
- 开独立补账路径，让作者事后补写 read/edit、手拼 call/result 或换目录清账。原单沿现有入口重核具体欠项。

## 五、怎样判断旧证据还能证明哪一项

**同一门禁指纹下，先定结论，再比输入。** 读原 request 的目标、蓝图验收 ID 或冻结 obligation，定位它的原始报告及规范化输入。检查该项预期、实际测试与注册、产品路径和依赖、使用的包、工具／设备条件，以及报告指向的执行原件。已有工具或用户提供的可验证原件可按相同口径使用。一段“跑绿了”的转述不足以回答这些问题。检查的是该项真正用到的字段。相同会话、相同目录、相同文件数、相同 HEAD 或同名 HAP 都不构成等价。

| 当前与原件的关系 | 在既有执行链做什么 |
|---|---|
| 只有时间、作者、读取轨迹、另一请求的文件或可重建说明变化 | 从原引用回读证据，仅重算当前报告／资格。并发任务新增、暂存或提交无关文件，不使本项过期。 |
| 本请求相关文件变了 | 作者查实际调用方、导出、蓝图／契约、测试和构建依赖，review 复核影响。共享筛选逻辑变更重验消费它的搜索或卡片行为。样式只影响显示时只核对应页面。动态路由、未知构建依赖无法排除影响时，复核最小的相关用例组、模块或实际包。不把“未知”当“无依赖”。删除、重命名与未跟踪文件照此处理。 |
| 一次执行覆盖多项，或运行期间输入变化 | 根据原 TC→AC/BD/NFR、步骤／断言及执行证据分别采信。一组原件只能证明整组时，以该组为最小单位，不拆造逐条 PASS。重读实际输入及产物核对首尾。前后不一致又无可核执行版本时，只保留对旧版本有效的历史结果。共享的整包输入真变，两项均依赖该包的结论可以同时过期。 |
| 唯一 result 缺失、错配、执行退出失败、条件不符或用户要求 fresh | 记录具体义务 ID、调用或原件、缺哪一侧和解除条件。已有等价的独立原件可补足。有较新真实失败就显示失败，不能往前挑旧 PASS。明确 fresh 时执行用户所指的范围。其余有效工作照常完成。 |

**留存 11/11 的适用范围。** 在原请求的原报告目录，用 `summary.evidence`、对应的 `request_ut_native`、执行键和冻结日志核对选中的用例／注册、实际执行数、适用的包与设备条件。与该结论无关的会话事件不改变这 11 项已有证明。同一门禁指纹下，业务输入、产物或运行条件确已变化时，按上表只重验相关项。[现有报告引用](../../harness/scripts/utils/report-generator.ts#L184) · [执行键与原件](../../profiles/hmos-app/harness/execution-key.ts#L252)

**范围取舍。** 零构建快路、跨目录承接旧报告移出本批。HMOS 沿原 provider 的构建顺序和原目录复用机制执行。若真机实测发现包不可复现导致复用失败，带原请求、构建输入、产物和运行记录另报另修。

## 七、最少的正反例

下列情景走公开入口，检查返回的具体结论、原件和实际调用。表内同组的一正一反共用原件，只改所列条件。

| 情景 | 必须观察到的结果 | 防止的漏判 |
