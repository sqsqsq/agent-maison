# 判定分级与失败传播收敛（宿主开卡回灌）

> 需求输入：2026-09-21 用户裁决「综合效率与准确率，允许影响较小的偏差；不是一点对不上就失败再重试」。
> 代码基线：main 44167ced（3.1.0）。上位与前序：[视觉证据闭环与失败恢复收敛](视觉证据闭环与失败恢复收敛_宿主开卡回灌_1f3d7a92.plan.md)、
> [失败归因与恢复效率收敛](失败归因与恢复效率收敛_宿主开卡回灌_c8b4e731.plan.md)、[阶段输入与证据归属修复](阶段输入与证据归属修复_宿主开卡回灌_6f2a9c41.plan.md)。
> 前两份修的是"谁产出证据、失败后怎么归因"；本份修的是"哪些检查配得上阻断，失败怎么只否定它真正否定的那一点"。

## 1. 核心原则与冻结范围

### 1.1 三档：只有第一档默认 fail-closed

每个检查先回答一个问题——**它保护的是什么**——再决定能不能阻断阶段。

| 档 | 保护对象 | 典型检查 | 默认处置 |
|---|---|---|---|
| 一 | **产品真值**：用户能不能完成核心操作、结果对不对、关键信息可不可读 | 测试/真机断言失败、视觉逐屏 `fail` 或 `must_fix`、review MAJOR、设计缺项 | **严格、阻断、回 owner**。不放宽。 |
| 二 | **账本与形状**：绑定、指纹、ID 同名、字段形状、来源追溯、新鲜度 | 参考图引用不可解析、facts 来源未绑定、UT 源码清单缺失、report subject 时间戳漂移 | 能确定性对齐的（同名、内容相等）**自动对齐**；对不齐的 **WARN 进既有披露渠道**（visual-debt / must_review），**不单独阻断阶段** |
| 三 | **能力缺口**：这台机器这一轮做不到 | OCR 不可用、参考图不可读、无性能采样原语、视觉采集未执行 | 沿用现成 `unsupported_gap`：**留分母、不算 PASS、带披露完成** |

一句话判别：**放过它，用户会不会拿到一个坏产品？** 会 → 一档。不会，只是我们的账本不好看 → 二档。不会，而且我们这轮根本测不了 → 三档。

### 1.2 判断顺序（四步，顺序不可交换）

1. **先判实际影响**：能否完成核心操作 / 结果是否正确 / 关键信息是否可读。
2. **再判证据是否足够**：已证实缺陷 / 疑似 / 无法测量。**辅助信号失败时，先看已有证据能不能覆盖同一目标**——四屏 VL 逐区域 `no_diff` 已覆盖"文本在不在、位置对不对"时，OCR 与原图对照缺席属于三档，不是整轮否定。
3. **再取最小动作**：只否定它真正否定的那一点，不扩散到同轮其它证据、不扩散到上游阶段。
4. **最后才重试**：重试必须有获得新结果的理由——针对性修复、输入变化、采集条件变化。报告时间、追加 notes、重写散文都不算。

### 1.3 冻结范围

**不做**：评分系统、豁免表、人工签字、状态机、manifest、注册表、次数闸；不撤动态工作流；不放宽第一档；不改宿主；不为 ref_id 对齐新增前置硬门禁，也不靠猜字符串（去掉 `_ref` 后缀）对齐。

**复用**（每条改动都点名既有机制，不新建平行通道）：`unsupported_gap`、`visual-debt.json` / `visual-debt.md`、`must_review`、`repair_candidates`、correction / 范围修订、`artifactsProgressed`、既有 `CheckResult → channel binding → summary → retry prompt` 链路。

本 plan 不重新实现 1f3d7a92 的聚合 identity 与 canonical overlay 映射，也不重新实现 c8b4e731 的 stale-summary 剥离与 detach 握手；只在它们之上改"档位"和"传播范围"。

### 3.1 辅助信号不得放大成整体否定（G13 先动，G11 / G14 随行）

**这是第一条、也是第一笔必须先落的一条。** `channel_evidence_usable` 现在的判据是"所有命中都 advisory"，等价于"只要有任何一条 WARN 没被 producer 显式标 advisory，整轮视觉证据作废"。这条判据保护的是"别拿没达标的结论绑 TC"，但它用的是**形状**（hit 列表干净）而不是**真值**（屏本身有没有问题）。

它不是一次性巧合：第三轮（`2026-09-20T18:44:00Z`）四屏 `pass=4 / fail=0 / must_fix=0`，`visual_diff` 详情里仍带着四屏的「参考原图缺失/不可读」降级行，整轮证据照样被判死。先修 G13，宿主当前的三个 BLOCKER 链就断；G11/G12 修的是"第一次为什么会发生"。

**判据换成逐屏、可从数据求值的条件**，不用 hit 列表形状。`channel_evidence_usable = true` 当且仅当对**每个 P0 屏**都成立：

1. **屏本身没问题**：`verdict !== 'fail'` 且 `must_fix` 为空（既有判据，保留）。
2. **采集确实完成**：该屏有 `evaluated_screenshot_hash`（既有字段，`visual-diff.json` 每屏都写）。
3. **该屏的目标被至少一路证据覆盖**：该屏**实际完成了文本 placement 核对**（新落盘字段 `placement_verified_screens` 含该屏 id），**或** 该屏有 `region_attest` 且其中存在 `vl_screening` 结论。

**第 3 条需要一个"核对确实跑完"的正面事实，现有四种表达都不行**：

| 候选表达 | 为什么不行 |
|---|---|
| 不在 `refUnavailable` / `ocrUnavailable` 里 | `collectTextPlacementSignals`（`visual-diff-ocr-gates.ts:345-348`）在 `screenTexts` 未命中（含 overlay 与 `ref_id` 两级回落）、去重后有效文本锚 < 2（每条去空白长度须 ≥ `MIN_ANCHOR_LEN`）、`screenshot_path` 为空时直接 `continue`，**两个集合都不登记**——"根本没核过"会被当成"核过没问题" |
| `placement.perScreen` 里有该屏条目 | **方向恰好反了**：`perScreen.push` 被 `:532` 的 `mustFix.length > 0 \|\| failSignals.length > 0 \|\| uncertain.length > 0` 门住，**核对成功、零异常的屏根本不在 perScreen 里**。用它判可用，等于"越干净越不可用" |
| `contentActionableMissing` 为空（代替第 2 条） | 它在熔断不合格（`fingerprintable=false`）时被清空，代表不了"采集完成" |
| hit 是否 advisory | 无 delegated 视觉 provider 时 `visual-diff-check.ts:2862-2872` 把 `visual_diff_region_attest` / `visual_diff_critic_receipt` 两类 hit **从列表删掉**（只删 hits，`visual-diff.json` 的 `region_attest` 数据仍在），"覆盖不上"在 hit 列表里没有落点 |

**而且 `placement` 在作用域上够不着判据**：它是 `visual-diff-check.ts:1748` 条件块内的局部变量，而 `channel_evidence_usable` 在 `:2886`，属于 `:2884` 那次 `const structuredPayload: VisualDiffStructuredPayload = {` 的**同一次对象初始化**——同一初始化里的属性不进入词法作用域，`:2886` 既看不到条件块里的 `placement`，也引用不了同对象的兄弟属性。

1. **返回结构增量**：`TextPlacementResult`（`visual-diff-ocr-gates.ts:161-173`）新增一个字段 `verifiedScreens: string[]`，与 `perScreen` **无关**——在 `:360` 之后、`:362` 之前登记该屏 id（`:358` 与 `:360` 两道 `continue` 已经过完，此时只证明 ref / shot 两次 OCR 都 `ok` 且 `words` 是数组，还没进 `clusterOcrLines`）。语义是"这屏的文本 placement 核对真的跑完了"，不管结果干不干净。

### 3.2 遮挡误报（G20，确定 bug）

`render-visibility.ts` 把布局树里每个面积占比 ≤ 25% 的 `Image` 节点都拿去测"区域内有没有前景结构"，`lumaStddev < 4` 即判"节点在、像素不可见"。半模态弹层盖住底页时，底页的 Image 节点仍在树里、bounds 仍有效，截图那块区域却是被遮住的纯色——7 处全部命中，全部是误报。

**不能用"被不透明容器完全包含"这条规则**：`layout-oracle-check.ts:32-40` 的 `LayoutNode` 只有 `bounds / type / text / id / key / clickable / children`，**没有背景色、透明度或 z-order**，这条规则没有数据来源。

改用现成信息——**overlay 屏的逻辑 id 本身就带着 overlay 根节点**（`card_type_sheet__overlay__cts_root` 的 `cts_root`）：

- **overlay 屏**：只在该根节点子树内做渲染可见性判定；子树外的节点按定义就是被弹层盖住的底页，不参与。
- **非 overlay 屏**：行为不变，全树判定。
- 被跳过的节点数计入既有 `unknowns` 如实披露（"未核 N 个 overlay 外节点"），不冒充已验。
- 顺带修一个既有缺陷：`unknowns` 现在**只在 PASS 分支打印**（`:159-165`），FAIL 分支（`:169+`）直接丢弃——两个分支都要报。

> **寻址必须走 slug 映射，不能直接匹配 `__overlay__`。** `render-visibility.ts:129` 的 `screen` 是从 **layout 文件名**取的（`lf.replace(/^layout-/, '')`），而文件名 slug 经 `sanitizeVisualDiffScreenSlug`（`visual-diff-capture.ts:247-256`）把 `[^a-zA-Z0-9_-]+` 换 `_` 后再把 `_+` 压成单个 `_`——宿主实际文件名是 `layout-card_type_sheet_overlay_cts_root.json`（单下划线），`script-report.json` 里七处报告用的也是 `card_type_sheet_overlay_cts_root`。按 `__overlay__` 匹配**会漏掉本次全部目标**。
> 改法：复用 `visual-diff.json` 的逻辑 `screen_id` 与既有 slug 寻址（`layoutDumpCanonicalFileName` / `sanitizeVisualDiffScreenSlug`）建立「文件名 slug → 逻辑 id → overlay 根 id」映射，不新造命名规则、不改 slug 算法。
> **该映射只在 slug 唯一时成立。** 多个逻辑 `screen_id` 归一到同一 slug 时**不得任选一个**——这种冲突已有真实 fail-closed：`visual-diff-capture.ts:1072-1080` 在采集开始前检测归一冲突，**冲突双方全部**记 P0 采集失败并跳过（不写、不猜），所以冲突屏本就没有 layout dump 可读。本 plan 只消费这个既有保证，**不在 render-visibility 侧新加冲突处理，也不放宽它**；万一读侧真遇到一 slug 对多逻辑 id，按 `unknowns` 如实披露、不判定。

### 3.3 诊断不丢失、失败回 owner（G12 / G28 / G31）

### 3.4 账本类降级：自动对齐优先，对不齐只披露（G01 / G02 / G04 / G10 / G15–G17 / G30）

统一口径：**能确定性对齐的自动对齐，对不齐的 WARN 进既有披露渠道，不单独阻断阶段。**

「确定性」的边界**必须写死为：身份明确 + 内容指纹相等**。**同名不能证明内容等价**——`readBoundInput`（`capability-resolution.ts:500-512`）本来就同时核依赖与 `content_fingerprint`，`:620-626` 更是拿整个 binding 与 `expected_bindings` 全等比较，这是保护已冻结输入的。一个改了条件的 `acceptance.yaml` 仍然叫 `acceptance.yaml`，自动换绑就等于把修订悄悄吞掉。

- **G01 facts 来源未绑定**：声明的来源路径在项目内且可读 → 按既有 `dependency()` **补登记**（只加登记，不改任何已绑定内容）；路径不在项目内或不可读 → WARN 进 `must_review`，不再产出 BLOCKER。
- **G02 facts 基线漂移 / G04 input binding stale**：
  - 只改"抛异常"这一点——改成出 `CheckResult`，让 runner 拿到本轮结构化结果（异常出口的"本次执行失败"语义保持 c8b4e731 已建立的形状，不回退）。
  - **身份明确且 `content_fingerprint` 相等** → 沿既有 `recomputeDefinitionFacts` 自动重算对齐。
  - **指纹不等**（内容真变了）→ 走既有 correction / 重验路径回责任方，**不自动换绑、不降 WARN、不当账本项放过**。
- **G10 verifier subject 时间戳漂移**：`generated_at` 一类纯时间戳字段不进 verifier material 的指纹计算，改用内容规范化后的指纹。**规范化后指纹仍不等 = 实质变化**，照旧作废并重验；只有"纯时间戳变、内容不变"才自动对齐。
- **G15–G17 P0 分母**：`testing_channel_evidence_obligation` 与两个 `p0_*` 共用同一逐 TC 裁决（1f3d7a92 批次 A 已建立的单次计算），本 plan 只改**分类去向**——证据不可消费的原因属三档时计入 `unsupported_gap`（留分母、不算 PASS、带披露完成），属一档（真实 fail / must_fix）时才计 `failed`。`gapCaseIds` / `gapAcIds` 语义不变，不伪造 native trace，不删 P0 分母。
- **G30 `visual_acceptance_present`**（**已从二档移出**）：改用既有 ui-spec 解析器判"在场且可读"。不可读不是账本项——它让 `pixel_1to1` 的视觉义务定义悬空，`execution-scope.ts:372-385` 已有对应出口 `acceptance-definition:visual`（`applicability: unknown`，spec 可执行去填）。**沿既有 definition-gap 路径，不承诺只 WARN**。

`visual-debt.json` 与 `must_review` 都是既有渠道，本 plan 不加新渠道、不加新 schema 字段。

### 3.6 重试必须有获得新结果的理由（G27）

`shouldHaltNoProgress` 对 `code_regression` 要求 `relevantEvidenceKnown === true && comparableContentBaseline` —— **这条保留，它是对的**（plan 1f3d7a92 §3.3：相关集合未知时不得用空快照冒充"无改动"）。本 plan 改的不是这个条件，而是**条件不满足时的出路**。

把同签名重复拆成两种情形：

| 情形 | 含义 | 出路 |
|---|---|---|
| 相关集合**已知且实际变化** | 有可修目标，而且真的改了 | **有重试资格**，继续（`artifactsProgressed` 已有判据：只认存在性与 `contentHash` 变化，本来就忽略 mtime） |
| 相关集合**已知但零变化** | 有可修目标，但没改 | 既有 no-progress 熔断，第二次即停（现状正确） |
| 相关集合**未知或为空**（无 repair candidate、无 blocker `affected_files`） | **没解析出可修目标 = 本阶段无路可走**（注意：这**不等于**"证明了没修"） | 沿**既有 `no_progress_guard`**（`goal-phase-runtime.ts:8968`）停下并交回，理由写「相关目标未知」；**不该**烧满 `max_retries_per_phase` 再判 `content_retry_exhausted` |

第三行就是宿主的实际形态：`a70eb7` 修完两轮产品缺陷后 testing 仍连续 3 次（i12/i13/i14）同签名失败、`f829b8` 3 次同签名失败，signature 逐字相同、产物零变化、相关集合为空，却各自烧满重试预算才以 `content_retry_exhausted` 收场——而这个终态理由（"内容重试耗尽"）把一个账本问题描述成了内容问题。

**这一条明确覆盖 1f3d7a92 §3.3（plan 文件第 116 行附近）的"相关集合未知时退回既有 `max_retries_per_phase` 有界重试/耗尽语义"。** 理由：那条裁决要保护的是"不得用空快照冒充无改动"——这个保护本 plan 完整保留（判据一个字不动）。它顺带选择的**出路**（继续烧满重试）在宿主实测里没有产生过任何价值：8 次同签名重复零进展，而且最终给出的终态理由是错的。改成"沿既有 `no_progress_guard` 停下并说明相关目标未知"既不削弱那个保护，又让终态理由变准确。

> **措辞守住一条线**：`extractContentRelatedFiles`（`goal-failure-classifier.ts:399-404`）的集合**只来自 `repair_candidates[].files` 与 `blockers[].affected_files`**，空集只说明"没解析出目标"，**不能被说成"证明了没修"**——plan 正文与实现里的提示文案都必须是「相关目标未知」，不是「未做修复尝试」。
> **不新增 runner 终态**：走既有 `no_progress_guard` 分支，**不把 `no_fix_attempt` 扩成新的 halt reason**，不动 `adjudication` 注册表。

同时按 §3.5 的责任文件集让相关集合**尽量已知**：blocker `affected_files` ∪ `repair_candidates[].files` ∪ 责任阶段产物。注意 `artifactsProgressed`（`goal-failure-classifier.ts:726-741`）比较的是快照里**同一相对路径的 `exists` 与 `contentHash`**——它天然忽略 mtime，但也只看得见被 watch 进快照的路径，所以相关集合的准确性直接决定它的有效性。报告时间、追加 notes、重写散文一律不算新事实。

> **放弃的准确性**：相关集合为空时改判"无路可走"而非继续重试，代价是放弃了"盲改也许能撞对"的那条路。三轮宿主实测里这条路一次都没走通，但它在原理上确实存在；P3-T11 必须锁住"相关集合已知且真实修复后仍可继续"，避免这条收紧变成对真实修复的误停。
