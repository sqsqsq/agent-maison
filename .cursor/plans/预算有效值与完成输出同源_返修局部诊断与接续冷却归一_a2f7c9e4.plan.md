## 3. 设计

### 3.1 本周期有效预算（t1）

- **数值来源**：预算数值只取现有 manifest 里的 `budget`（整个 `Required<GoalBudget>` 对象，轮次与活跃时长同口径）。事件不存数值，只证明授权：
  run R 的基线预算摘要按事件顺序取 `run_created.manifest_identity_fields.budget`，其后每条 `manifest_identity_rebase.to_fields.budget` 前进（与既有 `budgetEditedSinceBaseline`，goal-run-creation.ts:741-754 同一口径）；
  该摘要的授权时刻 = 使 R 的预算摘要最后一次变成该值的那条事件的 ts（model 替代型号写的 rebase 不改预算摘要，不移动时刻）。当前 `manifest.budget` 摘要与基线不等 = 未授权改动——
  它不能成为有效值，但**授权摘要仍按事件算数**，不因此被剔除（见下方"解析"情形 3）。
- **本次 override 在后继出生前如何生效**：本次调用带 `--override-manifest` 时，承接目标（`argv.supersede` / `continuation.targets`）中预算摘要偏离基线的 run，其当前 `manifest.budget`
  视为本次授权，授权时刻 = 本次出生；多个时取最后一个事件最晚的那个。不给前驱补写事件；授权的审计载体是后继自己的 `run_created.manifest_identity_fields.budget`（出生即基线）与出生日志一行。
- **周期边界**：不用 `deliveryCycleView.lastCompleted`。复用预算折叠的边界：把 goal-phase-runtime.ts:6063-6078 的计算（`assessFeatureCompletion(...).record` 为 ok 时取 `record.run_id`，
  经 `foldBudgetLineage(...).cycleBoundary` 只在落入本次血缘时生效）提成一处函数，出生段与预算段共用，算法不变。本周期的预算历史 = 该次折叠的 `ancestorRuns`（已剔除 {B} ∪ 祖先(B)）的事件，加上一条的本次授权候选。
- **解析**（新增 `resolveCycleEffectiveBudget`，名称实施时定，放 goal-run-creation.ts 或 goal-runner-phase.ts）分两种情形，不取最大值、不按"剔除后剩下谁"回退：
  1. **真正的新周期**：边界截断后的 `ancestorRuns` 为空、且没有本次授权候选——本周期没有任何历史预算，取本次出生输入的预算：传给 `inheritSuccessorManifest` 的那份 manifest
     在 `buildGoalManifestFromInput` → `mergeBudget`（goal-manifest.ts:371-375、751）得到的值，即 `--manifest` 显式给的预算，否则 `DEFAULT_BUDGET`（:188-193）。
  2. **本周期已有授权历史**：先只看事件，确定本周期**最新的授权预算摘要** D——本次授权候选存在时 D 取它的摘要（授权时刻 = 本次出生，最新）；否则在 `ancestorRuns` 全部事件里取
     使预算摘要发生变化的最后一条（`run_created.manifest_identity_fields.budget` 或 budget 摘要变化的 `manifest_identity_rebase.to_fields.budget`，按 ts，同 ts 按 run 内顺序）。
     再在现有数值里找摘要等于 D 的那份作为有效值：候选数值 = 本周期各 run 当前 `manifest.budget`、合同来源 manifest 的 budget、本次出生输入的 budget，逐个算 `manifestIdentityFieldDigest` 比对。
     摘要相等即证明数值就是被授权的那份，来源是哪个文件无关紧要。
  3. **找不到匹配数值**（本周期已有授权预算，但数值因未授权改动无法核验）：不出生后继，也不回退默认值或较旧的授权值。复用既有出生失败路径——runtime 在后继 manifest 构造块内抛出，
     走 goal-phase-runtime.ts:5333-5342 的 `[goal-runner] BLOCKER: 无法构造 supersede 后继 manifest`（发生在加锁、写 manifest、写事件之前，不产生 run）；prepare-run 在 goal-mode-entry.ts:156 前同样抛出、不建 run。
     指引给两条既有出路：要采用改过的预算，带 `--override-manifest` 重新发起（改动随即成为本次授权候选，回到情形 2）；否则把 manifest.budget 还原为已授权值再发起。不新增停机原因（启动前抛出，不产生 halt_reason）、不新增账本或协议。
  现有检查兜不住这一处，所以必须在解析里拦：需求增量在结构终局上允许起后继（goal-run-creation.ts:893-897），来源 run 出生记录检查 `validateRunCreatedEvent`（goal-run-creation.ts:1076）不核当前 budget 与基线是否一致，
  supersede 目标身份检查（goal-phase-runtime.ts:6729-6735）只核 `run_id`。
- **消费点**：只有两处后继出生点改用它——runtime `manifest = inheritSuccessorManifest(...)`（goal-phase-runtime.ts:5332）之后、有人在场 prepare-run（goal-mode-entry.ts:156-161）之后，覆盖 `manifest.budget`。
  其余字段仍由合同来源提供。运行期上限、启动预算打印、progress（goal-phase-runtime.ts:7050、7279、9694；goal-runner-phase.ts:945；goal-progress.ts:1038）不改：
  出生规则保证后继快照等于有效值，resume 时的身份漂移授权（`resolveManifestDriftDecision`，goal-phase-runtime.ts:3636 起）保证运行中快照仍是已授权值，于是"读本 run 快照"与"读有效值"同值。manifest 不改 schema。
- **反例**：①授权 42 后再起后继（追加 + 真实需求变化）→ 后继上限 42，再起一次仍 42；②无 override 的手改 → 不生效（结构终局保持停止 / 显式 resume 被漂移检测停下，均为既有行为）；
  ③上一次可信完成之后的新周期 → 首个后继取出生输入预算，不带上一周期追加；④边界算不出（评估不可算）时与消耗同口径按全血缘取值；
  ⑤本周期唯一 run 授权上限 10 已耗尽，manifest 被手改成 99，随后提交真实需求增量、不带 override → D = 10 的摘要；候选数值（该 run 的 99、合同来源的值、出生输入的 30）只有恰好等于 10 的才匹配，
  通常无匹配，出生失败停下并指引 override / 还原，不取默认 30（不会凭空多出 20 次）；
  ⑥旧 run 授权 42、最新授权降到 20，最新 manifest 被手改成 50 后提交需求增量、不带 override → D = 20 的摘要，42 与 50 都不匹配，不会重新选中 42；无匹配即停下，同⑤。
- **放弃的准确性**：①新周期不再继承来源 run 的预算快照，原先靠首次 `--manifest` 设定、从未改过的 feature 级预算在新周期需重新给出（MIGRATION 写明）；
  ②本次 `--override-manifest` 是整体授权（`overrideAuthorizedIdentityFields` 返回 `all`），承接目标上的任何预算改动都随之被授权；③本 plan 之前出生、已继承旧值的后继不追溯修正；
  ④未授权改动的值（调高或调低）都不会被采用；只有现有数值里找不到 D 对应的那份时才停下要求授权或还原——例如当前 manifest 从授权 20 手改成 10、而另一候选仍保存 20，按解析规则采用授权的 20，不停止；
  代价是未授权的调低不会静默生效（要生效须带 override 授权）。
