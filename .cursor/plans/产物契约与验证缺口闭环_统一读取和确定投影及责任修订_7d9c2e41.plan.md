## 4. 三条主线

### 4.1 输入契约同源

唯一内容入口拟为 harness/scripts/utils/artifact-content.ts 的 resolveArtifactContent，作为既有解析链的公共纯函数，调用原 artifact inventory/schema 和可复用字段判据；不另建 inventory、schema 注册表或版本真源。输入为 artifact id、原始 unknown 内容及片段/完整上下文，输出规范值和沿用 path/message 的问题列表。来源身份、哈希、权限与责任保持在原调用层；函数不写磁盘、不发布、不自行授权。该模块保持叶子依赖，不 import SpecLoader、capability-resolution 或 check-*；acceptance/contracts/use-cases 在 SpecLoader 汇合处理一次，外层复用结果，不为同份内容重复校验。t1 点名核对 checkUseCaseSpecSchema 与蓝图派生对它的调用，分离重复形状规则和仍需保留的语义规则。

1. 格式只保留一份字段定义，语义、实现存在性和验收保留原检查。Schema 只约束消费者需要的结构，不默认禁止所有扩展字段，不要求模型填无意义空集合。
2. 已有 UI-Spec schema、参考元素解析和其它真实字段定义按可执行能力复用。现有 validateLiteSchema 仅支持本地引用，实施不得直接写无效跨文件引用；可用现有模块装配定义后送原校验器，不引入通用远程 schema 框架。Schema 自身不支持/损坏归框架问题，不退给产物作者改业务数据。
3. 规范化先于按规范类型消费；格式允许的两种原始写法在权威对齐中也比较同一规范值。只在内存变换，不就地改蓝图/CU、重签摘要或伪造旧冻结绑定。绑定/缓存沿既有依赖与恢复规则处理。
4. 蓝图片段不要求 feature/source 等派生身份，不逐片要求整份用例版本/全量必填；合并完再检查完整性。缺失、冲突保留实际路径和原来源，经既有设计 owner 修订；普通阶段产物则按 Skill produces 和共享责任契约找原 owner，不能默认当前阶段。
5. 无歧义格式整理不调用模型；不能整理的通过现有 capability invalid / shape_issues / 设计内容问题携带字段路径、实际形状、最小合法示例及责任线索。必须真实贯通“发现→责任方修好→重读通过→继续”，不能只增加一个更早的拒绝。
6. SpecLoader 和各消费者原有手工形状判断，在同一责任被公共入口接住后才删除；业务语义检查、输入路径合法性、冲突诊断、框架故障诊断不能一并删除。直接调用的公开消费者也必须从该边界得到规范值，不能只靠 TypeScript 断言。

**calls 的本批语义**：外部输入兼容非空字符串或非空字符串列表，内部统一为有序列表；每个列表项必须是非空命名函数引用，按声明顺序保留，包括重复调用。存在的 user_action 不允许空 calls；纯展示 UI 可保持空 user_actions。逐项核对和生成追溯，不取首项、不逗号拼接、不按名称猜参数/接收者、不将数字或字典转成字符串。coordinator、ui、trigger 等单值字段仍按其单值定义，错误形状明确反馈，不全局套“单元素列表都变标量”。

@1 的旧合法字符串继续可读，不新增必填身份字段；内部类型调整覆盖所有消费点。既有别名 expected_boundary_calls 的兼容归一与冲突反馈收进同一路径，不能因为统一而丢失。字段定义与写作示例同源，文档说明业务含义而非另抄一套相反形状。

t1 同时核对输入指纹按原值还是规范值计算：纯内存表示变化不应被当成需求/权威变化。旧合法字符串的绑定沿既有身份中立与兼容读取保留等价性，规范化前后的原件不改写；若旧绑定无法证明等价，按已有恢复重验，不伪造哈希放行。真实内容或检查规则变化仍应触发相应复验，不能为了兼容跳过。

### 4.2 验证缺口如实处置

共享执行包装拟为 harness/scripts/utils/check-execution.ts；只收编现有 safeRun，不另建检查注册表。必需性来自已加载的规则、能力适用性和原调用点明确的执行要求，不能由 JavaScript Error 的类名决定。动态检查原来在调用点确定的严重级别显式传递，不再另登记一次。

| 情况 | 原有表达与处置 |
|---|---|
| 已确认不适用 | 保留 SKIP + not_applicable；不制造验证缺口 |
| 数据内容不能按契约解释 | 走 §4.1 的具体输入问题及责任恢复，不依靠 catch 推断产物有错 |
| 适用检查抛异常，未形成有效结论 | SKIP，保留原必需性、source、failure_kind=framework_bug、blocking_class=framework_internal、actionability=framework_blocked 及栈；文案明确“未执行/结论未知”，不是产品 FAIL |
| 仅有必需检查执行缺口 | 阶段 INCOMPLETE / open，进入既有 deferred 与依赖判断；不能给 Agent 内容重试、也不由 verifier 代签缺失脚本结果 |
| 执行缺口与真实产品 FAIL 混在一起 | 真实 FAIL 保留，可信候选仍送责任方；缺口不吞掉产品问题，也不把产品失败降成外部延迟 |
| 仅非必需检查无法完成 | 如实披露，沿原义务/处置规则决定是否影响完成；不把所有异常都升成硬门禁 |
| 根本无法形成可信报告、身份/写保护或硬预算故障 | 保留原硬边界和停机行为，不纳入“某项 checker 未完成”的延迟范围 |

沿 check-disposition 的有效判定入口补“必需但未执行”的判断，使 report、summary 的 blocking_skips、verifier 资格、阶段闭环和 Feature 完成使用同一结论。**仅返回 SKIP 而不接这些消费者不算完成**；完成/发布不能通过缺少必需证据的阶段。不得再让 testing 的异常降为 MINOR 后悄悄放行，也不把 disclosed 过程项异常升级为产品缺陷。

必须点名替换的消费者：report-generator.resolveVerdictFromChecks 当前只统计阻断 FAIL；harness-runner.decideNextAction 对 blocking_skips 给出 resolve_blocking_skips_then_rerun；goal-phase-runtime 的 framework_bug && verdict !== PASS 分支直接首停。这三处与完成判定必须消费同一个缺口谓词，不能一处叫等待、另一处要求 Agent 改内容重试，也不能漏掉原首停分支。旧历史记录的真实 framework_bug 原因保留，恢复动作按新政策及实际依赖重评。

调度复用 c2 的真实依赖（workflow requires / control_edges / 实际输入来源）和有效义务队列：

- 同阶段可独立检查继续收集，现有行为保留。
- 跨阶段先判断受影响的输入/前置；当前已知依赖粒度只能证明整阶段受影响时保守按该前置等待，不发明检查级依赖图，也不猜“应该不影响”。
- 有现成依据证明独立的授权工作可执行，保留原阶段未完成义务后继续；无可执行工作时按原 WAITING/external 停放，原因仍用已登记的 framework_bug，说明缺哪项验证和维护责任方，不称产品不合格。
- 不能复用 runtime 当前“defer 后直接 phaseIdx++”作为完成实现；选择下一可执行项前必须调用同一依赖判断，避免启动下游再被 upstream gate 拦回。现场 coding 有缺口时，不预先承诺 UT/testing 一定可启动。
- 停放期间不盲目重跑同一异常，不新增轮询常驻进程；重新发起同一请求时沿既有 continuation/resume、post-agent 重验和证据新鲜度判断恢复。新旧进程都保留未完成义务和累计预算。
- 不承诺只重跑某一个 check：修后按产物、检查实现和依赖变化决定受影响的阶段验证；只要需要，重跑该阶段脚本及其真实受影响下游，保留无关的有效模型产出/编译/测试结果。不新建 check-filter 执行协议。

### 4.3 确定投影先由机器提供

复用 materializeBlueprintSkillInputs 的派生内核、冲突检查与写出回滚。增加的是**在合法阶段准备入口的接线与现有 writer 的责任范围收窄**，不再造第二个投影 writer：
