## 1. 目标、责任与两份 plan 的边界

本 plan 修“数据为什么错”：什么是阶段要读的输入、什么是允许修改的文件、什么是历史研究观察、什么是本阶段或后继阶段的产出。

- plan 尚未产出写集时，仍能使用本次已核实的 Research 源码。

- UT 修改其负责的测试不使 coding 误过期；真实需求、契约和产品源码变更仍由相应责任方复核。
- 无 run 的受管路径能消费原始需求与参考图，不靠隐式借用其他 run。
- 所有修正同时覆盖 Goal 与无 run 的公共入口；独立 request、旧 run 与消费者 framework 只读边界不被破坏。

## 3. 最小实现方案

### 3.1 读取目标与写集解耦：修共享生产链，不改义务含义

改动主落点是 capability-resolution-entry-input.ts 和 capability-resolution.ts；feature-track.ts 只负责必要来源透传，不把“有读取需求”改成 implementation 义务。

调用内按用途区分三个集合：
- 源码读取目标：当前阶段确需读取的生产源码及必要上下文。
- 测试目标：实际待执行/编写的测试文件，由已有 profile 路径约定和 UT target resolver 解释。
- 写入许可：继续由有效 CU/contracts、阶段 produces、profile 写边界决定。

这些是同一次调用的内存投影，不新增持久清单或权限层。已有 InputBinding、source_refs、ResolutionDependency 是绑定载体；不得把读取路径自动写回 contracts.files。

来源顺序：
1. 独立 request 使用既有 targets.files / targets.tests，保持明确读写边界。
2. 已有 Feature/CU 设计使用已绑定 contracts/CU 的声明文件引用，配合本阶段 inputs/produces 和 profile 测试路径解释；不要求本轮包含 coding。先分开“必须读取的既有文件”和“有合法 owner 的待创建产出”，不能把整个写集当成全部已经存在的输入。
3. 尚无写集的设计/研究阶段，承接本次合法 facts 中真实读取的 source_code_paths/phase_delta，机器校验并绑定实际字节；不从“写集不存在”推断“无源码可读”。
4. 没有任何合法来源时保持 absent/invalid，交回既有来源责任方；禁止全仓扫描兜底、借用其他 Feature 或拿 impact-basis 自动补洞。

**新文件与 plan→coding 交接（F13/F14，必须修）**：
- 有效契约明确由 coding/后继阶段创建的新页面、组件、测试文件，当前缺失只表示待产出；保留授权路径与 owner，不读不存在字节、不伪造内容哈希，也不让它拖垮同组已存在源码。
- 不能简单 filter(exists) 忽略所有缺文件：原来要求读取的文件缺失、已绑定输入消失、路径越界仍是 absent/invalid；后续生产者应生成的文件未生成，仍由原有文件完整性门禁判失败。
- 写入授权来自有效契约及其目标路径，不以“源码文件已经创建”作为获得创建权限的前置条件。新文件从 planned 到实际存在沿当前产出绑定流程转换。
- plan 形成新 contracts 后，既有修订提案须同时刷新 implementation 义务的来源与后继实际读取目标，不能只更新 design-context 就留下 basis=[]。只更新受该新设计事实影响的义务；不增加未授权模块、不改 frozen manifest。
- P1-T12 通过生产入口跑“plan 起步→写出含既有文件及待创建文件的契约→范围修订→coding 创建文件→UT 读取”；不预先创建新页面来迎合旧 resolver。

对现有 testTargets 一字段承载两种 derive 的问题，优先复用现有绑定中 input/source 的区分；如果解析器调用参数确实无法表达，允许仅在现有调用类型增加一个可选 codeTargets 参数，与 testTargets 分责，旧调用仍保持原兼容分支。不批量重命名，不新增文件或 schema 家族。正例必须走真实入口，不能在测试里直接注入这个参数代替生产接线。

### 3.2 Research 与 facts：建立时就产生下游可消费的绑定

复用 parseContextExploration、assertFactsSourceReadable、项目内路径校验和 readBoundInput；同一输入解析结果供 checker、facts 与 evidence 消费。

- 首个真实阶段允许登记本次研究过、存在且可读的项目内文件，含必要只读 module.json5；不因文件不在 coding 写集而拒绝读取或授予写权限。
- 核验当前 subject、建立资格和已有 baseline；不能把其他 run/Feature 的 facts 原样冒充当前输入。
- 首阶段接受的 Research 声明必须成为实际绑定的观察来源，或给出明确缺口；不能上游 PASS、下游才发现“声明过但从未绑定”。
- 后续阶段追加自己的 delta，复用已建立且适用的事实；不靠修改 established_by、清空 source_code_paths 或重造 facts 来修基线。
- 路径校验覆盖真实路径越界、不可读/缺失、重复引用与不同 profile 测试目录；不新增全仓目录扫描。

该步骤和 §3.3 一起决定 Research 来源的生命周期：绑定历史读取事实，不等于要求它经过合法后续施工后仍与原字节相同。

### 3.3 证据生命周期：输入、观察与产出按既有 owner 解释

在既有入口和 evidence/facts 消费链共用同一个归属判据。优先复用 phase contract inputs/produces、有效 scope 的 owner、已绑定契约和 profile 路径约定；不要在 coding、review、ut 三处分别复制路径正则。

| 情形 | 正确行为 | 必须保留的反例 |
|---|---|---|
| plan 研究旧源码，coding 按有效写集实现 | 保留历史 Research 依据，由 coding 当前产出承接新的源码事实；不强迫 plan 因预期实现变化反复重签 | 无法归属于已授权施工的上游输入变化，仍报失效/复核需求 |
| contracts.files 同时列生产文件与 UT 文件 | 根据生产者/消费者职责投影，不能不加区分地将全表记成 coding 的不可变输入 | 不能把所有源码或所有测试从证据中全局排除 |
| UT 修改本阶段测试和注册入口 | UT 更新自身证据；不仅因该修改使 coding 失效 | UT 改了产品源码，仍触发源码变更检查与必要 coding/review 复核 |
| 需求、接口或真实设计契约改变 | 回实际 owner 更新，并对受影响消费者重验 | 不以“这是本轮输出”为由豁免需求/契约漂移 |
| 声明来源未变、只追加合法 phase_delta | 保留有效基线，按现有 phase projection 比较 | 改写建立事实的实质内容不能被当普通追加 |
| harness 重写相同覆盖结论的 ac-coverage.json | 相同语义保持文件字节与 verifier 审核对象编号（subject_id）稳定，不因 generated_at 换代 | 真实覆盖内容、用例、规则或其他审查输入变化，仍改变材料身份并按原规则处理 |

实现时先检查当前证据生产集合，再核对 recomputePhaseEvidenceStaleness 与 facts baseline 的消费口径，避免只修一个方向。
历史观察不承担当下内容真值；当前内容真值仍由实际负责它的阶段证据验证。不创建新的“观察登记表”。

**覆盖率回执稳定性（F15/F16）**：优先在 ac-coverage-report.ts 的单一生产/写入点做幂等处理：除生成时间外的真实覆盖内容相同，则保留已有内容及其 generated_at，不重复改写；变化时正常生成新内容和时间。本次实际执行时刻继续由原有 trace/执行日志记录，不把 generated_at 冒充每次运行的时间。

不另建 verifier hash 体系、不全局忽略所有 generated_at，也不把 ac-coverage.json 从全部证据面删除。核对内存 report 与落盘内容的消费者，避免 writer 保留旧字节、同轮 prompt 却读新时间。P1-T11 必须连续运行真实 UT harness 两次（外部设备执行可走原有测试接缝），第二次模拟 runner 收尾复跑：相同产物、检查状态和配置下 subject_id 不变，已有匹配报告仍可用；改真实覆盖条目或被审代码时编号应变化。受控注入时钟即可，不为测试睡眠。

已有错误生成的现代证据不得就地改哈希或假装 fresh。用现有重验/闭环路径重新产生受影响证据一次；旧 run 缺少足够归属依据时给出范围明确的恢复提示，不批量重写全部历史证据。

### 3.4 无 run 的需求输入与本阶段产出修订

原始需求：
- 保留 resolveRequirementInput 的 text/sources，而不是只保留内容指纹；原始正文、requested_results 和验收产物是不同语义。
- 文件型需求优先复用 requirement_basis 的 source_refs/dependencies 指向原始来源，沿既有绑定校验后读取，参考图继续走同一来源发现函数。
- 对没有可恢复来源的 inline 需求，最小方案是在现有 harness 命令接入 --requirement / --requirement-file 参数并透传同一解析函数；无 run 调用将正文与已冻结候选绑定核对。由 agent 传参，不增加用户仪式。
- 不新建需求快照文件或第二份正文真源；不以当前 spec、requested_results、其他 run 的文本猜回原始输入。已有 Goal 路径仍以 manifest 为准，冲突参数不得覆盖它。
- 新来源 metadata 的比较及旧候选兼容使用既有 binding/fingerprint 规则：不无条件改变旧 manifest 哈希，不为了兼容静默接受变更后的需求。旧无 run 候选若无可恢复正文，报告需要显式原始输入，而非“安装 SDK”。

spec 修改 acceptance（已确认修复项，不再仅作待判断线索）：
1. 真实时序为：候选生成后 spec 落盘验收，首次 harness 调用在验收已在场时冻结，spec 根据检查结果修改验收，再调用 harness。冻结在函数调用时发生；“一定晚于 spec 写盘”不是所有合法调用的代码保证，只是本次事故需复现的组合。
2. 修订前提按新产物自身的合法性及 owner 判断。避免旧派生依据造成的自指 stale／该 stale 产生的 FAIL，让 designScopeRevisionChecks 在形成修订前整条短路。其他真实内容 FAIL 仍阻止闭环和推进，不能简单删除全部 FAIL 保护。
3. 复用 ownsDesignOutput、设计事实 proposal、同一范围解析器与收尾修订。在 proposal 副本中同步刷新本次验收上下文及所有由它派生的 unit/device 等义务绑定，不能上下文用新指纹、派生义务仍克隆旧指纹；未受影响来源、控制依赖和合法写集保持约束。
4. 绑定失效要成为本次可定位检查/修订结果，不能异常穿透到 runner 再借旧报告指挥；本 plan 修来源与修订顺序，第二份负责统一异常出口及当前报告。
5. P1-T9 固定为“冻结时 acceptance 已在场 + completion_target=feature + 实际范围需要 spec”，经真实候选和 harness 调用建立，覆盖一次需要修正的验收及再次校验；不得删除 acceptance 后冻结或用手填 scope 冒充。宿主 00:43 的修正/重验没有解开这一组合，不能仅以‘建议再跑 correction’交付。
6. 保留反例：不属于本阶段的来源确实变化时仍回 owner；非法验收、未授权减项不得借刷新指纹放行。冻结文件与历史报告不删除、不搬走、不原地改哈希。
