## 3. 修复方案与最小责任边界

### 3.1 P0 义务、定义及证据消费同源（t1）

落点：`harness/scripts/utils/p0-semantic-gates.ts`、`check-acceptance.ts`、`runtime-step-evidence.ts`、`harness/scripts/check-testing.ts`，以及实际生产验收输入的 `blueprint-skill-projection.ts` / spec 检查调用点。同步相关 types、spec/plan/testing 指引与现有规则，不另建一层前置门禁。

**事实来源是有效验收义务和计划要求，不是本次实际执行了哪些用例，也不是是否填了 linked_flow。** 本批固定以下定义，由 `p0-semantic-gates.ts` 内一个共享解析函数产出设备义务集合、需要 UI checkpoint 的集合和已声明屏链，消费者只取相应投影，不再各自重写适用条件：

1. **P0 设备义务**：有效 acceptance 中 `priority=P0` 且 `ut_layer` 为 `device` 或 `both` 的验收项；不看 linked_flow、flows、checkpoint 或 ui-spec 是否存在。
2. **需要 UI checkpoint**：属于上述设备义务，且需求按既有 `resolveUiRelevanceForRun(projectRoot, feature, requirement)` 判为 UI 相关。传入当前已解析的有效需求，沿该函数的 spec.ui_change 优先口径；不以 ui-spec 文件存在性判断。不另造 UI 相关性探测器；必要定义来源缺失/冲突时沿原定义缺口处理，不能把缺少输入所得的 false 当作已证实的非 UI 结论。
3. **flows 可选**：不新增为 P0 原生证据对账的必填条件。UI checkpoint 完整且对应真实步骤证据成立，可以在未声明 flows 时通过；声明了 flows 才执行既有屏链约束。空 flows 不得抹掉设备义务或关闭 native gate。

接线覆盖现有六处：`isP0DeviceInteractive`、`evaluateFlowContract`、`evaluateNativeP0` 的 AC 选择与 P0 TC 消费、`check-testing` 的 native evidence 准备/生成/复用/消费、`composeRuntimeFidelityEvidence` 的 checkpoint 消费；spec/蓝图定义检查使用同一解析结果。原生证据适用性取设备义务，UI checkpoint 适用性取其 UI 子集；测试计划中的 P0 用例必须映射回有效义务，漏执行或漏列用例不能减少义务集合。非 UI 的 P0 设备义务仍核对已冻结验收、对应计划断言与原生执行证据，不强读 ui-spec，也不因免除 UI checkpoint 自动 PASS。

缺必要 checkpoint/action/元素绑定时沿既有设计缺口通道回定义责任方；属于 spec 补充职责的，复用 c6 t5 在同一授权 run 接入 spec，保留 fresh 阶段和累计预算。涉及业务目标或蓝图权威变化时仍回其原 owner，不让 spec 自行改变上游目标。

| 输入状态 | 处置 |
|---|---|
| 有效范围确实没有 UI 交互义务 | UI checkpoint 检查不适用；其他设备、数据或非 UI 验收继续按所属通道核验 |
| 有 UI 义务但 ui-spec、checkpoint 或必要关联缺失 | 定义缺口，回原责任方补齐；不得因文件缺失记 unsupported_gap |
| 定义完整但执行环境不支持某项验证 | 按既有能力缺口规则披露，保留原分母，不伪造元素或证据 |

**linked_flow 保持既有用例引用语义**：指向 `use-cases.yaml` 的 use_case id，linked_branch 指向其分支；不再把该字段同时当作 `acceptance.flows` 的屏链名。已声明的屏序继续来自既有 `acceptance.flows`，通过 checkpoint 的 pre/post/action 关系与屏链关联，替换按 linked_flow 查屏链和判断 flowHasP0 的写法；业务用例名和屏链名不要求相同。声明屏链时保留相邻关系、边覆盖和有序合成约束；未声明屏链时不强造一份，仍核 checkpoint 的动作可绑定及真实引用。确有无法确定的定义关系回 spec，不猜 ID、不补造屏序、不引入第二份流程真源。现有合法屏链及 native/legacy 直接读者同步消费；不能仅改当前 native 分支而留下另一入口继续误用字段。

`both` 的业务用例引用检查与设备 checkpoint 检查各验其职责。旧的合法材料沿现有解析/正式重验路径消费，不为字段混用新增白名单。缺定义不降成 SKIP，不只开启 native gate 却留下空 AC 集合，也不拿 7 个 CaseResult 的通过代替验收语义核验。

诊断区分：无适用义务、定义缺失、执行证据缺失/不匹配、工具协议不支持、已确认能力缺口。仅真实版本/协议问题提示升级。同步 `check-testing.ts` 中“gate 为 null 即不适用”的相关注释与调用，禁止消费者各自解释 null。

### 3.2 复用有效视觉观察，当前规则重新裁决（t2）

落点：`profiles/hmos-app/harness/visual-provider-review.ts`、`visual-diff-check.ts`、`harness/scripts/check-testing.ts` 的 delegated 调用及其既有证据读者。修改旧的“每次调用前清空、禁止跨 attempt 复用”策略与直接描述它的规格/注释。

**复用对象是已采信的 provider 观察载荷；旧 warn/PASS、旧 release_readiness 不是当前放行依据。** 同输入重跑 harness 时先检查既有原始输出、回执和采集/构建绑定；观察仍有效则不调用 provider，由当前 gate 重新裁决。所有有效观察都适用此规则，包括有真实缺陷的载荷；复用不清除缺陷，也不反复向模型重投以求有利结论。

有效性依据使用既有真源：目标屏及实际要求的元素、原参考图与派生比较图/截图哈希、构建指纹、导航配置、评审提示的实质输入（含 ref-elements、目标简报和提示契约/模板）、provider 身份。run/attempt/timestamp 等调用身份保留溯源，不单独视为实质输入变化；不改写旧输出身份冒充新调用。

严格度、有效目标或门禁变化时，先按当前要求校验旧观察能否继续支撑结论：例如 best_effort→hard 可用同一组有效观察重新裁决，原 major 不得因旧 warn 而放行；新增必需元素或评审契约使旧载荷不足时才重评。已有 `evaluation_invalidated` 等明确失效事实、原图/截图错误或不完整绑定，不得仅凭图片相同绕过。

禁止使用会被评审自身改写的 `visual-diff.json` 整体哈希作为跨调用复用判据。复用依据固定落在已有 `device-testing/reports/critic-receipt.json`：补充机器生成的“去除调用身份的实质提示输入摘要、构建指纹、导航指纹”，由 `visual-provider-review.ts` 的复用判断读取，图像/provider/输出绑定沿用现有字段及原始输出。实质摘要从同一次 prompt 组装的输入计算，包含目标屏/所需元素、ref-elements、目标简报和提示契约；只排除明确的 run/attempt/timestamp 承载信息，不用宽泛文本替换误删目标内容。原 `prompt_hash` 继续表示含身份的真实调用提示，不改变其溯源语义。写入沿现有回执原子提交路径；旧回执缺少这些复用依据时正常重评，不回填伪造历史摘要，不另建 manifest、缓存目录、注册表或状态机。

保留 `visual-diff-check.ts` 对 verified 回执的当前 run/attempt 精确绑定：跨 attempt 复用的观察如实按 `unverified` 呈现，不改旧 critic_run_id/runner_attestation，不为维持 verified 放宽验读判据。该披露等级与观察能否在当前输入下采信分开，沿现有 WARN 口径处理，不新增完成阻断；图像存在性、hash、有效性与当前 gate 裁决继续执行。

明确失效的旧观察不得继续驱动放行或修复；仍有效的观察不因无关 P0 检查重试或 attempt 变化而被清空。新评审沿既有原子提交路径落盘，确定性视觉检查继续执行。

### 3.3 视觉格式局部恢复与执行失败归因（t3）

落点：`visual-provider-review.ts`、`harness/scripts/utils/visual-provider-invoke.ts`、`check-testing.ts` 的失败投影与直接相关恢复调用。复用统一执行器及现有阶段重试、预算、熔断，不另写进程生命周期或失败状态机。

格式纠错每次评审最多一次，只回传原输出、精确校验诊断及所需格式契约；**不携带图像、不重新做视觉判断，不补造缺屏、缺失观察或不明语义关联**。适用于能从原输出恢复的语法/字段形状错误。错图、绑定不符、缺观察等不能通过格式修复获得事实的情况，保持原 invalid 出口。严格 JSON 校验及当前绑定检查保留，不执行载荷表达式、不由执行者手改裁决。

初始时限方案：仅把视觉 review 首评的本地默认调用上限从 300 秒改为 600 秒；格式纠错保留至多一次、单次最多 300 秒。两次均在调用开始时与当前有效配置/显式更小上限、剩余 gate/run 硬预算取小值，不再把首评自身的截止点当成纠错的唯一余量；不顺带扩大 spec 观察、探测或其他 provider 调用的默认值。依据是本轮数次返回已接近 300 秒且有一次首评触顶，继续用 300 秒缺少余量；600 秒是本批有界工程默认值，不是已实测的最优值。正常提前返回不等待到上限，真正卡住的调用可能多占时间，仍由原总预算和无进展边界限制。小样本不能推出长期“每6次必超时1次”，缩小后的格式纠错耗时也尚未实测，不承诺固定秒数内成功。所有调用与实际时间照实计入原预算，不延长用户总上限、不重置累计；总预算不足时不启动或按预算准确退出。

| 已观察事实 | 归因和处置 |
|---|---|
| 单次调用超过有效期限，任务预算仍允许恢复 | 保留调用超时事实，按已有有界执行恢复处理；不能仅凭 timed_out 推断外部能力缺失，也不宣称根因必为期限不足 |
| gate/run 硬预算耗尽导致截断或无法调用 | 保留预算原因，走原预算出口，不伪装成 provider 不可用或再发恢复调用 |
| CLI 缺失、服务/鉴权等有明确不可用证据 | 沿既有能力/外部条件分类准确停放；启动错误或终态失败需看具体原因，不全部归成能力缺失 |
| 有返回但正文格式或绑定无效 | 按适用条件局部纠错；仍无效走原 invalid 出口，不伪装成能力缺失或 PASS |
| 同一输入连续超时且既有恢复额度耗尽 | 按既有重试/无进展边界停放，报告超时耗尽；次数本身不证明能力缺失，不新增计数器 |

**单次 provider 超时的调度出口固定复用 `projectDelegatedVisualProviderFailure` 的 invalid→testing FAIL→现有 retry/fuse 分支**，不进入 unavailable→capability_missing/externalBlocked；保留执行器的超时事实和实际期限，details/suggestion 区分“未取得有效正文：调用超时”与“返回正文格式无效”，不能把超时描述成 JSON 错误或主阶段 Agent 被杀。gate/run 预算耗尽优先走原预算出口，不再派一次 testing 重试。同一失败签名且被监控产物无进展时沿现有无进展判断停放；不因换 attempt、写新诊断或复制回执重置恢复次数。既有事件与诊断保留原执行事实，修改投影时同步 runner 的直接消费者；不能只更改提示文字而仍按错误原因调度。合法格式但结论不利不属于纠错对象。
