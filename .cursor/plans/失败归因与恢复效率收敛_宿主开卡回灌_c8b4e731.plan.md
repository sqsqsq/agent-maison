# 失败归因与恢复效率收敛（宿主开卡回灌）

> 需求输入：2026-09-19 本对话的整晚复盘与追加核对。目标是减少已证实的空转，同时保留可靠性。
> 代码基线：main 3dffe4c1；与[阶段输入与证据归属修复](阶段输入与证据归属修复_宿主开卡回灌_6f2a9c41.plan.md)组成两份修复，不增加总纲。

## 1. 目标与冻结范围

修复三件事：
1. 本次调用的归因、重试和推进只消费本次可信事实；旧报告仅保留历史展示资格。
2. 由实际责任方修复真实缺口，不把输入/框架问题默认当产品回归原样重试；合法的新修复仍可继续。
3. 恢复复用仍有效的阶段结果，避免重复起停、重跑与额外心跳等待。

本 plan 不负责修正源码目标如何生成、facts 如何建立、UT 测试为何进入 coding 输入；这些由第一份处理。
不得在这里用降低 on_missing、跳过 UT/verifier、忽略真实漂移或手改旧报告来掩盖第一份的问题。

本轮不承诺“所有重试都能裁掉”“一小时完成”，也不把“此前 PASS”当成无条件可复用。
输入/契约/产品变化后的必要验证、独立语义审查与真实设备验证继续保留。

## 3. 最小实现方案

### 3.1 本次失败是唯一决策输入，stale 报告不再指挥

在 goal-phase-runtime 的公共汇合处产生一次“本次可决策视图”，复用现有 freshness、harness 结果、当前 invocation 信号与 SummaryJson/CheckResult；不是新报告文件或新的状态机。

顺序：
1. 先判报告身份和本次新鲜度，再收集 actionable defects、归因、affected_files、签名、repair candidates、reconcile、retry prompt 与事件。
2. 旧 summary 可以展示和定位历史，但其 blocker、PASS、verifier 路径、受影响文件不得被当成本轮已发生的内容事实。
3. 如果本次 harness 已在输入解析/预检失败，使用本次结构化检查、退出结果和真实诊断；不得退回上一轮编译失败签名。
4. 已知解析/来源失败沿当前 CheckResult/capability 结果输出；未知内部异常按既有执行/框架失败语义记录本次错误。错误 CLI/缺外部条件/内部异常不得统一改成“产品代码坏了”。
5. 既无本次有效报告也无充分诊断时，明确“本次未获得有效结果、未执行哪些步骤”并停止错误推进；不伪造 PASS，也不默认把旧摘要装成新报告。

harness 一侧复用既有 generateScriptReport / summary 写入路径，使有合法调用身份和安全报告目录的早期失败也产生本次结果。
若参数/目录身份本身非法，保留明确非零退出与当前诊断，不为强造报告写入不可信位置。
报告未写成仍须有 runner 本次执行失败事实；不能假定“修完 harness catch 后 runner 永远不会看到 stale”。明确覆盖 F13 的 facts baseline throw 和范围 input binding stale 两个真实入口；第一份修产生错误的输入/修订责任，本份统一当前执行结果，不能把二者都泛化为旧编译错误。

必须一次清理所有当前决策消费者，不能只给 classifyFailureKind 加一个 if，而 signature / actionableResult / events 仍吃旧值。
接口类型上的最小透传可使用已有 stale_summary/调用结果字段；不新增 freshness 台账、不改历史文件。
现有 timeout、API 断流、无输出、操作者中断等优先级保持，由正反例验证。

### 3.2 责任方与重试：不是“相同 ID 第二次就停”

复用 SourceAttempt 的来源/producer、冻结义务 owner、当前 checks 的 classification/actionability，以及已有 repair/reconcile 推荐。

| 本次事实 | 处理 | 禁止 |
|---|---|---|
| 有新鲜证据的产品/测试缺陷，当前 owner 可修 | 在已有预算内修复、针对性复验 | 因检查 ID 重复就拒绝真实修复 |
| 上游合法来源已改变，owner 可确定 | 返回实际责任方，修正后只重验受影响消费者 | 留在无权改上游的 UT/coding 原样重试 |
| 明确为框架输入/执行接线缺陷，宿主不可修 | 使用现有 halt/等待与回灌机制，说明事实和已尝试项 | 要用户改 framework、把框架 bug 叫“代码回归” |
| 只知道来源未解析，尚不能证明框架 bug | 准确列缺失来源与可执行补齐动作；不能确定 owner 就诚实停止诊断 | 看到 absent 就全部归 framework_bug，或编造 owner |
| 相同根因且没有新输入、有效修复或外部状态变化 | 复用已有无进展判断结束本轮；外层不原样 fresh run | 通过重生运行规避本次停止结论 |

没有新固定次数门槛：同 ID 可能代表不同具体问题，同一签名也可能因真实修复需要再次验证。
使用既有事件、阻断内容与实际输入/产物变化判断；不以文件 mtime、追加一句 notes、重写报告时间作为“新事实”。

主 agent 的恢复指引必须承接 runner 的责任判定。授权“持续完成”不等于授权绕过质量边界；已经证明宿主修不了时应报告阻塞，不再静默循环。

### 3.3 复用已有证据，缩小恢复范围

先等第一份修正证据归属，再检查恢复是否仍有生产缺线；不把第一份造成的 false stale 用“放宽复用”绕过。

- 用既有 staleness、satisfied_by、reused_phases 与受控修订判定有效成果；不能只看 summary.verdict=PASS。
- 因 UT 自身产物返修且产品未变，不重新产生 plan/coding；必要的测试运行和本阶段闭环照常完成。
- 真实接口/产品变更仍回对应 owner 并覆盖受影响下游，不能仅因“之前绿过”跳过。
- 恢复优先原 run/同一有效 Feature 范围；必要 successor 通过现有交接和来源关联创建，不为了补证据总是新建全链。
- 主 agent 手工指定 start/end 与解析范围冲突时，按范围解释修正调用；不尝试一串排列组合或直接跳过未闭环 UT 进入 testing。
- 用户明确要求“重新执行某阶段”与“恢复完整交付”分开消费，不能为了减少次数无视明确重跑请求。
- 若生产复用路径本来有效，改指引和覆盖即可，不重写复用算法。

所有有效性判断仍沿一个来源链；不新增复用缓存、successor 清单或请求级预算台账。
“旧阶段通过但现在无效”的判断应能指出具体变化，避免一句“回 Plan 重签”让整条链重新开始。

### 3.4 恢复操作与等待：用现有能力，不新建监控

主落点为 goal-mode Skill/operations 与必要的 phase-executor 指引；仅修改实际会被宿主读取的入口。并核对已有 resume guard 的真实调用方。

- 已授权完整交付时，不因预期会话结束自行制造停机；确需有人在场/无人值守转换，沿现有 handoff/attach/resume 契约办理。
- 启动后用已有有界握手核实运行身份、run_start 或明确失败；“创建了目录/返回 pid”不等于运行健康。优先由 runDetachLauncher 用已有 manifest/events/liveness/status 投影代做一次有界确认（沿现有 ≤30 秒约定），子进程早退即时给出真实原因，超时仍活跃只报尚未就绪，快速完成则报真实终态；不能每次都要求 agent 再猜和补握手。父进程管道/日志句柄仍及时释放，不等待整个任务，不因确认超时擅自杀仍正常工作的子进程。若现有宿主/launcher 约束确实无法代做，必须在实施记录给出具体证据和可执行替代步骤，不能只用一句“靠指引”结案。
- 始终携带合法 run/Feature 身份；遵守 harness cwd/tsconfig 约定，不用无身份 revalidate 接管旧证据。
- 对 --attach-created 核完整链：主流程参数校验 → detach parent 的 resolveRawRunInput → child argv → 子进程加载既有 manifest/出生事件 → owner/attachability。必须验证 parent/child 使用同一既有 run_id、不会先生成随机目录后另接旧 run；有/无 --run-id、与 --resume/manifest 冲突均有反例。实现已支持的路径写成准确指引；真实缺线只在现有解析/传参处补齐，不新增 attach 模式。不能因为 runtime 识别参数就假定 launcher 也已正确接通。
- 已配置的心跳继续使用原机制：等待没有变化就保持安静，真正失败/框架阻塞应通知；不能每五分钟创建一个新的同输入 run。
- 无需额外调度等待即可继续的已授权工作，应在当前调用完成必要动作；不主动结束后再等下一次心跳。
- 不全局关闭冷却，也不缩短所有轮询间隔。先审 checkTerminalResumeGuard 的 blockingCleared 来源：仅在已有机制能证明恢复条件满足、预算/权限均有效时，允许该事实走既有恢复出口而不再叠加固定等待。
- 若 blockingCleared 仅基于 mtime 或不足以证明恢复，不为提速新造证明系统；本轮保留保护，明确下次可恢复时刻，在实施记录披露残余等待。

这部分的性能收益必须有时间戳证据；不承诺每次省固定分钟数。
不改客户端心跳调度器，不创建新 automation 服务，不处理与本轮无关的跨平台进程生命周期。

## 7. 保留 / 裁剪 / 不做

保留：
- 新鲜的业务失败、真实编译/真机失败、必要语义 verifier、预算/权限、合法冻结与恢复身份。
- 真实契约/输入变化后的必要重验；明确重新执行请求。
- 超时/API 断流/中断等已有执行事实的优先级。

裁剪：
- stale summary 对本次 blocker/signature/repair/prompt/event 的支配。
- 当前阶段无法修的来源错误被盲判 code_regression。
- 没有新事实的同路径重启、修测试却重做未失效上游、没有必要的双重等待。
- 空泛的“运行健康”与让用户猜内部恢复命令的提示。

不做：
- 固定“同签名第二次即停”门禁、新的 FailureKind 体系、失败注册表或跨 run 预算台账。
- 新监控/心跳服务、全局取消冷却、强制 clean、批量重写历史报告。
- 为所有重试额外增加 verifier，或因性能问题撤掉现有有效 verifier。
- 给宿主修改 Maison 发布件开口子；新修复仍在源仓形成发布件集成。
- 以更换模型、更大上下文或人为一小时上限替代根因修复。

## 8. 实施顺序、验证、兼容与发布

顺序：
1. 优先落地本 plan 第一笔（当前结果/新鲜度），先让下一次失败能准确报告并停止错误重试；它不依赖第一份修完，可与其输入修复分别推进，但不承诺所有问题都能在几分钟内定位。
2. 第二笔 owner/复用必须基于第一份修正后的真实行为收窄；能由第一份自然解决的部分删除重复补丁并记录。
3. 第三笔只改仍有事实依据的恢复/等待问题，不为追求理论最优扩面。
4. 两份合并通过门禁后，共用发布与宿主验收；保留各自 todo 与结果，不增加第三份协调 plan。

验证：
- 生产改动跑 typecheck 和目标 suite；例如在 harness 目录运行 npm run test:unit -- --filter goal-phase-runtime、--filter goal-runner-hardening、--filter goal-reconcile-observation，按实际落点选用。
- 可交付生产切点必须 cd harness && npm test 全 PASS；纯文字返修只核 diff，复用仍有效全量结果。
- 对既有 OpenSpec delta 同步后 npm run openspec:validate；状态更新执行 node scripts/check-plan-version.mjs；文本为 LF，检查 git diff --check。
- 不以 grep 到用例名代替执行，也不为本 plan 自动跑宿主整晚或重复全部真机验证。

OpenSpec 优先落既有 obligation-execution-scope 的 goal-runner/reconcile-assessment/runtime-policy，以及 dynamic-workflow-closure-migration 的必要闭环条款；报告输入约定与 composable-skill-inputs 的修改由第一份主责，避免重复定义。不修改已归档 change、不新建空壳 change。

兼容：
- 原始历史 summary 保留，不就地删 blocker 或改 verdict；只收窄其在当前 attempt 的资格。
- 旧 run 的有效报告/闭环仍按既有协议读取；缺当前可信结果如实停下，不替其补造身份。
- 文档/adapter 更新使用现有物化与 UPDATE；模板/Skill 行数预算仍适用，优先改原句而非无限加长。
- 合并发布前走既有 release:all，不在本 plan 写作时执行提交、发包或宿主更新。
