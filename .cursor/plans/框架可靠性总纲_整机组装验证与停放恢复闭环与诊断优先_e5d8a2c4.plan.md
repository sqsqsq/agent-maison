  **模型：双平面、一内核（不新增公理——在既有「简单优先 + 回退重签」下补一条推论）：**
  > **证据只约束可以宣称什么，不决定还能不能修。证据缺失、失配或不可信时，
  > 失效旧声明并自动回到责任阶段重签；除真实授权、外部物理条件和硬预算外，
  > 不得因此停死。**
  运行时只保留四种职责：
  | 内容 | 唯一职责 |
  |---|---|
  | manifest.json | 不可变出生意图 |
  | events.jsonl | 唯一运行转换日志；恢复状态从这里折叠 |
  | phase evidence + feature-completion | 证明阶段 PASS 与最终完成（声明平面） |
  | snapshot/head/HWM/beacon/report 等 | 缓存、观察或投影——**永远不能独立否决继续执行** |
  三种运行模式共用同一裁决与证据代码，只区别执行策略：普通模式把下一步交给人；
  goal 有人在场自动执行安全恢复、真需要人的决定才问；goal 无人值守自动恢复 +
  外部条件用探针等待并自动唤醒。
  **安全论证（降权不弱化反自授权）**：不采信 ≠ 放行——不采信 = 失效声明 + 回责任阶段
  **经完整门禁重签**，比"信任缓存恢复"更强。b3e8d4c7 t5 已在 plan-scope 这一条缝上
  实证该模型（authority 不可信 → 自动 replan 而非停机）；本纲把它铺到全部证据面。
  授权域（真人签字 / 凭据签发 / 回执真伪 / 预算熔断）**保持 fail-closed 不动**。

      凡解除条件**可机器观测**就必须带 probe（含需要人操作但结果可探测的——如重新

      授权（visual 签字类）才允许无 probe。

      ② **报告/菜单展示的出口必须就是启动器实际接受的出口**（话术与门禁同源）。
      在案反例=事故④：停放话术列出 resume，恢复门禁拒绝 resume。机器化：对每个停放态
      断言"话术出口 ⊆ 门禁接受出口"。

      "启动后按承诺行事"**——话术说"设备就绪后 --resume 继续"，实测 resume 过门后
      `start_index=6` 直接 PARTIAL 收口（`WAITING(external)` 的 ut/testing 被当

      改码缺陷时无法自动回 coding"——adjudication.ts:443 backtrackBlocked，消费方须知情）。

### T3#3 settle 定案（第三批）

**先纠正我上一批的结论。** 我说过"唯一正确解是把 unlock 链异步化，但会传染到
`runHylyreDeviceTest` 等同步 provider"。查实后**这句话的前半段站不住、后半段的落点也说错了**：

- `runHylyreDeviceTest` **不在** `ensureUnlocked` 的调用链上（它是经
  `requireProviderFunction` 动态派发的 provider，与解锁链无调用关系）。
- 真实链路只有两条：① 门 → `ensureDeviceReady`（**本来就是 async**，接一下即可）；
  ② 运行期恢复 → `device-recovery-bridge` → 四个 profile provider 入口。
- 异步化真正的终点是 **`checkDeviceTestInstallGate` / `checkDeviceTestRunGate` 这两个
  同步 check 门**——再往上是整条 check 流水线。那不是"传染到 provider"，是**重写测试流水线**，
  而收益只是一个 400ms 的等待。

**决定：不做全链异步化；把同步等待做成有硬上限的一等公民，并把 R16 说准。**

R16 的**真实**规则是「**无界/长时**的纯等待必须异步」——它是为模拟器 boot 写的：最长
180s，期间没有任何设备命令在跑，纯等；冻住事件循环会让 supervisor 把活着的 run 判成死的。
但它的**字面**表述（"设备门链路不得同步阻塞事件循环"）与事实不符：同一条链路上
`dumpLayout` 每次数百 ms、`providers/device-test-run.ts` 的 hdc 调用 `timeout: 120_000`、
UT 整轮以分钟计，全是同步 `spawnSync`。**禁 400ms 的观察间隔、放行 120s 的同步 spawnSync**,
规则就不再是在保护活性——这正是本纲要治的"框架给自己造问题"。

落地（**规则被说准，并且扫描范围扩大、约束增多，不是放宽**）：

| 项 | 内容 |
|---|---|
| 新原语 | `bounded-sync-wait.ts` — 设备链路**唯一**允许的同步等待；`MAX_SYNC_WAIT_MS=1000`；**超限抛，绝不 clamp**（静默截断＝调用方以为等够了） |
| 间隔语义 | ~~契约改为「两次**观察**之间至少 `settleMs`」，dump 自身耗时计入间隔，只补差额~~ **第四批删除**（codex 判为过度通用化，复盘属实）→ 现为**固定间隔** `SETTLE_INTERVAL_MS=400`、`MAX_RESAMPLES=3`，均为模块常量不再注入 |
| 总量 | ~~`MAX_UNLOCK_SETTLE_TOTAL_MS` + `assertSettleBudgetBounded` 运行期校验~~ **第四批删除**：两个因子不再可注入后，总量已是编译期常量，运行期校验成了死代码 |
| R16 扫描 | 从 2 个门文件**扩到 4 个**（增 `device-unlock-helper` / `device-runtime-recovery`——解锁链原本根本不在管辖内）；直接调 `Atomics.wait` 仍全域禁；豁免模块须自带上限且抛 |
| 长等待 | `ensureDeviceReady` / `runDeviceReadinessGate` / boot 轮询**仍恒 async**，原有"等待期间其它 timer 仍在跑"的行为用例原样保留 |

**顺带查实的真 bug（比 settle 本身更严重）**：解锁 deps 在**两处各拼一份**——门这边
（`device-readiness-deps.ts`）和运行期恢复那边（`profiles/hmos-app/harness/
device-recovery-bridge.ts`）。settle 当时是**可选字段**，恢复那份连写都没写，于是
**运行期恢复这条路在真机上恒零等待**——正是 2026-08-05 宿主"永久零输入"的那条路，
而单测因为注入了计数桩全绿。处置：`settle` 改**必填**（类型层面挡住），并抽出唯一接线
`buildUnlockDeps()`，两处共用；再加结构性用例钉死"不得再手拼一份 / 不得注入空 settle"。

**变异复验**：等待原语退化成空壳 → 墙钟格红 + 接线格红｜恢复桥退回手拼 → 接线格红｜
解锁链里直接写 `Atomics.wait` → R16 格红。（另有三格随第四批删除的设施一并移除。）

#### 整机链首跑抓到的**真 bug**（不在七/八用例内，链路自己找出来的）

修完上面四个 P1、`--zip` 第一次真正跑通之后，`checkGlobal` 段当场红：

| 副本 | `check:global` |
|---|---|
| 宿主副本（LF） | **18/18 PASS** |
| `autocrlf=true` clone 副本（CRLF） | **61 项 / 44 BLOCKER** |

同一份 zip、同一份代码，只差一次 checkout。根因：`check-skills-confirmation-ux.ts`
的解析**全是手写正则且锚死在 `\n` 上**——`/\n    options:\n/` 在 CRLF 下遇到的是
`options:\r\n`，恒不匹配，于是 registry 的 44 个条目每个都报 `registry_options_missing`。

**真实影响面**：`core.autocrlf=true` 是 Windows 常见默认，任何消费者换机 clone
后跑 `check:global` 都会硬挂。这正是事故② 的同族，但此前无人走到。

**修法（用户裁定"直接修"）**：不逐条给正则打 `\r?` 补丁（会漏，且下一个手写模式
又重犯），而是**在边界归一**，复用发布 pack 同源的 `normalizeIntegrityTextEol`：
① 本文件 9 处 `readFileSync` 全部经 `readTextNormalized`；
② 导出 API `lintRegistryOptionsSchema` / `lintInitSetupNoFreeText` **在函数入口再归一**
——只在读文件那步归一，等于把契约寄托在"每个调用方都记得先归一"上。
（这第二层是被回归用例逼出来的：用例直接喂 CRLF 文本，只改读入口时它仍红。）

回归用例落在 `confirmation-ux` 套件，**先红后绿**已实测：修前红（`实得
[registry_options_missing]`）、修后 13/13 绿；夹具自带"必须真是 CRLF"的空转防护。

**遗留（已另立项，不在本纲）**：全库 39 个文件共 84 处 `\n` 锚定的手写解析，本次只走到
其中一处。这一类的其余部分另立
`.cursor/plans/文本读入口EOL归一_手写解析CRLF脆弱面普查与收口_b6d3f7a1.plan.md`
——**用户 2026-08-06 裁定同挂 3.0.0 窗口**，随本批入库。本纲**不顺手扩面**
（"非阻塞顺便实现"是 plan 膨胀之源，已四次实锤），但它是同窗口的发布必做项。

记一条门禁机制：`check-plan-version` **只看 `version` + 未完成 todo，不认
`status: draft`**，且扫的是**磁盘文件**（未跟踪也照扫）；`version > 当前` 时还必须

#### 第八批：T4 用例 #8 的行为面钉桩（棘轮）

**goal stage 仍未实现**，但 #8 的行为面先落地了：
`harness/tests/unit/goal-lineage-first-death.unit.test.ts`。

两条实证结论（供 goal stage 落地时直接用，别再走弯路）——**两者缺一不可**：

**① 不能 spawn `goal-runner.ts` 本体去测另一个临时宿主。** `inferRepoLayout` 会把
framework 根解析到脚本自身所在的仓，与目标宿主不匹配，config 读不到
`materialized_adapters`，卡在 adapter 物化门（实测 `adapter BLOCKER: … 不在已物化
候选 []`）。必须**进程内注入 `__testing_setRepoLayout`**，即 plan 原文的"复用既有缝"。

**② 但也不能在测试进程里直接跑。** `goalMain()` 会 `setupSignalHandlers()` 等一系列
**进程级**动作；run 正常返回时清理路径会跑，而本用例回放的恰恰是**异常终止**
（从 runChain 里裸 throw），清理没走 → 信号处理器/定时器留在测试进程里 →
后续套件一碰，**整个 run-unit 进程 SIGINT 退出（exit 130）**，连汇总都打不出来。
实测三段对照：摘掉该用例 3047/0 全绿｜加上它 exit 130｜单独跑它却 1/1 通过。
既有 `goal-runner-testing-integrity` 能共存，是因为它的 run **正常返回**。

**结论：子进程 + 进程内注入缝**（`tests/helpers/goal-run-driver.ts`）。

**③ driver 必须从"被测 framework 根"动态加载，否则复用不了**（codex 第八批 P1
订正我的记账）。初版静态 `import … from '../../scripts/goal-runner'`，即恒锚开发仓；
而 `harness/tests/**` 又被 `release-excludes.json:11` 排除、**根本不进发布件**。
两条合起来：它作为单测 driver 有效，但**不可能**用来验 `--zip` 解出的 candidate——
我原先写的"smoke 落地时直接喂 scenario 即可"是错的。现改为第 4 个参数
`frameworkRoot`，goal-runner / config 都从该根 require，smoke 传
`ctx.clonedFrameworkRoot` 即验发布件本身；缺省回落开发仓（单测形态）。

**④ driver 不自建宿主——一条整机链只能有一个宿主**（codex 第九批 P1）。
上一版只修了 frameworkRoot，driver 内部仍 `setupMinimalHost()`，于是即便 smoke 传对
发布件根，形态仍是「宿主 A：install→commit→autocrlf clone→integrity ／
宿主 B：新建最小宿主→goal run」——**两个半链各自绿**，宿主 A 上的 gitignore、CRLF、
配置与冻结状态全没被 goal 消费。现改为 `projectRoot` 由调用方传入且必填：
smoke 传 `ctx.cloneRoot`，单测传自建的最小宿主。

**⑥ layout 按两根关系派生，不得硬编码**（codex 第十批 P1）。driver 曾恒注入
`kind:'standalone'` + `frameworkRel:''`——单测形态（framework 在开发仓、宿主在临时
目录）下碰巧是对的，但 smoke 的真实组合 `projectRoot=cloneRoot` /
`frameworkRoot=cloneRoot/framework` 是**嵌套的 consumer 形态**。伪装成 standalone 会
跳过 consumer 专属的 `RELEASE-MANIFEST` 校验，并把 `harnessPrefixRel` 生成成
`harness` 而非 `framework/harness`（给人的指引指错路）。
**当前 #8 单测覆盖不到这个错**（它用外置开发仓），故另加纯结构断言钉住 consumer
组合；变异复验：退回硬编码 standalone → 该格转红。

**⑤ 临时宿主谁建谁删。** 初版写"留给 OS 回收"，实测 Windows 不回收：每跑一次多一个
`goal-drv-*`（定向后 4 个、全量后 5 个，codex 实测）。中间版把 `hostRoot` 从子进程
回传再顺序清理，但**子进程超时/缺结果标记/JSON 解析失败时拿不到路径**，
"父进程 finally 清理"的记账名不副实（codex 第九批 P3）。随 ④ 一并解决：
父进程建、父进程 `finally` 删，异常路径也兜得住。

这几条也是本纲判读的又一实例：**"单跑绿"证明不了"合跑绿"**，与"零件绿、整机没人
验过"同源。全量套件本身就是一个小整机。

**用例是棘轮，不是目标断言**：目标行为（自动 discontinuity 续跑）属 T2，尚未实现。
若写成"断言目标行为"就会长期红着，而常红的用例三天后没人看（本仓"越优化越差"
实锤）。故当前钉**现状**，T2 一改行为它立刻转红，强制回来翻断言 + 把 smoke 注册表
#8 改 covered。

`events = [run_start, vision_ledger_tamper]`（与宿主 run1 取证同形）、

| 行为钉 | `head_is_directory` 场景**加 `.bak` 残留**（最危险组合入钉）；新场景 `trust_namespace_is_file`（ENOTDIR 复现）——两格都断言 spec 照常+persist_failed+正常终态 |
| P2 文字/类型收尾 | MIGRATION 删 authenticated head/auth-subset 旧模型段（两套互斥描述并存）；两 doc 类型删 `mac`/`auth_subset_sha256` 声明（旧 JSON 多余字段解析自然忽略）；adjudication.ts/goal-manifest.ts/goal-runner.ts/测试注释的"恒 terminal/MAC 保护"全部改述为现行事实（events 出生基线+恒 recover+出生冻结判据）；plan 当前设计段同步改述，核实记录禁删只加时点按语 |

**硬学习**：缓存边界的 no-throw 必须盖住**整条恢复链**（rollback→quarantine→写入），
只给最后两环加守卫、第一环还在裸抛＝守卫顺序错位；"目录但无残留"不是"目录+残留"的
代表元，行为钉要钉**最危险组合**。

### 第十六批（2026-08-07，fable 实施）：收口终刀——finalize 虚假提交根除（codex 末条 P1）

第十五批把 finalize 也做成逐条吞错——codex 实测这是**把"run 不抛错"错扩成"事务失败
也算提交"**：目录形态 `.bak` 删不掉 → finalize 照常返回 → `lineage_reset_committed`
照写 → 下次 rollback 删掉新 head、把目录改名成 canonical head（head 永久变目录，
其后每次全量重建）。"事件声称已提交、缓存仍能回滚"= 事实作假。

| 处置 | 说明 |
|---|---|
| 残留**只认普通文件** | `listLineageResetBackups` 加 `lstatSync().isFile()` 守卫——目录/符号链接形态的 `.bak/.absent` 零识别（不还原、不清扫、不计数，人工删除）；rollback/枚举的 no-throw 保持 |
| finalize **不吞**已识别备份的删除异常 | 抛出交 `commitVisionAnchors` 既有外层 catch：persist_failed 记录+继续执行，**committed 不写、pending 保持在场**，下一成功写点重试提交——run 不死，事实不假。零新增状态/事件/门禁 |
| 行为钉 | adjudication 新格：目录形态 bak → rollback 零还原（canonical head 原样在场）、finalize 零计数、残留原样不动 |

**硬学习**：no-throw 的边界是**执行权**，不是**事实声明权**——恢复/清扫失败可以不
杀 run，但绝不能让"提交完成"事件在事务未完成时写出；降级要区分"跳过继续"与
"跳过但仍宣称成功"。

### 第十七批（2026-08-07，fable 实施）：同语义最后残口——共享枚举层不得替 finalize 降级

codex 故障注入：`listLineageResetBackups` 自己吞 `readdirSync` 异常返回 `[]`——rollback
需要这种降级，finalize 不能接受（"无法确认备份是否清空"被误作"没有备份"，committed
照写=同一虚假提交语义从枚举口漏回来）。

处置：list 删枚举 catch（异常向上抛）；rollback 在**自己的调用点**捕获降级（warn+按无
残留继续）；finalize 零捕获（删除与枚举失败都进 commitVisionAnchors 既有 catch——
persist_failed+继续、committed 不写、pending 重试）；`lstat isFile` 过滤保留。零新增类型/状态/事件。

测试口径订正（codex 抓的第二点）：上一批"目录 bak"格测不到 finalize 的 catch 回归
（加回 catch 照样绿）——新格用**测试内临时替换 `fs.rmSync`/`fs.readdirSync`**定向注入
（打在裸 require 的 fs 单例上；`import * as fs` 命名空间是只读 getter 包装，注入不进
生产），双向断言：finalize 两种失败都上抛、rollback 同枚举失败降级不抛、注入解除后清扫恢复。

**硬学习**：共享 helper 的降级要放在**需要它的调用方**，不能放在共享层替所有人决定；
行为钉必须能咬到"把 catch 加回去"这个回归（上一格咬不到=白钉）。
