## 3. 有界修复

### 3.1 四条过程检查统一披露，普通模式同出口（t1）

**仅新增以下四条处置登记**，在现有 `DISPOSITION_TABLE` 中归 `ledger_shape`，由 `resolveCheckDisposition/isBlockingCheck/collectDisclosedFailures` 消费：

- `context_exploration_inputs_coverage`
- `context_exploration_mode_allowed`
- `context_exploration_mode_required`
- `context_exploration_subagent_required`

保留真实原始检查结果和详情；命中者进入披露，不计阻断、不产生针对登记格式的返修或无进展停机。规则对 run、阶段和后续完成复核持续一致，不依赖某次模型写一条豁免。未登记项仍按原有声明处理；不把“没有列在硬清单”当成可放行。

普通模式明确包括：有人在场的 run、直接运行 Feature harness 的无 run 模式，以及日常 request。前两者沿已有 Feature 报告/处置链；request 的 `request-phase.ts::runExplicitRequest` 输入前检及 `report-generator.ts::generateRequestScriptReport` 仍有“任意 FAIL 就停”的旁路，须改为消费同一个 `resolveCheckDisposition`。只从原失败条件中排除已判 `disclose` 的项，其余任意 FAIL、阻断 SKIP 和输入解析失败的原语义不变，不能整体改成“只认 BLOCKER”。

这意味着 request 也会承认**现有去向表已经登记的披露项**；这是取消平行判定的明确影响，不重分类这些旧条目，也不复制一份四项 ID 白名单或增加模式特例。request 的披露要进入原报告及 summary，不能吞掉原 FAIL。普通模式无需新 run、伪造 run_id 或新增裁决绑定字段。

**硬边界不变**：来源可读、真实目标覆盖、基线新鲜度、身份；真实构建/测试/设备/视觉与 P0 验收；有效产品契约、数据正确性、需求范围、写权限、冻结范围及硬预算。没有任何账本行或模型意见能把这些真实失败直接改成通过。本批不建立硬检查名单、不调整这些检查的判定逻辑或降低用户验收。

### 3.2 基线与本阶段增量共同组成有效事实（t2）

复用 `context-facts.ts` 中 `findPhaseDeltaSection` 及已用于来源/覆盖检查的 `deltaPaths` 解析，由 `context-facts` 在调用 `context-exploration.ts::runQuantitativeChecks` 时传入本阶段补充路径；保持现有单向依赖，`context-exploration` 不反向引用 `context-facts`。只读取已核基线和**本阶段**合法增量，不扫整篇自由文本、不借后续阶段记录满足当前阶段，不建第二份有效事实文件。基线哈希、实际身份和来源新鲜度仍按原规则核验。

三条探索模式检查仅在事实建立时执行，建立资格复用 `isFactsEstablishingPhase` 和已有 baseline/established_by，不按“当前剩余链首”重新定义历史建立者。后续阶段使用已核基线，不因自己的模式枚举不同而重判 spec 的选择。无调用上下文的旧 per-phase 记录仍遵循其原建立语义，不改成全局跳过探索。

实际增量满足覆盖时，原检查应通过；真实没有登记时才保留披露。不能只靠 t1 把全部原始误报隐藏成非阻断，也不能要求 spec 预先登记未来所有阶段的输入。

### 3.3 plan 自产契约按现有权威路径交接（t3）

落点为 `phase-write-boundary.ts::loadCodingScope/resolvePhaseWriteBoundary`，对照 `capability-resolution-entry-input.ts::phaseOwnsDesignOutput` 的现有产物 owner 判据。plan 正在合法生产 contracts 时，不能为了构造其写边界，先要求尚未完成的 coding 施工绑定有效；当前阶段允许的工件写入仍来自原 produces/有效范围，未成立的源码权限仍不授权。不得直接信任未验证 contracts 扩大源码写域，也不得以持续关闭写归因作为修复。

plan 产物通过现有实质检查后，沿 `blueprint-skill-projection.ts::designScopeRevisionChecks` 发出既有 `scope_revision_input`，经原 run 的 `scope_revised` 或无 run 的 Feature 范围修订，使下游读取有效绑定。`readRunBoundContracts` 的 coding 消费仍严格；不改原 manifest、不改旧指纹、不把“文件现在存在”直接视为已获授权。

**组合必须覆盖**：冻结时 contracts.yaml 不存在 → plan 首次写出 → plan 重试读取自己的合法产物 → 原门通过并正式修订 → 同一个 run 的 coding 通过实际输入入口读到新契约。已有接线能完成的部分只加验证，确有缺口才在上述路径补接，不新增 rebind 命令、快照、状态或旁路加载器。

### 3.4 处置与现有责任出口（t4）

本批只核三个已有出口：四项过程差异由统一去向表披露；真实 contracts 缺陷由 plan 修复并复验；验收/范围/授权发生实质变化时，回现有 spec/设计 owner 裁定，经原修复候选和范围修订继续。R5 延后决定进入简报、664 CU 缺引用进入设计 owner 已修，不重做。

只修改 `report-generator.ts::resolveEffectiveSuggestion` 中“修复路径不明时如实 halt 上报”的唯一来源，按当前有效处置、已有 `repair_owner/repair_candidates` 和受影响产物说明下一步。重试提示沿原链带出这段指引，不在 `goal-phase-runtime.ts` 另写一份；不指示读改框架实现或用 notes 代替路由。无合法授权/外部条件/剩余预算时仍准确停放，不承诺所有硬失败都能自动继续。

只剩已披露的四项时，不能再进入 `code_regression` 重试、阻断计数或修复候选。核对 `goal-failure-classifier` 的实际输入是否已剔除披露项；若已同源则不改分类器，不新增 failure_kind 或 halt_reason。真实缺陷仍消费既有机器归因与责任通道，不靠新错误码表兜底。

**“支持裁决”在本批的含义**：已有 verifier/有权 owner 的判断必须落实到原 spec、contracts、CU 或对应报告，由原消费者重验；不是让自由文本替代机器事实。`headless-assumptions.jsonl` 继续只留痕，不参与改判，也不要求每个失败先增加一次 verifier 调用。

本批不改 verifier 的否决逻辑，只保留一条回归断言：**过程项被披露，不能盖过 verifier 对真实内容的有效否决。**
