## 3. 目标目录契约（终态，硬切）

所有路径以 `<features_dir>`（`paths.features_dir`，默认 `doc/features`）为根；本 plan 与
契约文档一律使用该写法，不把 `doc/features` 写死。

```text
<features_dir>/<blueprint_id>/                ← 演进工作区（一次演进一个）
  blueprint/                                  ← 保留目录名
    component-blueprint.yaml                  ← 蓝图 SSOT（canonical YAML）
    component-blueprint.review.md             ← 派生评审投影（derived_from 指回 YAML）
    component-closure.yaml                    ← closure 派生投影（可整体重算）
    component-closure.md                      ← closure 人读报告
  <change_unit_id>/                           ← CU 工作目录 = 该 CU 的 Feature 目录
    change-unit.yaml                          ← CU 契约（canonical artifact，文件名固定）
    spec/spec.md                              ← phase-scoped 施工产物（feature-artifact-layout）
    plan/plan.md
    contracts.yaml / acceptance.yaml / use-cases.yaml
    review/ · ut/ · testing/                  ← 各 phase 产物、receipt、reports
    goal-runs/                                ← Goal Mode run/manifest/lock
    context/                                  ← 探索事实等既有 feature 级目录

<features_dir>/<feature_id>/                  ← 老式平铺 Feature，保持现有 canonical layout
  spec/spec.md · plan/plan.md · contracts.yaml · review/ · ut/ · testing/ · goal-runs/ · …
```

规则：

1. `blueprint_id` 与 `change_unit_id` 均为安全路径段（沿用现有
   `/^[A-Za-z0-9][A-Za-z0-9._-]*$/`，拒绝 `.`/`..`/分隔符）；`change_unit_id` 不得为保留名
   `blueprint`。当前 App blueprint schema 的 `stableId` 允许冒号（`[A-Za-z0-9._:-]`），
   **只对承担路径身份的字段收紧**：蓝图根 `blueprint_id`、ComponentBlueprintRef 的
   `blueprint_id`、CU 根与 ChangeUnitRef 的 `blueprint_id`、closure ref 的 `blueprint_id`；
   节点、关系、flow、decision、obligation 等其它 stable id 保留原语义；
2. `blueprint_id` 是稳定路径标识，一次演进定名后不改；人读需求名可以体现在 id 命名里，但
   id 不是可修改的展示名；
3. `component_id` 继续存在于蓝图 YAML 与所有 ref 中做所有权与一致性校验，不再充当任何
   路径键或 CLI 定位参数；
4. 目录判别（§5.3）只认标志文件与既有 artifact layout，不认目录名前缀；歧义与不完整状态一律
   fail-closed；
5. 旧根 `blueprint/component/…` 硬切：不兼容、不双写、不回退、不迁移——该路径从未发布，
   工作树无真实存量。

## 4. 身份与引用规则

### 4.1 blueprint ref：形状不变，换定位键

`component_blueprint_ref` 的身份字段（component_id、blueprint_id、revision、
source_fingerprint、artifact_sha256）与 target 结构**零变化**——`blueprint_id` 本就在
ref 中。变化在解析：resolver 以 `ref.blueprint_id` 定位
`<features_dir>/<blueprint_id>/blueprint/component-blueprint.yaml`，随后要求路径段
blueprint_id、YAML 根 `blueprint_id`、ref `blueprint_id` 三方一致，且 YAML 根
`component_id` 与 ref `component_id` 一致。P0 归档 spec 无路径绑定（已实证），不触碰。

### 4.2 ChangeUnitRef：增加必填 `blueprint_id`

`ChangeUnitRef` 增加必填 `blueprint_id`；CU YAML 根同样增加 `blueprint_id`（与目录一致）。
加载时核对：目录路径段 blueprint_id/change_unit_id、YAML 根字段、ref 字段、以及 CU YAML 中
`component_blueprint_ref` 的 blueprint_id/component_id 全部一致。

### 4.3 featureId 与物理路径：唯一 SSOT

- **逻辑键**（events/receipt/reports/manifest 全框架引用，全局唯一）：
  `featureId = "cu-" + base64url(blueprint_id + "\0" + change_unit_id)`；
- **物理相对路径**（相对 `<features_dir>`）：legacy Feature = `<feature_id>`；
  CU Feature = `<blueprint_id>/<change_unit_id>`；
- **唯一实现**：一个中立纯函数 `featureRelativePath(featureId)`（或等价扩展现有
  `config.ts` 路径 SSOT），`featureDirResolved` 与 `<feature>` 模板替换、P2 path、各调用方
  **全部消费它**，不得在 `config.ts`、P2 path 和调用方分别实现；
- `<feature>` 占位符（`receipt_dir_pattern`、`reports_dir_pattern` 等）替换为上述**物理相对
  路径**，不再直接塞编码后的逻辑 id——否则 CU 的 receipt/report 会落到
  `<features_dir>/cu-<base64>/…` 影子目录；
- 判别规则：`cu-` + 合法 canonical payload → CU Feature；`cu-` + 非法 payload →
  **fail-closed**（不回退成平铺 Feature，避免损坏/手写 id 静默制造影子路径）；其它 id →
  legacy Feature。除非实测发现真实 legacy Feature 使用非法 `cu-*`，否则不预设兼容；
- 正反向往返：`derive(blueprint_id, unit_id) → featureId`，`parse(featureId) →
  (blueprint_id, unit_id)`，re-derive 必须逐字节相等；枚举器从路径 `(工作区目录名, 子目录名)`
  重建 featureId 时必须得到同一结果；
- 旧编码 `base64url(component_id\0unit_id)` 随 fixture 树重造消亡，生产无存量，不做版本标记
  或双解释。

### 4.4 唯一性域

- `<features_dir>` 下一层目录名由文件系统保证唯一；工作区名（blueprint_id）与老 feature
  目录名共享该命名空间；
- 同一工作区内 `change_unit_id` 唯一（目录即身份）；不同工作区允许相同
  `change_unit_id`——featureId 因编码含 blueprint_id 而不冲突（§7 证明 2）。

### 5.3 目录判别规则（共享函数与 fixture 断言共用）

### 5.4 Feature binding 状态机（CU 目录与 Feature 目录合一后）

`inspectDerivedFeatureBinding` 的合法状态：

- 只有 `change-unit.yaml` → `available`（CU 已立、未开工）；
- 有 `change-unit.yaml` 与部分施工产物（如 `spec/spec.md`）、尚无 `contracts.yaml` →
  `in_progress`，合法（spec 完成 → plan 进行中 → contracts 尚未形成是正常链路，不得判
  conflict）；
- 有 `contracts.yaml` → 校验其中 `change_unit.change_unit_ref` 与本 CU identity →
  `matched` / `conflict`；
- 工作区子目录有 Feature 施工产物但缺 `change-unit.yaml` → 孤儿，fail-closed；
- `blueprint/` 存在但缺 `component-blueprint.yaml` → 不完整 workspace，fail-closed；
- 无任何已知 Feature 标志的辅助目录 → 忽略。

### 5.5 跨蓝图语义接线

- P2：`requires/provides` 满足集合、carry-forward 重校验、ready/blocker 派生全部以单一
  工作区为域；跨工作区引用在 ref 校验层直接失败（blueprint_id 不匹配）；
- P3：closure 输入枚举（CU、Feature observation、evidence）限定同工作区；
  `input_fingerprint` 机制不变；
- 新演进依赖旧演进成果的唯一合法通道：P1 discovery 从当前代码与归位真源发现当前态
  （总纲 §5.3 裁决），不提供任何跨工作区 provides 读取接口。

## 7. 机械证明清单（t4）

每项必须可独立证伪并能定位失败原因；优先扩展现有 P1/P2/P3/MG/path-governance 测试，按最小
测试组合覆盖，不强制一项一个新 fixture，也不禁止复用现有用例。

身份、隔离与兼容：

1. 同一 `component_id` 的两个 `blueprint_id` 工作区并存，互不覆盖、无可见副作用；
2. 两个工作区使用相同 `change_unit_id` 时，featureId 与物理路径均不冲突；
3. P2 不会用另一工作区的 CU 满足 `requires/provides`（ref 层失败 + 派生层不可见双证）；
4. carry-forward 仅在同 `blueprint_id` 内跨 revision 生效；跨工作区历史 CU 的 provides
   不参与依赖满足；
5. P3 closure 不消费另一工作区的 CU/Feature/证据（跨工作区 row 直接失败）；
6. 已闭环蓝图被修改后原 closure `input_fingerprint` 失配 stale（既有机制回归）；
7. 创建新工作区不修改旧工作区的蓝图、CU 与 closure（前后字节对比）；
8. 老式平铺 Feature 全链路照常：枚举、receipt reconcile、catalog、spec-loader、Goal Mode 对
   纯平铺仓行为与改造前一致；
9. 判别 fail-closed：平铺产物与 `blueprint/` 并存、`blueprint/` 缺 component-blueprint.yaml、
   工作区子目录孤儿 Feature、非法 `cu-` payload 四种情形均报错定位，不静默选边或回退；
10. 旧根路径零残留（§10 口径）：生产代码无 `'blueprint','component'` 路径拼接（grep 断言）、
    有效 fixture 树无旧布局、resolver 对旧路径无回退读取；
11. featureId↔路径往返恒等：derive→path→从目录重建→parse 闭环逐字节一致，且全部枚举点经
    共享函数取得同一结果。

完整路径收编回归（证明散落的路径构造已真正收编）：

12. 自定义 `paths.features_dir`（非默认值）下，蓝图/CU/closure/Feature 全链完整运行；
13. Goal Mode 启动、暂停、恢复，其 receipt/report/manifest/lock/context 全部落在 CU 物理目录
    `<features_dir>/<blueprint_id>/<change_unit_id>/…`；
14. 整轮执行后不存在 `<features_dir>/<encoded-featureId>` 影子目录。
