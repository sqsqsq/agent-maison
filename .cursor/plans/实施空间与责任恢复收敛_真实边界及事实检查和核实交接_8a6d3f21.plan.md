# 实施空间与责任恢复收敛

## 1. 定位、裁决与边界

本 plan 挂 [a47c9d62](../goals/效率与准确率平衡总体目标_默认基线自主交付与可调精细度及可靠恢复_a47c9d62.goal.md) 的 R6，遵守 [AGENTS.md](../../AGENTS.md) 与 [总设计原则](../../docs/overview.md#121-四条总设计原则)。起草基线 `226fee6f`，版本 `3.1.0`。前期同类问题调查已收编到本 plan §2–§6：A–G 的事实、边界、消费者、修法和反例不再依赖独立调查文件；按双方收敛的三条主线实施，不扩成全仓规则普查。

目标是让 AI 在真实授权和规格内完成实现：上游说明目标、真实边界、公共契约和必须交付的行为，预计模块/文件/私有结构用于规划；框架提供实际事实，责任方处理真正的规格与架构变化，最终依靠真实构建、review、UT、testing 验收。合法实现不因未被逐项预测而停机，真实缺陷也不能因没在预测清单上而漏检。

本轮仅起草 plan 并同步路标，不实施、提交、打包、操作宿主或手机。工作区 DeepSeek adapter（`6d2e9a47`）等其它会话改动不纳入、不回滚。实施前重读最新代码，重合文件只改本批必要部分；28/395/5bdd/371 及前序已完成范围和历史验收不重开，本批独立承接已证实的剩余问题。所有宿主联合验收继续 pending。

### 1.1 统一口径

| 对象 | 本批含义 | 变化的处理 |
|---|---|---|
| 用户目标、明确禁止、真实外部授权、总预算上限 | 真实边界，以原请求及有效更正为准 | 不因 AI 提议、review 披露或设计重签自行扩大 |
| 有效架构、共享公共接口、数据契约、其它 Feature/CU 已承诺的行为 | 公共契约；保护兼容性和职责，不冻结整块共享模块 | 实质变更回原责任方；已授权无人值守下沿现有正式修订、质询、发布和重绑，不让 coding 自批 |
| 预计影响模块、文件、私有名称/组织、实施定位 | 实施预测；模型写的排除项不能冒充用户明确禁止 | 原目标内必要调整可实施；预测之外的模块在既有 review 中显著披露必要性、影响和回归依据 |
| 实际修改、源码关系、构建/测试/视觉结果 | 验证事实 | 从现有源码、diff、调用写入及验证产物取得；登记齐全不等于产品正确 |
| 阶段产物归属、框架发布件、秘密及其它任务的过程产物 | 原有职责与保护边界 | 普通实现自由不授予改验收、测试证明、别的任务产物或框架自身的权力 |

“其它 Feature/CU 已承诺内容”指有效行为和公共契约，不是历史预测文件或私有名字。共享模块内部修复、兼容增补不因目录身份就要求设计修订；反之，同模块内改变公共契约也不能只靠披露放行。

原需求内必要源码修改跨过**预测**模块时，不逐模块再申请许可；跨过用户明确边界、改变公共契约/架构时走真实责任流程。用户明确只许某目录/模块的限制仍有效，不能把所有限制都解释成预测。没有清楚的语义结论时用已有独立审查核对必要性，不靠清单差异直接推断越权，也不把 unknown 宣告为合格。

### 1.2 保留与不做

保留必需编译、业务断言、设备/视觉结果、真实缺陷、阶段职责、路径逃逸保护、有效冻结身份及累计预算。普通和无人值守消费同一事实；无人值守只改变已授权修订的自动执行方式，有人在场的实质确认流程不变。

不新增逐文件/逐模块许可表、实际文件注册表、拒修数据库、状态机、事件类型、停机原因、全局权限推理系统或“先请额外裁判再继续”的一轮调用。不靠增加重试、不断起后继、改需求或降低验收消化冲突。不顺带修设备环境、性能全仓优化、scratch 治理、适配器或其它会话事项。

### 1.3 两批实施、各自验收

实施按两批推进：第一批 t1–t4，随批完成相关 t6 文档及 t7 验收，独立证明取消逐项许可、检查实际事实和派生即可消除 1a0796 死路；不依赖 t5 的新入口。第二批 t5，随批完成剩余 t6/t7，集中核实 verifier 资格、候选消费与拒修语义。第一批形成可独立 review 的验收结果后再推进第二批；不增设用户审批点，实际提交仍按用户授权。t6/t7 两批都完成才标 completed，t8 联合验收不拆成两次宿主长跑。

## 4. 三条主线的实施边界

### 4.1 主线一：边界与预测分离（t2）

**源头不再要求穷举许可。** 蓝图/CU/plan 中既有 files、modules、planned_locations 和私有组织信息继续可读，作为预计实施线索；不新加一份“允许修改”的列表，也不为了凑清单要求上游预测全部文件。不能把文件封顶替换成同样僵硬的预测模块封顶。

真实用户限制从现有 requirement/有效更正和有来源的目标约束读取；设计方产物决定行为、公共契约和架构约束。brief 与检查使用同一解释。模型自己写的 out_of_scope_modules 是影响判断时，应显示为预测排除；如果确实转述用户禁止，保留原文依据。不得用缺少专门标签否认清楚的自然语言限制。

**写域与检查域同时收编。** 复用 profile 工程层/模块解析、已有源码与 UT 根、`resolvePhaseWriteBoundary` 及前后快照。普通业务源码域不再仅由 contracts 的预测模块决定；阶段许可仍来自当前有效工作流和原职责。源文件、资源与路由接线归本阶段的实现操作；UT 源码与 testing 证据保持各自职责，设计/DSL/验收仍由原 owner 生产。对其它模块的必要实现先核实真实契约；新增依赖边或模块职责变化继续由设计方在施工前正式修订。

同一 resolver 结果供通用 diff、UI diff、调用写域与分析输入使用；不得在每处各写一份放宽逻辑。已有 snapshot 的工程层取样覆盖实际变化，不通过只看事后已知路径来漏掉未知写入。明确禁止、框架发布件、路径逃逸、其它任务过程产物和真实秘密/外部操作边界照常保护。不能用目录匹配推断某个变化一定由本次 coding 产生。

**投影比较按事实含义收窄。** 在原 `compareAuthoritativeContent`/契约消费处区分：

- 需求行为、验收、外部接口/数据形状、有效架构和选型实质仍与责任方签发内容一致；
- 预计 files、实施目录、私有类/状态名、未作为公共承诺的拆分方式允许调整；不用先改蓝图才能实现；
- 同名字段处在公共契约中不能因“也是 name/file”被整体忽略。现有导出也不能一律等同共享 API（路由 builder 已有反例）；以实际消费关系和有效设计含义核对。

只读资源/源码引用从许可闭包退出，仍检查适用引用可解析与真实所需内容。删掉“既要读就得获准写”“文件不相等就设计漂移”的因果错误，不删除编译或实际引用错误。

本轮不允许以兼容旧 run 为由保留另一套逐文件许可。旧绑定/事件保持历史字节；当前策略改变涉及投影重签或冻结输入变化时，沿已有范围修订、owner 重签和 `decideRunContinuation` 接续，消耗不重置，不手工改哈希。用户明确给出的旧限制照旧守住。

### 4.2 主线二：检查实际改动和归属（t3）

**目标集合在既有入口派生。** 从已有 diff 基线、跟踪/未跟踪变化、阶段写入观察和 profile 源码解析获取本次实际产出；计划提供定位线索，不能再作为实际目标的过滤条件。沿 `capability-resolution-entry-input` 等原入口传给 AST、review、UT 目标分析、证据与完成核验，不增设落盘的实际文件表。删除/重命名读取前后路径和必要旧内容，不能只剩当前存在文件。必要依赖按既有解析链补入，避免为了“全面”扫描整个工程。

必须明确写清并测试：新增辅助源码、资源、未预计模块内的必要改动、注册文件和未预报的页面进入相应消费。其它会话已存在的修改不可冒认为本阶段写入或回滚；无法归属时按既有事实不确定/协作恢复处理，不把它洗为有效产出。

**新鲜度沿已有所有权。** 移除 `phase-evidence-manifest` 对合法写入的预测 files 过滤，承接 `phase_write_observed`、前后哈希、有效阶段及 pending-owner 的同源结果。UT 写测试、testing 写报告不回卷 plan/coding；coding 写正常资源/源码不把 spec 读过的观察一律作废。真正上游目标/契约变更、未说明的外部变化和不连续字节链仍失效。`assess`、上游门、有效范围、恢复和完成核验不可各自补新的“范围内即合法”算法。371 的单次动作 readers 生命周期保持，写入/重签后重新取样。

**page_registration 同时改输入和判据。** HMOS 从实际新增/修改页面及既有路由/导出关系确定受影响页面，再从 profile 支持的实际路由形式定位注册配置；`contracts.components[].nav_destination` 和 `navigation.config_files` 只作线索。已有 resolver/源码分析能用则复用，不复制配置解析。没有预填配置不能直接 FAIL，不能以 navPages 为空 SKIP 掉实际新页面。真实路由漏注册、指向错误/不存在入口或不可达仍由 coding 修复；不能确定的材料交原 review/真机验证，不宣布 PASS，更不为了满足检查生成项目本来不用的路由文件。

review 以真实改动对目标、架构/公共契约和其它 Feature 兼容性核对；超预测模块的必要性、影响和回归依据在**已有报告/提示**中突出显示，不加审批门。编译、UT、testing 对实际交付作判断，不能仅改一条文案就声称所有消费者完成迁移。

### 4.3 主线二：派生关系、实施定位和结构台账（t4）

**CU 根引用归设计方，闭包由框架算。** 复用 `deriveClosure` 与 `completeChangeUnitDesignRefs`，在正常单/批接受和 `reviseChangeUnitContent` 的原 consumer 链中、完整校验和写入之前补齐已确定依赖。候选复制后派生，不暗改调用方原件；验证的必须就是随后发布的同一份产物。原批量原子语义、来源、身份与锁规则保持，自动修复也调用同一处。

作者只须表达根引用/当前切片和实质决定，已有完整 design_refs 兼容；不另增 roots 字段或第二份闭包真源。touch 的根、显式根和既有关系同源解释。未决决定、缺失目标、冲突和错误身份不能因补全而变成 constructable；原设计方处理后再发布，已授权无人值守沿现有设计恢复，不把“不能发布当前坏 CU”等同于“整单要人接手”。派生函数不新建决定、不选方案、不把 open_decision 改成已裁决。

**实施名字不是产品义务。** 下游使用源码/导出/路由关系及现有阶段报告取得当前实现定位，不能把预测 file_ref/symbol 的位置变化当作未实现。可确定时重建原派生视图；无法唯一定位时保留不确定并交原审查核对行为，不用字符串近似相等伪证等价。coding 不修改只读契约自签：公共引用与设计真正变化仍交 owner；私有定位变化作为实现事实进入原报告/有效视图，不要求回 plan 重签。保留已有未来 UT `planned:` 时序，不重做。

`file_completeness`/`plan_file_to_code` 等不再要求为被替代的预测文件创建空壳。实际必需入口或被调用符号缺失仍是缺陷；“文件存在”只说明可读取，不写成“全部实现”。业务覆盖由原 review、UT、testing 验证。

**structure-ledger 仅作过程定位。** 范围限 `structure-ledger.ts` 与直接消费、指引和去向表，不扩成全仓降级。即使 hard pixel，台账缺行/缺 how/写错实现位置也只说明账本需要补齐/重建，沿既有披露处置继续真实验证；不能据它独立断言“结构被无视”。已由源码/实际视图证实的结构缺失、错误引用、交互或视觉违约仍报真实缺陷。无法取得必要验证证据仍未完成，不用台账 WARN 或补字来代替产品验证。

### 4.4 主线三：用已有核实链交给真正的责任方（t5）

链路是：**真实产物 → AI 诊断 → 同阶段结构化问题表 → 现有 verifier 逐条核实 → 原候选/设计 owner 通道 → 责任方修订或拒修 → 原阶段复验**。不是要求机器预先认识每一种故障，更不是从 Agent 的终态文字或账本解析出授权。

#### 4.4.1 复用对象与必要接线

`repair-candidates.ts:collectReviewRepairCandidates` 已提供问题表、`issue-verification`、证据绑定、候选指纹和拒修旧结论保护。但起草时它有三处 review 专属前提：主判结论格式、`source_phase='review'`、按文件兜底为 spec/plan/coding。蓝图/CU 路径会落进 coding，混域材料不能直接成为候选；不能把“已有函数”写成 coding/UT 已可直接调用。

本批抽取/参数化**现有共同部分**，保留 review 包装和语义，以真实 source_phase 提交同款“问题清单”。产物入口须分开说明：UT 复用既有 `testability-audit@1`（`ut/testability-audit.md`）；coding 的 `skills/feature/coding/contract.yaml` 当前只 produces `source/implementation`，没有 Agent 报告，本批明确新增一个**可选上游问题产物** `coding-upstream-issues@1`，路径 `coding/upstream-issues.md`。只在有上游问题时由 coding 作者填写，复用 review 问题表格式及证据列，不要求另写完整 review 报告；无问题时不生成、不补空表，缺席不能导致 coding 不完整或阻断。

沿 `specs/artifact-schemas/inventory.yaml`、coding contract 和原 artifact resolver 作最小产物登记，明确 coding 所有权、读取位置及可选语义；它不成为必需交付义务，不触发必需产物缺失、能力缺失或新完成门禁。问题表解析与证据核实仍用现有实现，不另建问题协议。`--repair-notes` 是外层续跑输入，`headless-assumptions` 是审计账本，两者均不作为这个入口。使用本阶段已有 verifier 调用逐条核实，不额外派一轮 reviewer，不伪造 review 阶段或把 coding 主结论改为 review 专用格式。

点名读取接线：`harness/harness-runner.ts` 当前仅在 review 分支读取 `review-report.md`（起草基线约 2238 行），扩为按阶段从同一个 artifact resolver 读取 review 问题表、coding 可选产物或 UT audit，供原诊断资格、verifier 材料及 `writeRunSummaryBase` 中 `buildSummaryRepairCandidates` 消费。`phase-closure-finalizer.ts:recomputeClosureRepairCandidates` 当前约 614–619 行也只读 review 文档，须使用同一读取/解析入口，重算时读取同一阶段产物并结合当前 verifier subject 调用 `buildSummaryRepairCandidates/collectPhaseRepairCandidates`，不能只改 writer 而在 finalizer 丢掉候选。自检尚无 verifier 时只保留提案；正式 gate 核实后才形成交接。summary、script-report 的 `scope_revision_input`、runtime 返修提示沿用该结果。可选文件缺席表示本阶段无此类提案，不因此清掉已有机器候选；文件存在但证据无效不产生已核实候选。

**失败时必须进得去核实。** `verifier-plan.ts:canProduceVerifierRequest` 目前只给 review 负面结论和 UT 编译通过后的代码断言失败开放 `repair_diagnosis`，coding 编译 FAIL 会先被拒绝。不能只接候选收集函数，留下“要编译先通过才能申请修编译所依赖的契约”的死锁。沿原 `repair_diagnosis/run_verifier_for_repair`，将“本阶段已有结构化上游问题、所引诊断材料可读取且当前、verifier 已启用”接为诊断资格，装配、writer 和收口重算共用该判定，不按编译检查 ID 添加白名单。诊断只核提案及责任，真实编译/测试 FAIL 和未执行检查保持原结论；没有上游提案的普通失败照常本阶段修，不让所有 FAIL 都多跑一次核实。坏报告先走原格式纠错，缺失诊断所需材料不得伪造 confirmed，显式关闭 verifier 也不自动改配置启用。

责任从**要修的权威产物及事实**判断，不从编译报错的源文件或 Agent 自选类别直接定案。证据位置和修订目标在既有问题列中分清：涉及文件列指责任产物，问题/依据列引用具体源码、日志行、规格条目；不滥用当前仅适合 StepResult 的 `RepairEvidenceRef` 结构塞入无关数据。

spec/plan/coding 沿现有候选及 `scopeRevisionInputFromRepairCandidates`；蓝图/CU/DSL 问题接入已有 `repair_owner: external`、`design_authority`、`designOwnerBlockers` 和设计修订链，不默认归 coding，不增加 design 枚举或检查 ID 路由表。继续复用原借锁、隔离质询、正式 writer、发布/重绑及有效范围/接续判断。责任阶段在授权内但不在队列时按 28 的有效视图接回，局部请求超授权仍不能自行扩大。

#### 4.4.2 候选必须有证据

候选引用具体文件/符号、编译或测试日志位置、现行规格条目，说明为什么本阶段修不了、请求谁核实什么；可引用多个证据，但不能用一句“上游有问题”替代。独立 verifier 看实际内容与当前输入，`confirmed/refuted/unclear` 沿已有语义；机器形状和资料缺口走原报告纠错，不能仅凭格式合格认定根因正确。

真正缺的行为/资源若在当前实现职责内，应由 coding 自修，不能把复用入口当成甩锅。候选不授权写入、不改变需求、不抹掉编译/测试 FAIL；责任方修好并签发后原阶段仍须复验。`string.json` 正例必须直接修，禁止另增 missing-resource 检查或扩写集候选来绕回旧方案。

#### 4.4.3 被拒有出口、重复有边界

复用 `repair_candidate:<fingerprint>` 的原账本记录、`phase_backtrack_completed`、`loadRepairDeclineState` 与当前 subject 校验，把拒修理由交回原提案阶段。责任方拒绝候选不等于产品 PASS；原阶段收到理由后继续修自身产物或补充真实新事实，不能拿旧核实重复派同一请求。

起草时 `verifiedDeclineBasis` 只接受逐字引用目标的拒修，runtime 提示也只讲 goal conflict。复用于一般上游诊断时须补齐这处**既有拒修链**：目标冲突仍按原引文核验；“事实不成立/当前契约已有合法做法”的拒修，依据放在原 decision/报告中，由原独立核实读取所引当前产物确认后采纳。不能要求责任方编造用户原话，也不能把任意 `declined:` 当有效结论。沿用原候选身份、轮次、事件和材料，不新增拒修载体、状态或无条件豁免。设计 owner 修订链拒绝提案时同样返回原有结果和理由，不能把“未发布”伪报为修复成功。

有拒修在案且旧 verifier 没看过理由时，沿用结论不能重发候选；新的核实要把双方依据带进去。只改候选 ID、措辞、路径格式不能假装新事实。现有无进展、重复回退与总预算继续约束，同一候选无新事实不通过加轮次/换 run 循环。有效责任交接先处理，再判断原阶段是否无进展；拒修返回本身不满足产品义务，也不能让总消耗归零。

验收要走到“owner 修好后继续”和“owner 拒修后原阶段据理由修好”，不能只测产出 candidate；最后确实无法收敛时仍用原停机原因，说明具体事实、双方依据、责任方与下一步，不声称任何问题都能自动解决。
