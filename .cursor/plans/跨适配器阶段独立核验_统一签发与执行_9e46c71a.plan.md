# 跨适配器阶段独立核验

**评审稿。** 版本窗口为 3.1.0，冻结比较基线为本地 main `f8554240`。计划经评审后进入实施。

## 1. 产品目标与范围

用户在同一个宿主把 Codex 换成 DSH 后，原本需要的阶段核验会被判为 `adapter_has_no_reviewer`，连 request 都不生成，回执只记 `not_reviewed`。因此框架既用不上已有的独立执行能力，也拿不到支持通过或返修的证据。目标是让**核验的义务由阶段策略决定，执行情况由实际报告决定**。模型和运输条件仍按各适配器的真实能力处理。

本计划取代 [5ea729d4 §6](verifier减负与按项复核_5ea729d4.plan.md) 中 DSH 继续不签发、第 130 行排除 DSH 阶段 verifier 的口径。历史计划、固定包和既有验收结论按原状保留。5ea 的 request、subject、材料、报告读取、同材料复用和按项复核均继续使用。此次只补两条业务入口；设计质询、独立 Review、视觉核验各自已有的职责、技术条件和计时仍各自保留。

## 2. 统一签发和报告契约

1. 在 `resolveVerifierPlan` 移除 `adapterHasVerifierSubagent` 分支及其登记读取。profile 禁用、workflow 未声明 `verifier_prompt`、track 对应的 policy 为 off 或不适用，仍按现行口径处理；已有同材料的有效否决仍按原规则消费。能力启用以后，由现有 `canProduceVerifierRequest` 决定本轮是否签发。覆盖正常 PASS、脚本已有实质可核事实的 FAIL，以及只有环境或未执行缺口的反例。[适用与签发](../../harness/scripts/utils/verifier-plan.ts)
2. 同步修改 runner 与 check-receipt 的调用点，退役 adapter schema 的布尔字段、Claude／CodeAgent／Codex 的登记、DSH 的排除说明，以及新运行的 `verifier_not_reviewed`、`not_reviewed` 告警和更换适配器重跑指引。原 manifest、summary、receipt 中的旧字段和 reason 按既有读法兼容；旧回执 `verifier_subagent` 是历史投影。新回执不得把运行时核验写成一次命名 Task。机器继续以原报告及其绑定为裁决依据。[runner](../../harness/harness-runner.ts) · [回执读取](../../harness/scripts/check-receipt.ts) · [回执生成](../../harness/scripts/utils/receipt-scaffold.ts)
3. 执行者先按当前 request 查已有有效报告、等价材料与独立原答。能复用即消费，包括已有 FAIL；确有缺项时用同一提示和已有补核逻辑。新调用读取 request 的 `prompt_path`，返回完整报告、原发现、逐项依据和当前 subject。历史事件名、purpose 及相关夹具保留，包括 `<phase>-verifier-format-repair` 与 `verifier_format_repair`。它们已经承担实际首核。运输失败、报告不可采信时保留当前欠交义务，沿既有恢复或能力缺口处理。[独核派发](../../harness/scripts/goal-phase-runtime.ts) · [独立原答恢复](../../harness/scripts/utils/session-execution-handoff.ts) · [证据读取](../../harness/scripts/utils/verifier-evidence.ts)

## 3. 两条生产入口

### 完整交付

运行时对原工作单元和变更材料拥有调度权。有人在场时，主会话执行现有 `execute_command`、等其交回，已绑定则用 `observe_command` 续等；无人值守时由现有后台 runner 持有原调用。两者复用既有 verifier 角色、授权模型、写边界和 subject 报告。保留调用前、绑定时与交回时的写入观察，越界结果按现行规则拒收并交回责任方。[有人在场与无人值守](../../skills/reference/goal-mode-operations.md) · [原生执行器](../../harness/scripts/utils/goal-phase-executor.ts)

统一 `buildPassGuidanceLines`、`buildNextLine` 和阶段 Skill 对同一事实的说明。PASS 首审与 `run_verifier_for_repair` 都须按当前所有权路由。现有 FAIL 分支的 `outerGoalRerun` 只改变末句，应调整**整段**指引。已有活跃外层负责时，作者结束本轮，交回实际检查状态、request 和报告目标，由运行时派独核。独核 FAIL 由现有处置重算，带原报告和发现接回原作者；原 SID 可续时实际复用，原生 SID 确实失效才按既有规则恢复。在生产入口验证同一 subject 只有一方派发。仓内无生产调用的 `extractPriorFailureContext` 及其专属断言退役，仍有其他用途的诊断分类和测试保留。[两处生产指引](../../harness/harness-runner.ts) · [旧诊断辅助函数](../../harness/scripts/goal-phase-runtime.ts)

### 单阶段直跑

保留 `harness-runner --phase <phase> --feature <feature>` 作为检查和签发入口。给原 runner 增加一个显式的**执行当前已签核验并等待**操作，例如 `--execute-verifier --phase <phase> --feature <feature>`。由已有阶段 NEXT 和 Skill 在需要独核时调用；有人在场使用一条可等待的前台命令，无人值守的单阶段调用者等待同一命令。仅查状态、仅跑机器检查和重复收口保持原有语义。

- **识别原请求。** 从本阶段 summary 取 request、subject 和报告目标，用 `parseVerifierRequest` 核对身份及当前处置。已有 Goal owner 负责时交还原 owner。单阶段命令先读该 request 的原调用、绑定或已消费结果；只有确需首次派发时，才按下表取得本轮模型。已有调用直接使用其冻结绑定，前台重进或 UI 改选均不触发重新选模。[模型入口](../../harness/scripts/utils/adapter-model.ts) · [Goal 执行请求读取](../../harness/scripts/goal-mode-entry.ts)
- **执行与写界。** 从 Goal 中提取可共用的独核调用部分；两边复用 `renderStageVerifierRepairInstruction`、`loadGoalCapability`、`resolveHeadlessInvokePlan` 和 `invokeAgentHeadless` 的真实运输、终态和取消处理。使用 `resolvePhaseWriteBoundary` 传入 `executionRole: verifier`、本轮结果目标和实际工程范围，配合 `capturePhaseInvocationSnapshot`、`classifyPhaseInvocationChanges` 核对受保护写入。保留正式输入只读、迟到的旧 subject 不覆盖新结果、已有有效报告不重复调用的约束。越界或中断所留下的未获接收输出不能在下次进入时变成有效报告；沿既有原答／交回处理保全证据。仅为单阶段分派建一个 CLI 接点，共用现有核验代码和报告格式，无需制造 Goal manifest、会话类型、第二套提示、场外状态或停机 reason。[无头运输](../../harness/scripts/utils/agent-invoke.ts) · [写边界](../../harness/scripts/utils/phase-write-boundary.ts)
- **消费与结束。** 在采纳前重读 summary 和当前材料，确认仍是所签对象。完整报告走 `loadVerifierEvidence`、现行逐项诊断及 `finalizePhaseClosure`／现有收口入口。PASS 且其他义务已满足时只结束所请求阶段；独核否决或原机器 FAIL 则交回当前处置、对应阶段的返修对象和证据路径，原作者处理后按原阶段重验。报告已交回和产品已完成分别呈现。独核无法运行时返回当前未完成和实际可恢复条件。[报告与复用](../../harness/scripts/utils/verifier-evidence.ts) · [阶段收口](../../harness/scripts/utils/phase-closure-finalizer.ts)

**等待命令再次进入。** 阶段 NEXT 给出一条执行并等待的命令。首次进入时，受管执行进程在模型启动前取得同一 request 的排他执行权，核对 subject 后沿用既有调用原件、`agent_invoke_start` 和 `agent_process_bound` 等事件。执行原件和绑定存在本阶段 `reports/` 内，按原 request／subject 定位；沿用现有锁、invoke 身份、事件和原生进程核对，不另建状态枚举、会话协议或场外登记。这个进程持有模型、日志、写入观察和阶段收口；前台命令只等待并显示真实进展。复用已有独立进程启动及 containment 的相关实现，使等待进程的超时、断连或退出不传给核验执行者。Goal 的 `execute_command`／`observe_command` 提供绑定与观察语义，单阶段不能假设调用现有同步 `--execute-request` 就已获得此生命周期。[执行与观察](../../harness/scripts/goal-mode-entry.ts) · [独立进程启动](../../harness/scripts/goal-phase-runtime.ts) · [原调用核对](../../harness/scripts/utils/session-execution-handoff.ts)

用同一命令再进入时，启动中或已有存活绑定只续等原 invoke；原生回合已结束但报告待消费时接完原交回；已消费则直接返回原处置。两次同时进入也只能有一次模型派发。PID 单独不足以判活，绑定未明时观察或调和原调用。确认原执行者中断且无可采信原答时才走既有恢复。用户明确取消或达到原任务截止仍沿原绑定停止；终止等待命令不代表取消任务。

**首次派发的模型来源。** 用户明确选模时沿用原任务授权；未指定时，由当前客户端的阶段 Skill／NEXT 从当前工程、当前主会话和发起这条命令的轮次取得实际选择，带入 `launchModelPin`。可传准确原件和对应 ID，也可用既有参数转交已核实的正式模型 ID、provider、适用推理设置和原生配置来源。无人值守调用者使用同一规则或其已冻结绑定。模型目录仅用于校对；最近一次会话、模型自述和后台默认值均不能证明前台选了什么。[Goal 模型选择约定](../../skills/project/goal-mode/SKILL.md) · [模型绑定与回放](../../harness/scripts/utils/adapter-model.ts)

## 5. 覆盖与证据等级

下表是实施后的验收目标。每格的“回放”指从实际业务入口运行生产签发、选择和消费逻辑，可控制外部模型交回；“实跑”指真实 CLI 和宿主产物。所有可执行格都由同一阶段 verifier 负责，交回带 subject 的完整报告。表中的命令或后台路径表示运输与交回方式。

|---|---|---|---|---|
| claude | execute／observe，原请求交回；回放 | 后台执行并接收报告；回放并与基线配对 | 真实前台未指定模型；短例实跑、计时，并做入口回放 | 调用者等待原命令交回；回放、单次计时 |
| codeagent | execute／observe，原请求交回；回放 | 后台执行并接收报告；回放 | 前台执行至报告被消费；回放 | 调用者等待原命令交回；回放 |
