## 2. 机制现状与设计意图

- **对账的意图**：events 记下的 row_hash 是期望集，账本删行（绕 no-progress 熔断）→ `missing_row`，改行（改 decision）→ `modified_row`。诚实边界写在 `visual-rounds-ledger.ts:5-9`：运行时一致性防护，非密码学防护；stability-over-total-control 已裁「防伪造机制降纯可选」，但删行/改行检测是稳定性护栏，保留。
- **单写者的意图**（S5 / b7e4d2a9 Todo3）：正式账本只由 gate 写；agent 侧自检写 journal、gate 前由 runtime 顺序重放收编。`process-integrity.ts:127-129` 明写「GATE 标 agent 树绝不携带，残留会让 agent 自跑 harness 重新获得直写权」；`harness-runner.ts:1584-1588` 明写 `isAgentSideGoalHarness` 是账本单写者谓词。
- **冲突点**：attended 规格（`openspec/specs/harness-gates/spec.md:958-977`「Attended phase entry validates explicit goal context」）要求绑定后注入 GATE 标、`isAgentSideGoalHarness()` 为 false、「visual/device writers SHALL select their formal path」。该条写于 08-24（attended 执行者自己收口），而现行 session driver 下 runtime 在执行者之后**仍自己 spawn gate**（events:357 `harness_start`）——执行者自检与 runtime gate 同时是「正式写者」，单写者被破坏。宿主现象由此而来：自检直写账本（绕开 journal），并被迫满足正式 gate 的真装机与 device 证据绑定（04:08 那次 `FORCE_INSTALL`）。

### 3.2 修法二（兼容恢复，不替代修法一）：最后一个已提交 attempt 的孤儿行按窗口收养

只动启动对账（`goal-phase-runtime.ts:6530-6564` + `reconcileLedgerWithEvents`）。不在期望集的行，除现有 pending 收养外，满足下列全部条件也收养，并用 :6554-6564 **现成的 recovered 事件写法**补事件：

- hash 重算相符（`modified_row` 判定在前，不变）；
- `loop_id` = 本 run（既有过滤）且 `attempt_id` = 本 run **最后一个已提交**的 testing attempt（与 `collectUncommittedVisualAttemptIds` 同一遍 events 回放：启动过、且有带 `visual_attempt` 事件的 testing attempt 中取最后一个）。只取最后一个的理由（codex 二轮裁决为默认）：testing 每次入口在分配新 attempt 之前都跑这次对账（:6530 在 :6575 `totalTurns++` 之前），更早 attempt 的孤儿行早已在上一次入口 HALT 或被收养，不可能合法遗留；实证对象只有 i11；
- `at` ∈ 该 attempt 的 invoke 窗口 `[agent_invoke_start.ts, 同 invoke_id=testing-<attempt> 的最后一条事件.ts]`。起点用 `agent_invoke_start`（detached 与 session 都有；session 的 `phase_start.attempt_id` 在其后 50ms，detached 无该字段）；终点取到 gate 结算（`visual_round`/`phase_verdict`/`phase_backtrack_requested` 均带同 invoke_id），覆盖 gate 自己那行的 `at`。

宿主 i11：窗口 04:05:50.657–04:16:47.458，三行全在窗口内 → 收养 e75c/29fd。

仍 HALT：hash 不符、attempt 不是本 run 最后一个已提交 testing attempt（含更早的已提交 attempt、别的 run、不存在的 id）、`at` 在窗口外、events 期望行缺失、重复 row_hash、损坏行——现有五类判定一条不删。为何不是新机制：只扩大「可收养」的判据（窗口取自既有事件字段），不加表、不加事件类型、不加 disposition。

**规格同步（第二笔提交）**：`openspec/specs/goal-runner/spec.md:1483-1492`「Ledger receipts round-trip through summary and events with integrity reconciliation」现文把收养限定为「single most recent testing-phase invocation that has started but not yet committed」并把其余孤儿行判 stale HALT。改为「既有 pending 收养 + 本 run 最后一个已提交 testing attempt 的 invoke 窗口收养（hash 自洽、窗口取自 `agent_invoke_start` 至同 invoke_id 最后事件）」；五类完整性检查（missing / modified / stale orphan / corrupt / duplicated）与「收养行立即回写 recovery visual_round」原文保留；补三个 Scenario：最后已提交 attempt 窗口内行被收养、窗口外仍 HALT、更早已提交 attempt 的行仍 HALT。同笔更新 `visual-rounds-ledger.ts:314-328` 的 pending-only 注释。

**结算处收养**（调度原案「gate 结算时补写该 attempt 全部行」）：修法一落地后执行者自检不再直写正式账本，结算时账本里只剩 journal 收编行（已有 appended 事件）与 gate 行，**无物可收**；故不在结算处另加一遍，只保留启动对账这一处入口（单一接线）。

## 4. 疑点一：row identity 是否应含判定内容（只查清，不改）

- gate 04:16:46 的 `visual_diff` 详情：`visual_diff_capture` =「同键复用：设备截图沿用被复用 run 的产物」；指纹段 `[fingerprints] ineligible：capture_not_run`。于是 `fingerprintable=false`、`defect_fingerprints=[]`、`fail/warn` 与 04:06 那轮相同 → `base_state_hash=41efa56f…` 与 `f4f2` 相同 → duplicate。
- identity = `(loop_id, attempt_id, base_state_hash)`；base_state_hash 已含全部决定性输入（`visual-rounds-ledger.ts:100-122`）。不合格轮把指纹收敛为空集是**设计**（不合格轮不参与熔断，decision 恒 `fused:false`），同 attempt 内所有不合格轮折叠成一个状态，重放的 decision 与重算结果恒等。must_fix 文本不入 identity：它不影响 decision，入了只会让同状态因措辞变化被当成新轮。
- 结论：不是缺口。附带观察（不入本 plan）：gate 以「同键复用」不重采时，本轮 gate 对熔断是盲的；若要 gate 必采，属 device 复用策略议题。

## 4b. 疑点二：must_fix 与回退（只查清，建议单列）

- 谁写的：`device-testing/device-screenshots/visual-diff.json` mtime 04:13:25Z（i11 内、04:15 自检前），两屏 overlay 的 `must_fix` 为执行者手写的整句修复指令，对应 defect `class=shape_mismatch severity=major` 并以 `must_fix_refs` 挂接——不是 harness 规则生成。
- 档位：`spec/reports/fidelity-intent.json` = `effective_fidelity: pixel_1to1`（未被钳）、`acceptance_strictness: best_effort`；gate 的 `visual_diff` 为 **WARN/MAJOR**（非 FAIL）。
- 如何变成回退：`goal-phase-runtime.ts:2413-2460` 按 defect severity 分流——minor 不产候选（B07 D1），major/blocker 产 `visual_diff` 回修候选 → `phase_backtrack_requested reason=repair_candidates`。分流**不看** `acceptance_strictness`；而 spec 下发给 agent 的话术（`goal-phase-runtime.ts:1446-1449`）是「best_effort：质量差距记视觉债务，不硬阻断」。severity 由执行者自评。
- 结论与建议：这是「严格度承诺」与「候选分流」两处不同源——best_effort 下 major 局部样式差仍驱动回退 coding，技术死锁修好后可能因低影响偏差反复回退（codex 警告成立）。**不进本 plan**（改的是视觉回修策略，与账本单写者无关）；建议单列一件：best_effort 下 visual_diff 的 major 候选是否降为债务 + 不回退、或只回退一次后转债务，需先定口径。

## 8. 风险

- **洗白真孤儿**：窗口收养只接受「本 run 最后一个已提交 testing attempt、其 invoke 窗口内写下、hash 自洽」的行。窗口内能写账本的只有该 attempt 的执行者自检或伪造者；伪造一行需按公开算法重算 hash——这正是 §2 声明的非密码学边界。**接纳范围确实扩大了**（虽已收窄到一个 attempt）：旧规则只收最后一个未提交 attempt 的行，新规则还收最后一个已提交 attempt 窗口内的孤儿行。反例：事后向账本追加一条 `attempt_id` 指向该 attempt、`at` 回填进其窗口并重算 hash 的新行——旧规则判 `orphan_pending_stale` 拒收，新规则收养。它能做的是往该 attempt 的历史里插一轮（可能改变之后 no-progress 熔断比较的「最后一有效行」基线），做不到删行（`missing_row`）或改行（`modified_row`），这两条照旧拦截；窗口外、别的 run、更早的已提交 attempt、未提交的旧 attempt 仍 HALT。按 stability-over-total-control 裁决接受。
- **备选（不做）**：全历史已提交 attempt 的窗口收养——接纳范围更大，且无宿主需求支撑（每次 testing 入口都先对账，更早 attempt 不可能合法遗留孤儿行）。仅当出现「对账被跳过的入口」实证时再议。
- 修法一后自检**不再被迫强装**：自检可复用已装的 HAP，看到的设备结果可能来自复用安装；真值仍由 runtime gate（强装 + 唯一证据）裁决，自检只是参考——与 detached 一致。
- D1 默认取「与 detached 拉齐」，若 review 认为 attended 执行者提前 finalize 会与外层裁决冲突，改取备选并扩大影响面评估。
