# 设计取舍

## 1. 硬闸放在控制流，而不是把 reveal 事实喂给分类器

初版设计让 `unlockFailureKindOf` 接收 reveal 执行事实，再据此避免产出
`layout_unsupported`。已否决。

```
reveal ├─ failed    → 立即零输入返回 reveal_failed（不进重采样）
       └─ succeeded → 重采样 → unlockFailureKindOf(snapshot)
```

理由：分类器只应对**成功 reveal 后的 UI 快照**负责。把设备命令状态作为入参塞进布局
分类器，等于让同一个函数同时承担两种真源，而收益为零——reveal 失败时它根本不会被调用，
`layout_unsupported` 在**结构上**就产不出来，比"传参进去再判一次"更强也更简单。

## 2. 新增第四类不违反「拒绝兜底类」的既有裁决

该枚举的既有裁决是「按处置差异收敛，不按事件来源分类」，并据此驳回过 `precondition_unmet`
——因为那一类的成员（冷却、状态不明、并发抢占）处置各不相同，合成一类等于没分类。

`reveal_failed` 相反：它成员单一（reveal 命令失败/超时），处置也单一且与既有三类都不同——
排查 hdc/设备连通性。判据因此**收窄**到命令自身失败，不吸纳任何其它形态。

「可重试」在此**不含自动重试**：同一 attempt 最多 reveal 一次，不得因本类在原地重复 swipe；
重试指人工排查后经新 invocation 或 `--resume` 再来。

## 3. 不做 distance/velocity 的算术相容性断言

这是本 change 最反直觉的一条：**看起来最该写的那个断言，恰恰会给事故组合放行**。

旧组合的理论时长 921 / 300 ≈ 3.07s，**小于**其 5s 超时——任何基于理论时长的相容性校验
都会判它"相容"。真机实测却是 5.2s（差 1.7 倍，真实耗时含进程启动与通信开销）。

同类「把偶然耗时当成保证」的错误此前已犯过一次并作废（`e5d8a2c4` T3#3 的「dump 耗时即
间隔、只补差额」计时契约）。故：

- 单测只钉**结构性事实**：velocity 与 timeout 同源、velocity 在 `uitest` 合法域内、
  timeout 不低于下限；
- **不写**「任一侧被改动测试必红」——不同参数组合可能同样合法，测试不锁死常量值；
- 参数是否真的相容，**由真机验收证明**。

## 4. 用执行器注入验证同源，而不是源码正则

"velocity 与 timeout 出自同一策略"这一性质容易被写成源码正则断言。已否决：源码正则会把
错误实现一起锁死，且不构成接线验证。

改为给 `revealLockKeypad` 开一个执行器注入点（**缺省即生产实现**），单测直接驱动生产函数、
观察它实际用了什么 velocity 与什么 timeout；argv 由导出的纯函数 `buildRevealSwipeArgs` 产出，
同样可被直接断言。

与 `settle` 那个反例的区别：`settle` 的可选缺省是 **no-op**（fail-open，静默回到坏行为），
这里的缺省是**正确行为本身**，注入只改变观察方式、不改变语义。

## 5. 类型不能强制消费返回值——所以保证写在行为里

`UnlockDeps.reveal` 从 `void` 改为返回 outcome，只让事实**可用**；TypeScript 对同步函数
返回值没有 must-use 语义，调用方仍可忽略它。

（`e5d8a2c4` T3#3 把 `settle` 从可选改必填时，类型确实能强制——那是**接口字段**必填，
与"返回值必须被读取"不是一回事。早期设计稿混淆过这两者。）

因此真正的保证是行为契约 + 行为回归：reveal 失败分支之后，
`snapshot` 调用次数不再增加、`settle` 为 0、`claimAndUnlock` 为 0（正证据计数，不用排除法）。

## 6. 不新增运行期原始 dump 落盘

根因诊断不依赖它，而原始锁屏树含通知与 UI 文本，属隐私面。同批只更正
`device-readiness-deps.ts` 中「原始 dump 仅在显式校准旗标下另行落盘」这句失实注释——
代码里从来没有那个旗标（全文件零 `writeFileSync`）。将来若确需采集，应另做显式、脱敏、
用户触发的校准能力，而不是在运行期悄悄留存。
