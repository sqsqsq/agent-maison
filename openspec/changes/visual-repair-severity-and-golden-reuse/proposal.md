# visual-repair-severity-and-golden-reuse

## Why

Host run `20260906T143404Z-ab463c` (bc-openCard-1, testing-i13) ended `HALTED / backtrack_limit (2/2) / TERMINAL` although both spent backtracks were genuine repairs. The third — refused — request came from two framework-side defects visible in the code, not from the product.

**Twelve minor visual signals were converted into coding candidates, and their severity was lost on the way.** `visual-diff.json` carried 3 `warn` screens with 12 defects, **all `severity: minor`** (10 T8 findings of the B1/B2/B3/A1-unlocatable warn tiers, 2 `other` defects for reference images the viewport filter had already excluded); the verifier's notes said "measured row height matches the reference — declaration mismatch, not a rendering defect" and every must_fix started with `[owner=spec]`. `collectActionableDefects` §A filters only on screen verdict, non-empty must_fix and screenshot/build identity, then turns **every** structured defect into an actionable item; `actionableDefectsToCandidates` hard-codes `category: 'coding'`; assess sees non-empty candidates and requests `rerun_phase → coding`. The severity the verifier had recorded never reached the decision.

**Same-key testing reuse silently skipped the golden contract.** The execution key does not contain `MAISON_GOLDEN_CONTRACT`; the reuse branch pushes a `visual_diff_capture PASS "same-key reuse"` line and `runDeviceVisualDiffCapture` — where golden's forced re-capture and forbidden-evidence production live — runs only on the real-run branch. On the host the agent ran the harness with the variable unset after a golden fail-closed BLOCKER, the run was reused, and capture was recorded PASS: that PASS cannot prove the golden condition, and the evaluator's `captured_in_run` binding rightly judges it FAIL.

A third observation — the ten-screen golden contract does not match the current three-image requirement baseline — is acceptance configuration, not code; it is handled in the B06 run sheet (applicability decided before run A starts) and is out of this change.

## What Changes

**Structured visual defects are routed by their machine severity before candidate materialization.** In `collectActionableDefects` §A, a defect with `severity: minor` no longer produces an actionable item — it stays in the report WARN and the visual debt ledger (`needs_fix`, still blocking release) — and the runner logs one per-screen count. `major` / `blocker` defects materialize exactly as before: same signal identity, same fingerprint, same instruction assembly. Provider-sourced defects follow the same rule. The plain-text must_fix fallback (no structured defect) and the identity-unverified route are untouched. No defect field is added, no note or `[owner=…]` prefix is parsed, no "back to spec" routing is built.

**A T8 hard finding must not be transcribed as `minor`.** The transcription reconciliation now keeps the matched defect instead of a boolean; a hard-tier finding whose matching defect is `minor` is reported under the existing `visual_diff_finding_transcription` id with its own wording ("severity at least major") and the same ratchet as an unlogged hard finding — BLOCKER FAIL under the hard pixel contract, MAJOR WARN under best_effort — and a FAIL makes the round non-fingerprintable like an unlogged hard finding. Warn-tier findings transcribed as `minor` remain legal; the copy-paste template is unchanged.

**Same-key reuse no longer bypasses an active golden contract.** The capture block in `checkDeviceTestRunGate` becomes a local closure. The real-run branch calls it as before. The reuse branch calls it too **when `MAISON_GOLDEN_CONTRACT` resolves to targets** — only capture runs; device_test/UT are not re-executed — with the nav executor's options read from the top-level `device-test-run.meta.json` that `adoptFrozenRunArtifactsForReuse` has already restored from the reused run, so navigation starts the app the way the reused execution did. Without a golden contract the reuse branch keeps its verbatim PASS line. Both branches append `golden_contract=<sha256 prefix 16 of the contract file>` or `golden_contract=none` to the `visual_diff_capture` details so the ordinary conclusion and the golden conclusion are readable apart in one report. The golden identity does not enter the execution key: keying it would force a full device rerun whenever golden is toggled, which contradicts "capture only".

## Impact

- **Affected specs**: `goal-runner` (visual signals adjudicated before materialization — severity threshold), `visual-diff` (transcription floor for hard findings; golden capture entry on the reuse path and its disclosure).
- **Affected code**: `harness/scripts/goal-phase-runtime.ts`, `profiles/hmos-app/harness/visual-diff-check.ts`, `harness/scripts/check-testing.ts`, `MIGRATION.md`.
- **Not changed**: backtrack budget and any "budget exhausted = complete" rule; defect schema (no owner field); T8 tiers and measurement geometry; `visual_reference_viewport` exclusion of full-page images; verifier template/prompt; the ten-screen golden fixture; the evaluator CLI.
- **Breaking**: no. A `visual-diff.json` that only carries `minor` defects now yields zero candidates instead of one per defect; consumers see one extra details line on `visual_diff_capture`.
- **放弃的准确性**: (1) A real product defect that the verifier mislabels `minor` gets no coding candidate in this round — it waits in the WARN and the debt ledger for the next verifier round or a manual upgrade; in exchange a minor signal can never spend a backtrack. (2) Only hard-tier T8 findings are protected from downgrading; warn-tier B-class findings transcribed as `minor` deliberately stay out of repair, and under best_effort the downgrade is still only a WARN. (3) Reuse cannot detect an operator who unset the golden variable — the framework cannot know a golden "should" have applied; it discloses `golden_contract=none` and relies on the evaluator's run binding (existing) to fail such a PASS. Tamper resistance is not a priority.
