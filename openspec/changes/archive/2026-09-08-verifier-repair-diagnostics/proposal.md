# verifier-repair-diagnostics

## Why

Two product failures that the framework already knows how to route cannot reach the router.

**F01 — the repair loop depends on the verifier, and the verifier is unreachable on failure.** `harness-runner` assembles `ai-prompt.md` (Step 4) and issues the verifier request (`writeRunSummaryBase`) only when the script verdict is `PASS`. Review's `negative_verdict_closure` / `conditional_pass_closure` and UT's real assertion failure are BLOCKER FAILs — so no request is issued. But `collectReviewRepairCandidates` requires the verifier's per-issue `confirmed`, and the UT coding candidate requires `end_to_end_driving` and `business_assertion_value` to be PASS. The conjunction can never hold, `repair_candidates` stays empty, `assess` sees no deterministic defect, and the run re-tries the same phase until the budget is gone. The production writer reproduces it exactly: `report_validity=PASS`, `verdict=FAIL`, `request=null`, `repair_candidates=[]`, `next_action=fix_blockers_then_rerun`.

The UT half has a second break underneath it. `buildUtHvigorTestFailDetails` classifies toolchain, signing, install and device-blocked failures, but an ordinary assertion failure falls through to the default branch and returns `failureKind: undefined`, with no `失败归因：` line in `details` either. So even a genuine "the tests ran and the product failed them" result carries no machine attribution, and the `code_regression` conjunction is unreachable through the real production path — only hand-written fixtures ever satisfied it.

**F02 — the formal report format and the parser disagree.** `verify-*.md` §7.1 requires a summary table with one row per check (PASS rows included); §7.2's YAML block lists **only** non-PASS items. `parseVerifierCheckStatus` reads only the YAML `- id: / status:` shape. A verifier that follows the prompt therefore produces a report in which no PASS is machine-readable — `end_to_end_driving: PASS` is invisible, and the UT coding candidate is zero. A verifier that ignores the prompt and dumps every item into YAML produces candidates. Same conclusion, two different machine outcomes.

**F09 (the named subset) — instructions that contradict shipped behavior.** The plan/coding Skills and `agent-behavioral-principles` still demand "default MUST subagent" and `source_code_paths ≥ N` for phases where the gate only checks a non-empty `## phase_delta:` section; the goal runtime prompt still calls post-review product source "attestation-locked (BLOCKER)" when both `review_closure_attestation` and `ut_no_src_mutation` have been graded WARN since 07a41ec6 T8; `device-testing-workflow-detail` still demands `region_attest` / critic receipts unconditionally although the no-provider exemption is implemented; `verify-ut.md` still calls `ut_no_src_mutation` a BLOCKER. Each one sends a weak model to satisfy something no gate checks, or to re-impose a gate that was retired.

## What Changes

**A product failure that the harness can diagnose gets a verifier request.** One new pure predicate, `canProduceVerifierRequest` in `verifier-plan.ts`, decides request eligibility from the resolved plan, the phase, the script verdict/checks, `report_validity` and the existing `has_blocked` projection. Step 4 and the summary writer both call it — one implementation, no second judgement. It opens exactly two doors, both reproduced in production:

- **review**: script FAIL, `report_validity=PASS`, at least one BLOCKER FAIL, every BLOCKER FAIL is `negative_verdict_closure` or `conditional_pass_closure`, no BLOCKER SKIP, no blocked capability;
- **ut**: script FAIL, UT compile PASS, UT run FAIL attributed `code_regression`, nothing else FAILing or SKIPping at BLOCKER, `report_validity ≠ FAIL`.

Everything else — missing source, broken tables, compile/device/toolchain failures, mixed negative-plus-material failures, INCOMPLETE — keeps the existing "fix the input or the environment first" exit. Attribution is read `failure_kind` first, falling back to the existing `extractFailureClassification(details)` parser; structured device/toolchain classification wins over text.

**The product verdict does not move.** FAIL stays FAIL, exit 1, `closure_status=open`. One new action string, `run_verifier_for_repair`, is added to the existing `next_action` — not a phase, not a state machine. It is decided first in `decideNextAction` so the UT panel's `can_claim_done=NO` cannot swallow it, and rendered first in `buildNextLine` so the failure console names the request path, the report path and the follow-up command. Under goal orchestration the follow-up is "return; the outer runner re-runs the gate harness"; otherwise it is "re-run this phase's harness once".

**The diagnosis is stated in the prompt, and the receiving end is told what to do with it.** `assembleAIPrompt` gains an in-memory option that appends a "this round is a product-failure diagnosis" section naming the released checks — no new request field, no persisted mode. The verifier still reads the raw FAIL report; it is never projected into a fake PASS. `verifier.md` and `verify-ut.md`'s precondition 6 are amended so the diagnosis request permits the semantic checks instead of collapsing to `verdict=FAIL`; `verify-review.md` states the counting rule explicitly. The terminal-state contract is unchanged and now written down in both branches: `blocker_count` counts **this round's own** BLOCKER-severity semantic FAILs, `verdict=PASS` iff it is zero. Confirmed product defects do not enter the count — a report that accurately confirms three defects is `PASS / 0`, and the product summary is still FAIL/open.

**The real UT attribution is produced.** `checkUtHvigorTest`'s final failure return fills `failure_kind: 'code_regression'` only when every selected module produced a real execution result and every failing module actually ran, produced cases (`total > 0`), failed some (`failed > 0`) with concrete failures, and shows no `toolMissing` / `timedOut` / non-`clear` `installBlocking` / structured on-device failure evidence. Otherwise the formatter's own attribution (or `unknown`) stands. `details` keeps the real formatter text — no log rewriting to satisfy a regex.

**The parser reads the formal output.** `parseVerifierCheckStatus` reads the §7.1 summary table through the shared `extractTables`, requiring exact `id` / `status` headers, and keeps the legacy YAML shape. Only PASS/FAIL/WARN count; consistent duplicates dedupe; conflicts and malformed statuses are not accepted (never resolve to the favourable PASS) and fall through each consumer's existing "unconfirmed" path. `end_to_end_driving`, `business_assertion_value` and `device_ac_delegation` share this one parser.

**The stale instructions named above are aligned with shipped behavior** — only the sentences that contradict code, not a rewrite. The establishing-phase thresholds, the subagent requirement where it still applies, the ban on test shortcuts, the ban on editing product source from UT, and the with-provider visual obligations all stay.

## Impact

- **Affected specs**: `harness-gates` (request eligibility for diagnosable product failures; the `run_verifier_for_repair` action and its ordering; verifier check-status parsing equivalence), `feature-artifact-layout` (the terminal-state counting contract and the diagnosis prompt section), `agent-adapters` (the verifier subagent template's dispatch precondition; no capability declaration changes).
- **Affected code**: `harness/scripts/utils/verifier-plan.ts`, `harness/harness-runner.ts`, `harness/scripts/utils/report-generator.ts`, `harness/scripts/utils/repair-candidates.ts`, `harness/scripts/goal-phase-runtime.ts`, `profiles/hmos-app/harness/ut-host-impl.ts`, `agents/claude/templates/agents/verifier.md`, `agents/claude/templates/agents/phase-executor.md`, `agents/claude/templates/hooks/check-phase-completion.mjs`, `harness/prompts/verify-ut.md`, `harness/prompts/verify-review.md`, the six feature `SKILL.md` verifier sections, `skills/reference/agent-behavioral-principles.md`, `skills/reference/device-testing-workflow-detail.md`.
- **Phases affected**: `review` and `ut` gain the narrow diagnosis path; every phase keeps its existing PASS path unchanged.
- **Breaking**: no. `disabled`, the PASS path, the request/report protocol, the terminal-block contract, adapter capability declarations and the closure gate are untouched. Consumers re-materialize `.claude/agents/verifier.md`, `phase-executor.md` and the Stop hook to pick up the amended dispatch preconditions; an un-refreshed instance simply keeps refusing to dispatch on script FAIL, which is the pre-change behavior.
- **放弃的准确性**: (1) only the two reproduced failure shapes are opened — other diagnosable failures still need new evidence before they are added, so some product failures keep waiting on a human; (2) the diagnosis request cannot prove the verifier read the FAIL report honestly rather than rubber-stamping it — the guard is the unchanged product verdict plus the per-issue `confirmed` conjunction, not tamper-proofing; (3) a report that is neither a formal table nor legacy YAML remains unparseable and must be rewritten — the parser will not guess, and on conflict it refuses rather than picking PASS; (4) `code_regression` is inferred from the absence of environment evidence, so an on-device failure mode with no structured evidence field could still be misread as a product defect — it only unlocks a semantic review, never a product verdict.
