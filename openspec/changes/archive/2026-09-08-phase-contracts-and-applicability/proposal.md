# phase-contracts-and-applicability

## Why

**F08 — an explicitly configured evidence profile is silently discarded outside interactive mode.** `resolveEvidencePolicy` returns `STRICT_EVIDENCE` whenever `ctx.mode !== 'interactive'`, before the `config` argument is consulted at all; `resolveProfileLabel` has the same shape. Production only ever assembles two modes — `goal` and `interactive` — so a host that writes `evidence_profile: "balanced"` into `framework.config.json` gets strict on every goal-orchestrated run, with no diagnostic saying the declaration was dropped. The declaration is the user's own; the framework either honors it or must say it will not.

**Turning an axis off is not the same as ignoring what that axis already found.** Under `disabled`, `check-receipt` writes `skipped_by_policy` without ever calling the evidence loader, and the summary writer's `resolveVerifierEvidenceState` returns `not_applicable` on its first line. The writer then anchors the repair-candidate body, the `next_action` branch and the three `verifier_*` summary fields to "the subject issued this round" — which is null. So a valid, self-consistent verifier FAIL report sitting on the same material is dropped four times over, and a passing script gate releases the phase. That converts "buy less evidence work" into "wash out a negative conclusion that already exists".

**A `trace.json` that is corrupt on disk can be hidden by one line of the receipt.** The legacy receipt branch decides whether to read the file from `trace_json.exists` / `trace_json.path`. With a corrupt trace at the canonical path and `trace_json: {}` in the receipt, strict still trips its `exists=false` blockers, but the `optional` tier records only a missing-WARN. "Provided but broken is always a BLOCKER" therefore does not hold on that path. The slim branch has read the canonical path directly all along.

**Plan has no way to say "this feature genuinely has none of these".** `data_model_typed`, `interface_signatures_complete` and `component_tree_per_page` accept only a code block. A pure-logic feature with empty `data_models` / `interfaces` / `components` in `contracts.yaml` leaves the author fabricating an empty `interface` to pass the gate.

**verify-ut judges assertion count.** Check 4B item 5 fails a case for "only one expect", so one precise assertion that fully verifies a pure function is a BLOCKER FAIL while three `assertLargerThan(0)` calls pass. The script-side heuristic for the same idea has been a MAJOR WARN for some time; only the prompt still hard-fails on the number.

**Three shipped instructions contradict the code they describe** — the `ut_no_src_mutation` exit path, the `review_closure_attestation` gate, and that gate's own JSDoc, all of which have been graded WARN since 07a41ec6 T8; plus a runbook precondition that predates the harness generating the testing report itself.

## What Changes

**The declared profile is honored in every mode.** The two mode early-returns are deleted. Nothing else moves: the "config is not balanced → STRICT" branch already carries every default case, so a project without the field resolves identically in all three modes. Under balanced the two axes shrink by **different scopes** and both are stated separately: `verifier` is `off` outside the retained `{spec, coding}` set (four feature phases), while `trace` drops to `optional` for **all six** feature phases including the retained ones. `receipt` is `not_applicable` in both tiers and `exploration` stays `required`.

**Policy off means "not required", never "ignored".** When the axis is off, the writer looks for the subject recorded by the previous round and carries it forward only if the report validates (subject echoed, verdict self-consistent), the verdict is not PASS, and the **material identity still holds**: the material view written when that subject was issued (`verifier.material.<subject>.json`) must still match this round's recomputed, policy-independent material face on three counts — phase input/output file hashes, `gate_fingerprint`, and the script-report projection. Changing `evidence_profile` is not a material change, so a FAIL recorded under strict survives the switch to balanced; changing a phase input or output releases it. (`source_commit_sha` and `worktree_digest` are deliberately not used: they left the subject derivation long ago, and `worktree_digest` covers `framework.config.json`, so keying on them would drop a valid FAIL on the config switch alone. Prompt template, phase-rule text and context files cannot be recomputed once the axis is off and are explicitly excluded — a change there still carries the old FAIL, which over-vetoes rather than under-vetoes.) When carried, the evidence state is `fail`, the candidate body is read from that subject, `next_action` resolves the fail branch **before** the disabled early-return, and the summary keeps `verifier_subject_id` and `verifier_report` (no `verifier_request` — nothing was issued). `check-receipt` then keeps its existing `verifier_not_pass` BLOCKER. No report, or a PASS report, means zero requirement — that is what balanced buys. No new check id, no new state member.

**The receipt stops deciding whether the trace is read.** The legacy branch resolves `trace.json` from the canonical path on disk first and falls back to the declared path only when the canonical file is absent; missing-versus-broken keeps its existing severities, and a `schema_valid: false` self-report no longer skips the parse of a canonical file.

**Plan gains a "not applicable, with stated grounds" exit, guarded by source trustworthiness.** One shared pure function decides it for all three checks. It applies only when the section carries a "not applicable: <grounds>" line **and** `featureSpec.contracts` is mounted (absent or unparseable `contracts.yaml` never mounts), **and** no `shape_issues` entry points at that collection. All three must hold; otherwise it returns null and every existing judgement stands unchanged. Empty collection produces `SKIP` at the check's existing severity, with the criterion and the author's grounds in `details`. Non-empty collection is a false claim: `FAIL` at the same severity, naming the contract entries, with a suggestion. Chapter presence itself is still required by `required_chapters`.

**Count becomes a clue, not a criterion.** verify-ut's 4B item 5 is rewritten around "would this `it` fail if the code were wrong" and "does it cover the rule's boundary/exception"; the "tested the wrong object" branch survives because it is not about count. Because the count rule alone is not enough, check 4 item 1 and 4B item 2 each gain an applicability scope: for a **pure-function / single-rule** case (no data_boundary double, no multi-stage transition) the call-sequence and intermediate-state requirements are **not applicable** rather than unmet. **Flow cases keep all three requirements verbatim.** Shape is decided from the code under test, not from the author's claim. The two `it_drives_flow` suggestions stop pointing at a number; its severity, status and predicate are untouched.

**The three contradicting sentences are aligned with the code**, plus one runbook precondition. Descriptions only — no requirement changes.

## Impact

- **Affected specs**: `runtime-policy` (evidence matrix resolution across modes; the pure-resolver scenario for strict), `harness-gates` (the plan applicability exit and its source-trust preconditions).
- **Affected code**: `harness/scripts/utils/runtime-policy.ts`, `harness/config.ts`, `harness/harness-runner.ts`, `harness/scripts/check-receipt.ts`, `harness/scripts/check-plan.ts`, `harness/scripts/check-ut.ts`, `harness/prompts/verify-ut.md`, `harness/scripts/check-testing.ts` (JSDoc), `skills/reference/business-ut-workflow-detail.md`, `skills/reference/device-testing-workflow-detail.md`, `docs/operations/goal-mode-runbook.md`, `MIGRATION.md`.
- **Phases affected**: `plan` gains the applicability exit; `plan` / `review` / `ut` / `testing` lose the verifier axis **only** under an explicit balanced declaration; all six feature phases drop trace to optional under that same declaration.
- **Breaking**: no. A project that does not write `evidence_profile` resolves identically to before in all three modes. `balanced_verifier_retained_phases` stays unwired (no `FrameworkConfig` field), so the retained set is the default `{spec, coding}`.
- **放弃的准确性**: (1) under goal×balanced the four phases get no semantic verifier review — script gates, compile/execute, contract closure and drift judgement all still run, but "did the implementation actually solve the need" has no second pair of eyes there; (2) trace can be absent on the two phases that still require a verifier, so the run cannot be reconstructed from trace afterwards; (3) the carried-forward veto compares only the three policy-independent faces of the material view — manifest file hashes (both directions, so a deleted optional input counts as a change), `gate_fingerprint`, and the `script_checks` projection; the prompt template, the phase-rule text and `contextFiles` (source, cases, images) cannot be recomputed while Step 4 is switched off and are explicitly excluded, so an edited template or edited reviewed source still carries the old FAIL (over-veto, not under-veto); clearing it requires a strict round in which the verifier retracts its own conclusion; (4) the applicability exit only checks whether the contracts collection is empty, so an author who both under-declares contracts and writes the not-applicable line is not caught; (5) `component_tree_per_page` judges on `contracts.components` as a whole and does not guess the `kind` field, so a feature with components but no pages keeps the existing judgement; (6) with the count rule gone the verifier leans harder on semantic judgement for shell tests — the `it_drives_flow` WARN and the flow-case requirements are the offset.
